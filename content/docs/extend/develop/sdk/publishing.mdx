---
title: "SDK publishing"
description: "How Ryu verifies and publishes its TypeScript, Rust, native, and language-binding SDKs."
---

The public SDK hub publishes the SDK packages from one versioned Ryu release train. The source,
tests, examples, generated bindings, and release workflow live in
[`amajorai/ryu-sdk`](https://github.com/amajorai/ryu-sdk); the monorepo remains the canonical input
to that generated tree.

## What is published

### npm

- `@ryuhq/sdk` - authoring factories, manifest builders, MCP adapters, and the `ryu` CLI.
- `@ryuhq/client` - a fetch-based Core client for embedded agent chat plus the standalone Notify API.
- `@ryuhq/core-client` - typed Core and Gateway domain modules.
- `@ryuhq/protocol` - shared protocol and wire helpers.
- `create-ryu-app` - project templates for plugins and Ryu Apps.
- `@ryuhq/sdk-native` - the platform-specific Node-API package used by the model client.

### crates.io

- `ryu-kernel-contracts` - the shared pure-data manifest and host contracts.
- `ryu-sdk` - the Rust SDK kernel.
- `ryu-sdk-ffi` - the C-ABI surface used by C and Go consumers.
- `ryu-sdk-uniffi` - the UniFFI surface used by Python, Swift, Kotlin, and C#.

### PyPI

- `ryu-sdk` - the platform wheel for the generated Python/UniFFI binding. Each wheel carries the
  matching native library for Linux x64, macOS x64/arm64, or Windows x64.

Install it with:

```bash
python -m pip install ryu-sdk==0.3.0
```

### NuGet

- `Ryu.Sdk` - the generated C# binding with native assets for Linux x64, macOS x64/arm64, and
  Windows x64.

```bash
dotnet add package Ryu.Sdk --version 0.3.0
```

### Java / Maven Central

`com.ryu:ryu-client` is the application-facing Java 17 client library. Its source and Maven
project live at `bindings/java` in the public SDK hub. It is published to Maven Central by the
release workflow and calls Core over HTTP without requiring a Rust or UniFFI runtime in the Java
application.

```xml
<dependency>
  <groupId>com.ryu</groupId>
  <artifactId>ryu-client</artifactId>
  <version>0.3.0</version>
</dependency>
```

### Source-distributed bindings

Go, Swift, and Kotlin do not have a single upload registry that can carry the generated native
library for every target without introducing a second platform-specific package design. They are
kept as versioned source bindings in the public SDK hub: Go is consumed as a Go module, Swift as a
Swift Package, and Kotlin from the generated Gradle project. Their release workflow still builds
and tests them from the same UniFFI/FFI sources.

### React Native / Expo

React Native uses the published TypeScript client libraries rather than a Node-API binding:
`@ryuhq/client` for embedded chat and `@ryuhq/core-client` for the full Core surface. Expo apps
can inject `expo/fetch` when they need response-body streaming. See [Client SDK](/docs/extend/develop/sdk/client)
and [Core client](/docs/extend/develop/sdk/core-client).

## Verification order

The release workflow performs credential-free verification before any registry publish step:

1. Check that the requested release tag matches the package/crate version.
2. Install the committed lockfile with lifecycle scripts disabled.
3. Build the native Node-API addon and the TypeScript packages.
4. Run TypeScript package tests, contract tests, Rust format/tests, Java tests, and the foreign
   binding smoke suites.
5. Build the NAPI addon, Python wheels, and C# native assets for the supported release targets.
6. Publish npm packages, Rust crates, the PyPI wheel set, the NuGet package, and the Maven Central
   Java library in dependency order.

The registry credentials are scoped to the release environment and introduced only by the final
publish steps. A dependency install, generator, test, or package build never receives a registry
credential. If a registry credential is absent, verification remains useful and the publish run
fails at the explicit credential gate rather than claiming a publication occurred.

The `release` environment needs `NPM_TOKEN`, `CARGO_REGISTRY_TOKEN`, `PYPI_API_TOKEN`,
`NUGET_API_KEY`, `MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_TOKEN`, `MAVEN_GPG_PRIVATE_KEY`, and
`MAVEN_GPG_PASSPHRASE`. Maven Central requires a verified `com.ryu` namespace and signed
artifacts; the Portal token is not the web-login password.

## Dispatch-only releases

The hub's [`release.yml`](https://github.com/amajorai/ryu-sdk/blob/main/.github/workflows/release.yml)
is dispatch-only. It rides the Ryu release train and does not mint an independent automatic SDK
version. A maintainer supplies the Ryu tag and must turn on the `publish` confirmation before
registry writes are attempted.

This matters because a source mirror can be synchronized more than once. A mirror commit is not a
package release, and a successful build is not proof that npm or crates.io accepted an artifact.
Check the registry package/version pages and the workflow result separately after a release.

## Version changes

SDK packages and crates move with the Ryu release train. A public API or binding change must update
the relevant Fumadocs page, examples, generated artifacts, compatibility notes, and focused tests.
Breaking changes require an explicit compatibility or migration note. Do not manually edit a
generated binding file or publish a package at a version different from the rest of the train.
