The public SDK hub publishes the SDK packages from one versioned Ryu release train. The source,
tests, examples, generated bindings, and release workflow live in
[`amajorai/ryu-sdk`](https://github.com/amajorai/ryu-sdk). The Ryu monorepo is the canonical input
to that generated tree. Every package and crate in the train carries the same version (currently
`0.4.0`).

## What is published

### npm

- `@ryuhq/sdk` - authoring factories, manifest builders, MCP adapters, and the `ryu` CLI.
- `@ryuhq/client` - a fetch-based Core client for embedded agent chat plus the standalone Notify API.
- `@ryuhq/core-client` - typed Core and Gateway domain modules.
- `@ryuhq/protocol` - shared protocol and wire helpers.
- `create-ryu-app` - project templates for plugins and Ryu Apps.
- `@ryuhq/sdk-native` - the platform-specific Node-API package used by the model client.

### crates.io

- `ryu-kernel-contracts` - the shared pure-data manifest and host contracts.
- `ryu-sdk` - the Rust SDK kernel.
- `ryu-sdk-ffi` - the C-ABI surface used by C and Go consumers.
- `ryu-sdk-uniffi` - the UniFFI surface used by Python, Swift, Kotlin, and C#.

<Callout type="warn">
The release workflow can publish the packages below, but `ryu-sdk` (PyPI), `Ryu.Sdk` (NuGet), and
`com.ryu:ryu-client` (Maven Central) are not published yet. Their install commands work only after
the first release that publishes them.
</Callout>

### PyPI

- `ryu-sdk` - the platform wheel for the generated Python/UniFFI binding. Each wheel carries the
  matching native library for Linux x64, macOS x64/arm64, or Windows x64.

Install it with:

```bash
python -m pip install ryu-sdk==0.4.0
```

### NuGet

- `Ryu.Sdk` - the generated C# binding with native assets for Linux x64, macOS x64/arm64, and
  Windows x64.

```bash
dotnet add package Ryu.Sdk --version 0.4.0
```

### Java / Maven Central

`com.ryu:ryu-client` is the application-facing Java 17 client library. Its source and Maven
project live at `bindings/java` in the public SDK hub. The release workflow publishes it to Maven
Central. It calls Core over HTTP and needs no Rust or UniFFI runtime in the Java application.

```xml
<dependency>
  <groupId>com.ryu</groupId>
  <artifactId>ryu-client</artifactId>
  <version>0.4.0</version>
</dependency>
```

### Source-distributed bindings

Go, Swift, and Kotlin have no single upload registry that can carry the generated native library
for every target without a second, platform-specific package design. They ship as versioned
source bindings in the public SDK hub. Go is consumed as a Go module, Swift as a Swift Package,
and Kotlin from the generated Gradle project. The hub's CI builds and tests them from the same
UniFFI and FFI sources.

### React Native / Expo

React Native uses the published TypeScript client libraries rather than a Node-API binding:
`@ryuhq/client` for embedded chat and `@ryuhq/core-client` for the full Core surface. Expo apps
can inject `expo/fetch` when they need response-body streaming. See [`@ryuhq/client`](/docs/extend/develop/sdk/client)
and [`@ryuhq/core-client`](/docs/extend/develop/sdk/core-client).

## Verification order

The release workflow performs credential-free verification before any registry publish step:

1. Check that the requested release tag matches the SDK version.
2. Install the committed lockfile with lifecycle scripts disabled.
3. Build the native Node-API addon and the client package.
4. Run the TypeScript type checks and package tests, the Java tests, and the Python and C# binding
   tests. Package `ryu-kernel-contracts` and check the `ryu-sdk`, `ryu-sdk-ffi`, and
   `ryu-sdk-uniffi` crates.
5. With `publish` on, build the NAPI addon, Python wheels, and C# native assets for the supported
   release targets.
6. Publish the PyPI wheel set, the NuGet package, the Maven Central Java library, and the Rust
   crates (in dependency order). npm packages publish after the native addon package.

Registry credentials are scoped to the `release` environment and enter only in the final publish
steps. A dependency install, generator, test, or package build never receives a registry
credential. If a credential is absent when `publish` is on, the run fails at an explicit
credential gate instead of reporting a publication.
Maven Central artifacts are signed.

## Dispatch-only releases

The hub's [`release.yml`](https://github.com/amajorai/ryu-sdk/blob/main/.github/workflows/release.yml)
is dispatch-only. It rides the Ryu release train and does not mint an independent automatic SDK
version. A maintainer supplies the Ryu tag and must turn on the `publish` confirmation before
registry writes are attempted.

A source mirror can be synchronized more than once, so a mirror commit is not a package release. A
successful build does not prove that npm or crates.io accepted an artifact. After a release, check
the registry package and version pages and the workflow result separately.

## Version changes

A public API or binding change must update the relevant docs page, examples, generated artifacts, compatibility notes, and focused tests.
Breaking changes require an explicit compatibility or migration note. Do not manually edit a
generated binding file or publish a package at a version different from the rest of the train.
