`@ryuhq/sdk` (`packages/sdk/`) is Ryu's developer SDK. You author governed Actions and Runnables
(agents, workflows, tools, and skills) as typed TypeScript, declare them in a `manifest.json`, and
pack the result into a publish-ready bundle. The one invariant is that **every model call routes
through the Gateway**.

The public source, binding projects, examples, tests, and release automation are collected in the
[`amajorai/ryu-sdk` public hub](https://github.com/amajorai/ryu-sdk). This Fumadocs section remains
the narrative API and integration reference for that hub.

This is the API reference. For a guided walkthrough that builds a plugin end to end, see
[TypeScript SDK](/docs/extend/develop/extensions/typescript-sdk). For the `manifest.json` schema, lifecycle
endpoints, and signing, see [Plugin manifests](/docs/extend/develop/extensions/plugin-json-manifest) and
the [Plugin API](/docs/extend/develop/sdk/plugin-api).

`@ryuhq/sdk` is the **authoring** layer. To **operate** a running Core node — install plugins,
manage agents/models/skills/MCP/spaces/workflows — the desktop app, CLI/TUI, and mobile app share
[`@ryuhq/core-client`](/docs/extend/develop/sdk/core-client). To embed agent chat, see
[`@ryuhq/client`](/docs/extend/develop/sdk/client).

For the complete package map and local verification commands, see [Public SDK hub](/docs/extend/develop/sdk/hub).

<Callout type="warn">
  The model client depends on the native addon `@ryuhq/sdk-native`, so a model call only runs where
  that addon has been built. Action authoring, manifest validation, and the MCP adapter are pure
  TypeScript and do not require the addon.
</Callout>

## Package layout

The package (`packages/sdk/package.json`) exposes a subpath per concern in its `exports` map:

| Subpath | Resolves | Holds |
|---|---|---|
| `.` | the main API | factories, builders, model client, manifest types and schemas |
| `./manifest` | the manifest schema | `PluginManifestSchema` and the manifest types |
| `./runnable` | the Runnable factories | `defineAgent`, `defineWorkflow`, `defineTool`, `defineSkill` |
| `./action` | the governed Action contract | `defineAction` |
| `./builder` | the fluent builders | `PluginBuilder` plus per-kind builders |
| `./model` | the model client | `defineModel`, `ModelClient` |
| `./agent` | the agent factory | `createAgent`, `query`, `ryuTool` |
| `./plugin` | the plugin facade | `definePlugin` / `defineApp` internals, `toDisposable` |
| `./agent-plugin` | Agent Plugins interop | the Agent Plugins v1 `plugin.json`/`mcp.json` emission |
| `./mcp` | the MCP bridge | `McpServer`, `listTools`, `callTool` |
| `./mcp/server` | the stdio server | `McpServer` |
| `./mcp/client` | the stateless client | `listTools`, `callTool` |
| `./cli` | the `ryu` CLI | also installed as the `ryu` bin |

The MCP bridge (`McpServer`, `listTools`, `callTool`, `MCP_PROTOCOL_VERSION`, `unwrapContent`) is a
first-class public export (`packages/sdk/src/mcp/`); see [MCP bridge](#mcp-bridge) below.

## The Runnable contract

Every factory returns a value satisfying one shared interface (`packages/sdk/src/runnable/runnable-types.ts`).
The four kinds are peers, not a hierarchy: an agent lists a workflow as a tool, a workflow lists an
agent as a step.

```typescript
interface Runnable<TInput = unknown, TOutput = unknown> {
  readonly id: string;
  readonly kind: "agent" | "workflow" | "tool" | "skill";
  readonly name: string;
  run(input: TInput, ctx: RunnableContext): Promise<TOutput>;
}

interface RunnableContext {
  gateway: GatewayClient;   // the only allowed path to a model; never null
  sessionId?: string;       // optional Core session id for stateful runs
  signal?: AbortSignal;     // optional abort for long-running runs
}

interface GatewayClient {
  chat(messages: ChatMessage[]): Promise<ChatResult>;
  stream(messages: ChatMessage[]): AsyncGenerator<ChatDelta>;
}
```

`RunnableContext` always carries a `gateway`. There is no way to construct a context without one, so
a Runnable cannot reach a model except through the Gateway. See
[Gateway enforcement](#gateway-enforcement) below for how that is guaranteed at construction time.

## Runnable factories

The four kind factories take an options object and return a `Runnable` with a fixed `kind`. The
semantic `defineAction` facade is also exported from `.` (`packages/sdk/src/runnable/`).

| Factory | `kind` | Distinct option | Returns |
|---|---|---|---|
| `defineAction` | `tool` | description, input/output schema, effect, approval | `ActionRunnable<TInput, TOutput>` |
| `defineAgent` | `agent` | `tools?: readonly Runnable[]` | `Runnable<TInput, TOutput>` |
| `defineWorkflow` | `workflow` | `steps?: readonly Runnable[]` | `Runnable<TInput, TOutput>` |
| `defineTool` | `tool` | `schema: ToolSchema` (required) | `ToolRunnable<TInput, TOutput>` |
| `defineSkill` | `skill` | none | `Runnable<TInput, TOutput>` |

Every options object shares `id`, `name`, and `run(input, ctx)`.

### defineAgent

```typescript
function defineAgent<TInput, TOutput>(options: {
  id: string;
  name: string;
  run(input: TInput, ctx: RunnableContext): Promise<TOutput>;
  tools?: readonly Runnable[];
}): Runnable<TInput, TOutput>;
```

Creates a `kind: "agent"` Runnable. The optional `tools` array lists other Runnables (including
workflows) the agent can invoke as named tools.

```typescript
const myAgent = defineAgent({
  id: "agent-researcher",
  name: "Researcher",
  async run({ query }, ctx) {
    const result = await ctx.gateway.chat([{ role: "user", content: query }]);
    return { answer: result.content };
  },
});
```

### defineWorkflow

```typescript
function defineWorkflow<TInput, TOutput>(options: {
  id: string;
  name: string;
  run(input: TInput, ctx: RunnableContext): Promise<TOutput>;
  steps?: readonly Runnable[];
}): Runnable<TInput, TOutput>;
```

Creates a `kind: "workflow"` Runnable that orchestrates other Runnables as steps. A step is any
`Runnable` (`WorkflowStep` is an alias), invoked directly with `step.run(input, ctx)`.

### defineTool

```typescript
function defineTool<TInput extends Record<string, unknown>, TOutput>(options: {
  id: string;
  name: string;
  schema: ToolSchema;        // JSON Schema, type: "object"
  run(input: TInput, ctx: RunnableContext): Promise<TOutput>;
}): ToolRunnable<TInput, TOutput>;
```

Creates a `kind: "tool"` Runnable with a JSON Schema. The input is validated against the schema at
`run` time, so a missing required field or a primitive-type mismatch throws a descriptive `Error`
naming the failing field before the body executes. Tools do not require a model call, but if one is
needed it must use `ctx.gateway`.

`ToolRunnable` extends `Runnable` with a public `schema` field. The schema types are:

```typescript
interface ToolSchema {
  type: "object";
  properties: Record<string, JsonSchemaProperty>;
  required?: string[];
}

interface JsonSchemaProperty {
  type: "string" | "number" | "integer" | "boolean" | "array" | "object";
  description?: string;
  enum?: unknown[];
  items?: JsonSchemaProperty;
  properties?: Record<string, JsonSchemaProperty>;
  required?: string[];
}
```

### defineAction

```typescript
function defineAction<TInput extends Record<string, unknown>, TOutput>(options: {
  id: string;
  name: string;
  description: string;
  schema: ToolSchema;
  outputSchema?: Record<string, unknown>;
  effect: "read" | "mutate";
  needsApproval?: boolean;
  run(input: TInput, ctx: RunnableContext): Promise<TOutput>;
}): ActionRunnable<TInput, TOutput>;
```

`defineAction` is the canonical authoring contract for a business operation. It returns a Tool
Runnable for compatibility with Core, but adds the metadata that makes the operation explicit to
Ryu's governed runtime:

- `effect: "read"` lowers to `readOnlyHint: true`.
- `effect: "mutate"` lowers to `destructiveHint: true`.
- `needsApproval: true` makes the existing Core approval gate queue the call before dispatch.
- `outputSchema` is preserved for structured MCP/Core results.

The Action can run in-process through `action.run(input, ctx)`, adapt to the SDK MCP server with
`action.toMcpTool(ctx)`, or lower to an installable manifest with
`action.toManifest({ id, version })`. See [Build Actions](/docs/extend/develop/extensions/author-actions)
for the complete example and the packaged-code boundary.

### defineSkill

```typescript
function defineSkill<TInput, TOutput>(options: {
  id: string;
  name: string;
  run(input: TInput, ctx: RunnableContext): Promise<TOutput>;
}): Runnable<TInput, TOutput>;
```

Creates a `kind: "skill"` Runnable that encapsulates a reusable prompt pattern. Like a tool it is
stateless, but its job is a reusable prompt rather than a side-effectful function.

## The model client

`defineModel` builds a gateway-mandatory `ModelClient` (`packages/sdk/src/model/client.ts`). The
client is a thin TypeScript wrapper over the `@ryuhq/sdk-native` addon, whose `ModelClient` is the
`crates/sdk/core` Rust core.

```typescript
function defineModel(modelId: string, options?: {
  baseUrl?: string;   // defaults to RYU_GATEWAY_URL, then the Rust core default
  token?: string;     // defaults to RYU_GATEWAY_TOKEN; the gateway token, never a provider key
}): ModelClient;

const model = defineModel("gemma4");
const reply = await model.chat([{ role: "user", content: "hello" }]);
console.log(reply.content);

for await (const delta of model.stream(messages)) {
  if (delta.content) process.stdout.write(delta.content);
}
```

Constructing a `ModelClient` validates egress in the Rust core, so a direct-provider base URL throws
immediately rather than at request time. The wire types are an OpenAI-compatible subset:

```typescript
interface ChatMessage { role: "system" | "user" | "assistant"; content: string }
interface ChatDelta   { content: string | null; finishReason: string | null }
interface ChatResult  {
  content: string;
  finishReason: string | null;
  usage?: { promptTokens: number; completionTokens: number; totalTokens: number };
}
```

`usage` is present only when the gateway reports token counts; otherwise it is `undefined`.

## Gateway enforcement

The Gateway path is enforced by construction (`packages/sdk/src/model/gateway.ts`, backed by
`crates/sdk/core/src/gateway.rs`):

- Every `RunnableContext` carries a `GatewayClient`; there is no context without one.
- The SDK ships **no provider bindings**, so credentials live in the Gateway, not in your code.
- `assertAllowedEgressUrl(baseUrl)` rejects direct-provider hosts at construction time. Only the
  configured gateway, loopback, or private addresses are allowed.
- It fails closed: a client that cannot reach the Gateway throws rather than calling a provider
  directly.

These helpers are exported for advanced use:

| Export | Resolves |
|---|---|
| `DEFAULT_GATEWAY_URL` | the constant `http://127.0.0.1:7981` |
| `resolveGatewayUrl()` | `RYU_GATEWAY_URL` when non-empty, else `DEFAULT_GATEWAY_URL` |
| `resolveGatewayToken()` | `RYU_GATEWAY_TOKEN`, or `undefined` when unset |
| `assertAllowedEgressUrl(baseUrl)` | throws on a known direct-provider URL |

For the architectural rule behind this (Core decides what runs, the Gateway decides what is allowed
and paid for), see [Core vs Gateway](/docs/start-here/architecture/core-vs-gateway).

## Builders and manifest schemas

For declaring a `manifest.json` in code, the SDK exports a fluent `PluginBuilder` plus per-kind
builders (`agent()`, `workflow()`, `tool()`, `skill()`) and their builder classes
(`AgentBuilder`, `WorkflowBuilder`, `ToolBuilder`, `SkillBuilder`) from `.`.

```typescript
const manifest = new PluginBuilder()
  .id("com.example.my-plugin")
  .name("My Plugin")
  .version("1.0.0")
  .runnable(agent().id("agent-main").name("Main Agent").build())
  .grant("mcp:web_search")
  .build();
```

The Zod schemas and helpers behind the builders are also exported:

| Export | Purpose |
|---|---|
| `PluginManifestSchema` | full `manifest.json` schema (also at `./manifest`) |
| `RunnableKindSchema` | enums the four authorable kinds (`agent`, `workflow`, `tool`, `skill`) |
| `RunnableMetaSchema` | per-runnable metadata block |
| `CompanionSurfaceSchema` | optional Companion surface declaration |
| `coreManifestJsonSchema` | the manifest as a plain JSON Schema |
| `validateManifestStrict(value)` | strict parse helper |
| `validatePluginId(id)` | plugin-id format check |

`RunnableKindSchema` enumerates only the four authorable kinds because that is the SDK surface. Core
validates all eight `RunnableKind` variants. The manifest schema itself is documented on
[Plugin manifests](/docs/extend/develop/extensions/plugin-json-manifest).

## MCP bridge

The SDK can expose your Runnables as MCP tools and call other MCP servers
(`packages/sdk/src/mcp/`). The protocol version is `2024-11-05`, matching Core's
`apps/core/src/sidecar/mcp/client.rs`.

`McpServer` is an stdio JSON-RPC server. `register()` advertises a local executable as a tool;
`passthrough()` forwards `tools/list` and `tools/call` to an upstream MCP stdio server (for example
Ghost), re-advertising its tools verbatim and degrading gracefully if the upstream is down.

```typescript
const server = new McpServer()
  .register({ name: "greet", run: () => Promise.resolve("Hello!") })
  .passthrough({ command: { command: "ghost" }, label: "ghost" });

await server.serve();   // reads stdin, writes stdout until EOF
```

The stateless client functions spawn a server, complete the handshake, make one call, and tear the
process down:

```typescript
function listTools(cmd: McpStdioCommand): Promise<McpTool[]>;
function callTool(cmd: McpStdioCommand, tool: string, args: unknown): Promise<unknown>;
```

`callTool` returns the full `tools/call` result object (`{ content: [{ type, text }], isError? }`);
extract `.content[0].text` for the plain output.

<Callout type="info">
  This MCP server intentionally implements no tool-approval or policy. Approval stays in the chat
  layer and policy stays in the Gateway, per the Core-vs-Gateway rule.
</Callout>

## definePlugin

`definePlugin` assembles a complete `manifest.json` manifest from typed options
(`packages/sdk/src/runnable/turn-hook.ts`).

```typescript
function definePlugin(options: DefinePluginOptions): PluginManifest;
```

| Option | Type | Purpose |
|---|---|---|
| `id` | `string` | Reverse-domain plugin id (e.g., `"com.example.my-plugin"`) |
| `name` | `string` | Display name |
| `version` | `string` | Semver version |
| `grants` | `string[]` | Permission grants the plugin needs |
| `tools` | `ToolRunnable[]` | Tools to include (auto-adds `tool:execute` grant) |
| `turnHooks` | `TurnHookContribution[]` | Turn hooks to include |
| `composerControls` | `Record<string, unknown>[]` | Chat composer toggles |
| `settingsTabs` | `Record<string, unknown>[]` | Settings UI tabs |
| `slashCommands` | `Record<string, unknown>[]` | Custom `/` commands |
| `activationEvents` | `string[]` | Lazy wake events |
| `requires` | `DefineAppRequires` | Dependencies and capabilities |
| `targets` | `Surface[]` | Target surfaces |

Each `ToolRunnable` is converted via `inlineToolRunnable()` into a `kind:"tool"` runnable with
`backend: "inline_deno"` config for Core's sandbox.

```typescript
import { definePlugin, defineTool } from "@ryuhq/sdk";

const searchTool = defineTool({
  id: "web-search",
  name: "Web Search",
  schema: {
    type: "object",
    properties: { query: { type: "string", description: "Search query" } },
    required: ["query"],
  },
  run: async ({ query }, ctx) => {
    const result = await fetch(`https://api.example.com/search?q=${query}`);
    return result.json();
  },
});

export default definePlugin({
  id: "com.example.search",
  name: "Search Plugin",
  version: "1.0.0",
  grants: ["tool:execute"],
  tools: [searchTool],
});
```

## defineApp

`defineApp` assembles a manifest for a Ryu App — tools whose results render as interactive widgets
in chat (`packages/sdk/src/runnable/app.ts`).

```typescript
function defineApp(options: DefineAppOptions): PluginManifest;
```

| Option | Type | Purpose |
|---|---|---|
| `id` | `string` | Plugin id |
| `slug` | `string` | URL-safe slug for widget templates |
| `title` | `string` | Display title |
| `version` | `string` | Semver version |
| `uiEntry` | `string` | Source entry for widget UI |
| `tools` | `AppToolSpec[]` | Render + companion tools |
| `tools[].runnable` | `ToolRunnable` | Optional executable body, packed as Core `inline_deno` |
| `grants` | `string[]` | Permission grants |
| `displayMode` | `string` | `"inline"`, `"fullscreen"`, or `"pip"` |

Each render tool gets a `contributes.widgets[]` entry binding its id to `ui://widget/<slug>.html`.
Each companion tool gets `widget_accessible: true`.

When a tool carries `runnable: defineTool(...)`, its body is embedded in the same manifest as an
`inline_deno` backend and `tool:execute` is added automatically. The body runs in Core's
deny-by-default sandbox; use the injected `host` capabilities for Gateway-routed model work.

```typescript
import { defineApp } from "@ryuhq/sdk";

export default defineApp({
  id: "com.example.chart",
  slug: "chart",
  title: "Chart Widget",
  version: "1.0.0",
  uiEntry: "src/widget.html",
  tools: [
    { name: "render_chart", description: "Render a chart from data" },
    { name: "chart_data", description: "Get chart data", accessible: true },
  ],
});
```

## defineTurnHook

`defineTurnHook` creates a turn hook that runs after assistant turns (`packages/sdk/src/runnable/turn-hook.ts`).

```typescript
function defineTurnHook(options: DefineTurnHookOptions): TurnHookContribution;
```

| Option | Type | Purpose |
|---|---|---|
| `id` | `string` | Hook id |
| `on` | `string` | Phase (default: `"post_assistant_turn"`) |
| `run` | `HookRun` | The hook function |

The hook function receives `ctx` (turn context) and `host` (capability bridge):

```typescript
import { definePlugin, defineTurnHook } from "@ryuhq/sdk";

export default definePlugin({
  id: "com.example.double-check",
  name: "Double Check",
  version: "1.0.0",
  grants: ["hook:side-model"],
  turnHooks: [
    defineTurnHook({
      id: "dc.review",
      run: async (ctx, host) => {
        if (!ctx.flags["com.example.double-check"]) {
          return { kind: "none" };
        }
        const last = ctx.transcript.at(-1);
        const review = await host.sideModel({
          prompt: last?.content ?? "",
          model_pref_key: "double-check-model",
        });
        return { kind: "note", text: review };
      },
    }),
  ],
});
```

## Composable primitives

`createPrimitives` builds typed clients for every capability (`packages/sdk/src/runnable/primitives.ts`).

```typescript
function createPrimitives(transport: PrimitiveTransport): RyuPrimitives;
```

| Client | Methods | Purpose |
|---|---|---|
| `rag` | `retrieve()`, `embed()`, `rerank()` | RAG operations |
| `memory` | `recall()`, `store()` | Long-term memory |
| `tts` | `speak()` | Audio |
| `stt` | `transcribe()` | Voice Recognition |
| `image` | `generate()` | Image generation |
| `engines` | `complete()`, `embed()` | Model inference |
| `realtime` | `broadcast()`, `subscribe()` | Real-time events |
| `durable` | `checkpoint()`, `resume()` | Durable execution |

```typescript
import { createPrimitives, httpPrimitiveTransport } from "@ryuhq/sdk";

const transport = httpPrimitiveTransport({
  nodeUrl: "http://localhost:7980",
  token: "your-node-token",
});

const { rag, memory, tts } = createPrimitives(transport);

// Search a space
const chunks = await rag.retrieve({ query: "How does auth work?", topK: 5 });

// Store a memory
await memory.store({ content: "User prefers dark mode", level: "user" });

// Speak a response
const audio = await tts.speak({ text: "Here's what I found..." });
```

Each primitive routes through the capability broker or direct HTTP, never bypassing the Gateway.

## The CLI

The `ryu` CLI (`packages/sdk/src/cli.ts`) is installed as the `ryu` bin and has four commands:

| Command | Does |
|---|---|
| `bunx ryu pack <dir>` | validate `<dir>/manifest.json`, emit `<dir>/dist/plugin.bundle.json` |
| `bunx ryu github-publish <url>` | submit a seller-owned GitHub repository/package URL to the Marketplace bridge |
| `bunx ryu agent-plugin <dir>` | emit the Agent Plugins v1 interop pair (`plugin.json` + `mcp.json`) |
| `bunx ryu dev <entry>` | run a Runnable module locally with an interactive chat loop |

`ryu pack` validates against `PluginManifestSchema` and exits non-zero with the failing field path
on any error. `ryu github-publish <url>` submits the GitHub-backed package to the bridge; private
repositories return the one-time GitHub App installation URL. `ryu agent-plugin <dir>` runs the same validation, then emits only the Agent
Plugins v1 interop pair — a `plugin.json` and, when the manifest declares MCP servers, an `mcp.json`
— derived from the manifest, so a Ryu plugin can be surfaced to agents that speak the Agent Plugins
wire format without shipping the full bundle. `ryu dev` resolves the gateway URL the same way
`ModelClient` does, imports your module, and starts a terminal REPL; it fails non-zero with a clear
message if the Gateway is unreachable, never falling back to a provider.

Publishing is governed by the Gateway (grant validation and manifest signing). See
[Marketplace](/docs/extend/develop/extensions/marketplace) for the full publish flow.

## Scaffold a project

```bash
npx create-ryu-app my-extension
```

`create-ryu-app` (`packages/create-ryu-app/`) generates a starter project: a `manifest.json` validated
against the manifest schema, a `package.json` with `dev` and `pack` scripts, and a starter agent in
`src/agent.ts` that streams one turn through the local Gateway.
