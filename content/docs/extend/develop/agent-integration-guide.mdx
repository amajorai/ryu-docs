An AI agent can reach Ryu through the Gateway HTTP API, the Core HTTP API, or MCP (Model Context
Protocol). This guide shows each path, how to find tools, how calls stay governed, and how to
package an agent with the SDK.

## Quick start: connect to Ryu

### 1. Point at the Gateway (recommended)

The Gateway exposes an OpenAI-compatible API on `127.0.0.1:7981` (release profile). Any tool or
framework that speaks the OpenAI protocol can call it with no Ryu-specific setup.

```bash
# List available models
curl http://localhost:7981/v1/models \
  -H "Authorization: Bearer $RYU_TOKEN"

# Chat completion
curl http://localhost:7981/v1/chat/completions \
  -H "Authorization: Bearer $RYU_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-4o",
    "messages": [{"role": "user", "content": "Hello"}],
    "stream": true
  }'
```

### 2. Use Core for the full agent lifecycle

Core on `127.0.0.1:7980` (release profile) runs conversations, memory, tools, and workflows.

```bash
# Chat with the default agent
curl http://localhost:7980/api/chat/stream \
  -H "Authorization: Bearer $RYU_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [{"role": "user", "content": "Hello"}],
    "agent_id": "ryu",
    "response_mode": "everyday"
  }'
```

#### Select the response mode

`POST /api/chat/stream` accepts `response_mode` with the values `everyday` and
`developer`. Omit the field for `everyday`.

`everyday` changes the flagship Ryu assistant's explanatory language to clear
standard English. `developer` keeps exact Ryu identifiers and architecture in
the response. The field changes wording only. It does not change tools,
permissions, approvals, model routing, or data access.

Desktop maps Ryu Work to `everyday` and Code to `developer`. Other clients can
send the field directly when they need the developer vocabulary.

### 3. Use MCP for tool access

The `ryu-mcp` server exposes Core tools over MCP (Model Context Protocol) using the stdio
transport. An MCP host can then list and call those tools.

```json
{
  "mcpServers": {
    "ryu": {
      "command": "ryu-mcp",
      "args": ["serve"],
      "env": {
        "RYU_CORE_URL": "http://127.0.0.1:7980",
        "RYU_CORE_TOKEN": "your-node-bearer"
      }
    }
  }
}
```

See [MCP quickstart](/docs/extend/mcp/quickstart) for the full setup.

This stdio bridge uses a node bearer. For a managed organization node, connect an
MCP host to the hosted `/mcp/<node-id>/<agent-id>` endpoint so OAuth can be
exchanged for a short-lived node-and-agent delegation. `ryu-mcp login` signs the
bridge into the Ryu account for `whoami`; it does not replace the target node
credential.

An agent-bound delegation also applies when opening an MCP-backed app through
`POST /api/widgets/open`. Its `agentId` must match the signed agent binding; Core rejects
a mismatch before creating an app conversation or dispatching its tool.

## From the desktop editor

Open a saved agent, choose **Integrations**, and copy an example with its agent id and node URL
already filled in. The tab covers the paths people usually need:

- **TypeScript SDK** - use `@ryuhq/client` to stream a saved agent from a Node, Bun, or Deno app.
- **Python, Go, and cURL** - call the same Core JSON + SSE endpoint without a Ryu-specific runtime.
- **GitHub Actions** - run the agent from pull requests, releases, or other CI jobs with the
  [`amajorai/ryu` action](/docs/ci/github-actions).
- **Ryu App** - build an interactive widget around an agent tool or result with the
  [`create-ryu-app` templates](/docs/extend/develop/extensions/ryu-apps).

The code samples call `POST /api/chat/stream`, so the saved agent's tools, rules, and Gateway
policies still apply. Keep a protected node's token in `RYU_TOKEN`, never in the copied source.

## Discover available tools

### Via Core's unified tool catalog

```bash
# Search all registered tools (ranked)
curl "http://localhost:7980/api/tools/search?q=file%20operations&limit=5" \
  -H "Authorization: Bearer $RYU_TOKEN"

# Describe one tool's argument schema
curl "http://localhost:7980/api/tools/describe?id=web_fetch.get" \
  -H "Authorization: Bearer $RYU_TOKEN"

# List registered MCP tools
curl http://localhost:7980/api/mcp/tools \
  -H "Authorization: Bearer $RYU_TOKEN"
```

### Inside a chat plane

An agent on the Gateway's OpenAI-compatible plane gets a `tool_search` meta-tool. An ACP agent gets
`tool_search` and `describe` through the MCP bridge. An MCP host connected to `ryu-mcp serve` lists
tools with the MCP `tools/list` request.

See [Unified tool catalog](/docs/core/unified-tool-catalog) and [MCP tools](/docs/extend/mcp/tools) for
the full tool inventory.

## Stay governed

The Gateway enforces policy on every model call that it routes.

### OpenAI-compat agents (Plane A)

When your agent uses the Gateway's `/v1/chat/completions`, all governance is automatic:

- **Firewall** scans requests and responses for PII, prompt injection, and custom patterns
- **Budgets** enforce per-user and per-agent charged-cost caps in micro-USD
- **Evals** score response quality
- **Audit** logs every request

No extra configuration is needed.

### ACP agents (Plane B)

ACP agents (such as Claude Code, Codex, and Pi) run as subprocesses. Their LLM calls are self-routed,
but **tool egress** is governed via the MCP bridge. New and auto-installed routable ACP agents
are routed through the Gateway by default. Direct egress is an explicit per-agent opt-out through
the `agent-gateway-routing` preference (`apps/core/src/agent_routing/mod.rs`): a missing entry stays
Gateway-routed, and an explicit `false` opts the agent out.

The default injects `OPENAI_BASE_URL` pointing at the Gateway into a routable agent's subprocess.

<Callout type="warn">
Not every agent reads `OPENAI_BASE_URL`. It works for BYO OpenAI-compatible agents but has no effect
on Gemini, OpenClaw, or Hermes, whose chat calls bypass the Gateway.
</Callout>

ACP subprocesses receive a small safe runtime environment plus values declared in their
ACP configuration. Core's ambient credentials, including `RYU_TOKEN`, provider keys, and
Gateway keys, are not inherited; configure a per-agent credential explicitly when that
agent needs one.

See [Gateway for any agent](/docs/gateway/gateway-for-any-agent) and
[Routing planes](/docs/gateway/routing-planes).

## Build with the SDK

The TypeScript SDK (`@ryuhq/sdk`) provides typed factories for building Runnables that route all
model calls through the Gateway.

### Define an agent

```typescript
import { defineAgent } from "@ryuhq/sdk";

const myAgent = defineAgent({
  id: "my-agent",
  name: "My Agent",
  run: async (input, ctx) => {
    const result = await ctx.gateway.chat([
      { role: "system", content: "You are a helpful assistant." },
      { role: "user", content: input },
    ]);
    return result.content;
  },
});
```

### Define a tool

```typescript
import { defineTool } from "@ryuhq/sdk";

const weatherTool = defineTool({
  id: "weather",
  name: "Get Weather",
  schema: {
    type: "object",
    properties: {
      city: { type: "string", description: "City name" },
    },
    required: ["city"],
  },
  run: async (input) => {
    return { city: input.city, forecast: "sunny" };
  },
});
```

A shipped tool body runs in Core's JS sandbox with only `input` and `host` in scope. `host` is the
capability bridge (`host.sideModel`, `host.storage`, `host.log`), each gated by the plugin's grants.
The body cannot capture outer variables or imports, and `ctx.gateway` is not available there, so a
shipped tool reaches models through `host.sideModel`.

### Bundle into a plugin

Create a `manifest.json` file.

```json
{
  "id": "com.example.my-plugin",
  "name": "My Plugin",
  "version": "1.0.0",
  "runnables": [
    { "kind": "agent", "id": "my-agent", "name": "My Agent" },
    { "kind": "tool", "id": "weather", "name": "Get Weather" }
  ],
  "targets": ["core"]
}
```

Pack and install:

```bash
bunx ryu pack ./my-plugin               # validate and pack the bundle
bunx ryu install ./my-plugin --enable   # install into Core and enable it
```

See [SDK Reference](/docs/extend/develop/sdk) for the full API surface.

## Built-in tools

Core registers built-in tool servers such as `sandbox`, `notify`, `delegate`, `skills`, and
`web_fetch`. Plugins add more, such as `exa` and `spider`. See
[Built-in tools](/docs/core/built-in-tools) for the list and
[Unified tool catalog](/docs/core/unified-tool-catalog) for how search and describe work.

## Configuration quick reference

### Core environment variables

| Variable | Purpose |
|---|---|
| `RYU_TOKEN` | Node bearer token. Without it, Core reads `secrets/node-auth.token` or mints one |
| `RYU_DIR` | Data directory (default `~/.ryu` on the release profile, `~/.ryu-<profile>` otherwise) |
| `RYU_DEFAULT_AGENT` | Default agent ID (default `ryu`) |
| `RYU_BIND` | Bind address (default `127.0.0.1:7980`) |

### Gateway environment variables

| Variable | Purpose |
|---|---|
| `GATEWAY_MASTER_KEY` | Admin key for config and audit endpoints |
| `OPENAI_API_KEY` | OpenAI provider credentials |
| `ANTHROPIC_API_KEY` | Anthropic provider credentials |
| `GATEWAY_FIREWALL_ENABLED` | Toggle firewall |

See [Environment variables](/docs/start-here/environment-variables) for the full Core and Gateway
variable reference.

### Core (`:7980`)

| Category | Key endpoints |
|---|---|
| Chat | `POST /api/chat/stream`, `POST /api/btw` |
| Agents | `GET /api/agents`, `GET /api/agents/:id` |
| Conversations | `GET /api/conversations` |
| Memory | `GET/POST /api/memory` |
| Spaces | `GET/POST /api/spaces`, `POST /api/spaces/:id/search` |
| Tools | `GET /api/tools/search`, `POST /api/tools/exec` |
| Workflows | `GET/POST /workflows`, `POST /workflows/:id/run` (no `/api` prefix) |
| Models | `GET /api/models/catalog`, `GET /api/models/engines` |
| MCP | `GET /api/mcp/servers`, `GET /api/mcp/tools` |
| Health | `GET /api/health` |

|---|---|

| Models | `GET /v1/models` |

| Config | `GET/PUT /v1/config` |

| Health | `GET /health` (alias `GET /v1/health`) |

## LLM-friendly documentation

Ryu's docs are also served in machine-readable formats.

| Endpoint | Format | Use case |
|---|---|---|
| `GET /llms.txt` | Compact Markdown index | Find a section, its main pages, and its folder indexes |
| `GET /llms/{folder}.txt` | Markdown index of one folder | List every page in a folder; large folders continue at `?page=N` |
| `GET /llms-full.txt` | Full text of every page | Bulk consumption of the complete content (large) |
| `GET /llms.mdx/docs/{slug}` | Per-page Markdown | Targeted page fetch |
| `GET /docs/{path}.md` or `.mdx` | Per-page Markdown | Explicit Markdown suffix |
| `GET /docs/{path}` with `Accept: text/markdown` | Per-page Markdown | Content negotiation on the canonical docs URL |

`/llms.txt` lists only each section's overview and direct children, so follow a folder index such
as `/llms/extend/develop.txt` to see every page in that folder. Each split folder index links its
previous and next `?page=N`. Only `/llms-full.txt` carries the page content itself.

On the main website, `https://ryuhq.com`, a page that does not exist returns HTTP `404` for both
HTML and Markdown requests. The website MCP server's `read_page` tool reports a missing page as not
found and a moved page with its new URL. See
[Website discovery and authentication](/docs/extend/mcp/llms#website-discovery-and-authentication).

See [LLM-friendly docs](/docs/extend/mcp/llms) for the full list, per-page fetch examples, and how the [Docs MCP server](/docs/extend/mcp/docs-server) exposes the same content as tools.

Each documentation page also links its Markdown version from the HTML head. A locale URL may show
English fallback content while a translation is being prepared; search metadata points that
fallback page to the English canonical. Use the page's canonical URL when citing it, and use a
localized URL when its content is translated.
