This page covers sending through hosted [Agent Inboxes](/docs/extend/develop/agent-inboxes). The
routes are listed in [Agent Inboxes API](/docs/extend/develop/agent-inboxes-api).

## Sending as an agent

An agent always sends as its own address, with its `displayName` as the sender name. A request
that sets `from` returns `400` with `code: "from_not_allowed"`. Its `replyTo` may only be its own
address (`400` with `code: "reply_to_not_allowed"` otherwise). A reply goes out as the address that
received the original. A revoked address returns `403` with `code: "alias_revoked"`, an agent with
no address `409` with `code: "alias_missing"`, and a disabled mailbox `403` with
`code: "mailbox_inactive"`.

A signed-in member sends as the mailbox by default, or as an agent's address by passing
`fromAliasId` to `POST /mail/inboxes/:id/send`. A member's `replyTo` must be an external address or
one the organization owns.

### Send approval

The service, not the agent's node, decides whether an agent's send needs a person's approval. The
send policy applies to agent sends; sends by members with `mail.manage` are exempt, because they
are the approvers.

| Setting | Default | Meaning |
|---|---|---|
| `mode` | `first_contact` | `auto` sends; `first_contact` holds a send to anyone the address has not corresponded with; `always` holds every send |
| `maxRecipientsPerMessage` | 10 | A send to more recipients is held |
| `newRecipientsPerDay` | 20 | A send that takes the address past this many new recipients in a day is held |
| `preApprovedDomains` | none | Recipients at these domains never count as new |

The recipient limits apply in every mode. `PUT /mail/send-policy` sets the organization's policy,
or one address's override with `aliasId`. A recipient becomes known after an approved send to them
or after they send authenticated mail to that address; each address has its own contacts, so one
agent's contacts never approve another agent's sends. People an existing inbox already
exchanged mail with before send approval was introduced (recipients of its delivered sends and
authenticated senders it received from) start out known, so turning on `first_contact` doesn't
hold mail to them.

A held send returns `202` with `status: "pending_approval"`, a `draftId`, and the `reasons`
(`policy_always`, `first_contact`, `over_recipient_cap`, `over_new_recipient_limit`). It uses no
send quota until it is approved. An admin reviews it in `GET /mail/approvals` and decides with
`POST /mail/drafts/:id/approve` or `/reject`. Each approval lists everything that would be sent:
To, Cc, Bcc, Reply-To, headers, the text and HTML bodies, and each attachment's name, type, and
size. Approval sends exactly what was reviewed: if any of it changed since the request, approval
returns `409` with `code: "approval_stale"`. An agent can't edit a held send (`409` with
`code: "approval_pending"`); it sends again instead.

Under `auto`, a recipient a send reaches is
known from then on, so repeat sends to them don't count as new recipients again. A request expires
after 7 days (`410` with `code: "approval_expired"`).

## Sending rate limits

Besides the monthly send quota, every plan has short-window limits that stop an agent loop from
sending in bursts:

| Limit | Sends |
|---|---|
| One agent address, per minute | 20 |
| One inbox, per minute (the mailbox: 60) | 20 |
| One organization or personal account, per minute | 60 |
| One organization or personal account, per hour | 600 |

A send over a limit returns `429` with `code: "send_rate_limited"`, the `limit`, `window`
(`minute` or `hour`), `subject` (`alias`, `inbox`, or `account`), a `retryAfterSeconds` value, and a
`Retry-After` header. A refused send uses none of the monthly quota. Replies, forwards, and
drafts sent now count toward these limits. A scheduled draft that hits a limit returns to the
`draft` state.

## Plan gating

Quotas are decided by the shared plan catalog. Claiming the mailbox or an agent address gates on a
live entitlement; sending
atomically reserves durable monthly units, one per listed recipient, before the provider call. A
paid plan meters its organization or personal account. The Free baseline is one allowance per
person: an organization without a paid plan draws on its owner's inbox, email, and storage
allowance, shared with the owner's personal workspace and their other unpaid organizations. A
send the provider refuses releases the units. An accepted send stays counted even if its history
row needs reconciliation, and so does an `unresolved` send, because it may have been delivered.

On a paid plan, a send past the monthly allowance goes ahead while the organization has credits,
and each recipient beyond the allowance is charged once the provider accepts the message. Without
credits, on the free baseline, and under an Enterprise contract limit, the send returns `403`. If
the service briefly can't check or record a charge, a send past the allowance returns `503`
without sending; retry it. See
[Agent Inboxes billing](/docs/billing/agent-inboxes#sending-past-the-monthly-allowance) for the price.

Deleting a message, thread, or inbox removes its stored objects first. If storage refuses, the
request returns `503` and keeps every message record so you can retry; an inbox stays disabled
until the retry succeeds.

Organization session callers need `mail.manage` to send, reply, forward, or schedule a draft.
Creating or updating a draft with a send time uses the same permission. Read-only access with
`mail.read` does not authorize sending. When a scheduled draft fires, the service checks again
that Agent Inboxes are still enabled for the organization and that the member who last scheduled
or edited it still has `mail.manage`. A draft last scheduled or edited with a gateway key is
checked against that key instead: it must not be revoked or expired, must still allow mail, and
must still reach the inbox. Otherwise the draft returns to an unscheduled draft without sending.

Per-plan mailbox, agent address, monthly email, and stored-mail allowances are listed in
[Agent Inboxes billing](/docs/billing/agent-inboxes#limits-by-plan). Each listed recipient counts as
one email.

Pending and active agent addresses count toward the address limit, and so do agent inboxes created
before mailboxes; revoked addresses don't. Agent addresses add no emails or storage: they share
their organization's allowance. On the Free baseline, a person who already has a mailbox in one
organization gets `403` with `code: "mailbox_requires_plan"` for a second organization's mailbox.
An organization already over a limit when it moved to mailboxes keeps everything it has; only new
claims are refused.

Stored mail counts message bodies, attachments, and unsent drafts in every inbox the allowance
covers, including paused and deactivated ones; sends, replies, forwards, and drafts that would
exceed it are refused. Inbound mail over the cap, or for a deactivated inbox, is not stored: the
service records a `message.received.blocked` event (sent to signed webhooks) and, when storage is
full, notifies the inbox's readers. After a downgrade, inboxes beyond the Free baseline's one
mailbox pause sending for a 30-day grace period, oldest inbox first to stay active, then deactivate. See
[Agent Inboxes billing](/docs/billing/agent-inboxes) for the full enforcement rules. Check your
current plan with `GET /mail/usage` before claiming an address or scheduling a send.

Inbound SES delivery ids are unique per inbox and agent address, so retries are storage-idempotent. Repeated SES
delivery, bounce, and complaint notifications update a message once and produce one event each, and
a later notification never moves a message back from bounced, complained, or opened. An inbox's own
`webhookUrl` is called after storage with SSRF checks and time bounds, with one attempt per message;
the managed webhook resource delivers a signed event envelope with bounded retries. Both are
best-effort and cannot delay the public inbound acknowledgement. Only members with `mail.manage`
(and gateway keys) can read an inbox's `webhookUrl`; other members see only `webhookConfigured` and
`webhookSigned`.

`Idempotency-Key` makes sends, replies, forwards, and draft sends safe to retry; reusing a key with
different request data returns `409`. The key is claimed before anything is sent, so a request that
repeats a key still being sent returns `409` saying it is still in progress; retry it shortly to get
the stored message. A request refused before sending, for example over the monthly limit or by the
mail provider, does not use up its key. If a send ended without a definite answer from the mail
provider, or never finished, the key returns `409` saying the outcome is unknown: check the inbox's
sent messages, and send again with a new key only if the message is not there. Keys are kept for 30
days. JSON request bodies for inbox routes are limited to 24 MiB and larger bodies return `413`.

A draft that is already being sent, or has been sent, cannot be sent again or edited, so those
requests return `409` even with the same key. A draft send that the mail provider refuses returns
the draft to its previous state, and a scheduled draft refused when it fires becomes an unscheduled
draft.

A draft send that ended without a definite answer from the provider may have been delivered, so
the draft moves to `unresolved` instead, with its `sendAt` cleared. A draft left being sent by a
service restart moves there too. The scheduler never sends an `unresolved` draft, and sending or
editing it returns `409` until you confirm. Check the inbox's sent messages first. If the message
is not there, send the draft with `{"confirmNotSent": true}` in the body of
`POST /mail/inboxes/:id/drafts/:draft_id/send`, or include `"confirmNotSent": true` in a `PATCH` to
edit or reschedule it; an edit without a new `sendAt` returns it to `draft`. If the message was
delivered, delete the draft.

Confirming also marks a message that the earlier attempt left `queued` as `unresolved`, so the
confirmed send goes out instead of being answered with that message. If Ryu recorded the provider
accepting the earlier attempt, that message answers the send and the draft is marked sent without a
second copy.

## Verifying webhook deliveries

Managed webhooks and inbox `webhookUrl` deliveries are signed with
[Standard Webhooks](https://www.standardwebhooks.com/), so the Standard Webhooks and Svix libraries
verify them with the webhook's secret. Each signed delivery carries:

```text
webhook-id: <event id>
webhook-timestamp: <unix seconds>
webhook-signature: v1,<base64>
```

The same values are repeated as `svix-id`, `svix-timestamp`, and `svix-signature`. The signature is
a base64 HMAC-SHA256 over `<webhook-id>.<webhook-timestamp>.<raw body>`, keyed by the
base64-decoded part of the secret after `whsec_`. Reject deliveries whose timestamp is far from
your clock; the libraries allow five minutes by default. The id is the event id, so use it to
deduplicate. An inbox `webhookUrl` delivery uses the id of the `message.received` event for the
same message.

Secrets are returned once: a managed webhook's `secret` on create, and an inbox's `webhookSecret`
when its `webhookUrl` is first set with `PATCH`. The mailbox's own `webhookUrl` receives message
metadata only, without message bodies or previews, because the mailbox holds every agent's mail; use a
managed webhook for full payloads. `PATCH /mail/webhooks/:id` with
`rotateSecret: true`, or `PATCH /mail/inboxes/:id` with `rotateWebhookSecret: true`, returns a new
secret once, and the old secret stops verifying immediately. Clearing an inbox's `webhookUrl` also
removes its secret.

Existing integrations keep working:

- **Inbox webhooks configured before signing** have no secret and keep receiving unsigned requests
  (`webhookSigned: false`) until you rotate the secret or set the URL again.
- **Managed webhooks created before Standard Webhooks signing** report `signatureScheme: "legacy"`.
  Their `svix-signature` is still keyed by the UTF-8 bytes of the whole `whsec_...` secret, prefix
  included, as earlier versions signed it, while their `webhook-signature` already uses the
  Standard Webhooks key, so a Standard Webhooks library verifies the `webhook-*` headers with the
  existing secret. Svix SDKs check the `svix-*` headers first: rotate the secret before switching
  to one, which moves the webhook to `signatureScheme: "standard"`.

A custom header can't use a name the signer sets (`webhook-id`, `webhook-timestamp`,
`webhook-signature`, any `svix-*` name, `content-type`, `content-length`, `host`, or `cookie`).

The public TypeScript client exposes the same developer surface as
`client.mail.send`, `client.mail.listThreads`, `client.mail.createDraft`,
`client.mail.createWebhook`, `client.mail.rotateWebhookSecret`, `client.mail.verifyDomain`, and
the list/domain/pod methods. Hosted callers that act for a node use its gateway key for that node's
agent inboxes, sending, and reads; creating or changing org-shared inboxes, domains, pods, and
organization- or pod-wide lists needs a signed-in session with Mail management permission. Self-host
callers use the standalone Mail bearer and the same path spelling.
