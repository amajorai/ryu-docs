---
title: "Sidecar WebSocket Routes"
description: "How Core's WebSocket ext-proxy at /api/ext/ws/<plugin>/<route> tunnels live sidecar streams such as the Virtual Desktop, and what the sidecar must implement"
---

The HTTP ext-proxy serves a sidecar's REST routes at `/api/ext/<plugin>/<route>`. Some features need
live streams instead of request/response calls. The Virtual Desktop panel is one example: it shows
a live VNC session.

A WebSocket is a live, two-way stream. The HTTP proxy uses `reqwest`, which cannot upgrade to a
WebSocket. Core therefore exposes a WebSocket version of the ext-proxy at:

```text
GET /api/ext/ws/:plugin_id/*rest
```

The route is registered in the same router (`ext_routes` in `apps/core/src/sidecar/ext_proxy.rs`).
It uses the same security rules as the HTTP route: the enabled check, route allowlist, node-token
check, and lazy sidecar start. An undeclared path returns 404 before the WebSocket upgrade.

## How it works

1. The client asks Core for a one-use ticket. It sends `POST /api/ws/ticket` with the node bearer
   and the body `{"route": "ext", "path": "/api/ext/ws/@ryu/desktop/ws"}`. The ticket expires after
   60 seconds (`apps/core/src/server/ws_ticket.rs`).
2. The client upgrades `wss://<node>/api/ext/ws/@ryu/desktop/ws?ticket=<ticket>`. A protected route
   requires the ticket. Core rejects a `?token=` or `?jwt=` query parameter with 401, so a node
   bearer or user JWT never appears in a URL.
3. Core resolves the manifest, sidecar, and matched route the same way as the HTTP proxy. It checks
   the route permission against the caller stored in the ticket, then upgrades the socket.
4. Core dials the sidecar's loopback WS endpoint (`ws://127.0.0.1:<port><route>`), re-stamps the
   plugin's minted hop token, and **pumps bytes both ways** until either side closes.

The sidecar owns the wire format. Core forwards bytes and does not parse VNC, RFB, or any other
sidecar protocol, the same as the HTTP lane. A sidecar that wants an interactive
surface declares the route and serves a WebSocket there.

## What the sidecar must do

The sidecar's route handler is a plain WebSocket endpoint on its loopback control server:

- It must accept the upgrade and validate the **hop token** before doing anything else. The hop
  token is the `Authorization: Bearer <token>` header Core sets, which carries the per-plugin
  secret from `RYU_EXT_TOKEN`. Core authenticates the client; the sidecar authenticates Core's hop,
  the same as for host-API callbacks.
- It should bind **loopback only** (`127.0.0.1`). The only path to it is Core's authenticated
  tunnel; nothing exposes the port to the network.
- The route must be declared in the manifest's `sidecars[].http.routes[]`, like any HTTP route, so
  Core's allowlist admits the upgrade. This example is trimmed from
  `apps-store/desktop/manifest.json`. It shows the route declaration:

```jsonc
"sidecars": [{
  "name": "desktop",
  "port": 8015,
  "http": {
    "routes": [
      { "path": "/health" },
      { "path": "/ws", "permission": "desktop.control" }
    ]
  }
}]
```

## The reference implementation: Virtual Desktop

The `@ryu/desktop` app is the shipped example. Its sidecar starts a headless X desktop (Xvfb, a
window manager, and TigerVNC on loopback). Its `/ws` route is a **websockify-style bridge**: it
accepts RFB-over-WebSocket from Core and pumps bytes onto the loopback VNC TCP port. The desktop
panel connects a noVNC client to the tunnel, so pixels come down and mouse/keyboard go up on one
socket.

See [Virtual Desktop](/docs/surfaces/desktop/user-guide/virtual-desktop) for the user-facing surface.

## Why not WebRTC

A low-latency interactive desktop could be streamed over WebRTC instead. WebRTC needs a signaling
channel, TURN/STUN for NAT traversal, and a media encoder on the node. That infrastructure does not
fit a self-contained sidecar behind Core's single authenticated port, and it would have to be
proxied through Core anyway. VNC over WebSocket (noVNC) works through the existing auth model with
no signaling or media server.
