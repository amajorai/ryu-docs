---
title: "Interface Protocol for Hosts"
description: "The @ryuhq/protocol/interfaces contract a Ryu client implements to render contributed interfaces."
---

Plugin authors only need the manifest described in [Publish an Interface](/docs/extend/develop/extensions/interfaces). If you are building a Ryu client that renders
interfaces, the contract is published in the `@ryuhq/protocol/interfaces` export of
`@ryuhq/protocol`. It defines these parts:

- **Descriptors.** `InterfaceDescriptor` is one switcher entry: `id`, `label`, `description`,
  `renderer`, `params`, `origin` (`"builtin"` or `"marketplace"`), and the owning `plugin`.
  `parseInterfaceContributions()` validates served rows, and `resolveInterfaceParams()` turns
  untrusted params into typed options with defaults. `interfaceTier()` maps a renderer to its
  `managed`, `workspace`, or `admin` tier.
- **Snapshot.** Every interface reads one `InterfaceSnapshot` (`version: 1`): `agents` (id, name,
  description, avatar, `idle` or `working`), `threads` (title, agents, team, project, latest
  activity, latest message, message count, pinned, running, and an optional last run outcome
  `runState`), and `groups` (teams and projects with their member agents). An optional, additive
  `events` list carries scheduled runs (`InterfaceEvent` with `id`, `title`, `agentId`, `kind` `past`
  or `upcoming`, `start`, and optionally `end`, `outcome`, and `count`, plus a schedule `label`).
  Hosts without schedules omit it, and renderers treat a missing list as no scheduled runs.

  An optional, additive `account` (`InterfaceAccount`) carries the user's usage account: `balance`
  and its `breakdown` (plan, top-up, and gift credit) in micro-units, a lower-case ISO 4217
  `currency`, and recent `transactions`, newest first (each an `InterfaceAccountTransaction` with `id`, `at`,
  a signed `amount`, `kind` `credit` or `debit`, `label`, `balanceAfter`, and, when known, the
  `model`, `provider`, token counts, and the `threadId` it belongs to). Hosts without a usage
  account omit it.
- **What waits on the user.** These fields are optional and additive too: hosts without them omit
  them, and renderers treat a missing field as absent.
  - `asks` lists everything waiting on the user, most urgent first (each an `InterfaceAsk` with `kind`
    `approval`, `question`, `permission`, `input`, or `reply`, the `text`, the owning `agentId`
    and `threadId`, `since` and `expiresAt`, and the `choices` the host can answer in place).
    Omitted means the host has no ask sources; an empty list means it looked and found nothing.
  - `askBlindSpots` names the ask kinds the host cannot see for every thread, so a renderer can
    say that some prompts only show in their chat. An empty `asks` says nothing about these kinds.
  - An ask is `blocking` when it needs the user's decision before something can happen. `holdsRun`
    is narrower: a live run is waiting on it. A non-blocking ask other than a `reply` is a
    suggestion (a fix, a skill proposal, a question saved for later).
  - `privacy: "redacted"` means the host has already removed text, titles, and details from the
    snapshot. Renderers show what they receive and offer no in-place answers.
  - `observedAt` is the host's clock when it built the snapshot. Renderers use it as "now" for the
    data.
- **Thread, agent, and event additions.** Also optional and additive:
  - threads: `runStartedAt` (with `runStartedApprox` when it is only the first time the host saw
    the run), `runEndedAt`, `lastProgressAt` (when a running thread last made progress),
    `progress` (plan, workflow, or estimate steps), `activity`, `outcome`, `blocker`, `helpers`,
    `unread`, `routineRun` (the cron routine whose firing started this run, set only when the run
    demonstrably started at that fire time), and `detail` (`summary` when the host read only the
    list, so a missing field means unknown);
  - agents: `focusThreadId`, `model`, and `limit` (the usage window);
  - events: `jobId`, `threadId`, `error`, and `requiresApproval`.
  - `runEndedAt`, `runStartedAt`, and `InterfaceBlocker.at` are exact only when they are not marked
    approximate. Never fill them from a "last updated" time.
- **Port.** Every interface acts through one `InterfacePort` with `openThread(id)`,
  `startThread({ agentId, teamId, projectId, prompt })`, and `closeThread()`. A `prompt` is sent
  right away, so hosts pass only text the user typed and submitted. Two methods are optional:
  `answerAsk(askId, choiceId)` answers an ask in place, and is called only from the shared ask
  card, after its confirm step for choices the host marks `destructive`; `openInbox()` opens the
  host's approvals inbox for an ask with no thread. Hosts without `answerAsk` get ask cards that
  offer only **Open**, and the card never answers while the snapshot is redacted.

  Ask ids are stable but not unique across threads, nodes, or restarts (`permission:<requestId>` and
  `question:<toolCallId>` can repeat), so a host answers the ask it shows, for that ask's
  `threadId` on the node the snapshot came from, and refuses when it cannot tell which ask was
  chosen. `updateSettings(patch)` is optional as well: a renderer calls it to save
  the user's choice for some of its own settings (keys from `interfaceSettingsFor()`), for example
  from an in-view toggle. The host keeps only keys and values that fit those settings, stores them
  per interface, and re-renders the interface with the new params. `resetSettings()` is optional
  too: a renderer calls it from an in-view "restore defaults" control to forget the user's saved
  settings for the interface, so its own defaults apply again.
- **Settings.** `rendererSettings(renderer)` lists a renderer's settings (each an `InterfaceSettingField` with
  `key`, `label`, optional `description`, `type` `boolean`, `select`, `number`, or `text`,
  `default`, and `options`, `min`, `max`, and `step` where they apply), held in step with the
  params `resolveInterfaceParams()` accepts. `interfaceSettingsFor(descriptor)` is what to show
  for one interface: a contribution's validated `settings`, else its renderer's.
  `interfaceParamsWith(descriptor, overrides)` resolves the live params: the contribution's
  setting defaults, then its `params`, then the user's overrides that fit
  (`settingValueFits()`).
- **Projections.** `projectChannels()`, `projectFeed()`, `layoutWorld()`, `projectBoard()`,
  `projectInbox()`, `projectGraph()`, `projectTimeline()`, `projectContacts()`, `projectArena()`,
  and `projectDeskViews()` turn a snapshot into each layout's channels, posts, world, columns,
  sections, nodes, days, contacts, cards, and views. World placement depends only on the agents' names, so an
  agent stands in the same spot in 2D, 3D, and after a reload. Every renderer added after these,
  from `card-table` to `warehouse`, builds its view from the same snapshot inside Ryu; the protocol
  does not export projections for them.

A host renders open conversations with its normal chat view. The interface only chooses which
conversation to show and where; it never sends messages through a second path.
