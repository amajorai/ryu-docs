---
title: "Feature Flags and Early Access Forms"
description: "Manage Ryu rollout flags and app-owned flags, then collect early access applications with a configurable form."
---

Ryu has two flag scopes. Ryu administrators manage platform rollout flags. An organization manages flags for the apps it publishes in Marketplace. Each flag can have an optional waitlist form, a kill switch, percentage allocation, targeting rules, and a schedule.

## Platform rollout flags

Ryu administrators can change a platform flag in **Admin → Feature flags & experiments**. The flag's catalog default, deployment override, and admin override determine whether the platform feature is available. A waitlist form collects interest; submitting it does not turn the flag on or grant access.

Platform flags also use a kill switch, percentage allocation, ordered targeting rules, and start/end
times. To evaluate one for a signed-in Ryu account, call `POST /api/feature-flags/evaluate` with its
key and request traits. The server uses the authenticated account as the stable allocation subject;
an approved waitlist grant opens only that flag for that verified account unless its kill switch or
schedule blocks it.

A platform flag can also be limited to specific plans. Select one or more plans in the flag's
**Rollout and targeting** section, including **Free (no paid plan)**. Ryu resolves the caller's plan
on the server. A caller on an unselected plan, or whose plan cannot be resolved (for example, while
billing is unavailable), gets the flag off with reason `plan_ineligible`. A one-time **Ryu Desktop**
license counts as the **Ryu Desktop** plan, not as **Free (no paid plan)**. An approved waitlist
grant does not override the plan limit. If no plans are selected, the flag is available on every
plan. Targeting rules see the same server-resolved value as the `plan` and `tier` traits. Any `plan`
or `tier` sent in the request is ignored. Plan limits apply only to platform flags; Marketplace app
flags cannot use them.

Ryu sets the `audience`, `org_role`, `waitlist_status`, `plan`, and `tier` traits from the signed-in
account on the server. The same values are used everywhere Ryu checks a platform flag, including
program enrollment, family sharing, and rollout-limited Marketplace listings. When a turned-off
targeting rule depends on one of these traits and Ryu cannot resolve it for a signed-in account,
the rule still applies and the flag is off with reason `targeted_off`.

Choose **Add waitlist** on a flag to add a form. Every form asks for an email address and can include up to 10 custom questions:

- short answer;
- long answer;
- choose one from a list of up to 12 options; or
- a consent checkbox.

Questions can be required. The form also has an introduction and a confirmation message. **Publish form** makes its link available; **Preview** opens the public signup page. Each application has a **Grant access** action. Approval grants that person the flag through their verified Ryu account, matched by email. A kill switch still forces the flag off for everyone, including approved applicants.

## Flags for published apps

An organization owner, administrator, or member with the `features.manage` permission can open **Organization → Features → Manage app flags**. This page lists the organization's live Marketplace apps. Add a flag with a stable key, name, and description, then choose whether that app capability is on. Keys are lowercase and may use dots, hyphens, or underscores.

If the flag list cannot be read, the page shows an error instead of an empty list or stale controls. Restore the required organization access, then select **Refresh** to load the current flags.

The app can read coarse flag defaults from:

```http
GET /api/feature-waitlists/public/apps/{appId}/flags
```

The response maps each key to its `enabled` value, display name, description, allocation, grant state, and optional `waitlistUrl`. For percentage rollout and targeting, evaluate a stable subject with its traits instead:

```http
POST /api/feature-waitlists/public/apps/{appId}/evaluate
Content-Type: application/json
```

```json
{
  "subjectId": "stable-app-user-id",
  "attributes": {
    "plan": "pro",
    "device": "ios",
    "region": "SG",
    "age": 24,
    "gender": "nonbinary"
  }
}
```

For an authenticated Ryu user, the server uses that account as the stable subject. For an
anonymous tester, the app supplies a stable pseudonymous ID. The response contains only each flag's
decision and matched rule ID; targeting values are not stored. This API does not replace trusted
server-side checks for entitlements or other authorization.

An app flag can have the same form builder as a platform flag. Public Marketplace apps can accept applications from anyone with the link. An organization-only app requires the applicant to be a member of its publishing organization. The organization that published the app can review its applications and grant access to matching verified Ryu accounts.

### Rollout rules

Set a default allocation from 0 to 100 percent. Assignment is stable for the same subject and flag. Rules run in order; a rule's conditions must all match before its enabled state and allocation apply. Add start and end times to schedule a rollout. The kill switch overrides every rule and grant immediately.

Target attributes can include plan or tier, organization or tester groups, device, platform, locale, region, age, gender, and app-defined attributes. An organization can create named tester groups on each published app and share a public invite link. A tester joins with a verified Ryu account; the evaluator supplies enrolled group keys from the account's server-side membership, so a caller cannot claim to belong to a tester group by sending a trait value. The evaluator ignores any `group` or `groups` attribute in the request, and an anonymous caller never matches a tester-group rule. The public invite page is `/feature-waitlist/invite`.

Marketplace beta, release-candidate, and other prerelease builds have their own rollout percentage
and tester-group gates in **Organization → Features → Manage app flags**. The gate covers every way
a build is fetched, including a direct download of its GitHub release archive by version. Ryu reviews each prerelease build before
it can be installed. Stable builds remain available while a prerelease is staged, and an app's
emergency kill switch can stop a feature independently of build publication.

Other attributes are sent with each evaluation request. Ryu evaluates them in memory and does not save them with a waitlist application. Treat client-supplied plan, device, locale, region, demographic, and app-defined attributes as targeting hints; enforce security and paid access on a trusted server.

## Public forms and applications

The public form page is `/feature-waitlist`, with the link parameters that the admin page sets. The page reads the form from this route:

```http
GET /api/feature-waitlists/public/form?scope=platform&key={flagKey}
```

For an app flag, include `scope=app`, `appId`, and `key`. Submit the email address, optional name, and answers to this route:

```http
POST /api/feature-waitlists/public/submissions
Content-Type: application/json
```

An application can be submitted once per email address for a flag. Form responses are visible to the Ryu admins for platform forms or the publishing organization for app forms. Removing a form disables its public link but keeps existing applications available to review.

Approving an application grants only that flag to the matching verified Ryu account. It does not
grant a Marketplace purchase, organization membership, plan entitlement, or another flag. The
kill switch and scheduled end time continue to apply.

For publishing and listing lifecycle details, see the [Marketplace guide](/docs/extend/develop/extensions/marketplace). Organization-owned app flags remain separate from the organization access controls described in [Authentication and organizations](/docs/security/authentication-organizations).
