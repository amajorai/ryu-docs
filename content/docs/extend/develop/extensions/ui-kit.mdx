Ryu apps use a shared, opinionated UI kit. The app chooses its data and domain workflow; the kit
chooses the visual grammar. This is intentionally similar to the useful part of shadcn's model:
the components are understandable source code in the repository, themed by semantic tokens, and
composed into product surfaces instead of hidden behind a remote design service.

Ryu App UI `v1` is the current stable contract version, not a partial-release marker. Every source
Companion app is required to mount through `RyuAppShell`; an app is not considered ported merely
because it imports the stylesheet.

## Source of truth

The package boundaries are deliberate:

- `@ryu/ui` owns controls, fields, dialogs, menus, badges, status, loading, and theme tokens.
- `@ryu/blocks/companion/app-ui` owns the fixed app roles: shell, toolbar, list, detail, form,
  empty state, and actions.
- `@ryu/app-host` owns the host seam: live theme subscription, root marking, and generic bridges.
- Ryu Desktop owns navigation chrome. Apps contribute `sidebar_sections` / `sidebar_buttons`; the
  same contributions render in the normal Ryu shell and in standalone Ryu App windows.
- A satellite owns its domain state and bridge adapter. It does not copy or fork the visual system.

The one packaging exception is a dependency-free static satellite mirrored outside the monorepo:
it may carry a small contract-compatible v1 adapter, but it must use the same semantic tokens and
manifest-owned navigation. It cannot create a second visual language.

The public catalog and examples should be generated from these same package exports. A catalog page
that drifts from the package is not a UI kit; it is a screenshot gallery.

## Fixed roles

Use the smallest role that expresses the surface:

| Role | Primitive |
| --- | --- |
| Root surface | `RyuAppShell` |
| Title and actions | `RyuAppToolbar` |
| Page grouping | `RyuAppMain`, `RyuAppSection` |
| Collections | `RyuAppList`, `RyuAppListSection`, `RyuAppListItem` |
| Selected content | `RyuAppDetail` |
| Data entry | `RyuAppForm`, `RyuAppField` |
| No data / recovery | `RyuAppEmpty`, `RyuAppActions` |

Domain-specific editors, graphs, canvases, and media surfaces may keep their specialized renderer,
but their chrome and generic controls still use the Ryu kit. This keeps a canvas app recognizable as
Ryu without pretending a graph node is a generic list row. A left navigation rail is not domain art:
move it into the app manifest so Ryu can render it consistently in both hosted and standalone modes.

## App contract

```css
@import "tailwindcss";
@import "@ryu/ui/app-ui.css";
```

```tsx
import { markCompanionAppRoot } from "@ryu/app-host/companion-theme";
import { RyuAppShell } from "@ryu/blocks/companion/app-ui";

markCompanionAppRoot(document.getElementById("ryu-plugin-root"));

export function App() {
  return <RyuAppShell>{/* domain content */}</RyuAppShell>;
}
```

The repository contract check covers every source Companion entrypoint. It verifies the root marker,
the shared stylesheet, the `@ryu/blocks` dependency, and the `RyuAppShell` composition. Primary
navigation is still owned by Desktop: app-specific sections belong in manifest sidebar
contributions, while editor, canvas, and inspector rails remain domain content inside the shell.

The repository checks every first-party Companion package for the v1 root marker and the shared
stylesheet import. Rendered checks still matter: inspect light/dark themes, focus, narrow widths,
empty/error/loading states, and reduced motion.
