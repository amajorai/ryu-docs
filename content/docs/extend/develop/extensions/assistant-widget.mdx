Ryu ships the assistant surface as a reusable UI package. Use it when your product needs the
same quiet floating or docked chat experience as Desktop but owns its own route, transport, or
conversation policy.

## Core-backed surface

For a Ryu Core node, the ready-made wrapper owns the chat loop and only needs a target:

```tsx
import { RyuAssistantCoreChat } from "@ryu/assistant-widget";

<RyuAssistantCoreChat
  agentId="ryu"
  placement="floating"
  target={{ token: nodeToken, url: "http://127.0.0.1:7980" }}
/>;
```

The target token stays in the host's memory and is sent directly to Core. Do not put it in an
iframe URL or expose it in a public page. Core still owns agent routing, grants, model policy,
and the chat stream.

## React surface

Install or link `@ryu/assistant-widget`, then pass the same state that your chat transport already
uses:

```tsx
import { RyuAssistantChat } from "@ryu/assistant-widget";

export function AssistantPanel({ messages, sendMessage, status, stop }) {
  return (
    <RyuAssistantChat
      messages={messages}
      onSend={({ content }) => sendMessage({ text: content })}
      onStop={stop}
      placement="floating"
      status={status}
    />
  );
}
```

`placement="docked"` fills a sidebar-sized surface, `placement="inline"` fits an existing page
layout, and `placement="floating"` uses the compact panel treatment. Floating mode uses the
minimal composer automatically: attachments and secondary controls stay available through the
host's chosen affordances, while the conversation remains the focus.

The primitive owns the transcript, composer, title row, recent-chat handoff, and responsive
geometry. The host owns `messages`, `status`, `onSend`, `onStop`, authentication, and the server
transport. This keeps provider credentials and product-specific policy out of the UI package.

For custom composition, use the lower-level `RyuAssistantWidgetFrame`,
`RyuAssistantWidgetHeader`, and `RyuAssistantRecentChats` primitives. Desktop uses these same
seams, so a shared surface does not need a second copy of the shell layout.

## Hosted iframe

When the assistant is served by another route or deployment, use the safe iframe wrapper:

```tsx
import { RyuAssistantWidgetIframe } from "@ryu/assistant-widget";

<RyuAssistantWidgetIframe
  className="h-[620px] w-full"
  src="https://assistant.example.com/embed"
  title="Ryu assistant"
/>;
```

The wrapper uses a sandbox, a strict cross-origin referrer policy, and no ambient browser
permissions by default. The hosted page must handle its own sign-in/session and must not put a
Core bearer token in the iframe URL. If the hosted assistant needs a capability, expose it through
the hosted page's own server boundary.

## Complete public-site assistant

If you want a working documentation assistant without wiring a transport, use the package's
existing `RyuAssistantWidget`. It provides browser-local inference or an explicitly approved local
Ryu Core node, grounds answers in public Ryu documentation, and keeps node credentials in the
current tab.

```tsx
import { RyuAssistantWidget } from "@ryu/assistant-widget/docs-assistant";

<RyuAssistantWidget docsBaseUrl="https://docs.ryuhq.com" />;
```

Choose the React primitive when your application already owns chat state. Choose the complete
widget when you want the public-site assistant behavior as-is. Both share the same compact visual
direction; the iframe form is a delivery boundary, not a second chat implementation.
