A **color theme** in Ryu is not its own kind of marketplace listing. It is a plugin whose only
contribution is `contributes.themes` — the same shape VS Code and Zed settled on. That choice is the
whole design: a theme inherits install, uninstall, enable/disable, versioning, signing, the store
detail page, reviews and the trust scorecard from the plugin system, and a plugin that ships a theme
*alongside* other things (an app with a matching skin) is expressible without inventing anything.

A theme ships **no code at all**. That makes it the one contribution family that is safe with **zero
permission grants**: the shell only ever assigns your `tokens` to CSS custom properties, and never
evaluates them. The worst a hostile theme can do is look bad.

`"runnables": []` is not a placeholder — it is the point. There is nothing to run.

## The fields

| Field | Role |
| --- | --- |
| `id` | Stable id, persisted as the user's selection. **Namespace it with your plugin id** (`@acme/midnight-theme:midnight`) so two plugins cannot collide and a rename does not lose the selection. |
| `label` | The name shown in Settings → Appearance. |
| `mode` | `"light"` or `"dark"` — which slot this theme fills. |
| `preview` | The four colors the picker paints as a swatch **before** the theme is applied. Drawn as inline style, so use plain CSS colors. |
| `tokens` | CSS custom property → value. Open by design: a new design-system token reaches clients without a Ryu release. |

### Light and dark are two entries, not one theme

Ryu keeps an **independent preset per mode** — a user can run your light theme by day and someone
else's dark one at night. A matched pair is therefore two entries in the same `themes` array, each
with its own `id`, not one theme with two halves.

<Callout type="warn">
  Cover the whole token set. The shell applies your `tokens` over whatever the previous theme left in
  place, so a property you omit keeps its old value — which is how a half-specified dark theme ends up
  with white borders. The list in the example above is the minimum.
</Callout>

## Export a theme you already made

You do not have to write the token map by hand. Build the theme in the app, then export it:

1. **Settings → Appearance → Color theme**, adjust the colors and **Save as preset**.
2. Select your saved theme. A **share** button appears next to the picker.
3. Click it — a complete `manifest.json` lands on your clipboard.
4. Save it into a new folder and publish.

The export re-keys the theme under a plugin id, because the locally saved id embeds the moment you
saved it and would change on every re-export.

## Publish it

Publish the theme from its GitHub repository after attaching an immutable `.ryupack` release:

```bash
bunx ryu github-publish https://github.com/your-org/your-theme
```

Themes land on the **Themes** shelf in the Store. See
[Marketplace](/docs/extend/develop/extensions/marketplace) for the listing, pricing and signing story, and
[GitHub topic discovery](/docs/extend/develop/extensions/github-topic-discovery) for the free index.

For a versioned folder or archive that carries a theme definition and its safe appearance metadata,
see [Portable packages](/docs/extend/develop/extensions/portable-packages). The theme contribution
itself remains declarative: colors, typography, sizing, spacing, density, radius, and layout defaults
are data, while executable code and undeclared permissions are not part of a theme package.

## How it reaches the picker

Installed themes appear in Settings → Appearance under an **Installed** header, above the built-ins
and below the user's own saved themes. They are **enabled-gated**: disabling the plugin removes its
themes from the picker, and a user who had one selected falls back to the shipped default. Updating
the plugin repaints the window immediately — no restart.
