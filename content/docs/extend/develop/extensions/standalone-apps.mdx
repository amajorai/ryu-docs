---
title: "Ship a Standalone App"
description: "Package a Ryu app as a desktop executable while keeping the same manifest, Companion, and Core seams."

A Ryu app can run in two modes without maintaining two implementations:

- **Hosted mode**: the app is installed into an existing Ryu desktop node and uses that node's
  Core, Gateway, data directory, and lifecycle.
- **Standalone mode**: the same app manifest and Companion are carried inside a small Ryu desktop
  executable. The executable starts the normal local Ryu services for that app and opens the app's
  Companion as its first surface.

The app still owns its domain behavior and data. Core owns generic lifecycle, permissions, routing,
and process supervision. This boundary is what lets an expense tracker, CRM, or research app ship
as a focused product without forking the Ryu runtime.

Standalone is app-first by design. The executable does not open the Ryu navigation shell; it mounts
the app's Companion as the window's primary surface. Ryu's host providers, capability bridge, and
Core/Gateway processes remain behind that surface so the app keeps the same governed integrations
as it has inside Ryu.

## Build one

From a Ryu checkout, pass either an `apps-store` directory name or its manifest id:

```bash
bun run --cwd apps/desktop build:standalone expenses
# or
bun run --cwd apps/desktop build:standalone @ryu/expenses
```

The command builds the Companion when needed, validates the app manifest, carries the UI into the
desktop host, names the executable from the app manifest, and produces the platform bundles
supported by the local Tauri toolchain. Use `--debug` for a development build. `--prepare-only`
validates the carriage and sidecar plan without building the desktop executable.

The app id, version, manifest, UI hash, and sidecar declarations travel together as one versioned
bundle. The portable `.ryupack` format remains useful for marketplace and hosted installation; it is
the app package, not the standalone executable itself.

The Core install boundary accepts self-contained UI carriages up to 32 MiB (with a 40 MiB bundle
request envelope). Keep larger model weights, media, and other binary assets in declared sidecars
or app-managed storage rather than embedding them in the HTML carriage.

The app host bridge accepts a bounded 64 MiB JSON envelope for `storage:kv` calls. Apps that persist
binary data should still use their own file/object layout and send only the bytes they need; the
limit exists to keep large editor assets possible without making the global Core request limit
unbounded.

## What is shared

Standalone and hosted apps use the same:

- `manifest.json`, runnable ids, permissions, Companion entrypoint, and public mounts;
- Core install/enable lifecycle and Gateway authorization path;
- `@ryu/app-host` bridge and `@ryu/ui` / `@ryu/blocks` design seams;
- app-owned storage and domain APIs.

Do not add an app-specific server, route, credential store, or port table to Core. Declare the
sidecar and its public mount in the app manifest so the generic host can supervise it in either
mode.

## External app example

An app can live in its own repository and still be a first-party Ryu Marketplace app. Backstage is
the reference shape: its editor remains in `amajorai/backstage`, while the repository carries a
Ryu manifest and a host build that produces one self-contained Companion HTML file.

```bash
bun install
VITE_RYU_HOST=true bun run --cwd apps/desktop build
bun run --cwd /path/to/ryu/apps/desktop build:standalone /path/to/backstage
```

The standalone builder reads the app's root `manifest.json`, packages the built Companion, and
boots it through the same Core/Gateway lifecycle as an app from `apps-store/`. Local AI stays
account- and BYOK-free. Cloud models and provider keys are configured in Ryu Console; the app
receives only the governed Ryu bridge, never provider credentials.

## Sidecar carriage

The standalone host carries local Rust sidecars and Bun sidecars that expose a compiled `--compile`
artifact with the executable. It points the manifest's declared command at that private resource.
This keeps those apps usable without a separately installed sidecar binary.

Apps whose sidecars are Python, Electron, or another externally provisioned runtime still use the
normal Core-provisioned sidecar contract. Their standalone shell is buildable, but the runtime
artifact must be supplied by the app's release channel or installation environment. This is
intentional: embedding a language runtime or browser engine into every app would change the
distribution boundary and security review.

Apps without a Companion can still be packaged as a standalone node-facing app, but they do not
have a visual first screen until they declare a Companion runnable. Add the Companion through the
manifest rather than special-casing the app in Desktop.

## App startup

At first launch the native host waits for Core to mint the local node token, installs the carried
manifest through Core's normal lifecycle API, enables it, adopts that local token in the webview,
and mounts the Companion. The startup path is bounded and does not require a Ryu account for local
operation. Subsequent launches reuse the app-private data directory and start the same generic
Core/Gateway process pair. If the carried bundle has a newer app version, the host sends it through
the local update carriage before enabling the app again; existing approved grants and enabled state
are preserved. Hosted installation follows the regular install and enable API instead.

Local models remain local-node configuration: they can run without a Ryu account or BYOK. Cloud
providers and user-supplied keys still require the normal Gateway/Console setup on the node; the
standalone executable never embeds provider credentials.

The native macOS traffic lights use the ordinary app-window inset for standalone products, while
the full Ryu shell keeps its tab-strip alignment. This keeps platform controls outside the app's
Companion content.

## Release checklist

- Keep `manifest.json` authoritative for lifecycle, permissions, public mounts, and sidecars.
- Keep the Companion self-contained and on the shared theme/bridge seams.
- Build the app in both hosted and standalone modes.
- Verify that every local sidecar has a release artifact for each target platform.
- Verify the app's data migration and update behavior before publishing a new executable.
- Do not put credentials in the bundle; provider accounts remain node or Gateway configuration.

<Callout type="info">
  Standalone packaging changes the distribution shape, not the app ownership model. If the app
  works only because it reaches into Desktop or Core internals, it is not ready to ship this way.
</Callout>
