Ryu keeps native effects behind the host. An extension can ask what its current host can do, then
request a specific, grant-gated operation. It never receives a node token, an Expo object, a browser
permission object, a raw BLE handle, or an operating-system process handle.

## Discover first

The local `host.capabilities` bridge is read-only and does not prompt for permission:

```ts
const capabilities = await window.ryu.host.capabilities();

if (capabilities.haptics) {
  // Request a haptic only after the host reports support.
}

if (capabilities.liveActivities || capabilities.dynamicIsland) {
  // Offer an activity affordance; do not assume that an iPhone is configured.
}
```

The descriptor is deliberately a set of booleans rather than a native object:

| Field | Meaning |
| --- | --- |
| `platform` | The host family (`browser`, `ios`, `android`, or `unknown`) |
| `browserNotifications` | The browser can offer its notification primitive |
| `localNotifications` | The host can schedule a local notification and the current permission state allows it |
| `pushRegistration` | Push registration is available on this build and device |
| `haptics` | The host can provide a short haptic feedback signal |
| `sounds` | A host sound or notification sound path is available |
| `liveActivities` | The host can update a Live Activity |
| `dynamicIsland` | The host can present the relevant Dynamic Island surface |
| `androidOngoingNotifications` | Android's ongoing notification surface is available |
| `quickActions` | The host can expose app quick actions |
| `hardwareBleRelay` | The host can reach an approved hardware relay |

Support is not authorization. A `true` value means that the host knows how to perform the operation;
the extension still needs the matching approved grant, and the user may still need to approve a
platform permission or an action. Treat a missing field or an unknown platform as unsupported.

## Bridge families

| Family | Desktop / web | Browser extension | Mobile | CLI / TUI | Hardware |
| --- | --- | --- | --- | --- | --- |
| Notifications | Core's governed notification tools and app notification feed | Browser notification support is discoverable; Core remains the privileged sender | Local notifications, push registration, Android ongoing notifications, and the notification feed are host-owned | Use Core notifications or a channel; do not assume a terminal OS notification | Send through the approved host or channel, never through an arbitrary device address |
| Haptics and sounds | Host-dependent; feature-detect | Browser vibration/audio APIs are feature-detected | Haptics and native notification sounds are available through mobile host actions when granted | No portable haptic contract; use status, bell, or a rendered state only when the TUI supports it | Hardware feedback belongs to the device relay contract |
| Live status | Live activities and dock/summary contributions | Use a contributed activity or widget | Live Activities, Dynamic Island, and Android ongoing notifications are separate capabilities | Render a live row, table, or feed item; the terminal owns repainting | Hardware dashboards can consume a relay projection |
| Widgets and views | `contributes.widgets` plus `ui.render`; Library views are host-rendered | Same contribution contract in the extension dashboard | Companion UI runs in a locked WebView | Declarative views render as terminal list/table surfaces | Hardware apps expose a narrow dashboard/control projection |
| Device and hardware | Host-specific capability descriptor | Browser APIs only, where available | Device status, quick actions, BLE discovery, and approved hardware operations | No raw device APIs; call Core tools | BLE relay and hardware APIs are explicit, allowlisted surfaces |

The same manifest can declare a contribution for several surfaces. The host filters it by surface,
then applies grants and approval policy. A contribution that has no renderer on the current surface
degrades to an unavailable entry; it must not silently fall back to a more privileged host.

## Mobile actions

Mobile owns the native permission boundary. Use the host's native action methods —
`native.haptics`, `native.notifications.create`, and `native.liveActivities.update` — for short,
user-visible effects such as a haptic, a bounded notification, or an update to an activity. Keep
titles and bodies concise, use an idempotent activity key, and end an activity when the work is
finished. Browser, desktop, and extension hosts may provide standards-based haptic and notification
fallbacks, but only when the host permission is already granted; a plugin never triggers a
permission prompt. Live Activities remain mobile-only.

The matching manifest grant is the plugin authorization boundary. Platform permission, foreground
requirements, and any model-tool confirmation are separate checks. A missing requirement returns a
structured failure, so the UI can explain the unavailable state instead of treating it as success.
The action grants are `native:haptics`, `native:notifications`, and
`native:live_activities`; they are intentionally separate from the Core inbox grant
`notifications:send`.

Do not use a notification as a hidden background scheduler, a haptic as a success proof, or a Live
Activity as a second data store. Persist durable state in Core, and treat all native effects as
projections of that state.

For a model-driven native operation, the mobile tool family also exposes device capabilities,
navigation, notifications, haptics, Live Activity updates, quick actions, calendar, contacts,
files, media, and hardware operations. The mobile host applies its tool permission and foreground
rules before invoking those operations. A plugin should prefer the host bridge for its own UI effect
and use a governed tool call for an agent operation.

## CLI, TUI, and hardware boundaries

CLI and TUI hosts expose the portable part of the contract: Core tools, contribution discovery,
keyboard-safe declarative views, and status updates. The current terminal renderer supports list and
table/data-table projections and can add more renderers without changing the plugin's data contract.
It intentionally does not pretend to provide iOS haptics, Dynamic Island, or a browser notification
permission.

Hardware is a separate trust boundary. A hardware-facing app or plugin should declare the relay or
device capability it needs, send typed actions through the hardware API, and consume sanitized
status/events. Raw BLE sessions and device tokens stay in the trusted host. If a relay is absent,
the contribution should show an unavailable state and leave the rest of the app usable.

## Security and portability checklist

1. Call `host.capabilities` before presenting a native affordance.
2. Request the narrowest grant for the one effect you need.
3. Treat permission denial, a background app, a missing device, and an old host as normal outcomes.
4. Keep durable records in Core; native effects are replayable projections.
5. Never read tokens, permissions, native module objects, or host filesystem paths from a frame.
6. Test the same manifest on desktop, extension, mobile, CLI/TUI, and a host with every capability
   disabled.

declarations, [built-in tools](/docs/core/built-in-tools) for governed operation ids, and
[mobile](/docs/mobile) for the native tool surface.
