---
title: "Learning loop: from experience to capability"
description: "Use feedback, experience, and approval-gated skills as the first low-risk RSI loop."
---

The [Learning app](/docs/apps/learning) is the lowest-risk place to start recursive improvement.
It turns real work into a candidate reusable capability without requiring a model retrain or an
autonomous code change.

## The loop today

```text
real task → feedback/experience → skill proposal → approval → reusable skill → measured reuse
```

The important boundary is that a proposed skill is not active merely because a model generated it.
The approval Inbox is the promotion gate.

<Steps>

<Step>

### Capture a useful signal

Capture a response rating, a correction, a successful procedure, or a repeated failure. A signal
should point to a task and a bounded piece of context; it should not turn every private conversation
or secret into training material.

Learning is opt-in and supports exclusions. Keep the consent decision visible, reversible, and
scoped to the actual data being used.

</Step>

<Step>

### Distill a procedure

Ask Learning to make a skill from a chat or run when the result contains a reusable method rather
than a one-off answer. A good skill states when it applies, what inputs it expects, the steps to
follow, and how to verify the result.

Do not confuse a memory fact with a skill. A memory helps retrieve context; a skill changes how an
agent performs a class of tasks.

</Step>

<Step>

### Review and activate

Review the proposed skill in the approval Inbox. Check provenance, scope, secrets, prompt-injection
content, and whether it duplicates or conflicts with an existing skill. Activation should create a
versioned skill and preserve the previous version as the rollback target.

</Step>

<Step>

### Measure reuse

Run the skill against the task set that motivated it and a small regression set. Record whether the
task completed, whether the agent needed fewer corrections, and whether latency, cost, privacy, or
safety regressed.

The [Learning API reference](/docs/extend/develop/api-reference/core/learning) exposes the current
capture, scoring, synthesis, and experience surfaces for integrations.

</Step>

</Steps>

## What to add for RSI

The next Learning improvements should make the loop compound rather than merely accumulate files:

1. **Skill lineage.** Link a skill to the experience rows, campaign, prompt, and model context that
   produced it.
2. **Skill scorecards.** Give every active skill a small, stable task set and a regression score.
3. **Retirement.** Detect stale, duplicated, or conflicting skills and propose deactivation with a
   reversible change.
4. **Conflict resolution.** Show which skill won when multiple skills apply, and let a user inspect
   the evidence rather than silently merging instructions.
5. **Feedback attribution.** Keep the human signal, evaluator signal, and downstream task outcome
   distinct so a skill cannot optimize for a proxy while making real work worse.
6. **Learning-to-experiment handoff.** Turn a promising skill proposal into a Research campaign
   automatically, with the current skill as the baseline and the proposed skill as the candidate.

## The first Ryu dogfood loop

Use Ryu to improve one bounded Ryu workflow, such as documenting a new app or triaging a failing
test:

1. Capture two or three representative tasks and the current successful procedure.
2. Let Learning propose a skill that describes the procedure and its checks.
3. Review and activate it only after removing private context and unrelated instructions.
4. Replay the tasks with and without the skill.
5. Keep the skill only if the holdout tasks improve without a safety, cost, or latency regression.

This is already useful without claiming that Ryu can rewrite Core. It gives the platform a measured
first step toward building the next tool or app more reliably.
