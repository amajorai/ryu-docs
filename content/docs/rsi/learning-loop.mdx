---

The [Learning app](/docs/apps/learning) is the lowest-risk place to start recursive improvement.
It turns real work into a candidate reusable capability without requiring a model retrain or an
autonomous code change.

## The learning loop

```text
real task → feedback/experience → skill proposal → approval → reusable skill → measured reuse
```

A proposed skill is not active because a model generated it. The approval Inbox is the promotion
gate.

<Steps>

<Step>

### Capture a useful signal

Capture a response rating, a correction, a successful procedure, or a repeated failure. A signal
should point to a task and a bounded piece of context; it should not turn every private conversation
or secret into training material.

<Callout type="warn">
Both Learning opt-ins are off by default. Learning distills skills from your chats on its own only
after you turn on **Learn skills from my chats** in the Learning settings tab. See the [Learning app](/docs/apps/learning#settings-tabs)
page for both opt-ins.
</Callout>

</Step>

<Step>

### Distill a procedure

Ask Learning to make a skill from a chat or run when the result contains a reusable method, not a
one-off answer. A good skill states when it applies, what inputs it expects, the steps to
follow, and how to verify the result.

Do not confuse a memory fact with a skill. A memory helps retrieve context; a skill changes how an
agent performs a class of tasks.

</Step>

<Step>

### Review and activate

Review the proposed skill in the approval Inbox. Check provenance, scope, secrets, prompt-injection
content, and whether it duplicates or conflicts with an existing skill. Keep the previous version as
the rollback target.

</Step>

<Step>

### Measure reuse

Run the skill against the task set that motivated it and a small regression set. Record whether the
task completed, whether the agent needed fewer corrections, and whether latency, cost, privacy, or
safety regressed.

The [Learning API reference](/docs/extend/develop/api-reference/core/learning) lists the capture,
scoring, synthesis, and experience routes for integrations.

</Step>

</Steps>

## What a complete loop needs

A complete loop keeps more context than the skill body alone.

<Callout type="warn">
This list describes the target loop. Not every item is available in the Learning app today; check
the [Learning app](/docs/apps/learning) page for what ships.
</Callout>

1. **Skill lineage.** Link a skill to the experience rows, campaign, prompt, and model context that
   produced it.
2. **Skill scorecards.** Give every active skill a small, stable task set and a regression score.
3. **Retirement.** Detect stale, duplicated, or conflicting skills and propose deactivation with a
   reversible change.
4. **Conflict resolution.** Show which skill won when multiple skills apply, and let a user inspect
   the evidence rather than silently merging instructions.
5. **Feedback attribution.** Keep the human signal, evaluator signal, and downstream task outcome
   distinct so a skill cannot optimize for a proxy while making real work worse.
6. **Learning-to-experiment handoff.** Turn a promising skill proposal into a Research campaign
   automatically, with the current skill as the baseline and the proposed skill as the candidate.

## A bounded example

Start with one bounded workflow, such as documenting a new app or triaging a failing test. Run the
[complete campaign](/docs/rsi/roadmap#a-complete-campaign) with the current procedure as the
baseline and the Learning skill proposal as the candidate. Remove private context and unrelated
instructions before activation, replay the tasks with and without the skill, and keep the skill
only if the holdout tasks improve without a safety, cost, or latency regression.

The change stays measurable, and the agent gets no authority over Core. The same pattern works for
a tool, app, or workflow when its owner supplies the right checks.
