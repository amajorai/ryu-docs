---
title: "Adoption roadmap"
description: "A practical sequence for making Ryu's learning, experiments, and self-building loops compound."
---

The fastest path to full RSI is not a giant autonomous agent. It is a sequence of small, durable
contracts that make the next improvement easier to measure and safer to promote.

## Phase 1: connect the evidence

Make every Learning proposal and Research campaign answer the same questions:

- What objective is changing?
- What is the baseline artifact and task set?
- What data and permissions were used?
- What candidate diff was produced?
- Which evaluations and host checks ran?
- Who approved it, and how is it rolled back?

This is the proposed improvement record from the [operating model](/docs/rsi/operating-model).
Start as a shared contract and projection before building a new dashboard or service.

## Phase 2: create a Ryu golden set

Build a small, versioned RyuBench covering the work Ryu must do to improve Ryu:

- onboard a new node and reach a first useful task;
- create or refine an agent with the correct tools and permissions;
- turn a successful procedure into a reviewed skill;
- run an Experiment and correctly keep or reset a candidate;
- author and verify a deterministic tool;
- build an app with the shared shell and bridge;
- diagnose an unavailable dependency without claiming success; and
- update public docs without inventing unsupported behavior.

Keep task completion, safety, cost, latency, accessibility, and documentation correctness as
separate dimensions. A single blended score hides the failure that matters.

## Phase 3: bridge Learning and Experiments

Add explicit handoffs:

1. Learning proposes a skill or procedure.
2. Research creates the baseline and holdout task sets.
3. Experiments compare the candidate and baseline.
4. The owning app reviews and promotes the winner.
5. Learning records the downstream outcome and proposes retirement when the skill becomes stale.

The same handoff should work in the other direction: an Experiment that discovers a reusable
procedure can submit it to Learning instead of writing directly into the active skill set.

## Phase 4: make self-building a factory

Standardize the build ladder:

- skill and prompt changes use review plus replay;
- workflows use schema and budget gates;
- deterministic tools use write → verify → install;
- apps use manifest, single-file bundle, shared UI, and host proof;
- sidecars use typed, authenticated lifecycle boundaries; and
- Core/Gateway changes stay human-owned until their repository and security gates are complete.

The factory should generate the evidence pack as part of the build, not ask someone to reconstruct
it after the fact.

## Phase 5: dogfood Ryu's product work

Choose a narrow internal target and run the whole loop for it. Good first targets are documentation
completeness, app contract migrations, or a recurring test-triage workflow. Do not begin with a
system that can rewrite security or release policy.

For every candidate, keep the diff, task-set digest, scores, screenshots or recordings where needed,
approval, and rollback target. Publish only the reusable artifact and public evidence; keep private
traces private.

## Phase 6: compound across the ecosystem

Once the local loop is reliable, add:

- Marketplace provenance and compatibility checks for shared skills and apps;
- opt-in sharing of redacted task sets and evaluator definitions;
- cross-node comparisons that preserve tenant and privacy boundaries;
- scheduled idle-window campaigns with explicit budgets; and
- release notes that identify the improvement evidence without overstating deployment proof.

Model fine-tuning can be part of this phase, but it should remain downstream of the skills,
evaluation, and promotion loop. A better skill or workflow often compounds faster and with less risk
than changing model weights.

## The first complete campaign

Use this as the acceptance test for Ryu's RSI design:

1. Pick one real Ryu task and write its success and safety criteria.
2. Snapshot the current artifact and run the baseline set.
3. Capture a failure or improvement signal in Learning.
4. Create a Research campaign with development, regression, and holdout cases.
5. Let Ryu propose exactly one bounded candidate.
6. Run tests, evals, policy checks, and the appropriate rendered proof.
7. Review the evidence and promote or reject the candidate.
8. Exercise rollback, then run the next task with the promoted version.
9. Record whether the downstream outcome improved.

When this works for a skill, repeat it for a deterministic tool, then an app. That is the path from
“Ryu can help build Ryu” to a full, measurable, and governable recursive improvement system.
