The central design decision is simple: **Learning and Experiments should share an improvement
contract, not share an implementation.** Learning owns experience and skill proposals. Research
owns campaign execution and winner selection. Core owns execution and workspaces; Gateway owns
policy, measurement, budgets, and audit; the owning app owns its domain state.

That follows Ryu's [platform consistency rules](/docs/start-here/architecture/platform-consistency):
one owner, one canonical contract, explicit projections, and evidence that says what actually ran.

## The proposed improvement record

The first shared slice of that primitive now exists as a versioned pure-data contract. Learning cycle
responses and Research campaign initialization can carry an optional `improvementRunId`, so a
proposal, experiment, and later promotion can be joined without either app becoming the authority
for the other. The full durable record and promotion store are still the next platform step.

| Field | Why it matters |
|---|---|
| Objective | Names the user or system outcome being improved. |
| Scope | Identifies the artifact kind: skill, prompt, memory rule, workflow, tool, app, route, or model. |
| Baseline | Pins the current artifact, task set, model/provider context, and starting score. |
| Candidate | Records the proposed diff, parent version, and input snapshot digest. |
| Evaluation | Links deterministic tests, offline evals, safety checks, and host/browser proof. |
| Guardrails | Sets cost, latency, privacy, capability, and regression limits. |
| Decision | Uses explicit states such as draft, running, verified, promoted, rejected, or rolled back. |
| Provenance | Records the user, agent, campaign, skill set, and source traces that produced it. |
| Rollback | Points to the last known-good version and the operation that restores it. |

The record should be append-only for decisions and evidence. Mutable settings can be updated through
their owning app, but a past score or approval must not silently change underneath an old result.

<Callout type="info">
The correlation field is additive and does not promote anything by itself. The owning app still
controls approval, activation, and rollback; an invalid reference is rejected before Research starts
a workspace. The next step is to persist the complete improvement record and its evidence envelope.

## Core record API

The first durable projection is node-local and protected by Core's normal node-admittance boundary:

- `POST /api/improvements` creates a draft record;
- `GET /api/improvements` returns bounded newest-first history;
- `GET /api/improvements/{id}` reads one record; and
- `POST /api/improvements/{id}/transition` applies one guarded lifecycle transition.

The transition endpoint accepts the candidate, evaluation evidence, guardrail result, decision, and
rollback reference needed for that transition. It validates the whole resulting record before the
SQLite update, so a rejected transition cannot leave a half-promoted record behind. The API is a
Core persistence and lifecycle seam; it does not execute an experiment or silently approve a change.

The Learning cycle and Research workspace APIs can carry the same opaque `improvementRunId`, which
lets an owner join experience, experiment, evidence, and promotion history without copying private
conversation content between stores.
</Callout>

## Where each responsibility belongs

| Responsibility | Owner | Example projection |
|---|---|---|
| Execute a task, workflow, tool, or experiment | Core or the owning app | A campaign attempt or a tool call. |
| Decide whether it is allowed and how much it may spend | Gateway | Grants, budgets, firewall, evaluator policy, and audit. |
| Capture a user experience and propose a skill | Learning | Experience log and approval request. |
| Generate candidates and compare variants | Research | Campaign, proposal lease, attempt, and winner. |
| Render progress and decisions | Desktop, Web, Mobile, or Companion | A bounded view of the same run. |
| Publish the public contract | Fumadocs | Usage, authoring, safety, and evidence guidance. |

Do not put a second policy engine inside the Learning app, or a second skill store inside Research.
The apps should link to the same run, while retaining their distinct product boundaries.

## Promotion states

Promotion should be a monotonic, inspectable path:

```text
draft → baseline → candidate → verified → approved → canary → promoted
                         ↘ rejected
promoted → rolled back
```

The exact storage can evolve, but the semantics should not. A candidate that has only been generated
is not verified. A candidate that passed an offline score is not automatically safe to run. A canary
that improved one benchmark is not a global promotion until its guardrails and holdout checks pass.

## A useful separation

Keep three signals separate:

- **Learning signal:** a human reaction, correction, successful procedure, or repeated failure.
- **Experiment signal:** a controlled comparison against a baseline.
- **Promotion signal:** an authorized decision that the artifact may affect future work.

This prevents a thumbs-up from becoming an automatic code release and prevents a model judge from
being the sole authority for its own improvement.

## How to use this now

Until the shared record lands, make the fields explicit in each campaign or design note:

- name the objective and baseline before changing anything;
- keep candidate changes in a bounded workspace;
- run a fixed task set plus a regression and safety set;
- attach the result to the Learning entry or Research campaign;
- require approval for activation; and
- record the previous version and the rollback action.

The [guardrails](/docs/rsi/guardrails) page defines the minimum evidence by change class, and the
[adoption roadmap](/docs/rsi/roadmap) turns this model into implementation phases.
