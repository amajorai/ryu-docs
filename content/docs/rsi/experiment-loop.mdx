title: "Experiment loop: from hypothesis to winner"
description: "Use Experiments and evals to compare bounded candidates before they affect future work."
---

The [Research app](/docs/apps/research) provides the second half of RSI: controlled search over a
versioned workspace. Its Experiments companion shows durable campaigns and attempts, while the
research tools prepare one proposal at a time, run it under bounded limits, and keep only a
direction-aware improvement.

## The loop today

```text
objective → baseline → one proposal → bounded run → score → keep/reset → next proposal
```

When history becomes large, Research can ask the RLM capability to analyze the campaign snapshot
before preparing the next variant. That is recursive analysis of evidence, not permission to skip
the experiment's budget, policy, or winner decision.

See [Evals & Audit](/docs/gateway/evals-audit) for the shared evaluator catalog and [Run an eval](/docs/learn/cookbook/run-an-eval)
for the user-facing replay path.

## What an RSI campaign should optimize

Prefer an artifact with a clear boundary and a measurable effect:

| Candidate | Example objective | Required comparison |
|---|---|---|
| Skill | Fewer corrections on a recurring task | Baseline agent with no skill versus the candidate skill. |
| Prompt or agent config | Better task completion | Same model, tools, and task set; only the prompt/config changes. |
| Workflow | Fewer handoffs or retries | Same inputs and budgets; compare terminal outcomes and cost. |
| Deterministic tool | Correct output for edge cases | Contract tests, case table, and repeated sandbox execution. |
| App UI | Faster or clearer completion | Interaction tests, accessibility states, and rendered host proof. |
| Provider route | Better quality/cost/latency tradeoff | Fixed dataset, policy checks, and the same judge configuration. |

Do not use a vague objective such as “make the agent smarter.” State what gets better, what must
not get worse, and when the campaign must stop.

## The holdout rule

Every campaign needs at least three sets:

- **Development cases** that help the proposal improve.
- **Regression cases** that protect known behavior and safety boundaries.
- **Holdout cases** that are not used to choose the next proposal.

The holdout prevents a campaign from learning the evaluator's wording instead of the user's task.
If there is no suitable holdout, label the result exploratory and do not call it a general
improvement.

## The handoff back to Ryu

When a candidate wins, Research should produce an evidence envelope that Learning, the app owner,
or the release process can consume:

1. campaign and attempt identifiers;
2. baseline and candidate versions;
3. task-set digests and evaluator configuration;
4. score deltas and guardrail results;
5. bounded logs and reasoning references;
6. approval status and rollback target.

The candidate is still only a proposal until its owning surface promotes it. A winning skill can go
to Learning. A winning tool or app can go through its package checks. A routing change belongs to
Gateway policy. A Core or security change requires a human-reviewed code change and its normal test
and release gates.

## Use Experiments to build Ryu

The most valuable early campaigns are Ryu's own recurring jobs:

- Which skill makes app documentation more complete without inventing behavior?
- Which agent/tool sequence resolves a failing test with fewer retries?
- Which evaluator catches regressions before a rendered host check?
- Which app shell or shared primitive improves task completion across Companion surfaces?

Each campaign should change one variable at a time. If a result changes the skill, prompt, tool,
model, and UI together, it may still be a useful product trial, but it is not diagnostic enough to
feed a compounding loop.

## A useful future surface

The Experiments companion should eventually let a user:

- start a campaign from a Learning proposal;
- see the active baseline and the exact candidate diff;
- open the evaluator evidence and rendered proof;
- promote a winner into the owning app's version history; and
- roll back without deleting the campaign history.

That makes Research the search surface and the owning app the source of truth for the promoted
artifact.
