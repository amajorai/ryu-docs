This page lists behavior changes that an existing integration can notice
without changing its code, using the same format as
[API Changes](/docs/reference/api/changelog): each entry says what changed,
who is affected, and what to do. **Must** marks a step an existing caller needs
to keep working as before; **may** marks an optional step that uses the new
behavior.

The `@ryuhq/services` SDK, the `ryu-services` CLI, and the Python
`ryu_sdk.services` client already handle every entry below.

## Unreleased

These changes are not yet assigned to a release.

### Managed Agents

#### Managed Agents 429s name the limit they hit

**What changed.** A `429` from the per-organization write limit, the sessions
created per hour, or the user event bytes per day carries `RateLimit-Policy`
and `RateLimit` named after `details.limit`. For the byte limit the policy says
`qu="content-bytes"`. A `401` carries a `WWW-Authenticate` challenge with
`resource_metadata`; the API still takes API keys, not OAuth tokens.

**Who is affected.** Clients that back off on Managed Agents `429`s.

**What to do.** Keep waiting for `Retry-After`. You may read `RateLimit` to see
how much is left. Do not start an OAuth flow from the `401` challenge. See
[Managed Agents rate limits](/docs/standalone/managed-agents-api#rate-limits).

#### Managed Agents accepts a quoted Idempotency-Key and keeps one request id

**What changed.** An `Idempotency-Key` may be sent bare or as a quoted
Structured Field string (`"create-agent-0001"`); both name the same key.
`X-Request-ID` is still a server-assigned `req_<32 hex>` that ignores an
inbound value, and it is now the same id the API host logs for the request.

**Who is affected.** Clients whose HTTP library quotes header values, and
anyone who quotes a request id to support.

**What to do.** Nothing is required. You may send the key in either form. See
[Idempotency](/docs/standalone/managed-agents-api-requests#idempotency).

### Notify

#### Notify negotiates problem details

**What changed.** A request whose `Accept` header names
`application/problem+json` gets errors as RFC 9457 problem details: `type`
(the error code's link on the Notify API page), `title`, `status`, `detail`,
`instance`, `code`, and `docs`, plus the usual `ok`, `message`, `requestId`,
and `error`. Only the legacy `type: "notify.error"` is replaced. Without that
`Accept` value, including `*/*`, errors keep the `application/json` envelope.

**Who is affected.** Nobody unless they opt in.

**What to do.** Nothing is required. You may send the `Accept` value and
branch on `code`. See [Endpoint surface](/docs/standalone/notify-api#endpoint-surface).

#### Notify publishes send the RateLimit fields

**What changed.** When a publish limit is configured, every publish response,
its `429` included, carries `RateLimit-Policy` and `RateLimit` for the
`publish` bucket. A `429 rate_limited` carries `Retry-After`.

**Who is affected.** Clients that publish at a high rate.

**What to do.** Keep waiting for `Retry-After` on a `429`. You may read
`RateLimit` to pace publishes. See
[Authentication and limits](/docs/standalone/notify-api#authentication-and-limits).

#### Notify answers 405 with Allow, HEAD, and OPTIONS

**What changed.** A known Notify path called with a method it does not serve
answers `405 method_not_allowed` with an `Allow` header. `HEAD` works wherever
`GET` does, and `OPTIONS` on a known path answers `204` with `Allow`. Path
validation still runs first, so a malformed path segment is `400`.

**Who is affected.** Clients that treat every non-`2xx` as `404`.

**What to do.** You may read `Allow` on a `405`. See
[Endpoint surface](/docs/standalone/notify-api#endpoint-surface).

#### Notify signs webhooks with Standard Webhooks headers

**What changed.** Deliveries to a webhook destination that has a secret carry
`webhook-id`, `webhook-timestamp`, and `webhook-signature` beside the
unchanged `X-Ryu-Notify-Signature`. A destination's custom `headers` cannot
use those three names, and Notify never forwards a stored value of them.

**Who is affected.** Receivers of Notify webhook deliveries, and destinations
whose custom headers use a `webhook-*` name.

**What to do.** You may verify deliveries with the `webhook-*` headers, which
also cover the delivery id and the timestamp, and deduplicate on
`webhook-id`. You must rename a custom destination header that uses one of the
three names. See
[Destinations and delivery history](/docs/standalone/notify-api#destinations-and-delivery-history)
and [SDK webhooks](/docs/standalone/sdk/webhooks#notify).

#### Notify decodes RFC 2047 encoded words on the topic route

**What changed.** `POST /v1/topics/:topic` decodes RFC 2047 encoded words in
`Title`, `Tags`, `Click`, and `X-Ryu-Source`, in UTF-8, ISO-8859-1, and
US-ASCII, as ntfy does. A word Notify cannot decode is stored as sent. A word
that decodes to a control character or a bidirectional text control, more
than 64 encoded words, or a header over 8,192 characters that contains an
encoded word answers `400 invalid_request`. `Actions` is never decoded.

**Who is affected.** Publishers that send text shaped like `=?UTF-8?B?…?=` in
those headers. Before, Notify stored that text as sent.

**What to do.** If you publish literal encoded-word text, you must wrap the
whole value in one UTF-8 B word, as the SDKs do, to keep storing it as sent.
You may send text outside Latin-1 as encoded words. See
[Destinations and delivery history](/docs/standalone/notify-api#destinations-and-delivery-history).

### Box

#### Box marks replayed creates

**What changed.** Replaying a Box create or fork with the same
`Idempotency-Key` and body answers with the header
`Idempotent-Replayed: true`, beside the `box.existing` type.

**Who is affected.** Clients that tell a replay from a new Box.

**What to do.** You may read either signal. See
[Box idempotency and errors](/docs/standalone/box-api#idempotency-and-errors).

#### Box refuses replays of a deleted Box with their own code

**What changed.** Repeating a Box create or fork with the `Idempotency-Key`
and body of a Box that has since been deleted answers
`409 idempotency_key_resource_deleted`. Before, it answered `404 not_found`.
A fork replay is now answered from its key before the source Box is loaded,
so it returns the fork (`200 box.existing`) or this `409` even after the
source Box was deleted; before, it answered `404 not_found` once the source
was gone. A fork's key is also bound to its source Box: the same key and body
sent to `POST /v1/boxes` or to a fork of another Box answers
`409 idempotency_conflict` instead of replaying the first fork. A fork sent
before this change and replayed after it answers `409 idempotency_conflict`.

**Who is affected.** Code that catches `RyuNotFoundError`, or checks
`code === "not_found"`, after `box.create` or `box.fork` to detect a deleted
Box. Clients that reuse one key across create and fork, or across forks of
different Boxes.

**What to do.** You must check for `RyuConflictError` with
`code === "idempotency_key_resource_deleted"` to detect a deleted Box, and
keep handling `not_found` for self-hosted Box servers built before this
change. Send a new `Idempotency-Key` to create another Box; the old key stays
spent. Use one key per create or fork. Retry behaviour is unchanged: the SDKs
never retried this `409`. See
[Box error codes](/docs/standalone/box-api#idempotency_key_resource_deleted).

#### Box negotiates problem details

**What changed.** A request whose `Accept` header names
`application/problem+json` gets errors as RFC 9457 problem details (`type`,
`title`, `status`, `detail`, `instance`, `code`, `docs`, then the envelope's
other members). Without it, including `*/*`, errors keep the `box.error`
envelope.

**Who is affected.** Nobody unless they opt in.

**What to do.** Nothing is required. See
[Box idempotency and errors](/docs/standalone/box-api#idempotency-and-errors).

#### Box commands that cannot start complete with 126 or 127

**What changed.** On the filesystem driver, a command that cannot start
completes like a shell: exit code `127` when the command or its interpreter is
not found, `126` when it cannot be run, or with `126` when `cwd` is missing,
not a directory, or not accessible, with the reason on stderr. It was an HTTP
`404` or `400`. File reads and writes on that driver answer `404`, `400`,
or `403` for a missing path, a path of the wrong kind, or a permission
failure, instead of `500`.

**Who is affected.** Clients that branch on an HTTP error to detect a missing
command, and clients that pass `cwd` and expect an HTTP error when it is
wrong.

**What to do.** You must read the exit code and stderr of the completed
command. See
[Box idempotency and errors](/docs/standalone/box-api#idempotency-and-errors).

### Connect

#### Connect negotiates problem details and sends challenges

**What changed.** A request whose `Accept` header names
`application/problem+json` gets errors as RFC 9457 problem details, followed
by `code`, `docs`, `error`, and `ok`. A `401` carries
`WWW-Authenticate: Bearer realm="ryu-connect"`, with `error="invalid_token"`
for a rejected bearer; a webhook signature failure carries
`WWW-Authenticate: Webhook-Signature realm="ryu-connect-webhooks"`. Errors
returned before a route runs, such as an oversized or invalid body, now carry
`x-request-id` too. MCP JSON-RPC errors and compatibility-mode upstream bodies
keep their own format.

**Who is affected.** Nobody needs to change; clients that opt in or read the
challenge see the new fields.

**What to do.** Nothing is required. You may send the `Accept` value and branch
on `code`. See [Connect errors](/docs/standalone/connect-api#errors).

#### Connect Composio executions send the RateLimit fields

**What changed.** When a tenant's Composio binding sets `maxCallsPerMinute`,
native Composio executions and their `429 rate_limited` carry
`RateLimit-Policy: "composio-calls";…` and `RateLimit`.

**Who is affected.** Clients that run Composio tools often.

**What to do.** You may read `RateLimit` to pace calls, and wait for
`Retry-After` on a `429`. See [Connect errors](/docs/standalone/connect-api#errors).

### Sites

#### Sites negotiates problem details

**What changed.** A request whose `Accept` header names
`application/problem+json` gets errors as RFC 9457 problem details that keep
the `error` member and add `type`, `title`, `status`, `detail`, `instance`,
`code`, `docs`, and, on the management listener, `requestId`. Without it,
including `application/json` and `*/*`, errors keep their shape.

**Who is affected.** Nobody unless they opt in.

**What to do.** Nothing is required. See
[Problem details](/docs/standalone/sites-api#problem-details).

#### Sites management responses carry X-Request-ID and a challenge

**What changed.** Every management response, errors included, carries
`X-Request-ID` (`req_` and 32 hex characters). A `401` carries
`WWW-Authenticate: Bearer realm="ryu-sites"`, with `error="invalid_token"`
when a bearer was sent but rejected. The management listener's own body cap
is now 2,200,000 bytes, above every route's limit, so a body over a route's
limit gets Sites's `413 too_large` error with a request id; only a body over
that cap still gets an empty `413`.

**Who is affected.** Clients that report Sites failures.

**What to do.** You may log `X-Request-ID` with every failure. See
[Bearer authentication](/docs/standalone/sites-api#bearer-authentication).

#### Sites visitor 429s say when to retry

**What changed.** A visitor request refused by the per-visitor or per-Site
budget answers `429 rate_limit` with `Retry-After` and the `RateLimit` and
`RateLimit-Policy` fields, which name the budget that ran out.

**Who is affected.** Visitor-facing code that retries on `429`.

**What to do.** You should wait for `Retry-After` before retrying. See
[Visitor routes](/docs/standalone/sites-api#visitor-routes).

### Gateway

#### Gateway answers every response with x-request-id and JSON errors

**What changed.** Every Gateway response, errors included, carries
`x-request-id`; on a model call it matches the audit record. Errors the router
produces on its own are the JSON error envelope instead of plain text or an
empty body: an unknown route is `404 not_found`, a wrong method is
`405 method_not_allowed` with `Allow`, a malformed or mistyped body is `400`,
`415`, or `422` with `invalid_request_error`, a body over the limit is
`413 request_too_large`, and a request that started no response within 300
seconds is `504 gateway_timeout`. Statuses are unchanged. Passthrough routes
and a few older routes keep their own bodies. Browser callers can read
`x-request-id`, `Retry-After`, `RateLimit`, `RateLimit-Policy`, `x-provider`,
and `x-routed-model`.

**Who is affected.** Clients that read these error bodies as text.

**What to do.** You must parse the JSON envelope if you read these bodies, and
branch on `error.code`. You may log `x-request-id` with every failure. See
[Ryu Gateway errors](/docs/standalone/gateway-api#errors-and-request-ids).

#### Gateway reports the provider's status

**What changed.** An upstream provider failure is a `502 provider_error`, and
when the provider's status is known it is in `error.upstream_status`.

**Who is affected.** Clients that retry every `502`.

**What to do.** Do not retry unchanged when `error.upstream_status` is a `4xx`
other than `408`, `425`, or `429`. The provider would refuse the same request
again. See [Ryu Gateway errors](/docs/standalone/gateway-api#errors-and-request-ids).

#### Gateway per-key 429s send the RateLimit fields

**What changed.** On every inference route, a refusal by the per-key request
or burst limit is `429 rate_limit_exceeded` with `Retry-After`,
`RateLimit-Policy`, `RateLimit`, and `error.retry_after`. Organization and
token-per-minute refusals carry none of these.

**Who is affected.** Clients that back off on Gateway `429`s.

**What to do.** Wait for `Retry-After` when it is sent; otherwise back off on
your own schedule. See
[Ryu Gateway errors](/docs/standalone/gateway-api#errors-and-request-ids).

### Passport

#### Passport errors all have a code

**What changed.** Every Passport error is JSON with `error` and a stable
`code`, including errors that had only a message before, such as
`404 not_found` for a missing connection. An unknown route is
`404 not_found`, a wrong method is `405 method_not_allowed` with `Allow`, and
a body that is not JSON, lacks a JSON `content-type`, or does not match the
route is `400`, `415`, or `422` with `invalid_request`. A request whose
`Accept` header names `application/problem+json` gets the same error as
RFC 9457 problem details that keep the `error` member. The OAuth callback
still answers with a short page for the browser.

**Who is affected.** Clients that match Passport error messages or read empty
error bodies.

**What to do.** You should branch on `code` instead of the message. See
[Passport errors](/docs/standalone/passport-api#errors).

#### Passport deduplicates connection creates

**What changed.** `POST /v1/connections` honours an `Idempotency-Key` in
Passport builds that report `features.idempotency_keys: true` in
`GET /v1/capabilities`. A replay answers with `Idempotent-Replayed: true` and
creates no second connection. The same key with a different body is
`409 idempotency_conflict`, a retry while the first request runs is
`409 idempotency_in_progress` with `Retry-After`, and a malformed key is
`400 idempotency_key_invalid`.

Before, Passport ignored the header. Records are kept for up to 24 hours.

**Who is affected.** Clients that retry a connection create, and clients that
already send `Idempotency-Key` on creates, including HTTP clients that add one
automatically.

**What to do.** If you already send `Idempotency-Key` on connection creates,
you must use one unique key (1 to 255 printable ASCII characters, bare or
quoted) per intended connection: a reused key now replays the first result or
answers `409`, and a malformed key answers `400`. You may otherwise send a key
on creates; retry only when the capability is reported. See
[Create a connection](/docs/standalone/passport-api#create-a-connection).
