This page lists behavior changes that an existing integration can notice
without changing its code. The reference pages linked from each entry describe
the current behavior in full. None of these changes moves a route to a new
major version; see [Versioning and Deprecation](/docs/reference/api/versioning)
for what ships without one.

Each entry says what changed, who is affected, and what to do. **Must** marks
a step an existing caller needs to keep working as before; **may** marks an
optional step that uses the new behavior.

The `@ryuhq/services` SDK, the `ryu-services` CLI, and the Python
`ryu_sdk.services` client already handle every entry below. If you call the
services yourself, check the entries for the services you use.

## Unreleased

These changes are not yet assigned to a release.

### Hosted API at api.ryuhq.com

#### Every response carries X-Request-ID

**What changed.** Every response from `https://api.ryuhq.com` carries an
`X-Request-ID` header, and browsers can read it cross-origin. A request that
sends its own safe `X-Request-ID` gets the same value back, except on Managed
Agents routes, which always answer with a server-assigned id; otherwise the
server assigns a `req_` id. The server's error logs record the same id.

**Who is affected.** Clients that log failures or contact support.

**What to do.** You may log `X-Request-ID` with every failure and quote it to
support. To correlate with your own logs, you may send your own id; do not
start it with `req_`, which is reserved and gets replaced. See
[Request IDs](/docs/reference/api/errors#request-ids).

#### Unhandled server errors are always problem details

**What changed.** An unhandled server error on any `/api/...` route answers
`500` with an `application/problem+json` body (`code: "internal_error"`) and
`instance` set to the request path, whatever the request's `Accept` header
says.

**Who is affected.** Clients that read a `500` body as plain JSON or text.

**What to do.** You must parse `application/problem+json` on a `500` if you
read its body. Quote the time and `X-Request-ID` when you contact support. See
[Errors](/docs/reference/api/errors#internal_error).

#### API key rate limits send Retry-After and the RateLimit fields

**What changed.** When an organization API key has its own requests-per-minute
limit, every `/api/v1` response to it carries `RateLimit-Policy` and
`RateLimit` for the `key` policy. Over the limit, the answer is `429` with an
`application/problem+json` body (`code: "rate_limited"`) and `Retry-After`.
Before, these responses carried neither the RateLimit fields nor `Retry-After`.
Managed Agents routes keep their own error format; see the
[Managed Agents entry](/docs/reference/api/changelog-services#managed-agents-429s-name-the-limit-they-hit).

**Who is affected.** Clients of an organization API key that has a limit.

**What to do.** Wait for `Retry-After` seconds on a `429`. You may read
`RateLimit` to slow down before you reach the limit. See
[API key limits](/docs/reference/api/rate-limits#api-key-limits).

#### Idempotent replays need a valid key

**What changed.** The API key is authenticated before a stored result is
replayed. A request whose key is missing, revoked, expired, or not allowed gets
the route's own refusal, such as `401` for a revoked key, instead of the stored
response. A stored result belongs to the API key's id, and when a request sends
both `x-api-key` and `Authorization: Bearer`, the `x-api-key` value is the
credential.

**Who is affected.** Clients that retry a write with an `Idempotency-Key` after
rotating or revoking the key that made the first attempt.

**What to do.** Retry with the same key that made the first attempt while it
is still valid. After a `401` on a retry, you must check the outcome with a
read before you send the write again under a new key. See
[Idempotency](/docs/reference/api/idempotency).

#### Scope refusals have their own code

**What changed.** A valid API key without the scope a route needs gets `403`
with `code: "insufficient_scope"`. Hosted Mail also names the scope in
`requiredScope` and in the `WWW-Authenticate` header.

**Who is affected.** Clients that treat every `403` as one error.

**What to do.** You may branch on `code` and create a key with the named
scope. See [Errors](/docs/reference/api/errors#insufficient_scope).

#### OAuth clients can request Mail scopes, and mail:manage only by name

**What changed.** The authorization server's `scopes_supported` keeps the node
capability scopes and adds `mail:read` and `mail:send`, which hosted MCP's
Mail tools honour. Ryu also accepts `mail:manage` but does not list it in
`scopes_supported`, so a client that requests every listed scope does not
ask for it. `mail:manage` is never granted by default: an authorization
request without a `scope` does not ask for it, whether it is a GET or a POST,
and the consent screen leaves it off until the user chooses it. With it, an OAuth grant can create inboxes and
nothing else that `mail:manage` covers. The other hosted-only scopes,
`messaging:read`, `messaging:manage`, `prompts:read`, and `prompts:manage`,
are not advertised, and an OAuth client cannot request them. Ryu API keys can
carry any of them.

**Who is affected.** OAuth (MCP) clients that read `scopes_supported` or want
hosted Mail, Messaging, or prompt registry access.

**What to do.** Nothing is required. To create inboxes through hosted MCP, you
must name `mail:manage` in the authorization request, or step up when
`mail_create_inbox` answers with an `insufficient_scope` challenge that names
it. A request for an unadvertised
hosted-only scope is refused, so for Messaging or the prompt registry, create
a Ryu API key with the scope in the console. See
[Official Ryu MCP OAuth](/docs/security/authentication-mcp#official-ryu-mcp-oauth).

### Prompt registry

#### The prompt registry accepts Ryu API keys

**What changed.** The organization prompt registry accepts a `ryu_` API key in
`x-api-key` with the `prompts:read` or `prompts:manage` scope, plus
`X-Ryu-Organization` for a personal key. `prompts:manage` is never included
unless you choose it when you create the key.

**Who is affected.** Code that reads or publishes organization prompts.

**What to do.** You may create a key with `prompts:read`, or choose
`prompts:manage` to publish. See
[Prompts](/docs/extend/develop/sdk/prompts#registries).

#### The prompt registry caps prompts, versions, and session writes

**What changed.** An organization holds at most 5,000 prompts and a prompt at most
1,000 versions; going over returns `409` with `prompt_quota_exceeded`. A console
session may make 60 prompt writes a minute and then gets `429` with
`Retry-After`. API keys keep their per-key limits.

**Who is affected.** Scripts that create prompts or commit versions in a loop.

**What to do.** You may delete unused prompts, and you must retry after
`Retry-After` on a `429`. See
[Prompts](/docs/extend/develop/sdk/prompts#registries).
