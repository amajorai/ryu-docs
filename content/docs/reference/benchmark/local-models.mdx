title: Local Models
description: Run RyuBench against a local model on your node, including how the node routes the model id and what tool-calling needs.
---

RyuBench is model-agnostic. The `direct-tool` driver sends each request, with a model id, to the
node's OpenAI-compatible `/v1/chat/completions`. On a local node that endpoint serves local
runtimes, so a local model needs no extra RyuBench setup. Read the tool-calling caveat below
before you trust a low local score.

## How the node routes a model id

`POST /v1/chat/completions` on Core is a direct proxy to a local runtime. It chooses the runtime
from the model id:

| Model id starts with | Upstream |
|---|---|
| `zeroclaw` | ZeroClaw on `127.0.0.1:42617` |
| `openclaw` | OpenClaw on `127.0.0.1:3118` |
| anything else | Ollama on `127.0.0.1:11434` |

The proxy does not go through the Gateway. Gateway routing, policy, and metering do not apply to
these calls, and the `x-ryu-raw-tools` header that the driver sends has no effect here. The
`--model` value must be a model the upstream can serve, such as an Ollama model you have pulled.

```bash
# runs against the local Ollama model
bun run --cwd apps/benchmark run:bench --model qwen2.5:7b-instruct --k 3
```

<Callout type="warn">
  A cloud model id, such as a Claude or GPT id, is also sent to Ollama by this proxy. It works
  only when your Ollama install serves that id. RyuBench does not route the model track to a
  cloud provider.
</Callout>

The response `usage` carries `prompt_tokens` and `completion_tokens`, so `tokens/task` is
reported for local models. Token **cost** is zero unless you add the model to `RYUBENCH_PRICES`;
see [Scoring and governance](/docs/reference/benchmark/scoring#cost-normalization).

## Tool-calling

The `direct-tool` driver gives the model one tool (`ryu_request`) and reads `tool_calls` back. A
model that does not emit OpenAI `tool_calls` scores near 0 on this driver. That result says the
model cannot drive this scaffold. It does not say the model cannot operate Ryu.

To get tool calls from a local model:

1. Pull a tool-capable model. Its chat template must support tools. Small instruct quants often
   do not. This depends on the model and the runtime, not on Ryu.
2. Run a small slice first and check that agents get created (see the recipe below).

## If your local model cannot tool-call

Use the **`ryu-agent`** driver. It drives the task through Ryu's own agent runtime
(`POST /api/chat/stream`), where Ryu's loop handles tool orchestration instead of the model
emitting `tool_calls`.

```bash
bun run --cwd apps/benchmark run:bench --driver ryu-agent --model <local-id>
```

<Callout type="info">
  Keep model-track and harness-track numbers separate. A local model measured under `ryu-agent`
  (native orchestration) is not comparable to a model measured under `direct-tool` (the model
  does its own tool-calling). The scorecard pins the driver so the two never merge.
</Callout>

## Practical recipe

```bash
# 1. pull a tool-capable model into the local Ollama

# 2. run a small, cheap slice first to confirm tool_calls flow
bun run --cwd apps/benchmark run:bench --model <local-id> --category agent --k 1

# 3. if agents are created, run the full Tier-A suite
bun run --cwd apps/benchmark run:bench --model <local-id> --k 3 --out ./.ryubench/local
```

If step 2 shows every task failing the `agent-exists` check ("was not created"), the model is not emitting tool
calls. Try a model with a tools template, or switch to the `ryu-agent` driver.
