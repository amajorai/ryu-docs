title: RyuBench

RyuBench measures how well a model, or a harness, can operate Ryu. A task asks the model to build a
working workflow, configure an agent card, use the tool registry, set a Gateway policy, run RAG
over a Space, wire a monitor, or drive a chat to a stateful outcome.

RyuBench is a Bun CLI (`ryubench`) in the Ryu monorepo at `apps/benchmark`.

<Callout type="warn">
  `apps/benchmark` is not included in the public `amajorai/ryu` repository. The `bun run --cwd
  apps/benchmark` commands in this section need a Ryu monorepo checkout.
</Callout>

<Callout type="info">
  RyuBench scores by **asserting persisted state through the public API after the agent
  acts**. It never judges the transcript. A task passes only if the thing it asked for
  exists on the node afterward (the tau-bench pattern).
</Callout>

## Scoring properties

- **Execution-based.** Hidden assertions check real state. No LLM in the scoring path.
- **Model vs harness kept separate.** Two tracks that never mix (see below).
- **Cost-normalized.** Reports `$/task` and `tokens/task` beside pass rate, estimated from the
  token usage the node reports.
- **Reproducible.** Every score is a pinned tuple written into the scorecard.
- **pass^k.** Each task runs `k` times; `pass^k` is the fraction of tasks that passed *every*
  time, and it exposes lucky single-shot passes. See [scoring and governance](/docs/reference/benchmark/scoring).

## The three layers

"Model vs harness" covers three layers. Ryu's configurable agent setup keeps them separate:

| Layer | In Ryu terms | On the model track |
|---|---|---|
| **Model** | the LLM in the `chat_model` slot | **varies**; this is what you rank |
| **Scaffold** | the agent setup: prompt, tool allowlist, the loop | fixed to one reference |
| **Platform** | Core + Gateway | pinned version |

This yields two leaderboards:

1. **Model track** (apples-to-apples). One fixed scaffold (the `direct-tool` driver
   gives the model exactly one tool, a `ryu_request` HTTP proxy, per mini-swe-agent's single-tool
   philosophy) and you swap only the model.
2. **Harness track** (open, self-reported). Vary the whole scaffold, or compare Ryu against
   other stacks. Kept physically separate so scaffold gains never touch the model number.

<Callout type="warn">
  No governed results are published yet. The [RyuBench page](https://ryuhq.com/benchmark) explains
  the method and will show the model-track leaderboard once measured scorecards exist.
</Callout>

## Two doc conditions

Run the same suite twice:

- `--docs no-guidelines` (default) - the model on its priors plus a short route cheatsheet.
- `--docs with-guidelines` - inject the reusable **Ryu AI rules** (`apps/benchmark/guidelines/ryu-ai-rules.md`).

The gap measures model capability and Ryu documentation quality. If a model needs the rules to
operate Ryu, that is a UX finding.

## Tasks and tiers

Task set `0.2.0` has 50 tasks. The 47 **Tier A** tasks check deterministic API state and form the
scored core. The 3 **Tier B** tasks check computer-use reachability (Ghost and Shadow), need a
sandbox VM, and are reported separately. Do not compare scorecards across task-set versions. See
[Tasks](/docs/reference/benchmark/tasks) for every category and how it is verified.

## Quickstart

RyuBench drives a **running** node (Core on `:7980`, Gateway on `:7981`). On the default
`direct-tool` driver, `--model` must name a model that the node's `/v1/chat/completions` can
serve; see [Local models](/docs/reference/benchmark/local-models) for how the node routes it.

```bash
# list the 50 tasks
bun run --cwd apps/benchmark list

# run the Tier-A model track, 3 reps per task, against a local node
bun run --cwd apps/benchmark run:bench --model <model-id> --k 3

# the with-docs condition, only two categories
bun run --cwd apps/benchmark run:bench --docs with-guidelines --category workflow --category agent

# re-render a saved results file to Markdown
bun run --cwd apps/benchmark src/index.ts score ./.ryubench/scorecard-<id>.json
```

Node and Gateway targets and auth come from flags or environment variables: `RYU_NODE_URL`
(default `http://127.0.0.1:7980`), `RYU_NODE_TOKEN`, `RYU_GATEWAY_URL` (default
`http://127.0.0.1:7981`), `RYU_GATEWAY_KEY`, `RYUBENCH_MODEL`, `RYUBENCH_DRIVER`, `RYUBENCH_DOCS`,
and `RYUBENCH_K`. Flags win over environment variables. Scorecards (JSON and Markdown) land in
`--out` (default `./.ryubench`).

<Callout type="warn">
  RyuBench mutates node state (it creates workflows, agents, spaces, monitors). Point it at a
  scratch/dev node, not a node you care about. Tasks namespace everything they create by run id
  and best-effort tear it down, but treat the target node as disposable.
</Callout>
