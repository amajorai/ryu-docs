---
title: Kernel boundary benchmark
description: Measure the local cost of plugin-shaped dispatch, event fan-out, and serialization without mixing it into RyuBench agent scores.
---

Ryu has two different benchmark questions:

- **RyuBench** asks whether a model or harness can operate Ryu and leave the correct persisted
  state.
- **The kernel-boundary track** asks how much local overhead a plugin-shaped call adds to a tight
  loop.

Keeping these numbers separate prevents model quality, network latency, and runtime dispatch from
being collapsed into one misleading score.

## Run it

From the repository root:

```bash
bun run --cwd apps/benchmark run:boundary
bun run --cwd apps/benchmark run:boundary --operations 50000 --samples 9 --fanout 1,5,20
bun run --cwd apps/benchmark run:boundary --json
```

The benchmark runs locally and does not require a model, Core node, Gateway, or network service.
The direct row in each family is the same-process baseline for that machine.

## What it measures

| Scenario | What it represents |
| --- | --- |
| Direct chunk | Kernel work with no plugin dispatch |
| Cached service call per chunk | An in-process capability/service call after activation |
| Registry lookup per chunk | Rediscovering a provider on every hot-path call |
| Event fan-out | Independent observers attached to each chunk |
| Serial transforms | A sequential plugin pipeline where each step changes the value |
| JSON per chunk | Serialization at the smallest event granularity |
| JSON batched | The same data moved as one batch |
| Direct reload cycle | Baseline registration-map activation/disposal |
| Generation reload/dispose | Activation, disposer cleanup, and stale-callback rejection |

The command reports median and p95 nanoseconds per operation and the overhead relative to the
matching direct baseline. Repeat comparisons on the same machine and runtime. The output is a
regression signal, not a production latency guarantee.

## Boundary rule

Ryu keeps the control plane dynamic and the data plane specialized:

| Prefer a plugin boundary for | Keep kernel-owned and tight |
| --- | --- |
| Model providers, tools, sandboxes, storage, schedulers, UI contributions, optional telemetry | Authorization, grant enforcement, event sequencing, backpressure, token/chunk assembly, queues, crypto |

Resolve providers once per run, cache service handles, and batch persistence or telemetry. A hook
that runs at a turn or tool boundary is usually a useful extension seam. A hook that runs for every
token or chunk needs an explicit performance budget and should be treated as an exception.

Ryu's approach is compatible with the service-and-event model described by [DeepSeek
Harness](https://github.com/deepseek-ai/deepseek-harness) and [Cordis](https://github.com/cordiverse/cordis):
the plugin contract can be broad while the hot data path remains bounded.
