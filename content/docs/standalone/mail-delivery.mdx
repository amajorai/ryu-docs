This page explains how Ryu Mail stores, receives, and sends messages, and how
to publish Mail activity to Ryu Notify. Mail separates durable message storage
from delivery. Receiving and reading messages work with the local database. Sending requires a configured transport
and creates an external side effect.

## Outbound delivery

`POST /api/mail/inboxes/:id/send` hands the selected message to the configured
transport. A successful response means the transport accepted the hand-off. It
does not prove that the recipient received the message, and the send cannot be
recalled.

Without a configured transport, inbox creation and receive/list/read operations
still work while sending is unavailable. Mail emits the outbound event only
after the hand-off succeeds, so consumers do not mistake a queued attempt for
accepted mail.

The send contract includes `cc`, `bcc`, `replyTo`, RFC headers, base64
attachments, labels, `references`, `inReplyTo`, and optional open tracking.
`Idempotency-Key` makes a send retryable without creating a second stored row;
the sender still has to treat a successful hand-off as irreversible.

Self-hosted Mail webhooks use a durable event envelope signed with Standard Webhooks
headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`, repeated as
`svix-*`), so Standard Webhooks and Svix libraries verify them. Webhooks created
by earlier versions keep their earlier `svix-signature` until their secret is
rotated; see [verifying deliveries](/docs/standalone/mail-api-webhooks#verifying-deliveries).
Subscriptions can be scoped to inboxes or pods and can select received, sent,
delivered, bounced, complained, rejected, and opened events. Delivery attempts
are recorded and retried; use the event log after reconnecting a WebSocket or
recovering from a process restart.

## Inbound storage

The inbound webhook accepts raw mail only after the per-inbox HMAC check. A
signed `X-Ryu-Timestamp` limits a captured delivery to a five-minute window and
lets Mail refuse its replay; an inbox can require it. Mail stores the message
body and attachment blobs in the process-owned data path. The HMAC secret is not
included in normal inbox or message responses.

Keep raw message content, attachment paths, transport credentials, and inbound
secrets inside the Mail boundary. Do not publish them to Notify or place them
in a model prompt.

When `RYU_SMTP_HOST` and `RYU_SMTP_PASSWORD` are set, the standalone process
sends directly through the local BYO SMTP transport. When Core credentials are
present, the same sidecar delegates to Core's node-owned SMTP capability, so
Core and standalone deployments share the MIME/threading behavior.

## Mail with Notify

Use [Ryu Notify](/docs/standalone/notify) when another product needs a small
event about Mail activity. The [Mail example](/docs/standalone/notify-streams#compose-with-box-and-mail)
uses separate credentials:

```text
Mail API bearer   -> read, create, and send Mail resources
Notify API bearer -> publish metadata to one Notify tenant
```

The example publishes the Mail message id, inbox id, sender, recipient, and
subject. It does not publish the message body, HTML, raw MIME, attachments,
SMTP credentials, or HMAC secret.

## Hosted organization behavior

For hosted Agent Inboxes, the organization owns its mailbox, its agent
addresses, its send policy, and their lifecycle state. The control-plane
session manages those resources without placing a Mail bearer or inbound
secret in the browser.

Hosted Agent Inboxes have different ownership, storage, entitlements, and
request fields from this standalone service. See [Hosted Agent
Inboxes](/docs/extend/develop/agent-inboxes) for that contract.
