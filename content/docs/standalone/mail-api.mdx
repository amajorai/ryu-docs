This reference covers the Ryu Mail HTTP API, for self-hosted Mail and for
hosted organization Mail where the two differ. The standalone Mail service
keeps the `/api/mail/*` route spelling used by the Companion UI. Protected routes use the standalone Mail bearer. Inbound
mail uses a per-inbox HMAC secret instead.

The canonical contract version is `v1` (also returned as `apiVersion` by the
status endpoint). Hosted organization Mail and the self-host sidecar keep the
same resource names and event vocabulary; only credential and ownership rules
differ.

## Inbox addresses

Creating an inbox requires a single `local@domain` address. The service lower-cases it and refuses
malformed values with `400`. Each address can belong to only one inbox on a node, compared without
regard to case. A second inbox with the same address returns `409` with
`code: "address_taken"`.

A store created by an earlier version may already hold two inboxes with one address. It still
starts, and new duplicates are still refused, but the database-level unique index is created only
after the duplicates are deleted or re-created.

## Bearer authentication

Protected calls send:

```text
Authorization: Bearer <RYU_MAIL_API_TOKEN>
```

The token is required before a standalone process may bind beyond loopback. It
is separate from Core sidecar credentials, Gateway keys, and the inbound HMAC
secret.

## Hosted Mail API keys

Hosted organization Mail (`https://api.ryuhq.com/api/mail/*`) also accepts a Ryu API key that
carries Mail scopes. Send it in `x-api-key`, or as `Authorization: Bearer <key>`. A node gateway
key in `x-gateway-key` still takes precedence when a request carries both, and an `x-api-key`
takes precedence over a signed-in session sent with it.

| Scope | Allows |
|---|---|
| `mail:read` | Every `GET` request, covering inboxes, messages, raw source, attachments, threads, drafts, lists, pods, domains, events, metrics, and webhooks |
| `mail:send` | Send, reply, reply-all, forward, create, update, delete, and send drafts, and label messages and threads |
| `mail:manage` | Create, change, and delete inboxes and addresses, lists, pods, domains, and webhooks (including headers and secrets), and delete messages and threads |

Scopes are chosen as cumulative levels when you create the key: **Read & send** grants
`mail:read` and `mail:send`. Each call checks the exact scope that the route needs. A classic token
includes at most **Read & send**; choose `mail:manage` explicitly on a fine-grained token.

- An organization key acts in its own organization. A personal key sends the organization ID in
  `X-Ryu-Organization`, and its owner must be a member.
- A key is also limited by the current organization permissions of what it acts for: the owner
  of a personal key, the role of the service account that holds a service-account key, or the
  member who created any other organization key. Reads need `mail.read`. Sends and changes need
  `mail.manage`, the same as a signed-in session.
- Sends count against that member's quota and billing in the organization, as they would from
  their session. A service-account key acts as the organization, so its sends and inboxes do not
  depend on the member who created it. The organization access policy and the key's own limits
  apply.
- An inbox's `webhookUrl` is returned only to a key with `mail:manage` whose principal holds
  `mail.manage`.
- Each inbox records which credential created it. Every inbox reply (reads, lists, creates,
  agent-inbox replays, updates and address changes) carries `createdWith`, which holds `via` (`session`, `api_key`, `oauth` for a hosted MCP app, or `gateway_key` for
  a node) and the matching ID (`apiKeyId`, `serviceAccountId`, `oauthClientId` or
  `gatewayCredentialId`). It holds IDs only, never a key or token, and is `null` for inboxes
  created before Ryu recorded it. Only callers who may manage Mail see `createdWith`. Those are a key
  with `mail:manage` whose principal holds `mail.manage`, a member with `mail.manage`, or a
  personal account's owner. `mail:read` keys, members without `mail.manage`, hosted MCP apps and
  node gateway keys do not, so a node never learns the organization's key or app IDs. `createdBy` is
  the member the credential acted for (`null` for a service-account key or a node).
- An inbox created with a key or a hosted MCP app adds a `mail.inbox.create` entry to the
  organization's audit log, with the same IDs and the new address.
- A missing scope returns `403` with `code: "insufficient_scope"` and the scope in
  `requiredScope`. A missing permission returns `403` with `code: "forbidden"`. A key that is not
  valid returns `401`. Platform admin routes accept only a signed-in session.

## Sends and retries

`POST /api/mail/inboxes/:id/send` accepts text and/or HTML, `cc`, `bcc`,
`replyTo`, RFC headers, base64 attachments, labels, `references`, and
`inReplyTo`. Use `Idempotency-Key` for a safe retry of a send; reusing a key with
a different request returns `409`. The API accepts at most 50 recipients and
8 MiB of decoded attachments (`413` above that), in a JSON body of up to 12 MiB.

Custom `headers` cannot set the sender, recipients, threading, or MIME
structure. `From`, `Sender`, `To`, `Cc`, `Bcc`, `Reply-To`, `Return-Path`,
`Message-ID`, `Date`, `Subject`, `In-Reply-To`, `References`, `Received`,
`MIME-Version`, `Content-*`, and `Resent-*` return `400`; use the typed fields
instead. At most 64 custom headers are accepted. Allow and block lists match the
parsed address, so a display name such as `Friend <a@example.com>` is checked
as `a@example.com`.

`trackOpens: true` adds a pixel only when `RYU_MAIL_PUBLIC_URL` (HTTPS) and
`RYU_MAIL_TRACKING_ENABLED=1` are configured; otherwise the HTML goes out
unchanged. Only an outbound message that carries its pixel records
`message.opened`.

## Hosted organization attachment limits

Hosted organization Mail fetches URL attachments only from public HTTPS destinations, with DNS
validation pinned to the connection. Redirects are not followed. A send reserves its monthly quota before
retrieving attachments and releases that reservation if retrieval fails.

One request accepts up to 20 attachments and 8 MiB of combined attachment data.
All URL attachments in a request share a ten-second retrieval deadline, including
DNS lookup. Each API worker admits up to 16 concurrent attachment retrieval
requests; further requests receive `429` and can retry after capacity is available.

## Scheduled drafts

A draft with `sendAt` is a scheduled send. It must pass the same recipient,
header, attachment, and list checks as a direct send when it is saved, and the
scheduler checks again when it fires. `sendAt` must be an RFC 3339 timestamp
with an offset, such as `2026-10-10T09:00:00Z`, and is stored in UTC. A value
without an offset returns `400`.

A scheduled draft that cannot be sent is marked `failed`, keeps its `sendAt`, and
is recorded as a `message.rejected` event with the reason. It is not retried
automatically, because a transport error can follow an accepted hand-off. Save
it again with a new `sendAt`, or send it with the draft send route.

A draft moves to `sending` while the scheduler or
`POST /api/mail/inboxes/:id/drafts/:draft_id/send` hands it to the transport, so
only one of them delivers it. Sending or editing a draft that is `sending` or
`sent` returns `409`. A refused send makes the draft editable again. When the
outcome is unknown, for example a keyed send whose transport result is
unresolved or a restart during the send, the draft stays `sending` so it is
never delivered twice; check the sent message and delete the draft.

## Errors

Hosted Mail answers an error as RFC 9457 problem details when the request
accepts JSON (the SDK always does), or as `{ "error": "...", "code": "..." }`
on the routes below. Self-hosted Mail answers `{ "error", "code"? }`. Branch on
`code`, not on the message. The
[Mail OpenAPI document](https://ryuhq.com/openapi/mail.json) lists the same
codes on each error response.

| Status | `code` | Meaning and what to do |
|---|---|---|
| 400 | `address_invalid` | `localPart` is not 1 to 64 lowercase letters, digits, dots, dashes, or underscores. |
| 400 | `invalid_request` | A request field is malformed; `field` names it. |
| 400 | `organization_required` | A personal `ryu_` API key was sent without `X-Ryu-Organization`. Name the organization the key's owner acts in. |
| 400 | `subprotocol_required`, `upgrade_failed` | The realtime upgrade did not offer `ryu-mail.v1`, or failed. Retry with a new ticket. |
| 401 | `unauthenticated` | No usable credential, or the realtime upgrade did not offer exactly one `ryu-ticket.<ticket>` subprotocol. |
| 401 | `invalid_ticket` | The realtime ticket is unknown, used, or expired. Mint a new one. |
| 403 | `insufficient_scope` | The Ryu API key lacks the scope the route needs (`requiredScope`, `missingScopes`). |
| 403 | `organization_mismatch` | `X-Ryu-Organization` names a different organization than the organization API key belongs to. Omit the header or send the key's own organization. |
| 403 | `forbidden` | The member or account the credential acts for lacks the Mail permission (`requiredPermission`), or the route does not accept this kind of credential. |
| 403 | `agent_inbox_forbidden` | A gateway key reached for another node's agent inbox. Use `<nodeId>:<agentId>` for the key's own node. |
| 403 | `oauth_client_not_allowed` | The organization has not allowed this OAuth app (`clientId`) to use its Mail. An owner or admin must allow it. |
| 403 | `org_access_denied`, `org_ip_not_allowed` | An organization access policy refused the request (`policyCode` says which), or the realtime connection came from an address the organization does not allow. |
| 404 | `agent_inbox_missing` | The agent has no inbox yet. Create it with `POST /api/mail/agents/:agentId/inbox`. |
| 409 | `address_reserved`, `address_blocked`, `address_unavailable` | The address cannot be issued (`address_unavailable` covers taken, held, and retired addresses without saying which). The body carries `address` and claimable `suggestions`. |
| 426 | `upgrade_required` | `GET /api/mail/realtime` was called without a WebSocket upgrade. |
| 429 | `send_rate_limited` | The inbox or account sent too fast: `limit` messages per `window`, counted per `subject` (`inbox` or `account`). Wait `retryAfterSeconds`, also sent as `Retry-After`. |
| 429 | `rate_limited` | Too many requests, realtime tickets, or open sockets. Wait for `Retry-After`. |
| 503 | `service_unavailable`, `policy_unavailable`, `realtime_store_unavailable` | A dependency is temporarily unavailable. Retry after `Retry-After`. |

A realtime socket answers a malformed or oversized subscription filter with a
`{ "type": "error", "code": "invalid_subscription" }` frame and stays open.

## Inbox and secret responses

The create and rotate-secret responses return `inbound_secret` once. List and
get inbox responses omit it. Treat the secret as sensitive and store it only in
the provider webhook configuration or another protected secret store. Webhook
signing secrets follow the same rule: the create response and a `rotateSecret`
update return `secret`, and other responses return `null`. Mail stores these
secrets encrypted; see
[sealing stored secrets](/docs/standalone/mail#sealing-stored-secrets).

The compatibility fields `created_at`, `inbox_id`, and
`provider_message_id` remain available to the Companion UI. The Mail service
owns the database and attachment blobs for its process.
