Ryu's standalone services run without the Desktop surface. Each service has its
own process, credential boundary, data directory, and versioned HTTP contract.
Run one beside Core, call it from another backend, or put a hosted control
plane in front of the same contract.

The sections in this area are organized by service. Start with the service
overview, then use its API and operations pages for the details.

## How the boundaries fit

The services own different kinds of state. Core still owns user identity,
workflow acknowledgements, desktop notifications, and the local
`/api/notifications/*` feed.

| Service | Owns | Main contract |
|---|---|---|
| [Ryu Gateway](/docs/standalone/gateway) | Governed model, tool, and Skill calls | OpenAI-compatible and Ryu APIs |
| [Ryu Box](/docs/standalone/box) | Persistent isolated workspaces | Ryu Box `/v1` API |
| [Ryu Mail](/docs/standalone/mail) | Agent inboxes, messages, and inbound mail | Authenticated Mail API plus per-inbox HMAC |
| [Ryu Notify](/docs/standalone/notify) | Durable product events and live event streams | `/v1/events` REST and SSE |

## Use services together

Each service remains the source of truth for its own domain. An adapter can
publish safe metadata to Notify without copying message bodies, command
output, provider credentials, or inbound secrets.

```text
Agent Mail ──message metadata──▶ Ryu Notify ──REST/SSE──▶ your dashboard or agent
Ryu Box    ──lifecycle metadata─▶ Ryu Notify ──REST/SSE──▶ your dashboard or agent
```

See [Notify streams and composition](/docs/standalone/notify-streams) for the
working examples and reconnect behavior. The standalone service commands prove
local process behavior, storage, authentication, and the documented API. They
do not by themselves prove hosted billing, TLS termination, DNS/MX setup,
provider deliverability, high availability, or a production deployment.
