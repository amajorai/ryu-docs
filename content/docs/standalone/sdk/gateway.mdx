<Callout type="info">
Self-hosted: run Ryu Gateway with your own provider keys.
</Callout>

This page makes a first call to a [Ryu Gateway](/docs/standalone/gateway) you
run yourself. The Gateway speaks the OpenAI wire format, so you can call it
with `@ryuhq/services`, with the `ryu_sdk.services` Python client, with the
official `openai` SDK, or with the AI SDK. The
route list and authentication rules are on
[standalone Gateway API](/docs/standalone/gateway-api), and the base-URL swap
for existing OpenAI clients is described in
[OpenAI-compatible endpoints](/docs/extend/integrate/openai-compat).

<Callout type="info">
@ryuhq/services is not yet published to npm; it requires @ryuhq/client 0.4 or later, which is also not yet on npm (latest is 0.3.0).
</Callout>

<Callout type="info">
The `ryu-sdk` Python package is not yet published to PyPI, so the Python client cannot be installed outside Ryu either.
</Callout>

## What you need

- **A running Gateway.** Start it as described in
  [Start a standalone Gateway](/docs/standalone/gateway#start-a-standalone-gateway).
  It listens on `127.0.0.1:7981` by default.
- **At least one provider key in the Gateway's environment**, for example
  `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, or `OPENROUTER_API_KEY`. The Gateway
  routes each model to a configured provider; see
  [Gateway routing](/docs/gateway/routing) for the full list. You pay those
  providers directly.
- **A Gateway client key.** Authentication is on by default. On first start
  the Gateway writes an inference key to `gateway-relay.key` next to
  `gateway.toml`, or you can add your own key under `[[auth.api_keys]]`. See
  [Configure client authentication](/docs/standalone/gateway-api#configure-client-authentication).

## Configure

The SDK and the CLI read these environment variables. Options passed to
`new Ryu()` win over them, and `new Ryu({ env: false })` turns env reads off.

| Variable | Default | Description |
|---|---|---|
| `RYU_GATEWAY_URL` | `http://127.0.0.1:7981` | Gateway origin. |
| `RYU_GATEWAY_TOKEN` | none | Gateway bearer token; required unless the Gateway runs with require_auth = false. |

```sh
export RYU_GATEWAY_URL="http://127.0.0.1:7981"
export RYU_GATEWAY_TOKEN="<contents of gateway-relay.key>"
```

If the Gateway has a sealing key, such as `RYU_MASTER_KEY`, the key file is
sealed. Read the key with `ryu-gateway print-key relay` instead, run with the
same environment as the Gateway.

The token is sent as `Authorization: Bearer`. It is the same relay key that
[Start a standalone Gateway](/docs/standalone/gateway#start-a-standalone-gateway)
exports as `RYU_GATEWAY_KEY`; the SDK and the CLI read it as
`RYU_GATEWAY_TOKEN` (or `gateway.apiKey`). The SDK never sends `RYU_API_KEY`
to the Gateway, and never sends the Gateway token to another origin.

The SDK's default is the local Gateway at `http://127.0.0.1:7981`. To call
another Gateway origin, set `RYU_GATEWAY_URL` (or `gateway.baseUrl`) and the
token that Gateway accepts.

## First call with curl

List the models the Gateway can route to, then send one chat completion:

```sh
curl -sS "$RYU_GATEWAY_URL/v1/models" \
  -H "Authorization: Bearer $RYU_GATEWAY_TOKEN"

curl -sS -X POST "$RYU_GATEWAY_URL/v1/chat/completions" \
  -H "Authorization: Bearer $RYU_GATEWAY_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"openai/gpt-4o-mini","messages":[{"role":"user","content":"Say hello"}]}'
```

Use a model id that `/v1/models` returned; the ids depend on the providers you
configured.

## First call with the SDK

With `result: "object"`, every call resolves to `{ data, error, meta }` and
never throws for API or configuration errors:

```ts tab="Node"
import { Ryu } from "@ryuhq/services";

// Reads RYU_GATEWAY_URL and RYU_GATEWAY_TOKEN.
const ryu = new Ryu({ result: "object" });

const { data, error } = await ryu.gateway.chat.completions.create({
  model: "openai/gpt-4o-mini",
  messages: [{ role: "user", content: "Say hello" }],
});

if (error) {
  console.error(error.code, error.message);
} else {
  console.log(data.choices[0]?.message.content);
}
```

```python tab="Python"
from ryu_sdk.services import Ryu

# Reads RYU_GATEWAY_URL and RYU_GATEWAY_TOKEN.
ryu = Ryu(result="object")

data, error, meta = ryu.gateway.chat.completions.create(
    model="openai/gpt-4o-mini",
    messages=[{"role": "user", "content": "Say hello"}],
)

if error:
    print(error.code, error.message)
elif data:
    print(data["choices"][0]["message"]["content"])
```

`ryu.gateway` also has `health()`, `auth.status()`, `models.list()` and
`embeddings.create({ model, input })`. To stream, pass `stream: true` or call
`chat.completions.stream()`. Both return an async iterable in either result
mode, and in object mode `create({ stream: true })` is typed as a stream, not
as `{ data, error, meta }`; like every iterator, it throws a `RyuError` on
failure. Chunks arrive until the Gateway sends `[DONE]`.

```ts tab="Node"
import { Ryu } from "@ryuhq/services";

const ryu = new Ryu();

for await (const chunk of ryu.gateway.chat.completions.create({
  model: "openai/gpt-4o-mini",
  messages: [{ role: "user", content: "Count to five" }],
  stream: true,
})) {
  const text = chunk.choices[0]?.delta.content;
  if (typeof text === "string") {
    process.stdout.write(text);
  }
}
```

```python tab="Python"
import sys

from ryu_sdk.services import Ryu

ryu = Ryu()

for chunk in ryu.gateway.chat.completions.create(
    model="openai/gpt-4o-mini",
    messages=[{"role": "user", "content": "Count to five"}],
    stream=True,
):
    text = chunk["choices"][0]["delta"].get("content") if chunk["choices"] else None
    if isinstance(text, str):
        sys.stdout.write(text)
```

A stream is one request: if the connection drops, the SDK raises a
`RyuError` and does not resume it.

## Use the official openai SDK or the AI SDK

`ryu.gateway.openAICompatible()` returns `{ baseURL, apiKey }` for any
OpenAI-compatible client. It makes no network call, and it throws a
`RyuConfigurationError` straight away (in both result modes) when the Gateway
settings are invalid, such as a malformed `RYU_GATEWAY_URL`. With the `openai`
package in Node:

```ts tab="Node"
import OpenAI from "openai";
import { Ryu } from "@ryuhq/services";

const openai = new OpenAI(new Ryu().gateway.openAICompatible());

const completion = await openai.chat.completions.create({
  model: "openai/gpt-4o-mini",
  messages: [{ role: "user", content: "Say hello" }],
});
console.log(completion.choices[0]?.message.content);
```

```python tab="Python"
from openai import OpenAI
from ryu_sdk.services import Ryu

gateway = Ryu().gateway.openai_compatible()
client = OpenAI(base_url=gateway["base_url"], api_key=gateway["api_key"])

completion = client.chat.completions.create(
    model="openai/gpt-4o-mini",
    messages=[{"role": "user", "content": "Say hello"}],
)
print(completion.choices[0].message.content)
```

With the AI SDK's OpenAI-compatible provider:

```ts
import { createOpenAICompatible } from "@ai-sdk/openai-compatible";
import { generateText } from "ai";
import { Ryu } from "@ryuhq/services";

const gateway = createOpenAICompatible({
  name: "ryu-gateway",
  ...new Ryu().gateway.openAICompatible(),
});

const { text } = await generateText({
  model: gateway("openai/gpt-4o-mini"),
  prompt: "Say hello",
});
console.log(text);
```

In Python, `gateway.openai_compatible()` returns `{"base_url", "api_key"}`,
the keyword arguments `openai.OpenAI` takes. Type checkers see it as
`GatewayOpenAICompatibleConfig` from `ryu_sdk.services.shapes`, with both keys
always present. Until the `ryu-sdk` package is on
PyPI, you can also point the official `openai` package at the Gateway
yourself:

```python
import os

from openai import OpenAI

client = OpenAI(
    base_url=os.environ.get("RYU_GATEWAY_URL", "http://127.0.0.1:7981") + "/v1",
    api_key=os.environ["RYU_GATEWAY_TOKEN"],
)

completion = client.chat.completions.create(
    model="openai/gpt-4o-mini",
    messages=[{"role": "user", "content": "Say hello"}],
)
print(completion.choices[0].message.content)
```

## Expected response

A chat completion has the OpenAI `chat.completion` shape. The SDK checks
`choices` and keeps every other field the provider returned:

```json
{
  "id": "chatcmpl-1",
  "object": "chat.completion",
  "created": 1790000000,
  "model": "openai/gpt-4o-mini",
  "choices": [
    {
      "index": 0,
      "message": { "role": "assistant", "content": "Hello there." },
      "finish_reason": "stop"
    }
  ],
  "usage": { "prompt_tokens": 5, "completion_tokens": 3, "total_tokens": 8 }
}
```

## Errors

Gateway errors are `{ "error": { "message", "type", "code" } }`. Each becomes
a `RyuError` subclass whose `code` is the Gateway's own code. Gateway error
responses carry no request id, so log the code and the time of the call.

| Status and code | SDK error | Notes |
|---|---|---|
| `400 invalid_request_error` | `RyuInvalidRequestError` | Read `error.message`. |
| `401 invalid_api_key` | `RyuAuthenticationError` | A missing or unknown Gateway key. |
| `402 budget_exceeded`, `insufficient_credits`, `provider_payment_required` | `RyuPaymentRequiredError` | A spend budget, credit balance, or provider account stopped the call. Never retried. |
| `403 policy_violation` | `RyuPermissionError` | A firewall, DLP, or policy rule blocked the request. |
| `404 model_not_found` | `RyuNotFoundError` | Pick a model from `models.list()`. |
| `429 rate_limit_exceeded` | `RyuRateLimitError` | The Gateway's own rate limit. It carries no wait hint and is not retried. |
| `429 provider_rate_limited` | `RyuRateLimitError` | The provider refused the request. `error.retryAfterSeconds` is set when the provider said how long to wait. |
| `502 provider_error` | `RyuServerError` | The provider failed or rejected the request. When the Gateway knows the provider's own status, `error.details.upstreamStatus` holds it (from the body's `error.upstream_status`). With an upstream `4xx` the error has `retryable: false` and is never retried, except an upstream `408`, `425`, or `429`, which stays retryable. |
| `503 circuit_open`, `engine_overloaded`, `all_providers_unavailable` | `RyuUnavailableError` | No provider can take the call right now. |
| `503 credit_accounting_unavailable` | `RyuUnavailableError` | The Gateway could not check credits, so it did not run the call. This is a billing-path outage, separate from `insufficient_credits`. Chat and embeddings are not retried. |
| `500 internal_error` | `RyuServerError` | The Gateway itself failed. |

A network failure gives `RyuConnectionError`, which usually means no Gateway
is listening at `RYU_GATEWAY_URL`.

## Idempotency and retries

No Gateway route deduplicates writes, so the SDK sends no `Idempotency-Key`.
Reads (`health`, `auth.status`, `models.list`) are retried on network errors,
timeouts, and `5xx` responses. Chat completions and embeddings are **not**
retried on those failures, because the provider may already have run, and
billed for, the request.

A `429 provider_rate_limited` is retried for every method when it says how
long to wait, in `Retry-After` or in the body's `error.retry_after`, and that
wait is at most `maxRetryDelayMs` (30 seconds by default): the provider
refused the request without running it. The Gateway's own
`429 rate_limit_exceeded` carries no wait hint and is not retried. A
`502 provider_error` whose `upstreamStatus` is a `4xx` is not retried for any
method, because the provider would refuse the same request again. An upstream
`408`, `425`, or `429` is transient: like an upstream `5xx`, or none, it keeps
`retryable: true` and a read is retried as above. A streamed
completion is never retried. The
defaults are two retries and a 60-second timeout until response headers
arrive; change them with `maxRetries` and `timeoutMs`.

## CLI

The `ryu-services` command line reads the same variables. Add `--json` for
`{ data, meta }` output, or `--dry-run` to print the equivalent curl command
with `$RYU_GATEWAY_TOKEN` in place of the key.

```sh
ryu-services gateway models
ryu-services gateway chat "Say hello" --model openai/gpt-4o-mini
```

Until `@ryuhq/services-cli` is on npm, run these as
`ryu-cli services gateway ...`, with the same flags; `ryu-cli services`
arrives in a Ryu release after 0.4.0, and until then neither the CLI nor the
MCP server can be installed outside the Ryu repository (see
[ryu-services CLI](/docs/standalone/sdk/cli#run-it-from-ryu-cli)).

`models` prints one JSON line per model (see
[list output](/docs/standalone/sdk/cli#list-output)); `--json` prints the whole
`/v1/models` reply with its meta. `chat` prints the assistant's reply. It also takes `--system`,
`--max-tokens`, and `--temperature`, and `--stream` prints one JSON chunk per
line.

## MCP

`ryu-services mcp` serves MCP tools over stdio for the services you have
configured. The Gateway's tools are registered only when `RYU_GATEWAY_URL` or
`RYU_GATEWAY_TOKEN` is set; the built-in local default alone exposes nothing.

Until `@ryuhq/services-cli` is on npm, start the server through `ryu-cli`,
as below (`ryu-cli services` arrives in a Ryu release after 0.4.0; until then
neither the CLI nor the MCP server can be installed outside the Ryu
repository); once it is published, use
`"command": "ryu-services"` and drop `"services"` from `args`.

```json
{
  "mcpServers": {
    "ryu-services": {
      "command": "ryu-cli",
      "args": ["services", "mcp", "--services", "gateway"],
      "env": {
        "RYU_GATEWAY_URL": "http://127.0.0.1:7981",
        "RYU_GATEWAY_TOKEN": "<contents of gateway-relay.key>"
      }
    }
  }
}
```

| Tool | What it does | Read-only |
|---|---|---|
| `gateway_list_models` | Lists the models the Gateway can route to. | Yes |
| `gateway_chat` | Sends one chat completion from a `prompt`, with optional `system`, `maxTokens`, and `temperature`. | No |

Results carry `{ data, meta }`; failures are tool errors that carry the
`RyuError` fields and never the key. `gateway_chat` reaches a model provider
that may bill for the call, so hosts should ask before running it.
By default the server registers only `gateway_list_models`; add
`--allow-writes` to the args to expose `gateway_chat`.
