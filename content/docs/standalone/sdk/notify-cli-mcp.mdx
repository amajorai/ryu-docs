This page runs the Notify calls from the
[Notify SDK quickstart](/docs/standalone/sdk/notify) with the `ryu-services`
command line and its MCP tools.

## CLI

The `ryu-services` command line reads the variables from
[Configure](/docs/standalone/sdk/notify#configure). Add `--json` for
`{ data, meta }` output, or `--dry-run` to print the equivalent curl command
with `$RYU_NOTIFY_API_KEY` in place of the key.

```sh
ryu-services notify publish --title "Deploy finished" --level success --topic deployments --recipient oncall --idempotency-key deploy-4823
ryu-services notify request-approval --title "Deploy to production?" --prompt "Approve the 4823 rollout" --recipient oncall
ryu-services notify events list --limit 20 --level error --recipient oncall --unacknowledged
ryu-services notify events get <event-id>
ryu-services notify events ack <event-id>
ryu-services notify usage --from 2026-10-01T00:00:00Z --to 2026-10-02T00:00:00Z
```

Until `@ryuhq/services-cli` is on npm, run these as
`ryu-cli services notify ...`, with the same flags; `ryu-cli services` arrives
in a Ryu release after 0.4.0, and until then neither the CLI nor the MCP
server can be installed outside the Ryu repository (see
[ryu-services CLI](/docs/standalone/sdk/cli#run-it-from-ryu-cli)).

`events list` prints one JSON line per event, and `events get` prints the
one event in the same shape. When more events remain, `events list` names the
next page's cursor on stderr; pass it back as `--before` (see [list output](/docs/standalone/sdk/cli#list-output)). With `--json`, `events list` prints `{ data, meta }` whose `data`
is the page as Notify returns it (an `events` array and `nextCursor`), and
`events get` prints the event as `data`. `events list --all`
pages through every matching event and prints one JSON line each. `usage` without `--from` and `--to` reads the last 24 whole UTC
hours, including the current one.

`--recipient` on `publish` and `request-approval` is your label for who the
event is for (such as `oncall`), and the recipient's preferences (mute, quiet
hours) apply to it. On `events list`, `--recipient` keeps that label's events,
and `--acknowledged` or `--unacknowledged` keeps events by acknowledgement.
`events ack <id>` marks one event acknowledged; acknowledging it again is
harmless. `request-approval` publishes an approval (or, with
`--response-type yes_no`, a yes/no) request and waits up to `--wait-ms`
(default 45 seconds) for an answer. A pending result means the request is
still open: read it later with `events get` rather than asking again.

## MCP

`ryu-services mcp` serves MCP tools over stdio for the services you have
configured. Limit it to Notify with `--services notify`. By default it keeps
only the read tools; add `--allow-writes` to the args to also expose the
tools that publish events, ask for approval, or acknowledge events. Until
`@ryuhq/services-cli` is on npm, start it through `ryu-cli`, as below
(`ryu-cli services` arrives in a Ryu release after 0.4.0; until then neither
the CLI nor the MCP server can be installed outside the Ryu repository); once
it is published, use `"command": "ryu-services"` and drop
`"services"` from `args`.

```json
{
  "mcpServers": {
    "ryu-services": {
      "command": "ryu-cli",
      "args": ["services", "mcp", "--services", "notify"],
      "env": {
        "RYU_NOTIFY_API_KEY": "<your tenant key>"
      }
    }
  }
}
```

| Tool | What it does | Read-only |
|---|---|---|
| `notify_publish` | Publishes an event; takes an optional `idempotencyKey`. | No |
| `notify_request_approval` | Asks for approval and waits up to `waitMs` (default 45 seconds, at most 50) for the answer. The request stays open for `timeoutMs` (default 10 minutes, at most 15); if nobody has answered within `waitMs`, it returns `status: "pending"` with the event, and `notify_get_event` reads the answer later. | No |
| `notify_list_events` | Lists events, newest first; page with `before`. | Yes |
| `notify_get_event` | Reads one event and its response state. | Yes |
| `notify_ack_event` | Marks one event acknowledged. | No |
| `notify_usage` | Counts accepted events for whole UTC hours. | Yes |

Results carry `{ data, meta }`. Failures are tool errors that carry the
`RyuError` fields, including `code` and `requestId`, and never the key. A
published event reaches the tenant's destinations, so hosts should ask before
running `notify_publish` or `notify_request_approval`. The approval wait stays
under the 60-second request timeout common in MCP clients, so a host does not
give up and call the tool again, which would publish a second request.
