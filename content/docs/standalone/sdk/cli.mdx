`ryu-services` is the command line in `@ryuhq/services-cli`. It is built on
`@ryuhq/services`, so it reads the same environment variables, adds the same
idempotency keys and retries, and reports the same `RyuError` codes.

<Callout type="info">
@ryuhq/services is not yet published to npm; it requires @ryuhq/client 0.4 or later, which is also not yet on npm (latest is 0.3.0).
</Callout>

`@ryuhq/services-cli` is not on npm yet either, so
`npm install --global @ryuhq/services-cli` does not work yet. Until it is
published, run the same command line as `ryu-cli services` (see
[Run it from ryu-cli](/docs/standalone/sdk/cli#run-it-from-ryu-cli)).

Once the package is published, install it globally:

```sh
npm install --global @ryuhq/services-cli
```

## Usage

```sh
ryu-services notify publish --title "Deploy finished" --level success
ryu-services notify events list --limit 20 --json
ryu-services box exec <box-id> -- ls -la
ryu-services doctor --check
```

Every service command takes the global flags below. Configuration comes only
from the environment and these flags; the CLI writes nothing to disk. Prefer
environment variables over `--api-key`, because flags end up in shell history.

| Flag | What it does |
|---|---|
| `--json` | Prints one JSON document: `{ data, meta }` on success, `{ error }` on failure. Streams print one JSON line per item. |
| `--dry-run` | Prints the equivalent `curl` command instead of sending the request. The key appears only as its variable name, such as `$RYU_NOTIFY_API_KEY`. Only the first request of a multi-step command is printed; when that leaves a later step out, a note on standard error says so, and with `--json` the output carries `complete: false` and the same `note`. |
| `--base-url <url>` | Overrides the service's base URL. |
| `--api-key <key>` | Overrides the service's key. |
| `--idempotency-key <key>` | The `Idempotency-Key` for the first deduplicated write of the call. |
| `--timeout <ms>` | Per-attempt timeout until the response headers arrive. |
| `--max-retries <n>` | Retries after the first attempt (default 2). |
| `--help` | Shows help for the CLI, a service, or a command. |

`ryu-services --help`, `ryu-services <service> --help`, and
`ryu-services <service> <command> --help` list each command's own flags.

## List output

Every command that reads one page of a list prints it the same way:

| Mode | stdout | stderr |
|---|---|---|
| Default | One JSON line per item, the same lines `--all` prints. | How to read the next page (for example `More events: pass --before <cursor> for the next page, or --all for every event.`), or `No <items>.` for an empty page. |
| `--json` | One `{ data, meta }` document; `data` is the page exactly as the SDK returns it, cursor fields included. | Nothing. |
| `--all` | Every item on every page, one JSON line each (NDJSON). | Nothing. |

So stdout holds only items unless you pass `--json`, and a script can pipe
either mode into a JSON-lines reader.

| Lists | Paging |
|---|---|
| `managed-agents agents list`, `managed-agents environments list`, `messaging messages list`, `mail messages list`, `notify events list` | More than one page; `--all` reads every page |
| `mail inboxes list`, `messaging numbers list`, `box list`, `sites list`, `passport profiles`, `passport connections list`, `gateway models`, `managed-agents sessions pending-approvals` | One page, so their human output has no paging line |

`sessions pending-approvals` writes a note on stderr when its scan stopped
before reading every approval event, and `--json` then shows
`complete: false`.

## Version and npm status

To check which CLI version is installed, pass `--version` (or `-V`) with no
command. It prints the version and exits `0`; with `--json` it prints
`{ "data": { "name": "ryu-services", "npmNote": …, "npmPublishedVersion": …, "version": … }, "meta": null }`.

After a service or command, `--version` is refused as an unknown flag, which
is why `--help` lists it apart from the global flags.

Until `@ryuhq/services` is published, `--version` and `doctor` also say where
the command line came from and that the package is not on npm:

- `--version` keeps the bare version on stdout and writes the note to stderr.
- `doctor` ends its report with it.

Run as `ryu-cli services`, the note names the `ryu-cli` release it is bundled
with, shown here as `<version>`.

```txt
note: This command line is bundled with ryu-cli <version>, not installed from npm. @ryuhq/services is not yet published to npm; it requires @ryuhq/client 0.4 or later.
```

Only a build that is neither installed from npm nor bundled with `ryu-cli`,
such as one run directly from source, calls itself a workspace build:

```txt
note: This @ryuhq/services-cli is a workspace build, not an npm install. @ryuhq/services is not yet published to npm; it requires @ryuhq/client 0.4 or later.
```

Under `--json`, the same text is `npmNote` (with `npmPublishedVersion: null`)
instead of a separate line. Once the package is on npm, `npmPublishedVersion`
is its version, `npmNote` is `null`, and no note is printed.

## Run it from ryu-cli

<Callout type="warn">
`ryu-cli services` arrives in a Ryu release after 0.4.0. Until then neither the
CLI nor the MCP server can be installed outside the Ryu repository.
</Callout>

The Ryu terminal client (`ryu-cli`) runs the same command line as
`ryu-cli services`. Put `ryu-cli services` where a page writes `ryu-services`,
so `ryu-services doctor` becomes `ryu-cli services doctor`.

Every argument after `services` goes to `ryu-services` unchanged, with the
same flags, environment variables, and exit codes, so
`ryu-cli services notify events list --json` matches the `ryu-services` call.

### Flags written before services

A `ryu-services` global flag written before `services` is forwarded, so
`ryu-cli --json services notify events list` is the same call as
`ryu-cli services notify events list --json`. That covers:

- `--json`, `--dry-run`, and `-h`/`--help`;
- the value flags with their value, written either way (`--base-url <url>` or
  `--timeout=5000`);
- `ryu-cli --version services`, which prints the `ryu-services` version.

Any other token before `services` exits with code `2` and prints the command
with that token moved after the command words. An `--api-key` value in that
command is shown as `<key>`, never echoed. Two cases get a plain message
instead: `--version` together with a service or command (run
`ryu-cli services --version`), and a value flag with no value.

This is not the `ryu` command that `@ryuhq/sdk` installs, which has no `services`
command. See the [command reference](/docs/surfaces/cli/reference).

```sh
ryu-cli services doctor
ryu-cli services notify publish --title "Deploy finished" --dry-run
```

The MCP server runs the same way. In an MCP client's configuration, use
`ryu-cli` as the command and put `services` first in its arguments:

```json
{
  "mcpServers": {
    "ryu-services": {
      "command": "ryu-cli",
      "args": ["services", "mcp", "--services", "notify,box"]
    }
  }
}
```

## Exit codes

| Code | Meaning |
|---|---|
| `0` | The command succeeded. |
| `1` | The service answered with an error. The CLI prints its `code`, `message`, HTTP `status`, `requestId`, `retryAfter` (when the service sent a `Retry-After` delay), and `hint`. |
| `2` | The command line or the configuration is wrong. |
| `4` | `webhooks verify` rejected the delivery. |

## Commands

### Managed Agents

| Command | What it does |
|---|---|
| `ryu-services managed-agents agents list` | Lists agents, one page, newest first; `--cursor` reads a later page and `--all` reads every page. |
| `ryu-services managed-agents environments list` | Lists environments, one page, newest first, with the `menv_` id that `sessions create --environment` takes; `--cursor` reads a later page and `--all` reads every page. |
| `ryu-services managed-agents sessions create` | Starts a session; `--message` sends a first message and `--follow` streams events until the turn ends. |
| `ryu-services managed-agents sessions get <id>` | Shows a session. |
| `ryu-services managed-agents sessions send <id>` | Sends a user message (`--text`); `--follow` streams the turn's events until it ends. |
| `ryu-services managed-agents sessions stream <id>` | Streams a session's events as JSON lines until it ends. |
| `ryu-services managed-agents sessions pending-approvals <id>` | Lists the tool calls waiting for approval, with each call's input and `expiresAt`. |
| `ryu-services managed-agents sessions approve <id> <toolUseId>` | Allows a tool call waiting for approval; `--follow` streams the rest of the turn. |
| `ryu-services managed-agents sessions deny <id> <toolUseId>` | Denies a tool call waiting for approval; `--message` is shown to the model, and `--follow` streams the rest of the turn. |

### Messaging

| Command | What it does |
|---|---|
| `ryu-services messaging status` | Shows whether Messaging is configured and which channels can send. Runs without credentials; every other Messaging command needs `RYU_API_KEY` and `RYU_ORGANIZATION_ID`. |
| `ryu-services messaging quote` | Quotes the hold an SMS would place (`--to`, `--body`), without sending. |
| `ryu-services messaging sms send` | Sends an SMS from an organization number; retry with the same `--idempotency-key`. |
| `ryu-services messaging numbers list` | Lists the organization's numbers; `--include-released` adds released and failed ones. The list is one page, so `--all` is refused with a pointer to `--include-released`. |
| `ryu-services messaging messages list` | Lists the message log, newest first; `--all` reads every page. |
| `ryu-services messaging messages get <id>` | Shows one message with its status and charge. |

### Mail

| Command | What it does |
|---|---|
| `ryu-services mail status` | Shows whether Mail is configured and can send. On hosted Mail it runs without credentials (and then sends none); a self-hosted `RYU_MAIL_URL` still needs `RYU_MAIL_API_KEY`. Every other Mail command needs a key. |
| `ryu-services mail inboxes list` | Lists the inboxes the key can see. |
| `ryu-services mail inboxes create` | Creates an inbox to send from (`--name`; `--address` on self-hosted Mail, optional `--local-part` on hosted Mail, which ignores `--address`); hosted keys need `mail:manage`. |
| `ryu-services mail messages list <inbox>` | Lists an inbox's messages, newest first; `--all` reads every page. |
| `ryu-services mail messages get <message>` | Shows one message. |
| `ryu-services mail send` | Sends a message from an inbox; `--from` takes its address or id. An address costs one extra call to look up the inbox, so `--dry-run` with an address prints only that lookup and a note that the send was left out; pass the inbox id to preview the send itself. |

### Notify

| Command | What it does |
|---|---|
| `ryu-services notify publish` | Publishes an event. |
| `ryu-services notify events list` | Lists events, newest first; `--before` reads a later page and `--all` reads every page. |
| `ryu-services notify events get <id>` | Shows one event and its response state. |
| `ryu-services notify events ack <id>` | Marks one event acknowledged. Acknowledging it again is harmless. |
| `ryu-services notify request-approval` | Publishes an approval (or yes/no) request and waits up to `--wait-ms` (default 45 seconds) for an answer. A pending result means the request is still open: read it with `notify events get`, and do not ask again. Running it again with the same `--idempotency-key` never publishes a second request, but it gets `409 idempotency_conflict`, so after a lost reply read the first request with `notify events get` or `notify events list`. |
| `ryu-services notify usage` | Shows accepted events for whole UTC hours. |

### Box

| Command | What it does |
|---|---|
| `ryu-services box list` | Lists the tenant's Boxes. |
| `ryu-services box create` | Creates a Box with one `Idempotency-Key` for all retries. |
| `ryu-services box get <id>` | Shows a Box. |
| `ryu-services box exec <id> -- <command>` | Runs a command and streams its output; never retried. |
| `ryu-services box stop <id>` | Stops a Box and keeps its disk, then prints the Box as read after the stop, so you can check its `status`. With `--json`, `meta` is the stop request's. If that read fails or takes longer than a few seconds, the stop still succeeded and it prints `OK` (`data: null` with the stop's `meta` under `--json`). |
| `ryu-services box resume <id>` | Resumes a stopped Box. |
| `ryu-services box delete <id>` | Deletes a Box and its disk. Not reversible. Prints `OK`. |

### Gateway

| Command | What it does |
|---|---|
| `ryu-services gateway models` | Lists the models the Gateway can route to. |
| `ryu-services gateway chat "<prompt>"` | Sends one chat completion (`--model`); never retried on a `5xx`. |

### Passport

| Command | What it does |
|---|---|
| `ryu-services passport capabilities` | Shows the Passport contract version and features. |
| `ryu-services passport profiles` | Lists profiles with their connections' status. |
| `ryu-services passport connections list` | Lists connections, status only. With `RYU_PASSPORT_API_KEY` set (alone or with the runtime key) it lists every connection in the tenant; with only `RYU_PASSPORT_RUNTIME_KEY`, the runtime grant's connections. `--dry-run` prints whichever route it would call. |
| `ryu-services passport connections get <id>` | Shows one connection's status and login-flow state. |
| `ryu-services passport usage` | Shows connection time and fetches for whole UTC hours. |

### Sites

| Command | What it does |
|---|---|
| `ryu-services sites status` | Shows the Sites process mode, limits, and visitor domain. |
| `ryu-services sites list` | Lists Sites. |
| `ryu-services sites get <id>` | Shows one Site; takes its id or slug. |
| `ryu-services sites create` | Creates a private Site (`--name`, `--slug`) and prints its id. |
| `ryu-services sites deploy <file.html>` | Saves an HTML file as a new version of a Site and deploys it (`--project` takes the Site's id or slug). |
| `ryu-services sites settings <id>` | Changes who can open a Site (`--audience` takes `private`, `invited`, `workspace`, or `public`; `--viewer`, `--no-viewers`, `--workspace`, `--no-workspace`) or its `--allow-remix` and `--optional-sign-in` options, and keeps every other setting; `--expected-revision` refuses a stale change with `409`. Takes its id or slug. Never changes editors (SDK only). |

`ryu-services <service> <command> --help` lists that command's flags, marks the
ones it needs with `(required)`, and shows an example and the service's SDK
page; a write that sends email, SMS or events, or replaces what a Site
serves, also says so. A usage mistake names the command's own help.

Each service's quickstart shows these commands with their flags.

Connect has no commands, because it is an MCP server itself.
`ryu-services connect` prints where its `/mcp` endpoint is and links to
[Connect API trigger management](/docs/standalone/connect-api-triggers) for the
account and trigger routes, which take the separate management key. See the
[Connect quickstart](/docs/standalone/sdk/connect).

## Check your configuration

`ryu-services doctor` shows what each service resolves to, with every key
shown only as set or unset. `--check` also sends one `GET` to each configured
service and exits with `1` when one fails:

```sh
ryu-services doctor
ryu-services doctor --check --json
```

While `@ryuhq/services` is unpublished, the report ends with the same
`note:` line that `--version` prints (see [Version and npm status](/docs/standalone/sdk/cli#version-and-npm-status)); under
`--json` it is `npmNote`, beside `services`.

A service that is not configured names the variables to set. Under `--json`,
its `problem` carries `code`, `message`, `hint`, and `missing` as separate
fields, so the message never repeats the hint.

When Mail or Messaging is not configured, `doctor` also names the status tool
that [`ryu-services mcp`](/docs/standalone/sdk/mcp) still registers for it
(`mail_status` on hosted Mail, `messaging_status`), because those tools need
no credentials and send none. That holds unless you start the server with a
`--services` list that leaves that service out.

Under `--json` each service carries them as `credentialFreeTools` (empty for a
configured service). A self-hosted `RYU_MAIL_URL` without its token lists no
Mail tool, because that server answers its status route only with the token.

### What --check probes

Most probes call a route that checks the key and report `authenticated`.

| Service | Probe |
|---|---|
| Managed Agents | `agents?limit=1` |
| Messaging | `/api/messaging/orgs/{orgId}/settings` |
| Mail | `/api/mail/pods` when hosted, `/api/mail/status` when self-hosted |
| Notify | `/v1/events?limit=1` |
| Box | `/v1/boxes` |
| Sites | `/api/sites/status` |
| Passport | `/v1/capabilities`, or `/v1/runtime/connections` with only a runtime grant |

Gateway and Connect are probed on their public `/health` route, so they
report `reachable (auth not verified)` - the service answers, but the key is
not checked. A service that is set only by a built-in default, such as
Gateway's local URL, is not probed.

`--check` also exits with `1` when you set a service but its configuration does
not resolve, for example a key with a URL that has no scheme. Such a service
cannot be probed, and every call to it would fail.

A `ryu_` key without `mail:read` (a send-only key) cannot read the hosted Mail
probe route. `doctor --check` reports it as
`authenticated (key lacks the scope this probe reads)` with
`403 insufficient_scope`, does not fail the exit code for it, and sets
`scopeLimited: true` on that probe in `--json` output.

## See a request before sending it

`--dry-run` builds the request with the real SDK and prints it as `curl`,
without sending it and without needing a key:

```sh
ryu-services notify publish --title "Deploy finished" --dry-run
```

The output uses `$RYU_NOTIFY_API_KEY` in place of the key, `$RYU_GATEWAY_TOKEN`
for Gateway, `$RYU_API_KEY` for Managed Agents and Messaging, and
`$RYU_MAIL_GATEWAY_KEY` for hosted Mail, or `$RYU_API_KEY` when hosted Mail is
reached with only the `ryu_` key, so it is safe to paste into a ticket.

## Webhooks and MCP

`ryu-services webhooks verify` checks a captured Mail, Notify or Messaging
delivery; see
[SDK webhooks](/docs/standalone/sdk/webhooks#check-a-delivery-from-the-command-line).
`ryu-services mcp` serves the service tools to an MCP client, only the
read-only ones unless you pass `--allow-writes`; see
[MCP server](/docs/standalone/sdk/mcp).
