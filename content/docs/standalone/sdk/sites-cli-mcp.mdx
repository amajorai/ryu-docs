This page runs the Sites calls from the
[Sites SDK quickstart](/docs/standalone/sdk/sites) with the `ryu-services`
command line and its MCP tools.

## CLI

The `ryu-services` command line reads the variables from
[Configure](/docs/standalone/sdk/sites#configure). Add `--json` for
`{ data, meta }` output, or `--dry-run` to print the first request as curl,
with `$RYU_SITES_API_KEY` in place of the bearer.

```sh
ryu-services sites status
ryu-services sites create --name "Launch notes (CLI)" --slug launch-notes-cli
ryu-services sites list
ryu-services sites get launch-notes-cli
printf '<!doctype html><title>Launch</title><h1>Launch notes</h1>\n' > index.html
ryu-services sites deploy ./index.html --project launch-notes-cli --message "First draft"
ryu-services sites settings launch-notes-cli --audience public
```

`sites list` prints one JSON line per Site (see [list output](/docs/standalone/sdk/cli#list-output)).

Until `@ryuhq/services-cli` is on npm, run these as
`ryu-cli services sites ...`, with the same flags; `ryu-cli services` arrives
in a Ryu release after 0.4.0, and until then neither the CLI nor the MCP
server can be installed outside the Ryu repository (see
[ryu-services CLI](/docs/standalone/sdk/cli#run-it-from-ryu-cli)).

`create` makes a private Site and prints it; `--template` picks a starter
(`website`, `help-center`, `dashboard`, `game` or `reset-calendar`) and
`--prompt` stores what the Site is for. `get` and `deploy --project` take the
Site's `id` or its slug: when no Site has that id, the CLI looks the value up
among the Sites you own or that are shared with you and uses that Site's id.

`deploy` reads the file, saves it as a new version, deploys it, and prints
`{ project, version, url }`. Add `--expected-revision <n>` to refuse the
deploy unless the Site is still at the revision you reviewed.

`settings` takes the Site's id or slug and changes only the settings you name:
`--audience`, `--viewer` (repeat it; the list replaces the current one),
`--no-viewers`, `--workspace <id>`, `--no-workspace`, `--allow-remix on|off`,
`--optional-sign-in on|off`, and `--expected-revision <n>`. It prints the Site
with its new `revision`. It does not change editors; use the SDK for those.

## MCP

`ryu-services mcp` serves MCP tools over stdio for the services you have
configured. `sites_list`, `sites_get`, `sites_create`, and `sites_deploy` have
the same names as the tools of `ryu-sites mcp`, but they call your standalone
process over HTTP with its management bearer. `sites_update_settings` has no
`ryu-sites mcp` counterpart of that name; like that server's
`sites_set_access`, it does not change editors.

Limit it to Sites with `--services sites`. By default it leaves out
`sites_create`, `sites_deploy`, and `sites_update_settings`; add
`--allow-writes` to the args to expose them. Until
`@ryuhq/services-cli` is on npm, start it through `ryu-cli`, as below
(`ryu-cli services` arrives in a Ryu release after 0.4.0; until then neither
the CLI nor the MCP server can be installed outside the Ryu repository); once
it is published, use `"command": "ryu-services"` and drop `"services"` from
`args`.

```json
{
  "mcpServers": {
    "ryu-services": {
      "command": "ryu-cli",
      "args": ["services", "mcp", "--services", "sites"],
      "env": {
        "RYU_SITES_URL": "http://127.0.0.1:8021",
        "RYU_SITES_API_KEY": "<the RYU_SITES_API_TOKEN value>"
      }
    }
  }
}
```

| Tool | What it does | Read-only |
|---|---|---|
| `sites_list` | Lists owned, shared, or all Sites with their revision, audience, and versions. | Yes |
| `sites_get` | Reads one Site, including its revision. | Yes |
| `sites_create` | Creates a private Site (`name`, `slug`, optional `template` and `description`) and returns its `id` and `revision`. Publishes nothing; a slug in use is `409 conflict`. | No |
| `sites_deploy` | Saves `html` as a new version and deploys it, or deploys a saved `versionId`. Requires `expectedRevision`. Destructive. | No |
| `sites_update_settings` | Changes `audience`, `viewers`, `workspaceId`, `optionalSignIn`, or `allowRemix` and keeps the other settings. Never changes editors. Requires `expectedRevision`; a repeat with the same revision is `409 conflict`. Not destructive, not idempotent. | No |

`sites_get`, `sites_deploy`, and `sites_update_settings` take `siteId`, the
Site's `id` from `sites_list` or `sites_get`, not its slug. Unlike the CLI,
they do not look a slug up, and a `404 not_found` for a value shaped like a
slug carries a `hint` that says so.

`sites_deploy` publishes what visitors with access see, so hosts should ask
before running it. Unlike the SDK and CLI, it does not read the revision for
you: the agent passes the `revision` it read with `sites_get`. It never widens access. Failures are tool errors that
carry the `RyuError` fields, such as `code: "conflict"`, and never the bearer.

`sites_update_settings` also takes the `revision` the agent read with
`sites_get`. It removes nothing, so it is not marked destructive, but setting
`audience` to `public` opens the Site to anyone with the URL: hosts should ask
before running it. A `503 unavailable` (a service the setting needs is not
connected) comes back with `retryable: false`.
