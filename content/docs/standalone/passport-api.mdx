This page is the HTTP reference for the standalone Ryu Passport service, which
stores sealed agent login state per tenant. The API is a tenant-scoped contract
under `/v1`. Management and runtime routes require their respective Passport bearer tokens.
Health, the state-bound OAuth callback, and the client metadata routes are
public. No response contains the `encrypted_state` column or a decrypted
credential value.

A missing or invalid token returns `401`. A client address that keeps presenting
unknown tokens is blocked for a while and gets `429` with a `Retry-After`
header in seconds, even for a valid token. Wait that long before retrying. See
[Failed authentication backoff](/docs/standalone/passport#failed-authentication-backoff).

## Errors

Every error is JSON with the message in `error` and a stable machine `code`,
for example `{"error":"connection not found","code":"not_found"}`. Branch on
`code`. A body that is not valid JSON is `400 invalid_request`, a request
without a JSON `content-type` is `415 invalid_request`, a JSON body that does
not match the route is `422 invalid_request`, an unknown route is
`404 not_found`, and a wrong method is `405 method_not_allowed` with an
`Allow` header. All of them have a JSON body. Send
`Accept: application/problem+json` to get the same error as RFC 9457 problem
details (`type`, `title`, `status`, `detail`, `instance`, `code`, `docs`)
that keep the `error` member; `type` and `docs` link the code's row below.
The OAuth callback still answers with a short page for the browser.

| Code | Meaning |
|---|---|
| <span id="invalid_request" />`invalid_request` | The body, a parameter or the usage window is not valid (`400`; `415` without a JSON `content-type`, `422` for a body that does not match the route). |
| <span id="unauthorized" />`unauthorized` | The bearer token is missing or not valid (`401`). |
| <span id="insufficient_credits" />`insufficient_credits` | Ryu-hosted Passport only: the organization has no credits left (`402`). |
| <span id="forbidden" />`forbidden` | The credential is not granted this request, such as an HTTP method (`403`). |
| <span id="not_found" />`not_found` | The connection or route does not exist (`404`). |
| <span id="method_not_allowed" />`method_not_allowed` | The route does not take this method; read `Allow` (`405`). |
| <span id="conflict" />`conflict` | The connection is not in a state that allows this request (`409`). |
| <span id="body_too_large" />`body_too_large` | The request body is larger than Passport reads (`413`). |
| <span id="rate_limited" />`rate_limited` | Too many failed authentications from this address; wait `Retry-After` (`429`). |
| <span id="idempotency_key_invalid" />`idempotency_key_invalid` | The `Idempotency-Key` header is not a valid key (`400`). |
| <span id="idempotency_conflict" />`idempotency_conflict` | The `Idempotency-Key` was used with a different body (`409`). |
| <span id="idempotency_in_progress" />`idempotency_in_progress` | The first request with this key is still running; wait `Retry-After` (`409`). |
| <span id="metering_unavailable" />`metering_unavailable` | Ryu-hosted Passport only: usage cannot be recorded right now (`503`). |
| <span id="internal_error" />`internal_error` | Passport failed to complete the request (`500`). |
| <span id="bad_gateway" />`bad_gateway` | The upstream request failed (`502`). |
| <span id="service_unavailable" />`service_unavailable` | Passport cannot serve the request right now (`503`). |
| <span id="gateway_timeout" />`gateway_timeout` | Reserved for an upstream that did not answer in time (`504`). |
| <span id="client_error" />`client_error` | Any other `4xx`. |
| <span id="server_error" />`server_error` | Any other `5xx`. |

## Create a connection

```sh
curl -fsS http://127.0.0.1:8093/v1/connections \
  -H "Authorization: Bearer replace-with-a-passport-management-token" \
  -H 'Content-Type: application/json' \
  -d '{"profile_id":"default","domain":"app.example.com"}'
```

To make a retry safe, add an `Idempotency-Key` header with a value of up to
255 printable ASCII characters (for example `-H 'Idempotency-Key: "c1f3..."'`).
Passport builds that honour it report `"idempotency_keys": true` under
`features` in `GET /v1/capabilities`; an older build ignores the header.

Keys are scoped to the tenant and kept for up to 24 hours; each tenant keeps
at most 10,000 keys and drops the oldest completed ones first. A retry with
the same key and body returns the first response with
`Idempotent-Replayed: true` and does not create a second connection. The same
key with a different body returns `409 idempotency_conflict`, and a retry
while the first request is still running returns
`409 idempotency_in_progress` with `Retry-After`.

Only a success or a `400`, `404`, `409` or `422` is replayed. An authentication, credit or metering
refusal, a `413`, a `429`, a server error, or a response larger than 64 KiB
frees the key, so a retry with it runs again. Without the header, every
request creates a connection. The `@ryuhq/services` SDK and the Python
`ryu_sdk.services` client send a key they generate, and retry the create with
it after a network error, timeout or `5xx`, only when `GET /v1/capabilities`
lists `features.idempotency_keys: true`; otherwise they never retry a create.
A key you supply is always sent (see
[Idempotency and retries](/docs/standalone/sdk/passport#idempotency-and-retries)).

New connections begin as `NEEDS_AUTH` with `IDLE` flow status. Start the manual
flow, complete the provider login out of band, then import the resulting state.

```sh
curl -fsS -X POST http://127.0.0.1:8093/v1/connections/conn_.../login \
  -H "Authorization: Bearer replace-with-a-passport-management-token"

curl -fsS -X POST http://127.0.0.1:8093/v1/connections/conn_.../import \
  -H "Authorization: Bearer replace-with-a-passport-management-token" \
  -H 'Content-Type: application/json' \
  -d '{"state":"cookie=session=..."}'
```

The import request accepts captured credential state. The OAuth callback
accepts a one-use authorization code bound to Passport's PKCE verifier.
Passport seals the state before it stores it and responds with status metadata
only.

## Routes

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/` | Public; redirects to `RYU_PRODUCT_DASHBOARD_URL` when set (Ryu's hosted deployment sets it), otherwise returns `{"name":"ryu-passport","version":…,"health":"/health"}` |
| `GET` | `/health` | Public service health and feature report |
| `GET` | `/v1/capabilities` | Authenticated contract summary |
| `GET` | `/v1/runtime/connections` | Runtime credential's profile-scoped connection metadata |
| `GET` | `/v1/profiles` | List profiles and status-only connections |
| `GET` | `/v1/connections` | List status-only connections |
| `POST` | `/v1/connections` | Create a `NEEDS_AUTH` connection |
| `GET` | `/v1/connections/:id` | Read status and flow metadata |
| `POST` | `/v1/connections/:id/login` | Begin the configured login source |
| `POST` | `/v1/connections/:id/import` | Seal manual state and authenticate |
| `POST` | `/v1/connections/:id/fetch` | Perform an authenticated, method-granted HTTPS request within Passport |
| `DELETE` | `/v1/connections/:id` | Remove the connection and sealed state |
| `POST` | `/v1/health/sweep` | Run one authenticated tenant sweep |
| `GET` | `/v1/usage?from=&to=` | Tenant usage meters for whole hours, up to 31 days |

The manual source checks for stored credential state within the authenticated
tenant. It does not validate that state against the remote provider. The MCP
OAuth routes are listed in the
[Passport MCP OAuth API](/docs/standalone/passport-mcp-api#mcp-routes).

## Out of credits

On a Ryu-hosted Passport, a tenant whose organization has no Ryu credits left
gets `402 Payment Required` on the routes that call an upstream or store a new
credential:

- `POST /v1/connections/:id/fetch`
- `POST /v1/runtime/mcp/transport`
- `POST /v1/connections`
- `POST /v1/mcp/connect` and `POST /v1/mcp/callback`, and the public OAuth
  callback, which shows a short page instead of JSON

```json
{
  "ok": false,
  "code": "insufficient_credits",
  "error": "insufficient_credits",
  "message": "This organization has no Ryu credits left. Add credits to resume upstream calls and new connections; reads, deletes, and the usage report still work."
}
```

Check `code`, as with the other Ryu services; `error` carries the same value
for older clients. The check runs right after authentication, for
administration and runtime tokens alike, so a refused call never reaches an
upstream and is not counted as usage. Every other route keeps working. A
self-hosted Passport never returns this response.

## Usage cannot be recorded

If Passport cannot store usage, for example because its disk is full, a call
that already reached its upstream still returns its result. Passport keeps that
call's count in memory and refuses the routes listed above with
`503 Service Unavailable` until the count is stored:

```json
{
  "ok": false,
  "code": "metering_unavailable",
  "error": "metering_unavailable",
  "message": "Passport cannot record usage right now, so upstream calls and new connections are paused until it can. Nothing was sent upstream; retry shortly."
}
```

A refused call never reaches an upstream, so it is safe to retry. Each new call
tries to store the kept counts first, and calls are accepted again as soon as
that works. While counts are kept, the usage report answers a window that
contains them with the same `503` instead of a total that leaves them out.
Other windows, reads, deletes, and health checks keep working.

## Usage report

`GET /v1/usage?from=2026-10-12T00:00:00Z&to=2026-10-12T02:00:00Z` with the tenant
administration token returns the tenant's usage for the window from `from`
(included) to `to` (excluded):

```json
{
  "type": "usage.report",
  "ok": true,
  "from": "2026-10-12T00:00:00Z",
  "to": "2026-10-12T02:00:00Z",
  "meters": { "connectionSeconds": 7200, "fetches": 42 }
}
```

Both bounds must be RFC 3339 UTC timestamps on whole hours, with `from` before
`to` and at most 31 days between them. Anything else returns `400` with
`"code": "invalid_request"` (also in `error`). Runtime grants cannot read the report, and the
failed-authentication backoff applies as on other administration routes.

`connectionSeconds` adds up the seconds each stored credential existed inside
the window. A stored credential is a connection or an MCP OAuth credential. It
counts from creation until it is deleted, whether or not it holds a working
login at the time. Importing new state into a connection or refreshing an MCP
token does not start a new count. Credentials created before usage tracking
count from the first start of a release that tracks them. Time after the
request is never counted.

`fetches` counts the authenticated fetches and runtime MCP transport calls that
got a response from their upstream, in the hours that start inside the window.
Requests refused before egress are not counted. That includes failed
authentication, validation errors, `409` responses, the backoff, and
destinations the egress screen denies. Starting a login does not contact an
upstream, so it is not counted either.

Passport keeps these meters in each tenant's directory, so they survive
restarts. A count that Passport could not store yet is reported in the hour it
was made, once it is stored. A self-hosted Passport is never billed by Ryu.
Ryu's hosted service reads this report to bill a hosted tenant; see
[pricing](/docs/standalone/passport#pricing).
