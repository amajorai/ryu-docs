Ryu Notify is a service-owned event and delivery contract, not a rebranded copy
of another notification product. The common product primitives are available
through one tenant-scoped API; provider-specific transports and identities stay
behind explicit adapters.

## Capability map

| Reference pattern | Ryu Notify surface | Boundary |
|---|---|---|
| [Boop](https://github.com/chrisgreg/boop) event inbox, grouping, actions, and redaction | Rich events, fingerprints, actions, redaction, archive/ack, groups, and SQLite history | Notify does not implement Boop's native device management or MCP server |
| [ntfy](https://ntfy.sh/) topic publishing, priorities, tags, and action headers | `POST /v1/topics/:topic` accepts JSON or plain text and maps priority, tags, click, and actions | An ntfy destination is an outbound adapter; Notify is not an ntfy server or account |
| [Hark](https://hark.ryan.ceo/docs) approvals, callbacks, retries, and Live Activities | Interactive responses, signed durable deliveries, and start/update/end activities | Notify does not provide Hark's native iOS device routing or Live Activity extension |
| [Novu](https://novu.co/) preferences and multi-channel workflows | Recipient mute/quiet hours, destinations, delivery attempts, and explicit service composition | Workflow DAGs, digests, billing, and provider-specific push/email remain separate owners |
| [LogSnag](https://logsnag.com/) event tracking and product analytics | Topic/source/level aggregates and fingerprint groups | The API returns bounded aggregates; it is not a hosted analytics dashboard |
| [BuzzKit](https://buzzkit.dev/buzz?t=6) human/agent realtime workspace | `buzzkit` HTTP bridge destination plus the same SSE event edge | Notify does not claim Buzz's Nostr signing, workspace identity, voice, or channel protocol |

## The durable contract

Every event is tenant-scoped and has an opaque id, source, type, project/topic
labels, priority, tags, optional actions and click-through URL, redacted data,
and acknowledgement/archive state. Event creation is safe to retry with an
`Idempotency-Key`. A disconnect is recovered by reading the bounded history
cursor before opening the live SSE stream again.

Destinations are also durable resources. Each enabled destination gets at most
one delivery row per event. Attempts are claimed from SQLite, retried with
bounded exponential backoff, and exposed through the delivery API. Webhooks
can be verified with `X-Ryu-Notify-Signature`; destination URLs and custom
header values are redacted from read projections.

## Interactive and live work

An event can carry one pending `approval`, `yes_no`, or `text` response. The
first valid response wins, an expiry is enforced when the event is read or
answered, and an optional HTTPS callback is invoked after the answer is stored.
Long-running work belongs in an activity resource: create it once, update it
with its sequence, and end it explicitly. Activity changes and notification
changes share the SSE connection but remain separate resource types.

## Choosing the adapter

Use the direct event API when your product already owns delivery. Use a webhook
when another system owns the channel. Use an ntfy destination for a compatible
topic server. Use the BuzzKit bridge only when your bridge endpoint owns the
BuzzKit authentication and protocol translation. Use Ryu Mail for email and
Core for Ryu user inboxes, workflow acknowledgements, desktop notifications,
and native push.
