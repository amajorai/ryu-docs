Use this sequence for a personal move or a production service cutover. It keeps the source
available, makes partial failures visible, and gives you a rollback path.

## Cutover sequence

1. **Inventory the source.** Separate setup, conversations, project folders, documents, app-owned
   records, provider configuration, webhooks, and secrets. Record the export time and the count for
   each category.
2. **Choose a stable identity map.** Keep each source ID beside its new Ryu ID. Do not match rows by
   display name or array position. Preserve timestamps, parent or reply links, source URLs, and the
   project folder that gave each item its context.
3. **Export before changing traffic.** Keep an untouched source export. For Ryu data, use the
   [data-folder zip](/docs/surfaces/desktop/user-guide/data-and-storage) for a complete node or a
   [portable package](/docs/extend/develop/extensions/portable-packages) for a definition or
   artifact tree.
4. **Preview the smallest slice.** Import one project, Space, agent, inbox, tenant, or date range
   first. Check titles, message order, links, attachments, permissions, and timestamps before
   importing the rest.
5. **Recreate access separately.** Sign in again to OAuth connections and create destination
   provider credentials. A copied identifier is not proof that the destination can use the source
   account.
6. **Run a canary.** Use a test project or internal recipients. For mail, confirm both the send
   path and inbound webhook before switching a production sender.
7. **Switch one boundary at a time.** Move reads first when possible, then writes, then webhooks.
   Keep the source in read-only or rollback mode until the destination passes its checks.
8. **Reconcile and close out.** Compare counts and source-ID maps, inspect failures, rerun only
   missing records, and record which source data was intentionally left behind.

Ryu's [agent sync](/docs/gateway/agent-sync) follows this shape. Its scan previews source items,
records source and generated hashes, avoids importing the same item twice, and pauses conflicts for
an explicit **Keep Ryu** or **Keep external** decision.

## Requirements for a migration-friendly importer

If you are building an importer or an alternative to an existing product, make these properties
part of the public contract:

1. **Export every durable resource.** Use bounded JSON, CSV, Markdown, or an archive. Include a
   schema version, stable IDs, timestamps, provenance, and an attachment manifest.
2. **Preview before writing.** Show counts, conflicts, unsupported fields, permissions, and
   secret-bearing files before the import changes state.
3. **Make retries converge.** Accept a source ID or idempotency key, record a source checksum, and
   make a retry update or skip the existing record instead of duplicating it.
4. **Separate content from access.** Import definitions and user-owned content. Reconnect OAuth,
   API keys, SMTP, webhooks, billing, and domain ownership through their own setup flows.
5. **Preserve unknown data.** Keep unrecognized fields in a bounded source snapshot or show a
   warning. Do not silently discard a user's data or guess provider-specific meaning.
6. **Provide rollback.** Keep the source read-only, support a staged canary, and let the caller
   switch the active provider or workspace back without rebuilding the mapping.
7. **Document guarantees.** State which resources, attachments, events, permissions, and delivery
   guarantees are supported. A successful HTTP response does not prove delivery, billing, or a
   production deployment.

## Verify before declaring success

- The source export opens and its record counts match the inventory.
- Re-running the import does not create duplicate threads, projects, documents, or messages.
- Imported threads have the expected title, message order, timestamps, project folder, and branch.
- Project files and Git history are present before an agent is allowed to edit them.
- Space source files are present and retrieval has been re-indexed on the destination configuration.
- Credentials, OAuth sessions, API keys, signing secrets, and billing state were recreated rather
  than copied into content exports.
- Mail canary sends are accepted by the configured transport, inbound signatures verify, and the
  application does not retry a lost response into a duplicate message.
- The old provider or source workspace remains available for the agreed rollback window.
