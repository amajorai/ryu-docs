A self-hosted Ryu server runs **Core** and **Gateway** on infrastructure you control.
Core runs agents, sessions, tools, memory, and workflows. Gateway controls model
and tool traffic. The server supports local, BYOK, and headless workloads without a
Ryu-operated account or backend.

This page covers the OSS server. Account, organization, billing, Marketplace,
managed inference, and Web/Mobile account surfaces are separate products.

## One-click deploy

Each button builds the repo's [`Dockerfile`](https://github.com/amajorai/ryu/blob/main/Dockerfile).
Core runs the stack and spawns the Gateway on loopback itself, so a hosted server
publishes only Core's port and is governed the moment it serves traffic.

&nbsp;
[![Deploy on Railway](https://railway.com/button.svg)](https://railway.com/new)

[![Deploy to DigitalOcean](https://www.deploytodo.com/do-btn-blue.svg)](https://cloud.digitalocean.com/apps/new?repo=https://github.com/amajorai/ryu/tree/main)

<Callout type="warn">
  Core downloads a fully-local model stack (llama.cpp + Gemma 4, nomic
  embeddings, whisper) on first boot. Pick a plan with **at least 2 GB of RAM**
  (4 GB is comfortable), or set a provider key such as `OPENAI_API_KEY` so Core
  routes to a hosted model and skips the local download. A 512 MB instance will
  not boot the local stack.
</Callout>

The templates live at the repo root — `render.yaml`, `railway.json`, `fly.toml`,
and `.do/deploy.template.yaml` — so each platform auto-detects its config.

## Docker

The whole stack is one image. To run Core and the Gateway as the two-service
split (the production shape):

```bash
git clone https://github.com/amajorai/ryu
cd ryu
docker compose up --build
```

That serves Core on `http://localhost:7980` and the Gateway on `:7981`, with
model state persisted in a named volume. Point any OpenAI-compatible client at
the Gateway's `/v1/chat/completions`.

The two-service file is an advanced topology: because Gateway binds on the
container network, configure Gateway authentication before exposing port 7981,
and give Gateway a provider or an engine URL reachable from the Gateway
container. Core's private loopback engine is not reachable through another
container's `127.0.0.1`. The single-image path below is the canonical simplest
self-hosted server shape.

To run just Core (it manages the Gateway in-process):

```bash
docker build -t ryu .
docker run --read-only --cap-drop=ALL \
  --security-opt=no-new-privileges:true \
  --pids-limit=1024 \
  --tmpfs /tmp:rw,noexec,nosuid,nodev \
  --user 10001:10001 \
  -p 7980:7980 -v ryu-data:/data ryu
```

Keep the Docker socket, host PID/network namespaces, host devices, and host
filesystem out of the container. The image already runs as UID `10001`; the
explicit flags above preserve that boundary when the command is copied into a
deployment script. For agent code that needs stronger isolation, use the
default `wasmtime` or a rootless container/microVM backend rather than mounting
host paths into an execution container.

## Fly.io

```bash
fly launch --copy-config --no-deploy
fly volumes create ryu_data --size 10
fly deploy
```

The committed [`fly.toml`](https://github.com/amajorai/ryu/blob/main/fly.toml)
sets the Dockerfile build, a `/data` volume, and a `/api/health` check.

## One VPS, one command

For a dedicated box, the Hetzner Cloud provisioner stands up a server end-to-end
(SSH key, firewall, server, Core + Gateway as systemd units). See
[Deploying Ryu](/docs/learn/academy/cloud/deployment) for the tiers, ports, firewall
model, and the managed-vs-self-hosted line.

The VPS installer keeps Core and Gateway under a dedicated non-login `ryu` user
with a read-only system view and one writable state directory. It refuses to
start a partially provisioned node when the pinned runtime or binary checksum
cannot be verified; do not weaken that failure-closed behavior in a systemd
override.

## What about Vercel and AWS?

Core and the Gateway are long-running servers, so they need a container host
(any of the above), not a serverless platform. **Vercel** is serverless: it is
perfect for the documentation site (`apps/fumadocs`, a Next.js app) but cannot
host Core or the Gateway. On **AWS**, run the same Docker image on Lightsail
Containers, App Runner, or ECS/Fargate with a persistent volume for `/data`.

For the common Core, Gateway, and client variables, see [Public environment variables](/docs/start-here/environment-variables).

<Callout type="info">
  The Gateway is **AGPL-3.0**. If you host a *modified* Gateway, section 13 of
  the AGPL requires you to offer your modified source to its users. Core is
  Apache-2.0 with no such obligation.
</Callout>
