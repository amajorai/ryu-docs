Use this page when you are moving from another AI agent, workspace, app, or provider. Start by
naming the data you need to move. Ryu keeps setup, conversations, source content, project folders,
app data, and credentials as separate boundaries, so the safest migration uses the smallest path
that contains what you need.

<Callout type="info">
Migration is a copy and cutover process. Keep the source available until you have checked the
destination. Ryu's agent setup importer reads the source folder and leaves the source files
untouched. It never imports API keys or provider credentials as agent secrets.
</Callout>

## Choose the migration path

| What you want to move | Use this path | What comes across | Important limit |
|---|---|---|---|
| Claude Code, Cursor, or Codex setup | [Import from another agent](/docs/surfaces/desktop/user-guide/import-agent) | Project instructions, skills, MCP servers, plugins, memories, subagents, and slash commands where the source format is supported | Review imported permissions and reconnect external accounts. |
| Past agent threads | [Agent import and export sync](/docs/gateway/agent-sync) | Claude Code and Codex transcripts become normal Ryu conversations; the working folder and branch can be retained as metadata | Cursor setup can be imported, but Cursor native conversation history is not currently a supported thread format. |
| An existing code project | [Git Workspace & Worktrees](/docs/surfaces/desktop/user-guide/git-workspace) | The existing folder, Git history, branches, and source folders | A project folder is not the same thing as a Projects app board. |
| An agent definition or extension | [Portable packages](/docs/extend/develop/extensions/portable-packages) | Versioned definitions and declared artifacts for agents, workflows, plugins, skills, themes, and other package kinds | Packages do not contain chat history, sessions, memory, or node credentials. |
| Documents and knowledge | [Spaces and RAG](/docs/core/spaces-rag) | Markdown pages, database schemas, and row files through a portable Space package | Embeddings and vector indexes are rebuilt on the destination node. |
| One complete Ryu node | [Data Folder & Storage](/docs/surfaces/desktop/user-guide/data-and-storage) | Conversations, Spaces, memory, media, models, and engine files in one zip backup | Restore is an offline operation because it replaces live database files. |
| One reviewed conversation between configured nodes | [RNP conversation continuity](/docs/extend/integrate/rnp) | A bounded, user-approved transcript snapshot | Files, credentials, run state, provider provenance, and native session state stay behind. |
| An existing OpenAI, Anthropic, or Gemini client | [Protocol compatibility](/docs/extend/integrate/protocol-compat) | The client can keep its native request shape while its base URL changes to Ryu | Compatibility changes the request path. It does not migrate the provider account or its history. |

<Callout type="warn">
There is no universal importer for arbitrary third-party app databases. Do not copy another
product's SQLite files into Ryu. Export through the source product or its API, map the data to a
Ryu-owned contract, and keep credentials in their existing secret boundary.
</Callout>

## Use a safe cutover sequence

For any source, use this order. It works for a small personal migration and gives a service owner
enough control for a larger move.

1. **Inventory the source.** Separate setup, conversations, project folders, documents, app-owned
   records, provider configuration, webhooks, and secrets. Record the source export time and the
   number of records in each category.
2. **Choose a stable identity map.** Keep the source ID beside the new Ryu ID. Do not match rows by
   display name or array position. Preserve timestamps, parent or reply links, source URLs, and
   the project folder that gave each item its context.
3. **Export before changing traffic.** Keep an untouched source export. For Ryu data, use the
   [data-folder zip](/docs/surfaces/desktop/user-guide/data-and-storage) for a complete node or a
   [portable package](/docs/extend/develop/extensions/portable-packages) for a definition or
   artifact tree.
4. **Preview and import the smallest slice.** Import one project, Space, agent, inbox, or date
   range first. Check titles, message order, links, attachments, permissions, and timestamps before
   importing the rest.
5. **Recreate access separately.** Sign in again to OAuth connections and create destination
   provider credentials. A copied identifier is not proof that the destination can use the source
   account.
6. **Run a canary.** Use a test project or internal recipients. For mail, confirm both the send
   path and the inbound webhook before any production sender is switched.
7. **Switch one boundary at a time.** Move reads first when possible, then writes, then webhooks.
   Keep the source in read-only or rollback mode until the destination has passed the checks.
8. **Reconcile and close out.** Compare counts and source-ID maps, inspect failures, rerun only
   missing records, and record which source data was intentionally left behind.

Ryu's agent sync follows this pattern. Its scan previews source items, records source and generated
hashes, avoids importing the same item twice, and pauses conflicts for an explicit **Keep Ryu** or
**Keep external** decision. Use [Agent import and export sync](/docs/gateway/agent-sync) when you
need that setup and transcript workflow.

## Move agent setup and threads

Open **Import a past agent thread** to bring a Claude Code or Codex transcript into a normal Ryu
conversation. Re-importing the same native thread adds only messages that were not imported before,
so you can keep working in the source tool during a staged migration. The imported conversation can
retain its recorded working directory and Git branch, which lets Ryu group it with the matching
project.

Open **Import agent setup** to scan a source folder. The scan can find project instruction files,
Agent Skills, MCP servers, plugins, Claude project memories, Codex subagents, and Codex slash
commands. Imported instructions register the containing folder as a project and are used on turns
that run in that folder.

After the import, review the following before you run an agent:

- MCP servers with custom headers or environment variables may need a new sign-in.
- Imported plugins stay disabled until you review their grants and enable them.
- Imported skills and commands can contain instructions that were written for the source tool.
- A native transcript restores readable message text. It does not automatically warm the source
  agent's private runtime context.

For a programmatic workflow, list and import native threads through `GET /api/agents/:id/threads`
and `POST /api/agents/:id/threads/import`. For agent definitions, use
`GET /api/agents/:id/export` and `POST /api/agents/import`; the imported definition receives a new
Ryu-owned identity. The [Agents API reference](/docs/extend/develop/api-reference/core/agents)
contains the generated request and response shapes.

If the source agent is already stored in Ryu, `POST /api/agents/:id/migrate-to-ryu` copies its
persona, tools, and model onto the Ryu engine without changing the source agent. See [Migrate an
agent onto the Ryu engine](/docs/extend/develop/api-reference/core/agents/migrate_to_ryu).

## Move projects without losing code context

There are two different meanings of project in Ryu.

### Project folder or repository

Open an existing folder, add source folders in **Edit project**, or use **Clone from GitHub**. The
folder remains the source of truth for code, Git history, branches, and project-local instruction
files. `AGENTS.md` and `CLAUDE.md` are read from the project hierarchy and can be edited without
creating a second instruction store.

When importing an agent thread, use the recorded working folder as the destination project. This
preserves the connection between a transcript and the files that gave it meaning. If the source
tool stored a path that no longer exists, import the transcript first and attach it to the correct
Ryu project after the repository is available.

### Projects app board

The Projects app is a local project board for project names, owners, due dates, delivery status,
and tasks. Its public page currently documents create and update behavior, not a cross-product
import/export contract. Treat an external board as an app-data migration, not as a Git folder
migration.

For a board migration, export the source board to CSV or JSON when the source supports it, keep the
source ID in your mapping, and map projects, owners, due dates, statuses, and tasks before creating
records. Import a small board first and check ownership and deadlines. If you need a repeatable
integration, build an app-specific importer rather than writing directly to another app's storage.

## Move a Ryu agent or Space

Use the portable contracts when the destination should receive a reusable definition rather than a
personal node copy.

- An agent export carries its name, version, system prompt, tools, engine, and per-attribute slots.
  Import creates a new unlocked copy. See [Import an agent](/docs/extend/develop/api-reference/core/agents/import_agent)
  and [Export an agent](/docs/extend/develop/api-reference/core/agents/export_agent).
- A Space package carries Markdown source, YAML frontmatter, database schemas, and row files. It
  does not carry embeddings, vector tables, credentials, or chat state. Re-index it with the
  destination node's current embedding configuration.
- A portable package can be a local folder, a `.ryupack` archive, or a pinned GitHub package. Use
  [portable packages](/docs/extend/develop/extensions/portable-packages) when the result should be
  versioned, reviewable, or installable by another user.

If the destination should look exactly like the source node, use the full data-folder export
instead. A package and a data backup solve different migration problems.

## Resend-style provider migration

Use this section when an application currently sends through Resend and you are moving it to Ryu
Mail or building a compatible alternative. Treat this as a provider cutover, not as an account
clone.

Resend separates email activity, domains, contacts, templates, API keys, and webhooks. Its dashboard
also offers admin CSV exports for emails, broadcasts, contacts, segments, domains, logs, and API
keys. Export those categories before you remove the old account or key. See the official [Resend
email export documentation](https://resend.com/docs/dashboard/emails/introduction).

<Callout type="warn">
Ryu Mail is not documented as a Resend drop-in importer. Its public contract covers inboxes,
messages, attachments, SMTP hand-off, and a signed inbound webhook. It does not define an import
for Resend domains, hosted templates, contacts, broadcasts, suppressions, API keys, or delivery
history. Keep each mapping explicit and keep the old provider available for rollback.
</Callout>

| Resend concern | Migration action | Ryu Mail boundary |
|---|---|---|
| Send calls | Put a provider adapter behind the application's existing send function. Map `to`, `cc`, `subject`, `text`, `html`, and `inReplyTo`. | `POST /api/mail/inboxes/:id/send` sends from the selected inbox through its configured SMTP transport. |
| Sending address and domain | Recreate the sender at the destination and verify its DNS and transport before changing production traffic. Keep the source DNS and sender configuration available during the canary. | An inbox has a fixed address. Ryu Mail uses a bring-your-own domain model and does not move the Resend domain record for you. |
| Inbound mail | Export any source routing rules you need. Configure the new forwarder only after the destination inbox exists, then test a signed inbound message. | `POST /api/mail/inbound/:id` accepts raw inbound mail with that inbox's HMAC secret. It is not a Resend event envelope. |
| Delivery events | Normalize provider events into your application's event model. Store the source event ID and received time, and make handlers safe to replay. | Ryu Mail exposes `Email received` and `Email sent` hook events. A successful send means transport hand-off, not recipient delivery; a later bounce is not visible in this process. |
| Contacts and audiences | Import the source CSV into the system that owns contacts and consent. Do not use an inbox table as a mailing list. | The documented Mail API has no contacts, audiences, segments, or broadcast contract. |
| Hosted templates | Keep the template source in your application or move it to the destination renderer. Test rendered HTML and plain text separately. | The send body accepts rendered `text` and `html`; the documented Mail API has no hosted-template endpoint. |
| API keys and signing secrets | Issue new destination credentials. Store them in the destination secret store and rotate the source key only after the cutover is proven. | Standalone Mail uses `RYU_MAIL_API_TOKEN` for protected routes. Inbound mail uses a separate per-inbox HMAC secret. |
| History and logs | Preserve the source export as a read-only archive. Keep source IDs and provider message IDs beside any records you recreate. | Mail messages are owned by the Mail service. The public contract does not provide a Resend-history importer. |

The Ryu Mail send shape is intentionally small:

```json
{
  "to": ["person@example.com"],
  "cc": [],
  "subject": "Your receipt",
  "text": "Thanks for your order.",
  "html": "<p>Thanks for your order.</p>",
  "inReplyTo": "<previous-message@example.com>"
}
```

The `inReplyTo` value is the source message's `Message-ID` when you want the recipient's mail
client to continue the same thread. Ryu Mail records a provider message ID after transport hand-off
but does not claim that the recipient received the message. See [Standalone Ryu Mail](/docs/standalone/mail)
for authentication, inbound signing, and the complete route table.

### Resend-to-Ryu cutover

1. **Create one provider interface.** Keep your application code independent of `resend` or Ryu
   Mail. Put provider-specific payloads, errors, retries, and event verification inside adapters.
2. **Export and map.** Download Resend's admin exports, preserve every source ID, and map contacts,
   templates, domains, webhooks, and message history to their real owners. Do not put all of them
   into the Mail inbox store.
3. **Provision the destination.** Create a Ryu Mail inbox, configure its SMTP transport, save its
   protected bearer, and store its inbound HMAC secret in the forwarder. Ryu Mail returns the
   inbound secret only when an inbox is created or its secret is rotated.
4. **Test without duplicate sends.** Send only to internal test recipients. Confirm the rendered
   message, reply threading, inbound signature check, attachments, and application event handling.
5. **Canary one workload.** Route one application, tenant, or notification class through the new
   adapter. Compare accepted-send counts, failures, reply threading, and inbound processing.
6. **Switch and retain rollback.** Change the provider selection, keep the old adapter and source
   exports available, and stop the old path only after the destination has passed the reconciliation
   window.

Resend supports an `Idempotency-Key` for email send and batch-send requests for a limited window.
The documented Ryu Mail send body has no equivalent idempotency field, so do not blindly retry a
lost `POST /api/mail/inboxes/:id/send` response. If a retry could duplicate a real email, keep a
send ledger in your application keyed by your own message or notification ID. See [Resend
idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys) and [Ryu Mail](/docs/standalone/mail).

Resend webhooks are at-least-once and can arrive out of order. A compatible alternative should
deduplicate by an event ID, persist the event timestamp, and make replay safe. Ryu hook consumers
should apply the same discipline even though the Mail service's inbound path uses per-inbox HMAC
instead of Resend's webhook signing scheme. See [Resend webhooks](https://resend.com/docs/webhooks/introduction)
for the source provider's event and retry behavior.

## Build migration into your own alternative

If you are building a Ryu app or a service that replaces another product, make migration a first
class contract from the first release.

1. **Expose an export.** Provide a bounded JSON, CSV, Markdown, or archive export for every durable
   resource. Include a schema version, stable IDs, timestamps, source provenance, and a manifest of
   attachments.
2. **Expose a preview.** Let users see counts, conflicts, unsupported fields, permissions, and
   secret-bearing files before the import writes anything.
3. **Make import repeatable.** Accept a source ID or idempotency key, record the source checksum,
   and make retries converge instead of duplicating rows or sending a second side effect.
4. **Separate content from access.** Import definitions and user-owned content. Reconnect OAuth,
   API keys, SMTP, webhooks, billing, and domain ownership through their own setup flows.
5. **Preserve unknown data.** Keep unrecognized fields in a bounded source snapshot or a visible
   warning. Do not silently discard a user's data or guess a provider-specific meaning.
6. **Give users a rollback.** Keep the source read-only, support a staged canary, and let the
   caller switch the active provider or workspace back without rebuilding the mapping.
7. **Document the exact boundary.** State which resources, attachments, events, permissions, and
   delivery guarantees are supported. A successful HTTP response must not imply delivery, billing,
   or production deployment.

These rules match Ryu's own split between [portable packages](/docs/extend/develop/extensions/portable-packages),
[agent sync](/docs/gateway/agent-sync), [node backups](/docs/surfaces/desktop/user-guide/data-and-storage),
and [protocol compatibility](/docs/extend/integrate/protocol-compat). Choose one canonical owner
for each resource and expose an explicit adapter when another surface needs a projection.

## Migration checklist

Before declaring the move complete, verify:

- The source export opens and its record counts match your inventory.
- Re-running the import does not create duplicate threads, projects, documents, or messages.
- Imported threads have the expected title, message order, timestamps, project folder, and branch.
- Project files and Git history are present before an agent is allowed to edit them.
- Space source files are present and retrieval has been re-indexed on the destination configuration.
- Credentials, OAuth sessions, API keys, signing secrets, and billing state were recreated rather
  than copied into content exports.
- Mail canary sends are accepted by the configured transport, inbound signatures verify, and your
  application does not retry a lost response into a duplicate message.
- The old provider or source workspace remains available for the agreed rollback window.
