---
title: "Platform consistency"
description: "The rules Ryu uses to keep clients, Core, Gateway, extensions, and documentation aligned."
---

Ryu is one platform across Desktop, Web, Mobile, CLI/TUI, extensions, and apps. The same behavior
should not be redefined separately for every host. Ryu keeps the surfaces aligned through explicit
ownership, versioned contracts, and bounded projections.

## The one-source rule

Every cross-surface capability has:

1. one owner;
2. one canonical contract;
3. one source of truth;
4. explicit adapters or projections for each host; and
5. verification that states what was actually tested.

Many clients may consume a capability, but they must not become independent authorities for its
policy or data model.

## Ownership

| Concern | Owner | What other surfaces do |
|---|---|---|
| What runs: agents, sessions, workflows, tools, files, and sidecars | Core | Clients request and display the result. |
| What is allowed, shared, measured, or paid for | Gateway | Core and clients consume the decision; they do not replace it. |
| Product-specific process and state | The owning app or plugin | The package exposes its declared contract through the generic host seams. |
| Shared data shapes | A contracts package, crate, or versioned fixture | Runtime implementations consume the shared shape. |
| Presentation | The host surface and shared UI system | Desktop, Web, Mobile, and CLI adapt the same behavior to their host. |
| Public product documentation | Fumadocs | Internal operational material stays outside the public docs. |

The placement rule is: **what runs belongs in Core; what is allowed, shared, measured, or paid for
belongs in Gateway**. A plugin or app should use the existing lifecycle, capability, and proxy
contracts instead of adding a host-specific bypass.

## Configuration and serialization

Ryu chooses a format by ownership:

| Format | Use it for |
|---|---|
| **JSON** | Machine-managed state, cross-language configuration, manifests, API payloads, and generated or signed artifacts |
| **TOML** | Human-authored service policy, including Gateway configuration |
| **YAML** | External contracts that require it, or document metadata such as this page's front matter |
| **Environment or secret store** | Secrets, bootstrap values, deployment shape, and process wiring |

Ryu does not introduce new Ryu-native YAML runtime configuration. The format is not a security
boundary: credentials remain in the appropriate secret or deployment boundary regardless of the
neighboring file format.

The same logical setting has one source of truth. A generated JSON, TOML, or TypeScript projection
is read-only output, not a second authoring surface.

## Public contracts

- HTTP surfaces are described by OpenAPI. SDKs and clients consume the published contract rather
  than duplicating endpoint shapes by hand.
- New public JSON fields use `camelCase`. Existing contracts retain their spelling for
  compatibility; an adapter handles legacy names at the boundary.
- Resource IDs are stable opaque identifiers, not display names or array positions. Package,
  capability, permission, and route IDs use stable namespaces.
- New public timestamps use RFC 3339 UTC. Existing epoch-millisecond contracts remain valid when
  their unit is explicit in the contract.
- Compatibility versions are explicit. Package versions, capability versions, schema versions,
  and product release versions are related but not interchangeable.
- Clients branch on stable error codes and documented status values, not human-readable error text.

## Requests and operations

Every mutating operation documents its authentication, authorization, input limits, conflict
behavior, retry policy, and success and failure states. Long-running work uses a stable operation
ID and an explicit state such as `pending`, `running`, `completed`, `failed`, or `canceled`.

Retries must be safe. A lost response must not duplicate a message, charge, side effect, or audit
record. When an operation cannot be naturally repeated, it uses an idempotency key or returns a
conflict instead of guessing.

Lists are bounded by the server. Data that can change during traversal uses a documented cursor
contract rather than requiring clients to infer pagination behavior.

## Security boundary

- Authorization is enforced by the server-side owner of the resource or capability. UI visibility
  is not permission enforcement.
- Grants and permissions are declarations, not approval. Activation resolves them before execution
  and fails closed when a required grant is denied.
- Bootstrap, node-control, inference, provider, session, and user credentials are separate
  purposes and are not interchangeable.
- Manifests, imported documents, provider responses, webhooks, and user-authored instructions are
  untrusted data at every boundary.
- Secrets, private keys, master keys, and deployment-only values do not belong in public manifests,
  examples, or ordinary behavior configuration.

See [Permissions](/docs/security/permissions), [Trust model](/docs/security/trust-model), and
[Plugin isolation](/docs/security/plugin-isolation) for the detailed security contracts.

## Plugins and apps

`manifest.json` is the native Ryu source of truth for an extension. Agent Plugins files,
Marketplace views, and other interop files are projections. A packed bundle must contain the
resolved wire form expected by the runtime; authoring-only references are not left unresolved.

Apps-store packages own their product process, sidecar, and companion surface. Their UI and backend
use the generic host and proxy contracts. Capability consumers declare an abstract requirement and
let the capability broker resolve the provider, so a consumer does not hardcode a provider app.

Start with [Extension schemas and layouts](/docs/extend/develop/extensions/schemas-and-layouts),
[Plugins versus apps](/docs/extend/develop/extensions/plugins-vs-apps), and
[The Runnable model](/docs/start-here/architecture/runnable-model).

## Host and UI consistency

- Shared components, semantic tokens, typography, spacing, motion, and accessibility behavior
  come from the shared UI system or a documented host adapter.
- Optional capabilities are feature-detected. A contribution declaration does not grant arbitrary
  host access.
- User-facing flows define the states that can occur: loading, empty, success, error, disabled,
  permission denied, and unavailable or offline.
- Shared flows keep their terminology, control order, keyboard behavior, focus behavior, and
  destructive-action confirmation consistent across hosts.

The host may change layout for its platform, but it should not silently change the meaning,
permission, or failure behavior of the underlying operation.

## Documentation, privacy, and evidence

- A user-facing behavior, configuration field, API, extension contract, install path, or upgrade
  behavior updates its relevant Fumadocs page in the same change.
- This Fumadocs site is public. Private environment variables, internal ports, private repository
  links, debugging endpoints, and unverified production claims do not belong here.
- Generated API, SDK, Marketplace, and mirror artifacts have a named source of truth and a check
  command. Generated output is not hand-edited.
- Logs and telemetry are structured, bounded, and redacted. Security audit, product analytics,
  crash reporting, and OTLP export are separate purposes with separate consent decisions.
- Focused tests, contract fixtures, service integration, host/browser tests, builds, releases,
  and deployments are separate evidence. A passing test or healthy endpoint does not prove the
  other boundaries.

## Feature checklist

Before implementing a cross-surface feature, write down:

| Question | Required answer |
|---|---|
| Where does it belong? | Core, Gateway, app/plugin, host, contracts, or docs |
| What is canonical? | Schema, fixture, manifest, OpenAPI document, or store |
| How is it projected? | REST, streaming, CLI, MCP/A2A, SDK, Desktop/Web/Mobile/TUI |
| How is it secured? | Auth, permission/grant, secret, trust, and fail-closed behavior |
| How does it evolve? | Version, compatibility, migration, idempotency, and rollback |
| How is it verified? | Focused, integration, host, build, release, and deployment evidence |
| What docs change? | Public Fumadocs, generated pages, and internal runbook if needed |

This is an incremental standard. Existing contracts are changed through explicit compatibility
windows or migrations rather than a big-bang rewrite.
