Pi is the coding agent from Earendilworks that Ryu uses as its default engine. This page covers how
Pi works inside Ryu's managed environment: the config layer, model routing, and the tool bridge.
Context trimming and compaction are in
[Pi Context Management](/docs/start-here/architecture/pi-context-management).

## The managed binary

Ryu ships its own Pi binary, completely separate from any Pi you have on your PATH:

| Location | Purpose |
|---|---|
| `~/.ryu/runtimes/pi/generations/<active>/node_modules/.bin/pi` | The managed Pi binary (installed via `bun add`) |
| `~/.ryu/runtimes/pi/generations/<active>/node_modules/.bin/pi-acp` | The ACP bridge (spawns Pi as a subprocess speaking ACP) |
| `~/.pi/agent` | User's own Pi config (never touched by Ryu) |
| `~/.ryu/runtimes/pi-agent` | Ryu's isolated Pi config directory |

Onboarding installs the managed Pi engine (`@earendil-works/pi-coding-agent`) and its ACP bridge
(`pi-acp`) together. Each install goes into a new runtime generation under `~/.ryu/runtimes/pi/generations/`, and Ryu
switches to it only after a local readiness check passes:

- Pi reports the expected version.
- Pi's own extension loader loads every Pi extension Ryu ships: the MCP, LSP and plan-mode
  extensions, plus those from built-in plugins such as `pi-shell`, `pi-subagent`, `pi-monitor` and
  `pi-copy`.
  A release that breaks an import they use, or an API they call while loading, is rejected here,
  before any conversation runs on it.
- The bridge completes an ACP `initialize` and `session/new` handshake.

The check sends no prompt and makes no provider request. If the check fails, the previous generation keeps running.

### Automatic updates

Ryu keeps the engine and the bridge up to date the same way it keeps other ACP bridges current:

- Core checks npm a couple of minutes after it starts, then every six hours.
- It installs the newest stable release of each package that has been published for at least seven
  days. The same seven-day rule applies to Pi's own dependencies while they are installed.
  Deprecated and prerelease versions are skipped.
- An update runs only when Pi is already installed, and it never moves below the version this Ryu
  release requires. If the installed runtime is incomplete or damaged, the same check repairs it.
- Conversations that are already running keep the generation they started with. New conversations
  use the updated one. Ryu removes older generations the next time Core starts, except one whose
  processes it could not confirm had stopped.

The **Update** action on the Ryu agent row runs the same check right away. It reports an update when the
engine or the bridge is behind the newest release that has passed the seven-day rule, or when the
installed runtime needs repair. To turn off background updates, for example on an offline machine,
set `pi.autoUpdate` to `"off"` in [`node-config.json`](/docs/start-here/configuration#core-node-config),
or start Core with `RYU_PI_AUTO_UPDATE=off`.

## The config directory

Ryu's Pi config lives at `~/.ryu/runtimes/pi-agent` (override with `RYU_PI_AGENT_DIR`). The env var
`PI_CODING_AGENT_DIR` is injected into the Pi subprocess to enforce this isolation.

Pi reads three files (per [pi.dev/docs](https://pi.dev/docs)):

### settings.json

```json
{
  "defaultProvider": "openai",
  "defaultModel": "gemma-4-E2B-it-Q4_K_M",
  "defaultThinkingLevel": "medium",
  "x-ryu-routing": "gateway",
  "x-ryu-provider-routing": { "openai": "gateway" },
  "x-ryu-active-provider": "gateway",
  "skills": ["!**"],
  "quietStartup": true,
  "defaultTools": ["+codemode"],
  "extensions": ["<path>/ryu-mcp.ts"]
}
```

| Field | Purpose |
|---|---|
| `defaultProvider` | The active provider id (`"openai"` because the Gateway is pinned as the `openai` provider) |
| `defaultModel` | The model to use (local Gemma 4 or `openrouter/auto` for managed) |
| `defaultThinkingLevel` | Reasoning effort (`none`, `low`, `medium`, `high`) |
| `x-ryu-routing` | Ryu-namespaced: `"gateway"` or `"direct"`, whether the active provider routes through the Gateway |
| `x-ryu-provider-routing` | Per-provider routing map: `{ "openai": "gateway", "anthropic": "direct" }` |
| `x-ryu-active-provider` | Logical active provider id (`"managed-openrouter"`, `"gateway"`, etc.) |
| `skills` | `["!**"]` disables Pi's own skill auto-discovery; Core injects its own allowlist-gated skills |
| `quietStartup` | Hides Pi's startup banner, so a new chat does not open with a skills listing |
| `defaultTools` | `["+codemode"]` adds Pi's codemode tool to Pi's default tools (see [Codemode](#codemode)) |
| `extensions` | The `ryu-mcp.ts` bridge extension giving Pi access to Core's tools |

Pi ignores unknown keys, so the `x-ryu-*` fields survive round-trips. Ryu writes `skills`,
`quietStartup` and `defaultTools` only when they are missing, so a value you set in this file
stays. Set `"defaultTools": ["-codemode"]` to turn codemode off.

### models.json

The critical file that pins Pi's providers. Ryu writes this to ensure model calls route through
the Gateway:

```json
{
  "providers": {
    "openai": {
      "baseUrl": "http://127.0.0.1:7981/v1",
      "api": "openai-responses",
      "apiKey": "<gateway_token>",
      "models": [
        {
          "id": "gemma-4-E2B-it-Q4_K_M",
          "input": ["text", "image"],
          "contextWindow": 128000,
          "maxTokens": 8192
        }
      ]
    }
  }
}
```

The `api: "openai-responses"` keeps Pi on its native Responses wire format. The Gateway translates
that request through the same governed inference pipeline. The `baseUrl` points at the local
Gateway (`:7981/v1`), and the `apiKey` is the Gateway token (not a provider key).

For the managed subscription, the default model is `openrouter/auto`. The Gateway maps this onto
the OpenRouter provider.

### auth.json

Per-provider API keys and OAuth subscription tokens:

```json
{
  "openai": { "type": "api_key", "key": "sk-..." },
  "anthropic": { "type": "oauth", "access": "...", "refresh": "...", "expires_at": "..." }
}
```

OAuth tokens are proactively refreshed by `refresh_pi_oauth_logins()` before each turn to prevent
mid-conversation auth failures.

Credentials are sealed with the at-rest master key (`RYU_MASTER_KEY`, then the OS keychain, then
`~/.ryu/secrets/master.key`) and stored in the multi-account vault at
`~/.ryu/secrets/pi-accounts.db`. `auth.json` holds only the active account, so Pi reads the file
format it expects.

## Context window management

Ryu bounds Pi's context so the system prompt is never evicted on overflow. Trim and Compact modes,
cache-stable cuts, model-switch handoff, and the preferences that enable them are in
[Pi Context Management](/docs/start-here/architecture/pi-context-management).

## The ryu-mcp.ts extension

Pi's ACP bridge does not pass MCP servers through from the ACP session, so Ryu connects Pi to its
tools itself. The `ryu-mcp.ts` extension does this in two ways:

- **As a Pi MCP server.** When a Pi session starts, the extension registers Core's MCP bridge
  with Pi's built-in MCP client as the server `ryu`. It is the same governed bridge every other
  ACP agent gets: the agent's allowlist, its selected Composio actions, its bound identity
  profiles, approval prompts and the `ask_user` question card all apply. The tools appear as
  `mcp__ryu__<tool>` with *deferred* exposure, so they stay out of the prompt until Pi's
  `tool_search` loads a match. `ask_user` is always declared. While codemode is on, Core's own
  script sandbox (`execute` / `resume`) is hidden, because Pi's codemode covers the same ground.
  If you turn codemode off, the extension leaves `execute` and `resume` deferred like the other
  tools, so Pi can still run scripts. It decides this when the session starts.
- **As two proxy tools.** `ryu_call_tool` calls any Ryu tool by its id, including tools that are
  searchable but not listed, such as Composio actions and operations derived from installed apps.
  `ryu_list_tools` lists the agent's Ryu tools. Core's script sandbox is never offered on this
  path.

Both paths use one short-lived credential that Core issues for that chat's Pi session. It is
bound to that session and works for nothing else in Core. Tools that render an interactive app
(Apps-SDK / MCP apps) show it inline in the chat on either path.

Subagents started by the `pi-subagent` plugin run as separate Pi sessions and do not register the
`ryu` server.

### Codemode

Ryu turns on Pi's `codemode` tool by default. With codemode the model can write a short
JavaScript script that calls several tools, including `mcp__ryu__*` tools, in one step. The
script runs in Pi's sandbox. Each tool it calls still goes through the same checks as a direct
call: plan mode, Ryu's command policy and approval prompts apply.

Scripts can also generate images with `models.generateImages()` (see Pi's
[codemode documentation](https://pi.dev/docs)). When the managed Pi routes through the Gateway,
Ryu lists the Gateway's image models under the `ryu-gateway-images` provider. Only models that a
provider configured on your Gateway can serve appear there. Those requests go through the
Gateway's `/v1/images/generations` route, so the Gateway's budgets, policies and audit log apply
to them as they do to chat. Image references are not supported on this route; prompts are text
only. If you sign in to OpenRouter in the managed Pi, OpenRouter's own image models are available
as well.

Plan mode also blocks `mcp__ryu__*` tools, except `tool_search`, `describe` and `ask_user`,
because those tools can change things the same way `ryu_call_tool` can.

## Provider routing

The Ryu agent supports per-provider routing. Each configured provider can independently route
through the Gateway or bypass it:

```json
{
  "x-ryu-routing": "gateway",
  "x-ryu-provider-routing": {
    "openai": "gateway",
    "anthropic": "direct",
    "local": "gateway"
  }
}
```

The desktop UI shows this as a per-provider toggle. The `x-ryu-routing` key records the *active*
provider's mode for backward compatibility.

## Error handling

| Scenario | What happens |
|---|---|
| Managed binary not installed | Core falls back to the `acp:pi` bridge (`npx -y pi-acp`) and your Pi on PATH, still reading Ryu's isolated config directory (slower first start) |
| Gateway unreachable | Pi fails to connect; error surfaced to user |
| Config directory missing | Core creates it on demand |
| OAuth token expired | `refresh_pi_oauth_logins()` refreshes before the turn |
| Context overflow (no management) | llama.cpp context-shift drops tokens (may lose system prompt) |
| Context overflow (trim mode) | Older turns dropped, system prompt preserved |
| Context overflow (compact mode) | Older turns summarized, summary injected as leading block |
