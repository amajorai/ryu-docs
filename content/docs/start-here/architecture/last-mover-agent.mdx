title: "The last-mover agent"
description: "How Ryu combines the delegated-work experience of Manus and Grok Bot with a portable, governed runtime."
---

Ryu is taking a deliberate last-mover position: let other products teach us what makes agents
useful, then make the underlying execution more durable, inspectable, and portable.

The target experience is simple:

> Give Ryu an outcome. Ryu shows the plan, does the work, asks when judgment matters, and leaves
> a receipt for what actually happened.

The interface should feel like handing work to a teammate. The runtime should still know exactly
which user, agent, model, tool, policy, budget, and execution location are responsible.

## What we borrow

[Manus](https://open.manus.im/docs/v2/task-lifecycle) and
[Grok Bot](https://x.ai/news/introducing-grok-bot) are useful product references because they make
long-running work feel like delegation instead of configuration.

Ryu's product direction is to bring these patterns to a governed, portable runtime:

| Product behavior | Ryu version |
| --- | --- |
| One natural-language handoff | A user starts a durable task from Bot, Console, a channel, CLI, or SDK without first assembling a workflow graph. |
| Visible plan and progress | The task shows a short intent plan, current step, waiting state, and bounded progress events. |
| Work that continues after the user leaves | The task has a durable run id, replay cursor, retry lineage, and a resumable transcript. |
| Work product, not only a reply | Artifacts, structured output, citations, diffs, and verification are attached to the final receipt. |
| Judgment at the right moment | A typed approval or input request pauses only the consequential action, with an exact scope and expiry. |
| A computer or workspace of its own | Local, worktree, remote, and cloud execution are explicit profiles; each reports its real sandbox and readiness state. |
| A small team of agents | Specialist runs can execute under one parent task while keeping child lineage, ownership, memory, and permissions separate. |
| Learning from successful work | Ryu proposes a Skill, routine, workflow, or memory diff after a successful run; the user reviews before it becomes durable. |

“Answer” and “Do” are different modes. A quick answer should not require a workflow ceremony.
Work that changes systems, runs for a long time, or needs verification should become a task with an
observable lifecycle.

## What we do not copy

The reference products also expose boundaries that Ryu should keep visible:

- [Hermes Agent](https://hermes-agent.nousresearch.com/docs/user-guide/security/) defines a
  single-tenant personal trust envelope. Its Python plugins and gateway injection are not a
  substitute for isolated, multi-user authorization.
- [OpenClaw](https://docs.openclaw.ai/gateway/security) explicitly is not a hostile multi-tenant
  boundary. Its security docs call out untrusted web, email, file, and attachment content, while
  [sandboxing](https://docs.openclaw.ai/gateway/sandboxing) is an option that is off by default and
  elevated tools can escape it.
- [Mastra](https://mastra.ai/ai-workflows) gives developers strong primitives, but the application
  still chooses persistence, execution infrastructure, memory layers, observability, and cost
  policy. Ryu should not turn every customer into its own platform team.
- [LangChain](https://docs.langchain.com/oss/javascript/concepts/products) correctly separates
  the easy framework from the durable runtime. That flexibility also means persistence, middleware,
  replay safety, and deployment choices remain part of the application's burden. Ryu keeps
  cross-cutting governance at the Gateway.
- [Manus](https://help.manus.im/en/articles/14178443-what-is-the-my-computer-feature-capable-of)
  demonstrates the value of local computer access, but local folders and logged-in applications
  require visible authorization and scope. Agent mode also has a credit cost and local execution
  depends on an online desktop.
- Grok Bot is announced as an early beta with separate Bot usage and limited availability. Its
  own-computer and teammate model is the right UX reference; Ryu should not hide cloud ownership,
  provider lock-in, usage, or the limits of its current adapter.

Prompt text is not authorization. Memory text is not canonical policy. A successful model response
is not proof that the requested side effect happened.

## The task receipt

Every durable task should project one consistent receipt across Ryu surfaces:

1. **Intent** — outcome, assumptions, data sources, execution profile, tools, budget, and approval
   policy.
2. **Plan** — a short, editable plan when the work is ambiguous, consequential, or long-running.
3. **Execution** — run id, owner, agent, model/provider, current step, elapsed time, and progress.
4. **Decision** — the exact action awaiting approval or input, affected resource, scope, expiry, and
   available choices.
5. **Evidence** — artifacts, citations, structured output, diffs, tool receipts, usage, and
   verification.
6. **Outcome** — completed, partially completed, waiting, canceled, or failed.
7. **Reuse** — a reviewable proposal for a Skill, memory, workflow, routine, or connector binding.

The receipt is the product bridge between Ryu's existing
[durable harness](/docs/extend/develop/sdk/harness), [approvals](/docs/core/approvals),
[workflows](/docs/core/workflows), [routines](/docs/core/scheduler), and
[chat artifacts](/docs/surfaces/desktop/user-guide/chat-messages) surfaces.

## Safety invariants

Ryu keeps these properties true even when the agent is autonomous:

- Every action has a server-enforced owner and permission boundary.
- External writes, deployments, messages, credentials, destructive operations, and policy changes
  require the appropriate approval.
- Approval binds to the action arguments, actor, resource scope, and expiry; replaying an old
  approval cannot authorize a different action.
- Tool results and fetched content stay untrusted when they return to the model.
- Context is bounded. Stable identity and policy stay separate from retrieved data, memory, and
  tool output.
- Mutable policy is read from its canonical source and verified after a write. Memory is evidence,
  not authority over live configuration.
- Budgets, timeouts, repeated failures, and missing verification stop a run clearly.
- A provider-native agent that bypasses the Gateway is labeled as a bypass. An unavailable remote
  or cloud adapter never silently falls back to local execution.
- Learning never silently rewrites persona, permissions, organization policy, or shared memory.

See [Core versus Gateway](/docs/start-here/architecture/core-vs-gateway) and
[agent hardening](/docs/gateway/agent-hardening) for the enforcement boundary.

## How we know it is working

This strategy is complete only when the real product can demonstrate that:

- one message creates a task with a plan, live progress, and a durable final receipt;
- closing and reopening the client resumes the same task without duplicate external effects;
- an approval can be approved, edited, rejected, or limited to its stated scope;
- poisoned external content cannot become a trusted instruction or bypass policy;
- long context stays usable through bounded loading and honest compaction state;
- failures say what completed, what did not, and whether retry is safe;
- delegated work shows parent and child lineage without merging permissions or memory;
- local, worktree, remote, and cloud status is truthful at the point of use;
- a successful run produces a reviewable reusable-change proposal.

That is the last-mover advantage: the front door is as easy as a bot, while the part that matters
after the demo is durable, governed work.
