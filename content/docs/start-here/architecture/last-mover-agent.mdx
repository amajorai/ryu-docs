Ryu's quality bar for delegated work: the normal path needs no setup, and every failure explains
itself.

The runtime handles persistence, permissions, routing, evidence, and recovery, so the user does not
assemble them. The user gets clear defaults, useful feedback, and an accurate answer when something
needs attention.

Give Ryu an outcome. Ryu shows the plan, does the work, asks when judgment matters, and leaves a
receipt for what actually happened. The system must know which user, agent, model, tool, policy,
budget, and execution location are responsible for the result.

## The quality bar

| Product behavior | Ryu behavior |
| --- | --- |
| One handoff | Start a durable task from Bot, Agent, a channel, the CLI, or the SDK without first assembling a workflow graph. |
| Visible progress | Show a short intent plan, the current step, waiting states, and bounded progress events. |
| Continuity | Keep a durable run id, replay cursor, retry lineage, and resumable transcript when work continues after the user leaves. |
| A work product | Attach artifacts, structured output, citations, diffs, and verification to the final receipt. |
| Judgment at the right moment | Pause only the consequential action for typed approval or input, with an exact scope and expiry. |
| An explicit workspace | Report whether execution is local, in a worktree, remote, or in the cloud, including its real sandbox and readiness state. |
| Reusable work | Propose a Skill, routine, workflow, or memory change after a successful run, then wait for review before making it durable. |

The experience should stay small even when the work is large. A quick answer should not require a
workflow ceremony. Work that changes systems, runs for a long time, or needs verification should
become a task with an observable lifecycle.

## The task receipt

Every durable task should project one consistent receipt across Ryu surfaces:

1. **Intent.** Outcome, assumptions, data sources, execution profile, tools, budget, and approval policy.
2. **Plan.** A short, editable plan when the work is ambiguous, consequential, or long-running.
3. **Execution.** Run id, owner, agent, model or provider, current step, elapsed time, and progress.
4. **Decision.** The exact action awaiting approval or input, affected resource, scope, expiry, and available choices.
5. **Evidence.** Artifacts, citations, structured output, diffs, tool receipts, usage, and verification.
6. **Outcome.** Completed, partially completed, waiting, canceled, or failed.
7. **Reuse.** A reviewable proposal for a Skill, memory, workflow, routine, or connector binding.

The receipt connects Ryu's existing [durable harness](/docs/extend/develop/sdk/harness),
[approvals](/docs/core/approvals), [workflows](/docs/core/workflows),
[routines](/docs/core/scheduler), and [chat artifacts](/docs/surfaces/desktop/user-guide/chat-turn-review)
surfaces.

## Safety is part of the experience

Ryu keeps these properties true when an agent works independently:

- Every action has a server-enforced owner and permission boundary.
- External writes, deployments, messages, credentials, destructive operations, and policy changes require the appropriate approval.
- Approval binds to the action arguments, actor, resource scope, and expiry. Replaying an old approval cannot authorize a different action.
- Tool results and fetched content remain untrusted when they return to the model.
- Context is bounded. Stable identity and policy stay separate from retrieved data, memory, and tool output.
- Mutable policy is read from its canonical source and verified after a write. Memory is evidence, not authority over live configuration.
- Budgets, timeouts, repeated failures, and missing verification stop a run clearly.
- A provider-native agent that bypasses the Gateway is labeled as a bypass. An unavailable remote or cloud adapter never silently falls back to local execution.
- Learning never silently rewrites persona, permissions, organization policy, or shared memory.

See [Core vs Gateway](/docs/start-here/architecture/core-vs-gateway) and
[agent hardening](/docs/gateway/agent-hardening) for the enforcement boundary.

## How the quality bar is verified

The standard is met when a real product flow can demonstrate that:

- one message creates a task with a plan, live progress, and a durable final receipt;
- closing and reopening the client resumes the same task without duplicate external effects;
- an approval can be approved, edited, rejected, or limited to its stated scope;
- poisoned external content cannot become a trusted instruction or bypass policy;
- long context stays usable through bounded loading and accurate compaction state;
- failures say what completed, what did not, and whether retry is safe;
- delegated work shows parent and child lineage without merging permissions or memory;
- local, worktree, remote, and cloud status is truthful at the point of use; and
- a successful run produces a reviewable reusable-change proposal.

The bar does not mean nothing can fail. It means the normal path is clear, the runtime handles
persistence and recovery, and a failure tells the user what happened and what to do next.
