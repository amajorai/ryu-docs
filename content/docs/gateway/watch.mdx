title: Ryu Watch
description: Enroll gateways for private exposure monitoring and review security findings.
---

Ryu Watch automatically enrolls Ryu-managed cloud nodes after live provisioning succeeds.
External self-hosted domains require their owners to enroll them. It checks transport and
management authentication without reading private response bodies or running commands on a
node. Availability depends on the service operator enabling the monitoring worker.

See the [Gateway reference](/docs/gateway) for the surrounding control-plane configuration.

## Cloud nodes are enrolled automatically

New and recovered cloud nodes appear as **Auto-enrolled cloud**. No DNS record or separate
signup is needed: Ryu uses its provisioned-server record to establish the target and owning
organization. Current organization owners and admins can view findings and pause or resume monitoring.
Reconciliation also covers existing active cloud nodes and missed enrollment after a restart;
it never re-enables a paused record. Simulated provisioning does not enroll a public target.

Before each managed scan, Ryu checks that the server is still active in the same organization
at the recorded address. An inactive, removed, or changed target is paused without probing it.
Monitoring still requires the service operator to enable the Watch worker. A cloud enrollment
does not enable exploitation or publish an account email.

## Enroll an external self-hosted gateway

Open **Ryu Watch** from the web dashboard. A verified account email is required.

1. Enter a private display name and your gateway's HTTP or HTTPS domain origin.
2. Confirm that you control the domain and authorize recurring exposure checks.
3. Publish the generated DNS TXT record.
4. Choose **Verify ownership**. Keep the DNS record in place while monitoring.

External enrollment supports domain origins on standard HTTP and HTTPS ports with public IPv4
addresses. IP literals, custom ports, private destinations, credentials in URLs, and URL paths
are not accepted. IPv6-only destinations are currently inconclusive. DNS ownership is checked
again before every scan; losing the proof pauses monitoring.

Checks are scheduled hourly. **Pause monitoring** stops future checks. Removing an external
asset through the account API also removes its stored monitoring record. Managed cloud records
use pause rather than deletion so reconciliation respects the owner's choice. A running request may finish after
pause, but it cannot replace the paused asset's findings.

## Interpret results

| Result | Meaning |
| --- | --- |
| Pass | The specific check passed at the displayed observation time. |
| Finding | Evidence needs review; it is not a claim that an attacker accessed your node. |
| Inconclusive | The check could not establish the result. Previous findings remain unresolved. |

An open port alone does not establish a vulnerability. An unauthenticated successful response
from a management path is a **potential exposure**: a proxy or fallback page may produce the
same response. The scanner does not read its body to establish access to private configuration.
A transport pass establishes TLS certificate validation for that origin, not the security of
every route or encryption at rest.

## Notifications and repair

External findings are private to the enrolled owner and authorized platform administrators.
Cloud findings are also visible to the owning organization's current owners and admins. Credential
reports for an organization are visible to its current owners. Ryu uses verified account
contacts rather than guessing emails from IP addresses. Email preferences remain in effect;
notification processing and successful email delivery are distinct states. **Ryu Watch alerts**
in notification settings controls email and inbox delivery separately.

**Prepare repair in Ryu** opens a prefilled chat. Select and confirm the matching node before
sending it. The link does not connect to a new node or execute a command. Review the proposed
change and its rollback before approving disruptive work. A later successful check is required
to establish that the relevant exposure is no longer observed.

Analysis reports can prepare a review prompt, and open credential reports can prepare a
credential-rotation prompt. Both use the same review-before-send chat behavior.

Managed hosting is available separately through Ryu Cloud. Reviewing findings and preparing a
manual repair does not require buying managed hosting.

## Public security contacts

A gateway can optionally publish an operator-selected public name and contact at
`/.well-known/security.txt`, using [RFC 9116](https://www.rfc-editor.org/rfc/rfc9116.html).
Publication is disabled by default and never copies your account email automatically.

Add an explicit section to `gateway.toml`, then restart the gateway:

```toml
[public_contact]
enabled = true
name = "Example research gateway"
contact = "mailto:security@example.com"
canonical = "https://node.example.com/.well-known/security.txt"
expires = "2027-03-01T00:00:00Z"
```

Use a dedicated security alias, or an HTTPS contact-form URL in `contact`. Anyone can read a
published address, including spammers. This is an operator-declared contact, not proof that Ryu
verified the mailbox or the person's legal identity. A public contact is **not authorization
for testing**. Monitoring enrollment and any later red-team authorization are separate.

Serve the record over HTTPS at its canonical URL. Expiration must be in the future and within
366 days; expired or invalid records return not found. Set `enabled = false` and restart to
withdraw it. Third parties may retain a copy after publication.

## Credential and analysis coverage

GitHub partner intake verifies GitHub's signature before processing a report. It matches a hash
of the reported token against Ryu-issued gateway credentials. Raw tokens, source URLs, and
source content are not stored in findings. Unmatched reports do not identify an owner and do
not trigger guessed-email outreach. Partner registration and live delivery require separate
setup with GitHub; an enabled endpoint alone does not prove partnership activation.

Platform administrators can review repository and node analysis reports separately. Repository
analysis checks leaked secrets, selected static-analysis rules, and JavaScript dependency
advisories. Node analysis uses local file metadata and Core's existing encryption-posture
report. It does not download or decrypt vaults. Reports show their source, subject, revision,
and observation time. Stale, failed, or missing checks must not be interpreted as secure.

Automated analysis is bounded coverage, not a certification that all vulnerabilities have been
found. Active exploitation and internet-wide red teaming are not enabled by these checks.
