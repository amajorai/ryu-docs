title: "Account Standing on Hosted Gateways"
description: "How Ryu's hosted Gateway refuses requests for suspended, throttled, or restricted accounts and keys, how it picks an enforcement step, and how provider safety refusals and policy availability are handled."
---

Every `rgw_` token resolution on the [managed data plane](/docs/gateway/managed-data-plane) also
carries the platform standing of the key and its owner. This page covers what the hosted Gateway
does with that standing.

## Account standing

Every resolution also carries the key's platform standing. When Ryu suspends an
organization, suspends a key, or bans the account that owns a key, the token
still resolves, and the Gateway refuses the request with a specific code instead
of a generic `401`, as follows.

| Standing | Status | `error.code` | Refused on |
|---|---|---|---|
| Organization suspended for Ryu-managed traffic | `403` | `org_suspended` | the hosted Gateway (every request there spends Ryu credentials) |
| Organization fully suspended | `403` | `org_suspended` | every Gateway |
| Key owner banned | `403` | `user_banned` | every Gateway |
| Key suspended | `403` | `key_suspended_abuse` | every Gateway |
| Standing could not be read | `503` | `standing_unavailable` | every Gateway, with `Retry-After` |

A refusal keeps `error.type: "policy_violation"` and adds `layer: "platform"`,
`remedy: "appeal"`, the public `appeal_url`, and the `reason_class` and `until`
fields when they apply:

```json
{ "error": {
    "type": "policy_violation",
    "code": "org_suspended",
    "layer": "platform",
    "remedy": "appeal",
    "message": "This organization is suspended.",
    "appeal_url": "https://<your Ryu site>/appeal",
    "reason_class": "fraud",
    "until": "2026-11-01T00:00:00.000Z" } }
```

`appeal_url` is the public appeal page. It cannot file an appeal for a key or organization step on
its own: file that appeal from the **Appeal this decision** link in the notice email, or contact Ryu
support when the email carried no link. See
[Appeal an automatic step](/docs/security/authentication-account-restrictions#appeal-an-automatic-step).

A suspension limited to Ryu-managed traffic does not affect a self-hosted
Gateway or a managed node using your own provider keys. A restricted
organization is still served, with the limits described in
[Throttled and restricted accounts](#throttled-and-restricted-accounts).

The Gateway fails closed on standing. A missing or unreadable standing, or one
it does not recognize, is refused with `503 standing_unavailable` rather than
served. On the hosted Gateway, a resolution whose credit balance could not be
read is refused with `503 credit_accounting_unavailable` before any provider is
called.

A standing change reaches the Gateway through the resolve cache. When the
Gateway is notified of a change, it drops the affected cached resolutions at once,
and work already running checks again: a tool loop (including the hosted
`web_search` loop of the Responses API) before each round and before each
follow-up completion, a request before each fallback attempt, and a stream
before each chunk it forwards. A request refused before a fallback attempt or a
later round gets the same `403` envelope, and the next provider is not called.

A stream refused mid-way ends after the text already delivered, with the same
error fields in its own dialect, and never with a normal finish:

| Endpoint | Last event |
|---|---|
| `/v1/chat/completions` | one `data:` frame carrying the error envelope |
| `/v1/messages` | an `error` event, `{ "type": "error", "error": { ... } }`, with no `message_delta` or `message_stop` after it |
| `:streamGenerateContent` | one `data:` frame carrying the error envelope, with no `finishReason` after it |
| `/v1/responses` | `response.failed`, whose `response.error` keeps the `code`, `message`, `appeal_url` and the other fields above |

Without a notification, a change applies when
the cached resolution expires: within 60 seconds for a key in good standing, or
10 seconds once its standing already refuses.

## Throttled and restricted accounts

Short of a suspension, Ryu can narrow what a key, the account that owns it, or
an organization may do on the hosted Gateway. These steps apply only on the
hosted Gateway, where requests spend Ryu's provider credentials. A self-hosted
Gateway and a managed node using your own provider keys are never throttled or
restricted by them.

| Step | What changes on the hosted Gateway |
|---|---|
| Throttled | A lower request rate and a cap on requests in flight for the throttled key, account or organization. A stream counts as in flight until it ends or the client disconnects |
| Restricted | Everything a throttle does, plus: content Ryu's platform policy would only flag is blocked, image, speech, transcription and video generation are refused (polling a video job submitted earlier still works), requests are not served from Ryu's own vendor supply, and only the chat models on Ryu's list for restricted accounts can be used. Embedding and rerank models are not limited by this list. A model id that lets the provider choose the model, such as `openrouter/auto`, is refused, and models outside the list are dropped from an OpenRouter `models` fallback list |

| Situation | Response |
|---|---|
| A throttled key, account or organization past its rate or in-flight cap | Refused with `429`, `type: "rate_limit_exceeded"`, `code: "abuse_throttled"`, `layer: "platform"`, `remedy: "appeal"`, the `appeal_url`, and a `Retry-After` header |
| A restricted key, account or organization asking for media generation, a model outside the list, or a model the provider chooses | Refused with `403`, `type: "policy_violation"`, `code: "account_restricted"`, `layer: "platform"`, `remedy: "appeal"` and the `appeal_url` |
| A gateway key less than a day old past its first-day rate of 30 requests a minute, or with 4 requests already in flight | Refused with `429`, `type: "rate_limit_exceeded"`, `code: "new_key_rate_limited"`, `remedy: "none"` and a `Retry-After` header. Every new key starts this way, so it is not an action on your account and there is nothing to appeal |
| A throttled or restricted key, account or organization while the screener runs in reduced mode | Refused with `503`, `type: "service_unavailable"`, `code: "screening_unavailable"` and a `Retry-After` header, instead of being served at the reduced-mode rate |

A step on an account applies to the requests that carry that user's verified
identity, as described in [Per-user attribution](/docs/gateway/managed-data-plane#per-user-attribution). Other
members of the organization who use the same key are not affected, and neither
is a request that names no verified user. A step on a key applies to every
request that key sends.

Both refusals carry `reason_class` and `until` when they apply, like the
suspension codes above. Rates and in-flight caps hold across the whole hosted
Gateway, not per server. A change in standing applies from the next request: a
request already running finishes under the step it started with, unless the
key is suspended or banned while it runs.

Throttling and restriction are automatic steps. Banning a user is always a
decision a person at Ryu makes.

## How Ryu picks a step

Requests on the hosted Gateway that break Ryu's usage policies add to a score
for the end user, the key, the account and the organization involved. The score
fades over days or weeks. When the score of a key or of the organization
crosses a threshold, Ryu takes the next step for it:

| Step | What happens |
|---|---|
| Warn | A notice to the organization's owners and admins. Nothing else changes |
| Throttle | The throttle described above, for at least a day |
| Restrict | The restriction described above, for at least 7 days |
| Suspend Ryu-managed traffic | For the organization: its Ryu-managed traffic is refused with `org_suspended` until a person at Ryu reviews it. A key is never suspended automatically: it stays restricted, and a person at Ryu decides whether to suspend it |

- Each step on a key or the organization sends its owners and admins an inbox
  notification and an email with the policy area, how many violations there
  were, up to 5 sample request ids and what changed.
- The email for a throttle, a restriction or a suspension carries an
  **Appeal this decision** link. It opens the appeal page without signing in,
  lasts 30 days, and lets your organization appeal that step once. The inbox
  copy of the notice does not carry the link. A warning changes nothing, so it
  has no link: to report a false positive there, contact Ryu support and quote
  the request ids. See [Appeal an automatic step](/docs/security/authentication-account-restrictions#appeal-an-automatic-step).
- When your requests carry [end-user ids](/docs/gateway/managed-data-plane#end-user-identity), Ryu counts
  violations against that end user first and tells you which one. Your key and
  your organization go no further than a warning for 72 hours after that
  notice, which gives you time to stop serving that user before the key is
  affected. An end user flagged after those 72 hours have passed starts a new
  72 hours. Steps on an end user are recorded and reviewed by Ryu; they do not
  change that end user's traffic on their own.
- An account's score goes to a person at Ryu for review. It does not change
  traffic on its own.
- An organization's first step is always a warning.
- A throttle or a restriction ends a day or 7 days after the score falls back
  below its threshold. A suspension ends only when a person at Ryu lifts it, and
  after that only new violations count. If the organization is already
  suspended for a set time when it reaches this step, that suspension keeps
  its scope but no longer ends on its own.
- An identifier block or account warning a model provider sends Ryu can also
  restrict the keys behind the requests it names, as described in
  [Provider safety refusals](#provider-safety-refusals).
- These steps apply only to requests that spend Ryu credits. A self-hosted
  Gateway, or a managed node using your own provider keys, is never throttled,
  restricted or suspended by them. No step bans anyone.

## Provider safety refusals

A model provider can refuse a request for a safety reason of its own: it
refuses the content, it has blocked the end user the request was sent for, or
it has warned the account the request spent. When a request on the hosted
Gateway, which spends Ryu's provider credentials, gets one of these refusals,
the Gateway returns it to you and does not try another provider, so a refused
request is never sent elsewhere until one accepts it.

This holds inside a Fusion or Pipeline provider pool too: when one panel or
stage refuses your request, the whole request ends with that refusal, and the
other panels' answers are neither judged nor returned.
It also holds for the Gateway's own model calls that send your text before
the request is served: the traffic inspector, a smart routing classifier or
escalation judge, and the semantic cache's embedding. When the provider
refuses one of them, the request ends with that refusal and is not sent to the
model it was meant for. An LLM-judge guardrail's own call is not covered yet:
when its provider refuses, the guardrail falls back to its built-in check and
the request continues.

The refusal never counts against the provider's health, so other requests keep
being served.

The Gateway recognizes a refusal only from the provider's documented error
code or error shape, never from the wording of its message. Today it
recognizes:

| Provider | Refusal |
|---|---|
| OpenAI | A `400` with `code: "invalid_prompt"` or `code: "content_policy_violation"` |
| OpenRouter | A `403` moderation refusal (an error whose `metadata` carries `reasons`), or a `400` whose `metadata.provider_code` is `invalid_prompt` |
| Anthropic, OpenAI and OpenRouter | A successful response the model's own safety system stopped (`stop_reason: "refusal"`, or `finish_reason: "content_filter"`) |

| Situation | Response |
|---|---|
| The provider refused the content | Refused with `403`, `type: "policy_violation"`, `code: "upstream_content_refused"`, `layer: "upstream"`, `provider` and `remedy: "report_false_positive"` |
| The provider blocked the end user the request was sent for | Refused with `403`, `type: "policy_violation"`, `code: "upstream_identifier_blocked"`, `layer: "upstream"`, `provider` and `remedy: "appeal"` |
| The provider refused the request for the account it spent | Refused with `403`, `type: "policy_violation"`, `code: "principal_blocked"`, `layer: "upstream"`, `provider` and `remedy: "appeal"` |
| A successful response the model's safety system stopped | Returned unchanged |

`provider` names the vendor, such as `openai`. The message is fixed for each
code: the provider's own wording is never passed on, because it can quote the
request. Each refusal, and each stopped response that was not streamed,
records one [violation event](/docs/gateway/audit#violation-events). A self-hosted Gateway,
a Gateway on a managed node, your own SDK connections and the passthrough
routes are not affected: there the same provider error is returned as an
ordinary `provider_error`, as before.

## Policy availability and provider regions

When a Gateway is configured with a control-plane URL and node credential, the
initial effective-policy fetch is required for startup. A failed refresh keeps
the last verified policy; it does not replace it with an empty, permissive
policy. A policy-lock failure is also treated as unavailable and denies
inference.

`allowed_regions` is checked against the final routed provider before any
provider call, including fallback routes. Region metadata is explicit: local
providers use `local`, geography-neutral hosted providers use `global`, and
regional Bedrock or Vertex routes derive their region from the configured
endpoint. A provider without verified region metadata is rejected whenever a
non-empty region allowlist is active. An empty list remains the documented
unrestricted setting.
