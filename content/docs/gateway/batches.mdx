---
title: "OpenRouter Batch Inference"
description: "Submit, inspect, and clean up asynchronous OpenRouter inference batches through the Gateway."
---

Use Gateway batches for work that can finish asynchronously: comparing prompts on one model,
scoring evaluation datasets, bulk classification or summarization, and refreshing embeddings.

- OpenRouter accepts chat completions, Responses, Anthropic Messages, and embeddings in separate
  batches.
- Every request in one batch shares an endpoint and model.
- Every row returns independently under its `custom_id`.

OpenRouter allows up to 24 hours to complete a batch. It reports that batch-capable provider
endpoints generally cost about half their normal per-token price, with the exact discount varying
by model.

Results may arrive much sooner, but timing is variable. Treat a batch as background work, not a
latency-sensitive call or an SLA. See OpenRouter's
[Batch API guide](https://openrouter.ai/docs/batch-quickstart) for current provider support and
routing details.

```mermaid
flowchart LR
  CLIENT["Core client"] --> CORE["Core /api/gateway/batches"]
  CORE --> GW["Gateway /v1/batches"]
  GW --> OR["OpenRouter account"]
  OR --> PROV["One eligible provider for the whole batch"]
```

## Access

<Callout type="warn">
  The hosted Ryu Gateway does not accept new batches. `POST /v1/batches` returns `403` with
  `code: "feature_not_permitted"`, because a batch sends every row upstream without the per-request
  screening, budget, and organization attribution that the hosted Gateway applies to other calls.

  Run batches on a self-hosted Gateway with your own OpenRouter account. See
  [Hosted Gateway restrictions](/docs/gateway/managed-data-plane#hosted-gateway-restrictions).
</Callout>

- Batch operations require a Gateway master key.
- Core's `/api/gateway/batches` proxy keeps that Gateway credential on the server when a Core
  client is used.
- All Core batch operations, including listing and reading results, require node-owner access.

## Billing, routing, and retention

Batch inference uses the configured OpenRouter account directly. It does not run each row through
the Gateway's normal per-request routing, budget, firewall, or wallet settlement path.

- OpenRouter applies the workspace's provider allowlist, data policy, and BYOK settings, then
  selects one eligible provider for the whole batch. You can pin it with `provider.only`.
- OpenRouter returns token and cost usage on completion and includes batches in workspace logs.
- OpenRouter retains batch inputs and results for up to 30 days. Review account and provider
  retention policies before you submit private data.
- Deleting a terminal batch purges OpenRouter-held artifacts, but upstream provider deletion may be
  unsupported. Inspect the deletion response's `deletion.upstream` status.

### Settings that block a batch

The Gateway refuses new batches when its OpenRouter configuration uses a setting the Batch API
cannot carry. Disable these before you submit a batch:

| Gateway setting | Why it blocks |
|---|---|
| Per-request `data_collection: "deny"` | The Batch API request shape documents no control for it |
| Zero-data-retention routing | The Batch API request shape documents no control for it |
| Response-healing plugin | `provider.only` is the Batch API's only request-level routing preference |
| Provider sort preference | `provider.only` is the Batch API's only request-level routing preference |

These Gateway checks are separate from OpenRouter's workspace-level data policy, which OpenRouter
applies during provider selection.

### Provider configuration changes

- New submissions use the currently published provider configuration, including changes made after
  the Gateway starts.
- A submission keeps the provider generation it began with while its request is in flight.
- Disabling or removing that account prevents later submissions. An unrelated provider
  configuration update preserves the unchanged account's batch capability.

## Submit an eval dataset

The published `@ryuhq/core-client/gateway` module includes `buildGatewayEvalBatchPlan`, which turns text eval cases into chat requests with stable row IDs. Expected answers, assertions, and other grading metadata remain in the returned local mapping and are not sent as prompts.

```ts
import type { ApiTarget } from "@ryuhq/core-client/client";
import {
  buildGatewayEvalBatchPlan,
  createGatewayBatch,
  getGatewayBatch,
  scoreGatewayEvalBatch,
} from "@ryuhq/core-client/gateway";

declare const target: ApiTarget; // Authenticated Core target supplied by your host app.

const plan = buildGatewayEvalBatchPlan("openai/gpt-4o-mini", [
  {
    id: "refund-policy",
    prompt: "Summarize the refund policy in one sentence.",
    expected: "30 days",
  },
]);

const submitted = await createGatewayBatch(target, plan.request);
let current = await getGatewayBatch(target, submitted.id);
while (!["completed", "failed", "expired", "cancelled"].includes(current.status)) {
  await new Promise((resolve) => setTimeout(resolve, 15_000));
  current = await getGatewayBatch(target, submitted.id);
}

if (current.status === "completed") {
  const scored = await scoreGatewayEvalBatch(target, plan, current);
  console.log(scored.result?.aggregate);
  console.log(scored.failures); // Per-row OpenRouter failures stay independent.
}
```

### How scoring works

The helper scores completed rows with the Gateway's existing eval runner, including assertions,
run-level evaluators, and judge calls.

- **Latency** is the whole batch turnaround, because OpenRouter does not provide per-row latency.
  Do not compare it directly with synchronous inference latency.
- **Cost** per row is copied from the response when OpenRouter reports it.
- **Policy** stays unset. Batch generations did not traverse the Gateway's firewall and policy
  path, so `provider_output_policy_pass` is unset and scored rows report `policy_available: false`.
  The aggregate excludes that dimension instead of counting it as a pass or a failure.

### What a plan supports

Submit one plan per model.

| Supported | Rejected |
|---|---|
| Text prompts and ordered text messages | Nunjucks filters and control blocks |
| Run-level system prompts and messages | Cases that override the provider or model |
| Simple `{{path.to.value}}` lookup | Precomputed outputs |
| JSON variable transforms | Per-case response caching |
| Prompt prefixes and suffixes | |

Pre-render advanced templates before you build the batch plan.

## Bulk embeddings

Submit `/v1/embeddings` with one `{ custom_id, body: { input } }` item per document or document
group. The completed row's `response.body` has the normal embeddings response shape. Keep each
`custom_id` stable enough to join the vectors back to your source records.

## Batch lifecycle

| Operation | Gateway route | Behavior |
|---|---|---|
| Submit | `POST /v1/batches` | Returns `202` with the OpenRouter batch ID and initial status |
| List | `GET /v1/batches?limit=20&status=in_progress` | Cursor pagination uses `after`; `status` may be repeated |
| Poll | `GET /v1/batches/{id}` | Returns status and request counts; completed results arrive inline |
| Delete | `DELETE /v1/batches/{id}` | Deletes only terminal jobs; an in-flight job returns a conflict |

The Core proxy exposes the same resource under `/api/gateway/batches`. The client methods
`createGatewayBatch`, `listGatewayBatches`, `getGatewayBatch`, and `deleteGatewayBatch` use that
proxy.

There is no in-flight cancellation operation. Delete a batch after it reaches `completed`,
`failed`, `expired`, or `cancelled` to purge OpenRouter-held request and result artifacts sooner
than the retention deadline. Check the returned upstream deletion status separately.

### Retrying after an error

A resubmission creates a separate billed batch, so check before you retry a Submit.

| Operation and error | Meaning | What to do |
|---|---|---|
| Submit returns `504` | It timed out or lost its connection after sending, so OpenRouter may already have created the batch | List recent batches (for example with `created_after`) before you resubmit |
| Submit returns `502` on a direct Gateway call | The connection failed before the request reached OpenRouter | Safe to retry |
| Any failed Submit through the Core proxy | Unknown | List batches before you resubmit |
| Poll or List returns `504` | Timed out | Safe to repeat |
| Delete returns `504` | It may already have taken effect | Poll the batch before you retry |

### Limits

- The Gateway accepts up to 10,000 rows and an 8 MiB submission body.
- List pages are bounded to 100 rows.
- Completed results are capped at 64 MiB per response.
- OpenRouter may reject a model without a batch-capable endpoint, unsupported request fields, or
  provider pins that have no eligible batch endpoint.
- Audio, video, and OpenRouter-managed web search are not supported in batch jobs. Use the
  synchronous inference API for those requests.
- Image and file inputs, where the selected provider supports them, must use public URLs.
  Base64 and data-URI images are rejected. Other multimodal support depends on the selected
  provider.
