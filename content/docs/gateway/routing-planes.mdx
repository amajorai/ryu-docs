---
title: Routing Planes
description: Explains model routing (Plane A, in the Gateway) versus agent routing (Plane B, in Core), and which plane governs an agent's chat and tool egress.
---

Ryu uses "routing" for two separate mechanisms. **Plane A (model routing)** lives in the Gateway
and picks *which LLM* an OpenAI-compatible completion uses. **Plane B (agent routing)** lives in
Core and picks *which agent* serves a chat turn, where the agent brings its own model and (for ACP subprocess
agents) makes its own provider calls. The two planes run at different layers, and only one of them
governs chat egress.

<Callout type="info">
  Core decides what runs. The Gateway decides what is allowed. Plane B (Core) chooses the agent;
  Plane A (Gateway) governs the LLM call - see
  [Core vs Gateway](/docs/start-here/architecture/core-vs-gateway).
</Callout>

## The two planes

```mermaid
flowchart TB
  subgraph PlaneA["Plane A · Model routing (Gateway)"]
    direction TB
    REQ["/v1/chat/completions\nbody.model = 'claude-sonnet-4-5'"]
    SR{"Smart routing\n(optional)\npick model?"}
    MR["ModelRouter::route\nmodel → provider"]
    GOV["Governance\nfirewall → budget → audit"]

    REQ --> SR
    SR -->|"rewrite body.model"| MR
    SR -->|"no rules / skip"| MR
    MR --> GOV
  end

  subgraph PlaneB["Plane B · Agent routing (Core)"]
    direction TB
    TURN["Chat turn"]
    RESOLVE["agent_route()\npick backend"]
    OAI["OpenAiCompat\nvia_gateway: true"]
    ACP_R["Acp\nown subprocess"]

    TURN --> RESOLVE
    RESOLVE -->|"catalog / registry"| OAI
    RESOLVE -->|"ACP agent"| ACP_R
  end

  OAI -->|"feeds Plane A"| PlaneA
  ACP_R -->|"chat: self-routes\n(bypass)"| Engine["Upstream Provider"]
  ACP_R -->|"tool: governed\n(MCP bridge)"| GOV
  GOV --> Engine
```

| Plane | Owns | Surface | Model lifetime | Governed how |
|---|---|---|---|---|
| Plane A - Model routing | Gateway | Picks the LLM for one OpenAI-compatible `/v1/chat/completions` request | Model is fixed for the whole turn (and its tool loop) once routed | Full Gateway plane: allowlist + inbound firewall + budget + audit |
| Plane B - Agent routing | Core (ACP / catalog) | Picks the agent that serves the turn; the agent brings its own model | Model is owned by the agent/subprocess, not by a single Gateway route | Routable ACP chat egress is Gateway-governed by default; non-wirable agents bypass it. Tool egress is governed through the MCP bridge |

Plane A rewrites `body["model"]` inside one completion request. Plane B
chooses a backend (`AgentRoute`) and, for ACP agents, hands the whole turn to a subprocess that Ryu
cannot intercept at the chat-LLM level.

## Plane A: model routing

Plane A runs inside the Gateway pipeline on the OpenAI-compatible chat path. It is a two-stage
decision.

**Stage 1 - optional smart routing (classifier).** On the chat path, `apply_smart_routing` runs
before `pre_process` (`apps/gateway/src/pipeline/mod.rs`). It only does anything when
`SmartRouter::is_active()` is true (`apps/gateway/src/router/smart.rs`) and no per-agent chat-model
setting is pinned. `SmartRouter::resolve` caches the decision per session (keyed by
`x-ryu-session-id`) and dispatches on the configured strategy (a cheap classifier model, an embedding nearest-match, or a
keyword match). The classifier strategy resolves its model through the normal `ModelRouter::route` and
then issues a plain `provider.complete` call.

**Model routing is not tool calling.** The classifier is a direct
`provider.complete`, not a tool call, so it bypasses the pipeline and cannot recurse into routing.
The result is a single rule index that rewrites `body["model"]` in place. Every failure (inactive
config, timeout, provider error, or an unparseable reply) keeps the requested model. The full
strategy vocabulary (llm / embedding / keyword) and per-agent overrides are documented in
[Smart model routing](/docs/gateway/smart-routing).

<Callout type="warn">
  Smart routing is off by default. `SmartRoutingConfig::enabled` is false, and `is_active` also needs
  at least one rule (and, for the `llm` strategy, a classifier model). Without those, Plane A stage 1
  is inert and the requested model is kept.
</Callout>

**Stage 2 - deterministic model-to-provider routing.** Once the model string is fixed,
`ModelRouter::route` (`apps/gateway/src/router/mod.rs`) maps it to a provider with no hardcoded lock:
exact `model_map` hit, then longest-prefix user map, then the built-in prefix table
(`crates/gateway/router/src/lib.rs`), then the configured `default_provider`. The built-in table is
listed on [Routing](/docs/gateway/routing#provider-selection).

The model is fixed for the whole turn. Tool calls in the loop re-enter the completion API with the
already-routed model and never re-trigger stage 1 or stage 2. The only thing that changes the
model *after* routing is budget: the lifetime token-budget block and `enforce_budget`'s Downgrade
action both rewrite `body["model"]` to a cheaper model and re-route.

## Plane B: agent routing

Plane B is the "bring-your-own-model agent" path and lives in Core. A chat turn resolves its backend
in `agent_route` (`apps/core/src/sidecar/adapters/mod.rs`), which then matches the resolved
`AgentRoute`. That match is the two-backend split:

- **Catalog / OpenAI-compatible registry agents** become `AgentRoute::OpenAiCompat { via_gateway: true }`
  and stream through the Gateway. These agents feed Plane A, so their chat is governed.
- **ACP subprocess agents** become `AgentRoute::Acp { spawn_cmd }` and stream via `route_acp_stream`.
  An ACP agent runs its own subprocess and makes its own provider calls, so Core cannot intercept its
  chat-LLM egress in general.

**Base-URL injection.** For an ACP agent whose HTTP client honors the OpenAI base URL, there is one
interception point. `acp::openai_gateway_cmd` (`apps/core/src/sidecar/adapters/acp.rs`)
prefixes the spawn command with `OPENAI_BASE_URL` (the local Gateway `/v1`) and `OPENAI_API_KEY` (the
Gateway token), so the agent's chat calls flow through the Gateway. It is gated by the per-agent
toggle `agent-gateway-routing` (`apps/core/src/agent_routing/mod.rs`), which defaults on for new and
auto-installed routable ACP agents. A missing entry remains Gateway-governed; an explicit `false` is
the direct-egress opt-out. The full mechanism (base-URL injection, the subscription-preserving
passthrough proxy for Claude Code and Codex, and the bypass list) is documented in
[Gateway for any agent](/docs/gateway/gateway-for-any-agent).

**Agents that bypass the Gateway.** For registry ACP agents, chat egress is governable only when
the CLI honors a base URL Core injects and the Gateway speaks that wire format. Only the Codex and
Pi registry agents meet both (`registry_gateway_bypass` in
`apps/core/src/sidecar/agents/acp_registry.rs`). Every other registry agent bypasses the Gateway
for chat. Examples are Gemini CLI (Google wire format), OpenClaw (its own WebSocket gateway),
Hermes (its own credentials), and self-fetching agents such as Cline, Goose, and OpenCode. Claude
Code and Codex also have dedicated
[passthrough routing](/docs/gateway/gateway-for-any-agent#subscription-preserving-passthrough-claude-code-codex)
that preserves their subscription billing.

**Tool egress is always governed, regardless of chat.** The MCP bridge `build_ryu_mcp_server`
(`apps/core/src/sidecar/adapters/mcp_bridge.rs`) is wired into the live ACP session, and every tool
call dispatches through the bridge into `McpRegistry` allowlist enforcement, with no direct-egress
bypass. The same governance is exposed over HTTP at `POST /api/mcp/tools/call`, which requires a known
agent id so the allowlist cannot fail open.

The same defaults apply when an ACP runtime is installed from the catalog or discovered during
onboarding: its new agent configuration starts with the live MCP, plugin/app tool scope and enabled
skills, and routable model traffic starts through the Gateway. Customize the configuration or turn
off its routing switch when that agent needs a narrower tool scope or direct provider egress. Existing
explicit choices are preserved.

<Callout type="info">
  Plane B backend resolution (the `OpenAiCompat` / `Acp` split above) is separate from the
  **agent-auto picker**, a per-turn choice of which agent serves the turn by your own rules
  (`apps/core/src/agent_routing/auto.rs`). See
  [Agent auto routing](/docs/gateway/agent-auto).
</Callout>

## The ownership rule

A turn has one chat-egress plane:

- **OpenAI-compatible requests get Plane A model routing.** The Gateway picks and fixes the LLM, and the
  full policy plane (allowlist, firewall, budget, audit) applies to that chat.
- **ACP agents self-route (Plane B).** The agent owns its model. Only its *tool egress* is governed
  (via the MCP bridge); its chat egress reaches the Gateway *only* if it honors `OPENAI_BASE_URL`
  and the per-agent toggle is on.

```mermaid
flowchart LR
  subgraph Turn["One chat turn"]
    direction TB
    A["OpenAI-compat agent"]
    B["ACP agent"]
  end

  subgraph PlaneA["Plane A (Gateway governs chat)"]
    direction TB
    GA["firewall + budget + audit"]
    LA["ModelRouter picks LLM"]
    GA --> LA
  end

  subgraph PlaneB["Plane B (agent self-routes)"]
    direction TB
    CHAT["chat egress\nbypass (unless\nOPENAI_BASE_URL)"]
    TOOL["tool egress\nalways governed\n(MCP bridge)"]
  end

  A --> PlaneA
  B --> CHAT
  B --> TOOL
  TOOL --> Gateway["Gateway\n(governance layer)"]
```

Both planes feed **one** governance layer, the Gateway. It decides what is allowed, shared,
measured, and paid for. In the pipeline, `pre_process` runs rate-limit then inbound
firewall then routing on every request, `enforce_budget` applies budget decisions, and every model
call is audited. The unified tool surface is deny-by-default and activates only on an explicit
per-request signal. Tool-call guarding runs in the Gateway firewall and the command-scan
`POST /v1/exec/scan` path.

## Where things live

| Concern | File |
|---|---|
| Smart routing classifier (Plane A stage 1) | `apps/gateway/src/router/smart.rs` |
| Model-to-provider resolution (Plane A stage 2) | `apps/gateway/src/router/mod.rs` |
| Smart routing config (opt-in, fail-open) | `apps/gateway/src/config.rs` |
| Chat pipeline: smart routing, route decision, budget, audit | `apps/gateway/src/pipeline/` (`mod.rs`, `routing_smart.rs`, `budget.rs`, `budget_charge.rs`, `audit.rs`) |
| Unified tool surface (deny-by-default, `tool_search`) | `apps/gateway/src/tools/mod.rs` |
| Backend resolution + dispatch (Plane B) | `apps/core/src/sidecar/adapters/mod.rs` |
| ACP spawn, session pool, `OPENAI_BASE_URL` injection | `apps/core/src/sidecar/adapters/acp.rs` |
| Registry agents' default Gateway bypass | `apps/core/src/sidecar/agents/acp_registry.rs` |
| Governed tool egress (MCP bridge) | `apps/core/src/sidecar/adapters/mcp_bridge.rs` |
| Per-agent Gateway-routing toggle | `apps/core/src/agent_routing/mod.rs` |

## Gotchas

- **Everything in Plane A fails open.** Inactive config, classifier timeout, provider error, or an
  unparseable reply all keep the originally requested model. A routing misconfig can never break chat.
  A provider safety refusal of the classifier call on the hosted Gateway is not a failure mode: it
  ends the request ([Provider safety refusals](/docs/gateway/account-standing#provider-safety-refusals)).
- **Explicit model pins beat the classifier.** A per-agent chat-model setting wins over smart
  routing in both `apply_smart_routing` and the `pre_process` route decision.
- **Budget can override the routed model after routing.** The lifetime token-budget block and
  `enforce_budget`'s Downgrade action both rewrite `body["model"]` and re-route *after* the normal
  route decision, so the final model may differ from the classifier's pick.
- **ACP chat egress bypasses the Gateway for agents that ignore the OpenAI base URL.** Agents such
  as Gemini CLI, OpenClaw, and Hermes ignore `OPENAI_BASE_URL`, so their chat LLM calls are never
  governed even with the per-agent toggle on. Their *tool* egress is still governed through the MCP bridge.
