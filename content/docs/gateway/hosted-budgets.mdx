On the [managed data plane](/docs/gateway/managed-data-plane), each resolved `rgw_` token carries
its organization's credit budget and limits. These checks run on every request before and after
dispatch.

<Figure name="budgets" />

## Organization budgets and rate limits

Organization admins set budgets and rate limits in the control plane. They arrive with each
resolution and apply to every request on the organization's `rgw_` tokens:

| Cap | Applies to |
|---|---|
| Organization | All traffic in the organization |
| Member | One verified user. Users without their own entry get the member default |
| Team | Every verified member of the team |
| Key | Traffic on one `rgw_` credential |

### What a cap can set

| Setting | Values |
|---|---|
| Charged-spend budget | An amount over a UTC `daily`, `weekly`, `monthly`, or `lifetime` window |
| Exhaustion action | `stop`, `downgrade` to a named cheaper model, or `notify` |
| Alert thresholds | Early-warning percentages of the budget |
| `rpm`, `tpm` | Requests-per-minute and tokens-per-minute ceilings, at least `1` |

Leave a field empty (`null`) for no limit. A budget of `0` is a real cap that blocks all charged
spend.

### How caps are enforced

- Every applicable cap is checked, and the most severe outcome wins. A request is blocked if any
  applicable `stop` cap is exhausted.
- A `stop` returns `402 budget_exceeded`.
- Exhausted caps and crossed thresholds are reported on the `x-ryu-policy-alert` response header.
- Rate ceilings return `429` and keep a separate bucket per member, team, key, and organization.

The node's own `[budgets]` rules still apply alongside the organization's caps. Spend counters
persist next to the audit database, and the Gateway reports daily spend per user, key, and team
back to the control plane.

### Plan rate ceilings

On the hosted Gateway, each plan also sets a ceiling on the organization-wide `rpm` and `tpm`,
because many organizations share the same Gateway capacity.

- Organizations without a managed plan (the free baseline, a desktop license, or promotional and
  prepaid credit only) get the lowest ceiling.
- Per-seat organization plans scale with their seat count.
- An organization cap you set can lower these ceilings but cannot raise them.

The ceiling travels separately from your limits, and only a Gateway that bills tenants (one
configured with the credits debit secret) applies it. A Gateway without the debit secret enforces
only the caps you set. The limits page and `GET /api/control-plane/orgs/{orgId}/limits` show the
ceiling as `planRateCeiling`.

A single request larger than a Gateway's whole per-minute token share is not refused outright. It
is admitted once that share is unused, and its excess counts against the following minutes, so
requests after it wait until the share recovers.

## The pre-flight credit gate

Credit enforcement is **pre-flight**, in `preflight_credit_gate`
(`apps/gateway/src/pipeline/budget_charge.rs`, run inside `enforce_budget`). It fires before
dispatch, so an empty wallet blocks the request rather than one that already ran.

```mermaid
flowchart TD
  A[Request with rgw_ token] --> B{Resolves?}
  B -- no --> H[401 - never anonymous]
  B -- yes but balance unknown --> R[503 credit_accounting_unavailable]
  B -- yes --> C{managed_inference?}
  C -- no --> F{Gateway bills tenants?}
  F -- no --> P[Proceed - BYOK/self-hosted not gated]
  F -- yes --> E
  C -- yes --> D{remaining_budget <= 0?}
  D -- yes --> E[402 insufficient_credits]
  D -- no --> P
```

### Gateways that bill tenants

A Gateway that bills tenants (one configured with the credits debit secret) serves every `rgw_`
organization from its own provider keys. On that Gateway, an organization the control plane reports
as not managed is treated as having nothing left and receives `402 insufficient_credits`.

That covers an organization with no plan allowance and no remaining balance, for example after
promotional credit runs out or a subscription lapses.

Such an organization is never served as bring-your-own-key traffic. A Gateway without the debit
secret keeps the control plane's reading unchanged.

### When the balance cannot be read

A failed read is not an empty wallet. When the control plane cannot read an organization's plan or
credit balance (for example during a billing-provider outage):

1. It answers with the plan and balance it last read for that organization, if that read is only a
   few minutes old. The Gateway's own debit responses keep gating spend.
2. Without a recent read, it reports the balance as unknown. A Gateway that bills tenants then
   returns the retryable `503 credit_accounting_unavailable` instead of `402 insufficient_credits`.
3. The Gateway asks the control plane again after about 10 seconds rather than waiting out the
   60-second cache.

The gate reads the resolved balance, which is at most 60 seconds old because of the cache. It
recovers on its own after a top-up and keeps no sticky wallet-empty flag.

### Output ceilings

For Chat Completions, clients may name the output ceiling with `max_tokens` or
`max_completion_tokens`. When both are present, the managed-credit reservation uses the larger
value, so either provider interpretation has enough reserved credit. Send only one field to avoid
provider-specific alias behavior.

### Error codes

`insufficient_credits` is a distinct error from `budget_exceeded`. Both return HTTP `402`, but they
mean different things.

| Error code | HTTP | Meaning |
|---|---|---|
| `insufficient_credits` | 402 | A managed org's credit wallet is exhausted (the pre-flight gate) |
| `budget_exceeded` | 402 | A per-user / per-agent / per-session charged-cost cap ([Reliability](/docs/gateway/reliability)) or an organization budget `stop` cap was hit |
| `credit_accounting_unavailable` | 503 | The managed org's balance is unknown (unreadable at resolution, or a debit could not be recorded). Retry later |
| `budget_store_unavailable` | 503 | A budgeted request (a local user or agent budget rule, or control-plane org limits) was refused because the budget store (`spend.db`) is sealed under a different key or the Gateway has no sealing key. Restore the right key; see [Reliability](/docs/gateway/reliability) |

The post-call credit debit, which subtracts the served call's cost from the org wallet, is
documented under `[credits]` in [Configuration and auth](/docs/gateway/configuration).

<Callout type="warn">
Credit debit failures are fail-closed by default. A transport error, non-success response, or
malformed success response marks accounting unavailable, and the next managed request returns the
retryable `credit_accounting_unavailable` (503) error.

This is kept separate from `wallet_empty_action`, so a funded organization is not permanently classified as empty. Do not
disable `GATEWAY_CREDITS_FAIL_CLOSED` on a managed fleet; the Gateway refuses that combination at
fleet startup.
</Callout>

## Per-tool-call debits

The model-call debit bills the model call. On the managed plan a request can also run **Composio**
tool actions, and Composio charges per action execution, so those are billed separately.

1. Each tool loop returns `(value, billable_count)`. `run_tool_loop` (`apps/gateway/src/tools/mod.rs`)
   counts the executed `composio.*` calls (prefix `COMPOSIO_TOOL_PREFIX`) that pass the allowlist
   gate. Denied, builtin, MCP, and app tool calls are free and never counted.
2. At request end, `spawn_tool_call_debit` (`apps/gateway/src/pipeline/tool_debit.rs`) fires one
   debit for the whole request (`count × cost_per_tool_call_micro_usd`, at cost) against the org
   wallet.

| Field | Value | Why it matters |
|---|---|---|
| `reason` | `composio` | Distinguishes the tool-call ledger row from the `gateway_usage` model-call row |
| `refId` | `{request_id}:composio` | A **distinct** ref from the model-call debit's `{request_id}`. Ledger writes are idempotent on `refId`, so a shared ref would merge the tool debit into the model-call debit |
| Cost source | `[credits] cost_per_tool_call_micro_usd` | Per-executed-call rate; the default is `500` micro-USD ($0.50 per 1,000 Composio actions, the managed-app rate) |

The debit is spawned off the response path, so it never adds client latency. It is a no-op when
credits are inactive, the org is absent, the billable count is zero, or the per-call cost is zero.
Managed nodes provision the rate through the `GATEWAY_CREDITS_COST_PER_TOOL_CALL_MICRO_USD` env var
(`from_env` in `apps/gateway/src/config.rs`).

<Callout type="info">
  The service-to-service tool path (`POST /v1/exec/tool`, trusted-forwarder / master-key only) has no
  per-user org context, so it is not metered here. It is bounded by the exec budget instead, covered
  on the [tools](/docs/gateway/tools) page.
</Callout>

## Sandbox metering

An org-bound remote sandbox is metered through the same Gateway-to-control-plane debit boundary.
The tick, quote and completion routes are on
[Loopback and internal routes](/docs/gateway/loopback-routes#sandbox-metering-post-sandboxtick).

- If a debit cannot be confirmed, the Gateway returns `kill_accounting` and Core destroys the
  sandbox instead of continuing provider or compute spend without an accounting record.
- A malformed or unknown tick response is also treated as an accounting failure.
- The final short-run tail is retried before a completed billable execution is reported. If it
  still cannot be confirmed, the execution reports an error after the remote workspace is
  destroyed.
- Unattributed local sandboxes remain outside the billing path.
