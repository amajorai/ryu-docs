Measurement is a Gateway concern. The Gateway scores a sampled fraction of responses to feed
eval-driven [routing](/docs/gateway/routing), and records every model call (plus sandbox, identity,
and control-change events) in a local audit log you can query. Both run on the request path; neither
blocks it.

## Evals

The eval runner (`EvalsRunner`) does three jobs: it passively scores sampled live responses and folds
those scores into a rolling per-provider average, replays a dataset on demand for explicit eval runs,
and scores already-completed outputs through the online scoring endpoint. Passive scoring is **on by
default** (`EvalsConfig.enabled`
defaults to `true` and `sample_rate` defaults to `1.0`).

### Dimensions

Each scored response combines three normalized dimensions into one weighted `overall` value.

| Dimension | Range | How it is computed |
|---|---|---|
| `latency_score` | 0 to 1 | `1 - (latency_ms / max_latency_ms)`, clamped. 1.0 is instant, 0.0 is at or beyond `max_latency_ms` |
| `token_efficiency` | 0 to 1 | `output_tokens / input_tokens`, normalized so 2x output caps at 1.0 |
| `policy_pass` | bool | Whether the request cleared all firewall and policy checks |

The weighted score is `0.4 * latency + 0.3 * token_efficiency + 0.3 * policy`. A sampled response
carries its `overall` value back in the `x-eval-score` response header.

### Sampling

Sampling is deterministic, with no RNG. `EvalsRunner::should_sample` increments a counter and keeps a
request every `1/sample_rate` boundary, so a `sample_rate` of `0.25` scores exactly one request in
four. A rate of `1.0` scores every request (the default), `0.0` scores none. This keeps scoring overhead
predictable and even rather than bursty.

### Rolling scores

Each sampled score is folded into a per-provider exponential moving average (`EMA_ALPHA = 0.2`),
stored lock-free so the routing path reads it without a mutex. `eval_routing` consumes these averages
to bias provider choice toward the current leader while reserving an `explore_ratio` of traffic for
non-leaders, so scores stay fresh. See [Routing](/docs/gateway/routing) for the full A/B selection
logic.

```
GET /v1/evals
```

returns the live config plus the current rolling score per provider:

```json
{
  "enabled": true,
  "sample_rate": 1.0,
  "max_latency_ms": 10000,
  "providers": { "openai": 0.84, "anthropic": 0.79 }
}
```

When evals are disabled the endpoint still returns `200` with `enabled: false` and an empty
`providers` map. It never panics and never returns a non-200 for a healthy gateway.

### Configuration

`EvalsConfig` lives under `[evals]` in `gateway.toml`. All fields have defaults so no configuration
is required out of the box.

| Field | Default | Description |
|---|---|---|
| `enabled` | `true` | Master switch. Set to `false` to disable all passive scoring |
| `sample_rate` | `1.0` | Fraction of completed requests to score, in `[0.0, 1.0]` |
| `max_latency_ms` | `10000` | Latency (ms) at which `latency_score` drops to 0 |
| `stream_usage` | `true` | Inject `stream_options.include_usage=true` into streamed requests so the provider emits a terminal usage frame. Only OpenAI-compatible providers honour this flag; non-conforming providers fall back to `estimate_prompt_tokens` |

### Dataset runs

```
POST /v1/evals/run
```

replays each prompt in `dataset` through the full pipeline (firewall, routing, provider call) and
returns per-case scores plus an aggregate. An explicit run always scores, independent of whether
passive evals are enabled. The expanded dataset is capped at 1,000 cases and the request's
conservative provider/judge-call upper bound is capped at 2,000 calls. Cases can run concurrently
within those limits; the request body is capped at 8 MiB, each case at 256 KiB, and recursive
assertion sets at eight levels/128 nodes. The response preserves input order so a result matrix
remains deterministic.

| Field | Purpose |
|---|---|
| `model` | Model under test, forwarded to the router as-is. Defaults to `gpt-4o-mini` |
| `models` | Run the whole dataset against each model and return a per-model breakdown |
| `dataset` | Array of `EvalCase` (`prompt`, optional `expected`, `vars`, `assertions`). Empty uses a built-in 3-case dataset |
| `system_prompt` | Run-level system prompt prepended to every case, with `{{vars}}` substituted per case |
| `judge_model` | One fixed model that judges every `llm_judge` assertion (fair cross-model compare) |
| `evaluators` | Optional run-level registry evaluator ids (from `GET /v1/evaluators`) scored against every case, unioned with any per-case `evaluators` |
| `agent_id` | Optional id forwarded for per-agent budget tracking |
| `max_concurrency` | Maximum provider calls in flight, clamped to 1–32; cache-enabled runs serialize duplicate-input lookup so a miss cannot charge the same input twice |
| `timeout_ms` | Per-case provider deadline, bounded to 100–120000 ms |
| `repeat` | Repeat every case up to 20 times, with stable repetition ids, subject to the 1,000-case and 2,000-call limits |
| `cache` | Reuse identical provider inputs within the run |
| `tags` | String key/value labels retained in the run envelope |
| `prefix`, `suffix` | Run-level text around each single-turn prompt |

Each case also supports stable `id`/`description`, typed `vars`, `metadata`, a per-case
`provider`/`providers` selection, a precomputed `provider_output`, and `options` for prefix, suffix,
output/variable transforms, timeout, and caching, plus an optional `context`/reference payload for
factuality and faithfulness checks. Assertions evaluated against the response include

the deterministic Promptfoo-compatible set (`contains`, `not_contains`, `equals`, `regex`,
`icontains`, `starts_with`, contains-any/all, JSON/HTML/XML/SQL containment, validity/refusal,
Levenshtein, latency, cost, moderation, negation via `not: true`, and nested assertion sets) plus model-assisted
`llm-rubric`, `similar`, `factuality`, `context-faithfulness`, and `answer-relevance`. Custom JS/Python
assertions run through Core's sandbox seam and report unavailable runtimes as `executed: false`; the
same flag is returned for model/media checks whose prerequisites are unavailable.

Deterministic
assertion sets may be nested, but model-graded assertions (`llm_judge`, `similar`, factuality,
faithfulness, and answer relevance) must be top-level case assertions; the API rejects them inside
an `assert_set` rather than reporting a misleading unexecuted failure. Assertion scores remain
separate from latency, token, policy, and cost measurements.

Unlike `GET /v1/audit`, this
endpoint authenticates with any valid API key, not the master key, because a dataset run is a normal
metered call.

From Core, `POST /api/gateway/evals/run` proxies the dataset run (including optional
`evaluators` and Core-local `code_evaluators`). `GET /api/gateway/evaluators` proxies the
evaluator catalog.

### Online scoring

```
POST /v1/evals/score
```

scores an already-completed output without replaying its provider request. Send `response` plus
optional `prompt`, `model`, typed `vars`, `metadata`, `expected`, assertions, and evaluator ids. Pass
`latency_ms` and `cost_micro_usd` when the measurements came from an external trace; latency and cost
assertions use those submitted measurements. The request body is capped at 512 KiB and the submitted
response is bounded to 256 KiB; expensive
Levenshtein comparisons skip oversized inputs. Model-graded assertions may make an explicit second judge
call through the normal Gateway pipeline. Core exposes the owner-routed equivalent at
`POST /api/gateway/evals/score`, so desktop clients never need the Gateway admin key.

### Bounded red-team campaigns

Core also exposes a local Promptfoo-style security campaign:

```
POST /api/gateway/redteam/run
```

The request accepts an agent id, an optional model, and an optional closed list of strategy ids.
When the list is omitted, Core runs ten server-owned probes covering `prompt_injection`,
`jailbreak`, `pii_exfiltration`, `tool_misuse`, `toxic_output`, system-prompt and indirect
injection, SQL and shell injection, and bias/fairness. Each probe is scored through the existing
Gateway evaluator catalog and returns a `protected` boolean plus bounded evaluator detail. Unknown
strategy ids are rejected. The tool-misuse probe is text-only; the campaign never executes a real
tool. Because the probes are provider-backed, they use the normal Gateway authentication, policy,
budget, and audit path.

The desktop and Activity Companion render this as **Security sweep**. The CLI exposes the same
contract as `ryu redteam <agent-id> [model] --json`; `tools/check-observability-gate.ts` can fail CI
when `summary.needs_attention` is non-zero or an evaluation aggregate is below a supplied threshold.

<Callout type="warn">
  Dataset runs are bounded and synchronous. A multi-model run with `llm_judge` fans out
  `models * cases * (1 + judge_calls)` provider calls, all under Core's 120s proxy timeout, so a large
  matrix can time out at the proxy even though no field is dropped. Use `max_concurrency`, `timeout_ms`,
  and `repeat` deliberately.
</Callout>

## Evaluator catalog

The eval runner above scores responses on three fixed dimensions. Separately, the Gateway ships a **unified evaluator catalog** - one shared taxonomy meant to power both inline guardrails and offline eval scoring from a single definition. `GET /v1/evaluators` returns the full catalog.

```
GET /v1/evaluators
```

It is a read-only computation over static seed data (`EvaluatorRegistry`, seeded by `apps/gateway/src/evaluators/catalog.rs`), so it mutates no state and exposes no secret - it is ungated like `GET /v1/evals` and `POST /v1/firewall/check`.

### The catalog

30 built-in evaluators across 8 categories (`builtin_catalog`). Each entry carries a `capabilities`
object with two booleans — `inline` and `offline` — derived from the entry's own config so they
can never disagree. This is a first-class **gate**: an evaluator that is offline-only is never
offered as an inline guardrail.

| Category | Count | Evaluators | Inline? | Offline? |
|---|---|---|---|---|
| **Security** | 3 | `pii_leakage`, `code_injection`, `prompt_injection` | Yes (enforced) | Yes |
| **Safety** | 2 | `toxicity`, `bias_fairness` | Yes (enforced, LLM judge) | Yes |
| **Quality** | 7 | `hallucination`, `assertions`, `code_checker`, `exact_match`, `correctness`, `conciseness`, `answer_relevance` | No | Yes |
| **Conversation** | 6 | `perceived_error`, `support_intent`, `tone`, `knowledge_retention`, `user_satisfaction`, `task_completion` | No | Yes |
| **Trajectory** | 3 | `plan_adherence`, `trajectory_accuracy`, `tool_selection` | No | Yes |
| **Image** | 2 | `explicit_content`, `sensitive_imagery` | Yes (Block / Warn) | Yes |
| **Voice** | 5 | `audio_quality`, `user_interrupts`, `transcription_accuracy`, `vocal_affect`, `language` | No | Yes |
| **Custom** | 2 | `llm_as_a_judge`, `code_evaluator` | Configurable | Configurable |

Key flags per entry:

- **`enforced`** — whether the evaluator is wired to execution. The five Security + Safety text
  detectors (`pii_leakage`, `code_injection`, `prompt_injection`, `toxicity`, `bias_fairness`)
  report `enforced: true`. Every other entry reports `false` so the UI can distinguish catalogued
  from wired.
- **`higherIsBetter`** — score polarity. Negative-signal judges (toxicity, bias, hallucination)
  score a BAD signal, so a high score is worse and this flag is `false`.

### Inline vs offline

The two execution modes serve different purposes:

| Mode | When it runs | What it needs | Action |
|---|---|---|---|
| **Inline** | On every scored request, before the response reaches the client | Only the request/response text | `FirewallPolicy` action: Block, Sanitize, or Warn |
| **Offline** | On demand (dataset runs, batch scoring) | A reference answer, conversation history, or trajectory | Score only; no inline action |

Inline evaluators are bound to the firewall scope through `FirewallConfig.evaluators` and cascade
node → org → agent with the same union-plus-lock semantics as the firewall dials. The five
enforced inline detectors run on the chat pipeline for both input and output. Image evaluators are
catalogued but not yet enforced on the image path.

### Custom evaluators

Two blank-slate evaluators let you create your own:

| Evaluator | What it does | Configuration |
|---|---|---|
| `llm_as_a_judge` | Sends the response to a configurable judge model with a custom rubric | `judge_model`, `rubric` |
| `code_evaluator` | Runs JS/Python code against the response in a sandboxed environment | `language`, `code`, `entry_point` |

Custom evaluators follow the same `inline`/`offline` capability pattern. A code evaluator that
needs filesystem or network access is offline-only; one that just parses JSON can be inline.

Promptfoo-style JavaScript assertions can use the injected `output`, `input`, `expected`, `vars`, and
`context` names, and may return a boolean, numeric score, or `{ score, pass, reason }` result. Ryu
executes these forms in Core's deny-all sandbox and reports `executed: false` when the required
runtime is unavailable.

### Binding an evaluator

Evaluators are bound to a firewall scope through `FirewallConfig.evaluators`, a list of `EvaluatorBinding` entries that cascade node → org → agent with the same union-plus-lock semantics as the firewall dials (see [Hierarchical policy resolution](/docs/gateway/security)).

| Binding field | Meaning |
|---|---|
| `id` | The catalog evaluator this binding enables |
| `enabled` | Whether the binding is active in this scope |
| `inline_action` | The `FirewallPolicy` (Block / Sanitize / Warn) applied inline when it fires |
| `offline` | Offline scoring config (threshold, judge model) |
| `locked` | Freeze the binding so a narrower scope can only tighten it |

<Callout type="info">
Inline evaluator bindings (`FirewallConfig.evaluators`) cascade node → org → agent and are
enforced on the chat pipeline for input- and output-target evaluators that report
`enforced: true` (the five text detectors plus additional wired judges as they land). Image-target
evaluators are catalogued but not yet enforced on the image path. The `enforced` flag on each
catalog entry remains the honesty signal for what a surface may claim is live.
</Callout>

## Audit

The audit log (`crates/gateway/audit/src/lib.rs`, `AuditLogger`) records every model call to a SQLite
store, alongside sandbox exec events and Passport credential reads. Writes go to a background OS
thread over a bounded channel, so the async request path never blocks on disk I/O; reads use a
separate query-only connection under WAL mode. The store is off when `AuditConfig.enabled` is false,
in which case writes are dropped and queries return empty.

### DB path

When `RYU_DIR` is set, the default path is `$RYU_DIR/audit.db`. Launching Core
and its managed Gateway with this override keeps audit rows in the selected
node data directory. If `RYU_DIR` is unset, the Gateway keeps the platform default:

- Linux - `~/.local/share/ryu/audit.db` (respects `$XDG_DATA_HOME`)
- macOS - `~/Library/Application Support/ryu/audit.db`
- Windows - `%LOCALAPPDATA%\ryu\audit.db`

An explicit `db_path` under `[audit]` in `gateway.toml` overrides the defaults.
Core-managed Gateway children receive the runtime `RYU_AUDIT_DB_PATH` value for
the active Core data directory; that profile-isolation override wins for the
child and is never written back to `gateway.toml`.

### Retention

Local audit storage is bounded automatically when the Gateway opens. The default policy keeps 90 days
and at most 1,000,000 rows. Set `RYU_AUDIT_RETENTION_DAYS=0` or `RYU_AUDIT_MAX_ROWS=0` to disable one
bound, or set a positive value to choose a different bound. Owners can run the same maintenance pass
through `POST /v1/audit/prune` (or Core's `POST /api/gateway/audit/prune`); the endpoint only applies
the configured bounds and never accepts SQL or a path.

### Record schema

Each row captures the request, its tenant attribution, usage, and quality. The `event_type`
discriminator separates a `model_call`, `exec_call`, `credential_read`, or `control_change`.

| Field | Notes |
|---|---|
| `request_id` | Gateway-internal id, also returned as the `x-request-id` response header |
| `api_key` | Redacted to a short prefix in query results; raw keys never leave the store |
| `user_name`, `org_id`, `team_id`, `project_id` | Tenant attribution |
| `user_id`, `agent_id` | Verified caller and stable agent attribution when Core has it |
| `provider`, `model` | Resolved route for the call |
| `input_tokens`, `output_tokens`, `cache_hit`, `latency_ms` | Usage and timing |
| `eval_score` | The `overall` eval score when this request was sampled, else null |
| `skill_ids` | Comma-separated active Agent Skill ids, from `x-ryu-skill-ids` |
| `session_id` | Core conversation/session id, from `x-ryu-session-id` |
| `error` | Error message when the call failed |
| `event_type`, `backend`, `command`, `duration_ms`, `exit_code` | Exec, credential-read, and control fields; null when not applicable |
| `user_id` | Verified Core user id when a signed-in organization member initiated the request or control; null for direct gateway-admin changes |
| `feature` | Product surface; control rows use `control` |
| `widget_instance_id` | Bounded widget-render correlation for widget tool/follow-up rows |

### Querying

```
GET /v1/audit
```

returns matching rows newest-first with `count` and `entries`. Every filter is an optional
query-string parameter combined with `AND`. Filters cannot inject SQL (the WHERE clause is fully
parameterized), and `limit` is clamped to a maximum of 1000 (default 100).

| Filter | Matches on |
|---|---|
| `api_key` | The full (unredacted) API key |
| `org_id`, `team_id`, `project_id` | Tenant scope |
| `provider`, `model` | Resolved route |
| `request_id` | A single gateway request |
| `session_id` | All rows belonging to one Core session |
| `agent_id` | All model, tool, credential, widget, and control rows attributed to one agent |
| `event_type` | `model_call`, `exec_call`, `credential_read`, `widget_follow_up`, or `control_change` |
| `errors_only` | Only rows that recorded an error |
| `limit` | Row cap, 1 to 1000 |

For complete usage analytics, use:

```
GET /v1/audit/usage?from=<rfc3339>&until=<rfc3339>
```

It returns model and execution activity in canonical 15-minute UTC buckets.
`from` is inclusive, `until` is exclusive, the maximum range is 400 days, and
optional `provider` and `model` filters use the same exact-match semantics as
raw audit search. The result is aggregated across the complete range and has no
raw-row limit. Core exposes the owner-only proxy at
`GET /api/gateway/audit/usage` and returns a fail-soft `reachable` status when
the Gateway is unavailable.

The signed-in organization aggregation view is a read-only projection of the
latest gateway reports. It presents gateway count, request/error/token/cost
totals as KPI cards, ranks gateway cost and provider eval scores as horizontal
bar charts, and keeps the recent audit rows below the charts. The projection
does not become a second measurement or billing source.

This endpoint is master-key only. Audit data is tenant-wide and sensitive, so a per-tenant key cannot
read it. The one exception is no-auth mode from a loopback peer, and even that loopback trust is
withdrawn when [mesh](/docs/core/node-and-presence) is enabled (a tailnet peer can appear as
`127.0.0.1`). From Core, `GET /api/gateway/audit` proxies the supported filters for the node owner and returns
`reachable: false` rather than erroring when the Gateway is down.

### Control activity and agent traceability

Successful administrator changes are recorded as `control_change` rows as well as being reflected
in the owning configuration. Direct Gateway-admin calls are attributed to the authenticated local
admin boundary; Core proxies carry the already-verified signed-in user id and email across that
boundary. The row uses `user_name` for the actor label, `user_id` for the verified user id when
available, `model` for the target (for example `gateway_config`), and `command` for a compact action
plus changed-section summary. Raw policy bodies, API keys, and other request payloads are never
copied into the row.

Core agent-management mutations (create, edit, delete, capability changes, prompt-version changes,
runtime authentication, imports, and session operations) also emit a bounded `control_change` row.
The row carries the verified organization caller and the stable `agent_id`; it never carries the
agent prompt, tool arguments, credentials, or request body. This is what lets an Agent passport
answer both sides of the question: **what did the agent perform, and which person changed its
controls?**

The organization Audit log page merges these gateway rows with organization control-plane activity,
including policy, config-as-code, firewall, key, budget, server, role, and membership changes. The
combined view is permission-gated by `audit.view` and can be filtered to organization or gateway
scope. Supplying `agentId=<stable-agent-id>` narrows the same projection to one agent's control
changes; the organization aggregation audit query uses the same `agentId` filter for its model and
tool activity rows.

The desktop Gateway activity view shows the same agent, caller, request, session, event, and result
columns. An agent's **Agent passport** combines its read-only identity/configuration snapshot with
the latest organization activity and the Gateway's redacted execution rows. Run history remains the
place to open the full persistent transcript for a correlated session.

## Local versus hosted capabilities

Ryu's parity target is the portable observe → evaluate → secure workflow: correlated traces, prompt and
model experiments, deterministic and model-assisted scoring, custom sandboxed evaluators, human review,
facets/views, exports, online scoring, red-team probes, CI gates, and local retention. Ryu keeps these
records on the node by default and routes provider calls through its own Gateway.

The following are hosted-service boundaries rather than missing local behavior:

| Hosted capability | Ryu behavior |
|---|---|
| Vendor-managed multi-tenant storage, cloud search, and SaaS uptime | Node-local SQLite stores with explicit Core/Gateway ACLs and bounded retention |
| Vendor account billing, hosted sharing links, and organization administration | Ryu account, node, project, and existing sharing/ACL surfaces; no claim of Braintrust or Promptfoo Cloud tenancy |
| Vendor-managed enterprise SSO/compliance contracts and proprietary hosted attack generation | Ryu's local auth/RBAC, privacy controls, bounded server-owned security campaign, and provider-neutral adapters |
| Vendor-specific cloud integrations and managed support | Ryu SDK/API/CLI contracts and self-hosted provider configuration |

These boundaries are deliberate: local Ryu can export reproducible artifacts to a hosted service when an
operator chooses, but it does not silently send prompts, responses, traces, or secrets to an external
vendor.

<Callout type="info">
  The Gateway records tokens, cost, and quality. Core records sequencing and latency. The two are
  joined by `session_id`, which Core forwards as `x-ryu-session-id`. See
  [Observability](/docs/core/observability).
</Callout>
