A device captures, a node infers, and one protocol connects them over either of two transports. The LLM, the dashboards, and the memory loop do not run on the device.

## Two transport modes, one protocol

A device reaches the node one of two ways.

- **Mode B (direct WiFi)** - the device opens a WebSocket straight to the node. This is the home case, where known WiFi is available and the node is reachable.
- **Mode A (BLE relay)** - the device speaks BLE to a paired phone, and the phone relays the traffic to the node over a WebSocket. This is the mobile, away-from-home case.

The logical protocol is **identical** in both modes. A device paired with RHP v1.1 runs an end-to-end encrypted session with the node in both, so in Mode A the phone is an **opaque forwarder**: it carries encrypted packets between the BLE GATT characteristics and the node WebSocket without being able to read or change them. The node learns that a session is relayed from the device's authenticated `hello` and the relay credential the phone presents. Devices still on the v1 protocol use the phone as a plaintext tunnel until they are re-paired. See [Protocol](/docs/hardware/protocol) for the session, frame, and message detail.

Because the ESP32-S3 has both radios, the device picks its mode at runtime:

<Steps>
  <Step>
    If provisioned WiFi credentials are present and the node WebSocket is reachable, use Mode B (direct).
  </Step>
  <Step>
    Otherwise, if a paired phone is in BLE range and connected, use Mode A (relay).
  </Step>
  <Step>
    Otherwise buffer to flash (for ambient capture) or show an offline state (for chat), and retry.

</Steps>

## Where inference happens

All inference is on the node. When a device streams audio, the node decodes Opus, transcribes with whisper.cpp, runs the chat turn through Core's `run_text_turn` (called from `apps/core/src/hardware/turn.rs`), and synthesizes TTS with OuteTTS. For ambient capture it hands the audio to the Meetings app through its `meetings.*` capabilities, which drive transcription, summary, and recall. Model calls from the chat turn route through the Gateway. Hardware adds no separate inference stack.

The ESP32-S3 has megabytes of PSRAM, while a 4-bit 8B model needs several gigabytes, so the device cannot run a useful model and does not try.

## The phone relay

The relay exists because WiFi transmit dominates a wearable's power budget, so a wearable cannot keep WiFi on all day. The device uses low-power BLE to reach a phone, and the phone, which has power and a network connection, carries the traffic to the node.

The relay does three jobs:

- Forwards the device's encrypted session between BLE and the node WebSocket, splitting and reassembling packets to fit BLE. It does no cryptography and cannot read the traffic.
- Holds a **relay credential** for that one device and presents it on the WebSocket upgrade. The credential only opens the relay connection. The device's own token and keys never reach the phone.
- Reconnects with backoff when the node drops and tells the device the link is back, so the device runs a fresh encrypted handshake and a flaky link recovers on its own.

The phone can see how much data flows and when, and, if you leave it on, a coarse face state so the app can show the assistant's expression. [Hardware Security](/docs/hardware/security#what-the-relay-phone-can-and-cannot-see) lists exactly what the relay can and cannot see.

The relay is the mobile app today (`apps/native`), which is also the pairing UI. The desk hub, being always plugged in, is always Mode B and needs no relay.

## One chip for every device

Some wearables use a BLE-only chip such as the Nordic nRF52840 for lower power use. Ryu uses the **ESP32-S3 for all three devices** for two reasons:

- **A unified codebase.** One toolchain (ESP-IDF), one set of shared firmware components, and one protocol implementation across the watch, necklace, and desk. A second chip family would fork the firmware.
- **WiFi fallback.** The ESP32-S3 carries both WiFi and BLE, so a device can run Mode B directly when WiFi is available and fall back to the BLE relay when it is not. A BLE-only chip cannot do Mode B at all.

The tradeoff is shorter battery life on the BLE relay than a dedicated BLE-only design, which is why on-device VAD is required. [Hardware Devices](/docs/hardware/devices) covers the battery reality per device.
