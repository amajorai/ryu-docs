The Ryu Hardware Protocol (RHP) v1.1 is the wire contract between a Ryu hardware device and a node. It is one WebSocket protocol that runs identically over both transport modes (direct WiFi and the BLE relay). Devices paired with v1.1 run it inside an end-to-end encrypted session. Devices paired under v1 keep working in legacy mode. This page is the reference for firmware, relay, and node authors.

<Callout type="info">
  RHP is implemented three times and kept in lockstep: in **C** for the device firmware, in **Rust** for the node (the `ryu-hardware` crate and Core), and in **TypeScript** for the mobile app (`@ryuhq/protocol`). The message `type` strings and field names are normative across all three, and all three are tested against the same shared test vectors.
</Callout>

## Endpoint and auth

- URL - `GET wss://<node-host>/api/hardware/ws` (a WebSocket upgrade), or `ws://127.0.0.1:7980/api/hardware/ws` on loopback.
- Auth - an HTTP header `Authorization: Bearer <token>` on the WebSocket upgrade request.
  - In Mode B (direct WiFi) the device adds the header with its own device token.
  - In Mode A (BLE relay) the phone adds the header. For a v1.1 device it uses a relay token that only opens this WebSocket for that one device; the phone never holds the device's own token.
- Loopback does not skip device auth. The token is **always required** on every bind, loopback
  included. The upgrade handler checks it against the device registry and rejects unregistered or
  mismatched tokens before any other work (`apps/core/src/server/hardware_ws.rs`). The encrypted
  session then checks the device's pinned key on top of the token. Pair the device first.

## The encrypted device session

A device paired with v1.1 talks to the node over an end-to-end encrypted session that runs inside the WebSocket.

- **Noise XX with pinned keys.** The session is a Noise `XX` handshake (X25519, AES-GCM, SHA-256). The device and the node each have a long-term key, and each side pins the other's key at [pairing](/docs/hardware/pairing). A stolen token alone is not enough to impersonate a device, and a device refuses a node whose key does not match the one it paired with.
- **The phone relay is opaque.** In Mode A the phone forwards encrypted bytes between BLE and the node WebSocket. It cannot read or change chat, audio, camera frames, or credentials. See [Hardware Security](/docs/hardware/security#what-the-relay-phone-can-and-cannot-see) for exactly what it can see.
- **The same ciphertext in both modes.** Mode A and Mode B carry the same encrypted records, so moving between WiFi and the relay does not change what the node or the device trusts.
- **Fresh keys every connection.** Each connection runs a new handshake, keys rotate during long sessions, and any tampered, replayed, or reordered record closes the session instead of being skipped.

### How a connection picks its mode

There is no separate endpoint or version header. The node looks at the first message a device sends:

- A v1.1 device always opens with an encrypted handshake. Once it has paired with v1.1 it never falls back to plaintext, even if something on the path asks it to.
- A device that only has v1 credentials (old firmware, or new firmware that has not been re-paired yet) sends the legacy plaintext `hello` and runs in **legacy mode**. The app badges it as legacy, and re-pairing upgrades it.
- If the node is too old to understand the encrypted handshake, the device backs off and shows "Update your Ryu node" rather than downgrading.

## Frame types

In legacy mode RHP multiplexes two kinds of frame over the single socket.

| Frame | Meaning | Encoding |
|---|---|---|
| TEXT | One JSON control message, dispatched on its `type` field. | UTF-8 JSON |
| BINARY | One Opus audio packet. Direction is implied by stream state. | Opus, mono, 60 ms frames |

In an encrypted session every WebSocket message is a binary encrypted record, and the same JSON control messages, Opus packets, and camera images travel inside it as typed records. The message tables below apply to both.

Audio is directional by sample rate: the **mic uplink** is Opus mono at 16 kHz, and the **TTS downlink** is Opus mono at 24 kHz, both in 60 ms frames.

## Control messages

There are 25 control message types: 10 from the client (device or relay) to the node, and 15 from the node back to the client. The capability messages are only accepted on encrypted sessions.

### Client to server

| `type` | Fields | Purpose |
|---|---|---|
| `hello` | `device_id`, `device_type`, `fw_version`, `relay`, `audio`, `caps` | First message after connect. Identifies the device, declares `relay: true` if tunneled via a phone (Mode A), and advertises the audio format and capability flags (`display`, `camera`, `speaker`, `mic`). |
| `mode` | `value` - one of `idle`, `chat`, `ambient` | Sets the device operating mode. |
| `listen` | `state` - `start` or `stop` | Marks a chat turn boundary (push-to-talk, wake word, or VAD). |
| `text` | `content` | Typed or derived text input, the fallback path when audio is not used. |
| `abort` | none | Barge-in. Stops the current TTS playback and generation. |
| `camera_meta` | `w`, `h`, `fmt`, `bytes` | Announces that the next image data is a JPEG of the given dimensions and size. |
| `telemetry` | `battery_pct`, `rssi`, `charging` | Periodic device health for the registry. |
| `ping` | none | Keepalive. |
| `capabilities_register` | `generation`, `capabilities` | Encrypted sessions only. Advertises the device's tools, each with a name, description, typed parameters, a timeout, and whether it is sensitive or needs a button press. |
| `capability_result` | `request_id`, `ok`, `result` or `error` | Encrypted sessions only. The answer to one `capability_invoke`. |

### Server to client

| `type` | Fields | Purpose |
|---|---|---|
| `hello_ack` | `session_id`, `ambient_session_id`, `tts`, and on encrypted sessions `proto` and `cap_limits` | Acknowledges `hello`. `ambient_session_id` is the long-running meeting id, present when the device is ambient-capable. `tts` declares the downlink format. `cap_limits` tells the device how many tools and concurrent calls the node accepts. |
| `stt` | `text`, `final` | Live transcript to display. |
| `chat_delta` | `text` | One chunk of the assistant reply. In v1 Core sends sentence-sized chunks after the reply is complete, not per-token deltas. |
| `chat_end` | `conversation_id` | The chat turn finished. |
| `emotion` | `value` | Drives the face: one of `neutral`, `listening`, `thinking`, `happy`, `sad`, `surprised`, `speaking`. |
| `tts_start` | none | Opus audio frames follow until `tts_end`. |
| `tts_end` | none | End of the TTS stream. |
| `ambient_ack` | `segment_id` | An ambient chunk was transcribed and indexed. |
| `ambient_skip` | `reason` | An ambient chunk was dropped, for example `silence`. |
| `display` | `surface`, `widget`, `payload` | A nudge to re-poll the dashboard now (`payload` is `{"action":"repoll"}`). `surface` is `eink` or `lcd`. |
| `error` | `code`, `message` | A protocol or runtime error. An unknown message type gets an error and the session continues. |
| `pong` | none | Reply to `ping`. |
| `capabilities_ack` | `generation`, `accepted`, `rejected` | Encrypted sessions only. Which advertised tools the node accepted, and why any were rejected. |
| `capability_invoke` | `request_id`, `generation`, `name`, `args`, `deadline_ms` | Encrypted sessions only. Asks the device to run one of its tools. |
| `unpaired` | none | Encrypted sessions only. The device was removed from the node; it wipes its credentials and returns to pairing. |

## Device tools

A device on an encrypted session can advertise small, typed actions, such as showing a line of text on the watch or beeping so you can find it. It sends them in `capabilities_register`. The node checks every advertised tool against strict limits (names, descriptions, parameter types, sizes, and timeouts), answers with `capabilities_ack`, and offers the accepted ones to your agents as tools from a built-in `device` server. Each call is a `capability_invoke` that the device answers with `capability_result`.

[Hardware Security](/docs/hardware/security#device-tools) owns the rules for when tools are offered and how to turn them off.

## Flows

### Interactive chat (mode chat)

<Steps>
  <Step>
    The device sets `mode: chat`. On wake word, button, or VAD onset it sends `listen: start` and streams mic Opus frames.
  </Step>
  <Step>
    On end of speech (VAD or button) the device sends `listen: stop`.
  </Step>
  <Step>
    The node decodes Opus, transcribes it in-process with whisper.cpp, and emits `stt`.
  </Step>
  <Step>
    The node runs the chat turn in-process through Core's `run_text_turn` (`apps/core/src/hardware/turn.rs`), sends `emotion` messages and the reply as sentence-sized `chat_delta` chunks, then `chat_end`. Model calls route through the Gateway.
  </Step>
  <Step>
    The node synthesizes TTS with OuteTTS, Opus-encodes it, and sends `tts_start`, the audio frames, then `tts_end`. An `abort` from the device cancels mid-stream for barge-in.
  </Step>
</Steps>

### Ambient 24/7 capture (mode ambient)

On `hello` an ambient-capable device gets an `ambient_session_id`. It then streams Opus only while its on-device VAD detects speech, and the node answers each ingested chunk with `ambient_ack` or `ambient_skip`. [Ambient Capture](/docs/hardware/ambient-capture#how-it-works) owns the full flow, the VAD defaults, and the Meetings app dependency.

### Camera (necklace, optional)

A `camera_meta` message followed by the JPEG hands the image to a vision-capable agent, which captions it into recall or answers an attached chat turn. On an encrypted session the image travels as its own record type, so it can never be mistaken for audio.

## REST surface

The non-realtime device endpoints live alongside the WebSocket. Every pairing and registry route needs your node token.

```text
POST   /api/hardware/pair/begin     start a v1.1 pairing
POST   /api/hardware/pair/reveal    get the code to compare
POST   /api/hardware/pair/confirm   finish after the device button press
POST   /api/hardware/pair/cancel    abandon a pairing
POST   /api/hardware/pair           legacy v1 pairing, for old firmware
POST   /api/hardware/identity/reset replace the node's device key (devices must re-pair)
GET    /api/hardware/devices        devices, their security status, and their tools
PATCH  /api/hardware/devices/:id    { name?, prefs? }
DELETE /api/hardware/devices/:id    remove the device and revoke its tokens
```

The pairing routes (`/api/hardware/pair` and `/api/hardware/pair/*`), `/api/hardware/identity/reset`,
and the `/api/hardware/devices` routes require Core's node bearer token. The `/api/hardware/devices`
routes also require the Hardware Devices app (`@ryu/hardware`, pre-installed) to be enabled. The WebSocket and the `/api/hardware/display/*`
routes authenticate the per-device token in the handler instead.

The device list reports, per device, its `last_seen` time, online status, battery, whether it runs the encrypted protocol, whether its key was verified at pairing, its key fingerprint, whether it needs re-pairing, its live tools, and its stored preferences. `PATCH` replaces preferences as a whole, so a client that changes one setting sends back every preference it read, with that one changed. The device registry persists in Core (SQLite). The dashboard adds further REST endpoints under `/api/hardware/display/*` and `/api/hardware/devices/:id/dashboard`, covered in [Device Dashboard](/docs/hardware/dashboard). The [Pairing](/docs/hardware/pairing) page walks through the pairing steps.

## Non-goals

- No on-device LLM. The node infers. For inference at the desk, run the node itself on a local host such as a Pi (see [Hardware Deployment](/docs/hardware/deployment#pi-as-node-optional)).
- No MQTT or UDP transport. RHP is WebSocket only.
- No in-place upgrade of a v1 device to the encrypted protocol. A legacy device is upgraded by re-pairing it, so a relay phone can never enroll a key on its own.
