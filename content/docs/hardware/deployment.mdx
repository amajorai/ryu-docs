Deploy a node, then flash and pair a device so it hears you and talks back through that node. Flashing and pairing have their own pages: [Hardware Firmware](/docs/hardware/firmware) and [Pairing](/docs/hardware/pairing).

<Callout type="warn">
  The firmware is ESP-IDF source with build and flash steps. Building it for the ESP32-S3 is not part of the automatic checks, and the boards have not completed hardware-in-the-loop testing. Treat the device steps as first bring-up.
</Callout>

The device does no inference. See [Hardware Architecture](/docs/hardware/architecture) for where work runs and how a device picks between direct WiFi and the phone relay.

## Prerequisites

**Node host** (your desktop, a server, or a Pi):

- Rust toolchain (stable) and **CMake on PATH**. The `opus` crate vendors and builds libopus via CMake. Keep the repo's `.cargo/config.toml` (it sets `CMAKE_POLICY_VERSION_MINIMUM=3.5` so a newer CMake still builds the vendored libopus).
- Sidecars for full chat: whisper.cpp (ASR) and OuteTTS (TTS), the same sidecars the rest of Ryu uses. Core manages them.
- The [Meetings](/docs/apps/meetings) app for ambient capture and the [Dashboards](/docs/apps/dashboards) app for device dashboards. Both are experimental and not pre-installed. The Hardware Devices app itself is pre-installed.

**Firmware build host** - ESP-IDF >= 5.1 with the ESP32-S3 toolchain. See [Hardware Firmware](/docs/hardware/firmware).

**Mobile build host** - Bun and the Expo toolchain. BLE needs a custom dev client, not Expo Go.

## Run the node

### Local loopback (dev)

```bash
cargo run --manifest-path apps/core/Cargo.toml
```

This binds `127.0.0.1:7980`. Loopback limits who can reach Core, but it does not
disable Core authentication. After first boot, Core mints `node-auth.token`, and
local clients such as Desktop resolve it automatically. For a direct `curl`, send
that node bearer. Confirm it is up:

```bash
curl -H "Authorization: Bearer <node-token>" http://127.0.0.1:7980/api/hardware/devices
```

Before any pairing the response has an empty `devices` array, plus a `node_identity` status.

### Remote always-on node (real devices)

Real devices need to reach the node over the network, authenticated.

<Steps>
  <Step>
    Bind beyond loopback and set a token. Core fails closed without a token on a non-loopback bind.

    ```bash
    RYU_BIND=0.0.0.0:7980 RYU_TOKEN="<strong-random-secret>" \
      cargo run --manifest-path apps/core/Cargo.toml --release
    ```
  </Step>
  <Step>
    Expose it privately with Tailscale rather than opening a public port. Install Tailscale on the node host, then put the relay phone (and any direct-WiFi device's network) on the same tailnet. Restrict who can reach the node with narrow access rules. See [Harden your tailnet](/docs/core/private-networking#harden-your-tailnet).
  </Step>
  <Step>
    Pin the URL handed back at pairing so devices get a stable address. Core returns this value
    verbatim as `node_url`, and the device dials it as its WebSocket URL, so give the full URL:

    ```bash
    RYU_HARDWARE_NODE_URL="wss://<node>.<tailnet>.ts.net/api/hardware/ws"
    ```

    If unset, the node derives the URL from the request `Host` header, then the MagicDNS name, then
    `RYU_BIND`. A `Host` header is used only when it names a loopback, private, link-local, or CGNAT
    address, `localhost`, the bound host, the MagicDNS name, or a name in
    `RYU_HARDWARE_ALLOWED_HOSTS` (comma-separated). Core ignores any other `Host` value
    (`apps/core/src/server/hardware_public.rs`).
  </Step>
</Steps>

### Sidecars

For full interactive chat the node needs whisper.cpp (ASR) and OuteTTS (TTS) running. Ambient capture also needs the Meetings app. Start Core once and let it manage the sidecars.

### Pi as node (optional)

A Pi 5 can **be** the node (run Core on it) so the desk hub has local inference. The Pi is the node host here, not the desk device itself. Use the Linux arm64 Core binary from a release (`ryu-core-linux-aarch64`), or install Rust and CMake on the Pi and build Core from source with the same commands.

<Callout type="warn">
  Running the node on a Pi has not been tested.
</Callout>

## Flash, pair, and dashboard

These steps have their own pages:

- **Flash the firmware** - see [Hardware Firmware](/docs/hardware/firmware) for the `idf.py` build and flash commands and board config.
- **Pair and provision** - see [Pairing](/docs/hardware/pairing) for the press-to-confirm flow in the mobile app. Pair against the same node URL the devices will use. Pairing and the encrypted session need no extra node configuration.
- **Set up the dashboard** - see [Device Dashboard](/docs/hardware/dashboard) to author a device dashboard and have the desk e-ink or watch view show it.

## First end-to-end smoke test (do Mode B first)

Mode B avoids the BLE relay, so it isolates the core path. Do it first.

<Steps>
  <Step>
    Run Core on an address the device can reach on your LAN or tailnet, with a token, as in
    [Remote always-on node](#remote-always-on-node-real-devices). A loopback bind gives a `node_url` of
    `ws://127.0.0.1:7980/api/hardware/ws`, which only the node host itself can reach.
  </Step>
  <Step>
    Pair the device from the mobile app against the node URL the device will use: compare the code and press the device button (see [Pairing](/docs/hardware/pairing)). Enter WiFi credentials during pairing for an over-the-air test. Firmware with RHP v1.1 only accepts credentials delivered by the app's press-to-confirm pairing.
  </Step>
  <Step>
    **Chat** - press the button, speak, and expect `stt` (transcript on screen), then `chat_delta` (the reply), then TTS audio.
  </Step>
  <Step>
    **Barge-in** - start talking while it is speaking. The device sends `abort` and TTS stops immediately.
  </Step>
  <Step>
    **Ambient** - put the device in `ambient` mode (the RHP `mode` message). Speech is transcribed into the device's long-running meeting and flows into recall and summary.
  </Step>
  <Step>
    **Dashboard** - author a widget. The desk e-ink (or the watch dashboard view) shows it, and editing it triggers a re-poll.
  </Step>
</Steps>

## Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| Core won't build, CMake error about policy `< 3.5` | Make sure the root `.cargo/config.toml` (`CMAKE_POLICY_VERSION_MINIMUM=3.5`) exists and CMake is on PATH. You do not need an older CMake. |
| Phone never finds the device over BLE | UUID mismatch or BLE permissions. Confirm `ble_prov.c` and the app's GATT UUID table use the same `7e1a...` UUIDs, that Android `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT` are granted, and that you are on a dev client, not Expo Go. |
| Paired but no chat | Sidecars down (whisper.cpp or OuteTTS) or wrong `node_url`. Check Core logs and verify the provisioned URL is reachable from the device's network. |
| Assistant talks over me | Firmware build missing the `abort`-on-speech-onset path, or Core not honoring `abort`. |
| Ambient speech never shows up in Meetings | No enabled app provides the `meetings.*` capabilities. Install and enable the [Meetings](/docs/apps/meetings) app, then reconnect the device. |
| Mode A drops and stays dead | An older relay without reconnect, or an older app relaying a v1.1 device (it cannot forward the encrypted packets). The current relay reconnects with backoff, and the device runs a fresh encrypted handshake each time. Update or rebuild the dev client. |
| Device shows "Node identity changed" | The node's device key changed. Remove the device in the app, hold its button for 10 seconds, and pair again. See [Hardware Security](/docs/hardware/security#if-your-nodes-device-key-is-lost). |
| Dashboard blank or no image | The device is Mode A (relay), and the image path is WiFi-only, so provision WiFi credentials for Mode B. Or the Dashboards app is not enabled, or no device dashboard has been authored yet. On the watch, also check that its screen preferences request RGB565 (see [Device Dashboard](/docs/hardware/dashboard#per-device-behavior)). |
| Dashboard shows shapes but no text | The node host has no system fonts. Install fonts so `resvg` can render text. |
| E-ink ghosting builds up | Expected. The desk firmware does a periodic full refresh. If it never clears, check the ghosting budget. |
| RGB565 colors look wrong on the watch | A byte-order change on one side. RGB565 is big-endian on the wire; see [Device Dashboard](/docs/hardware/dashboard#per-device-behavior) and leave both sides as shipped. |
