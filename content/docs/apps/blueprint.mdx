## What it does

Blueprint lets you review an agent's plan before it edits a file. The agent publishes the plan over MCP; Blueprint parses the markdown into addressable blocks and builds a dependency graph from each step's `depends_on` edges. You can see what must happen first and which step blocks the rest.

Annotate a block or step with a comment, redline, question, or blocker, then approve or request changes. A requested-change verdict is stored as deterministic text and returned through `blueprint.plan_status`. Each finding names the block or step it belongs to; a redline includes the exact replacement text.

Republishing with the same plan id adds a revision instead of creating a new plan. Block ids stay stable across revisions, so the next draft arrives as a diff against the first.

### Capabilities

- **plan.review** - capability `plan.review`
  - Grant: `blueprint:review`

### MCP server

- **`blueprint`** - Publish a plan for review and read the verdict back as text. Use it before work that is expensive to undo, such as a migration or a refactor across many files. `plan_publish` posts numbered steps with their `depends_on` edges and returns a review URL. `plan_status` polls with a bounded wait and returns the reviewer's annotations as readable findings. `plan_get` fetches the plan and its annotations. `step_update` marks steps done as the work lands.

## UI it contributes

### Hook events

- **A plan was published for review** - A revision was written and the plan is now `in_review`. Fires on every publish, including a republish under an existing `plan_id`; that creates a new revision of the same plan. Use `revision` to distinguish the first draft (1) from later responses to a verdict (2 and up). It does not fire when someone annotates a plan or changes a step's status.
- **A plan was approved** - A reviewer recorded an `approved` verdict against a specific revision. The event fires only when the verdict is posted. Resolving annotations is not a verdict, and a plan with no annotations is not approved by default. `note` is optional and never controls approval. Unresolved `comment` annotations may remain on an approved plan and are included in the feedback as advisory text.
- **A reviewer asked for changes** - A reviewer recorded a `changes_requested` verdict. `annotation_count` reports how many annotations were open when the verdict landed. It is a count, not the annotations themselves; read those through `blueprint.plan_status`. The event does not fire when someone creates an unsubmitted `blocker` annotation.
- **A plan step was marked done** - A step's status changed to `done`, normally through `blueprint.step_update`. Fires once per transition into `done`. Changes to `in_progress` or `blocked` are silent, and later updates that leave a step at `done` do not fire it again.
