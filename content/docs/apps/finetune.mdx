## What it does

Fine-tuning is a local training studio for supervised fine-tuning (SFT) and preference tuning (DPO). Launch LoRA/QLoRA jobs on this node's GPU or on a remote GPU node, track them durably, merge the trained adapter to GGUF, and register the result as a swappable local model.

<Callout type="warn">
Training on a remote GPU node needs a node URL and token that you configure yourself (**Train on a remote GPU node**). A remote node is external to this Ryu node, so its availability and setup are your responsibility.
</Callout>

## Train a model

### Import a dataset and start a run

Drop a PDF, CSV, JSON, JSONL, or TXT file into the dataset area, or choose one from the file picker.
Files are parsed in the Companion. Their contents are sent to the selected training node only when
you start the run. Imports are limited to 32 MB. PDFs need selectable text; scanned PDFs need OCR
before importing. You can also edit the generated JSON rows directly.

If the start request fails, retrying the unchanged configuration reuses its idempotency key, so a
request that reached Core but lost its response does not start a duplicate job. Editing the
configuration before retrying creates a new request identity. After Core accepts the job, the run
view opens with the chosen adapter name immediately while the persisted job record and live progress
stream catch up.

### Choose a training method and dataset

- **SFT** learns from `chat`, `alpaca`, or `text` rows. For example, a chat row contains a `messages`
  array with `role` and `content` values.
- **DPO** learns from preference pairs. Each row needs non-empty `prompt`, `chosen`, and `rejected`
  strings. `chosen` is the response to prefer and `rejected` is the alternative to avoid.

CSV imports use column headers. SFT accepts `messages` (JSON in each cell), `instruction` plus
`output` (and optional `input`), or `text`. DPO accepts `prompt`, `chosen`, and `rejected` columns.
Plain text and PDF imports become text samples for SFT; DPO requires structured preference rows.

The Companion checks the selected method's row shape and DPO beta (greater than 0 and at most 1,
default `0.1`) before starting. Both methods use LoRA/QLoRA and produce an adapter that can be merged
to GGUF and used from the Models catalog.

### Follow run progress

The run view shows training steps, loss, method, and an estimated remaining time while training is active. Completed, failed, and cancelled runs show no remaining-time estimate. Failed runs keep the worker error for review.

## Merge an adapter

Open a trained run in **History** and choose **Merge**. A successful merge notice identifies the GGUF model and its output path. The model is registered under the name you chose (or the adapter's name) followed by a short unique suffix, so a merge never replaces an existing model, including another person's merged model on a shared node. Check the Models catalog to confirm that the model is registered before selecting it for inference.

If the node returns no usable model identity or output path, the Companion shows an error and keeps the trained adapter available. Choose **Merge** again to retry the same adapter.

Adapter names are labels, not storage locations. Each run saves its adapter to its own new folder,
so two runs (or two people on a shared node) can use the same adapter name without overwriting each
other's adapter. On a shared node, the adapter list and **Merge** include only adapters produced by
your own runs. A run trained on a remote GPU node keeps its adapter on that node, so it does not
appear in this node's adapter list.

## Data at rest

Trained adapters and merged models are not encrypted, because the training and inference engines
read them directly from disk. They are stored so only your user account can open them, and
training checkpoints and export scratch files are deleted when a run ends. Any that an
interrupted run leaves behind are removed the next time the app starts. Datasets you import in
the Companion are sent with the run and held in memory. Dataset files you place in the app's
dataset folder yourself are read as they are and are not encrypted. A model trained on private
data can repeat parts of it, so share or back up adapters and merged models with the same care
as the dataset.

### Hook events

- **Fine-tune started** - Fires when a fine-tune job has actually been accepted and a job id exists - either the local Unsloth worker returned one from POST /api/finetune/start, or a remote GPU node did. A start the GPU gate refused (no CUDA device on this node) or one the worker never accepted does not fire. Nothing is trained yet: the adapter arrives with `job.succeeded`. `target` says where it runs; dispatching to a remote node also starts the job on that node, so that node raises its own `job.started` against its own record - two Cores, two job ids, not a duplicate.
- **Fine-tune succeeded** - Fires once, when a job finishes training and, for a local job, the adapter it produced has been added to the adapter catalog. `adapter_name` is the stem it is filed under (the adapter's server-generated folder name, not `output_name`), which is exactly what POST /api/finetune/merge takes as `adapter_name` - so "when a fine-tune finishes, merge it into a GGUF" needs nothing else from the payload. A remote job's adapter stays on the remote node, so its `adapter_name` is null. TIMING: this crate has no background poller, so the event fires when Ryu next READS the job's state (a job list or a job detail fetch), not the instant the worker finished. A remote job is refreshed only by a detail fetch - the list refreshes local jobs only - so a remote job's completion is announced when someone opens it.
- **Fine-tune failed** - Fires once, when a job ends in failure - the training run itself broke (out of VRAM, an unusable dataset, a worker crash), so no adapter exists. Cancelling a job does NOT fire this: a cancel is user-initiated and recorded as `cancelled`, and the person who asked for it already has the answer. Same timing as `job.succeeded` - it fires on the next read of the job's state, and for a remote job only on a detail fetch. `error` is the worker's own message when it gave one, otherwise null.
