## What it does

Monitors watch website prices, stock, keywords, content, and uptime, plus provider quota windows and API-credit balances.

Provider reset monitors detect scheduled refills and provider-initiated resets by comparing live usage snapshots. A first check records a quiet baseline. Later checks notify when a selected window refills or a credit balance increases.

When no monitor is selected, the Companion can also show a **Usage pace** estimate for a subscription provider. It uses the average usage since the provider-reported window began to estimate whether a timed quota will be exhausted before its next reset.

Estimates update while the Companion is open and are available when the provider reports both a window length and reset time. They are projections, so they can change as usage changes.

### Hook events

- **Monitor alert raised** - A scheduled (or run-now) check tripped its alert condition and the alert was stored. Fires once per transition, not once per check. `kind` identifies transitions including `uptime_down` / `uptime_up` / `keyword` / `content_change` / `price` / `stock` / `usage_reset`.
- **Monitor check failed** - A check could not complete - the fetch failed, the crawler was unavailable, or the price/region regex matched nothing - so the site was never actually evaluated. The watch is broken, not the watched page. Unlike an alert this is NOT transition-gated: a monitor that keeps failing emits this on EVERY run until it is fixed. Uptime checks never emit it, because for them a failed fetch is the signal (`uptime_down`) rather than an error.
