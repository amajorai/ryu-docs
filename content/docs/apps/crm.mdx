## What it does

Harbor starts with a data model instead of a fixed set of screens. It includes the five objects most pipelines need: companies, people, deals, notes, and tasks. You can add objects and give them typed fields such as currency, status, rating, multi-select, or relations. Views, filters, boards, and reports use those fields without a schema migration.

Records are validated value bags. A `stage` that started as free text can become a status field while existing rows keep working. Relations are materialized in both directions, so a company page can show its people, open deals, and related notes without a separate reverse model. Each record has one timeline for notes, calls, meetings, tasks, and store-written field changes.

CSV import previews inferred columns and sampled values. Map columns to existing or new fields, choose a dedupe key, and run a dry run that reports how many rows would be created, updated, or skipped. Duplicate records can be merged field by field, with activities, list memberships, and relation edges moved to the survivor.

The node owns the app's SQLite database and indexes it with FTS5. Harbor runs as a loopback sidecar, so the pipeline stays on the node rather than in a separate cloud tenant.

## What it exposes

### Tools

### `crm.search` - Search CRM

Full-text search across every CRM record on this node. It ranks hits across companies, people, deals, and custom objects, and each hit names the matching field and includes a snippet. Returns `&#123;ok, hits:[&#123;record_id, object, title, field, snippet&#125;]&#125;`. Use `crm.find_record` when you need an exact field match such as an email address or domain.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `query` | string | yes | What to search for. |
| `object` | string | no | Optional object slug to scope the search to, e.g. `company`, `person`, `deal`. Omit to search everything. |
| `limit` | integer | no | Max hits. Defaults to the node's page size; clamped to its ceiling. |

### `crm.find_record` - Find CRM Record

Look up records by an exact field value on one object. Use it before creating a record when you want to avoid duplicates. With no `field`, it matches the object's title field. Returns `&#123;ok, records:[…]&#125;`; an empty result is a normal answer, not an error.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `object` | string | yes | Object slug, e.g. `company`, `person`, `deal`. |
| `field` | string | no | Field slug to match on, e.g. `email` or `domain`. Omit to match the object's title field. |
| `value` | string | yes | The exact value to match. |
| `limit` | integer | no | Max records to return. |

### `crm.get_record` - Get CRM Record

Read one record in full by id: every field value as the store normalized it, plus its related records and recent timeline. Values come back normalized rather than as they were written, so this is also how you check what an update actually stored.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `record_id` | string | yes | The record's id, as returned by search or find. |

### `crm.create_record` - Create CRM Record

Create a record on an object. `values` is keyed by field slug and uses the same validator as the UI form. Invalid values are rejected, and the response reports every rejected field so one retry can fix them all. Check for an existing record with `crm.find_record` first; this tool does not deduplicate. Returns `&#123;ok:false, errors:&#123;field: reason&#125;&#125;` on rejection.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `object` | string | yes | Object slug, e.g. `company`, `person`, `deal`. |
| `values` | object | yes | Field values keyed by field slug. Currency fields are integer cents. Dates and datetimes are RFC-3339 strings. A select or status field takes one of its declared option values. |

### `crm.update_record` - Update CRM Record

Merge new values into an existing record. Fields you omit stay unchanged, so the tool accepts partial updates. The response names only fields that changed; resending an existing value reports no change. Moving a status field raises the same stage-changed event as dragging the card in the UI.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `record_id` | string | yes | The record to update. |
| `values` | object | yes | Field values keyed by field slug. Only the fields present are touched. |

### `crm.log_activity` - Log CRM Activity

Append a note, call, or meeting to a record's timeline. Use `crm.create_task` for future work; this tool records activity that has already happened.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `record_id` | string | yes | The record this happened against. |
| `kind` | string (one of: note, call, meeting) | yes | What kind of entry this is. `field_change` and `stage_change` are written by the store itself and cannot be logged here. |
| `title` | string | yes | One-line summary shown in the timeline. |
| `body` | string | no | Optional longer detail. |
| `assignee` | string | no | Optional person this is attributed to. |
| `due_at` | string | no | Ignored for notes/calls/meetings; use crm.create_task instead. |

### `crm.create_task` - Create CRM Task

Create a follow-up task, optionally attached to a record. A task with `due_at` is swept when it comes due and raises `task.due` once, making it reachable by automation. A task without a due time remains a to-do and never emits that event.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `title` | string | yes | What needs doing. |
| `record_id` | string | no | Optional record to hang the task off. Omit for a standalone to-do. |
| `body` | string | no | Optional detail. |
| `assignee` | string | no | Who owns it. |
| `due_at` | string | no | RFC-3339 timestamp. Required if you want the task to raise `task.due` when it comes due. |

### `crm.pipeline` - CRM Pipeline Report

Summarize a pipeline: record count and summed value per stage of a status field, with win rate and average age in stage. Defaults to the `deal` object and its own status and currency fields, so calling it with no arguments answers "how is the pipeline doing". Point `object_id` at any object that has a status field to get the same shape for it.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `object_id` | string | no | Object slug or id. Defaults to `deal`. |
| `field_id` | string | no | The status field to group by. Defaults to the object's own status field. |
| `value_field_id` | string | no | The currency/number field to sum per stage. Defaults to the object's amount field. |
| `include_closed` | boolean | no | Include stages marked as closed/won/lost. Defaults to false, i.e. open pipeline only. |

## Permissions

**Grants:** `crm:crud`, `tool:http-egress:127.0.0.1`

| Level | Description | Implies |
|---|---|---|
| **Can view** | Read the objects, records, views, lists, and activity timelines on this node, and run searches and pipeline reports. |  |
| **Can edit** | Create and change records, log activities, and manage views and lists. Does not include changing the schema or importing files. | `crm.view` |
| **Can administer** | Change the schema, add or delete objects and fields, run CSV imports, and merge records. These operations can rewrite or remove many rows at once. | `crm.edit` |

### Hook events

- **Record created** - A new record was committed to an object. Fires once per durable row, including each row created by a CSV import. It does not fire for a validation failure or for the survivor of a merge, because that record already existed.
- **Record updated** - At least one field value changed. `changed` lists only the fields that differ, so resending identical values emits nothing. Fires once per write, not once per field. A stage move also raises `deal.stage_changed`; subscribe to one event or the other unless you need both.
- **Deal stage changed** - A record's status field moved to a different stage. The event includes the old and new values and fires for any object with a status field, including custom objects. Keeping the same value is silent. Dragging a board card and PATCHing the field raise the same event.
- **Task became due** - An open task passed its due time and was claimed by the sweep. Fires once per task through a compare-and-set, even when two Harbor processes share one data directory. A node that was offline emits its backlog over several ticks. Completing or rescheduling the task first prevents the event; reopening an announced task can make it fire again.
