## How Projects fit together

Ryu organizes long-running work as **Projects › Bots and Groups › Sessions**:

- A **project** is the top level. It has one **main thread**, run by its
  coordinator agent, plus shared context, instructions, and model defaults.
- **Bots** and **Groups** join a project as members. Each member gets its own
  main thread inside the project. A Group's main thread is coordinated by the
  Group's lead agent using the Group's coordination strategy (Broadcast,
  Round-robin, Debate + synthesis, or Smart router).
- **Sessions** are where the work happens: one thread per activity. When a main
  thread delegates, the session shows up in that thread's transcript as a session
  card, and in its **Sessions** panel. Sessions do not clutter the sidebar.

Talk to the project's main thread. The coordinator plans the work, delegates to
member threads or new sessions, checks their progress, and reports back.

Projects is installed by default, and onboarding offers to create your first
project right after you personalize your default agent. You can skip that step
and create a project later from the **Projects** section of the sidebar or from
the Projects app.

## Members

Add bots, Groups, or people in the Projects app under **Members**. Adding a bot
or Group creates its main thread in the project. Removing a member ends the
membership but keeps its thread as project history.

## Instructions

Project instructions are optional standing rules for the whole project, such as
how to cite sources or which conventions to follow. Set them in the Projects app
under **Instructions**. Every thread in the project carries them in its system
prompt, next to the goals, including the coordinator's main thread and each
member's main thread. Background turns, such as delegated sub-agents, and
untrusted callers do not get them. A project run started from the Projects app
is a background turn, so its run request states the instructions instead.
Instructions are limited to 4,000 characters. Ryu asks before saving changed
instructions, because the change resets the prompt cache for every thread in
the project once.

## Goals

Goals are optional. Each one you set is added to the system prompt of the
threads it applies to, so the bots keep their work pointed at it:

- **Project goal**: set it when you create the project or later in the Projects
  app under **Goals**. Every thread in the project carries it.
- **Bot goal**: set it in the bot's settings under **Goal**. Every thread that
  bot runs carries it, in every project.
- **Bot goal in a project**: set it per bot in the Projects app under
  **Goals**. Only that bot's threads in that project carry it.

When more than one applies, the thread gets all of them, broadest first. Goals
are limited to 2,000 characters each. Removing a bot from a project clears its
goal in that project. Deleting a project clears its goal, instructions, brief
replies setting, and its bots' goals in that project.

## Brief replies in main threads

Project and bot main threads are where you check in, so their replies are short
by default: the answer or status first, a few bullets at most, and the full
detail when you ask for it or in a session. Long work moves into a session that
reports back to the main thread in one line. Sessions and Group main threads keep
the bot's usual reply length.

Choose **Full length** under **Main thread replies** to turn this off for a
project (in the Projects app's **Goals** section) or for a bot (in its **Goal**
settings). The most specific setting wins: a bot in a project, then the bot,
then the project. A personality profile selected for the bot or the turn takes
precedence over brief replies.

## Settings changes and the prompt cache

Providers cache the start of each request, including the system prompt, and
charge less for the cached part on later messages. Project instructions, goals,
brief replies, and a bot's instructions, name, tone, personality profile, and
skills are all part of that system prompt. Changing any of them makes the next
message in each affected thread re-send its whole conversation at the full
input price, once. Later messages are cached again.

Ryu asks before applying such a change and says which threads it reaches. The
same applies to changing a project's or bot's default model, because prompt
caches are per model. Changing only the effort does not reset the cache. Saving
a setting with an unchanged value applies nothing and costs nothing.

## Model defaults

Every thread resolves its model from the most specific setting available:

1. the session's own model choice in the composer;
2. the bot's default inside this project;
3. the bot's default everywhere;
4. the bot's own configured model;
5. the project's default;
6. your node-wide default in **Gateway › Defaults › Models**;
7. the node's default agent and model.

Provider and model are always taken together from the same level, so a thread
never pairs a model with a provider that cannot serve it. Effort is resolved on
its own. Set project defaults in the Projects app under **Model defaults**, or
from the **Defaults** button above any thread in the project, which also shows
where the current value comes from and lets you reset a level to inherited.
**Reset to defaults** in **Gateway › Defaults › Models** clears both coordinator
and thread defaults for the node, so they inherit from the next level.

Each level has two sets of defaults:

- **Coordinator model and effort** apply to main threads: the project's, a
  bot's or a group's thread that you talk to and that starts sessions.
- **Thread model and effort** apply to the sessions those main threads start.

So a project can coordinate on a strong model while its sessions run on a
cheaper one. A main thread uses a coordinator value from any level before it
falls back to the thread values, and a level that only sets thread values
applies to every thread. A blank picker shows what it inherits, for example
**Default (claude-opus-5-5)**.

If the node cannot save a defaults change, it reports an error and keeps the
existing values. Retry the same change once storage is available.

## Memory

Bots in a project share the project's memory, and each bot keeps its own memory
across projects.

## Folder projects from earlier versions

Projects you made from folders in earlier versions move into the Projects app
automatically the next time the desktop connects to a node that has it. Each one
becomes a project with the same name and icon (or joins a project that already
uses the same folder), keeps the memory its bots learned in that folder, and its
existing chats are filed under the project's main thread, where they appear in
**Sessions**. New chats started in those folders join the project too. Nothing
is deleted, and the folder stays linked on that device.

## Where projects live

Projects are stored on the node that runs them, next to their threads. Connect to
that node from another device to see its projects. The arrangement of your
sidebar sections follows your account. Project folders stay on the device where
you added them.

## Saving, ownership, and access

Project edits show right away while they save. The node's response is the final
state: a rejected update restores the previous value and shows an error. If a
context, coordinator, worker, or subscription request fails, its form stays open
so you can retry.

Projects and their context, workers, and subscriptions belong to the
organization or local user that created them. Only the owner can delete a
project. A delete request from another organization returns not found and
leaves the owner's records intact.

Moving a session to another project saves its project and parent together and
keeps the main thread that originally spawned it. The move checks that you can
open both conversations. If the parent is missing or inaccessible, or the save
fails, the session stays where it was.

Delegated credentials need these Core capabilities for the thread hierarchy:

| Operation | Requires |
|---|---|
| Read main threads, sessions, and a project's threads | `chat:read` |
| Move a session to another project, or change a Group thread's coordination strategy | `chat:write` |
| Create a main thread, change scope defaults or goals, migrate project memory | Node owner credentials |

Conversation access checks still apply to every thread.

## Data at rest

Projects encrypts each project, its context notes, workers and subscriptions with a key only this app receives from Ryu. Which account a project belongs to and when a subscription next runs stay readable so the schedule can run. Projects saved by an earlier version are encrypted when the updated app starts. If the app is updated before Ryu itself, it keeps working unencrypted until Ryu delivers its key, and its health status says it is waiting for a Ryu update.
