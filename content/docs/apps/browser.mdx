## What it does

Browser is a real Chromium browser (Electron) that Ryu agents and the desktop share. It provides the grant-gated `browser.control` capability.

- On a local node, agents can share one embedded session with you.
- On a managed cloud node, each Bot gets a hidden tab lane with its own persistent Chromium profile (see [Agent profiles](#agent-profiles)).

Core routes the desktop Browser panel and agent tools through its authenticated ext-proxy.

## Appearance bridge

The desktop Browser panel sends the current Desktop appearance to the browser chrome through the authenticated sidecar bridge. The shell follows the selected light or dark palette, contrast colors, interface and heading fonts, locale, and display time zone as they change.

History labels use that display time zone and locale. Appearance tokens are never injected into websites opened in browser tabs.

## Language

The browser window's own interface follows your Ryu interface language: the tab strip,
toolbar, menu, settings, history, downloads, and activity pages, its messages, and
the system dialogs it opens (site permission prompts, save and folder pickers). Arabic
lays the window out right to left. File sizes and times such as "5 min ago" use that
language's conventions. The window remembers the last Ryu language the desktop panel
sent, so when an agent opens the browser on its own it starts in that language; before
the panel has ever connected, it starts in your operating system's language. Error
messages are shown in that language too: when an action fails for a reason the browser
cannot describe in it, such as a folder with no extension manifest, you see a short
translated message instead of the engine's English text. Text with no translation yet
appears in English, and websites in tabs keep their own language. On Windows and Linux the window has no native
menu bar; its commands are in the Browser menu on the toolbar.

On Windows and Linux, the controls the browser engine draws inside pages also use that
language: form validation messages, date, time, and list pickers, and media controls. Sites
are asked for content in that language first too. These follow a language change the next
time the browser starts. On macOS they follow your system language.

## Activity center

The browser toolbar includes an Activity center. It shows active and recently active
sessions started by Ryu:

- audio/video playback;
- microphone and camera capture;
- screen capture;
- browser control.

Selecting an activity for a visible tab brings that tab forward. Activity records are
ephemeral browser-chrome state. They are not written to browsing history or sent to an
agent, and a closed or navigated tab clears its activity.

### When an activity counts as active

- Media capture is reported only after a page receives a real `getUserMedia` or
  `getDisplayMedia` stream. A permission prompt by itself does not appear as active capture.
- Audio/video playback comes from Chromium's media lifecycle events. A tab with several media
  elements stays active until the page has no playing element left.
- Camera, microphone, and screen indicators stay active until the captured tracks actually end.
  This includes cloned tracks, capture in additional frames, and same-page or unsuccessful
  navigation.

A page cannot clear these indicators by sending an activity message or dispatching a synthetic
track event. Once capture stops, the activity briefly appears under **Recently active**.

## Browser window

The tab strip lets you select, open, and close tabs. The navigation controls go back, forward,
or reload the selected tab, and the address field accepts a URL or search. The Browser menu also
contains Find in page, zoom, the device toolbar, screenshot capture, cookie import, History,
Downloads, and Browser settings.

- **History** lists visited page titles, URLs, and visit times. Choose **Open** to bring a saved
  page into a visible browser tab, or **Clear history** to remove the list. Use the page's back
  control to return to the browser while keeping the active tab.
- **Downloads** on the toolbar shows recent download status and a shortcut to the download
  folder. Open the Downloads page from that popover or the Browser menu to review the list, open
  the folder, or clear its history.

### Desktop Browser dock

The Desktop dock opens a URL in the sidecar, refreshes its tab list, and lets you select or close
a tab. Choose **Agents** to watch an agent's own browser instead (see
[Watching an agent's browser](#watching-an-agents-browser)). To annotate a page:

1. Choose **Annotate** to freeze the current preview, then click an element or drag an area.
   Hold **Shift** while clicking to add more targets.
2. Describe the change. When your browser supports speech recognition, **Dictate annotation**
   appends recognized words to the comment, and **Stop voice annotation** finishes dictating.
   Dictation listens for the language Ryu's interface is set to.
   Review the comment before saving it. You can always type the comment directly.
3. Optionally open **Adjust styling**, then choose **Add note**.
4. Choose **Ask Ryu to address notes** to open the assistant with the current page, its latest
   saved notes, and their style adjustments queued as context.

Press **⌘⇧D** on macOS or **Ctrl+Shift+D** on other platforms to toggle annotation mode.

Saved notes appear as overlays and in the tab's note list. Remove one note, or choose
**Clear notes** to remove all of them. **Cancel draft** discards an unsaved selection, comment,
and style adjustments. Notes remain with the open tab and are cleared when that tab navigates
or closes.

Failures keep your work so you can retry:

- If saving a note fails, the dock keeps the selection and comment so you can choose **Add note**
  again. After a successful save, the error clears and the note appears in the preview.
- Failed note deletions and clears keep the saved notes visible.
- While Ryu prepares assistant context, the **Ask Ryu to address notes**
  button stays disabled to prevent duplicate requests. If preparing context fails, the notes remain
  saved and you can choose it again.

## Chromium extensions

Open **Browser settings → Extensions → Load unpacked** to add a local Chrome or Chromium
extension folder. Ryu loads the extension into the visible browser session with local file access
disabled and remembers the folder for the next browser launch. Remove an extension from the same
list to unload it and forget its path.

Electron accepts unpacked extension folders, not `.crx` packages, and does not implement every
Chrome extension API. Only load extensions you trust. Extension code stays in the browser
profile and is not exposed through Ryu's browser-control tools.

## Agent profiles

On a managed cloud node, each agent browses in its own Chromium profile. Cookies, logins, and
site storage from one agent's session are never available to another agent or to your own
browser tabs.

Each agent signs in to sites separately. An agent stays signed in to a site across browser
restarts until it signs out or the site ends the session.

Each agent also keeps its own:

- **Browsing history.** Pages an agent visits are not added to your History or to another
  agent's.
- **Site permissions.** An agent's profile never prompts. Camera, microphone, location,
  notification, and clipboard requests are blocked unless that agent's own profile has the
  permission saved. Permissions you save in your browser never apply to an agent.
- **Downloads folder.** Files an agent downloads are saved in that agent's own folder, not your
  download location.

Your own browser's history, site permissions, and download settings are unchanged.

### Agent network access

Each agent's browser traffic goes through its own network guard, separate from your browser's.
Local and private network addresses are always blocked.

When you limit an agent to a list of sites (**Allowed sites** on the agent editor's **Advanced**
tab), that agent's browser can reach only those hosts.
An entry is either one host, such as `example.com`, or every subdomain of a domain, such as
`*.example.com`. Requests to any other host fail before they leave the browser. Other agents
and your own browser are not affected. A shorter list applies right away. A longer list
applies after the agent's browser session restarts, for example after Browser stops when idle.

To keep agent traffic behind the guard:

- WebRTC in agent tabs (calls, screen sharing, peer connections) never sends traffic around
  the guard.
- Browser does not use DNS over HTTPS. Names are resolved where the guard checks them.
- If Browser is started with a command-line option that changes or bypasses its proxy or name
  resolution, agent sessions do not open.

### Watching an agent's browser

Agent profiles run in hidden windows. To see what an agent is doing, open the Desktop Browser
dock and choose **Agents**. The list shows every agent whose browser session is open and that
agent's tabs. Pick a tab to watch it live.

- The view is read-only. Nothing you do in it reaches the agent's page.
- Agents can't open this view, so one agent never sees another agent's pages.
- Opening the view doesn't start a browser session for an agent. An agent appears once it has
  used the browser.
- The picture updates while you watch and stops when you pick another tab, choose **Agents**
  again, or hide the dock. Up to four agent tabs can be watched at once.
- Turning off **Let Ryu control the built-in browser** in Browser settings also turns this
  view off.

### Managing agent profiles

Each agent's profile (its sign-ins, site storage, history, site permissions, and downloads) stays
on the node until you delete it. Through the Browser API, the owner can:

- **List profiles** with `GET /api/ext/@ryu/browser/profiles`: every agent profile on the node,
  its size, how many history entries, site permissions, and downloads it holds, and, when the
  agent's browser session is open, which agent and session it belongs to.
- **Export a profile** with `GET /api/ext/@ryu/browser/profiles/<id>/export`: its history, site
  permissions, download list, and the names, domains, and expiry of its cookies. Cookie values
  and site storage are never exported, because they are live sign-ins.
- **Delete a profile** with `DELETE /api/ext/@ryu/browser/profiles/<id>`: closes the agent's
  session, clears its cookies, site storage, and cache, and removes its history, site
  permissions, and downloads. The agent signs in again the next time it browses.

Agents can't list, export, or delete profiles, including their own.

### Agent browser sessions

An agent's browser session is its open hidden window and tabs. An agent can manage only its own:

- `chromium.list_sessions` returns the agent's open session, its id, and its tabs. The list is
  empty until the agent uses the browser.
- `chromium.close_session` closes the agent's tabs and window. Its profile stays, and its next
  browser call opens a new session with a new id.

Both tools are also available to agents connected over Ryu's hosted MCP endpoint.

### Upgrading from earlier versions

| Upgrading from | What changes once |
| --- | --- |
| Before Browser 0.1.17 | Every agent on a managed cloud node shared one profile. Browser clears that shared profile's cookies and site storage, which signs agents out. Each agent signs in again in its own profile. |
| Before Browser 0.1.18 | Agents also shared one browsing history, site-permission list, and download list. Those entries can't be traced to a single agent, so updating deletes them and each agent starts empty. Files already in the old shared downloads folder stay where they are. |

## Agent accounts

Agents can sign up for and log into websites with their own accounts instead of yours. The
account's password, and any two-factor secret, live in the Ryu vault. The agent never sees,
types, or is told them.

1. **Sign up.** The agent calls `chromium.create_account` with the site and the username or
   email it will register with. Ryu generates a strong password and stores it. The agent then
   fills the sign-up form with `chromium.fill_credential`, naming the account and the form
   field (`username`, `email`, or `password`). Ryu types the value straight into the page.
2. **Two-factor setup.** When the site shows an authenticator setup page, the agent calls
   `chromium.capture_totp` on the QR code or the text setup key (sites usually reveal it behind
   a "can't scan?" link). Ryu reads the secret from the page and stores it.
3. **Log in.** The agent finds the account with `chromium.list_accounts`, fills the username,
   email, and password with `chromium.fill_credential`, and fills the current six-digit code
   with field `totp` when the site asks for it.

```mermaid
sequenceDiagram
  participant A as Agent
  participant R as Ryu
  participant V as Vault
  participant P as Web page
  A->>R: chromium.create_account
  R->>V: Store generated password
  A->>R: chromium.fill_credential
  R->>V: Read secret
  R->>P: Type value into field
  A->>R: chromium.capture_totp
  R->>V: Store two-factor secret
```

Ryu fills credentials only under these rules:

- The page is HTTPS on the account's own host. Subdomains do not match, since they can serve
  other people's content.
- Only the page's top-level document is filled, never an embedded frame.
- A password is typed only into a password field.
- Each agent sees and fills only the accounts it created. Listing accounts returns names and
  addresses, never passwords or two-factor secrets.

### Items you attach to an agent's session

You can also let an agent sign in with one of your own vault items, without giving it the value.
Attach the item under **Attached sign-ins** on the agent editor's **Advanced** tab
([how](/docs/surfaces/desktop/user-guide/agent-attached-sign-ins)); `chromium.list_accounts` then lists it under
`attached` with a handle such as `attached:1`, and the agent fills it with
`chromium.fill_credential`. The same rules apply, plus:

- The item fills only on its own site, and only in the browser session that filled from the set
  first. Closing that session, or a browser restart, ends the agent's use of the set.
- The agent can't create, read, or keep attached items, and they expire when you revoke the set
  or it times out.
- In a session Box an attached item fills only through the login URL you set for it, or anywhere
  on its site if you allowed a Box fill without a login URL (the agent can then capture it).

Reading a QR code needs Chromium's built-in barcode detection, which is not available on every
platform. The text setup key works everywhere.

### Login URLs and fills in a session Box

An account can carry up to four **login URLs**: the `https` pages on its site that its sign-in
form submits to. `chromium.create_account` takes them as `submit_urls`, the agent can replace them
with `chromium.set_account_login_urls`, and you can change them under **Account login URLs** on
the agent editor's **Advanced** tab. Every change is recorded in the vault audit log.

In a session Box the agent fills with `browser.fill_credential` and finds account ids with
`browser.list_credentials` (metadata only). There a password is typed as a single-use
placeholder, and the Box's egress puts the real value in only when the form is submitted to one
of the account's login URLs ([how it works](/docs/standalone/box-network-secrets#browser-credential-fills)).
An account without login URLs is refused in a Box. The same tools work with this app installed:
Ryu maps them to `chromium.fill_credential` and `chromium.list_accounts`.

Own accounts have a limit. The agent picks its own account's site and login URLs, so a fill
protects that password only from hosts the agent does not control: an agent that points an
account at a site it runs can read the password it generated. None of your passwords is involved;
for items you attach, the login URL is yours to set.

## Security keys

A browser on a cloud node, in a virtual machine, or in a Bot's hidden lane has no hardware
security key plugged in. When a site asks for one, Browser relays the request to the security key
connected to your desktop:

1. Your desktop shows the site, whether it wants a sign-in or a registration, and whether the
   request came from your own browser or a Bot.
2. Choose **Use security key** and touch the key, entering its PIN if the key asks for one, or
   choose **Deny**.
3. The key's answer goes back to the page. A denied, cancelled, or unanswered request fails the
   sign-in as if no key were present.

The relay works only when **Allow hardware security key** is on for both the device running the
browser and your desktop (see [Security key relay](/docs/gateway/configuration-settings#security-key-relay)).
Every request asks you first and needs a touch of the key, so an agent cannot use your key without
you. When the setting is off, your own browser tabs use Chromium's built-in security key support
and a Bot's request is refused.

Browser takes the site's origin from the tab's address, never from the page, and accepts only
HTTPS pages (or `localhost`) whose site ID matches that address.

Current limits:

- Only roaming hardware keys (USB FIDO2 keys, plus USB or NFC keys on Windows) are supported. Touch
  ID, Windows Hello, and synced passkeys are not relayed.
- Only top-level pages are relayed, not embedded frames. Passkey autofill in sign-in fields is not
  relayed.
- Browsers inside a session Box are not supported yet.
- Only the macOS and Windows desktop apps can answer relayed requests. The Linux desktop app does
  not reach security keys yet.

### `chromium.create_account` - Create Agent Account

In a session Box the password is only ever submitted to one of these, and an account without any cannot be filled there. |

### `chromium.list_accounts` - List Agent Accounts

List the website accounts you created with chromium.create_account, optionally only those for one site. Use it before logging in to find the account `id` to pass to chromium.fill_credential, and before signing up to avoid creating a duplicate. Returns `{accounts:[{id,site,host,username,email,label,has_password,has_totp,submit_urls,...}],attached:[{handle,site,host,kind,fields,submit_urls,login_url_bound}]}` - metadata only; passwords and 2FA secrets are never returned. `has_totp` tells you whether a login will need chromium.fill_credential with field `totp`. `attached` lists the user's own vault items the user attached to your browser session: fill one with chromium.fill_credential, passing its `handle` (`attached:<n>`) as `account` and one of its `fields`, only on its `host`. You cannot create, list the values of, or keep attached items; they expire when the user revokes them.

Backend: HTTP · Method: GET

| Parameter | Type | Required | Description |
|---|---|---|---|
| `site` | string | no | Optional site URL or host (e.g. "github.com") to filter by. |

### `chromium.set_account_login_urls` - Set Agent Account Login URLs

Replace the login URLs of one of YOUR OWN accounts: the https pages the site's sign-in form POSTs to (e.g. "https://github.com/session"), on the account's host, its www. variant or a subdomain, with no query or fragment, at most four. In a session Box the account's password is only ever submitted to one of these, so set them before logging in there; an empty list clears them. The change is audited. Returns `{account:{id,site,host,...,submit_urls}}` with no secrets. An account created before login URLs existed cannot hold them: create a new account for the site.

Backend: HTTP · Method: PUT

| Parameter | Type | Required | Description |
|---|---|---|---|
| `account` | string | yes | Account id from chromium.create_account or chromium.list_accounts, e.g. "github.com--a1b2c3d4". |
| `submit_urls` | array | yes | The complete new list of login URLs. |

### `chromium.fill_credential` - Fill Agent Credential

Type one field of your vault account into the input a chromium.snapshot_tab `ref` names, replacing what is there - WITHOUT you ever seeing the value. Use it for sign-up and login forms, with your own account or with an item the user attached to your browser session (its `attached:<n>` handle from chromium.list_accounts) instead of chromium.type: field `username` or `email` for the identifier, `password` for the password, and `totp` for the current 6-digit two-factor code (only after chromium.capture_totp enrolled it). Never ask the user for the password and never try to read it back from the page. Ryu refuses when the page is not https, its host is not the account's site, the input is inside an iframe, or (for `password`) the input is not a password field. Returns `{ok,tab,account,field,filled}`; set `submit` to press Enter afterwards.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `account` | string | yes | Account id from chromium.create_account or chromium.list_accounts, e.g. "github.com--a1b2c3d4", or the `handle` of an item the user attached to your session, e.g. "attached:1". |
| `field` | string (one of: username, email, password, totp) | yes | Which credential to fill. `totp` fills the current two-factor code. |
| `ref` | string | yes | Element reference of the input from a prior chromium.snapshot_tab, e.g. "@e3". |
| `submit` | boolean | no | Press Enter after filling (a real key event, so the form submits). |
| `tab_id` | string | no | Tab to act on. Omit for the tab the browser is currently showing. |

### `chromium.capture_totp` - Capture Two-Factor Setup

When a site shows a two-factor (authenticator app) setup page for your account, enroll it in the vault: point `ref` at the QR code image, or at the text setup key (a "can't scan?" or "enter this key manually" link usually reveals it). Ryu reads the secret straight from the page and stores it; you never see it. Then complete the site's verification step with chromium.fill_credential field `totp`, and use the same at every later login. Returns `{ok,tab,account,enrolled}`. A 400 means no setup key was found under `ref`.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `account` | string | yes | Account id from chromium.create_account or chromium.list_accounts. |
| `ref` | string | yes | Element reference of the QR code image or the text setup key, from a prior chromium.snapshot_tab. |
| `tab_id` | string | no | Tab to act on. Omit for the tab the browser is currently showing. |

### `chromium.list_sessions` - List Browser Sessions

List your own open browser session: `{sessions:[{id,agent_id,profile,tabs:[{id,url,title}]}]}`, empty when you have not used the browser since it last closed. The `id` is the browser session the user's attached vault items are pinned to after your first fill from them; it changes when the session is closed or the browser restarts. You never see another agent's session.

Backend: HTTP · Method: GET

_No parameters_ (empty schema).
### `chromium.close_session` - Close Browser Session

Close your own browser session: every tab you have open and its hidden window. Your sign-ins and history stay in your profile, and your next browser tool call opens a new session with a new id, so items the user attached to the old session can no longer be filled. Returns `{ok,closed}`; `closed` is false when you had no open session.

Backend: HTTP · Method: DELETE

_No parameters_ (empty schema).
