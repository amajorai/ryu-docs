## What it does

Run durable autoresearch campaigns that prepare one proposal at a time, execute it in a git-versioned workspace, and keep only metric improvements. Campaigns and attempts live in a restart-safe local database with status, timing, scores, decisions, bounded logs, and stop reasons. The Experiments companion lists every campaign and opens its complete attempt history.

The `ryu-research` binary embeds and materializes its reviewed Python engine payload, so a satellite install does not require a separate Research source checkout.

Each run is isolated in its own process group. The wall-clock budget and peak-memory reading include
child workers, timed-out trees are terminated together, and stdout/stderr are retained in bounded
tails so a verbose experiment cannot exhaust the sidecar before its result is recorded.

Every attempt consumes a one-shot proposal tied to the exact current history. While the history is small, the researcher supplies the hypothesis. Once it exceeds the configured threshold, Research automatically asks Recursive Language Model to analyze that snapshot. Research accepts the result only when it cites the submitted history and includes a successful recursive read. The recorded recommendation becomes the next attempt's hypothesis, so copied ids or unrelated prose cannot bypass the reasoning gate.

## Experiment policy

Each experiment declares whether its metric should be minimized or maximized. It also declares minimum, default, and maximum run times, so a workflow cannot request an unbounded experiment. Optional campaign policies stop on a target score, maximum attempts, patience without improvement, or repeated failures. The database records the selected direction, effective budget, and stop reason for the companion and future audits.

## What it exposes

### Companion surfaces

- **Experiments** (html)

Experiments uses Ryu's shared cards, badges, tables, buttons, empty states, and
semantic theme tokens. It follows the active desktop theme while showing campaign
status, elapsed time, metric direction, stop reason, complete attempt history,
winner decisions, and verified RLM recommendations in one list-and-detail workspace.

### MCP server

- **`research`** - Research - durable autoresearch campaigns over MCP. `next_variant` creates the one-shot proposal required by `run`; it performs recursive analysis automatically when the history is oversized. The engine records every attempt, enforces direction-aware winner selection and budgets, and applies the campaign's stop policy.

## Permissions

**Grants:** `app:http`, `rlm:query`, `mcp:research`

| Level | Description | Implies |
|---|---|---|
| **Can view** | Browse durable campaigns, attempts, scores, winner decisions, and recorded reasoning. |  |
| **Can run experiments** | Create and evaluate local experiment variants. Oversized histories may spend model calls through the Recursive Language Model app. | `research.view` |

## UI it contributes

### chat widget templates

- **Research widget** - Research chat widget metadata is coming soon; no render tool is available yet.

### Hook events

- **Research workspace created** - A fresh git-versioned workspace was initialized for an experiment and its initial commit was created. The autoresearch loop can now read, edit, run, and keep or reset changes. Fires once per `POST /api/research/workspace`, whether the desktop or an agent requested it. The event confirms that a workspace exists; attempts run through the `research.*` MCP tools inside Core and are not reported here. `mutable_files` lists the files the researcher may edit. The payload omits the researcher instructions (`program_md`) because they are a document, not an event signal.
