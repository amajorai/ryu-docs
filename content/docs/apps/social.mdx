## What it does

Outpost is a publishing workspace for your social accounts. Compose once, tailor the post per platform, schedule it, and let the node publish while you are away. Scheduled posts, a retrying publish queue, a unified reply inbox, engagement history, and reusable post templates all live in a local SQLite database owned by the node.

Writing assists and inbox reply drafting use Ryu's shared model/provider picker. The selected lane
travels through the host bridge into Ryu's Gateway path; provider credentials and subscription
entitlements never enter Outpost.

Publishing uses Outpost's provider-neutral router. It can select a direct adapter, Composio, or a
configured Treg connection according to the capability the account needs. For example, a text X
thread can use Treg's `x.post.create` and `x.post.reply` endpoints when Composio does not expose
the matching action. The first Treg slice is text-only: media stays on a provider that explicitly
supports it rather than being silently dropped.

Treg is a Ryu-managed provider. Outpost never asks for a Treg token: the Gateway supplies the
configured provider connection, while eligible calls are charged to the active organization's Ryu
wallet and appear in the organization usage statement with the endpoint and transaction reference.

### Hook events

- **Post scheduled** - A post was queued for a future time, with its per-account fan-out legs written. Fires once per `POST /posts` when the row commits, before any provider is contacted. It does not fire for publish-now, cancellation, rescheduling, or retry operations.
- **Post published** - Every leg of a post finished successfully. Fires once when the last target settles, so a three-account post produces one event with all remote ids and permalinks in `targets`. A post with in-flight or failed legs does not fire this event; a partly failed post raises `post.failed` instead.
- **Post failed or partly failed** - A post settled with at least one leg that did not publish. `status` is `partial` when some accounts succeeded and `failed` when none did; each leg includes its `error`. Fires once after the retry budget is spent, not on each failed attempt. Retrying a failed post can make it settle again, so the same post id can appear twice.
- **Inbox item received** - A new reply, mention, or comment was stored in the inbox. Fires once per item after it is durable, so a refresh that pulls twelve new comments raises twelve events. Deduplication makes a later poll of the same thread silent. Marking an item read or replying to it raises no event.
