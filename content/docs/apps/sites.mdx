## What it does

Create, refine, save and deploy websites with private access, browser-local data, and visitor records backed by Ryu Spaces.

## Published page branding

On the Free baseline, every published page carries a small [Powered by Ryu badge](/docs/billing/powered-by-ryu). Paid subscription plans remove it. The badge is added when the page is served, so it does not change the Site's saved source.

## Shared visitor data

A connected Site can opt in to **Shared visitor data**, records that every permitted
visitor sees together with live updates. It is off by default. Turn it on and choose who
can add records in the
[Sites user guide](/docs/surfaces/desktop/user-guide/sites#shared-visitor-data). The access
rules, revisions, and routes are in the
[Sites API](/docs/standalone/sites-api#shared-visitor-data).

## In-page AI

A connected Site can turn on **AI for visitors** in either of two modes. **Grounded
answers** (the default) answers only from a bound knowledge Space. **General page AI**
lets the page call the Ryu model for summaries, classification, or a chat widget with
`RyuSite.ai.complete({ prompt, system, maxTokens })` or `RyuSite.ai.chat(messages)`.
General calls need visitor sign-in unless you allow anonymous use, always apply your
**Owner AI instructions** before the page's own, and share the Site's daily AI limit.
See the [Sites user guide](/docs/surfaces/desktop/user-guide/sites#in-page-ai).

## Gallery, remix and duplicate

The **Gallery** lists the built-in starters with script-free previews and the
deployed Sites you can remix. A Site is remixable only when you can visit it and its
owner turned on **Allow remixing** (off by default). **Remix** copies the deployed
page into a new private Site you own; owners and editors can **Duplicate** the latest
saved version instead. Only the page, its starter and its data runtime choices are
copied. Sharing, sign-in, AI instructions, knowledge, databases, records, files,
shared data, connections, extensions, domains and analytics stay with the original,
and the copy shows which Site it came from. Each person can start 20 remixes or
duplicates a day. See the
[Sites user guide](/docs/surfaces/desktop/user-guide/sites#gallery-remix-and-duplicate).

## Build Sites from chat

The bundled **Site Builder** agent uses the `sites` tools to list your Sites, create
one from a starter, save generated or edited HTML as a new version, deploy a saved
version, and change who can visit. Ask for something like "build me an incident
dashboard and deploy it" and it works through the same steps you would take in the
Sites app. Sharing with invited people or a workspace needs platform sign-in to be
configured, as it does in the app.

The tools follow the same rules as the app. HTML must be a complete self-contained
document up to 2 MB, every save needs the Site's current revision, and a version
deploys only after its secret scan passes. New Sites stay private until you choose
another audience, and only the owner can change access or deploy a Site's first
version. Saving never changes what visitors see. If a step fails, the agent reports
the error instead of claiming it worked. Changes made from chat appear in the
Sites app after a reload.

On a personal desktop the tools act as you, the node's owner. On a node registered
to an organization, the tools act only for an identity Ryu can verify; when chat
cannot provide one they refuse, and you can use the Sites app instead.

## Reset-calendar account checks

Reset-calendar account checks run from the owner's **Settings** in the Sites Companion.
Enable and save **Owner reset checks**, choose a provider, and confirm **Run account check**.
Reports stay in Ryu. Generated websites and embedded Site views cannot run these checks.

## Site MCP tools

Open a Site's **Extensions** section to configure MCP tools and visitor connections.
Site tools can list, save, or delete records in a named collection, or search the
Site's approved knowledge source. Records retain the same per-visitor permissions
as the website. Tools cannot execute arbitrary code or SQL.

Enable MCP, add tools, and save extensions. Save a new version and deploy it to
publish that exact tool configuration. Draft edits do not change deployed tools.
Unpublishing the Site also takes its MCP endpoint offline. Each client must
connect an account with access to the Site; installation alone does not grant access.
Platform identity and an OAuth issuer must be configured by the operator.

### Show the Site in chat

Enable **Show Site UI in chat** to publish the saved website as a versioned MCP Apps
resource. Supported hosts can show it beside chat or from an app entrypoint. Record
and knowledge operations use the Site's published tools through the app bridge.
Connected apps, uploads and browser sign-in remain on the visitor website; the
embedded view does not borrow the owner's account or browser session.

### Install the Site as a plugin

Choose **Install plugin** to send the generated native manifest to Ryu's plugin
installer. It uses the normal validation and lifecycle permissions. Review and
enable the installed plugin in Plugins, then connect your account. After publishing
new tools, choose **Update installed plugin** to update the existing installation.

## Visitor connections

Visitor connections use specific plugin or MCP tools approved by the operator.
The Site must use connected mode and a workspace-restricted audience. Each visitor
signs in, reviews the connection permissions, and chooses whether to allow access.
Consent is scoped to that visitor and Site. Changes to the approved tool or its
permissions require a new review. Visitors can revoke access independently.
Write calls require explicit confirmation; failures must be checked before retrying.
Background jobs cannot reuse visitor sessions or consent.

### Owner connections

Owners and editors can also add their own connections in **Extensions** › **Owner
connections**. Enter a label, a description visitors see when they review it, the Ryu
tool ID (for example `slack.post_message`), and read or read-and-write access. Each
visitor still signs in, reviews the connection, and runs it with their own connected
account, never the owner's. Changing a connection, or choosing **Ask every visitor to
allow it again**, asks every visitor to review it again. Removing it revokes visitor
permissions. Your operator can turn owner connections off or limit them to specific
tools; connections outside that policy are refused and hidden from visitors. A Site
holds up to 20 owner connections, and each signed-in visitor can make up to 200
connected tool calls per Site per day.

<Callout type="warn">
The runtime supports declarative Site tools, not arbitrary hosted server frameworks.
Public hosting, external identity setup, and provider connections are deployment
prerequisites that an operator configures.
</Callout>

## Data at rest

Sites encrypts what visitors leave behind and who may see a Site, on disk, with a key only this app receives from Ryu: uploaded files and their names, records saved by Sites that keep their records on the node, and each Site's settings including viewer and editor email addresses. Published pages, saved versions, visitor ids, record keys, sizes, and analytics counts stay unencrypted so pages, quotas, and lookups keep working; upload quotas count the original file size. Data saved by an earlier version is encrypted the first time the updated app starts. If the app is updated before Ryu itself, new data stays unencrypted until Ryu delivers its key, and the app's status reports that it is waiting for a Ryu update. A Sites service run on its own uses the key you provide or creates a key file in its data folder; keep that file with the data.

## Errors and retries

The database panel shows the selected Site’s connection and SQL results. Switching Sites clears the previous query and results; delayed responses from the previous selection cannot change the new panel or end its pending request. If a query or connection refresh fails, the panel shows the reason and lets you retry with **Run query** or **Refresh**.

If the project list cannot be read, Sites keeps the error visible and offers **Reload**. It does not present a failed read as an empty account or suggest that your existing sites were deleted.

If a URL name is already in use, the create dialog keeps your draft open, shows the conflict there, and lets you correct the name and retry.
