## What it does

Dashboards provides composable widget boards over monitors, meetings, quests, and other Core surfaces through soft HTTP loopback. The out-of-process `ryu-dashboards` sidecar owns the store, refresh loop, and `/api/dashboards/*` surface. The desktop receives it through the generic ext-proxy `public_mount`.

Core starts the sidecar eagerly so the hardware device-dashboard renderer and nudge loop can reach it before the desktop opens Home. The `dashboard_builder` MCP runnable and hardware render seam connect through `dashboards_client`.

## Managed provider widgets

Composio-backed widgets use Ryu's provider-neutral Core → Gateway bridge. The sidecar sends only the curated action id and widget arguments; Gateway supplies the managed provider credential, executes the call, and records its provider cost against the active organization wallet. Dashboards does not ask for or store a Composio key.

## UI it contributes

### Hook events

- **Dashboard widget broke** - A widget's data source stopped resolving because its endpoint errored, an agent refused, or the monitor or workflow it reads is gone. Fires on the transition into failure, including when a new widget's first resolve fails. A widget that stays broken retries on each interval without emitting again. `source_type` identifies the resolver (`core_endpoint`, `monitor`, `workflow`, `composio`, `http`, or `agent`). Expensive sources refresh only while someone is watching the dashboard, so their failures surface when the board opens.
- **Dashboard widget recovered** - A widget that was failing resolved successfully. Fires only on the transition back to healthy; a widget that never failed does not emit on every refresh.
