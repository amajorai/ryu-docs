## What it does

Recipes record, save, and replay desktop UI action sequences. They use Ghost's RecipeStore and declare
Ghost as a dependency, so the capability graph cannot disable Ghost while a recipe depends on it.

## Permissions

**Grants:** `ghost:record`

| Level | Description | Implies |
|---|---|---|
| **Can view** | Browse saved desktop-automation recipes and the steps each one replays. |  |
| **Can record** | Record and save new recipes, which captures every UI action performed while recording. | `recipes.view` |
| **Can replay** | Replay a saved recipe, which drives this machine's real mouse and keyboard against whatever is on screen. | `recipes.view` |

## UI it contributes

### Hook events

- **Desktop recording finished** - Fires when `POST /api/recipes/record/stop` stops a session and turns the captured action sequence into an editable recipe draft. The draft is not persisted; `save` is a separate call, so a consumer that wants to refine or install it must take it from this payload. Fires once per session, and a session that is never stopped emits nothing. If the draft exceeds Core's event-size cap, it is omitted and `draft_omitted: true` is set. The event still fires, which distinguishes an omitted draft from an empty one.
- **Recipe replay succeeded** - Fires when a recipe finished replaying against the native desktop without erroring. Carries ghost's structured run result (per-step success/timing), which is the only place that detail exists - nothing persists a run record. Fires once per replay, so a recipe run on a schedule fires on every run.
- **Recipe replay failed** - Fires when a replay could not complete: ghost is unreachable, the recipe is missing, or a step's target could not be found on screen. `error` is the same message the caller received. A replay raises either this or `replay.ended`, never both.
