## What it does

Tests (app ID `@ryu/checks`) plans, runs, and keeps evidence for UI and API checks against a
live target, all on your Ryu node. Its command-line tool is `ryu-checks`.

## Verification loop

Tests keeps the local loop in one Companion surface.

1. Describe a target with a URL, product brief, optional acceptance/reference context,
   or an attached Markdown/JSON/YAML/text source.
2. Generate or edit observable UI/API cases with the optional Ryu model lane.
3. Explore the live target to map feature signals.
4. Run one case, a project, or an explicitly assigned collection and retain a verdict,
   coverage, response timing, bounded text evidence, generated source, and one failure
   bundle per failing case. UI cases also open the target in the Ryu Browser and retain a
   real screenshot and accessibility DOM snapshot.
5. Inspect the root-cause bucket, failed step, suggested fix, and rerun the same plan.

The All Tests view narrows projects by UI/API type, project text, and the latest run
status: Passed, Needs attention, Running, or Ready to run.

When a project selects a granted Ryu agent lane, the app retains the agent transcript
and any explicitly declared artifacts separately from the deterministic run result.
The agent is asked to use the browser capability when it is available and must not
claim screenshots or DOM snapshots it did not capture.

## Evidence boundary

Tests requires the Browser app's `browser.control` capability and the
`browser:control` grant. Enabling Tests also enables the Browser app, and Tests can't
be enabled while the `browser:control` grant is denied. For each
UI case it opens the target URL in a new Browser tab, waits for the rendered page to
settle, and keeps a PNG screenshot and DOM snapshot on the node. Signals and response
assertions match against both the served HTML and the rendered page. Evidence from
these runs is labeled `live-browser`. In the Test Report, select **View screenshot and
DOM snapshot** on an evidence record or failure bundle to open the retained files.

If the browser can't capture the page, for example because Browser control is off or
the browser refused the target, the case still runs over HTTP. It is then labeled
`live-http-fallback` and shows the reason, and no screenshot is claimed. The Browser
app never opens localhost, loopback, or private-network addresses, so UI cases against
an explicit localhost target always fall back this way. Tests closes each evidence tab
after capture, including when the capture fails. Screenshots and DOM snapshots are kept
for the newest 50 runs, up to 512 MiB in total; older evidence files are deleted and
their runs no longer claim a screenshot. Files from a run that stops before it is saved
are deleted as well.

The HTTP lane runs every API case, labeled `live-http`, and fetches every UI case before
its browser capture. It accepts http and https targets, does not follow redirects,
limits response bodies, blocks private and link-local destinations except an explicit
localhost target, and stores a clipped text preview instead of the raw response.

A run's own label summarizes its cases: `live-browser` when every case captured browser
evidence, `mixed` when only some did, `live-http-fallback` when none did and a UI case
fell back, and `live-http` for API-only runs.

API cases can select an HTTP method, request path, expected status, bounded response assertions, and optional response-time
budgets. Generated source includes the saved Playwright case and a Python equivalent for
API-oriented workflows. UI/API smoke coverage is node-local; hosted browser grids,
real-device clouds, and visual-regression services remain external capabilities.

Collections and schedules are node-local definitions. Run now executes an explicitly
assigned collection immediately; an active schedule is executed by the local sidecar
while the node is available. Its next run and last result are retained without claiming
that a cloud worker or external CI system is running after the node is unavailable.

## Authoring, healing, and history

Cases can be refined from their detail view: update the description, steps, API
method/path/status/assertions, or context, then rerun it to attach fresh evidence.
Agent-assisted single-case refinement is not available in the Companion; use Edit
plan for these manual updates. Project-level agent execution remains a separate,
optional lane.

If Save plan fails, the Companion displays the reason and keeps your edited criteria
open. Retry Save plan to submit the same draft; the editor closes only after the
save succeeds. Saving a plan does not create execution evidence.

Cases belong to the project created by the planning flow. The Companion does not
currently add newly generated cases to an existing project.

Each run remains in the project's retained history; a new verdict does not overwrite
an earlier run. Failure bundles expose the failed step, root-cause bucket, suggested
fix, and bounded source preview. Heal plan adds an explicit live-observation checkpoint
to the case and marks the bundle healed as a plan change, but it does not claim the
product is fixed until a rerun passes.

## CLI, CI, and MCP

The installed sidecar supports the same persisted contract outside the Companion.

```sh
ryu-checks list
ryu-checks run --project-id PROJECT_ID --trigger ci
ryu-checks analytics
```

The run command emits JSON and exits non-zero when a case needs attention, so a CI job
can treat it as a merge gate. `ryu-checks mcp` exposes the node-local `run_project` and
`analytics` tools through the manifest's `checks` MCP server.

## What needs an external service

Ryu owns planning, context ingestion, editable cases, live exploration, deterministic
UI/API verification, case/project/collection execution, optional agent execution,
retained evidence and agent transcripts, healing, history, collections, schedules,
analytics, CLI/CI, and MCP access. Hosted browser screenshots/video, cross-browser or
real-device matrices, OAuth/GitHub authorization, hosted grid workers, and
provider-backed data fixtures require a granted Ryu agent/browser capability or an
external CI integration. Tests never turns an unavailable external capability into a
passing artifact.

## What it exposes

### Tools

### `checks.run_project` - Run Checks Project

Run one persisted Checks project against its live target and return the retained verdict, evidence level, and failure bundles. Use this from an agent or CI bridge when the Companion is not the right entry point.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `project_id` | string | yes | Stable Checks project id. |
| `trigger` | string | no | Run provenance such as agent, ci, or manual. |

### `checks.analytics` - Checks Analytics

Read node-local Checks totals, coverage, and failure buckets for release or agent summaries.

Backend: HTTP · Method: GET

_No parameters_ (empty schema).

- **`checks`** - Run persisted Checks projects or read node-local analytics from an IDE or coding agent. The MCP server shares the Companion's sidecar store and evidence contract.

## Permissions

Recurring checks require both plan management and permission to run live checks.
Tests verifies execution permission when a schedule is created or enabled and
again before each scheduled run. Removing run permission or organization or team
access stops subsequent runs. Schedules saved by an older version without execution authorization must be
enabled again by an authorized user. Local owner schedules
continue to use the personal node's local execution policy.

The app also requests deferred authorization from the host. Approve that capability
when updating an existing installation to keep managed schedules running.

**Grants:** `app:http`, `tool:http-egress:127.0.0.1`, `core:list_agents`, `hook:side-model`, `hook:run-agent`, `mcp:checks`, `authorization:defer`, `browser:control`

| Level | Description | Implies |
|---|---|---|
| **Can view verification evidence** | Read projects, plans, runs, evidence, collections, schedules, and analytics. |  |
| **Can run live checks** | Explore a target and execute node-local verification runs against it. | `checks.view` |
| **Can manage verification plans** | Create and remove projects, collections, and schedules. | `checks.view` |

## Data at rest

Tests encrypts its saved projects, cases, runs and failure bundles, and every retained screenshot and DOM snapshot, with a key only this app receives from Ryu. Data saved by an earlier version is encrypted when the updated app starts; older evidence files are encrypted in the background. If the app is updated before Ryu itself, it keeps working unencrypted until Ryu delivers its key, and its health status says it is waiting for a Ryu update. The `ryu-checks mcp` server and the `ryu-checks` command line reach encrypted data through the running Tests app; when the app is not running they can use only data that was never encrypted.
