## What it does

Answer questions about a corpus far larger than any model's context window - without putting it in a prompt. The usual options all degrade: truncate and you lose the answer, embed-and-retrieve and you get fragments without their argument, buy a bigger window and attention over the middle of it thins out anyway. This app does the other thing. Your documents are held here as a variable. A root model plans over an outline of them - chunk ids, sources, line spans, headings - and reaches the text only through operators that summarise before returning: `grep` to locate, `map` to run a cheap model over the chunks that matter in parallel and fold the answers back, `recurse` to give a sub-question its own plan over a subset. The root model never sees the corpus, so its context stays roughly the same size whether you point it at 40 KB or 40 MB, and the answer does not get worse as the input gets bigger. Every answer carries `path:line` citations read back out of the chunks it rests on, and every run keeps a full trace - each operator, each sub-call, what it cost - that you can open and replay. Depth, step, call and wall-clock budgets are hard: a run that hits one says so and returns what it had, rather than quietly shortening the answer. Agents get the same engine as tools, and `grep` and `peek` need no model at all, so a workflow can branch on a deterministic search of a 40 MB corpus. Capability callers may query an existing context or submit bounded inline documents that are persisted as a context and analyzed in the same recursive run.

### MCP server

MCP (Model Context Protocol) is a standard way for an AI host to find and call tools. An MCP server provides those tools.

- **`rlm`** - Read more than fits in your context. `ask` takes paths and a question and returns an answer with `path:line` citations - the files never enter this conversation, so reach for it instead of reading a large directory yourself. `load` builds a reusable context, `query` asks follow-up questions against one, and `grep` and `peek` search and read it with NO model call at all, which makes them safe to branch a workflow on.

## UI it contributes

### chat widget templates

- **Recursive Language Model widget** - Open Recursive Language Model data in a host-rendered chat widget.

### Sidebar sections

- **Contexts**

### Composer controls

- **Deep read the corpus** - After each answer, ask the same question of the selected context and append what the documents actually say, with citations. Use it when the answer should come from your files rather than from the model. (type: toggle)

### Settings tabs

- **Recursive Language Model** (fields: Context to read (text), Planner model (model_picker), Reader model (model_picker))

### Turn hooks

- **rlm.deep-read** (on: `post_assistant_turn`)

### Hook events

- **A corpus-grounded answer was produced** - A deep read finished and returned an answer read out of the loaded context, with at least one citation. Fires once per read, not once per citation. A read that could not run - no context selected, no reader tool available, budget exhausted before anything was read - does NOT fire this, because routing those to the same place trains people to ignore it.

- **Delete all loaded contexts**
