## What it does

Agent Inboxes - email as a service for agents. Runs the out-of-process ryu-mail sidecar; Core proxies /api/mail/* to it. Its sandboxed companion and developer clients cover inboxes, messages, threads, attachments, drafts, scheduling, labels, webhooks, delivery events, lists, pods, and domains through the mail:crud bridge/API.

### Hook events

- **Email received** - An inbound message was accepted and stored. Fires once per accepted POST to the inbound webhook, after the per-inbox HMAC verified and the row was written. A forwarder retry with the same Message-ID or identical raw bytes is deduplicated and does not fire this again. The payload is metadata only; fetch the body with GET /api/mail/messages/:id.
- **Email sent** - An outbound message was handed to the SMTP transport and recorded against the sending inbox. Fires once per successful send; a send that the transport rejects fires nothing. Hand-off is not delivery - providerMessageId is the relay's id, and a later bounce is not visible here.

## Safe retries for sends

Mail send API callers can provide an `Idempotency-Key` header of 1 to 256 printable ASCII characters, with at least one non-space character. Reusing a completed key with the same inbox and message returns its recorded response without another transport handoff, even if the transport is subsequently unconfigured. Reusing a key with a different inbox or message returns a conflict.

Local preflight refusals, such as an unconfigured transport or invalid recipient address, do not consume a retry key. Correct the configuration or input before retrying. A request still in progress or with an unresolved transport outcome also returns a conflict. If a transport acknowledgement cannot be recorded, reconcile the existing request before sending again; creating a new key can send another message. Unresolved keys are retained across restarts rather than automatically retried. Older retry records that cannot establish an inbox-bound outcome require reconciliation. Sending without a key preserves the normal send behavior.

These responses describe transport acknowledgement and local records, not confirmed delivery to a recipient’s inbox.

## Data at rest

Mail encrypts message and draft content on disk with a key only this app receives from Ryu: subjects, bodies, previews, headers, sender and recipient addresses, draft attachments, attachment file names, event payloads, and saved send responses. Attachments and raw messages are stored as encrypted files. Inbox names and addresses, allow and block lists, labels, read state, and timestamps stay unencrypted so lists, threads, and filters keep working; search still finds words in decrypted messages. Mail saved by an earlier version is encrypted the first time the updated app starts, and older attachment files are encrypted in the background.

If the app is updated before Ryu itself, new mail stays unencrypted until Ryu delivers its key, and the app's health status says it is waiting for a Ryu update. A self-hosted Mail service without Ryu uses the key you provide or creates its own key file in its data folder; keep that file with the data.
