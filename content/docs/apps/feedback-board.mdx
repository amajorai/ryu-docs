Feedback Board gives a product team a public place for requests and a private
Ryu workspace for deciding what happens next.

## The feedback loop

1. Share a public board with your customers or community.
2. Visitors submit ideas, vote on existing requests, and add context in
   comments.
3. The Ryu companion groups, tags, summarizes, and prioritizes the signal.
4. Move a request through the roadmap and optionally create a brief in Ryu
   Spaces.
5. Use a Ryu workflow to prepare or build the work, with Blueprint approval
   when the board is configured to require it.
6. Publish a changelog update that links back to the requests that shaped it.

## Public board

The public board includes:

- Search and sorting by demand, recency, or activity.
- Guest submissions with configurable moderation.
- Upvotes and comments.
- Request detail pages with public status.
- A public roadmap and changelog.

Public visitors never see internal notes, AI prompts, Space documents, agent
context, or workflow credentials. A board can require an operator to approve
new requests and comments before they appear publicly.

The public board and private companion follow Ryu's semantic theme tokens for
color, typography, focus states, controls, and radius. When mounted in Ryu, the
companion tracks the host's live theme; the board accent starts with Ryu blue
and remains configurable from board settings.

## Ryu workspace

The private companion includes:

- **Overview** — demand, requests needing review, roadmap activity, and build
  runs.
- **Requests** — filters, tags, duplicate suggestions, impact scores, private
  notes, and request history.
- **Roadmap** — the same statuses that are projected onto the public board.
- **Changelog** — drafts and releases linked to shipped requests.
- **Automation** — workspace defaults and per-request build behavior.
- **Settings** — public description and moderation behavior.

The request detail includes a build path:

```text
heard → understood → planned → building → shipped
```

Each step represents persisted request, Space, Blueprint, workflow, or status
state. It is not a decorative progress indicator.

## Automation modes

Automation is configurable at the workspace, board, and request level. A
request override wins over a board setting, which wins over the workspace
default.

| Mode | What Ryu does |
|---|---|
| **Manual** | Waits for an operator to choose every action. |
| **Assist** | Suggests tags, summaries, duplicates, and impact. |
| **Prepare** | Creates a product brief and acceptance criteria in Spaces. |
| **Build with review** | Runs a workflow, publishes a Blueprint plan, and pauses before code changes. |
| **Autopilot** | Runs the selected workflow within its configured limits and approval gates. |

Autopilot is opt-in and visibly labelled. Every run keeps its mode, agent or
workflow, plan id, progress, result, and failure state. A failed or unavailable
model/workflow does not become a fake success or a fabricated shipped update.

## Data and current boundary

Public requests, votes, comments, board configuration, roadmap projections, and
changelog releases are stored by the Feedback Board app on the current Ryu
node. Ryu Spaces stores the product briefs, acceptance criteria, research
context, and build artifacts created by the companion.

This release is node-local. It does not include custom domains, hosted
multi-tenant provisioning, SSO, email delivery, weekly digests, or integrations
with external support and project-management tools. Those are separate hosted
and delivery concerns, not silently implied by the local board.
