## What it does

Automated Reasoning checks an answer against a written policy with a solver. Give it a document such as an HR handbook, refund policy, or underwriting rule sheet. It drafts typed variables and rules that you can read and edit in plain language.

The solver translates a question and answer into logic, then evaluates them with finite-domain enumeration, Fourier–Motzkin elimination for linear rational arithmetic, and branch-and-bound for integers. The verdict has four states: `valid` means the policy proves the answer; `invalid` includes a concrete counterexample; `satisfiable` means the policy does not settle the question; and `impossible` means the policy contradicts itself.

Every finding names the smallest set of rules that decided it, the facts assumed by the answer, and the facts that would change the result. Exact rational arithmetic prevents a rule such as `0.1 + 0.2` from failing because of floating-point rounding. Model calls happen only at the two language edges, so the verdict can be reproduced offline from the formulas.

## What it exposes

### Companion surfaces

- **Automated Reasoning** (html)

The desktop host renders the **Policies** sidebar section from the app's policy feed.
Selecting a policy opens `/reasoning/<id>` with that policy focused, while the
companion remains focused on authoring and checking the selected policy.

### Capabilities

- **reasoning.check** - capability `reasoning.check`
  - Grant: `reasoning:check`

### MCP server

- **`reasoning`** - Automated reasoning checks as tools. `solve` decides claims written in the policy language without a model call, `check` does the same for prose, `policies` lists the vocabulary a policy declares, and `analyze` reports whether the rules are consistent. `solve` is deterministic, so a workflow branch takes the same path for the same inputs.

## Permissions

**Grants:** `reasoning:check`, `hook:side-model`, `hook:run-agent`, `mcp:reasoning`

| Level | Description | Implies |
|---|---|---|
| **Can view** | See the reasoning policies on this node and the findings of past checks. |  |
| **Can edit** | Create and change policies. This decides what every check on this node counts as correct, so it is the level that changes outcomes. | `reasoning.view` |

## UI it contributes

### Composer controls

- **Check against policy** - After each answer, check it against the selected reasoning policy and report anything the policy contradicts. (type: toggle)

### Settings tabs

- **Automated Reasoning** (fields: Policy to check against (text), Extraction model (model_picker), Policy drafting model (model_picker))

### Turn hooks

- **reasoning.check** (on: `post_assistant_turn`)

### Hook events

- **An answer contradicted the policy** - A check finished with at least one `invalid` finding. The policy proves the answer wrong and includes a counterexample. Fires once per check, not once per finding. A `satisfiable` result means the policy does not settle the answer; `impossible` means the policy contradicts itself. Neither result fires this event.
