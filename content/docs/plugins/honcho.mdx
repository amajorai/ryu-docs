## What it does

Give the swappable `memory` layer a provider that MODELS the user instead of only storing rows, via Honcho (https://honcho.dev) - the Plastic Labs identity layer Hermes uses for exactly this. Honcho watches the messages you hand it and derives a per-peer REPRESENTATION; its Dialectic endpoint (`POST /v3/workspaces/&#123;workspace_id&#125;/peers/&#123;peer_id&#125;/chat`) then answers a natural-language question about that peer with its own synthesis. That is what the canonical `memory.context` verb has always promised and no shipped provider served, so this is the first plugin to make the kernel's `context` bridge (`memory.provider-context`) do anything at all. Honcho here serves TWO verbs: `memory.context` (the Dialectic synthesis) and `memory.search` (`POST .../peers/&#123;peer_id&#125;/search`, documented as "Search a Peer's messages" - conversation text, not the conclusions Honcho derives from it, which matters because the `prefetch` bridge is on by default and will start injecting message excerpts each turn). It also binds the two WRITE verbs, `memory.sync` and `memory.store`, through an adapter. Honcho's only documented write is `POST /v3/workspaces/&#123;workspace_id&#125;/sessions/&#123;session_id&#125;/messages`, whose `messages[]` items each require a `peer_id` - a NESTED position the declarative `arg_template` cannot reach, because a template substitutes only from CALLER arguments and never sees a resolved `pref:`. That is why both verbs went unbound and why `memory.mirror-builtin` (default ON) was inert. An adapter receives those `pref:` values already resolved, so the per-install peer lands inside `messages[]` without hardcoding one bucket for every install. The session and both peers are caller-named and created on first write, so nothing has to be set up by hand; Ryu's own replies are written as a SEPARATE peer, since attributing an assistant turn to your peer would poison the representation Honcho derives about you. `memory.forget` stays unbound: Honcho documents no message-delete endpoint, which no adapter can invent. The built-in store's own `memorystore.save` tool and this node's per-turn memory write are kernel and untouched. Every call is scoped to one workspace and one peer, both set per install in the settings tab - a hardcoded pair would put every install in one shared bucket. Requires a BYOK Honcho API key.

## What it exposes

### Tools

### `honcho.chat` - Honcho Dialectic

Ask Honcho's Dialectic endpoint a natural-language question about one peer and get back ITS synthesis - the reasoning Honcho has derived from that peer's messages and conclusions, not a list of stored rows. Answers `&#123;"content": "…"&#125;`. `reasoning_level` defaults to `minimal` here rather than Honcho's own `low`, because the kernel context bridge abandons a memory provider after 4 seconds and a deeper reasoning pass routinely costs more than that; raise it in the Honcho settings tab if you call this tool directly and can wait. Streaming is deliberately not exposed - the endpoint answers `text/event-stream` when `stream` is true, which is not a JSON tool result. Requires RYU_HONCHO_API_KEY.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `workspace_id` | string | yes | The Honcho workspace to query. Filled automatically from the Honcho settings tab when this runs as the `memory` layer; pass your workspace id from https://app.honcho.dev if you call this tool directly. |
| `peer_id` | string | yes | The peer whose representation to query. Filled automatically from the Honcho settings tab when this runs as the `memory` layer. |
| `query` | string | yes | The natural-language question to put to the peer's representation. |
| `session_id` | string | no | Optional session id to scope the representation to one conversation. |
| `target` | string | no | Optional other peer to get the representation FOR, from this peer's perspective. |
| `reasoning_level` | string (one of: minimal, low, medium, high, max) | no | How much reasoning Honcho applies before answering. More reasoning is slower; Honcho's own default is `low`. |

### `honcho.search` - Honcho Search

Search one peer's MESSAGES in a Honcho workspace and return the matching messages. This searches conversation text that was handed to Honcho, not the conclusions Honcho derived from it - use honcho.chat for the derived view. Answers a bare JSON array of messages. Requires RYU_HONCHO_API_KEY.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `workspace_id` | string | yes | The Honcho workspace to search. Filled automatically from the Honcho settings tab when this runs as the `memory` layer. |
| `peer_id` | string | yes | The peer whose messages to search. Filled automatically from the Honcho settings tab when this runs as the `memory` layer. |
| `query` | string | yes | Search query. |
| `limit` | integer | no | Number of messages to return (Honcho default 10). |

### `honcho.messages` - Honcho Add Messages

Add messages to a Honcho session. Honcho derives each peer's representation from the messages you hand it, so this is the WRITE side of the memory layer. Answers a 201 array of the created messages. The session and every named peer must exist first (see honcho.session_upsert / honcho.peer_upsert). Requires RYU_HONCHO_API_KEY.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `workspace_id` | string | yes | The Honcho workspace to write to. Filled automatically from the Honcho settings tab when this runs as the `memory` layer. |
| `session_id` | string | yes | The session to append to. Filled automatically when this runs as the `memory` layer. |
| `messages` | array | yes | The messages to add. Each item needs a `content` and the `peer_id` that produced it. |

### `honcho.session_upsert` - Honcho Get or Create Session

Get a Honcho session by id, or create it if it does not exist. The id is CHOSEN BY THE CALLER, which is what lets this node use a stable session without the user having to create one first. Requires RYU_HONCHO_API_KEY.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `workspace_id` | string | yes | The Honcho workspace the session belongs to. |
| `id` | string | yes | The session id to get or create. |

### `honcho.peer_upsert` - Honcho Get or Create Peer

Get a Honcho peer by id, or create it if it does not exist. Ryu writes the user's turns as one peer and its own replies as another, and creating them explicitly is why writing a turn never depends on a peer having been set up by hand. Requires RYU_HONCHO_API_KEY.

Backend: HTTP · Method: POST

| Parameter | Type | Required | Description |
|---|---|---|---|
| `workspace_id` | string | yes | The Honcho workspace the peer belongs to. |
| `id` | string | yes | The peer id to get or create. Honcho allows letters, digits, underscore and hyphen. |

### Capabilities

- **Memory** - capability `memory`
  - Verbs:
    - `memory.context` -> `honcho.chat`
    - `memory.search` -> `honcho.search`
    - `memory.sync` -> `honcho.messages`
    - `memory.store` -> `honcho.messages`
