## What it does

Adds bash_background / bash_output / bash_kill to the managed Pi agent, so a long-running command does not hold the turn open.

Starting, polling, and manually stopping a shell appear in chat as tool activity. If a shell exits on its own, fails to start, or reaches its lifetime limit, the plugin sends the lifecycle event back to the parent agent and starts a follow-up turn. The agent collects the final output with `bash_output`, so the completion and its output remain visible even when they happen between turns.

### Surviving a restart

Background shells are tracked in a durable per-project ledger
(`~/.ryu/pi-agent/sessions/<encoded-cwd>/ryu-background-shells.json`). On the first `context` event
of a new process, shells recorded as `running` under a different pid are marked `stopped` (orphaned —
the process died with its parent), and the model is told "Session restarted — re-verifying state…" so
it checks whether a port or file is still actually live instead of assuming the shell is still up.
`bash_output` / `bash_kill` on a stale id read the ledger and report the shell's story rather than a
bare "unknown id". The ledger never carries output — that died with the process.

## Pinned summary

While a shell is running, the desktop's pinned summary includes a **Background processes** section.
Each row shows the command, working directory, and elapsed time. Hover a row (or focus it with the
keyboard) to reveal **Stop**. Stopping from the panel sends a cooperative request back to this
extension, which uses the same SIGTERM/SIGKILL cleanup path as `bash_kill`; the row disappears after
the next lifecycle snapshot confirms that the child has ended.

The section is backed by Core's generic background-process registry, so it can also be consumed by
approved companion apps and plugins. A process owner publishes snapshots and polls its own stop
requests; Core never signals an arbitrary PID.
