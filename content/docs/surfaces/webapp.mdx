The browser app currently requires a Ryu account that has cleared the waitlist. The former
**Try Ryu without an account** path is temporarily disabled while waitlist access is active, so a
browser cannot bypass the queue with an anonymous session. Choose **Get Started** to complete the
normal account sign-in flow.

The Web app is a browser-hosted wrapper around the shared Desktop shell contract. It reuses the
same Marketplace contribution vocabulary and Core-backed routes, but its browser host omits native
Desktop windows, tray behavior, filesystem launchers, and updater controls. Marketplace support on
Web therefore means “this package can render through the shared shell here,” not “this package owns
the Web shell.”

## Choose where the work runs

- **Device path.** After account approval, the browser prefers a reachable local Core when one is
  already running and otherwise uses the hosted browser experience.
- **Cloud path.** Hosted access remains subject to the account's waitlist approval and any applicable
  plan or usage limits.
- **Phone or tablet.** Ryu continues with the hosted browser experience because mobile browsers
  cannot install and manage a device runtime.

The browser never displays the session bearer. It stores the account session in its local auth vault
and uses it only for authenticated requests. Signing out removes the browser session.

## What the browser app adds

The browser app owns browser navigation and browser-safe actions. After approval it can prefer a
reachable local Core or continue with Ryu Cloud, but it cannot load native modules or run the mobile
`llama.rn` path.

| Capability | Browser behavior |
|---|---|
| Account access | Normal account sign-in followed by the server-authoritative waitlist gate |
| Local setup | Prefer a reachable local Core after the account is approved |
| Cloud access | Use the hosted browser experience after approval |
| Browser actions | Use browser navigation, **Open in new tab**, reload, copy, fullscreen, and external links |
| Native boundaries | Hide Desktop windows, tray settings, native updater, local launchers, and OS-only controls |

For browser-local model execution and in-page tools, use the [Browser extension](/docs/browser-extension).

## Ask Ryu on the public site

The public site and these docs include an **Ask Ryu** widget as a small, working example of a
visitor-facing AI surface. It has two explicit runtime choices:

- **This browser** downloads the reviewed `SmolLM2 135M` ONNX artifact once, caches it in the
  browser, and runs the answer with Transformers.js using WebGPU or WASM. No account is required,
  and the question stays in the tab.
- **My local server** connects directly to a running Ryu Core server after you provide its address and
  server token. The browser sends the question to that server's `/api/chat/stream` endpoint; the Ryu
  website does not proxy or store the token, and visitor turns use `persist: false`.

Choose **Connect a local server** from the widget or open the dedicated
[`/connect` route](https://ryuhq.com/connect). Loopback addresses are the default. A LAN or remote
address requires an explicit trust confirmation, and Core must allow the site's origin through its
CORS configuration. This is a browser bridge, not a silent account registration or a replacement
for Core's server authentication.

The widget grounds public answers against a small, auditable documentation index and links to the
source page. It is intentionally separate from the authenticated browser app: a visitor can try
the local model without creating a cloud session, then choose a running server when they want Ryu's
configured agent and Gateway policy.

## Browser extension

The browser extension is a separate browser host. It reuses the web and Desktop chat patterns, then
adds browser-owned entry points and local inference. See [Browser extension](/docs/browser-extension)
for its model runtime and permission boundaries.

## App-like navigation

Ryu's browser app uses app-style navigation for public pages. Links stay in the current browser
session, reusable route UI can arrive before the click, and pages with live data show a matching
loading shell while that data streams in. This keeps navigation responsive without moving the
page's server-rendered content into the browser.

The Webapp, its phone-sized layout, and the browser extension dashboard align their top navigation
to the browser viewport. They do not reserve the macOS traffic-light gutter or the Windows/Linux
caption-button gutter used by Ryu's native Desktop window.

The shared interface also follows the host's capabilities. Browser surfaces keep browser-valid
actions such as **Open in new tab**, browser fullscreen, reload, copy, and external links. They do
not show Desktop-only actions such as **Open in new window**, launch-at-login and tray settings,
the native app updater, local editor or file-manager launchers, native backup/restore controls, or
the always-on-top media window. Right-click keeps the browser's normal context menu instead of the
Desktop app menu.

The experience applies to the blog, help center, changelog, marketplace, and other content
surfaces. Cached route UI can be reused across visits, while request-specific data still loads for
the destination. Search, filters, sign-in, and downloads keep their existing behavior.

## Signed-in workspace

After sign-in, the Web app opens at the workspace overview with a two-row portal header. The first
row places the account controls before the active organization with a `/` separator and omits the
separate Ryu mark. Inbox and Download remain aligned on the right. The second row holds the primary
workspace routes in one place: **Overview**, **Apps**, **Servers**, and **Marketplace**. In an
organization view, that row changes to the organization tabs with a **Dashboard** back link; the
Ryu-level admin view uses the same pattern with a compact **Admin areas** menu, so the full admin
section list remains available without clipping the desktop header. Its landing page keeps the
workspace areas grouped into four focused panels rather than repeating every route as a separate
tile.

Admin pages use the inverse header treatment and place the routed content inside one full-width
bordered page card with a rounded top edge. The card begins directly below the header and fills the
available page height. The admin landing groups its links into four dashboard areas — review and
trust, publishing and community, programs and growth, and business and platform — so the home page
stays focused while every section remains one click away.

The overview keeps a simple count row for servers, organizations, and teams, followed by a getting-
started checklist, a desktop-app card, an Explore card, and plan actions. Certifications remain
available from the overview's Explore card and the public Academy navigation. Account and
organization actions remain available from the account and organization menus.

## Landing page

The public landing page opens with the two-line headline **We deploy and run AI agents safely in the
cloud**. Its final word gets a color sweep. The page then shows **Download** and
**Documentation** links, a workflow preview with several use cases, the Ryu surface selector, and
a concise explanation of how Apps, Bot, and Console fit together.

The shared footer closes the page with an animated Aurora gradient behind the cursor-aware outline
Ryu mark.

On desktop, Products and Resources share one hover-activated surface, while Marketplace remains a
direct top-level link.

The interactive preview uses the same Bot-mode reading as the desktop app: **Agents** are the
primary sidebar tab, **Sessions** are secondary, and each agent row shows its latest message.
Switching use cases morphs the running preview into the selected workflow at its current phase.
