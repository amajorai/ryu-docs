This page summarizes the user-visible parity between the `ryu` terminal client and the desktop
application.

## The principle

The CLI reaches the **same Core** the desktop uses, so parity is overwhelmingly a matter
of surfacing existing Core endpoints, not new backend work. The goal is **capability parity, not
modality parity**: a terminal cannot render a React Flow canvas or a screen-capture timeline, so some
desktop surfaces are deliberately out of scope rather than missing. Those are marked N/A in the TUI.

The same rule applies to native bridges: the CLI/TUI can consume Core notifications, app contributions,
and declarative Library views, but it does not claim phone-only haptics, Live Activities, Dynamic Island,
or browser permission APIs. Apps should feature-detect the host and keep a portable list/table fallback.

Two design notes shape the layout. First, extend, do not rewrite: every new terminal surface follows
the shared client state, keyboard, rendering, and Core-service seams. Second, the command palette
(`Ctrl+P`) is the information architecture: a narrow sidebar cannot hold every tab, so a fuzzy
palette is the primary jump surface (the Cmd+K analog) and the sidebar stays a short grouped list.

<Callout type="info">
The matrix is a product contract: ✅ means the surface is available, ⬜ means it is planned, and
🚫 means the modality does not have a safe terminal equivalent. Runtime availability still depends
on the active node, permissions, and connected providers.
</Callout>

## Matrix

Legend: ✅ built, 🟡 in progress, ⬜ planned, 🚫 N/A in TUI (with reason).

### Chat

| Feature | Status | Notes |
|---|---|---|
| Multi-turn streaming chat | ✅ | `POST /api/chat/stream`, `conversation_id` minted per chat |
| Agent picker (`Ctrl+A`) | ✅ | `GET /api/agents` |
| Tool-call loop surfacing | ✅ | tool-input/output frames rendered inline |
| `/btw` side question | ✅ | `POST /api/btw`, ephemeral overlay |
| `/goal` set/clear plus judge loop | ✅ | judge endpoint plus client continuation loop (capped at 25), goal status bar |
| Double-check (armed with `/check`) | ✅ | `POST /api/conversations/:id/double-check`, result overlay |
| Model override (`/model <id>`) | ✅ | sent as `acp_model`, status-bar indicator |
| Council team (`/team <id>`) | ✅ | `team_id` body field |
| Sessions (`/sessions`) | ✅ | `GET /api/conversations/:id/sessions` overlay |
| Permission mode / reasoning effort | ⬜ | needs `GET /api/agents/:id/acp-config` probe |
| Conversation fork/branch | ⬜ | `POST /api/conversations/:id/fork` |
| Message queue | ⬜ | client-side scheduler |
| Voice input | 🚫 | needs mic capture and Web Audio, no TTY equivalent |
| File attach / Plate editor | 🚫 | rich editor, `ryu open` hands media to desktop |
| Diff review pane | ⬜ | `GET /api/worktree/:id/diff` (read-only summary feasible) |

| Deep links (`ryu open …`) | ✅ | hands `ryu://` to the desktop app |
| Split view / tabs / island | 🚫 | desktop window features |

## The deferred set

The pieces consciously not yet in the TUI, in roughly priority order:

- Permission-mode and reasoning-effort pickers (need an `acp-config` probe).
- Conversation fork (`/fork`) and a client-side message queue.
- Memory and settings tabs (blocked on Core list endpoints that do not exist yet).
- Marketplace browse (lives on the authenticated control-plane service, not Core).

Modality-bound surfaces (voice input, the workflow canvas, recipe recording, marketplace buy, the
Shadow timeline, split view and the island) stay N/A in the TUI by design: a terminal hands those off
to the desktop with `ryu open` rather than reimplementing them.
