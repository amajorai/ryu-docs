description: "Feature matrix of which desktop app features the ryu-cli terminal client has, which are planned, and which have no safe terminal equivalent, with the Core routes behind each."
---

The `ryu-cli` terminal client reaches the same Core the desktop app uses, so parity is mostly a
matter of surfacing existing Core endpoints, not new backend work. Command examples use `ryu` as
shorthand for `ryu-cli`, as in the [command reference](/docs/surfaces/cli/reference).

## The principle

The goal is **capability parity, not modality parity**. A terminal cannot render a React Flow
canvas or a screen-capture timeline, so some desktop surfaces are out of scope rather than missing.
Those are marked N/A in the TUI.

The same rule applies to native bridges. Apps should feature-detect the host and keep a portable
list/table fallback; see [TUI Extensions and Integrations](/docs/surfaces/cli/tui-integrations).

Every new terminal surface uses the shared client state, keyboard, rendering, and Core-service
seams. The command palette (`Ctrl+K`) is the primary way to move around: a narrow sidebar cannot
hold every tab, so the sidebar stays a short grouped list.

## Matrix

Legend: ✅ built, 🟡 in progress, ⬜ planned, 🚫 no safe terminal equivalent (with reason).

### Chat

| Feature | Status | Notes |
|---|---|---|
| Multi-turn streaming chat | ✅ | `POST /api/chat/stream`, `conversation_id` minted per chat |
| Agent picker (`Ctrl+A`) | ✅ | `GET /api/agents` |
| Workflow mention target (`@workflow`) | ✅ | Completes only workflows with a root Input node and sends `workflow_id` with the submitted chat turn. |
| App and plugin references (`@app`, `@plugin`) | ✅ | Completes enabled entries from `GET /api/plugins` and inserts the display name used in Desktop. These are prompt references and do not route the turn. |
| Human mentions and Inbox notifications (`@person`) | ✅ | With Inbox enabled, completes Core's authorized human directory, sends a recipient-scoped notification for each selected person, and reports permission or delivery failures in the TUI. |
| Incoming per-user notifications | ✅ | Core's verified per-user stream appears as a terminal toast; recipient filtering is server-side and repeated notification ids are shown once. |
| Agent create/edit | 🟡 | The TUI edits name, title, engine, model, description, instructions, persona name/tone, delegation, agent creation, and tool/skill allowlists. Pickers list registered MCP tools and installed skills, keep unavailable saved grants visible, and preserve Core's all/none scopes. A new agent opens on **How should this agent work?** (Acts as you, Its own identity, or Both). The **works as** and **account access** fields set the identity mode and account allowlist: Space allows or denies a listed account, or type a key. Before saving, the TUI asks Core whether the engine would start, and does not save when Core says it would not. Account groups and the save rules are in [Agent Commands](/docs/surfaces/cli/agent-commands). Connecting apps (including to the agent's own identity), identity-profile, memory, and safety editing remain Desktop-owned. |
| Per-agent sampling defaults | ✅ | Agents → Edit → sampling reads the agent's `inference` field and saves it with the existing Core `POST /api/agents` or `PUT /api/agents/:id` contract. Common sampling fields and engine-gated local samplers are validated and preserved on reopen. Core layers defaults as agent, then engine, then request, so engine values override matching agent values and request values override both. |
| Tool-call loop surfacing | ✅ | tool-input/output frames rendered inline |
| `/btw` side question | ✅ | `POST /api/btw`, ephemeral overlay |
| `/goal` set/clear plus judge loop | ✅ | judge endpoint plus client continuation loop (capped at 25), goal status bar |
| Double-check (armed with `/check`) | ✅ | `POST /api/conversations/:id/double-check`, result overlay |
| Model override (`/model <id>`) | ✅ | sent as `acp_model`; the model chip above the composer shows the override or the routed agent's configured model |
| Agent group | ✅ | `/group` or `/team` opens the named-team picker; `/group <id>` and `/group clear` remain available. The selected team is sent as `team_id` on the next turn. |
| Structured plugin slash arguments | ✅ | The `/` menu reads argument choices from enabled plugin commands, advances through sequential arguments, and supports declared custom values. Selected values stay in the exact slash text submitted to Core. |
| ACP agent-advertised commands | ✅ | The active ACP agent's `available_commands_update` replaces its command suggestions. Selecting one inserts `/name`; submission keeps the selected agent or team route and sends the command as chat text. |
| Sessions (`/sessions`) | ✅ | `GET /api/conversations/:id/sessions` overlay |
| Permission mode / reasoning effort | ✅ | `Ctrl+R`, `/config`, or `/reasoning` reads the selected agent's `GET /api/agents/:id/acp-config`; the chosen mode and select values are sent on the next turn as `acp_mode` and `acp_config`. |
| Conversation fork/branch | ✅ | `/fork [message-id]` creates a separate conversation, optionally from a selected branch point. |
| Message queue | ✅ | `Ctrl+Q` or `/queue` opens queued prompts; queued turns can be reordered or removed and run after the active turn. `Esc` during a reply pauses the queue; `Enter` on an empty composer resumes it. |
| Turn receipt and session usage | ✅ | Each finished reply ends with agent, model, duration, tokens, and tokens per second; the bar above the composer shows session tokens, context share when known, and cost when reported. |
| Voice input | 🚫 | needs mic capture and Web Audio, no TTY equivalent |
| File attach / Plate editor | 🚫 | rich editor; use the desktop app |
| Diff review pane | ⬜ | `GET /api/worktree/:id/diff` (read-only summary feasible) |

The tool picker shows registered MCP tools. An unchanged Core-wide grant remains all-tools; once
changed, the selection saves the listed MCP ids. An empty skill list means all globally enabled
skills, and explicit no-access scopes remain distinct from those defaults.

### Desktop product modes and host controls

| Desktop task | CLI equivalent | Coverage |
|---|---|---|
| Select Bot, Agent, or OS | `Ctrl+Shift+M` opens the CLI mode picker; mode and last CLI surface persist in `~/.ryu/state/cli/cli-product-mode.json`. | ✅ Bot and OS stay available. Agent appears only after the active managed node confirms you hold Gateway configuration permission; unmanaged nodes are available without an organization check. This preference belongs to the CLI profile and does not change Desktop's product-mode setting. |
| Choose the startup realm (Bot, Agent, OS, or Last used) | Settings → General stores this independently from the current mode and its per-mode last surface. Starting in Agent still verifies managed-node Gateway configuration permission and fails closed. | ✅ |
| Use Bot for chat | Bot conversations are pinned to Ryu; the composer hides agent/group routing, model, and approval controls. Agent and named-group targeting remain available in the Agent and OS workspaces. | ✅ Local/provider chat remains available when managed routing is signed out, plan-limited, or unavailable. Bot adopts a scoped managed-node session and seeds the managed cloud lane only when entitlement is verified and no cloud selection exists. |
| Configure nodes and Gateway in Agent | `ryu node …`, the node picker (`Ctrl+N`), Gateway surfaces, and `ryu apply`, `ryu diff`, `ryu config` use the Core/Gateway contracts. | ✅ Unmanaged local nodes are available. Managed nodes require verified Gateway configuration permission (owners and admins by default, or a custom role that grants it); Agent stays out of the mode picker until the permission check succeeds, and falls back to Bot when a node switch is denied. Delegated credentials stay in memory. |
| Open an app from the OS App Launcher | Choose OS mode, then `Ctrl+K` → **Go to App Launcher**. The launcher opens CLI surfaces and enabled Apps with contributed terminal views. | ✅ Apps without a terminal view are labeled Desktop-only; Plugins & Sidecars opens `/store`, the current Plugins/Sidecars landing. |
| Arrange app windows, use the Dock, or change wallpaper | Use Desktop's native window controls and Dock. | 🚫 Window geometry, Dock state, and wallpaper belong to the Desktop host. |
| Change host permission grants for microphone, Accessibility, Screen Recording, or Input Monitoring | Use the Desktop control that invokes the native Tauri/OS flow. | 🚫 The terminal cannot present Desktop's Tauri prompts or report its host grant state. Core chat permission responses are a separate CLI-supported flow. |

Bot, Agent, and OS are terminal workspaces over shared Core, Gateway, and app-view contracts. The
CLI stores its current mode, startup realm, and per-mode landing surfaces in its own profile;
Desktop continues to use its own setting. A CLI mode switch never claims to update Desktop local
storage. Startup realm changes apply on the next CLI launch.

Bot confirms a newly saved managed cloud lane by reading it back. If the save cannot be
confirmed, chat remains available and the mode picker offers `r` to retry setup. Existing
cloud selections are preserved. If the current selection cannot be read, Bot leaves it
untouched and offers the same retry.

## Memory and safety controls

Memory settings, the memory library, and the Gateway safety editors are described in
[Memory settings and library](/docs/surfaces/cli/tui-settings#memory-settings-and-library) and
[Gateway safety settings](/docs/surfaces/cli/tui-settings#gateway-safety-settings).

## Not yet in the TUI

In rough priority order:

- Agent connection, identity-profile, memory, and safety authoring. Identity mode and account
  access are already covered by the agent editor and `ryu-cli agents`.
- Per-model launch writes, which have no shipped Desktop editor yet (see [Catalogs and local stack](/docs/surfaces/cli/parity#catalogs-and-local-stack)).
- Marketplace browse (lives on the authenticated control-plane service, not Core).
- Desktop's React layout, native Dock/window management, wallpaper, and Tauri OS permission prompts remain host-specific.

Modality-bound surfaces (voice input, the workflow canvas, recipe recording, marketplace buy, the
Shadow timeline, and Island) stay N/A in the TUI. Use the desktop app for those rather than a
terminal reimplementation.
