`ryu tui` is a Bun plus [OpenTUI](https://github.com/sst/opentui) React terminal client for Ryu
Core. It is the successor to the ratatui CLI: a terminal client that reaches the **same Core**
node over HTTP and SSE, holds no model, and runs no inference of its own. It follows the active
node selected by the CLI launcher.

<Callout type="info">
  The OpenTUI client ships **alongside** the ratatui CLI, not as a replacement yet. The TUI is at
  full interactive feature parity with the CLI (Teams surface, guided Setup wizard, launch update-notice
  all added) and is ahead on chat, split-pane workspace, and store-wide search. It is the recommended
  terminal client. See [Desktop parity](/docs/surfaces/cli/parity) for the parity matrix.
</Callout>

## Launch it

The CLI owns the launcher. `ryu tui` opens the OpenTUI client and hands it the active node so both
talk to the same Core:

```sh
ryu tui
```

## What the TUI adds

The TUI is a terminal-native client. It keeps shared Core behavior and replaces pointer-heavy or
OS-specific interactions with keyboard commands and compact projections:

| Capability | TUI behavior |
|---|---|
| HTTP/SSE client | Connect to a running Core node; models and tools execute through Core |
| Workspace navigation | Use `Ctrl+K`, tabs, panes, and node switching without a mouse |
| App contributions | Render portable list, table, and data-table views, or show an explicit unavailable state |
| Native effects | Consume Core notifications and status; it does not claim phone haptics, Live Activities, Dynamic Island, or browser permissions |

The TUI does not duplicate Desktop-only UI. Use [Desktop parity](/docs/surfaces/cli/parity) to see
which features have a terminal equivalent and which need `ryu open`.

The launcher inherits the active node selected with the CLI's node controls, so the terminal and
desktop operate on the same conversations, agents, apps, and tools. Source contributors can use
the repository's workspace development command; installed users only need `ryu tui`.

## The shell

The client is a tabbed workspace shell. Its Ctrl-modified bindings own the workspace:

| Key | Action |
|---|---|
| `Ctrl+K` | Open the fuzzy command palette (the Cmd+K analog) |
| `Ctrl+T` | Open a new chat tab (`Ctrl+Shift+T` restores the last-closed tab) |
| `Ctrl+W` | Close the focused pane's active tab |
| `Ctrl+Alt+S` | Toggle a two-pane split |
| `Ctrl+Tab` | Cycle tabs in the focused pane (Shift reverses) |
| `Alt+←` / `Alt+→` | Move between panes |
| `Ctrl+C` | Quit |

The command palette is the primary navigation surface - a narrow sidebar cannot hold every tab, so
the palette fuzzy-jumps to any tab plus global actions. Switching nodes is one of those actions and
is driven with the arrow keys and Enter.

## The tabs

The shell registers **17 tabs** in an order that mirrors the CLI's sidebar so the two surfaces line up:

Chat, Services, Agents, Models, Skills, Tools, Apps, Gateway, Workflows, Recipes, Teams, Spaces, Engines, Monitors, Meetings, Schedules, Account.

Each tab is a thin view over Core services, matching the CLI's list-tab model. Because this is a
pure HTTP/SSE client to the same Core, parity is a matter of surfacing existing contracts rather
than adding terminal-only backends (see [CLI](/docs/surfaces/cli)).

## Extension surfaces in a terminal

The terminal host consumes the same contribution metadata as the other clients, filtered to the CLI
or TUI surface. Library contributions use the portable declarative view contract: `list`, `table`,
and `data-table` projections render today; richer board, calendar, gallery, map, or custom renderers
can be added without changing an app's record schema. When a renderer is not available, the TUI
reports that state rather than opening a browser or silently changing the view.

Native effects are intentionally different in a terminal. Plugins can use Core tools, channel
notifications, and status contributions, but should not assume browser permission prompts, phone
haptics, Live Activities, or Dynamic Island. See [Native bridges](/docs/extend/develop/extensions/native-bridges)
for the cross-surface capability contract.

## Chat

The Chat tab streams over Core via SSE and supports the same chat-side flows as the CLI:

- **`Ctrl+A`** opens the agent picker. The selected agent and team show as chips; the model is set via the `/model` command and shown as a read-only chip.
- **`Ctrl+L`** starts a new chat.
- **`Ctrl+Q`** focuses the queued-prompt bar while a turn is streaming. Enter opens the full queue, `x` removes the selected prompt, `c` clears the queue, `Shift+↑/↓` reorders it, and Esc returns to the composer. Queued turns retain the agent, team, model, ACP settings, and plugin flags that were active when they were entered.

The typed slash commands are:

| Command | What it does |
|---|---|
| `/goal <text>` | Pass-through to Core's server-side goal turn-hook, which owns the completion condition and judge loop. |
| `/proof` | Pass-through to Core's server-side proof turn-hook. |
| `/check` | Arm the per-turn double-check hook via `plugin_flags`; Core reviews the next turn and the note lands in the stream. |
| `/btw <question>` | Ask a quick side question; ephemeral, dismissible, never enters history. |
| `/model <id>` | Override the model for the turn (cleared with a bare `/model`). |
| `/group <id>` | Route the turn to an agent group. |
| `/sessions` | Open the run history for the current conversation. |
| `/new` (`/newchat`) | Reset the chat. |
| `/queue` (`/q`) | Inspect queued prompts; `/queue clear`, `/queue drop <id>`, `/queue up <id>`, and `/queue down <id>` manage them. |
| `/theme` | Choose system/light/dark mode or the Ryu/Ryu Mono terminal preset. A fresh terminal follows the desktop's shared theme mode, while explicit terminal choices are saved to the active Core node. |
| `/help` (`/commands`) | Show the complete registry-backed slash-command reference. |

The composer also completes slash commands and `@agent` mentions. Tool output is rendered as bounded, collapsible terminal content; reasoning starts collapsed, todos show progress counts, and patch-shaped tool results use the terminal diff renderer so a long stream cannot take over the viewport.

`/goal`, `/proof`, and `/check` are Core server-side plugin turn-hooks: `/goal` and `/proof` pass through as normal messages, and `/check` arms the double-check hook, so their behavior lives in Core, not the client. The tool-call loop is surfaced inline as the agent works.
