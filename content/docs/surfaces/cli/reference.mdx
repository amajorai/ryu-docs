`ryu-cli` is Ryu's command-line client (`apps/cli`). Run it with no arguments to open the
[terminal workspace](/docs/surfaces/cli/tui), or run `ryu-cli <subcommand>` to run one command and
exit. The tables below use `ryu` as shorthand for the command name; type `ryu-cli` in your shell.

<Callout type="info">
Automatic updates apply to the installed `ryu-cli` binary when the shared setting is enabled. The
`update` subcommand reports release status for the selected Core node; it does not install the
terminal binary. See [Ryu updates](/docs/core/updates) for both update paths.
</Callout>

## Global flags

| Flag | Meaning |
|---|---|
| `--node <name\|url>` | Target a saved node by name or URL (`ryu node list`), with that node's saved token, or any other `http(s)://` URL for this one command. A value that is neither is rejected. Without `--node`, `RYU_CORE_URL` is used when set, otherwise the active node. Accepted by every command that talks to Core. |
| `--json` | Machine-readable output for agents and CI |
| `--dry-run` | Preview supported mutating commands without writing changes |
| `-h`, `--help` | Show help |

The interactive terminal client (`ryu` with no arguments, or `ryu tui`) starts a local node if none
is answering. One-shot commands connect to the selected node and do not start one. Run `ryu help`
for the full command list, including app-contributed commands (`ryu <app> <cmd>`). `troubleshoot`
reports a stopped Core rather than starting it; `troubleshoot --fix` starts it.

## General

| Command | What it does |
|---|---|
| `ryu` (no args) | Open the terminal workspace |
| [`ryu tui`](/docs/surfaces/cli/tui) | Open the OpenTUI terminal client (`apps/cli`) |
| `ryu status` | Show sidecar statuses (installed, running/stopped) |
| `ryu observability <audit\|trace\|eval\|redteam\|score\|audit-prune>` | Inspect audits/traces or run quality/security/online scoring checks |
| `ryu trace <run-id>` | Print the Core spans correlated to a run |
| `ryu eval [agent-id] [model]` | Run the Gateway's Promptfoo-compatible evaluation dataset, or your own with `--dataset`; exits 1 below a `--threshold` |
| `ryu redteam <agent-id> [model]` | Run the bounded local security probe campaign; exits 1 above `--max-attention` |
| `ryu start <name\|all>` | Start a sidecar, or all of them |
| `ryu stop <name\|all>` | Stop a sidecar, or all of them |
| `ryu restart <name\|all>` | Restart a sidecar, or all of them |
| `ryu setup` | Inspect dependency setup |
| `ryu version` | Show the CLI version |
| [`ryu troubleshoot ["what went wrong"]`](/docs/surfaces/cli/troubleshoot) | Check this install, apply safe fixes with `--fix`, search similar issues, and print a prefilled bug report link. Accepts `--dry-run`, `--open`, `--offline`, and `--json`; alias `bug-report` |
| `ryu update` | Check the selected Core node's release status and print its release information |
| `ryu open <page>` (alias `link`) | Send a deep-link request to Core. See the warning below |
| `ryu-cli acp [--agent <id>] [--node <name\|url>]` | Run Ryu as an ACP agent over standard input and output for editors such as Zed. It does not start a local node. It serves the local node unless `--node`, `RYU_CORE_URL`, or a remote active node (`ryu node use`) points it elsewhere. See [Editors (ACP)](/docs/surfaces/editors) |
| `ryu connect <agent>` | Add Ryu's MCP tools to a coding agent's user config. See [Coding agents](/docs/surfaces/cli/reference#coding-agents) |
| `ryu disconnect <agent>` | Remove the entry `connect` added |
| `ryu connect [status\|browse\|search\|describe\|request\|call\|balance]` | Browse Ryu's tool catalog and call Ryu Connect tools. See [Ryu Connect from the command line](/docs/standalone/connect-cli) |
| `ryu doctor agents` | Check each coding agent's Ryu MCP setup and the node's MCP endpoint |
| `ryu migrate [chatgpt\|claude\|openclaw\|hermes\|muse\|mastra\|langchain\|dots] [path]` | Preview and import ChatGPT or Claude chats and projects, or an existing agent's persona, memory, skills, MCP servers, and code-defined agents. Accepts `--dry-run`, `--yes`, `--only <kinds>`, `--secrets`, and `--json`. See [Migrate from other agents](/docs/start-here/migration/from-other-agents) |
| `ryu services <service> <command> …` | Call Ryu's standalone services (`ryu-cli services …`, in a Ryu release after 0.4.0; the `ryu` command from `@ryuhq/sdk` has no `services` command). Everything after `services` is passed unchanged to the bundled [`ryu-services` command line](/docs/standalone/sdk/cli), so its flags, environment variables, and exit codes apply. A `ryu-services` global flag written before `services` (such as `ryu --json services …` or `--base-url <url>`) is forwarded; any other flag there exits with code 2 and prints the corrected command. It does not need a Core node. `ryu services` alone prints its help |

<Callout type="warn">
`ryu open` posts its arguments to `POST /api/deep-link` on the selected Core node, and Core does not
currently serve that route, so the command fails. Open the page in the desktop app directly.
</Callout>

## Coding agents

`ryu connect <agent>` registers your Ryu node as an MCP server named `ryu` in a coding agent's
user-level config, so the agent can call Ryu's tools in every project. The entry points at the
node's MCP endpoint, `<node URL>/mcp/<agent-id>` (the local default is
`http://127.0.0.1:7980/mcp/ryu`), and sends the node token as an `Authorization: Bearer` header.

| Agent | `<agent>` | File it edits | Entry it adds |
|---|---|---|---|
| Claude Code | `claude-code` | `~/.claude.json` (or `$CLAUDE_CONFIG_DIR/.claude.json`) | `mcpServers.ryu` with `type: "http"`, `url`, `headers` |
| Codex | `codex` | `~/.codex/config.toml` (or `$CODEX_HOME/config.toml`) | `[mcp_servers.ryu]` with `url`, `http_headers` |
| Cursor | `cursor` | `~/.cursor/mcp.json` | `mcpServers.ryu` with `url`, `headers` |
| opencode | `opencode` | `~/.config/opencode/opencode.json` | `mcp.ryu` with `type: "remote"`, `url`, `enabled`, `headers` |
| Gemini CLI | `gemini` | `~/.gemini/settings.json` | `mcpServers.ryu` with `httpUrl`, `headers` |

```sh
ryu-cli connect claude-code          # write the entry
ryu-cli connect codex --dry-run      # show what would change, token redacted
ryu-cli connect cursor --print       # print the snippet to paste yourself
ryu-cli connect opencode --agent coder   # scope the tools to another Ryu agent
ryu-cli disconnect claude-code       # remove it again
ryu-cli doctor agents                # check every agent
```

How `connect` edits files:

- It changes only the `ryu` entry. Other servers and settings stay as they are. In Codex's
  `config.toml` it adds or replaces only the `[mcp_servers.ryu]` table, so comments and layout are
  kept. Files are written atomically, a new file is created readable only by you, and an existing
  file keeps its permissions.
- It refuses to replace a `ryu` entry that it did not write. Pass `--force` to replace it.
- `disconnect` removes the entry only if it is still the one `connect` wrote. Pass `--force` to
  remove an entry you changed. If `connect` created the file and nothing else is in it, the file is
  deleted.
- If a file cannot be edited safely, for example a JSON file with comments such as
  `opencode.jsonc`, nothing is written and the snippet is printed for you to paste instead.
- Restart the agent, or start a new session, after connecting.
- Codex must support MCP servers reached by URL. Some older Codex releases load them only with
  `experimental_use_rmcp_client = true` in `config.toml`; if the `ryu` server does not appear,
  update Codex or check its MCP documentation.

<Callout type="warn">
By default the node token is written in plain text into the agent's config file, because that is
the only way the agent can send it without extra setup. Anyone who can read that file can use your
Ryu node. Pass `--token-env` to write a reference to the `RYU_CORE_TOKEN` environment variable
instead; the agent must then be started with `RYU_CORE_TOKEN` set. If the node token changes, run
`connect` again to update the entry.
</Callout>

`connect` uses the node from `--node <url>` or `RYU_CORE_URL`, and the token from `RYU_CORE_TOKEN`.
For the local node it reads the token Ryu created on this machine, so Ryu must have started at least
once.

`ryu doctor agents` reports, for each agent: whether its command is on your `PATH`, whether a `ryu`
entry exists and points at this node, and whether the node accepts the entry's token. It sends one
MCP `initialize` request to check. It prints a fix for each problem, such as `ryu-cli connect codex`,
and exits with status 1 when the endpoint check fails or a configured entry is broken. Add `--json`
for machine-readable output.

## Marketplace

| Command | What it does |
|---|---|
| `ryu models <list\|add> [id]` | Browse the model catalog, or install a GGUF model by catalog id |
| `ryu skills <list\|add> [id]` | Browse the skills catalog, or install a skill by catalog id |
| `ryu apps <list\|add> [id]` | List apps, or install an app by manifest id (e.g. `@ryu/clips`) |
| `ryu mcp <list\|add> [id]` | Browse the MCP server catalog, or install an MCP server by catalog id. These are servers Ryu itself uses; to give a coding agent Ryu's tools, see [Coding agents](/docs/surfaces/cli/reference#coding-agents) |
| `ryu okf export <dir>` | Export indexed knowledge as an OKF bundle |

`models add` hands the download to Core (`POST /api/models/catalog/install`).

## Config-as-code (GitOps)

| Command | What it does |
|---|---|
| `ryu apply -f <file> [--dry-run]` | Validate and write the Core-writable Gateway TOML subset; `--dry-run` previews the changes |
| `ryu diff -f <file>` | Compare the file against the active Gateway config |
| `ryu config [show]` | Print the active Gateway config, with secrets redacted |

These commands read and write the node's Gateway config through Core (`GET` and
`PUT /api/gateway/config`). Core exposes no revision or rollback route for this config. See
[Gateway configuration](/docs/gateway/configuration).

## Auth

| Command | What it does |
|---|---|
| `ryu login` | Start Core's device-login flow and print its verification URL and code. After sign-in, Core saves the account in its local account vault in the data folder's `secrets/` directory |
| `ryu logout` | Sign out of the active account in Core's local account vault |
| `ryu whoami` | Read the signed-in Better Auth profile (name, email, verification, and 2FA) through the active local Core bearer |
| `ryu sessions` | List active Better Auth browser sessions |
| `ryu sessions revoke <id>` | Revoke a selected non-current browser session and confirm it is absent on readback |
| `ryu sessions revoke-all --force` | Revoke all other browser sessions; `--dry-run` previews the number without writing |
| `ryu plan` | Read the Better Auth subscription status |
| `ryu account` | Show account profile, password/2FA status, plan, and active-session count |

There is no non-interactive subcommand for the display name; change it in the workspace's
Settings → Profile. The workspace's Account tab runs the same sign-in flow; see
[Account and security](/docs/surfaces/cli/tui-settings#account-and-security).

## Apps, plugins, and packages

Apps and plugins install, enable, disable, and uninstall by id through the same commands. An app is a
plugin that also ships a full-page UI. Use `--kind app|plugin|all` to browse one at a time.

| Command | What it does |
|---|---|
| `ryu list [--kind app\|plugin\|all]` | List installed apps and plugins |
| `ryu catalog [query] [--kind app\|plugin\|all]` | Browse or search installable apps and plugins |
| `ryu add <id> [--dry-run]` | Install an app or plugin from the catalog |
| `ryu enable <id> [--dry-run]` | Enable an installed app or plugin |
| `ryu disable <id> [--cascade] [--dry-run]` | Disable an app or plugin; `--cascade` includes its dependents |
| `ryu uninstall <id> [--cascade] [--dry-run]` | Uninstall an app or plugin; `--cascade` includes its dependents |
| `ryu init <name> [--template <t>]` | Scaffold a new app or plugin project (the template is passed to `create-ryu-app`) |
| `ryu plugin <doctor\|eval> [id]` | Validate or evaluate an installed plugin or app |
| `ryu package <validate\|inspect\|pack\|unpack\|import\|export\|publish> <path> [destination]` | Validate, inspect, import, export, and pack portable packages |
| `ryu stack export` | Print the fleet stack template as JSON (there is no import command) |
| `ryu <app> <cmd>` | Run a command that an installed app or plugin contributes; run `ryu <app>` to list them |

## Agents, chat, mail, and secrets

| Command | What it does |
|---|---|
| `ryu chat "<message>"` | Send one message and print the reply |
| `ryu action <id> <json> --agent <agent-id>` | Call one governed Action through Core; `--agent` is required |
| `ryu mail <status\|inboxes\|messages\|threads\|drafts\|webhooks\|events\|send> …` | Manage agent inboxes, messages, threads, drafts, and webhooks |
| `ryu secrets <list\|get\|set\|run\|export\|import\|scan\|…>` | Manage Secret Vault values, run commands with them, and scan for leaks |
| `ryu doctor [--fix] [--dry-run]` | Audit Gateway configuration and security; see [Gateway operations](/docs/gateway/configuration-operations#safety-posture-and-doctor) |

For example, `ryu secrets run --env prod -- bun run start` runs a command with the `prod` secrets, and
`ryu secrets scan . --json` scans the current folder for leaks. `--include-secrets` adds an encrypted
local secrets envelope to an export.

The full list, with every flag, is printed by `ryu help` (`renderHelp` in
`apps/cli/src/cli/commands.ts`).

## Observability and CI

The observability commands use the same Core endpoints as Desktop and preserve the raw machine
contract with `--json`, as in these examples:

```sh
ryu observability audit --agent <agent-id> --json
ryu trace <run-id> --json
ryu eval <agent-id> <model> --json
ryu redteam <agent-id> <model> --json
ryu observability audit-prune --json
ryu observability score <agent-id> 'completed output' <model> --json
```

Pipe the `--json` output of `ryu-cli eval` or `ryu-cli redteam` into your own CI step for custom
gating, or use the built-in gates below.

### Eval gates

`ryu-cli eval` replays a dataset through the Gateway eval runner and prints a summary. Without
thresholds it always exits 0; with `--threshold` it exits 1 when any threshold is missed, so it
can gate CI directly.

```sh
ryu-cli eval support-agent gpt-4o-mini \
  --dataset evals/support.jsonl \
  --scorer answer_relevance --scorer toxicity \
  --threshold 0.8 --threshold overall=0.7 \
  --junit > ryu-eval.xml
```

| Flag | Meaning |
|---|---|
| `--dataset <file>`, `-d` | JSON, JSONL, or CSV dataset. Each row needs `prompt` (or `input`, `question`, `query`); `expected` (or `expected_output`, `answer`, `reference`), `context`, `id`, `assertions`, and `evaluators` are optional, and extra CSV columns become `{{vars}}`. The Gateway's built-in dataset is used when omitted |
| `--scorer <id>`, `-s` | Repeatable or comma-separated. An offline Gateway catalog evaluator id, or a built-in metric: `overall`, `assertions`, `policy`, `substring`, `latency` |
| `--threshold <n\|scorer=n>`, `-t` | Repeatable. A bare `n` (0 to 1) applies to every `--scorer`, or to `overall` when none is given; `scorer=n` sets one scorer |
| `--model <id>` | Model to evaluate (same as the second positional argument) |
| `--judge-model <id>` | Judge model for model-graded assertions and evaluators |
| `--concurrency <n>` | Maximum cases in flight (the Gateway caps it) |
| `--json` | The Gateway result, plus a `gate` object when thresholds are set |
| `--junit` | JUnit XML: one test case per dataset case and one per threshold check |

Thresholds compare aggregate means. Evaluators that score a bad signal, such as `toxicity`, are
inverted first, so every threshold reads "at least this good". A scorer that never executed,
for example because no judge model is configured, fails its threshold instead of passing.
Unknown or inline-only scorer ids are rejected before the run starts.

`ryu-cli redteam <agent-id> --max-attention 0` exits 1 when more probes need attention than allowed,
and `--junit` reports one test case per probe.

Provider availability, configured models, and the normal Gateway budget still determine whether
a run itself succeeds. To score agents from TypeScript instead, see [Evals](/docs/extend/develop/sdk/evals).

## `ryu node` - node management

| Command | What it does |
|---|---|
| `ryu node ls` (or `list`) | List configured nodes and mark the active one |
| `ryu node use <name\|url>` | Set the active node by name or URL. Later commands and the next terminal workspace launch use it unless `--node` or `RYU_CORE_URL` overrides it |

Nodes are stored in `state/nodes.json` in the data folder (`~/.ryu/state/nodes.json` by default),
which Desktop also reads. To target a node that is not configured for one command, use
`--node <url>` or set `RYU_CORE_URL`.

Saved node tokens in `nodes.json` are not encrypted: the terminal client reads the file directly and
cannot reach the desktop's OS keychain. Ryu Desktop and the CLI write the file with owner-only
permissions instead. If the file holds an encrypted token the CLI cannot open, the CLI keeps it
unchanged and never sends it; set `RYU_CORE_TOKEN` to that node's token to use it from the terminal.

## `ryu tui` - the terminal client

Run `ryu-cli` with no arguments, or `ryu-cli tui`, to open the OpenTUI workspace. Inside it, press
`F1` (or `Ctrl+?`) for a searchable list of every keyboard shortcut and slash command. Keys, views,
settings, and the account service address (`RYU_AUTH_URL`) are documented on
[OpenTUI terminal client](/docs/surfaces/cli/tui).
