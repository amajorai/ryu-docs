This page is the complete `ryu` command reference. The binary is built from the `ryu-cli` crate
(`cargo build -p ryu-cli`); run `ryu` with no arguments to open the control-panel TUI, `ryu` with an
unknown command to print this usage list, or `ryu <subcommand>` to run headless and exit.

<Callout type="info">
The Rust CLI is in maintenance mode — new terminal features land in the OpenTUI client
([`ryu tui`](#tui)). The headless, script-shaped subcommands below (`okf export`, gateway
config-as-code `apply`/`diff`/`config`, `open`, `node`, `update`) are the ones the interactive TUI
intentionally does not reproduce, so they stay here. See [CLI](/docs/cli) for the framing.
</Callout>

## Global flags

| Flag | Meaning |
|---|---|
| `--node <name>` | Target a saved node by name (`ryu node list`); without it the active node is used. Accepted by every command that talks to Core. |

Commands that talk to Core auto-start a local node if none is running. Purely local commands
(`version`, `help`, `init`, `login`, `logout`) skip that so they stay instant offline.

## General

| Command | What it does |
|---|---|
| `ryu` (no args) | Open the control-panel ratatui TUI |
| [`ryu tui`](#tui) | Open the modern OpenTUI terminal client (`apps/tui`) |
| `ryu status` | Show sidecar statuses (installed, running/stopped) |
| `ryu start <name\|all>` | Start a sidecar, or all of them |
| `ryu stop <name\|all>` | Stop a sidecar, or all of them |
| `ryu restart <name>` | Restart a sidecar |
| `ryu setup` | Open the setup-wizard TUI (dependencies, providers, tools, agents) |
| `ryu version` | Show the CLI version plus Core's view of the release train and any update |
| `ryu update` | Check for a newer Ryu release and print the release URL |
| `ryu open <ryu://…\|page\|chat …>` | Forward a deep link (or a page/chat shorthand) to the desktop app |

### `ryu open`

The CLI is headless, so a deep link to a desktop surface is handed to the GUI rather than rendered:

| Syntax | Opens |
|---|---|
| `ryu open ryu://open/agents` | An explicit `ryu://` deep link |
| `ryu open monitors` | A page shorthand → `ryu://open/monitors` |
| `ryu open chat Fix the failing test` | A new chat, composer pre-seeded (not sent) → `ryu://chat/new?prompt=…` |

Only `ryu://` URLs are ever handed to the OS opener. If the scheme is unregistered (the desktop app
is not installed), the open fails with guidance.

## Marketplace

| Command | What it does |
|---|---|
| `ryu models add <id> [--file <name>]` | Install a model by catalog id (best-fit quant by default; `--file` picks an exact GGUF) |
| `ryu skills list [query]` | Browse the skills catalog |
| `ryu skills add <id\|owner/repo\|url>` | Install a skill: a catalog id, a bare repo ref, or a `://` URL source |
| `ryu mcp list [query]` | Browse the MCP server catalog |
| `ryu mcp add <id>` | Install an MCP server (written disabled; enable it to use) |
| `ryu okf export <dir> [--bundle <id>]` | Export indexed knowledge as an OKF bundle directory |

`models add` delegates the download to Core (verified, source-pinned); there is deliberately no
`models list` because model discovery is a browse-and-compare task the TUI and Store do better. A
`skills add` argument that contains `://` is always treated as a source; anything else is tried as a
catalog id first and falls back to install-from-source on failure, so both a real catalog id and a
bare `owner/repo` route correctly.

## Config-as-code (GitOps)

| Command | What it does |
|---|---|
| `ryu apply -f <file> [--org <id>]` | Validate + apply a scope's `gateway.yaml` to the control plane |
| `ryu diff -f <file> [--org <id>]` | Preview the change without applying it |
| `ryu config revisions [--org <id>]` | List applied revisions (newest first) |
| `ryu config rollback <rev> [--org <id>]` | Revert to a prior revision (creates a new revision) |
| `ryu config show [--org <id>]` | Print the org's current config as YAML |

These hit the same control-plane store the dashboard UI writes to, so a config applied here is
visible and rollback-able in the UI and vice versa. The org id comes from `--org <id>` or the
`RYU_ORG` environment variable. Validation of the policy shape happens server-side so the CLI and UI
share one validator. See [Gateway configuration](/docs/gateway/configuration).

## Auth

| Command | What it does |
|---|---|
| `ryu login` | Log in via browser (opens Core's `/api/auth/login`; token saved to `~/.ryu/auth.json`) |
| `ryu logout` | Clear saved credentials |
| `ryu whoami` | Show full account status (name, email, auth method, 2FA, plan, session count) |
| `ryu sessions` | List active sessions |
| `ryu sessions revoke <id>` | Revoke a specific session |
| `ryu sessions revoke-all` | Revoke all other sessions |
| `ryu plan` | Show the subscription plan, renew date, and invoice history |
| `ryu account` | Show detailed account info (name, email, password/2FA status) |
| `ryu account name <new-name>` | Update the display name |

`login` is the browser flow; inside the TUI the same flow is reachable from the Account tab with `l`.

## `ryu node` — node management

| Command | What it does |
|---|---|
| `ryu node list` | List saved nodes with URL and which is the default |
| `ryu node add <name> <url> [--token <token>]` | Register a node (name must be alphanumeric + hyphens) |
| `ryu node remove <name>` | Remove a node (the `local` node cannot be removed) |
| `ryu node use <name>` | Set the active node |
| `ryu node current` | Show the active node |
| `ryu node test [<name>]` | Ping a node's `/api/health` and report latency |
| `ryu node discover [--port <port>] [--add]` | Sweep the local /24 for Core nodes; `--add` registers them |
| `ryu node init [--force]` | Generate a node token (run on the remote machine) |

`discover` probes up to 254 hosts concurrently (800 ms per probe). Without `--add` it just lists what
it found; with `--add` it registers each as `discovered-<n>` and prints how to activate one. `init`
writes a fresh `ryu_…` token to `~/.ryu/core.token` and prints the `ryu node add` + `ryu-core
--bind 0.0.0.0:2049` invocation to use it. Nodes are stored in `~/.ryu/nodes.json`.

## `ryu tui` — the modern terminal client

`ryu tui` shells out to the OpenTUI client (`apps/tui`) and hands it the active node so both talk to
the same Core. What it runs is resolved in this order:

1. `RYU_TUI_CMD` — a full command line, the escape hatch for packaged installs.
2. Walking up from the current directory for the monorepo root (first ancestor with
   `apps/tui/package.json`), then `bun run --filter tui dev` from there.
3. Otherwise, print guidance and error out.

Either way it exports `RYU_CORE_URL` (and `RYU_CORE_TOKEN` when the node has one) so the OpenTUI
client inherits the node you selected. Run it directly during development with
`bun run --filter tui dev`. See [OpenTUI terminal client](/docs/cli/tui).
