Ryu Console is the power-user and admin surface for Ryu. This page is the full desktop feature
reference: everything you do in the app. [Ryu OS](/docs/surfaces/desktop/ryu-os) is the
agent-first workspace view in the same desktop app. The [Mobile](/docs/mobile), [Browser app](/docs/surfaces/webapp),
[Browser extension](/docs/browser-extension), [CLI](/docs/surfaces/cli), [Island](/docs/surfaces/island),
and [Raycast](/docs/surfaces/raycast) pages cover those surfaces and how they differ.

Ryu also ships [Ryu Bot](/docs/surfaces/desktop/bot), the focused account-only mode in the same
desktop app. Bot is managed end to end and hides Console's provider, model, node, and infrastructure
controls. The Bot/Console switch is shown only to owners/admins of a Ryu-managed node's organization;
self-hosted and local nodes open directly in Console.

### Choose the startup realm

The Desktop app opens new users in **Bot**. After you switch between Bot, Console, and [Ryu OS](/docs/surfaces/desktop/ryu-os),
the app remembers the last realm you used and opens there on the next launch. Change this in
**Settings → General → On startup → Realm on startup**:

- **Last used** follows the most recent realm, with Bot as the fallback for a new install.
- **Bot**, **Console**, or **OS** always open that realm when the Desktop app starts.

Console remains subject to the active node's organization access. A user without Console access is
kept in Bot even if an older startup preference requested Console.

The native window title follows the active realm — **Ryu Bot**, **Ryu Console**, or **Ryu OS** —
after a switch, while macOS keeps its native traffic-light controls and the rounded window surface.

Every surface uses the **same Core contract**. Console may run a local Core or connect to a
managed or self-hosted node; Bot uses the managed path. A chat can remain the same conversation
when you move between Console, the CLI, the Island, or your phone.

## Switching tabs and opening pages

Desktop keeps open pages mounted so returning to a tab preserves its working state
and scroll position. Switching tabs reuses the existing page; opening a new page
loads its content as needed. Pages that need Core, a companion app, or a remote
service can still show a loading state while that service responds.

Unchanged pages avoid navigation-only updates. Session saving is coalesced during
rapid switching and flushed when the window is hidden or closes.

Agent and app lists share their loaded data across pages on the same node and
identity. Reopening a picker can reuse a recent list, and edits update other open
pickers. Background query polling pauses while the window is unfocused or hidden;
returning to it resumes the queries that need live updates.

Office file editors load when you open that file type, so opening the workspace
does not also initialize every editor. Long conversations defer drawing older
offscreen turns while keeping the current turn ready for updates. PDF reading
resources are released when you close the viewer.

Settings dialogs, rich-text editors, document previews, and map widgets load on
first use. Settings-menu hover or keyboard focus prepares the dialog before you
open it. A brief loading indicator can appear on first use; later openings reuse
the loaded implementation.

To manage memory, use **Settings → General → Tabs → Unload inactive tabs**.
Unloaded tabs rebuild their view when selected again; unloading does not delete
saved conversations. Keep a tab pinned when it should remain available without
idle unloading.

## What Desktop adds

Desktop owns the native workspace and local-machine features that do not fit a browser or terminal:

| Capability | Desktop behavior |
|---|---|
| Ryu OS workspace | Dock, live App windows, App Launcher (`Cmd/Ctrl-K`), and curated wallpapers |
| Native media picture-in-picture (PiP) | Open a live browser, desktop, or recording preview in an always-on-top media window |
| Multi-window workspace | Use split panes, tabs, separate windows, and Desktop-only window actions |
| Local machine integrations | Manage local engines, sidecars, files, Git workspaces, and the Virtual Desktop |
| Full host rendering | Render the complete shared app shell, rich views, widgets, and contributed panels |

Plugins should still check the host capability descriptor before offering a native effect. See
[Native bridges](/docs/extend/develop/extensions/native-bridges) for the cross-surface rules.
