title: Audio, Voice Recognition, and Speech Processing engines
description: Audio, Voice Recognition, and Speech Processing engines that run alongside Chat.
---

Voice engines provide Voice Recognition, Speech Processing, and Audio. Unlike Chat, they run
**alongside** the active Chat rather than instead of it. Voice Recognition produces the raw
transcript; Speech Processing optionally cleans it; Audio speaks text back. Speech Processing is
lazy, so its model is only loaded when cleanup is used or the engine is started from the node menu.

## The engines

| Engine | Default port | Model | Status |
|---|---|---|---|
| `whispercpp` | `8090` | `ggml-base.en` (whisper.cpp) | Built; downloaded on first run |
| `parakeet` | in-process | Parakeet v3 ONNX bundle | Built, but transcription is behind a cargo feature |
| `audiocpp` | `8086` | Parakeet-TDT Q8 + PocketTTS Q8 | Optional native runtime; installed on first use |
| `llamacpp-speech` | `8088` | S1-mini by Superwhisper (`s1-mini-q4_k_m.gguf`) | Downloaded with the default local models; lazy |

Whisper.cpp is the local fallback Voice Recognition engine. Its model path defaults to
`~/.ryu/models/ggml-base.en.bin` and is overridable with `RYU_WHISPER_MODEL`. Feature builds that
include `voice-parakeet` use Parakeet as the default Voice Recognition engine.

Parakeet v3 is a second, ONNX-based engine that runs in-process via the `transcribe-rs` crate. Its
model bundle downloads from a public host. In-process inference is gated behind the off-by-default
`voice-parakeet` cargo feature (it pulls a heavy native ONNX Runtime dependency). Without the feature,
the lifecycle, download, and routing are all present, but a transcription request returns a clear
"feature not built" error.

audio.cpp is the native process alternative. Core downloads the pinned `audiocpp_server` release
and its default Parakeet-TDT and PocketTTS GGUF packages into the node's Ryu data directory, writes
the server config, and starts it on loopback port `8086` (the development profile adds the normal
Ryu port offset). It is optional and independent of the in-process Parakeet feature. Set the
`audiocpp` engine in Voice Recognition or Audio settings to route a request there.

## Speech Processing

S1-mini by Superwhisper is the default Speech Processing engine. It is a local 0.6B English text
normalizer, separate from the Voice Recognition engine and the resident Chat engine. Core serves it
through a dedicated llama.cpp instance on port `8088`, using the Q4_K_M GGUF from
`superwhisper/s1-mini-GGUF`. The model is downloaded through the shared checksum-verified download
center during first-run setup and can be installed again from the Speech Processing layer when a
download was skipped or failed.

The weights are downloaded at runtime rather than bundled in the desktop installer. S1-mini is
Apache 2.0 with Superwhisper's naming clause; keep the exact name **S1-mini by Superwhisper** when
showing or redistributing the model, and retain the upstream [license](https://huggingface.co/superwhisper/s1-mini-GGUF/blob/main/LICENSE).

S1-mini must receive its published system prompt, a control line, greedy decoding (`temperature: 0`),
and thinking disabled. Ryu sends those settings through the Core route; callers should not treat it
as a general chat model. The supported controls are:

| Control | Values | Default |
|---|---|---|
| Style | `casual`, `semi-casual`, `semi-formal`, `formal` | `semi-formal` |
| Structure | `prose`, `lists` | `prose` |
| Context | `general`, `email` | `general` |

The cleanup route is:

```
POST /api/voice/speech-processing
```

It accepts `{ text, engine?, styling?, structure?, context? }` and returns `{ text, engine, model }`.
The model install route is `POST /api/voice/speech-processing-model/install`; discovery is
`GET /api/voice/speech-processing-engines`. Both are protected by the Voice app gate.

System-wide Dictation enables this stage by default on new installs, but the user can turn it off
in Dictation settings. When disabled, no cleanup request is made and the raw ASR transcript is
inserted. If a cleanup request fails, Dictation fails open to the raw transcript.

## Voice Recognition

```
POST /api/voice/transcribe?engine=whisper|audiocpp|parakeet|gateway
```

The request is a multipart form with the audio bytes in a `file` field, and the response is the
transcribed `text`. The `engine` query parameter selects which voice engine handles the request.

In the desktop app, the composer's microphone button captures 16 kHz mono WAV through the Web Audio
graph and POSTs it to this endpoint, then appends the transcript to your message. See
[the desktop tour](/docs/surfaces/desktop/user-guide) for the UI.

## Audio

Audio is the generative counterpart to whisper and parakeet's transcription. Like the Voice Recognition
engines, Audio engines are opt-in and run alongside Chat. There are three local paths: the native
audio.cpp server, the built-in OuteTTS engine, and a universal sidecar that fronts many other engines.

### Native audio.cpp

The `audiocpp` engine uses audio.cpp's OpenAI-compatible `/v1/audio/speech` route. Ryu's managed
config declares the same server for PocketTTS TTS and Parakeet-TDT STT, so installing the curated
audio.cpp voice model provisions both capabilities. The default TTS voice is `alba`; `speed`,
`language`, and a reference voice path are passed through when supplied. An explicit `audiocpp`
selection returns an actionable error when the runtime or model is unavailable rather than silently
switching to OuteTTS.

The upstream runtime supports more model families than Ryu's curated package currently provisions.
Those upstream packages need a compatible audio.cpp server config and model-specific validation;
they are not implied by the single `audiocpp` picker row. See the [audio.cpp project](https://github.com/0xShug0/audio.cpp)
for its current model matrix.

<Callout type="warn">
  The Audio engines are opt-in. An installed `audiocpp` runtime starts with the other managed
  sidecars; built-in OuteTTS remains a per-request CLI path, and the universal RyuTTS sidecar is
  still separately installed. Built-in OuteTTS synthesis has not been exercised live here. On the
  universal sidecar, Pocket TTS was verified producing a WAV, but KittenTTS install is blocked by an
  upstream `misaki` dependency pin. The sidecar needs Python.
</Callout>

### Built-in OuteTTS

The built-in engine (`outetts`) has **no resident server**. Each `POST /api/voice/speak` shells out
to the `llama-tts` CLI, which ships in the same llama.cpp release as `llama-server` and is extracted
by `LlamaCppDownloader::ensure_tts_binary` (`apps/core/src/sidecar/providers/outetts/downloader.rs`).
`llama-tts` runs an OuteTTS GGUF plus a WavTokenizer vocoder GGUF and writes a WAV file, which Core
reads back and returns as `audio/wav` (`apps/core/src/sidecar/providers/outetts/mod.rs`). Because
there is no server, the sidecar lifecycle maps to "binary plus models present": `start` ensures the
binary and both models are installed, `stop` marks it not ready.

The two models are swappable defaults, not locks. The OuteTTS language model and WavTokenizer vocoder
paths are overridable with `RYU_OUTETTS_MODEL` and `RYU_OUTETTS_VOCODER`.

| File | Default | Override |
|---|---|---|
| Language model | `OuteTTS-0.2-500M-Q4_K_M.gguf` (~400 MB) | `RYU_OUTETTS_MODEL` |
| Vocoder | `WavTokenizer-Large-75-F16.gguf` (~130 MB) | `RYU_OUTETTS_VOCODER` |

Both default to `~/.ryu/models/`. If the binary or either model is missing, `/api/voice/speak`
returns a clear error pointing you to install the OuteTTS voice engine from the Store first.

### Universal Ryu Audio sidecar

For engines beyond OuteTTS, Core manages the `ryutts` sidecar (`apps-store/voice/`), a small Python
FastAPI server on port `8085` that fronts many Audio engines behind one normalized HTTP contract:
`/health`, `/engines`, `/generate`, `/unload`. Adding an engine is one backend file plus one registry
row in that app, so Core never grows a per-engine branch
(`apps/core/src/sidecar/providers/ryutts/mod.rs`).

Two engines are seeded:

| id | Model | Notes |
|---|---|---|
| `kitten` | KittenTTS (15-80M ONNX) | CPU-only, fixed expressive voices |
| `pocket` | Kyutai Pocket TTS (100M) | ~6x realtime on CPU, voice cloning via `reference_audio` |

Core adopts an already-running sidecar (for example `bun run dev:tts`) rather than spawning a
competing process; otherwise it spawns `python -m ryu_tts` from the installed sidecar directory
(overridable with `RYU_TTS_DIR`, interpreter with `RYU_TTS_PYTHON`). Heavy per-engine inference
dependencies are the user's to `pip install`. Core points the sidecar's `HF_HOME` at
`~/.ryu/models/hf` so every downloaded model's bytes live under `~/.ryu` and Core's catalog can detect
installs (`RYU_TTS_HF_HOME` overrides).

### Speaking

```
POST /api/voice/speak
```

The body is `{ text, engine?, voice?, speed?, language?, reference_audio? }` and the response is an
`audio/wav` body. The `engine` field selects the path: omitted or `"outetts"` runs the built-in
`llama-tts` path, `"audiocpp"` uses the native audio.cpp server, and other ids (for example
`"kitten"` or `"pocket"`) are proxied to the RyuTTS sidecar's `/generate`. An explicit `audiocpp`
selection does not silently fall back to another engine when its runtime is unavailable.

Engine and model discovery exposes the built-in/native rows plus the RyuTTS registry:

| Action | Endpoint |
|---|---|
| List available Audio engines (built-in plus whatever the sidecar serves) | `GET /api/voice/tts-engines` |
| List the curated, installable Audio model catalog | `GET /api/voice/tts-models` |
| Install a curated model into the Core-managed HF cache | `POST /api/voice/tts-models/install` |

`GET /api/voice/tts-engines` always includes the built-in `outetts`, native `audiocpp`, and the cloud
slot, then appends the sidecar's `/engines` catalog when it is reachable. The curated model catalog
is the voicebox-style known-good set, distinct from the raw Hugging Face
audio-generation browse in the Models tab. Curated installs run `huggingface_hub.snapshot_download`
into the Core-managed cache and are registered with the download overlay as a spinner entry, since
Hugging Face reports no byte total there.

In the desktop app, Settings then Voice has an engine and voice picker plus a "Test voice" button
(`apps/desktop/src/components/settings/TtsEngineSettings.tsx`). The engine set comes from
`/api/voice/tts-engines`, so it reflects whatever Core and the sidecar registry serve. The choice is
persisted to localStorage so any future in-chat "speak" surface can read the same default. The Voice
page also links directly to Keyboard Shortcuts, where voice-mode and other voice actions can be
customized.
