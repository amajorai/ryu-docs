title: "Chat Engines"
description: The local chat engines Ryu can install or connect, their platform requirements, where their models are stored, and how to configure them.
---

Open **Store → Engines** to install or connect a Chat engine. Ryu can manage local runtimes or
connect to a runtime configured in its own desktop app. The connected node determines which engines
are available.

## Engines

| Engine | What it runs |
|---|---|
| `llamacpp` | Local GGUF models using llama.cpp. This is the default local runtime. |
| `ollama` | Models managed by Ollama. |
| `vllm`, `sglang` | High-throughput local serving runtimes. Linux only (x86_64 or arm64), ideally with an NVIDIA GPU. |
| `mlx`, `mlx-vlm`, `mlx-serve`, `omlx` | Apple Silicon runtimes for text and multimodal models. `mlx-serve` also needs macOS 26.2 or newer. |
| `apfel` | Apple Foundation Models. Needs Apple Silicon with macOS 26 or newer and Apple Intelligence on. |
| `mesh-llm` | Local serving and distributed inference managed by Mesh LLM. |
| `lemonade` | Local models managed by Lemonade Server. |
| `magnitude` | Local models managed by Magnitude, which tunes its kernels for Apple Silicon, NVIDIA, AMD, or CPU. |
| `llama-swap` | Models and backend processes managed by llama-swap. |
| `freetoken` | NVIDIA-focused local inference managed by FreeToken. Linux or Windows on x86_64. |
| `docker-model-runner` | Models managed by Docker Model Runner. |

Availability and install controls are based on the connected node. An engine the node can't run
stays listed but dimmed, with the exact reason (for example "Needs a Mac with Apple Silicon running
macOS 26.2 or newer"). Core enforces the same check when you install, start, or switch to an engine,
so an engine copied over from another computer's data folder can't be launched on the wrong
platform.

The **llamacpp-embed** server is separate backing infrastructure for semantic embeddings. Configure
it from the llama.cpp detail page under **Embedding engine**.

## Configure an engine

Choose an engine in **Library → Engines** or **Store → Engines** to open its shared configuration,
including lifecycle actions and adapter limits. Sampling defaults apply to chat requests sent to that
engine. Where Ryu has verified an engine adapter, the detail page also shows engine-specific launch
controls. Raw request fields are available for other server options. Request-level settings can
override engine defaults.

Launch settings take effect the next time a managed runtime starts. For a runtime Ryu only connects
to, its detail page can save a raw launch-argument profile to copy into that runtime's own settings;
Ryu does not apply those arguments to an external process. The llama.cpp detail page keeps Chat and
embedding launch settings separate. See
[Advanced engine configuration](/docs/surfaces/desktop/engines/advanced-inference) for the settings
and adapter limits by engine.

Only one local Chat runtime is active at a time. Switching engines does not remove models or change
the configuration held by an upstream runtime.

## Where models are stored

Engines that Ryu installs live in the data folder under `engines/chat/<engine>/`, and their models
stay in the data folder too, so moving or resetting the folder covers them:

| Engine | Model location |
|---|---|
| llama.cpp | `models/chat/<stem>.gguf`, with vision projectors next to the model |
| vLLM, SGLang, MLX, MLX-VLM | Catalog installs in `models/chat/snapshots/<repo>/`; anything else the engine downloads from Hugging Face goes to `models/hf/` (Ryu sets `HF_HOME`) instead of `~/.cache/huggingface` |
| Ollama started by Ryu | `models/chat/ollama/`, unless you set `OLLAMA_MODELS` |
| oMLX started by Ryu | `models/chat/omlx/`, unless you set `RYU_OMLX_MODEL_DIR` |
| MLX Serve started by Ryu | `models/chat/mlx-serve/`, unless you set `RYU_MLX_SERVE_MODEL_DIR` |

Paths are relative to the [data folder](/docs/surfaces/desktop/user-guide/data-and-storage#whats-in-the-data-folder).
Removing an engine and its data deletes only these Ryu-owned folders. It never deletes `~/.ollama`,
`~/.cache/huggingface`, or a model folder you chose yourself, and shared stores such as `models/hf/`
and catalog snapshots stay until you remove those models from the catalog.

## Engines managed by another app

For **Lemonade Server**, **Magnitude**, **Ollama**, **llama-swap**, **FreeToken**,
**Docker Model Runner**, and **Mesh LLM**, install the runtime and prepare its models in the
upstream app. Then open its entry in **Store → Engines**, choose **Add** or **Enable**, and select a model exposed by that runtime.
Model downloads, hardware tuning, and external process settings remain with the runtime that owns
them.

See the upstream guides for [Lemonade Server](https://lemonade-server.ai/docs/guide/install/),
[Magnitude](https://docs.magnitude.dev/get-started),
[llama-swap](https://github.com/mostlygeek/llama-swap),
[FreeToken](https://github.com/FlashML-org/FreeToken),
[Docker Model Runner](https://docs.docker.com/ai/model-runner/), and
[Mesh LLM](https://github.com/Mesh-LLM/mesh-llm).

Ryu connects to Magnitude on its default local API at `http://127.0.0.1:10100`, so keep the
Magnitude app open or run `magnitude serve` on a headless machine. For a Magnitude server on another
machine, add it as an OpenAI-compatible provider in **Settings** with its `/inference/v1` base URL
and API key.

## Apple Silicon engines

The MLX engines appear when the connected node supports them. MLX-VLM handles multimodal models;
the other MLX entries expose the text or GGUF formats supported by their runtime. Model catalogs
and runtime options can vary by upstream version.

## Managed runtime readiness

A managed llama.cpp runtime must report the selected model before Ryu publishes its
local provider connection. An exited process or a different model cannot satisfy
that readiness check. Image input also needs the selected model's compatible
multimodal projector. Other models' vision support depends on their backend.

Managed vLLM, SGLang, MLX, oMLX, and Apple Foundation Models runtimes follow the same rule:
Ryu will not start one when another process already holds its port, and the runtime is ready
only when the process Ryu started answers its API. vLLM and SGLang must also report the
selected model. If the runtime exits during startup, Ryu reports the failure with its last
error output instead of waiting. Apple Foundation Models run on their own port, so they
work while an Ollama server is also running.

Ryu owns its managed MLX Serve process. Stop an existing server before starting
MLX Serve in Ryu; another process's health response cannot establish ownership.
Forwarded requests are refused when the managed engine is stopped or its process
identity cannot be verified. Model discovery stays with MLX Serve.
