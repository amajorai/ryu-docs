title: Chat
description: The local Chat runtimes Core can run, and how to swap the active one.
---

Chat is an OpenAI-compatible inference server bound to a model. Core can manage several, but **only
one is the resident, active local runtime at a time**. The Gateway routes local model calls to
whichever runtime is active.

## The engines

| Engine | Default port | Process | Default model |
|---|---|---|---|
| `llamacpp` | `8080` | `llama-server` | Gemma 4 E2B-it Q4_K_M (the bundled default) |
| `llamacpp-embed` | `8081` | `llama-server --embeddings` | nomic-embed-text v1.5 (for RAG) |
| `ollama` | `11434` | `ollama serve` | user-managed |
| `vllm` | `8000` | vLLM OpenAI server (Python) | Qwen2.5-1.5B-Instruct |
| `sglang` | `30000` | SGLang server (Python) | Qwen2.5-1.5B-Instruct |
| `mlx-serve` | `11234` | native Zig MLX + GGUF server | models configured by mlx-serve |
| `docker-model-runner` | `12434` | Docker Model Runner (adopt-only) | any HF GGUF / Docker Hub model you pull |
| `mesh-llm` | `9337` | Mesh LLM (adopt-or-start) | models configured by Mesh LLM |

`llamacpp` is the default Chat runtime, installed and downloaded on first run. `llamacpp-embed` is a
second llama.cpp instance dedicated to embeddings; it runs alongside Chat and is in the
startup order, so RAG gets real semantic vectors on install. `vllm` and `sglang` are Python-based and
require their packages installed; each resolves its model from an environment variable
(`RYU_VLLM_MODEL`, `RYU_SGLANG_MODEL`) or a built-in default.

`docker-model-runner` is **adopt-only**: Ryu downloads nothing - it routes to Docker's built-in model
server, which serves any Hugging Face GGUF (Llama, Qwen, …) or Docker Hub model you pull. You install
Docker Desktop and enable it yourself. See **[Docker Model Runner](/docs/surfaces/desktop/engines/docker-model-runner)**
for the full setup.

`mesh-llm` is an opt-in local engine for the [Mesh LLM project](https://github.com/Mesh-LLM/mesh-llm).
Mesh LLM exposes an OpenAI-compatible API at port `9337`, can serve a model locally, and can route
through its own distributed mesh. Ryu does not reimplement that runtime or copy its model cache: it
adopts an already-running `mesh-llm` process or starts the installed executable in headless serve
mode, then points the existing Gateway `local` provider at it. The port is profile-shifted when Ryu
starts the process, so development and release nodes do not collide. Install Mesh LLM from its
documented release or package-manager path, then choose **Mesh LLM** in Store → Engines.

If you start Mesh LLM yourself, use the active Ryu profile's port. The Outreach companion can then
send its draft requests through the same governed `model.complete` bridge; enter the model id shown by
Mesh LLM's `/v1/models` endpoint when you want a specific model.

`mlx-serve` is an opt-in native Apple Silicon engine for the
[mlx-serve project](https://github.com/ddalcu/mlx-serve). It runs as a single Zig binary without a
Python runtime, serves MLX and GGUF models, and exposes the OpenAI-compatible API Ryu already uses.
Core starts the CLI with its model directory, an explicit loopback bind, and the active profile's
port (`11234` in release, `12234` in dev). Models and model discovery remain owned by mlx-serve;
they are not copied into Ryu's model catalog by this integration. The current upstream release
requires Apple Silicon macOS 26.2+.

<Callout type="info">
  Apple Silicon also has four MLX engines (`mlx`, `mlx-vlm`, `mlx-serve`, `omlx`) that appear only on
  arm64 macOS nodes. `mlx-serve` currently requires macOS 26.2+. They follow the same active-engine
  swap as the engines above, but model-directory engines remain outside format-derived Models Store
  activation.
</Callout>

<Callout type="info">
  These ports are configured defaults. The Gateway runs on its own port (`7981`), so it no longer
  contends with `llamacpp` on `8080`. If you point two engines at the same port, change one through
  its configuration (the Gateway via `RYU_GATEWAY_URL`, llama.cpp via the registry).
</Callout>

## The active engine

Core tracks one resident local engine and persists the choice in `~/.ryu/active-engine.json`, so it
survives restarts (`apps/core/src/sidecar/active_engine.rs`).

| Action | Endpoint |
|---|---|
| Report the active engine and what is available | `GET /api/engine/active` |
| Swap the active engine | `POST /api/engine/active` |

Swapping stops the incumbent and starts the new engine under a lock, so at most one resident Chat
runtime runs at a time. The choice is persisted before the start completes, so your intent is durable
even if the start fails. When Core spawns the Gateway, it sets `LOCAL_LLM_URL` to the active engine's
URL so the engine registers as a routable provider.

## Swappable defaults

The default chat and embedding models are resolved through the registry, in order of precedence:

1. An environment variable (for example `RYU_LOCAL_CHAT_MODEL_URL`).
2. A built-in constant.

This is how you change the bundled model without recompiling. To browse and install other GGUF
models, see [Models](/docs/surfaces/desktop/models).

**Model weights are environment variables only, not `registry.json`
keys.** The file has no `local_chat_model_*`, `local_embed_model_*`, `local_reranker_model_*`,
`local_classifier_model_*`, `embed_model`, `embed_dims` or `embed_base_url` field, and writing one
does nothing. That is deliberate. One moment downloads a weight to `~/.ryu/models/<id>.gguf`
(onboarding, once, at boot) and a different moment serves it (a llama.cpp sidecar, lazily, much
later); a file that can be edited between those two moments lets the sidecar hunt for a weight
nobody downloaded. Freezing the answer for the life of the process makes them agree by construction.
The embedding values are the same story against a different artifact — the vector space of your
`spaces.db`, `retrieval.db` and `message-embeddings.db`.

`registry.json` remains the place for `default_llm_base_url`, `default_llm_model`, `providers`,
`default_agent_id`, `rag_strategy`, `reranker_model`, `reranker_base_url` and
`graph_extraction_model` — every one of which is read by consumers that do open the file.
