## Agent session controls

The chat surface follows the interface you pick from the **Ryu** lockup at the top of the sidebar
([Interfaces](/docs/surfaces/desktop/interfaces)). Switching to **Bot** selects **Ryu Work**, and
switching to the others selects **Code**. You can also flip the **Ryu Work** / **Code** switch in the
account menu. **Ryu Work** keeps the agent picker visible but hides model, approval, and effort
controls, and Core automatically routes the turn's model for the selected agent.

**Code** exposes the explicit model, ACP session, workspace, and full
transcript controls. Hidden model and effort choices are not sent as request pins, so Ryu Work does
not override automatic model routing. For an ACP agent, Ryu Work chooses its
advertised **Auto** permission preset when one exists; otherwise it chooses an advertised
approval/default preset, or leaves the agent's own default in force. This only hides configuration
controls: agent safety approvals still apply and approval prompts still appear when a turn needs one.

Ryu Work also selects the built-in **Agents view** sidebar automatically. Each bot's direct threads
appear inline beneath its row, while group or otherwise-unassigned conversations stay reachable in
the **Other chats** section below the roster. No separate app or plugin is required.
The view is labeled **Bots view** when **Use Bot terminology** is enabled and **Agents view** when
it is off.

In **Other chats**, you can organize the fallback conversations locally into custom sections. Create
a section from that header, drag chats into it, and drag section headers to reorder them;
**Unorganized** is the default first section but can be moved too. Renaming or deleting a section
changes only this Desktop sidebar: deleting one returns its chats to Unorganized and never deletes
the conversations. Chats inside every section stay sorted by newest activity.

## Branch a conversation

Every message has a **branch** action in its hover toolbar. Branching forks the conversation up to
that message into a new, independent conversation in a new tab, so you can explore an alternative
direction without disturbing the original thread. Before it runs, choose whether to **Fork in this
workspace** or **Fork in a new worktree**. The first keeps the branch in the current workspace; the
second starts the next turn in an isolated worktree so changes stay separate until you apply them.
Conversations stay linear - there is no in-place message tree. For how the fork is stored, see
[Conversations and Sessions](/docs/core/conversations-sessions).

In the **Agents view**, the sidebar presents those independent conversations as a branch-style thread list
under the bot. Expand the bot to browse its direct threads, including newly-created forks, with the
same paging and searchable overflow controls used by other sidebar sections. Group or unassigned
conversations appear in **Other chats** instead of being hidden. If a conversation has
multiple participants, the Chats list converges its related conversations into a **Group chat** with
a 2x2 grid of participant avatars (groups of more than four show three avatars and a **+N** count of
the rest in the bottom-right corner) and expandable child threads.

Agent-to-agent Switchboard activity
also stays visible in the workspace transcript as one **Messaged** line per fan-out, showing the
recipients' avatars and a count. Select it to choose a recipient and open that exchange, including
both sides of a completed `agents.ask`, as a **Sender ⇄ Recipient** conversation.

## Keep a chat's workspace tabs

With the standard tab layouts, a chat's workspace tabs live in the window's
[Right and Bottom panes](/docs/surfaces/desktop/user-guide/tabs-and-panes#right-and-bottom-panes), which Ryu
remembers when it reopens. Tabs a chat saved in an earlier version reopen there once, in the
background, and tabs pinned to a project become that project's pane tabs. Artifact, inspector, and
subagent-detail tabs are not carried over, because their content ended with the earlier session.

In the scrolling and **Infinite canvas** tab layouts, each chat keeps its own bottom and right docks.
When you reopen a desktop chat tab there, Ryu restores its open bottom and right workspace tabs,
their selected tab, and whether each dock was open. This includes project tabs such as **Terminal**,
**Files**, **Changes**, and installed workspace panels, as well as chat-run tabs such as **Sources**
and **Subagents**. Project tabs that were pinned remain shared with the other chats in that
workspace; unpinned tabs return to the chat that opened them.

Pinned tabs retain their identities when the app reopens, including multiple tabs of the same kind.
A saved panel that this version cannot render keeps its identity and label and shows an
unavailable-panel message. Older saved pinned layouts are upgraded automatically. Closing a dock removes its controls from
keyboard navigation; use the toolbar button or hover over the right edge to bring it back.

The pinned summary also lists background processes for the chat. If stopping a process fails,
Ryu keeps it in the list and shows a retry message. Stop it again to retry; it disappears from
the list after the node confirms the stop.

Changing the selected node or signing in as a different user clears the previous background
process list. Stop requests stay attached to the node and user that started them; a late
response cannot show an error or stop a process for the newly selected user. Returning to
the original node waits for its pending Stop request before allowing another request.

## Edit and regenerate with versions

Every user message has an **edit** action, and every assistant reply a **regenerate** action, in
its hover toolbar. Editing a message or regenerating a reply forks a new version in place rather
than overwriting: a `< n / m >` pager appears on the affected turn so you can page between versions
and pick the one to keep. Unlike branching, this stays in the same conversation. Core keeps a
version tree over the flat history (`POST /api/conversations/:id/messages/:message_id/edit`,
`/regenerate`, and `/select`).

## Annotate a selection

Select any text in a message and a small annotate box opens, with the cursor in its note field.
Type a note or question if you want one, then pick an action under the box. The note is
optional, and every action still works on the selection alone.

- **Quote** drops the selection into the composer as a pending quote and puts your note in the
  composer as the reply text. When you send, the quote is prepended to your message as a leading
  Markdown blockquote. Pressing **Enter** in the note box does the same.
- Enabled plugins can add actions to the same row. The built-in Side Chats plugin contributes
  **Ask in side chat**, **Explain**, and **Fix grammar**. They send the highlighted text, your
  note, the visible main-chat context, and the active main-chat model to the no-tools side chat;
  the answer stays out of the main timeline. With **Ask in side chat**, the note is your
  question.

**Esc** or clicking elsewhere closes the box. Copying with the box open still copies the
highlighted text.

## Message timestamps

Hover any message, user or assistant, and its send time shows in the hover toolbar beside Copy and
Branch. The time comes from Core's stored `created_at`, set when the message is saved.

## Rate replies with thumbs up or down

Each assistant reply carries thumbs-up and thumbs-down buttons in its hover toolbar
(`POST /api/conversations/:id/messages/:message_id/feedback`). One vote has three effects: it is
saved on the message, it upgrades the continual-learning reward from a model guess to your human
label, and (on by default, local and private) it writes a memory fact. Vote again to clear it.

<Callout type="info">
  Voting on a reply you just received works through a latest-turn fallback. Voting on an older
  reply in a session you have not reloaded may need a reload first.
</Callout>

## Runs, cost, and trace for a conversation

Outside **Ryu Work**, the composer toolbar has a **Sessions** button (activity icon) once a
conversation exists. It lists the runs recorded on this conversation with their status, plus the number of
model calls, the estimated cost, and the total model latency, taken from the Gateway audit. Cost shows a
dash when cost attribution is off.

After a reply finishes, a collapsed **Run trace** row sits under the diff review. Expand it to see the
ordered steps the run took: each model call and tool call, how long it took, and any error. Token counts
and cost are not part of the trace; they stay in the Gateway audit.

## Session stats

The pre-installed **Session Stats** plugin places a compact readout under the latest reply. It combines
the structured usage that a provider reports with the saved transcript, so the same widgets work for
ACP agents, BYOK endpoints, Ryu providers, and local models. Providers that do not report a value
leave that widget hidden instead of showing zero.

The readout includes:

- **Turns** and **Steps** for the current transcript session.
- **Tokens Input**, **Tokens Output**, **Tokens Cached**, and **Tokens Total**. Input and output use
  cumulative transcript metrics when available, with the provider's context-window totals as a
  fallback; cached and total counts stay transcript-based.
- **Cache Hit Rate**, **Cache Read**, and **Cache Write**, including each cache value's share of the
  prompt context. The default is the latest turn; open the stats card to switch to cumulative
  session totals.
- **Cache Timer**, which shows a hot glyph during the active main-chain turn, then estimates the
  prompt-cache lifetime. The default is five minutes; a one-hour TTL and custom hot/countdown/cold
  glyphs are available in the card settings. The timer is best-effort because some transcripts expose
  cache activity but not the provider's expiry timestamp.
- **Input Speed**, **Output Speed**, and **Total Speed** as session averages. A rolling window from
  0 to 120 seconds can be selected; zero means the full session.
- **Context Length**, **Context Window**, **Context %**, **Context % (usable)**, and a context bar.
  The window prefers the provider's reported context window, then a model suffix such as `[1m]`,
  then a 200,000-token fallback.
- **Compaction Counter**, with total/auto/manual/unknown/reclaimed selectors, optional trigger
  detail, reclaimed-token totals, and independent controls for each add-on.
- **Cost**, when the provider reports an amount and currency.
- **Session Usage**, **Weekly Usage**, per-model weekly windows, extra usage, and block/weekly reset
  timers when the selected subscription account exposes them. Usage can be shown as used or remaining
  percentages; session and weekly bars include an optional reset-window time cursor. Reset timers can
  show remaining time, elapsed progress, or the exact reset date/time with local/UTC timezone and
  locale controls. Sonnet, Opus, and Fable windows are omitted when the account does not report them.

When the chat runs on a Ryu subscription provider with saved logins, the usage shown is the reading
for the login Ryu knows the conversation uses, and the readout names that login. If Ryu only knows
which login is active for the provider, the name is marked **(active account)**: that is the login the
next turn would start on, which an account pool may change.

Subscription usage polling runs only for the active chat with stats enabled. Cached usage is scoped
to the node credentials and caller identity.

The card's **Hide unavailable or empty metrics** setting keeps a provider with partial usage support
compact. Immediately after a compaction boundary, the context display uses the boundary's
`postTokens` until a later main-chain usage frame reports a fresh current value.

For provider prompt-cache behavior and the built-in agent context and Gateway trace views, see [Provider prompt caching](/docs/providers/prompt-caching).
