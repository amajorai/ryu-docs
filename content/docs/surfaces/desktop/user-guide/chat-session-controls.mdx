## Agent session controls

The chat surface has an **Interface mode** switch directly in the account menu. **Ryu Work** keeps the
agent picker visible but hides model, approval, and effort controls; Core automatically routes the turn's
model for the selected agent. **Code** exposes the explicit model, ACP session, workspace, and full
transcript controls. Hidden model and effort choices are not sent as request pins, so Ryu Work cannot
accidentally override automatic model routing. For an ACP agent, Ryu Work quietly chooses its
advertised **Auto** permission preset when one exists; otherwise it chooses an advertised
approval/default preset, or leaves the agent's own default in force. This only hides configuration
controls: agent safety approvals still apply and approval prompts still appear when a turn needs one.

Ryu Work also selects the built-in **Agents view** sidebar automatically. Each bot's direct threads
appear inline beneath its row, while group or otherwise-unassigned conversations stay reachable in
the **Other chats** section below the roster. There is no separate Sessions toggle to maintain. This
is part of the Core/desktop experience; no separate app or plugin is required.
The view is labeled **Bots view** when **Use Bot terminology** is enabled and **Agents view** when it is off.

In **Other chats**, you can organize the fallback conversations locally into custom sections. Create
a section from that header, drag chats into it, and drag section headers to reorder them;
**Unorganized** is the default first section but can be moved too. Renaming or deleting a section
changes only this Desktop sidebar: deleting one returns its chats to Unorganized and never deletes
the conversations.
Chats inside every section stay sorted by newest activity.

In the **Agents view**, open an agent's context menu and choose **Pin agent** to keep it at the top of the
roster. Pinned agents are removed from the ordinary list so they do not appear twice: one pinned
agent gets a larger hero tile, two use a two-up pair, and three or more use a compact three-up grid.
Use the pin control on a tile, or the same context menu, to unpin it.

For a code session with a saved project folder and branch, **Code** mode can show a compact
pull-request status icon beside the chat when the **Pull Requests** app finds a request. The icon is
shown only for these code sessions in Code mode: open is GitHub green, draft is gray, closed is red,
and merged is purple. It links to the request; Ryu Work keeps the simplified sidebar row.

Ryu's native agent does not publish ACP permission presets, so Ryu Work leaves its Core approval
policy in force for that agent. The separate **Auto** entry in the agent picker is agent-auto
routing: it chooses which agent handles a turn, using its configured local classifier, and is not a
permission mode or a replacement for the selected agent.

When the active agent is an ACP agent, the composer surfaces per-agent session controls: pickers for
the agent's permission mode, reasoning effort, and model. Nothing here is hardcoded by Ryu. Each
picker is built from what the agent advertises at `session/new`, so a control only appears when that
agent actually reports it (`apps/desktop/src/lib/api/acp.ts`,
`apps/core/src/sidecar/adapters/acp.rs`).

| Control | When it appears | Source |
|---|---|---|
| **Permission mode** | The agent reports modes (for example `Auto`, `default`, `acceptEdits`, `plan`, `bypassPermissions`) | The agent's advertised mode set and active mode |
| **Reasoning effort** | The agent exposes a `thoughtLevel`-style select config option | That config option |
| **Model** | The agent supports the unstable ACP session-model capability | That capability (null and hidden otherwise) |

Core fetches this advertisement once per agent via `GET /api/agents/:id/acp-config` (cached per
agent) and returns all-null for non-ACP agents. Your choice is applied to the next chat turn, which
Core re-applies to that turn's session.

The picker adapts to the composer’s available width, which is useful in a split pane. The active
agent stays named as the orientation cue; the model label becomes a model icon when space is tight,
reasoning effort becomes a small stepped bar meter, and secondary controls progressively become
icons or remain available in the picker. Hover text and accessible labels retain the full setting
names.

You can choose where this shared **model and agent picker** lives in **Settings → Appearance →
Interface → Chat model & agent picker**. **In composer** is the default. **In tab bar actions tray**
moves the same picker to the actions beside the chat tabs, leaving the composer controls less busy.

The same Interface page has **Show latest message / tool state in sidebar**. When enabled, ordinary
chat sessions become two-line rows: the second line rotates between the latest message and an active
run state such as **In progress**, **Needs input**, or **Interrupted**. The setting does not change
The **Agents view** always keeps its own two-line agent rows. Both layouts use the app-wide
**Enable animations** preference, so disabling animations leaves the latest state visible without
the transition.

### Keep inactive thread views from using memory

Desktop automatically unloads inactive tab trees after **10 minutes** by default. Set the window in
**Settings → General → Tabs → Unload inactive tabs**, or choose **Never** to keep every tab mounted.
Unloading only unmounts the route and its in-memory message parts, providers, and subscriptions; the
conversation transcript remains in Core's durable store and reloads when you focus the tab. The
currently active, pinned, split-visible, and running tabs are always protected. This is a built-in
Desktop lifecycle control, not a plugin, and is separate from the Gateway's ACP subprocess timeout.

Hover a chat row to open its preview popover. Alongside the title, branch, folder, worktree, and
agent details when available, it shows **Messages**, the authoritative total for that conversation.
This makes the size of a thread visible without opening it.

Messages with Markdown tables—including your sent messages and assistant replies—keep a compact,
horizontally scrollable presentation in the transcript. A soft fade at the visible edge shows when
more columns are available. Hover a table and select the expand button in its top-right corner to
open a larger dialog; the expanded table can scroll in both directions while you keep the surrounding
chat in place.

The **Enable animations** switch in **Settings → Appearance → Motion** is the master control for
new chat motion, including sidebar state rotation, loading treatments, and composer progress motion.
The operating system's reduced-motion preference takes priority. Plan and file-change chips above
the composer remain translucent with a blurred backdrop so they stay readable over the chat without
becoming an opaque panel.

If you change the composer target while an agent is replying, Ryu shows a brief confirmation that
the agent, model, or effort choice will be used on the next turn. Idle changes stay quiet because
the next message is already the next turn. You can choose **Settings → General → Chats → Composer
selection changes** to describe these changes as applying on the next turn or from your next user
message.

### Agent-controlled target changes

An active agent can request a different installed agent, model, or reasoning effort for the next
user turn through the built-in `agent_control.set_active_target` tool. Core validates the request
against the current conversation, applies it once after normal model routing, and leaves saved agent
defaults unchanged. The desktop adopts an agent handoff for the conversation and shows the effective
agent/model/effort in the transcript. This is separate from model routing: routing decides from the
user's message, while agent control is an intentional escalation or handoff requested during the
agent's work. For ACP targets, Core applies the effort through the target's advertised/conventional
effort option when one is available; an agent with no supported effort control continues on its own
default.

### Interactive tool-permission prompts

When an agent in a gating permission mode wants to run a tool, Core streams a `data-ryu-permission`
part and pauses the turn. The desktop renders the agent's offered options (allow once, allow always,
reject once, reject always) in the same composer surface as the chat editor. If you are typing, Ryu
keeps the draft uninterrupted and waits for the shared 2.5-second idle window before morphing the
editor into the approval card. Your choice is sent to `POST /api/chat/permission`, keyed by the
request id, which unblocks the awaiting turn.

In **Ryu Work**, this card uses plain-language action text and keeps raw commands out of the approval
surface. **Code** can show the technical tool details when you need to inspect exactly what the agent
requested.

### Agent questions

When an agent needs structured input, its Q&A card takes over the same composer surface as the chat
editor. If you are already typing a chat message, Ryu keeps the draft uninterrupted and waits until
you have stopped editing for 2.5 seconds before morphing the editor into the pending question. Until
then, the question stays visible in the conversation. The microphone is also available inside the
card's **Other** input and its free-text question input, so spoken answers can be transcribed
without leaving the pending question.

<Callout type="warn">
  These controls are data-driven, so they only appear when the ACP agent advertises the capability.
  The model picker in particular depends on the agent's support for the unstable ACP session-model
  feature, so many agents show no model picker at all.
</Callout>

## Branch a conversation

Every message has a **branch** action in its hover toolbar. Branching forks the conversation up to
that message into a new, independent conversation in a new tab, so you can explore an alternative
direction without disturbing the original thread. Before it runs, choose whether to **Fork in this
workspace** or **Fork in a new worktree**. The first keeps the branch in the current workspace; the
second starts the next turn in an isolated worktree so changes stay separate until you apply them.
Conversations stay linear - there is no in-place message tree. For how the fork is stored, see
[Conversations and Sessions](/docs/core/conversations-sessions).

In the **Agents view**, the sidebar presents those independent conversations as a branch-style thread list
under the bot. Expand the bot to browse its direct threads, including newly-created forks, with the
same paging and searchable overflow controls used by other sidebar sections. Group or unassigned
conversations appear in **Other chats** instead of being hidden. If a conversation has
multiple participants, the Chats list converges its related conversations into a **Group chat** with
an orbit of participant avatars and expandable child threads. Agent-to-agent Switchboard activity
also stays visible in the workspace transcript, including both sides of a completed `agents.ask`.

## Keep a chat's workspace tabs

When you reopen a desktop chat tab, Ryu restores its open bottom and right workspace tabs, their
selected tab, and whether each dock was open. This includes project tabs such as **Terminal**,
**Files**, **Changes**, and installed workspace panels, as well as chat-run tabs such as **Sources**
and **Subagents**. Project tabs that were pinned remain shared with the other chats in that
workspace; unpinned tabs return to the chat that opened them.

## Edit and regenerate with versions

Every user message has an **edit** action, and every assistant reply a **regenerate** action, in
its hover toolbar. Editing a message or regenerating a reply forks a new version in place rather
than overwriting: a `< n / m >` pager appears on the affected turn so you can page between versions
and pick the one to keep. Unlike branching, this stays in the same conversation. The backend keeps a
lazy tree over the flat history (`POST /api/conversations/:id/messages/:mid/edit`, `/regenerate`,
`/select`); the pager and inline editor live in
`packages/blocks/src/desktop/agent-elements/user-message-editor.tsx`.

## Quote a selection to reply

Select any text in a message and a compact floating toolbar appears. **Quote** drops the selection
into the composer as a pending quote; when you send, it is prepended to your message as a leading
Markdown blockquote. Enabled plugins can add buttons to the same toolbar. The built-in Side Chats
plugin contributes **Ask in side chat** and **Explain**, each separated from the quote action by a
vertical divider. They send the highlighted text with the visible main-chat context and active
main-chat model to the no-tools side chat; the answer stays out of the main timeline.

## Message timestamps

Hover any message, user or assistant, and its send time shows in the hover toolbar beside Copy and
Branch. The time comes from Core's stored `created_at` (stamped at persist), formatted in place - no
extra round-trip.

## Rate replies with 👍 / 👎

Each assistant reply carries thumbs-up and thumbs-down buttons in its hover toolbar
(`POST /api/conversations/:id/messages/:mid/feedback`). One vote fans out to three sinks: it is
persisted on the message, it upgrades the continual-learning reward from a model guess to your human
label, and (on by default, local and private) it writes a memory fact. Vote again to clear it.

<Callout type="info">
  Voting a reply you just received works via a latest-turn fallback. Voting an older reply in a
  session you have not reloaded may need a reload first - a known v1 limitation.
</Callout>

## Session stats

The pre-installed **Session Stats** plugin places a compact readout under the latest reply. It combines
the structured usage that a provider reports with the saved transcript, so the same widgets work for
ACP agents, BYOK endpoints, Ryu providers, and local models. Providers that do not report a value
leave that widget hidden instead of displaying a fabricated zero.

The readout includes:

- **Turns** and **Steps** for the current transcript session.
- **Tokens Input**, **Tokens Output**, **Tokens Cached**, and **Tokens Total**. Input and output use
  cumulative transcript metrics when available, with the provider's context-window totals as a
  fallback; cached and total counts stay transcript-based.
- **Cache Hit Rate**, **Cache Read**, and **Cache Write**, including each cache value's share of the
  prompt context. The default is the latest turn; open the stats card to switch to cumulative
  session totals.
- **Cache Timer**, which shows a hot glyph during the active main-chain turn, then estimates the
  prompt-cache lifetime. The default is five minutes; a one-hour TTL and custom hot/countdown/cold
  glyphs are available in the card settings. The timer is best-effort because some transcripts expose
  cache activity but not the provider's expiry timestamp.
- **Input Speed**, **Output Speed**, and **Total Speed** as session averages. A rolling window from
  0 to 120 seconds can be selected; zero means the full session.
- **Context Length**, **Context Window**, **Context %**, **Context % (usable)**, and a context bar.
  The window prefers the provider's reported context window, then a model suffix such as `[1m]`,
  then a 200,000-token fallback. Set `CCSTATUSLINE_CONTEXT_SIZE_FALLBACK` to a positive integer
  when an older provider does not report its window size.
- **Compaction Counter**, with total/auto/manual/unknown/reclaimed selectors, optional trigger
  detail, reclaimed-token totals, and independent controls for each add-on.
- **Cost**, when the provider reports an amount and currency.
- **Session Usage**, **Weekly Usage**, per-model weekly windows, extra usage, and block/weekly reset
  timers when the selected subscription account exposes them. Usage can be shown as used or remaining
  percentages; session and weekly bars include an optional reset-window time cursor. Reset timers can
  show remaining time, elapsed progress, or the exact reset date/time with local/UTC timezone and
  locale controls. Sonnet, Opus, and Fable windows are omitted when the account does not report them.

The card's **Hide unavailable or empty metrics** setting keeps a provider with partial usage support
compact. Immediately after a compaction boundary, the context display uses the boundary's
`postTokens` until a later main-chain usage frame reports a fresh current value.
