title: "Git Workspace and Worktrees"
description: "How to pick a project folder and branch in Code mode, clone a repository, run in an isolated per-conversation worktree, set local environments, and review or apply the diff"
---

In **Code** mode, choose the folder and branch for a chat. You can also use a separate Git worktree
so the agent's changes stay apart from your main folder until you apply them. The workspace controls
are in the composer, and the diff and apply actions appear in chat.

## The workspace bar

In **Code** mode, a **workspace bar** sits directly below the composer. Click a segment to change it.
The bar keeps the active folder and branch visible.

| Segment | What it sets |
|---|---|
| Project folder | The active folder the run is rooted in |
| Run mode | Run in place, or in an isolated worktree |
| Local environment | The named setup used for a new worktree and its agent process |
| Git branch | The branch the folder is on, with a switcher |

The branch and run-mode segments appear only when the selected folder is a Git repository. The local
environment segment appears when the project has at least one environment configured.

The branch segment polls `GET /api/git/status?cwd=<path>` for the current branch and dirty state.
It shows an amber dot when the working tree has changes. Click it to open a searchable dialog of
local branches from `GET /api/git/branches`, and switch with `POST /api/git/checkout`. The run-location
control (**Local** or **New worktree**) opens the same kind of dialog, with a branch-name field for a
new worktree. Checkout goes through `git switch` and is validated against the real branch list, so a
typo or an injected argument is rejected. If checkout fails, the picker stays open and shows the
error so you can retry. Creating a branch is disabled while the working tree has uncommitted
changes.

Use the project control to search recent projects by name or source-folder path, open a folder on the
active node, clone a Git repository, or create a new folder. The control opens a command dialog.
Type to filter, use the arrow keys to highlight a project or action, and press **Enter** to choose it.
The sidebar's **Add project** button and the folder name in a new chat's title open the same dialog.
If the active node denies a folder operation, the picker keeps the form open with an error so you can restore access and retry.
Typing a new path clears the previous folder selection. **Add folder to Ryu** stays disabled until
the node validates the new path; an invalid or unreadable path cannot add the previous folder.
Choosing a folder from the tree replaces any typed-path check still in progress.

## Use more than one source folder

One named project can include multiple source folders. Open **Edit project**, then use **Source folders**
to add the folders the agent should be able to read and edit. The first folder is marked **Primary**.
It is the project name's path, the chat's `cwd`, and the root used for relative commands and git
worktrees. To change it, select **Make primary** beside another source folder and then choose **Save**.
The selected folder moves to the top of the list; additional folders remain available to the same agent
session without changing that primary workspace.

The project picker and sidebar show every source folder beneath the project name. Remove a folder from
the same **Source folders** list and select **Save**; the project keeps its other folders. Existing
single-folder projects continue to work unchanged.

To drop a project from the project picker, hover its row and select the remove control, or highlight
it with the arrow keys and use the keyboard. On macOS press **Command+Delete** (or **Fn+Delete**
with the search caret at the end of your query). On Windows and Linux press **Delete** with the
search caret at the end of your query. Plain **Delete** on a Mac keyboard, like Backspace elsewhere,
only edits the search. The project leaves both the picker and the sidebar's **Projects** list; its
folders stay on disk.

## Project name and agent instructions

Choose **Edit project** from a project's menu to change its display name and its local agent
instructions. The name is shown in the sidebar and project pickers; it does not rename or move the
folder on disk. The instruction editor loads an existing `AGENTS.md` or `CLAUDE.md` at the project
root. If neither exists, saving creates `AGENTS.md` there. **Cancel** or the dialog's close button
discards unsaved changes. **Save** writes the instruction file and the project's local settings. If
the folder or node rejects a write, the dialog stays open with the draft so you can restore access
and retry.

## Clone from a Git provider

From any project-folder picker, or from **Edit project → Source folders**, choose **Clone from Git**.
Paste an HTTPS or SSH clone URL from GitHub, GitLab, Azure DevOps, or another publicly reachable Git
host, including a self-hosted provider.

| Provider | Example URL |
| --- | --- |
| GitHub | `https://github.com/owner/repository.git` |
| GitLab | `https://gitlab.com/group/subgroup/repository.git` |
| Azure DevOps | `https://dev.azure.com/organization/project/_git/repository` |
| Custom host | `https://git.example.com/team/repository.git` or `git@git.example.com:team/repository.git` |

Ryu clones the repository into `~/Documents/Ryu/<folder-name>` on the active node. From a project
picker, the new checkout opens as the active project; from **Source folders**, it is added to the
project's folder list and remains there when you save. The clone happens where the node runs, whether
that is this device or a remote cloud node.

HTTPS uses the node's configured Git credential helper. SSH uses the node's configured SSH keys. Do
not put passwords or access tokens in the URL. Credentials stay on the node and do not cross the desktop
boundary. Core rejects local, private, loopback, and cloud-metadata host addresses before starting
the clone, and an HTTPS clone connects only to the addresses that passed that check. HTTPS clones
by host name need Git 2.37 or later on the node; with older Git, Core refuses the clone. HTTPS
redirects are not followed, so a renamed or moved repository fails to clone; paste its current clone
URL instead. A failed clone leaves no project entry or partial checkout behind.

## Commit, sync, and open pull requests

The pinned summary's Environment row holds the commit, pull, sync, compare, hand-off, and
pull-request actions. See [Git project controls](/docs/surfaces/desktop/user-guide/git-workspace-controls).

## Work handed off from another computer

When you continue a chat on another computer and choose **Bring working tree**, the destination
opens the work in a new worktree on a `handoff/<thread>` branch inside a fresh clone in its
handoffs folder. The chat's folder points at that worktree, and the unpushed commits and uncommitted changes you reviewed are already
in it. The source computer's folder, branch, and staging area are left as they were, and its copy
of the chat shows **on** and this computer's name in the sidebar. That is a reminder, not a lock.
Choose **Take back here** from the chat's menu on the source to clear it.

A handed-off worktree is not trusted automatically. Trust the folder on the destination before you
let agents run tools in it. The chat opens there with its run mode set to **Local**. Keep it there.
Ryu refuses to fork a second isolated worktree from a handed-off one, because the fork would start
from the last commit and leave the handed-off uncommitted changes behind. See
[RNP continuity](/docs/extend/integrate/rnp#bring-the-working-tree).

## Follow the project graph

Open **Git graph** from a project row's branch icon or its project menu. The graph is a read-only
history view for the selected folder, with a ref list on the left, colored lanes for branches and
merges, and commit details on the right. Select a ref to narrow the history, or filter commits by
message, author, short SHA, or ref name.

Selecting a commit shows its full SHA, author, relative date, parents, and decorated refs. The
details card also says whether the working tree has local changes and links to the project's
**Changes** view. The same graph is available as a right-side workspace tab beside
**Files** and **Changes**, so you can keep the history visible while working in a chat.

The graph reads the local repository through the active project folder. Refreshing it never checks
out a branch, edits files, or changes the working tree.

<Callout type="info">
  The branch and worktree controls apply only to a folder that is a Git repository. Pick another
  folder and those segments disappear. In Ryu Work, Environment still offers **Create local Git**.
  Code shows a non-repository folder read-only.
</Callout>

## Open workspace files in desktop apps

Open the **Files** workspace tab to browse the active project. Right-click a file or folder, or use
its row action, to open it with the operating system's default app, reveal it in Finder, Explorer, or
Files, or send it to an installed editor such as VS Code, Cursor, or Zed. Installed terminal options
also appear; for a file, Ryu opens its containing folder in the selected terminal.

The **Compact**, **Default**, and **Relaxed** controls change file-tree spacing. Toggle file search
to filter the tree. Both preferences are remembered when you reopen the workspace. If the file
listing fails, Files shows the error and a **Retry file listing** action. Switching project folders
keeps a delayed response from the previous folder from replacing the current tree.
**Match app theme** follows Ryu's selected light or dark mode even when it differs from the
operating system's theme.

With **Inline rename** enabled in file-tree settings, use **F2** or the inline rename action
to change a file or folder name. With **Drag and drop** enabled, drag an item into another
folder to move it. These actions update the files on disk in the selected local workspace, and the
tree refreshes to show the new paths. They require the native desktop connection to that folder.

Hold **Ctrl** (or **Cmd** on macOS) to select multiple items, then drag the selection to move them.
If an item cannot move, successful moves stay in place and the error identifies the refused item.

Ryu refuses a rename or move that would replace an existing destination, leave the workspace, or
move a folder inside itself. If the filesystem cannot perform a move safely, the original item stays
in place and the tree refreshes with an error. Choose another name or destination and retry.

Choose the defaults for these actions in **Settings → General → Terminal** and **Settings → General → Files**.
**Default shell** controls the terminal and git commands, and starts on the platform's OS shell.
**Default file open destination** controls the file tree's **Open** action and starts on the OS default
(Finder on macOS, Explorer on Windows, or the platform file handler elsewhere). You can pick an
installed editor instead. **Default terminal location** chooses whether the terminal
shortcut and project environment actions open tabs in the Bottom or Right pane (or the chat's bottom
or right dock in the scrolling and canvas tab layouts).

Ryu resolves every action beneath the active project folder before handing it to the operating
system. A path that leaves the project through parent traversal or a symlink is rejected.

## Annotate a file and send it to chat

Click a file in **Files** (or choose **View and annotate** from its context menu) to read it in the
dock with syntax highlighting. Clicking a folder still expands it, and Ctrl/Cmd- or Shift-clicks
still select multiple items.

1. Click a line number, or drag across several, to select a range.
2. Type a note in the box that opens under the selection. Press **Add note** (or Ctrl/Cmd+Enter) to
   keep it on those lines, or **Quote in chat** to send just this selection now. Escape cancels.
3. Repeat for other ranges, then press **Send** in the viewer header (it shows how many notes are
   waiting).

Each note goes into the chat composer as the file path, the line range, the selected lines in a code
block, and your comment, so you can add a question before sending. Nothing is sent until you send
the message. If no chat is open beside the dock, the notes go to the assistant sidebar instead.

Notes stay with each file while the Files tab is open, including after **Back to files**. Use
**Clear** to discard them. The viewer is read-only and opens UTF-8 text files of up to two million
characters. For binary or larger files it offers **Open externally**. A note quotes at most 120
lines of its selection.

## Run mode: this folder vs an isolated worktree

The run-mode picker offers two choices:

- **Work in this folder** edits the selected folder directly.
- **Isolated worktree** runs in a persistent git worktree dedicated to this conversation. When you
  pick it, you can give the worktree a friendly branch name (the **Suggest a new name** button
  regenerates one), defaulting to a `ryu/...` style name.

The worktree is **persistent per conversation, not per message**. Core creates the worktree on the
conversation's first message and reuses it for every later turn, keyed by the conversation id. Once a
chat has a live worktree, the branch is fixed, and the picker shows it read-only with the count of
changed files.

Worktree isolation is off unless you pick **Isolated worktree**. Each chat request carries `cwd`,
`worktree_isolation`, and the desired `worktree_branch`.

## Local environments

Open a project's menu and choose **Edit project** to add one or more named local environments. Each
environment can define:

- Plain environment variables inherited by project actions and the coding agent.
- Named actions such as **Dev stack**, **Desktop**, **Core**, or **Tests**, each with optional
  platform-specific commands. Actions appear in the workspace bar.

The active environment can be switched from the workspace bar before a worktree is created. Once a
conversation has a live worktree, its environment is fixed; select a different environment for the
next worktree instead.

Environment settings are saved with the project's local desktop preferences. Saving the project
editor also writes its instruction file and any managed project mapping. If the node or project
folder denies a write, the editor stays open with the changes so you can restore access and retry.

Chat worktrees do not run project-provided setup or cleanup shell hooks, because shell text supplied
with a request must not run in the Core process. Use a named local action or a
reviewed project instruction when a setup step is needed. Environment variables are passed only to
the coding agent and local actions.

<Callout type="warn">
  Environment variables are stored as local project settings. Do not put passwords, API keys, or
  other secrets in them. Use the credential or secret storage supported by the tool that needs the
  secret.
</Callout>

### Monorepo example

For a Bun/Turborepo workspace that also contains Rust crates, add a **Setup** action that runs:

```sh
bun install --frozen-lockfile
cargo fetch
```

Then add focused actions such as `bun run dev`, `bun run dev:desktop`, `bun run dev:core`, and
`bun run check-types`. Separate actions mean a worktree does not have to start every service.
Commands run from the worktree root, so package-specific actions can use the repository's workspace
filters or an explicit `cd`.

## What Core does with a worktree

When a chat request arrives with `cwd` set, `worktree_isolation` true, and the folder is a git repo,
Core creates a per-conversation worktree:

- The worktree directory is placed under `<repo>/.ryu-worktrees/ryu-run-<uuid>` by default, or under
  the absolute **Worktree root** configured for the node.
- The branch is your sanitized friendly name when you supplied one (with a short suffix appended on a
  name collision), or the auto-generated `ryu/run-<uuid>` otherwise.
- Core records the HEAD commit at creation time as the diff base.
- The worktree remains available across turns. When Core releases it, the managed retention
  settings determine whether its directory and branch stay available or are snapshotted and pruned.

## Managed worktree settings and recovery

Open **Gateway settings → Developer → Worktrees** to set the worktree root, fetch remote updates before
creation, and control automatic cleanup. Select **Node** to change the root. Leave it blank to use
the default repository folder. Fetching is off by default and only runs for new worktrees.

Automatic cleanup is on by default and keeps the newest 15 completed worktrees per repository and
root. The limit accepts whole numbers from 1 to 100. Active conversation worktrees are protected.
Ryu also keeps a worktree that contains another registered checkout beneath it.
Cleanup runs when Core releases a worktree. Disabling it keeps completed directories and branches
for manual management. Worktrees still marked active after a crash are retained for manual review.

Before pruning, Core saves a Git snapshot under `refs/ryu/worktree-snapshots/ryu-run-<uuid>` in the
original repository. The snapshot includes committed history, staged changes, and nonignored
working files. It excludes ignored files such as build output and ignored credentials.
Worktrees containing submodules or embedded Git repositories are retained when a snapshot cannot
preserve their contents. If snapshotting fails, Core keeps the original worktree.

List recovery snapshots from the original repository:

```sh
git for-each-ref refs/ryu/worktree-snapshots/ --format='%(refname)'
```

To recover one snapshot into a new folder, substitute its full ref:

```sh
git worktree add -b recovered-worktree ../recovered-worktree refs/ryu/worktree-snapshots/ryu-run-<uuid>
```

The snapshot's first parent contains the saved staged state. That parent's parent is the worktree's
original HEAD. Recovery creates a normal Git worktree for manual review.
