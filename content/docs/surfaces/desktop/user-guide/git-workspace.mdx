---
title: "Git Workspace & Worktrees"
description: "Run an agent against a folder on a branch, optionally in an isolated per-run worktree, and review the diff in chat."
---

Ryu can root a chat turn in a real working folder, run on a chosen git branch, and optionally isolate
the run in its own git worktree so the agent's edits never touch your main checkout until you choose
to apply them. **Code** exposes the workspace controls in the composer, with the
diff and apply actions surfaced in chat.

## The workspace bar

In **Code** mode, directly above the composer is a **workspace bar** with
click-to-change segments:

| Segment | What it sets |
|---|---|
| Project folder | The active folder the run is rooted in |
| Run mode | Run in place, or in an isolated worktree |
| Local environment | The named setup used for a new worktree and its agent process |
| Git branch | The branch the folder is on, with a switcher |

The branch and run-mode segments render only when the selected folder is a git repository. The local
environment segment appears when the project has at least one environment configured.

## Use more than one source folder

One named project can include multiple source folders. Open **Edit project**, then use **Source folders**
to add the folders the agent should be able to read and edit. The first folder is marked **Primary**:
it remains the project name's path, the chat's `cwd`, and the root used for relative commands and git
worktrees. To change it, select **Make primary** beside another source folder and then choose **Save**.
The selected folder moves to the top of the list; additional folders remain available to the same agent
session without changing that primary workspace.

The project picker and sidebar show every source folder beneath the project name. Remove a folder from
the same **Source folders** list and select **Save**; the project keeps its other folders. Existing
single-folder projects continue to work unchanged.

In **Ryu Work** mode, the new-chat composer starts without the project-folder picker. Ordinary
conversation does not require a folder; when a message clearly asks to edit or run local project files,
Ryu pauses that turn and asks for a project in context. After the first turn, the conversation remembers
its folder independently of the global project selection.

The same project, run-mode, branch, and change totals remain available in the connected **Pinned
summary** rail beside the conversation. Its first Environment row is the conversation's project name,
shown read-only so changing the global project selection cannot retarget an existing chat. Choose
**Commit or push** there to open the git action
dialog: target the current branch or create a new one, add an optional commit message, choose
whether to include unstaged changes, then select **Commit**, **Commit and push**, or **Push**. While
Core is working, the Environment row replaces the action with **Generating message**, **Committing**,
or **Pushing** and a stop control aligned to the right. The summary refreshes its counts after the
action.

The Environment row also has **Pull** and **Sync** controls for repositories with an upstream.
**Pull** runs a fast-forward-only pull, while **Sync** pulls first and then pushes the current branch.
Neither action stages or commits local changes; divergence, missing upstreams, and remote failures are
reported in the row instead of creating an implicit merge commit. While either action runs, the row
shows **Pulling** or **Syncing**, then refreshes the shared branch counts. Remote Git work is owned by
Core, so the progress row does not offer a client-side stop control; the bounded operation either
finishes or reports its failure.

Git controls only appear after the selected folder is recognized as a Git repository. In **Ryu Work**,
a non-repository folder instead gets a **Create local Git** action in Environment. It initializes a
repository on `main` without staging or committing the folder. Once local Git exists, the normal branch,
change, commit, and remote controls appear. If the Pull Requests app is enabled, **Create GitHub
repository** opens a small publish flow for the repository name and **Private** or **Public** visibility.
Ryu commits the folder locally, asks the authenticated GitHub CLI to create the remote, adds `origin`,
and pushes the current branch. A failed provider operation does not remove the local repository.

For a GitHub-backed repository, the same Environment row includes **Compare branch** when the current
branch is different from its comparison base. The base is selected from the current pull request when
available, then GitHub's default branch, then local `main` or `master`, with `main` as the fallback. The
action opens the provider's compare view in a new browser tab.

When a conversation is already underway in the local checkout, choose **Hand off to worktree** in
the Environment row to keep the same chat while moving its next response into an isolated worktree.
Enter the branch name in the dialog and choose **Hand off**. If a response is running, Ryu interrupts
it before arming the handoff; Core creates the named worktree on the next turn. The action is hidden
once this conversation already has a live worktree.

On an organization-bound node, **Pull** and **Sync** require the caller's `agent.edit` permission.
The node accepts only workspaces inside its node-home boundary, disables repository-local executable
clean/smudge/process filters, and keeps Git non-interactive. A remote operation times out after two
minutes rather than waiting indefinitely for credentials or a remote server.

On a branch other than `main` or `master`, the Environment row also offers **Create pull request**.
Its dialog names the source and base
branches, accepts an optional title and description, and lets you **Commit and push local changes**
before choosing **Create draft PR**, **Create PR**, or **Open PR in browser**. Pull-request creation
uses the Core node's authenticated GitHub CLI (`gh`), so the repository's remote and credentials
must be available on that node. Ryu allows only one open pull request for a branch: if one already
exists, the row changes to a GitHub-linked pull-request title instead of offering a second create
action. When the **Pull Requests** app is enabled, its GitHub provider supplies the CI rollup below
that link. A failing rollup shows **Fix**, which stages a bounded `ci-failures-pr-<number>.txt`
report in the current chat composer for review before you send it. The row also shows the PR's
comment count and links to its discussion. The app obtains this metadata through the local
authenticated `gh` CLI.

The same pull-request title, status icon, and CI summary are available in a chat's sidebar hover
card. In **Code** mode, a code-session row with a pull request also gets a compact linked status
icon; open is GitHub green, draft is gray, closed is red, and merged is purple. The lookup is lazy,
so merely having many chats open does not start a GitHub request for every row. Install and enable
**Pull Requests** to show this metadata; local Git status and the create flow remain usable without
the app.

The branch segment polls `GET /api/git/status?cwd=<path>` for the current branch and dirty state,
shows an amber dot when the working tree is dirty, and on click lists
local branches from `GET /api/git/branches` so you can switch with `POST /api/git/checkout`. Checkout
goes through `git switch` and is validated against the real branch list, so a typo or an injected
argument is rejected.

## Follow the project graph

Open **Git graph** from a project row's branch icon or its project menu. The graph is a read-only
history view for the selected folder, with a ref list on the left, colored lanes for branches and
merges, and commit details on the right. Select a ref to narrow the history, or filter commits by
message, author, short SHA, or ref name.

Selecting a commit shows its full SHA, author, relative date, parents, and decorated refs. The
details card also tells you whether the working tree has local changes and links directly to the
project's **Changes** view. The same graph is available as a right-side workspace tab beside
**Files** and **Changes**, so you can keep the history visible while working in a chat.

The graph reads the local repository through the active project folder. Refreshing it never checks
out a branch, edits files, or changes the working tree.

<Callout type="info">
  The branch and worktree controls only apply to a folder that is a git repo. Pick a non-repo folder
  and those segments disappear. In Ryu Work, Environment still offers the explicit Create local Git
  entry point; Code keeps the non-repository state read-only.
</Callout>

## Open workspace files in desktop apps

Open the **Files** workspace tab to browse the active project. Right-click a file or folder—or use
its row action—to open it with the operating system's default app, reveal it in Finder, Explorer, or
Files, or send it to an installed editor such as VS Code, Cursor, or Zed. Installed terminal options
also appear; for a file, Ryu opens its containing folder in the selected terminal.

Choose the defaults for these actions in **Settings → General**. **Default shell** controls the
terminal and git commands, and starts on the platform's OS shell. **Default file opener** controls the
file tree's **Open** action and starts on the OS default (Finder on macOS, Explorer on Windows, or
the platform file handler elsewhere); installed editors can be selected when you want one to take
over.

Ryu resolves every action beneath the active project folder before handing it to the operating
system. A path that leaves the project through parent traversal or a symlink is rejected.

## Run mode: this folder vs an isolated worktree

The run-mode picker offers two choices:

- **Work in this folder** edits the selected folder directly.
- **Isolated worktree** runs in a persistent git worktree dedicated to this conversation. When you
  pick it, you can give the worktree a friendly branch name (the **Suggest a new name** button
  regenerates one), defaulting to a `ryu/...` style name.

The key behavior is that the worktree is **persistent per conversation, not per message**. Core
creates the worktree on the conversation's first message and reuses it across every following turn,
keyed by the conversation id. Once a chat has a live worktree the branch is fixed, and the picker
shows it read-only with the count of changed files
(`apps/desktop/src/components/chat/WorkspacePicker.tsx`).

You can also choose **Hand off to worktree** from the pinned summary's Environment section after a
chat has started. This keeps the existing conversation and arms its next turn for the named branch;
the running response is interrupted first when necessary.

On each turn the chat request carries `cwd`, `worktree_isolation`, and the desired `worktree_branch`
. Worktree isolation is opt-in per the run-mode pick, not on by default for every folder.

## Local environments

Open a project's menu and choose **Edit project** to add one or more named local environments. Each
environment can define:

- A default setup script plus optional macOS, Linux, and Windows overrides.
- A default cleanup script plus the same platform overrides.
- Plain environment variables inherited by setup, cleanup, project actions, and the coding agent.
- Named actions such as **Dev stack**, **Desktop**, **Core**, or **Tests**, each with optional
  platform-specific commands. Actions appear in the workspace bar.

The active environment can be switched from the workspace bar before a worktree is created. Once a
conversation has a live worktree, its environment is fixed; select a different environment for the
next worktree instead.

Setup runs once from the new worktree root. Ryu supplies `RYU_PROJECT_PATH` for the main checkout and
`RYU_WORKTREE_PATH` for the isolated checkout. Cleanup runs from that same worktree immediately before
Ryu removes it, including after apply. A failed setup stops the agent turn and reports the script
error instead of silently running against the main checkout.

<Callout type="warn">
  Environment variables are stored as local project settings. Do not put passwords, API keys, or
  other secrets in them; use the credential or secret storage supported by the tool that needs the
  secret.
</Callout>

### Monorepo example

For a Bun/Turborepo workspace that also contains Rust crates, a useful setup is:

```sh
bun install --frozen-lockfile
cargo fetch
```

Then add focused actions such as `bun run dev`, `bun run dev:desktop`, `bun run dev:core`, and
`bun run check-types`. Keeping these as separate actions avoids forcing every worktree to start every
service. Commands run from the worktree root, so package-specific actions can use the repository's
workspace filters or an explicit `cd`.

## What Core does with a worktree

When a chat request arrives with `cwd` set, `worktree_isolation` true, and the folder is a git repo,
Core creates a per-conversation worktree:

- The worktree directory is placed under `<repo>/.ryu-worktrees/ryu-run-<uuid>`, inside the repo so
  it stays below `.gitignore`.
- The branch is your sanitized friendly name when you supplied one (with a short suffix appended on a
  name collision), or the auto-generated `ryu/run-<uuid>` otherwise.
- Core records the HEAD commit at creation time as the diff base.
- The worktree remains available across turns. Applying or discarding it runs the selected
  environment's cleanup hook, then removes the directory and branch automatically.

## Review the diff in chat

After a run, the in-chat **diff panel** reads
the aggregate worktree diff from `GET /api/worktree/:run_id/diff`, where `run_id` is the conversation
id. It shows one file at a time with line numbers and visible additions and deletions. Use the
filterable changed-file list to move between files; the header keeps the aggregate totals visible.
The diff captures both committed changes on the worktree branch and uncommitted working-tree edits,
so files the agent created but never committed still appear (Core stages with `git add -A` before
diffing).

## Apply the changes

From the diff panel you can apply the run's work via `POST /api/worktree/:run_id/apply` in one of two
modes:

| Mode | What it does |
|---|---|
| **Apply (merge)** | Commits the worktree's changes, then merges the worktree branch into the base branch with `git merge --no-ff`. |
| **Open PR** | Commits, pushes the branch to `origin`, and opens a pull request with `gh pr create`. |

On a clean merge the panel shows the resulting commit; for a PR it shows the created PR URL. If the
merge cannot complete cleanly, Core runs `git merge --abort` so your base repo is never left
mid-merge, returns the list of conflicted files (HTTP 409), and still cleans up the worktree.

<Callout type="warn">
  PR mode requires the GitHub CLI (`gh`) to be installed and authenticated on the machine running
  Core. Merge mode needs only git. Both modes operate on the Core node, so for a remote node these run
  against that node's repo and credentials.
</Callout>
