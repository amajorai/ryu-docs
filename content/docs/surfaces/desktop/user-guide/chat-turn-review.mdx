## Review files changed by a turn

When an agent finishes a turn that edited or created files, the transcript keeps an edited-files
card at the end of that assistant reply. A one-file turn uses a compact **Edited filename** row with
its insertion and deletion totals. Turns that touched multiple files keep the expanded **Edited N
files** card, including the first few paths and a **Show more files** control for longer turns.

Select **Review** to open the workspace **Changes** view on **Files from this turn**. Select **Undo**
and confirm to reverse only the exact text replacements made during that turn, preserving unrelated
changes. If an affected file is staged or its edited text has changed since the turn, Undo refuses
without changing the files. Other changes remain available for Review.
The card remains visible after a successful undo, but its Undo control is marked **Undone**.

If you switch connections, chats, or project folders while Undo is waiting, the submitted operation
still belongs to its original workspace. Its eventual result does not mark the new turn undone or
show a success or failure message in the new workspace. Reopening the original workspace lets you
review its current files.

The card is derived from the saved tool activity, so it remains available when you reopen the chat;
hiding tool detail does not hide this completed result. Only completed tool results contribute: a
failed write or a tool call still streaming at turn end is not presented as a finished file change.

Agents can also leave a completed JSON UI or artifact card in the same end-of-turn position. Those
cards support the interactive components and safe web links described in the [built-in tools
reference](/docs/core/generative-ui-tools#end-of-turn-result-cards), while the existing inline tool
previews continue to behave as before.

## Rewind with checkpoints

Ryu takes a checkpoint before every message you send. When the chat has a project folder, the
checkpoint also snapshots that folder's files. When worktree isolation is on, it snapshots the
chat's worktree instead. Checkpoints work the same for every agent and provider, including Pi,
Claude Code, Codex, other ACP agents, and Ryu's own provider chats. Files changed by an agent's
edit tools and by its shell commands are both captured, because the snapshot covers the folder
rather than individual tool calls.

Open the rewind picker in either of these ways:

- Type `/rewind` in the composer.
- Open a user message's **More message actions** menu and select **Rewind to here**.

Pick the message you want to go back to. If the checkpoint has a file snapshot, the picker lists
the files a restore would change: **restore** for edited files, **recreate** for deleted files, and
**remove** for files created since. Then choose what to restore:

- **Restore both** restores the folder and rewinds the conversation to just before that message.
- **Restore conversation** rewinds only the conversation. Files stay as they are.
- **Restore code** restores only the folder. The conversation stays as it is.

Rewinding the conversation puts the rewound message back in the composer so you can edit and send
it again. The rewound turns are kept as an earlier version of the thread, so the version arrows can
still reach them. The agent's next turn starts a fresh session from the rewound transcript, so Pi
and other ACP agents do not remember the turns you rewound.

Before restoring files, Ryu snapshots the folder's current state. That snapshot appears in the
picker as **Before a rewind**, and restoring it undoes the rewind's file changes.

A rewind never destroys work that is not saved somewhere. Ryu changes or removes a file only when
its current content is in that **Before a rewind** snapshot. It leaves a file unchanged in these
cases:

- Its current content is not in any snapshot. For example, it is ignored, larger than 25 MB, or
  unreadable.
- A folder now sits where the file was.
- One of its parent folders is a symbolic link, which could point outside the project.

If anything is left unchanged, the picker stays open and lists each file with the reason. Every
other file is still restored. Files are written to a temporary file and then moved into place, so
an interrupted rewind never leaves a half-written file. Contents are restored byte for byte,
including line endings, executable bits, and symbolic links. Git LFS and other `.gitattributes`
filters do not change them.

Checkpoints have some limits:

- Rewind is unavailable while this chat, or any other chat using the same folder, is running a
  turn. Stop the turn first.
- Files matched by the folder's `.gitignore`, dependency and build folders such as `node_modules`
  and `target`, files larger than 25 MB, and nested Git repositories are not captured. Rewind never
  changes them.
- A folder with more than 200,000 changed files, your home folder, or a filesystem root gets a
  conversation-only checkpoint.
- Snapshots need `git` on the device that runs the agent. They are stored in that device's Ryu data
  folder, separate from your project's own Git history, and they are not included in node backups.
  Your project's repository is never written to. In a Git project, the first snapshot reuses the
  repository's data to finish quickly. Ryu then copies that data into its own store, so later
  history rewrites or cleanup in your repository cannot affect your checkpoints.
- Rewind is local undo, not version control. Changes made outside the chat in the same folder are
  part of the snapshot too, so restoring a checkpoint also reverts them. Use Git for permanent
  history.

## Pursue a goal

A goal is a persistent completion condition attached to a conversation. After each turn a separate
model judges whether the goal has been met; if not, the conversation keeps going on its own until
it is met or a safety cap is reached.

- Type `/goal <condition>` to set a goal, or use the composer **+** menu and pick **Pursue goal**.
- An active-goal chip and a goal bar appear above the composer, showing the editable condition, a
  live elapsed timer, and the latest judge reason. The Target icon on the chip turns into an
  **✕** on hover to clear it.
- When you create or edit a goal from the goal bar, Ryu adds the condition to the transcript as a
  user message and labels it **Sent as goal** beneath the bubble.
- Type `/goal` alone to open the bar, and `/goal clear` to remove the goal.
- The **Stop** button halts the loop at any time.
- An agent with the `goal.set` tool can set or replace the goal for the current conversation; the
  tool is scoped by Core and resets the judge progress when it is called.

The judge runs as its own model call, separate from your chat model. Choose which model judges
goals in **Settings → Goals**. The continuation loop is capped at a fixed number of turns so a goal
can never run away. For how the goal state and judge primitive work, see
[Goals](/docs/core/goals).

## Ask a side question with `/btw`

`/btw <question>` asks a quick question about the current conversation. The side model sees the
conversation context but has no tools, returns a single answer in a dismissible overlay, and the
exchange never becomes a chat message. It is the inverse of a sub-agent - full context, no tools.
Because the desktop asks over the active conversation, the exchange is kept as a lightweight side
chat you can re-open from the Context rail or sidebar. The built-in [Side Chats](/docs/plugins/side-chats)
plugin owns the `/btw` command; see
[Side Questions](/docs/core/side-questions) for how persistence works.

Expand a conversation in the sidebar to see its saved side chats in a connected branch-style list.
Each entry keeps the question visible, shows a short answer preview and relative age, and opens the
side-chat overlay without adding the exchange to the main transcript. Sub-agent entries use the
same list so related follow-ups stay together under their parent conversation.

In the Context rail or pinned summary, hover over a saved side chat to reveal **Delete side chat**.
Ryu asks you to confirm before anything is deleted; choose **Cancel** to keep it. The entry is
removed after deletion succeeds. If deletion fails, it stays available with an error
so you can try again. If the saved list cannot load, expand **Side chats** and choose
**Retry side chats**. A failed refresh keeps the saved answers already displayed.
Deleting a side chat does not change the main transcript.

Type `/btw` once you have at least one message in the thread. The built-in **Side Chats** plugin
sends the visible main-chat transcript with the question, including the latest in-flight text, so
the answer has the context you are looking at. Pick the model and reasoning effort it uses in
**Settings** (the `btw-model` and `btw-effort` preferences).

Selection actions fork the context. They reuse the active main-chat model and the
same bounded visible transcript, but they do not copy tools or add a new message to the main chat.

## Double-check answers

Toggle **double-check** in the composer to have a second model review each answer as it arrives. It
fires once per assistant message and flags problems it finds. Configure which model reviews and at
what reasoning effort in **Settings → Double-check**. For the review primitive, see
[Double-Check](/docs/core/double-check).
