title: "Agent Account Access"
description: "Choose which of your accounts, app connections, and model providers an agent may use, and how its Identity setting limits them."
---

An agent uses accounts according to its **Identity** setting (**Acts as you**, **Its own identity**,
or **Both**) and its **Account access**. Set both in the agent editor.

## Choose which accounts an agent can use

Each agent has an **Identity** setting, chosen when you create it and editable later under
**Tools & knowledge** in the agent's editor:

- **Acts as you** works on your behalf with the accounts you've connected. While its account access
  is unrestricted it keeps any [agent accounts](/docs/security/secret-vault-agent-accounts) it
  already has. Once you limit it to selected accounts, it cannot create or use agent accounts.
- **Its own identity** never touches your accounts. It does not fall back to your default profile
  for MCP sign-ins, it does not use your [Identity Vault](/docs/surfaces/desktop/identities)
  profiles, and models Ryu routes for it never run on your provider keys (agents that call their
  provider themselves are the exception, see below). Its own accounts are the website logins
  it creates in the Vault and the apps you connect for it (see
  [Connect apps for an agent](#connect-apps-for-an-agent)). Its Composio actions run as its own
  Composio user, never with an app you connected for yourself.
- **Both** has its own accounts, and can also use the ones of yours you allow.

**Account access**, on the agent editor's **Connections** tab, lists the accounts the agent's
Identity setting allows:

- **Your accounts** (Acts as you and Both): your Composio connected accounts, the MCP servers you
  signed in to, your **Model providers** (the provider keys and signed-in subscriptions your
  Gateway uses), and two more rows:
  - **Services using your saved keys**: MCP servers and app tools that call out with an API key or
    secret you saved, such as a server you added with a key in its headers or a search app that
    uses your API key. There is one row per app, or per MCP server you added. A key could be
    anywhere in a server you added, so Ryu counts one that has any header or environment value, or
    what looks like a key in its address or command arguments.
  - **Control of your desktop**: Ghost clicking, typing and reading your screen, the Shadow
    tools that search what it captured from your screen, audio and input, and the tools that
    operate your paired Ryu devices.
- **Agent's own accounts** (Its own identity and Both): the logins the agent created for itself and
  the apps connected to its own Composio user.

### Limit to selected accounts

By default, **Limit to selected accounts** is off and the access is **unrestricted**. The agent may
use every one of these accounts that its Identity setting allows. Turn it on and select accounts
to narrow that list. With the limit on, an
account you don't select is unavailable to the agent. For **Acts as you**, a Composio action or MCP
sign-in that needs an account you didn't select is refused instead of falling back to another
account. For **Both**, a Composio action with no selected account of yours runs on an app connected
for the agent that you selected instead, and is refused when there is none. An MCP sign-in you
didn't select is refused.

With the limit on, a service using your saved keys, or control of your desktop, is refused unless
you select its row. An agent with **Its own identity** never uses either, even when the limit is
off. For **Its own identity**, a Composio action runs only on an app connected for the agent that
you selected. Selecting nothing means the agent can use none of these accounts. Accounts
you connect later are not added to the selection automatically, except that a website login the
agent creates for itself, or an app you connect for the agent, is added so it can use it right away.

With the limit off, an agent with **Its own identity** runs a Composio action as its own Composio
user, and Composio picks that user's account for the app. An agent with **Both** uses your connected
account for the app when you have an active one, and its own Composio user otherwise.

### Connect apps for an agent

An agent with **Its own identity** or **Both** can have Composio apps of its own. Under **Agent's own
accounts → Connected apps**, choose **Connect app**, pick the app, choose its access level in the
connection review, and authorize in your browser with the account the agent should use. The app is
connected to the agent's own Composio user, not to yours, and only that agent uses it. Its access
level applies on top of the access level of your own connection for the same app, so the stricter
of the two wins. **Disconnect** removes the app from Composio, from the agent's selection, and
removes the event triggers that watch it.

Composio actions an agent runs on its own apps are charged to you, the agent's owner, in the same
way as actions on your own apps. Where Composio usage is billed, it comes out of your credits and
counts toward a budget you set for yourself and toward a budget you set for that agent. The agent's
own Composio user is used only to pick the account, so Composio's own dashboard still lists the
action under that user.

Connecting needs a saved agent and a Composio API key on the node. When you switch an agent from
**Acts as you** to **Its own identity** or **Both**, save it first. Until then, **Connected apps**
shows **Save to connect apps for this agent**, and **Account to watch** doesn't offer its apps.
Connecting, listing, and disconnecting an agent's apps needs the node owner's access and edit
access to the agent. The agent cannot do it for itself, because these actions are not available
through the agent's Ryu API tools.

When Core runs Composio through a [Connect service](/docs/standalone/connect#core-composio-execution),
an agent's apps are available only if the Connect operator enabled agent accounts for your tenant.
Otherwise Ryu shows that they are not available. With them enabled, the agent's app is an account
of its own inside your tenant. It can only be the app your tenant is set up for, it can run only the
actions your tenant is granted, and its actions count toward your tenant's limits and usage. After
you authorize in the browser, the sign-in returns to Ryu and completes the link you started most
recently, whether that was for you or for an agent. Start one link at a time.

### Triggers on an agent's apps

An event trigger can watch one of the agent's own apps. In the agent's **Triggers** tab, **Account
to watch** lists its connected apps that are active and that its account access allows, marked
**This agent's account** when some of your accounts are listed too. Before it adds the trigger, Ryu
checks that the app is connected to this agent. An agent can never watch another agent's apps.
On every event, Ryu checks again that the agent has **Its own identity** or **Both** and that its
account access still allows the app, and skips the event otherwise. A trigger on one of your
accounts must likewise name an account connected to you. Triggers on an agent's own apps are not
available with a Connect service.

The editor makes the same check against the **Identity** and account access on screen before you
save. A trigger whose account they no longer allow is marked **Paused: account not allowed** in the
**Triggers** tab, and the **Identity** section says how many triggers that fire today will stop
firing. The trigger is kept. Allow its account again and it fires again.

Identity Vault profiles are separate. They are always bound one by one in the **Identities** list
under **Your accounts**, whether or not the limit is on. An agent uses only the profiles you tick
there, and **Limit to selected accounts** does not change them. They apply only to **Acts as you**
and **Both** agents.

### Treg and app checks

The **Treg** switch controls whether apps and the agent's own Treg tool may use Treg for the agent.
It follows **Limit to selected accounts** rather than the Identity setting. While the limit is off,
every agent may use Treg. With the limit on, only an agent with **Treg** turned on may. Ryu checks
the switch on each Treg call an app makes for the agent, including calls the app makes later for
work the agent set up. Turning **Treg** off also stops that work, which fails with a message saying
the agent isn't allowed to use Treg. The same check applies to the Composio account an app uses for
the agent. It must be one the agent may use. While an app is handling a request from an agent set to **Its own identity** or
**Both**, or with limited account access, Ryu refuses any call the app makes to Treg, Composio or
another Ryu-managed provider without saying which agent it is for.

A Dashboards widget that an agent adds or changes through the Dashboards app's own tools runs for
that agent. Each time it refreshes, on its schedule or when you refresh it, its Composio action
must use an account the agent may use. Changing its title or layout keeps it that way. When you
choose a new source for it, it runs as yours. Widgets the dashboard builder adds or changes run
as yours, whichever agent built them. An agent set to **Its own identity** or **Both**, or with
limited account access, cannot add or change widgets through the dashboard builder (see below).

Accounts you saved inside an app are yours too, such as the Bluesky sign-in in Outpost's settings.
An app uses such an account for an agent only after Ryu confirms that the agent is **Acts as you**
with **Limit to selected accounts** off. For any other agent the request fails, and nothing is sent
with your account.

Today Outpost is the app that applies these checks. Dashboards Composio widgets and UGC's
engagement metrics still run on your Composio account whichever agent set them up, so don't give
an agent you have limited access to those apps if that matters to you.

### Model providers

**Model providers** decide which of your chat model provider keys and sign-ins the agent's models
may run on. The list shows only providers that can run an agent's chat turns. Speech, image, video,
embedding, and rerank providers are not listed, and this setting does not limit the calls Ryu makes
to them for the agent. Ryu credits and local models are not your accounts, so every agent may always
use them. The same holds for model use your organization buys from Ryu Cloud. When a request runs on
Ryu Cloud's own provider keys and is billed to your organization's credits, every agent may use it,
and your organization's model and provider policy still applies. With the limit off, the agent may
use all of your providers.

With the limit on, the Gateway skips every provider you didn't select. If the agent's model or
routing points at one, the Gateway moves on to the next allowed provider in its fallback order. When
none is left, the request fails with a message saying the provider isn't in the agent's account
access. On the routes below, an agent with **Its own identity** never uses your providers, so its
models run on Ryu credits, your organization's Ryu Cloud model use, or a local model. On a node with
none of these, it has no model to run on. Providers you add later are not added to a limited
agent's selection automatically.

This applies to the agent's chat turns and to agents that run their own engine through the Gateway,
such as Ryu's built-in engine and OpenAI-compatible agents routed through the Gateway. Ryu does not
send a limited agent around the Gateway. A turn that would send your provider key straight to the
provider (for example while the Gateway is unreachable, or for Ryu's engine with Gateway routing
turned off) is refused instead, and an agent that runs its own engine does not start when the node
uses a Gateway it doesn't manage. When Ryu's built-in engine runs for such an agent, it starts with
none of your saved provider keys, so its only model route is the Gateway.

### Engines that call their provider directly

Some engines call their model provider themselves with your own sign-in or key. Ryu checks them when
it starts the agent:

- **Claude Code** starts for a limited agent only when **Anthropic** is selected, **Codex** using
  your ChatGPT sign-in only when **OpenAI** is selected, **Gemini CLI** only when **Google Gemini**
  is selected, and **Kiro** only when **Kiro** is selected. When the agent's engine is one of these,
  the list shows that provider even if you haven't added a key for it. Once it is selected, the
  engine uses whatever sign-in or key it has for that provider, and the Gateway doesn't narrow it
  further.
- Any other engine that calls its provider itself (such as OpenClaw, Hermes, your own Pi or a
  developer SDK app) doesn't start for a limited agent.
- A limited agent on any engine other than **Ryu** whose Gateway routing you turned off doesn't
  start either. Turn routing back on, or turn the limit off.
- An agent with **Its own identity** can't use your sign-ins, so Claude Code, Codex with your
  ChatGPT sign-in, Gemini CLI, Kiro and the other engines that call their provider themselves
  don't start for it.
- A custom agent whose engine is **Ryu** in the agent editor's engine list runs your own installed
  Pi with your own Pi settings and keys while its model providers are unrestricted. Once they are
  limited, including for every agent with **Its own identity**, Ryu runs it on Ryu's built-in engine
  instead, under the agent's own identity and with none of your saved provider keys, so its models
  go through the Gateway and the limit applies. Ryu starts it on a model the limit lets it use: your
  default model when its provider is one you selected, or when Ryu credits pay for it (a **Ryu
  Router** model when it is marked **Free**, or the Auto Router while any model is marked **Free**).
  Otherwise it uses the first suggested model of a selected provider you're signed in to, and then
  Ryu's local model. A model Ryu credits pay for answers the agent only while you have credit left.

  If the agent would start on the local model and it isn't downloaded, the new-agent dialog and the
  agent's editor warn that the agent has no model it can use. It doesn't start while Ryu's engine
  has Gateway routing turned off, and the agent's **Account access** panel says so. Once its tools
  are limited to specific tools, it can use only those tools and its shell and file tools are off.

Codex without your ChatGPT sign-in, and custom or catalog agents with Gateway routing on, send their
model calls through the Gateway, which applies the limit. Ryu relies on those agents honouring the
Gateway address it gives them. A custom command recognised as Claude Code or Codex is checked as
that engine, and so is a custom command that runs Gemini CLI (its `gemini` program or the
`@google/gemini-cli` package) or Kiro CLI (`kiro-cli`).

### Delegation and Ryu API limits

An agent with limited account access, or with its own identity, cannot get around that limit
through another agent. It cannot hand a task to, schedule a routine for, or switch the chat to an
agent that may use more of your accounts than it may (including the default agent), and an agent it
creates starts with its identity and selection. Parallel sub-tasks (`delegate`) run without any
agent's tools or accounts, but on your model providers, so an agent whose model providers are
limited cannot start them.

Through Ryu's own API tools, such an agent can read, and can change workspace content (Spaces,
memory entries, conversation titles and folders, notifications, prompt suites). It cannot change
connections, accounts, plugin secrets, agents, plugins, sharing, providers, routines, or node
settings, or start another agent or a model run that way. See
[Self-API](/docs/extend/develop/extensions/self-api).

An agent set to **Its own identity** or **Both**, or with limited account access, can read
workflows and dashboards but not create or change them, because they run with your accounts.

### Published agents

When you publish an agent, its Identity setting goes with it, because it says whose accounts the
agent works with, not which ones. Its account access stays behind, because those accounts belong to
your node. The Store shows the Identity setting before anyone adds the agent. The added agent keeps
it and starts with no account limit, like an agent you create. Set to **Acts as you** or **Both**, it
can use the installer's connected accounts until they limit it under **Account access**. Listings
published before the Identity setting existed install as **Acts as you**.
