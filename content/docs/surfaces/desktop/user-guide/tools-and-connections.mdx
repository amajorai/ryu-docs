title: "Tools and Connections"
description: "Give agents tools and connect MCP servers or third-party apps"
---

Tools let an agent do work beyond chat. A tool can read a page, run a command, file a GitHub issue,
or search the web.

MCP (Model Context Protocol) is the protocol used by MCP servers. An MCP server provides tools to
an MCP host such as Ryu. A connection is different. It is usually a signed-in account or a link to
an outside service.

Ryu shows tools from three sources on the desktop **Tools** page:

- **MCP servers** you register, plus the built-in servers in Core and the servers that enabled
  plugins provide.
- The **unified tool catalog**, which makes every tool searchable by query.
- **Composio**, a hosted catalog of third-party actions (Gmail, GitHub, Slack, and more). You can
  search it, but it is never listed in full.

An agent sees only the tools on its **allowlist**, wherever the tools come from. For the
registry and catalog details, see [MCP registry](/docs/core/mcp-registry) and the [unified tool
catalog](/docs/core/unified-tool-catalog).

## Browse and allowlist tools

Open **Tools** in the desktop sidebar. The page lists every registered server and the tools each
one exposes (`GET /api/mcp/servers` and `GET /api/mcp/tools`). If tool discovery fails, server
details stay available and **Refresh tools** tries again.

To see one agent's tools, use the **agent filter** at the top of the page. Core then resolves
`GET /api/mcp/tools?agent=<id>` against that agent's allowlist. An empty allowlist means the agent
sees every enabled tool. A non-empty allowlist is the intersection with what is enabled.

Edit the allowlist in the **agent editor** (open an agent, then the Tools section). The Tools page
is for browsing, testing, and connecting servers.

The allowlist key is the **fully qualified tool id** `<server>.<tool>`, for example `spider.crawl`
or `ghost.ghost_click`. You grant, test, and call a tool by the same id.

The pre-installed **Goal** plugin contributes `goal.set`. Add it to an agent's allowlist when the
agent should be able to set or replace a goal for its current conversation. Core takes the
conversation from the caller, so the tool cannot write a goal into another chat.

<Callout type="info">
  Tool calls are governed the same way on both chat paths. Whether an ACP agent or the
  OpenAI-compatible chat path calls a tool, the allowlist applies and the Gateway records an
  exec-budget and exec-audit entry. See [unified tool catalog](/docs/core/unified-tool-catalog).
</Callout>

### Test a tool

On the Tools page, pick an agent and a tool, supply JSON arguments, and run it. The call goes to
`POST /api/mcp/tools/call` with the chosen agent as the caller, so it meets the same allowlist and
governance an agent would.

## Connect an MCP server

To add your own MCP server, use **Add server** on the Tools page. It registers the server with
`POST /api/mcp/servers` as a local process or a remote endpoint:

| Field | Meaning |
|---|---|
| `name` | The server name; becomes the `<server>.` prefix on its tool ids |
| `transport` | `stdio`, Streamable HTTP, or legacy HTTP + SSE |
| `command` | The executable Core spawns for a local `stdio` server |
| `args` | Arguments passed to a local process |
| `url` | The endpoint used by a remote server |
| `env` | Environment variables passed to a local process; values are kept on the Core node |
| `headers` | Request headers sent to a remote server; values are kept on the Core node |

The server and its tools appear in the lists at once. Each server row shows an availability
indicator, so you can see a missing binary before an agent tries to call it.

### MCP authentication and settings

Every MCP row declares one of three visible authentication states: **No auth required**, **Authentication
required**, or **Credentials configured**. OAuth-backed servers are marked **OAuth** and expose their
live connection card in the server detail view. Use **Connect** to start authorization and **Log out**
to remove the local connection. A disconnected OAuth connection, or one that needs you to sign in
again, never sends a stale token.

Before an OAuth connection opens, Ryu shows a **connection access review**. It sets the most Ryu
lets the connected account do with data that can include contacts, messages, customer records, or
other people's data:

| Level | What it allows |
|---|---|
| **Risk-based (recommended)** | Safe reads flow normally; Ryu's default smart approval policy asks before risky writes or deletes. |
| **Read only** | View and search only. Create, change, send, and delete actions are blocked. |
| **Write access** | View, create, update, and send. Delete actions stay blocked. |
| **Full access, including delete** | View, create, update, send, and known delete actions. Ryu's destructive-action confirmation still applies. |

The default is **Risk-based**. Core stores the choice with the connection on the selected node and
enforces it before it uses the provider credential. The provider's OAuth scopes and the agent's
tool allowlist are separate checks.

Open **Settings** on a user-owned server to edit its transport, command or endpoint, arguments,
environment variables, request headers, description, and enabled state. Existing environment and
header values are masked. Leave a masked value unchanged to keep it, replace it to rotate it, or
remove the row to delete it. Built-in and plugin-owned MCP servers remain managed by their owner and
do not expose destructive local settings.

To install servers from a catalog (the official MCP registry, Smithery, or the Ryu-hosted
marketplace), see [Store: Install and Manage Downloads](/docs/surfaces/desktop/user-guide/store-installation#install-an-mcp-server)
and [MCP registry](/docs/core/mcp-registry). A catalog install adds a **disabled** entry to
`state/mcp.json` in the Ryu data folder, which you enable yourself. Core never launches an installed registry
command on its own.

## Search the catalog

The unified tool catalog lets you find a tool by query. It serves two routes:

```text
GET /api/tools/search?q=<text>
GET /api/tools/describe?id=<tool-id>
```

`search` returns ranked descriptors across MCP servers, built-ins, plugin tools, and Composio in one
`{ object, data }` envelope. `describe` returns the full schema for one tool. Both accept `?agent=`
or `?kind=` to narrow the results. Agents use the same search, describe, then call loop, so they
can reach many tools without loading them all up front.

## Connect Composio

Composio gives agents third-party actions for apps such as Gmail, GitHub, and Slack. It is
**searchable, not listed**. It is never registered as an MCP server or added to the full tool list.
When a key is configured, a capped set of Composio actions is pulled live into search results. An
agent calls an action by its fully qualified id `composio.<slug>` (for example
`composio.GITHUB_CREATE_ISSUE`).

### Use Composio Connect (For You)

Composio's **For You** product is a separate hosted MCP path. Ryu offers it as
**Composio Connect**, using the remote `composio_connect` server and OAuth. It is an alternative to
the direct API-key integration below, so it does not need a Composio API key.

To connect it, open **Marketplace → Connections**, choose an identity profile, and select
**Connect** on **Composio Connect**. Ryu opens Composio's browser authorization flow and stores the
provider token in the node's encrypted identity storage. The resulting tools use the
`composio_connect.*` namespace, keeping them separate from direct `composio.<slug>` actions.

Ryu shows the same connection access review before direct Composio authorization. The selected
Ryu level is a ceiling for the toolkit: **Read only** cannot change records, **Write access** cannot
delete them, and **Full access, including delete** is still subject to Ryu's destructive-action
confirmation. Ryu's own tool allowlist and approval policy remain separate checks. In **Ryu Work**
mode, **Auto** refers to the selected agent's advertised permission preset. It does not select an
upstream Composio policy or bypass Ryu approvals.

### Enable direct API-key actions

To enable the direct Composio action backend:

1. Open **Settings → Integrations**, choose **Open Gateway keys**, and paste your Composio API key
   in the Gateway API keys section. Saving the key makes Composio actions available in search.
2. In the **agent editor**, add the Composio actions you want to that agent's allowlist.

### The connection-required prompt

Composio actions run against a per-user entity. The first time an agent calls an action for an app
you have not authorized, Composio returns a connection-required response. Core turns it into a
`__ryu_elicitation__` envelope, a pause that asks you to sign in to that app before the action runs.
[Passport](/docs/standalone/passport) uses the same pattern, so a tool does not fail without telling
you when a connection is missing.

<Callout type="warn">
Composio actions require a configured API key. With no key, Composio does not appear in search.
</Callout>

## Connect and install from the chat

When an agent needs an account you have not connected, or a capability it does not have, it can
ask you in the conversation instead of telling you where to go. The request appears as a card in
the transcript, and nothing happens until you choose.

- **Connect an app.** The card names the app and says why the agent needs it. **Connect** opens
  the app's own sign-in page in your browser. You never type a password or API key into the chat.
  Before you sign in, choose what Ryu may do with the account, the same choices as
  **Store → Connections** (risk-based is recommended). The card waits while you sign in, shows
  **Connected**, and tells the agent to continue. If the app is already connected, the card offers
  **Continue** instead. Connections made from a card use your personal profile.
- **Install a plugin.** The card lists up to three matching plugins, ordered by publisher trust:
  official Ryu plugins first, then plugins from verified publishers, then community plugins.
  Within each group, plugins with stronger ratings and more installs come first. Each row shows
  the publisher mark, rating and review count, installs, GitHub stars when reported, version, and
  author. **Install** uses the same signed install as the Store and follows your organization's
  install policy. A new plugin starts turned off. The card then asks you to review its
  permissions and turn it on in the Store, and tells the agent to continue once it is on. A
  plugin you already have shows **Use it**; one that is installed but off shows
  **Open in Store**.
- A plugin listed in a marketplace other than your node's active one shows **Open in Store**, so you
  install it where you can see exactly which marketplace it comes from.
- **Community plugins** are marked **Not reviewed by Ryu** and can't be installed from the chat.
  **Review** opens the source so you can check it first, then install it from the Store.
- **Not now** declines. The agent is told you declined and continues without it.

A card is the only way an agent can get an account connected. No agent, including one that acts as
you, can start, finish or remove a connection, sign a model provider or MCP server in or out, or
change provider keys, plugin secrets or a plugin's permissions through
[Ryu's own API tools](/docs/extend/develop/extensions/self-api). It can still read their status.

The app names, trust marks, and stats come from Ryu, not from the agent, so an agent cannot make a
plugin look official or label one app as another. If your answer can't reach the agent, the card
stays open with **Send again**. These cards stay visible even when the chat's tool detail level is
set to **None**.

## Connections during onboarding

Onboarding can suggest read-only Composio sources from the work context you connect. Gmail,
Notion, Slack, and other available apps appear with a plain-language reason for the suggestion.
Raw email contents are not shown. You can connect more than one account. On a shared node, only
the owner or an admin can continue this setup. See
[Onboarding](/docs/surfaces/desktop/user-guide/onboarding).

## Choose which accounts an agent can use

Each agent's **Identity** setting and **Account access** decide which of your accounts, app
connections, and model providers it may use. See
[Agent Account Access](/docs/surfaces/desktop/user-guide/agent-account-access). An agent with
limited access also runs in the
[account sandbox](/docs/surfaces/desktop/user-guide/agent-account-sandbox).

## Built-in tool servers

Core ships built-in tool servers. They need no registration and appear alongside the servers you
add. They include:

| Server | What it does | Notes |
|---|---|---|
| `web_fetch` | Fetch a page, optionally as the logged-in user | Uses [Passport](/docs/standalone/passport) credentials when bound |
| `search_conversations` | Semantic search over past chats | See [Search & Auto-Recall](/docs/surfaces/desktop/user-guide/search-and-recall) |
| `threads` | Spawn and manage worker conversations | Opt-in per agent. Only an agent granted `threads.*` can spawn workers. See [coordinator threads](/docs/core/coordinator-threads) |
| `delegate` | Fan out subtasks to sub-agents in parallel (short-lived) | For durable workers, use `threads` instead |
| `skills` | Discover and load Agent Skills on demand | `skills.search` and `skills.load` |
| `marketplace` | Search public Marketplace listings and read one listing | Read-only `marketplace.search` and `marketplace.describe`. Installs still need your approval. A server you register as `marketplace` is hidden by this built-in, so give yours another name |
| `notify` | Show a native desktop notification | |
| `consent` | Ask you to connect an app or install a plugin with a card in the chat | Nothing is connected or installed until you confirm |
| `channel` | Post a message to a Slack or Discord webhook | |
| `challenges` | List open [Ryu Challenges](/docs/programs/challenges), read one, and submit your project | Uses your Ryu sign-in. `challenges.submit` always asks for your approval first |
| `sandbox` | Run WASM/WASI modules with default-deny capabilities | Uses the built-in Wasmtime backend |

## Plugin tool servers

These servers come from Ryu plugins. They are available while the plugin is enabled:

| Server | Plugin | What it does | Notes |
|---|---|---|---|
| `ghost` | Ghost | Desktop automation (click, type, screenshot, recipes) | Needs the Ghost sidecar installed |
| `shadow` | Shadow | Screen and audio capture, search | Needs the Shadow sidecar installed. Calls go through Core |
| `spider` | Spider | Web scraping | Needs the `spider` command-line tool (`spider_cli`) installed |
| `exa` | Exa Search | Web search | Needs an Exa API key (`RYU_EXA_API_KEY`) |

<Callout type="info">
  Ryu downloads prebuilt Ghost and Shadow binaries for Linux (x86_64), macOS (Apple silicon and
  Intel), and Windows (x86_64). On any other platform the install fails with an error that names
  the platform, and you can build the sidecar from source. On a node with a virtual desktop, Ghost
  drives the display that the [Virtual Desktop](/docs/surfaces/desktop/user-guide/virtual-desktop)
  panel streams, so you can watch and take over.
</Callout>

### Shadow's port check

Ryu checks that the server on Shadow's port really is Shadow before it sends it anything. Shadow's
API is protected by a secret that Ryu keeps in its data folder, and Shadow must prove it holds that
secret without Ryu revealing it. A Shadow you started yourself, or one left running by an earlier
Ryu, is still used when it passes the check.

When another program holds the port and fails the check:

- Ryu does not start Shadow and sends that program no secret and no screen-history request.
- The Shadow status shows a port conflict.
- Ryu replaces the stored secret in case that program saw the old one. Clips and Meetings pick up
  the new secret on their next request.

Stop the other program, then start Shadow again. The desktop app's own Shadow calls (the tray's
capture toggle and the companion overlay), the Island overlay, and Ghost's journal markers run the
same check and send nothing when it fails. Island shows Shadow as unavailable, the companion
overlay shows no suggestions and returns an error, the tray's capture toggle leaves capture and its
label unchanged, and a Ghost journal marker fails with an error.

A Shadow binary that is too old to answer the check is replaced with the current one the next time
you start Shadow. Until then, on Linux and macOS Ryu can keep using a binary it started itself, but
Clips, Meetings, and the clients above can't reach it.

Shadow's optional terminal-capture shell hook never sends the secret. After each command it adds a
line to a file in a folder only your account can read, and Shadow picks it up from there. It records
only while Shadow is running. It skips commands your shell keeps out of history (for example ones
that start with a space, when your shell is set up that way). In PowerShell it also skips commands
that start with a space and lines PSReadLine keeps out of its history, such as lines that contain a
password or token. A new terminal never
records the last command of an earlier session.
