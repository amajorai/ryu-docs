A `ryu://` link opens Ryu from a web page. It can open a screen, start a chat, install an item, or
connect to a node. Ryu asks you to confirm actions that change data. Desktop, web, and mobile share
one link grammar, so a link built on the website works the same way in the app.

## Choose a profile

`ryu://` opens the main Stable app. Profile-specific builds use separate schemes:

| Scheme | Profile |
| --- | --- |
| `ryu://` | Stable |
| `ryu-dev://` | Dev |
| `ryu-beta://` | Beta |
| `ryu-nightly://` | Nightly |
| `ryu-canary://` | Canary |

The destination stays the same: `ryu-dev://open/settings` opens Settings in Dev.
Install the matching profile build before using its scheme. A link does not
switch the running app into another profile, and a mismatched link is ignored
or rejected rather than reading another profile's data. Development and test
builds do not take over the Stable scheme.

## The two kinds of link

The host segment (the word right after `ryu://`) decides whether a link only navigates or performs
an action with a side effect.

| Link | What it does | Confirm? |
|---|---|---|
| `ryu://open/<page>` | Opens a desktop surface (agents, settings, models, ...) | No |
| `ryu://chat/new?prompt=...` | Opens a new chat with the composer pre-filled | No |
| `ryu://chat/<id>` | Opens an existing conversation | No |
| `ryu://models/<source>/<id>` | Installs or switches the local model | Yes |
| `ryu://skills/<source>/<id>` | Installs a skill | Yes |
| `ryu://apps/<id>` | Installs a marketplace app | Yes |
| `ryu://bundles/<id>` | Installs a Marketplace bundle | Yes |
| `ryu://nodes/connect?url=...` | Connects the app to a Core node | Yes |
| `ryu://handoff/<conversation-id>?source=...&v=0` | Reviews and continues a chat on another configured node | Yes |

Navigation links open immediately. Action links install, switch, or connect, so they always open a
confirm dialog first.

<Callout type="warn">
Custom-scheme links need the corresponding app registered with the operating
system. Running the web interface alone does not register a desktop handler.
</Callout>

## Continue a chat on another node

An RNP handoff link is a credential-free locator:

```text
ryu://handoff/<conversation-id>?source=<node-url>&v=0
```

It never contains the transcript or a node token. The source must use HTTPS, except for a
loopback Core. Ryu matches `source` to a node you already configured, exports a bounded preview,
then shows the same exact-message review used by **Continue on another node** in a chat's menu.
You choose the destination before Ryu imports that frozen bundle. Tool state, workspace paths,
node credentials, structured authentication data, and the running agent session stay on the
source node. When the chat works in a git repository and both nodes support it, the same review
also offers **Bring working tree**: you see the changed files, tick which untracked files to
include (secret-looking files start unticked), and confirm the remote URL the destination clones.
See [RNP continuity](/docs/extend/integrate/rnp) for the
bounds and API contract.

## Install or switch a model

A model link points at a catalog entry. For a Hugging Face GGUF the shape is:

```text
ryu://models/huggingface/unsloth/gemma-4-12B-it-qat-GGUF
```

Everything after `<source>` is the verbatim catalog id, joined by `/`, so an `author/repo` id
(including a trailing `-GGUF`) survives intact.

What happens when you click it:

1. Ryu opens and shows a confirm dialog.
2. If the model is **not installed**, Ryu picks the best-fitting quantization for your device and
   the dialog reads **Install & use**. Confirming downloads the GGUF through Core's verified path
   (`POST /api/models/catalog/install`) and then makes it the served model.
3. If the model **is installed**, the dialog reads **Switch**. Confirming switches the local engine
   to serve it with `POST /api/models/active`.

The switch uses Core's active-served-model override. See
[Model Catalog](/docs/core/model-catalog) for the `local-chat-model` preference and the
`/api/models/active` route that backs it.

<Callout type="warn">
The switch affects only the llama.cpp engine. The success toast reads "Now serving ..." only when
llama.cpp reloaded. Otherwise it reads "selected (takes effect on next engine start)" or "applies
when llama.cpp is the active engine".
</Callout>

## Install a skill

A skill link works the same way, against the skills catalog:

```text
ryu://skills/skills.sh/<owner>/<repo>/<slug>
```

Clicking it opens the confirm dialog. If the skill is already installed, the dialog says so.
Otherwise, confirming installs it with `POST /api/skills/catalog/install`. See
[Skills Catalog](/docs/core/skills-catalog) for what a skill is and where it lands on disk.

## Install an app

An app link installs a marketplace app (a plugin-catalog entry) by its manifest id:

```text
ryu://apps/@ryu/clips
ryu://apps/com.ryu.agentbrowser
```

The id is the same one the app's README and `ryu-cli apps add <id>` use (see the
[CLI reference](/docs/surfaces/cli/reference)). Every `amajorai/ryu-<app>` README carries this link.
Clicking it opens the confirm dialog. If the app is already installed, the dialog says so.
Otherwise, confirming installs it with `POST /api/plugins/:id/install` on the active node, or on the
node a `?node=` hint names if you already have that node.

## Connect to a node

A node-connect link carries its payload in the query string rather than the path:

```text
ryu://nodes/connect?url=<base-url>&token=<bearer>&name=<label>
```

`url` is required. `token` and `name` are optional. Confirming adds the node and makes it active.
The Desktop node selector's **Share** button and the website's node controls generate these links,
so you rarely write one by hand. The QR code's expand button opens a larger preview. See
[Nodes and Presence](/docs/core/node-and-presence) for how nodes work.

Console's server cards on the web generate tokenless links with the server address and a sanitized
label. Ryu still asks for confirmation and signs in to the server itself; copying the string or
showing its QR never grants access.

<Callout type="warn">
Only connect to nodes you trust. A connected node runs your agents and sees your chats, and the
confirm dialog says so.
</Callout>

## Open a surface

A navigation link jumps straight to a screen without any confirm step:

```text
ryu://open/agents
ryu://open/settings
ryu://open/models
```

The page keys are the `DEEP_LINK_PAGES` list in `packages/protocol/src/deep-link.ts`
(chat, agents, models, skills, tools, spaces, workflows, automations, monitors, marketplace,
settings, channels, timeline, delegation, credits, fleet, extensions, apps, engines, store,
calendar, services). Each surface maps a key to its own route. An unknown key is
ignored rather than erroring.

A chat link can pre-seed the composer:

```text
ryu://chat/new?prompt=Summarize%20this%20page&agent=ryu&project=/repo/path
```

<Callout type="warn">
A `prompt` only fills in the composer. Ryu never sends it automatically. Any page can fire a
`ryu://` link, so the message waits for you to read it and press send. There is no `send=true`
parameter.
</Callout>

## The confirm dialog is the security boundary

A `ryu://` link is untrusted input, because a malicious page can fire one. The protocol module only
parses links. It never installs, connects, or sends a message on its own. Two guarantees follow.

- **Nothing installs without your confirmation.** Every action link routes through the confirm
  dialog, and the actual download runs through Core's verified, checksum-pinned install path, not
  the link.
- **Source is advisory, not an instruction.** The `<source>` segment names a catalog
  (`huggingface`, `skills.sh`) for display, but installs stay pinned to your configured catalog
  source. A link cannot point Ryu at an arbitrary registry.
