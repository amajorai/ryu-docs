Beyond plain back-and-forth, the Ryu chat composer carries a set of power features modeled on the
ergonomics of Claude Code. They live in the chat view: some as slash commands you type, some as
composer toggles and hover actions.

## Local and cloud defaults

Ryu keeps two node-scoped selections. Normal interactive chats use the cloud selection when one is
configured and fall back to the local selection otherwise. Plugins, side-model calls, and local
utility work always use the local selection. You can edit both from the Gateway **Defaults** dialog;
the same universal agent/model picker is used in onboarding and settings. External ACP agents retain
their own model, effort, and permission configuration.

## Start with Ryu in everyday language

After first setup, Ryu opens a new conversation and says hello as your main assistant. The greeting is
an assistant message, so there is no pretend question from you in the chat. Paid or ready-to-use cloud
models can answer straight away; when a local model is still being installed or started, Ryu waits and
continues when it is ready.

You can describe the result you want in ordinary words. Ryu can look at the files, notes, conversations,
apps, connections, and routines already available, then make a short checklist when setup needs more
than one step. It explains what needs adding or connecting and asks before it installs something, changes
access, sends a message, or saves a recurring routine. You do not need to know the names of the internal
technical parts to get started.

## Pick up chats after Wi-Fi or LAN returns

The optional [Reconnect Retry](/docs/plugins/reconnect-retry) plugin covers the gap
between a dropped connection and a chat that never finished underneath it. When the
selected node or network goes away, it remembers conversations that were actively
running. When both are reachable again, Ryu first reconnects to any turn that kept
running; only a turn that became **failed** or **interrupted** is retried, and each
conversation gets one bounded attempt.

The retry reuses the user message already saved in the conversation, so it does not
append a duplicate prompt. Core checks the conversation's access and run permission
before accepting it, and unrelated old failures are not retried. If you do not enable
the plugin, a lost stream still gets the normal live-turn resume behavior, but a
terminal failure remains available for a manual retry.

## Give an agent a role and a name

When you create or edit an agent, you can add any short title — for example **CTO**, **Researcher**,
or **Travel planner**. Ryu shows that title as a badge beside the agent name in chat, the sidebar,
and the agent picker. New agents start with a common English first name; use the refresh button to
pick another one, or use the magic button after describing what the agent should do to ask the local
agent for a contextual name. The generated value is still just a suggestion that you can edit.

## See when a reply is being written

While Ryu is generating a response, the transcript shows a compact speech-bubble typing indicator
with three animated dots. It replaces the shimmering status text and stays visible through the
thinking, tool-work, and first-token stages of a live reply.

If you scroll up while a reply arrives, the chat keeps the latest incoming messages unread instead
of pulling you away from what you are reading. A theme-colored divider marks where those messages
begin, and the bottom affordance shows the count beside its arrow or live dots. The count clears
when the divider enters view or when you return to the latest message; updates to one streamed reply
still count as one message.

## Reply to any message

Hover a user message, an agent reply, or a message from another person in a shared chat and choose
**Reply to message** from its action icons. Ryu opens the same quote composer used for text
selections, carrying the whole message into the pending quote above the composer. You can add your
response before sending, or dismiss the quote and keep the draft.

When the reply points back into a chain of three or more turns, the composer shows a **Long reply
chain** infobar with **Create thread**. That action forks the conversation at the replied-to message,
copies the earlier history and chat context into a new tab, keeps the same agent and selected model,
and carries the quote and unsent draft with it. The original conversation is unchanged. This is an
AI-chat fork with the full preceding context, rather than a Discord-style thread containing only the
reply chain.

## Rename a chat without losing the thread

Manual chat renames and titles supplied automatically by an enabled chat-title feature use the
same desktop transition. The new title appears one character at a time while the previous title
fades away from left to right underneath it, so the change reads as one continuous handoff instead
of a sudden replacement. The transition follows your animation setting and the operating system's
reduced-motion preference.

## Manage a saved chat from the sidebar

Open a chat's **⋯** menu, or right-click the row, to access the same session actions. You can pin,
rename, remove the chat from its project, archive it, open a side chat, fork it into the current
workspace or a new worktree, and open it in a separate window. Removing a chat from a project only
clears its workspace grouping; it does not delete the chat or touch files on disk.

The **Copy** submenu can copy the working directory, session ID, Ryu deeplink, or the full chat as
Markdown. **Add scheduled task…** appears when the Calendar app is enabled, and **Open side chat**
appears when the Side Chats app is available.

## Track a session from the sidebar

When an agent is working from a checklist, its session row shows a slim progress rail along the
bottom. The filled portion represents the steps already complete, so you can scan several sessions
without opening them. Bot rows mirror the latest direct session for that bot.

An active checklist gives the whole row the same gentle diagonal sheen used by plan badges. When
every step is finished, an unread session gets a subtle green gradient and a large checkmark until
you open it. Chats without a saved checklist keep their normal sidebar treatment.

## Load older messages in long chats

Long conversations open at the newest message page. Scroll to the top of the transcript to load the
next older page; Ryu prepends it and keeps your reading position anchored so the messages already
on screen do not jump. Continue scrolling upward to walk back through the full history. New replies
still arrive at the live edge at the bottom.

## Ask a supported local model to answer now

For a supported local reasoning turn, Ryu waits briefly before showing **Answer now** directly below
the active thinking block. The grace period follows the selected effort: higher-effort turns get
longer to think before the action appears. Choose it to end the current reasoning block and continue
toward the final answer; it does not cancel the turn or discard the response.

This action is provider-native, so it is intentionally hidden when the selected cloud provider,
Gateway route, ACP agent, or local runtime does not advertise the operation. The first bundled
runtime with this support is the current `llama.cpp` runtime. **Stop** remains the control for
ending the whole turn.

## Make agent activity easier to follow

The optional [Action Summary](/docs/plugins/action-summary) plugin can add one plain-language line
for each visible thinking block or tool action while the agent works. It keeps the main transcript
unchanged, bounds the action input, redacts likely secrets, and lets you choose brief, standard, or
full detail plus a side model in Settings.

For long-running or high-risk work, the opt-in [Observer Agents](/docs/plugins/observer-agents) plugin
can review a bounded digest of recent activity after an assistant turn. It normally stays silent
and emits only concise advisory notes; it cannot call tools, change files, grant permissions, or
stop the worker.

## Use slash commands, Skills, and mentions

Type `/` to discover commands and enabled Skills. Commands stay in the **Commands** group; installed
Skills appear in **Skills** and insert their stable `/<skill-id>` command. A selected command or Skill
does not send the message until you finish writing and choose **Send**.

Type `@` to discover **Agents**, **Apps**, **Plugins**, and **Workflows**. When the [Inbox app](/docs/apps/approvals)
is installed and enabled, the same picker also shows **Users** from the current organization/team
scope. Each human row uses the person's name and avatar, with initials when no avatar is available.

Selecting a User inserts a visible `@Name` reference and sends that person an Inbox notification after
the chat message is saved. It does not change the selected agent, workflow, team, or conversation
target, and it never routes the turn to that person. Users are not shown when Inbox is unavailable;
Core still verifies the organization/team scope and recipient before delivering the notification.

## Reference another chat

Use the composer **+** directory and choose a conversation from **Chats**, or drag an open chat tab
into the active chat. Ryu inserts an `@Chat title` mention and attaches that saved chat's recent
transcript to the next turn as read-only context. Referencing a chat does not merge the two threads or
change where the reply is saved. Up to three chats can be attached to one turn.

## Use multiple desktop windows

Right-click an open chat tab or a supported sidebar item and choose **Open in new window**.
**Open in new tab** keeps the destination in the current desktop window; a new window gets its own
tab strip and layout. The same action is available for chat rows, agents, Spaces and Space pages,
and the main sidebar destinations.

When you click a chat from a sidebar, Ryu checks the other desktop windows first. If that chat is
already open elsewhere, Ryu focuses that window and activates its tab instead of creating a second
live owner. Explicit **Open in new window** is the opt-in exception: it creates another view of the
same saved conversation. Conversation data and Core work remain shared; tabs, splits, and window
layout remain local to each window. Closing a secondary window does not stop Core or the work in
other windows.

Dragging a tab currently reorders it within its window. Dragging a tab out to create a new native
window, and restoring a tab back into another window, are not enabled yet.

## Share a saved chat

Open a saved chat and choose **Share conversation** in the title bar. The access dialog separates
the live conversation from a public copy:

- Add a person as a **Viewer** to let them read the live chat, or as a **Participant** to let them
  read and send new messages.
- Set **General access** to **Restricted**, **Anyone in the organization**, or **A team**. Team access
  requires choosing a team. Organization and team roles still apply, so read-only members do not
  gain write access.
- Choose **Anyone with the link** to publish a frozen, read-only copy that opens without sign-in.

Public links contain only the chat title and the user/assistant transcript. They omit owner names,
tool activity, files, system messages, and other private context. Messages added later do not appear
automatically; choose **Update copy** when you want to replace the published snapshot. Returning
General access to a signed-in option revokes the public link.

The owner and organization admins can change access. A person who can only read the chat can inspect
the current access list but cannot edit it. Sharing a chat never shares the owner's private Spaces or
long-term memory, and temporary chats cannot be shared because they are not saved.

## Send attachments without text

Use the composer **+** menu and choose **Files and images** to stage context for a turn. You can
send the attachment on its own without typing a prompt; a staged file or image counts as composer
input and keeps the **Send** action available. When live voice mode is enabled, its phone action
appears only while the composer has neither text nor staged attachments.

## Paste links and Markdown in the composer

The default composer stays a lightweight textarea. If you regularly paste formatted notes or need
to adjust links before sending, turn on **Rich Markdown composer** in **Settings → Appearance →
Interface**. The rich mode uses the same Markdown editor as the rest of Ryu's editing surfaces and
keeps the composer value compatible with the normal chat send path.

After a conversation has messages, a plain draft that fits on one visible line uses the compact
composer: the textarea and controls share one row. As soon as the text wraps or you insert a line
break, the textarea moves above the normal controls row so the buttons are not squeezed beside a
taller editor. Deleting back to one visible line restores the compact row. The Rich Markdown
composer always uses the full stacked layout.

Choose how the Enter key behaves in **Settings → General → Chats → Send shortcut**. **Enter** is
the default and sends immediately while **Shift + Enter** inserts a newline. If you prefer the
inverse, choose **Shift + Enter** so plain Enter adds a line break and **Shift + Enter** sends.
Choose **Command/Ctrl + Enter** when you want Enter to stay a newline and only the modifier chord
to send the message.

Paste a Markdown link such as `[project plan](https://example.com)` and it appears as a clickable
link while you write. Click the link to open its small editor, where you can change the destination
URL or the display text, or remove the link. Common Markdown marks and blocks—including emphasis,
code, lists, quotes, headings, tables, and fenced code—are rendered inline as you edit. You can turn
the rich mode off at any time to return to plain text editing; it is off by default.

Chat mentions remain special in rich mode. The `@` picker still inserts the same interactive mention
tokens, and existing app, page, chat, team, workflow, and file mention renderings are preserved when
the message is sent. Rich mode changes how Markdown is edited and displayed; it does not change the
mention targets or the chat message format.

## Open mentions from the transcript

Entity mentions stay interactive after a message is sent. This works for both your messages and
agent replies: click an Agent, App, Plugin, Workflow, or older reference mention to open its
destination. Apps open their companion surface when available; plugins and Skills open their
installed catalog; chats open in their saved conversation tab; and Teams, workflows, spaces, MCP
servers, integrations, and project folders open their corresponding surface. App-owned rows from the
sidebar and Library lists can still resolve to the exact page, board, or meeting they contributed.

Human User mentions are reference-only in the transcript because they have no Desktop profile route.
They keep the person's avatar/initials and colored name without a filled chip background. Website and
file links in the same message remain clickable, and app, plugin, and app-owned item mentions keep
their app icon and accent-colored text inline in the composer and transcript without a filled chip
background.

## Review files changed by a turn

When an agent finishes a turn that edited or created files, the transcript keeps an edited-files
card at the end of that assistant reply. A one-file turn uses a compact **Edited filename** row with
its insertion and deletion totals. Turns that touched multiple files keep the expanded **Edited N
files** card, including the first few paths and a **Show more files** control for longer turns.

Select **Review** to open the workspace **Changes** view filtered to **Last turn**. Select **Undo**
and confirm to restore the listed tracked files to their last committed versions. Undo deliberately
refuses untracked or ignored files because they do not have a committed version to restore safely.
The card remains visible after a successful undo, but its Undo control is marked **Undone**.

The card is derived from the saved tool activity, so it remains available when you reopen the chat;
hiding tool detail does not hide this completed result. Only completed tool results contribute: a
failed write or a tool call still streaming at turn end is not presented as a finished file change.

Agents can also leave a completed JSON UI or artifact card in the same end-of-turn position. Those
cards support the interactive components and safe web links described in the [built-in tools
reference](/docs/core/built-in-tools#end-of-turn-result-cards), while the existing inline tool
previews continue to behave as before.

## Pursue a goal

A goal is a persistent completion condition attached to a conversation. After each turn a separate
model judges whether the goal has been met; if not, the conversation keeps going on its own until
it is met or a safety cap is reached.

- Type `/goal <condition>` to set a goal, or use the composer **+** menu and pick **Pursue goal**.
- An active-goal chip and a goal bar appear above the composer, showing the editable condition, a
  live elapsed timer, and the latest judge reason. The Target icon on the chip turns into an
  **✕** on hover to clear it.
- When you create or edit a goal from the goal bar, Ryu adds the condition to the transcript as a
  user message and labels it **Sent as goal** beneath the bubble.
- Type `/goal` alone to open the bar, and `/goal clear` to remove the goal.
- The **Stop** button halts the loop at any time.
- An agent with the `goal.set` tool can set or replace the goal for the current conversation; the
  tool is scoped by Core and resets the judge progress when it is called.

The judge runs as its own model call, separate from your chat model. Choose which model judges
goals in **Settings → Goals**. The continuation loop is capped at a fixed number of turns so a goal
can never run away. For how the goal state and judge primitive work, see
[Goals](/docs/core/goals).

## Ask a side question with `/btw`

`/btw <question>` asks a quick question about the current conversation. The side model sees the
conversation context but has no tools, returns a single answer in a dismissible overlay, and the
exchange never becomes a chat message. It is the inverse of a sub-agent - full context, no tools.
Because the desktop asks over the active conversation, the exchange is kept as a lightweight side
chat you can re-open from the Context rail or sidebar. The built-in [Side Chats](/docs/plugins/side-chats)
plugin owns the `/btw` command; see
[Side Questions](/docs/core/side-questions) for how persistence works.

Expand a conversation in the sidebar to see its saved side chats in a connected branch-style list.
Each entry keeps the question visible, shows a short answer preview and relative age, and opens the
side-chat overlay without adding the exchange to the main transcript. Sub-agent entries use the
same list so related follow-ups stay together under their parent conversation.

Type `/btw` once you have at least one message in the thread. The built-in **Side Chats** plugin
sends the visible main-chat transcript with the question, including the latest in-flight text, so
the answer has the context you are looking at. Pick the model and reasoning effort it uses in
**Settings** (the `btw-model` and `btw-effort` preferences). For the underlying primitive, see
[Side Questions](/docs/core/side-questions).

Selection actions are a lightweight context fork: they reuse the active main-chat model and the
same bounded visible transcript, but they do not copy tools or add a new message to the main chat.

## Double-check answers

Toggle **double-check** in the composer to have a second model review each answer as it arrives. It
fires once per assistant message and flags problems it finds. Configure which model reviews and at
what reasoning effort in **Settings → Double-check**. For the review primitive, see
[Double-Check](/docs/core/double-check).

## Voice Recognition

Click the **microphone** in the composer to dictate. A live waveform (an `AnalyserNode`-driven
wave) shows you are being heard; when you stop, the 16 kHz mono WAV is posted to
`POST /api/voice/transcribe` and the transcript is appended to the composer
(`apps/desktop/src/hooks/useVoiceRecorder.ts`). The default Voice Recognition engine (whisper) is bundled and
auto-downloaded, and is swappable. Pick your default microphone in **Settings → Audio**.

For the speech engines you can swap in, see [Voice Engines](/docs/surfaces/desktop/engines/voice-engines).

## React to messages

Reactions are supplied by the built-in [**Message Reactions**](/docs/plugins/reactions) plugin, so the feature can be enabled
or disabled like any other plugin. When it is enabled, hover a message and choose the reaction
button to add a quick emoji reaction. The popover keeps the common reactions one click away; choose
**+** to open the complete searchable emoji picker. Your reaction is added immediately and the
picker closes after you choose an emoji.

## Temporary chats

The built-in [**Temporary Chats**](/docs/plugins/ghost-chats) plugin adds a **Temporary chat** toggle to the composer’s **+**
menu. A temporary chat stays in the current tab and is never written to conversation history,
long-term memory, drafts, presence, or reactions. Its composer is marked with the temporary-chat
state so you can tell when the privacy boundary is active. This plugin is separate from the
`@ryu/ghost` computer-control plugin and is packaged as `@ryu/ghost-chats`; disabling **Temporary Chats** removes the chat lifecycle
feature without changing computer control.

## Expand the composer

The built-in [**Expanded Composer**](/docs/plugins/expanded-composer) plugin adds an **Expand composer** ghost button to the
composer toolbar. Select it to grow the composer in place with more room to write, while keeping
the same attachments, plugin controls, voice actions, and send behavior.

The expanded composer uses the same state, so text remains intact when you press **Escape** or
choose the close button in its top-right corner. The transition respects the system reduced-motion
preference.

## Live voice calls

Select the **phone** icon when the composer has no text or staged attachments to start a live voice
call with the selected agent. The compact call screen names who you are calling, shows the elapsed
time, and keeps the live activity beam and waveform visible while the microphone is active. Use
**Mute** to pause microphone frames without ending the session, **Interrupt** to stop the current
reply, or the red **End call** action to leave voice mode.

The call screen keeps the running transcript visible by default. The **Show transcript in voice mode**
setting can hide the transcript while leaving the call identity, timer, microphone state, activity
feedback, errors, and call controls in place. The same activity treatment is available in the Island
companion. Microphone permission errors remain visible in the call screen and the existing audio
and transcript behavior is unchanged.

On narrow screens, shared dialogs use a bottom drawer layout with a drag affordance and bounded
scrolling. The same form and approval state are preserved when a dialog changes into a drawer.

## Recover interrupted and compacted history

If the app closes or crashes while an agent is replying, Ryu keeps the partial reply and places an
**Interrupted** separator beneath it. Send a follow-up yourself to continue the conversation; an
interrupted turn does not resume automatically after a restart.

When Ryu compacts earlier context to make room for a new turn, it places an **Earlier context was
compacted** separator in the transcript. The separator is informational and does not add another
message to the conversation.

With no text or staged attachments, the primary action is a quiet icon-only **Play** control with no
visible label. It remains disabled until there is text or an attachment to send, and it does not
start voice mode by default. Voice dictation remains available from the microphone control.

## Agent session controls

The chat surface has an **Interface mode** switch directly in the account menu. **Ryu Work** keeps the
agent picker visible but hides model, approval, and effort controls; Core automatically routes the turn's
model for the selected agent. **Code** exposes the explicit model, ACP session, workspace, and full
transcript controls. Hidden model and effort choices are not sent as request pins, so Ryu Work cannot
accidentally override automatic model routing. For an ACP agent, Ryu Work quietly chooses its
advertised **Auto** permission preset when one exists; otherwise it chooses an advertised
approval/default preset, or leaves the agent's own default in force. This only hides configuration
controls: agent safety approvals still apply and approval prompts still appear when a turn needs one.

Ryu Work also selects the built-in **Agents view** sidebar automatically. The sidebar opens on
**Agents** by default, with **Sessions** as the secondary tab. This is part of the Core/desktop
experience; no separate app or plugin is required.
The view is labeled **Bots view** when **Use Bot terminology** is enabled and **Agents view** when it is off.

In the **Agents view**, **Sessions** can also be organized locally into custom sections. Create a section from
the Sessions header, drag chats into it, and drag section headers to reorder them; **Unorganized**
is the default first section but can be moved too. Renaming or deleting a section changes only this
Desktop sidebar: deleting one returns its chats to Unorganized and never deletes the conversations.
Chats inside every section stay sorted by newest activity.

In the **Agents view**, open an agent's context menu and choose **Pin agent** to keep it at the top of the
roster. Pinned agents are removed from the ordinary list so they do not appear twice: one pinned
agent gets a larger hero tile, two use a two-up pair, and three or more use a compact three-up grid.
Use the pin control on a tile, or the same context menu, to unpin it.

For a code session with a saved project folder and branch, **Code** mode can show a compact
pull-request status icon beside the chat when the **Pull Requests** app finds a request. The icon is
shown only for these code sessions in Code mode: open is GitHub green, draft is gray, closed is red,
and merged is purple. It links to the request; Ryu Work keeps the simplified sidebar row.

Ryu's native agent does not publish ACP permission presets, so Ryu Work leaves its Core approval
policy in force for that agent. The separate **Auto** entry in the agent picker is agent-auto
routing: it chooses which agent handles a turn, using its configured local classifier, and is not a
permission mode or a replacement for the selected agent.

When the active agent is an ACP agent, the composer surfaces per-agent session controls: pickers for
the agent's permission mode, reasoning effort, and model. Nothing here is hardcoded by Ryu. Each
picker is built from what the agent advertises at `session/new`, so a control only appears when that
agent actually reports it (`apps/desktop/src/lib/api/acp.ts`,
`apps/core/src/sidecar/adapters/acp.rs`).

| Control | When it appears | Source |
|---|---|---|
| **Permission mode** | The agent reports modes (for example `Auto`, `default`, `acceptEdits`, `plan`, `bypassPermissions`) | The agent's advertised mode set and active mode |
| **Reasoning effort** | The agent exposes a `thoughtLevel`-style select config option | That config option |
| **Model** | The agent supports the unstable ACP session-model capability | That capability (null and hidden otherwise) |

Core fetches this advertisement once per agent via `GET /api/agents/:id/acp-config` (cached per
agent) and returns all-null for non-ACP agents. Your choice is applied to the next chat turn, which
Core re-applies to that turn's session.

The picker adapts to the composer’s available width, which is useful in a split pane. The active
agent stays named as the orientation cue; the model label becomes a model icon when space is tight,
reasoning effort becomes a small stepped bar meter, and secondary controls progressively become
icons or remain available in the picker. Hover text and accessible labels retain the full setting
names.

You can choose where this shared **model and agent picker** lives in **Settings → Appearance →
Interface → Chat model & agent picker**. **In composer** is the default. **In tab bar actions tray**
moves the same picker to the actions beside the chat tabs, leaving the composer controls less busy.

The same Interface page has **Show latest message / tool state in sidebar**. When enabled, ordinary
chat sessions become two-line rows: the second line rotates between the latest message and an active
run state such as **In progress**, **Needs input**, or **Interrupted**. The setting does not change
The **Agents view** always keeps its own two-line agent rows. Both layouts use the app-wide
**Enable animations** preference, so disabling animations leaves the latest state visible without
the transition.

Hover a chat row to open its preview popover. Alongside the title, branch, folder, worktree, and
agent details when available, it shows **Messages**, the authoritative total for that conversation.
This makes the size of a thread visible without opening it.

Assistant replies with Markdown tables keep a compact, horizontally scrollable presentation in the
transcript. A soft fade at the visible edge shows when more columns are available. Hover a table and
select the expand button in its top-right corner to open a larger dialog; the expanded table can
scroll in both directions while you keep the surrounding chat in place.

The **Enable animations** switch in **Settings → Appearance → Motion** is the master control for
new chat motion, including sidebar state rotation, loading treatments, and composer progress motion.
The operating system's reduced-motion preference takes priority. Plan and file-change chips above
the composer remain translucent with a blurred backdrop so they stay readable over the chat without
becoming an opaque panel.

If you change the composer target while an agent is replying, Ryu shows a brief confirmation that
the agent, model, or effort choice will be used on the next turn. Idle changes stay quiet because
the next message is already the next turn. You can choose **Settings → General → Chats → Composer
selection changes** to describe these changes as applying on the next turn or from your next user
message.

### Agent-controlled target changes

An active agent can request a different installed agent, model, or reasoning effort for the next
user turn through the built-in `agent_control.set_active_target` tool. Core validates the request
against the current conversation, applies it once after normal model routing, and leaves saved agent
defaults unchanged. The desktop adopts an agent handoff for the conversation and shows the effective
agent/model/effort in the transcript. This is separate from model routing: routing decides from the
user's message, while agent control is an intentional escalation or handoff requested during the
agent's work. For ACP targets, Core applies the effort through the target's advertised/conventional
effort option when one is available; an agent with no supported effort control continues on its own
default.

### Interactive tool-permission prompts

When an agent in a gating permission mode wants to run a tool, Core streams a `data-ryu-permission`
part and pauses the turn. The desktop renders the agent's offered options (allow once, allow always,
reject once, reject always) in the same composer surface as the chat editor. If you are typing, Ryu
keeps the draft uninterrupted and waits for the shared 2.5-second idle window before morphing the
editor into the approval card. Your choice is sent to `POST /api/chat/permission`, keyed by the
request id, which unblocks the awaiting turn.

In **Ryu Work**, this card uses plain-language action text and keeps raw commands out of the approval
surface. **Code** can show the technical tool details when you need to inspect exactly what the agent
requested.

### Agent questions

When an agent needs structured input, its Q&A card takes over the same composer surface as the chat
editor. If you are already typing a chat message, Ryu keeps the draft uninterrupted and waits until
you have stopped editing for 2.5 seconds before morphing the editor into the pending question. Until
then, the question stays visible in the conversation. The microphone is also available inside the
card's **Other** input and its free-text question input, so spoken answers can be transcribed
without leaving the pending question.

<Callout type="warn">
  These controls are data-driven, so they only appear when the ACP agent advertises the capability.
  The model picker in particular depends on the agent's support for the unstable ACP session-model
  feature, so many agents show no model picker at all.
</Callout>

## Branch a conversation

Every message has a **branch** action in its hover toolbar. Branching forks the conversation up to
that message into a new, independent conversation in a new tab, so you can explore an alternative
direction without disturbing the original thread. Before it runs, choose whether to **Fork in this
workspace** or **Fork in a new worktree**. The first keeps the branch in the current workspace; the
second starts the next turn in an isolated worktree so changes stay separate until you apply them.
Conversations stay linear - there is no in-place message tree. For how the fork is stored, see
[Conversations and Sessions](/docs/core/conversations-sessions).

In the **Agents view**, the sidebar presents those independent conversations as a branch-style thread list
under the bot. Expand the bot to browse its direct threads, including newly-created forks, with the
same paging and searchable overflow controls used by other sidebar sections. If a conversation has
multiple participants, the Chats list converges its related conversations into a **Group chat** with
an orbit of participant avatars and expandable child threads. Agent-to-agent Switchboard activity
also stays visible in the workspace transcript, including both sides of a completed `agents.ask`.

## Keep a chat's workspace tabs

When you reopen a desktop chat tab, Ryu restores its open bottom and right workspace tabs, their
selected tab, and whether each dock was open. This includes project tabs such as **Terminal**,
**Files**, **Changes**, and installed workspace panels, as well as chat-run tabs such as **Sources**
and **Subagents**. Project tabs that were pinned remain shared with the other chats in that
workspace; unpinned tabs return to the chat that opened them.

## Edit and regenerate with versions

Every user message has an **edit** action, and every assistant reply a **regenerate** action, in
its hover toolbar. Editing a message or regenerating a reply forks a new version in place rather
than overwriting: a `< n / m >` pager appears on the affected turn so you can page between versions
and pick the one to keep. Unlike branching, this stays in the same conversation. The backend keeps a
lazy tree over the flat history (`POST /api/conversations/:id/messages/:mid/edit`, `/regenerate`,
`/select`); the pager and inline editor live in
`packages/blocks/src/desktop/agent-elements/user-message-editor.tsx`.

## Quote a selection to reply

Select any text in a message and a compact floating toolbar appears. **Quote** drops the selection
into the composer as a pending quote; when you send, it is prepended to your message as a leading
Markdown blockquote. Enabled plugins can add buttons to the same toolbar. The built-in Side Chats
plugin contributes **Ask in side chat** and **Explain**, each separated from the quote action by a
vertical divider. They send the highlighted text with the visible main-chat context and active
main-chat model to the no-tools side chat; the answer stays out of the main timeline.

## Message timestamps

Hover any message, user or assistant, and its send time shows in the hover toolbar beside Copy and
Branch. The time comes from Core's stored `created_at` (stamped at persist), formatted in place - no
extra round-trip.

## Rate replies with 👍 / 👎

Each assistant reply carries thumbs-up and thumbs-down buttons in its hover toolbar
(`POST /api/conversations/:id/messages/:mid/feedback`). One vote fans out to three sinks: it is
persisted on the message, it upgrades the continual-learning reward from a model guess to your human
label, and (on by default, local and private) it writes a memory fact. Vote again to clear it.

<Callout type="info">
  Voting a reply you just received works via a latest-turn fallback. Voting an older reply in a
  session you have not reloaded may need a reload first - a known v1 limitation.
</Callout>

## Session stats

The pre-installed **Session Stats** plugin places a compact readout under the latest reply. It combines
the structured usage that a provider reports with the saved transcript, so the same widgets work for
ACP agents, BYOK endpoints, Ryu providers, and local models. Providers that do not report a value
leave that widget hidden instead of displaying a fabricated zero.

The readout includes:

- **Turns** and **Steps** for the current transcript session.
- **Tokens Input**, **Tokens Output**, **Tokens Cached**, and **Tokens Total**. Input and output use
  cumulative transcript metrics when available, with the provider's context-window totals as a
  fallback; cached and total counts stay transcript-based.
- **Cache Hit Rate**, **Cache Read**, and **Cache Write**, including each cache value's share of the
  prompt context. The default is the latest turn; open the stats card to switch to cumulative
  session totals.
- **Cache Timer**, which shows a hot glyph during the active main-chain turn, then estimates the
  prompt-cache lifetime. The default is five minutes; a one-hour TTL and custom hot/countdown/cold
  glyphs are available in the card settings. The timer is best-effort because some transcripts expose
  cache activity but not the provider's expiry timestamp.
- **Input Speed**, **Output Speed**, and **Total Speed** as session averages. A rolling window from
  0 to 120 seconds can be selected; zero means the full session.
- **Context Length**, **Context Window**, **Context %**, **Context % (usable)**, and a context bar.
  The window prefers the provider's reported context window, then a model suffix such as `[1m]`,
  then a 200,000-token fallback. Set `CCSTATUSLINE_CONTEXT_SIZE_FALLBACK` to a positive integer
  when an older provider does not report its window size.
- **Compaction Counter**, with total/auto/manual/unknown/reclaimed selectors, optional trigger
  detail, reclaimed-token totals, and independent controls for each add-on.
- **Cost**, when the provider reports an amount and currency.
- **Session Usage**, **Weekly Usage**, per-model weekly windows, extra usage, and block/weekly reset
  timers when the selected subscription account exposes them. Usage can be shown as used or remaining
  percentages; session and weekly bars include an optional reset-window time cursor. Reset timers can
  show remaining time, elapsed progress, or the exact reset date/time with local/UTC timezone and
  locale controls. Sonnet, Opus, and Fable windows are omitted when the account does not report them.

The card's **Hide unavailable or empty metrics** setting keeps a provider with partial usage support
compact. Immediately after a compaction boundary, the context display uses the boundary's
`postTokens` until a later main-chain usage frame reports a fresh current value.

## Jump around with the TOC rail

A Notion-style table-of-contents rail runs down the left gutter of the message list, one marker per
user message. Hover the rail to reveal each message's text, click to scroll that turn into view; the
active turn's marker is highlighted. The same rail is available in compact chat surfaces; when the
surface is too narrow, it collapses into a compact message count. Click that count to open the full
message list in a bounded, scrollable popover and jump straight to any turn.

## Use the same chat primitives everywhere

The main desktop chat, the floating **Ask Ryu** assistant, the island mini chat, and side-chat panels
share the same transcript and composer primitives. That means tool rows—including agent-emitted JSON
UIs—use the same renderer, while `@` mention tokens and the searchable composer directory keep the
same behavior as the surface changes. Compact surfaces use tighter spacing but retain the preview rail
through its collapsed popover form.

The `/btw` side-question service intentionally remains no-tools and does not add its exchange to the
main transcript. Its presentation and follow-up composer still use the shared chat primitives, so the
surface stays familiar without changing the side-question safety boundary.

## Queue messages while a reply streams

You can keep typing and sending while a reply is still streaming: extra messages stack in a
**queue** above the composer and drain automatically, one per turn, when the run finishes
(`packages/blocks/src/desktop/agent-elements/queue/`). Each queued item has send-now and remove
actions, plus inline editing and **Send all**. A list-end icon and count identify the waiting queue
above the composer. Attachments are saved with the queued message and
shown as thumbnails, so adding or removing an attachment in the composer later does not change what
that queued turn will send. Drag the cards to reorder them, or focus a card and press **Alt + Up** or
**Alt + Down** for keyboard reordering. Choose the automatic drain order (oldest-first,
latest-first, or send-all-combined) in **Settings -> General -> Chats**. The primary composer action
becomes **Send** whenever there is text or a staged attachment, including during a reply; it shows
**Stop** only when the composer has no text or attachments and a reply is running. When the composer
has no text or attachments and is idle, it stays the icon-only **Play** control; the phone icon is an
explicit surface-level opt-in rather than the default send action.

## Follow the current turn above the composer

While an agent works, two floating status chips sit side by side above the composer: one shows the
current `TodoWrite` progress, and the other shows the files changed in the latest user turn,
including total lines added and removed. The step chip is shown as **Step 2 of 3** and opens the
agent's tracked todo list, including completed, active, and pending items; it is not a separate
plan-progress list. The files chip includes edits from the turn while it is still in progress and
opens the per-file change breakdown. The chips reset for each new user turn, so they never mix
older edits into the current run.

## Keep plans in the pinned summary

When an agent creates a plan, the pinned summary adds a **Plans** section. It accepts ACP and Pi
plan signals, including `TodoWrite`, Pi's `PlanWrite`, and the compatible `update_plan` shape.
Each completed snapshot is saved as a markdown document in the node's built-in **Artifacts**
Space, so earlier plan versions remain available instead of only the latest checklist.

Open the pinned summary, expand **Plans**, and select a plan to open its saved artifact in the
workspace artifact viewer. The row shows whether the snapshot is still being saved, was saved
successfully, or could not be persisted.

## Tune how much tool detail you see

Agent tool calls can render compactly or in full. **Settings -> Appearance -> Chat** has a
**Tool detail** knob with three presets - Compact, Minimal, and Detailed - a monotonic ramp from
grouped-and-collapsed to fully expanded (`apps/desktop/src/components/settings/AppearanceTab.tsx`).
The individual toggles it drives sit under the **Advanced settings** section for fine control.

With **Group tool uses** enabled, consecutive compact actions appear in one activity disclosure.
The row streams while tools are running, then collapses to a summary such as "Ran 4 tools"; open it
to inspect each action in chronological order. Rich results such as file diffs, expanded command
output, questions, app widgets, and failures remain standalone so their controls and detail stay
available.

Activity rows use an icon that matches the operation so a long run is easier to scan: a book for
file reads, a pencil for writes and edits, a globe for web search, a terminal for commands, and a
wrench for other tool calls. The icon is visual shorthand; the operation label remains visible for
accessibility and precision.

## The composer picker

### Prompt suggestions

When the composer is empty, a plugin or chat surface can show a ghost prompt. Press
**Tab** to accept it, or use **Arrow Down/Up** to open and move through the suggestion
list; **Enter** or a click fills the highlighted prompt. Typing hides the list. The
shared bridge lets hosts provide suggestions from a fast side agent using recent chat
and project context instead of a hardcoded list.

The **+**, `@`, and `/` entry points share one sectioned, searchable menu that opens above the
composer. After opening **+**, keep typing in the composer to filter the list; choosing a result
replaces that search text with its tag. Enabled apps and plugins appear automatically from their
installed manifests, alongside files, chats, and composer actions, without a separate registration
step.

### Pin frequent composer items

Every row in the **+** menu can be pinned, including apps, skills, plugins, and built-in actions.
Hover a row and select its pin button to move it into the **Pinned** section at the top. Pins are
stored on this device and stay available across composer surfaces; select the pin again to remove
one. Search still filters the pinned section, so clearing the search shows the complete pinned list.

The composer's agent and model picker is one grouped dropdown with a search box and three sections
(`packages/blocks/src/desktop/agent-elements/input-bar.tsx`):

In **Ryu Work**, the same dropdown is agent-only; the model selector is not shown anywhere in the
composer or nested provider/ACP picker. The selected agent remains the user's choice while model
routing stays automatic. Ryu Work's hidden permission choice is limited to the agent's own advertised
options; it never invents a bypass/full-access mode.

Ryu Work mode also removes the project-folder picker from a new-chat composer. A normal conversation can
start without a folder; a message that clearly asks Ryu to edit or run local project files opens a
contextual project chooser and resumes that message after selection. Once a chat has a project, its
Pinned summary Environment row shows that chat's project name without allowing the row to retarget it.
Ryu Work keeps the Environment section and the number of changed files visible, while hiding
insertion and deletion line-count chips.

- **Ryu Portal** - the flagship `ryu` agent, with its live model and reasoning-effort pickers when active.
- **Providers** - your configured Pi providers; an unconfigured one links straight to credential setup.
- **External Agents** - installed ACP agents, each probed lazily for its model and permission options when you drill in; agents you have not added yet show an Install button.

Connected subscription providers in the **Providers** section show the same user-configured usage
meters as subscription ACP agents. The rings or bars follow the Usage meter settings, including
remaining-versus-used mode, 5h/7d windows, and reset details; managed Ryu pool rows continue to show
their separate grant balance.

Hover a model row to open a compact insight preview. Rounded meters compare speed, cost,
intelligence, and context on a five-point scale; available rate and token details appear beneath
the meters.

## Target a turn with `@` mentions

The composer's `@` menu routes a turn before you send it:

- **`@agent`** directs the message at a specific conversation participant.
- **`@team`** fans the message out to a team's members under its coordination strategy (see [Teams](/docs/surfaces/desktop/user-guide/teams)).
- **`@workflow`** runs the message through a workflow: the text becomes the workflow's input, its nodes stream back as a live checklist, and the output is the reply. Only workflows that accept a chat input (a root `input` node) appear — see [Run a workflow from chat](/docs/core/workflows#run-a-workflow-from-chat).
- **`@app`**, **`@plugin`**, and **`@skill`** add an installed capability as a reference in the prompt.
- **App list items**, **Space pages**, and **output styles** are also available from the same `@`
  directory. App list items come from the app's existing sidebar/Library source, so the row opens
  the same destination in chat that it opens from those surfaces.
- **`@integration`** references an active connected integration, such as a Composio GitHub or Slack account. Integrations appear only when the active node has Composio access configured through BYOK or its managed subscription/proxy; unconfigured nodes show none.

Picking an agent, team, or workflow also sets the turn target from the mention itself; chats, Space
pages, output styles, app list items, spaces, skills, apps, plugins, integrations, MCP servers,
folders, and composer plugins are plain reference tokens.

## Open and preview links in messages

Links in both your messages and agent replies show a preview when you hover or focus them. Website
previews include the page title, description, and Open Graph image when the site provides them.
Clicking a website link opens it in an installed app that declares support for web links, such as
Browser; without one, Ryu uses your system browser. Preview requests block local and private network
addresses.

Agents can reference a workspace file as `@src/components/App.tsx`. For paths containing spaces,
use `@<docs/project notes.md>`. These mentions use the same complete file-type icon set as the Files
tree, preview the first few lines with a soft scroll fade, and open the file in a workspace editor
tab. Ryu only resolves files inside the conversation's active workspace folder.

## Attach a Clip as context

**Clips** are agent-native screen recordings. Record your screen (with audio) or paste a video URL,
and Ryu turns it into a frame-plus-transcript context bundle you can attach to a chat message so the
agent can watch what happened (`apps/desktop/src/components/clips/`). You can also attach the last
few minutes of ambient activity without a discrete recording. Finished clips are filed into a
default **Clips** Space.

<Callout type="warn">
  Recording sources (display and window enumeration) are cross-platform, and the full
  desktop-to-Core-to-Shadow live path is not yet fully runtime-verified. Frame extraction and local
  ingest are proven; treat live capture as early.
</Callout>

## Image generation

Image generation runs on a local engine you install from the Store. The backend is live
(stable-diffusion.cpp via `POST /api/images/generate`), and the engine ships install, start, and
stop lifecycle in the Store's **Engines → Image** group.

<Callout type="warn">
  There is no "generate an image" action in the chat composer yet. Image generation is reachable
  through its backend and the engine lifecycle, but it is not surfaced as a chat composer feature
  today (this is a known gap in `CLAUDE.md` §4). To install the image engine, see
  [Voice Engines](/docs/surfaces/desktop/engines/voice-engines) and the Store's Engines section.
</Callout>

## Viewing images

Images that arrive in chat — a picture you attached to a message, or one staged in the composer —
open in a fullscreen **lightbox** when you click the thumbnail. The viewer morphs open from the
thumbnail, supports zoom and pan, and shows the image title above a `− / percentage / +` zoom
control at the bottom. **Download** and **Close** stay in the top-right corner. It shows a gallery
when more than one image is present: arrow keys, chevron buttons, and dot navigation move between
images, and **Esc** or clicking the overlay closes it. Assistant-generated images are not clickable;
only user-attached and composer attachments open the viewer.

Attachments sent with user messages also appear under **Pinned summary → Sources → Chat
attachments**, alongside the web, connector, and local-file sources the agent used. The list keeps
the original filename and media type so the context supplied to the conversation remains visible.
Pinned-summary sections show at most five rows so the rail stays scannable. Open **Sources** or
**Subagents** from the workspace tabs for the complete live list. Subagents are named after the
concrete task they own, with active work grouped above completed work. The first four active tasks
stay visible before a **Show more** control, live rows show elapsed working time, and completed rows
show when they finished. Selecting a task opens its transcript inside the same **Subagents** tab;
use the back button to return to the roster.

The lightbox is gated by the `enableImagePreview` preference (default on). The same viewer is reused
for marketplace listing screenshot galleries. See
[Marketplace](/docs/surfaces/desktop/user-guide/marketplace).

## Audio

Audio has a working backend (the OuteTTS engine, swappable, via `POST /api/voice/speak`)
and the engine installs from the Store.

<Callout type="warn">
  There is no "play this reply" action on assistant messages in the desktop chat UI yet. Audio
  playback is wired in surfaces like the Island companion, but not on chat messages (a known gap in
  `CLAUDE.md` §4). The voice engines you can swap in are documented under
  [Voice Engines](/docs/surfaces/desktop/engines/voice-engines).
</Callout>
