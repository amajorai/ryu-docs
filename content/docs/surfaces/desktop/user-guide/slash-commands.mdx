title: "Slash Commands"
description: "Every chat slash command in Ryu - client-side, Core turn-hook, agent-advertised, and imported user commands - and which surface supports each"

Slash commands are shortcuts you type at the start of the chat composer in Desktop or in the
terminal client (`ryu-cli`). Use them to set a goal, ask a side question, check a reply, or send a
turn to a group.

There are four kinds. They differ in **where the command is handled**:

- **Client-side** - the desktop or terminal client intercepts the command and does the work itself
  (or arms a Core hook).
- **Core turn-hook** - the command is sent as a normal chat message. A plugin's turn hook in Core
  owns the behavior, so it works the same on every surface.
- **Agent-advertised** - an ACP agent publishes its own `/` commands once a session is live. These
  are per-agent and appear only in that agent's composer.
- **User commands (imported)** - commands you brought in from another agent (Codex slash commands).
  They expand into a prompt template in the composer instead of running client or Core logic.

## Client-side commands

`ryu-cli` with no subcommand (or `ryu-cli tui`) opens the terminal client. `/goal`, `/proof`, and
`/receipt` also work in both clients, but they are [Core turn-hook commands](#core-turn-hook-commands)
that the client passes through as normal messages.

| Command | What it does | Desktop composer | Terminal client |
|---|---|---|---|
| `/btw <question>` | Ask a quick side question. The answer never enters the conversation history | Yes | Yes (alias `/b`) |
| `/rewind` | Restore code, the conversation, or both to before a message | Yes | No |
| `/check` | Toggle the double-check review for the next turn | No (composer toggle) | Yes (alias `/double-check`) |
| `/model [id\|clear]` | Open the model picker, or set or clear the model for the turn | No | Yes |
| `/group [group-id\|clear]` | Route turns to an agent group, or clear the route | No | Yes (alias `/team`) |
| `/sessions` | List the run sessions for the current conversation | No | Yes (alias `/session`) |
| `/new` | Start a new chat | No | Yes (alias `/newchat`) |
| `/agent` | Open the agent picker | No | Yes |
| `/config` | Choose ACP settings | No | Yes (aliases `/acp`, `/reasoning`) |
| `/fork [message-id]` | Fork this conversation | No | Yes |
| `/resume <conversation-id>` | Resume a conversation | No | Yes |
| `/rename <title>` | Rename this conversation | No | Yes |
| `/delete [conversation-id]` | Delete a conversation | No | Yes |
| `/pin [off]`, `/unpin` | Pin or unpin this conversation | No | Yes |
| `/queue [list\|clear\|drop <id>\|up <id>\|down <id>]` | Inspect or change queued prompts | No | Yes (alias `/q`) |
| `/theme [mode\|preset]` | Choose the terminal theme | No | Yes |
| `/help [command]` | Show slash command help | No | Yes (alias `/commands`) |

<Callout type="info">
  Not every command exists on every surface. Where the Desktop column says "No", Desktop reaches
  the same action through its agent and model pickers, menus, or composer controls instead of a
  typed command.
</Callout>

`/btw` runs entirely in the client. The client calls the side-answer endpoint and shows the answer
in an overlay that never becomes a chat message. In Desktop, the command comes from the
[`side-chats`](/docs/plugins/side-chats) plugin, so it appears while that plugin is enabled. It is
not a turn hook. Sent to a channel bot as literal text, it would be the word "btw". See
[Side questions](/docs/core/side-questions).

## Core turn-hook commands

These commands are Core plugin turn hooks. They pass through as normal messages, and the hook in
Core owns the loop. Because a plugin contributes each one, the command works only while that plugin
is enabled. The same mechanism means a channel bot offers the same commands (see
[Channel commands](/docs/extend/develop/api-reference/core/chat/channel_commands)).

| Command | Plugin | What it does |
|---|---|---|
| `/goal <condition>` | [`goal`](/docs/plugins/goal) | Keep working until a judge model agrees the goal is met, re-prompting each turn instead of stopping. `/goal clear` stops the loop. The judge model is configurable. |
| `/proof` | [`proof`](/docs/plugins/proof) | Pursue a goal until an independent verifier proves it with tool-gathered evidence. This is stricter than `/goal`, which judges only the transcript. `/proof clear` stops it. The verifier model is configurable. |
| `/expand` | `auto-expand` | Expand a terse prompt into a fuller one before it reaches the agent. |
| `/plan-continue` | [`plan-continue`](/docs/plugins/plan-continue) | Continue work after a plan. |
| `/recap` | [`recap`](/docs/plugins/recap) | Summarize progress. |
| `/receipt` | [`receipts`](/docs/plugins/receipts) | Produce a receipts proof-of-work note. |
| `/advisor` | [`advisor`](/docs/plugins/advisor) | Get an advisor review of the plan. |
| `/mistakes` | [`no-more-mistakes`](/docs/plugins/no-more-mistakes) | Recheck for recurring mistakes. |
| `/security` | [`security-guidance`](/docs/plugins/security-guidance) | Run security guidance over the conversation. |
| `/security-scan`, `/security-verify`, `/security-fix`, `/security-clear` | [`security-scanner`](/docs/plugins/security-scanner) | Run a security scan, try to falsify its findings, draft a patch (never applied), or forget the scan. |
| `/polite` | [`polite-prompts`](/docs/plugins/polite-prompts) | Rewrite one message politely and send it. |
| `/auto-continue` | [`auto-continue`](/docs/plugins/auto-continue) | Arm or disarm the auto-continue loop (`/auto-continue on` \| `/auto-continue off`). |

<Callout type="info">
  `/goal` is not a Ryu built-in. The `goal` plugin contributes it, so it works only while that
  plugin is enabled. The same holds for every row above. Enable the plugin, and its command appears.
</Callout>

## Plugin and app command arguments

Plugins and Ryu Apps can register the choices that follow their command. Use `args` in the
`contributes.slash_commands` entry. Each argument is shown only after the previous one is selected,
so the menu stays focused on the next value the command needs.

```json
{
  "contributes": {
    "slash_commands": [
      {
        "command": "/deploy",
        "description": "Deploy the current project",
        "args": [
          {
            "name": "environment",
            "options": [
              { "label": "Staging", "value": "staging" },
              { "label": "Production", "value": "production" }
            ],
            "custom": { "label": "Use another environment" }
          },
          {
            "name": "region",
            "options": [
              { "label": "Singapore", "value": "sg" },
              { "label": "Virginia", "value": "us-east" }
            ]
          }
        ]
      }
    ]
  }
}
```

Type `/deploy` and choose an environment. The composer then shows the region choices. A custom
choice lets you type a value that the app did not list. The selected values are appended to the
slash command in order, so the app's existing turn hook receives `/deploy <environment> <region>`.
`parameters` is accepted as an alias for `args` in hand-authored manifests.

## Agent-advertised commands

An ACP agent can publish its own slash commands once a session is live
(`available_commands_update` over ACP). These are per-agent and known only while that agent's
session exists, so Core cannot list them ahead of time. In the desktop composer they appear in the
same `/` popover as the commands above. See
[ACP agents](/docs/start-here/architecture/acp-agents) for the session model.

## User commands (imported)

These are commands you bring in from another agent, such as a Codex slash command
(`~/.codex/prompts/<name>.md`) imported through **Import agent setup** (see
[Import from another agent](/docs/surfaces/desktop/user-guide/import-agent)). They are your own
commands, not plugin commands.

- Picking one in the composer **expands it into the input box**. Its prompt template appears as
  editable text you can change before sending. No client or Core logic runs.
- The command name is the file stem of each prompt. Your list is whatever you imported.
- They appear in the `/` popover alongside the other kinds, whichever plugins are enabled.
- Core stores them in the `user.slash-commands` preference.

## Discovery

`GET /api/channels/commands` serves the commands a channel bot publishes: commands from enabled
plugins, one command per enabled skill, and imported user commands.
`GET /api/plugins/contributions` serves plugin commands, also with imported user commands. Core
does not add `/btw` or `/goal` on its own. Each one arrives only from its plugin (`side-chats` or
`goal`) while that plugin is enabled.

See [Channel commands](/docs/extend/develop/api-reference/core/chat/channel_commands).
