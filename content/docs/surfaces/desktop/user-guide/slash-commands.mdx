---
title: "Slash command reference"
description: "Every chat slash command in Ryu: client-side commands, Core turn-hook commands, plugin-contributed commands, and imported user commands, with which surface supports each"
---

Slash commands are shortcuts you type in chat. Use them to set a goal, ask a side question, check a
reply, or send a turn to a group. Type them at the start of the composer in Desktop or a terminal.
This page lists every command and where it works.

There are four kinds, distinguished by **where the command is handled**:

- **Client-side** — the desktop or terminal client intercepts the command and does the work itself
  (or arms a Core hook).
- **Core turn-hook** — the command is sent as a normal chat message and a plugin's server-side
  turn-hook in Core owns the behavior, so it works the same on every surface.
- **Agent-advertised** — an ACP agent publishes its own `/` commands once a session is live; these
  are per-agent and appear only in that agent's composer.
- **User commands (imported)** — commands you brought in from another agent (Codex slash commands),
  which expand into a prompt template in the composer instead of running any client or Core logic.

## Client-side commands

| Command | What it does | Desktop | CLI (`ryu`) | TUI (`ryu tui`) |
|---|---|---|---|---|
| `/btw <question>` | Ask a quick side question; ephemeral, never enters the conversation history | ✅ | ✅ | ✅ (`/b`) |
| `/goal <condition>` | Set a persistent completion condition and run the judge loop | ✅ | ✅ | ✅ |
| `/goal clear` | Clear the active goal | ✅ | ✅ | ✅ |
| `/check` | Arm the per-turn double-check review for the next turn | toggle | ✅ | ✅ (`/double-check`) |
| `/model <id>` | Override the model for the turn; bare `/model` clears it | — | ✅ | ✅ |
| `/group <id>` | Route the turn to an agent group; `/group clear` resets | — | ✅ | ✅ |
| `/sessions` | Open the run history for the current conversation | — | ✅ | ✅ |
| `/new` / `/newchat` | Reset the chat (new conversation) | — | — | ✅ |
| `/agent` | Open the agent picker | — | — | ✅ |

<Callout type="info">
  Not every command exists on every surface. The desktop composes `/goal` and `/btw` natively; the
  terminal clients add `/model`, `/group`, `/sessions`, and `/new`, which the desktop reaches through
  its agent/model pickers and composer instead. `—` means the surface offers the equivalent
  interaction through its UI rather than a typed command.
</Callout>

`/team` remains accepted as a compatibility alias for `/group` in the terminal clients, but new
workflows and help text should use `/group`.

`/btw` is implemented entirely client-side: the client calls the side-answer endpoint and renders
the answer in an overlay that never becomes a chat message. That is why it is deliberately **not**
published to channel bots — sent as literal text it would just be the word "btw". See
[Side questions](/docs/core/side-questions).

## Core turn-hook commands

`/goal` and `/proof` are Core server-side plugin turn-hooks: they pass through as normal messages
and the hook in Core owns the loop, so their behavior lives in Core, not the client. Because they
are plugin-contributed, they only work while the contributing plugin is enabled — and the same
mechanism means a channel bot offers exactly the same commands (see
[Channel commands](/docs/extend/develop/api-reference/core/chat/channel_commands)).

| Command | Plugin | What it does |
|---|---|---|
| `/goal <condition>` | [`goal`](/docs/plugins/goal) | Keep working until a judge model agrees the goal is met, re-prompting itself each turn instead of stopping; `/goal clear` stops the loop. Judge model is configurable. |
| `/proof` | [`proof`](/docs/plugins/proof) | Pursue a goal until an independent verifier proves it with tool-gathered evidence — stronger than `/goal`, which only judges the transcript; `/proof clear` stops it. Verifier model is configurable. |
| `/expand` | `auto-expand` | Turn a terse prompt into a fuller one before it reaches the agent. |
| `/plan-continue` | [`plan-continue`](/docs/plugins/plan-continue) | Continue work after a plan. |
| `/recap` | [`recap`](/docs/plugins/recap) | Summarize progress. |
| `/receipt` | [`receipts`](/docs/plugins/receipts) | Produce a receipts proof-of-work note. |
| `/advisor` | [`advisor`](/docs/plugins/advisor) | Get an advisor review of the plan. |
| `/mistakes` | [`no-more-mistakes`](/docs/plugins/no-more-mistakes) | Recheck for recurring mistakes. |
| `/security` | [`security-guidance`](/docs/plugins/security-guidance) | Run security guidance over the conversation. |
| `/auto-continue` | `auto-continue` | Arm or disarm the auto-continue loop (`/auto-continue on` \| `/auto-continue off`). |

<Callout type="info">
  `/goal` is not a Ryu built-in: it is contributed by the `goal` plugin, so it arrives through the
  plugin source and is correctly gated on that plugin being enabled. Hardcoding it would publish it
  even with the plugin off. The same holds for every row above — enable the plugin, and its
  command appears.
</Callout>

## Plugin and app command arguments

Plugins and Ryu Apps can register the choices that follow their command. Use `args` in the
`contributes.slash_commands` entry. Each argument is shown only after the previous one is selected,
so the menu stays focused on the next value the command needs.

```json
{
  "contributes": {
    "slash_commands": [
      {
        "command": "/deploy",
        "description": "Deploy the current project",
        "args": [
          {
            "name": "environment",
            "options": [
              { "label": "Staging", "value": "staging" },
              { "label": "Production", "value": "production" }
            ],
            "custom": { "label": "Use another environment" }
          },
          {
            "name": "region",
            "options": [
              { "label": "Singapore", "value": "sg" },
              { "label": "Virginia", "value": "us-east" }
            ]
          }
        ]
      }
    ]
  }
}
```

Type `/deploy` and choose an environment. The composer then shows the region choices. A custom
choice lets you type a value that the app did not list. The selected values are appended to the
slash command in order, so the app's existing turn hook receives `/deploy <environment> <region>`.
`parameters` is accepted as an alias for `args` in hand-authored manifests.

## Agent-advertised commands

An ACP agent can publish its own slash commands once a session is live
(`available_commands_update` over ACP). These are per-agent and only known while that agent's
session exists, so there is nothing server-side to enumerate ahead of time. In the desktop composer
they appear in the same `/` popover as the commands above. See
[ACP agents](/docs/start-here/architecture/acp-agents) for the session model.

## User commands (imported)

Commands you bring in from another agent — a Codex slash command (`~/.codex/prompts/<name>.md`)
imported through **Import agent setup** (see
[Import from another agent](/docs/surfaces/desktop/user-guide/import-agent)). They are *your* own
commands, not plugin-contributed: picking one in the composer **expands it into the input box** —
its prompt template appears as editable text you can adjust before sending, the Cursor/Codex
convention — rather than running client or Core logic. There is no fixed list here: whatever you
imported is what you have, and the command name is the file stem of each prompt. They appear in the
`/` popover alongside the kinds above, independent of which plugins are enabled, and are stored in
the `user.slash-commands` preferences list.

## Discovery

The full union of what the composer offers is served at `GET /api/channels/commands` in the shape
channel bots publish, and plugin commands are surfaced through `GET /api/plugins/contributions`.
Imported user commands ride alongside plugin commands in the same payloads, independent of any
plugin's enabled state. Two desktop-only things are deliberately absent from the channel list:
`/btw` (client-side, would be literal text over a channel) and `/goal` (already arrives via the
`goal` plugin source). See
[Channel commands](/docs/extend/develop/api-reference/core/chat/channel_commands).
