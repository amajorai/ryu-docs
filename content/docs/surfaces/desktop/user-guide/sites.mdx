Sites is a Ryu app for creating and managing websites independently of the chat
that started them. Open **Sites** from the Apps shelf.

## Create and refine

Choose **New site**, enter a name and URL name, and select a website, help-center,
dashboard, game, or **reset-calendar** starter. New sites are private and use browser-local data.

The reset-calendar starter is a small, provider-aware runway for Codex, Claude Code, and
GitHub Copilot. It includes provider tabs, **Month** and **Agenda** views, two minimal themes,
and editable personal reset times stored in that browser. The sample windows are clearly
advisory until you replace them with your own provider-reported times.

Describe changes and choose **Generate changes** to use your configured Ryu model.
You can also edit the HTML source or import a self-contained HTML build. Build an
existing project before importing it; Sites does not execute imported package scripts.
The supported artifact is a complete HTML document with inline styles and scripts,
up to 2 MB. External dependencies and network calls are blocked by the default policy.

The preview runs in a sandbox. Use its desktop and mobile widths to review the
result. Browser storage is available on the deployed site; sandbox previews do
not have a persistent browser origin.

### Use reset safely

On a reset-calendar site, **Use reset** is disabled until the owner enables **Owner reset
checks** in **Settings**. The owner must also be signed in when using the deployed site. Ryu
then launches a bounded agent through the existing app bridge. The agent checks the connected
account's current reset window first; an upcoming automatic reset stops the flow without spending
a banked reset. If no reset is upcoming, the agent may continue only when the account reports an
unexpired reset and a real provider/reset plugin exposes an idempotent, separately authorized
action. Missing actions, stale/public forecasts, and unsupported Claude/Copilot redemption paths
are reported as blocked rather than simulated.

## Save and deploy separately

**Save version** creates an immutable build without changing the deployed version.
Open **Versions** to review a build and choose **Deploy version**. Deploying changes
which saved build is served to the selected audience. Saving another version leaves
the deployed build unchanged.

A local deployment is served by the running Sites service. A public internet URL
requires a configured public edge, DNS, and TLS. A local URL is not evidence that
managed hosting has been provisioned.

## Security checks before deployment

Open **Security** to check the latest saved version. Sites sends that exact artifact through the
Gateway secret scanner and shows its build fingerprint and check time. Deployment repeats the
check for the version being deployed. A detected secret or unavailable scanner blocks deployment.
The result does not include source snippets or the detected value.

The page also explains the enforced visitor-origin, browser-capability, data-permission and
request-size boundaries. A passed secret check is not a complete code audit or certification.

## Data and knowledge

The starters use the shared browser data primitives. The help center imports text
and Markdown articles and searches their contents locally. Its default results are source
excerpts. Connected sites can optionally enable AI answers grounded in approved
Space passages, with a daily request limit. Model access remains governed by Ryu. The dashboard saves its request list in the
current browser. Browser data is scoped by origin and is not a server backup;
clearing browser storage removes it.

A connected site can use per-visitor durable records and file uploads. These
operations require verified visitor identity and remain scoped to that visitor
and site. Changing from browser-local to connected mode never uploads local data.

An operator can bind approved Spaces through Ryu's existing retrieval capability.
A site can search only its approved binding; visitors cannot select another Space
or supply a node address. The help-center starter uses connected retrieval when
that binding is available. Unavailable services return an error instead of silently
substituting demo data.

## Access and sign-in

Keep a site private while reviewing it. Public publishing must be enabled by the
operator. Platform identity must be connected before using invited viewers,
workspace access, editors, or visitor sign-in.

Viewer access and editor access are separate. Editors must belong to the site's
workspace. They can save versions and deploy updates after the owner's first
deployment. Only the owner manages sharing, domains, URL names, analytics and deletion.
Removing a viewer does not override access they still have through public or workspace
sharing.

The identity connection uses the platform's OpenID Connect provider. Sites validates
the issuer, audience, nonce and verified email, and keeps visitor sessions in
HTTP-only, origin-scoped cookies. Operator credentials are never sent to generated pages.
Sessions expire and are cleared when the Sites service restarts.

## URL names and custom domains

URL names start with a lowercase letter, contain at least five characters, and use
lowercase letters, digits and single hyphens. Changing a name keeps saved versions
and redirects the previous name, including its path and query. Browser storage is
origin-scoped, so a new hostname has separate local data.

In **Settings**, add a custom domain you own and copy the ownership TXT record to
your DNS provider. **Check DNS and TLS** refreshes its state. Successful ownership
verification moves it to pending TLS; it becomes active only when an edge provider
confirms a working TLS binding. Sites does not register domains or automatically
provision certificates in the local runtime.

## Analytics and limits

**Analytics** shows daily page requests and estimated unique visitors over 7, 30,
or 90 days. Visitors are estimated with a daily keyed digest; no tracking cookie
or analytics SDK is required. Counts are approximate, include page requests such
as bots, and are retained for 90 days. Restarting the service rotates the digest key.

| Resource | Local runtime limit |
| --- | --- |
| Projects | 30 per service |
| Saved versions | 100 per site |
| Saved build storage | 50 MB per site |
| Durable records | 1,000 per site; 64 KB per record |
| Uploaded files | 100 per site; 5 MB per file |
| Custom domains | 5 per site |

A limit does not prevent reviewing existing saved versions or taking a site offline.

## Take down or delete

**Take site offline** removes the deployed build from visitor access while keeping
saved versions and data. To delete a site permanently, enter its URL name in the
confirmation dialog. Deletion removes its versions, records, uploads and analytics.
