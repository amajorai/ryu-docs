An agent is a saved assistant. It has its own instructions, model, tools, memory, and voice. You
can change these parts without creating a new agent.

## Browse agents

Open **Agents** from the sidebar to see every agent you have. Pi is always present as the
local, no-setup default. Selecting an agent in chat routes your messages through that card's
configuration.

## Create a new agent

1. On the Agents page, click **+** to create a new agent.
2. Give it a **name**.
3. Write its instructions in the setup composer. It accepts Markdown, and the expand button
   opens the full Plate editor with formatting, blocks, links, and other writing controls.
4. Use the agent and provider/model picker at the bottom of that composer to choose the model and
   provider that run it.
   The same setup composer is used for both a new agent and an existing agent, and the choice is
   saved with that agent.

After you create the agent, Ryu opens a new chat with it. The agent introduces itself and asks what
you want to do first. You can keep the full editor open in another tab when you use **Advanced
setup**.

Before creating it, choose the channel setup toggles for **Telegram**, **Discord**, and **WhatsApp**.
The first selected setup opens automatically with the new agent already selected. Telegram can use
Ryu's managed bot flow; Discord and WhatsApp still ask for the credentials required by their
platforms. If you select more than one, finish the first setup and add the remaining selected
channels from **Channels**.

The built-in **Ryu** assistant is the main front door for this setup. On first onboarding it sends
its welcome as an assistant message, without creating a hidden user message to prompt itself. If a
local model is still downloading or starting, the chat waits and resumes the welcome when the model
is ready; a ready paid model can answer immediately.

## Get agent suggestions from your work

On an eligible first-run setup, Ryu can use the read-only connections and imported agent sessions
you approved to spot repeated workflows. For example, repeated release checks can become a draft
release helper. Each suggestion keeps the card simple: a generated avatar, its name, what it does,
and the connected apps it can use.

Select the drafts you want and click **Add** once. Each card uses the original Ryu SiriOrb fill
clipped inside an animated expressive ghost and shows connected-app logos, so you can recognize the
helper at a glance. Ryu creates the
selected agents together in **Trial** mode with a read-only safety profile, so you can test and
review them before promoting them. Nothing is created if you skip the step, and connected accounts
or external content are never changed automatically. The profile build and these suggestions remain
subject to the same organization-owner/admin and managed-inference eligibility checks as the initial
profile.

## Choose an agent avatar

In the agent editor, choose **Upload**, **Icon**, **Emoji**, **DiceBear**, **Dither**, or
**Expressive** for the agent's avatar. Expressive keeps Ryu's ghost body and gives its eyes named
moods such as **Happy**, **Laughing**, **Curious**, and **Sleepy**. Choose **Random** to let the
avatar cycle through moods while blinking and following the pointer, or choose a named expression
to keep one mood selected. Choose a separate animation from **Idle**, **Thinking**, **Wink**,
**Wide eyes**, **Alert**, **Notification**, **Exclamation**, **Sleep**, **Egg**, **Hexagon**,
**Play**, **Orbit**, **Burst**, or **Comet**. **Random** runs the full sequence with the same
smooth cross-fade between states; a named animation stays deterministic for the saved avatar.
Ryu automatically uses **Orbit** for an expressive avatar in the live thinking/working status row.
The existing eyes-only logo remains a separate compact logo variant.

## Give each agent a personality profile

The **Personality & tone** section belongs to the agent card. Choose **Agent's own voice**
to use its saved instructions and tone, or assign a reusable profile such as **ELI5**,
**Plain Technical**, or **No AI slop**. Profiles come from the enabled Output Styles plugin
and user/project Markdown style files, so each agent can have a different voice on the same
node. The Store's **Personality Profiles** tab is a browse-only catalog; assignment happens
in the agent editor.

## Start with Ryu in ordinary language

You do not need to know how assistants are built. Tell Ryu what you want, such as “keep track of
new customer enquiries and remind me every Friday.” Ryu checks what is already available, then
turns the request into a short checklist:

1. what is already available;
2. what app or service is missing;
3. what needs your approval or sign-in;
4. a small test that proves the setup works; and
5. an optional schedule or reusable instruction to save afterward.

Ryu can search the app directory and Ryu Marketplace for an app, workflow, reusable instruction, or
local helper. It explains what each addition can see, whether it uses a cloud service or your device,
and whether it may cost money. Ryu asks before it adds something, changes access, sends a message,
or saves a schedule. You do not need to learn internal names such as **MCP**, **Skill**, or **CLI**
to get started.

## Choose when the agent can run

Every new or imported agent starts in **Trial** with **Read-only** access. This gives you a safe
place to test it before schedules or other agents can use it.

- **Draft** is for editing. You cannot use it in chat, schedules, workflows, or channels.
- **Trial** is for testing. It can read and preview, but it cannot change data, send messages, or
  run in the background.
- **Active** lets the agent run in chat, schedules, workflows, channels, and delegated work.

The safety profile controls Active agents:

- **Read-only** blocks tools that change data.
- **Approval required** sends risky tools to the approval inbox.
- **Verified plans only** accepts only typed plans checked by a Safe Actions policy.
- **Autonomous** allows the configured capabilities.

Verified plans replace raw tool access with `plans.submit`, `plans.status`, and `plans.catalog`.
Core blocks direct tool calls and programmatic JavaScript for this profile. Tools without a trusted
effect contract stay blocked. Trial stays read-only, even if you save another profile for later.
Moving an agent back to Draft or Trial pauses its schedules without deleting them.

Use the **Safe Actions** app to attest live catalog tools, create a default-deny policy, bind it to a
Verified plans only agent, inspect plans that need review, and audit execution receipts. See
[Safe Actions](/docs/security/safe-actions) for the plan language, certificate bindings, and failure
behavior.

To promote an agent, save it as Trial first, test it in a normal chat, then choose Active. Ryu
does not allow Draft → Active as a shortcut.

You can also bring agents in from another coding agent: Codex subagents are
imported through **Import agent setup** and appear here like any agent you
created (see [Import from another agent](/docs/surfaces/desktop/user-guide/import-agent)).

## Set up agent routines

Open an existing agent's **Triggers → Routines** view to manage its background work. A routine
contains a cron expression or interval, custom instructions, an optional model pin, and an
approval choice. The view also shows a compact 24-hour status strip and each routine's recent
outcomes, so a schedule is an operational surface rather than a hidden toggle.

Choose **New chat each run** when every firing should have its own durable transcript. Choose
**Keep one persistent chat** to append every firing to an existing chat; this is also what happens
when an agent creates a routine from inside a chat and omits a destination. From a chat's action
menu, **Add scheduled task** opens with that chat selected and lets you switch to another chat for
the same agent before saving. You can edit, pause,
run now, or delete routines from the same view. Deleting a routine does not delete the chat
transcripts it already produced.

The **Run history** view combines interactive chats with automated runs. Open an automated entry to
inspect its transcript; the status overview and **Calendar → Agenda** use the same green-success,
red-failure, and amber-scheduled timeline vocabulary.

## Configure tools

Each agent can be granted a set of **tools** from MCP (Model Context Protocol) servers. An MCP
server provides tools that an agent can use, such as browsing the web, reading files, or calling a
service. New, imported, published, and auto-installed agents start with all currently
enabled MCP tools, including tools contributed by enabled plugins and apps. An empty skills
selection likewise means all enabled skills. Use the access controls to choose a custom subset,
or turn the capability off explicitly when you want a narrower agent; disabled plugins and
skills remain unavailable regardless of an agent's broad default.

The pre-installed **Goal** plugin contributes `goal.set`. Grant it to an agent when you want that
agent to set or replace a durable goal for the conversation it is currently working in. The tool
derives the conversation scope from Core's caller context, so an agent cannot target another chat.

Agents can also use the always-on `workspace` tools. `workspace.open_tab` opens a safe first-party
Ryu page in a normal workspace tab, `workspace.open_panel` keeps the current chat visible beside
that page, and `workspace.open_browser` opens an HTTP(S) URL in the embedded Browser panel. The
browser capability tools (`browser.tabs`, `browser.navigate`, `browser.snapshot`, `browser.click`,
`browser.type`, `browser.scroll`, and `browser.screenshot`) then inspect or control the browser
when its provider is enabled. Page keys and browser URLs are validated by Core and the Desktop
shell; an agent cannot supply an arbitrary shell route or broadcast a shared-node navigation to
another user.

<Callout type="info">
  Tool calls made through Ryu Core are governed by the Gateway. Built-in tool servers such as
  Ghost (desktop automation) and Shadow (screen and audio capture) are available through the
  MCP registry.

  Trial guarantees apply to tool and background paths routed through Ryu Core. A native ACP
  client may expose tools outside that bridge; treat those tools as untrusted until the client
  routes them through Ryu Core.
</Callout>

## Configure memory

Attach a **Space** to an agent so it can ground its answers in your documents (see
[Spaces and Memory](/docs/surfaces/desktop/user-guide/spaces-memory)). Separately, each agent keeps its own
encrypted long-term memory automatically.

## Agent builder studio

The agent edit page is a two-pane **studio**. The left pane is a builder chat that edits *this*
agent's configuration, and the right pane is the organized config panel (model, tools, skills,
identities, rules, instructions) that updates live as you make changes.

Tell the builder what you want in plain language, for example "make it formal" or "add the web
search tool", and it applies the change for you. Under the hood the builder chat is offered Core's
built-in `agent_builder` tools (`get_agent`, `configure_agent`, `create_agent`), wired into the
MCP registry in `apps/core/src/sidecar/mcp/mod.rs` and dispatched from
`apps/core/src/runnable/agent_builder.rs`. When you ask for a change, the model calls
`configure_agent` to patch the persisted agent record, and the right-hand panel re-hydrates once the
turn settles (`apps/desktop/src/components/agents/AgentBuilderChat.tsx`).

The editor keeps the setup decision in one familiar place: instructions in the composer, with the
agent and provider/model picker in its footer. Expand the composer when you need the full Markdown
toolbar. The remaining tabs are for advanced behavior, tools, connections, triggers, and testing;
they do not split the basic “what should it do?” and “what should run it?” choices apart.

A few details worth knowing:

- The builder conversation runs as the flagship **Ryu** agent runtime (its tool loop is what
  applies the edits) with `persist: false`, so these builder turns never enter your chat history.
- For a brand-new agent, a **draft record** is created on your first builder message so the chat has
  something real to edit (`apps/desktop/src/pages/AgentEditPage.tsx`).
- `configure_agent` refuses to edit a `built_in` or `locked` record, so the flagship `ryu` agent and
  the builder meta-agent itself cannot be rewritten through the builder chat
  (`apps/core/src/runnable/agent_builder.rs`).

<Callout type="warn">
  The builder chat is a tool-loop round-trip, so it needs a running Core and a model that can drive
  tool calls.
</Callout>

## Per-agent evals

The edit page has an **Evals** view scoped to the agent you are editing
(`apps/desktop/src/components/agents/AgentEvalsView.tsx`). Running an eval scores cases on latency,
token efficiency, policy pass, and an optional substring match. With no custom dataset, the gateway
falls back to its built-in case set, so the panel is useful immediately.

Evals are a measurement concern, so they reuse the Gateway's eval and audit API rather than
re-implementing policy: the run posts to `POST /api/gateway/evals/run` via `runGatewayEvals`, and the
run history reuses `fetchGatewayAudit`. A **Prompt Studio** view on the same page lets you edit the
agent's system prompt, fill `{{variables}}`, preview a rendered prompt, author test cases, run an
LLM judge, compare prompt variants and models, and inspect per-case assertion results. The suite
editor accepts Promptfoo YAML/JSON/JSONL/CSV plus text, Markdown, and Jinja-style prompt files;
exports the same dataset formats; preserves typed variables, metadata, providers, chat messages,
default tests, assertion thresholds/weights/transforms, and model-graded rubrics. Its evaluator
catalog includes the common deterministic, structured-output, moderation, refusal, model-graded,
and code/webhook assertion shapes, with unsupported runtime adapters reported as explicit failures
rather than silently passing.

Suites are Core-owned resources scoped to the agent. Saving creates immutable suite versions;
restoring a version is undoable and ACL-checked. Completed runs are durable, can be reopened from
run history, and expose per-result human pass/fail review, score, comment, and highlight state.
Prompt snapshots use the same Core-owned server history, with diff and undoable restore, rather
than browser-only storage. The source history is backed by immutable local Git commits under
`~/.ryu/source-history/agents/`; the older SQLite prompt snapshot table remains a migration fallback.
Agent configuration saves are checkpointed as JSON alongside the Markdown prompt snapshots, while
credentials, run state, and provider data are never committed.

<Callout type="info">
  Prompt Studio targets Promptfoo's local authoring and evaluation contract. Provider calls still
  flow through Ryu Gateway, Core owns persistence and ACLs, and executable JavaScript/Python/Ruby
  or webhook assertions remain sandbox/runtime adapters; imported config is retained and the UI
  reports when an adapter is unavailable. Promptfoo-hosted sharing, cloud red-team campaigns, and
  hosted account billing are outside a local-first Ryu node.
</Callout>

## Council chat

Council chat lets several agents share one conversation. **@mention** an agent by name to
direct a turn to it, and bring multiple agents into the same thread to compare answers or have
them build on each other. It is the multi-agent counterpart to a normal one-on-one chat.
