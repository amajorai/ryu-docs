An agent is a saved assistant. It has its own instructions, model, tools, memory, and voice. You
can change these parts without creating a new agent.

## Browse agents

Open **Agents** from the sidebar to see every agent you have. The **Ryu** agent is always present
and cannot be removed. Selecting an agent in chat routes your messages through that agent's
configuration.

The model picker keeps an agent's advertised models available when it reports an invalid current
model, so you can choose a valid model from the list. Your saved model choice takes priority.

During first-run onboarding, you can rename the default Ryu agent and choose its avatar before
adding optional agents. The avatar carries through the remaining onboarding pages. Gemma 4 remains
the starting local model in the later local-default step. The agent keeps its stable `ryu` id when
renamed.

On first onboarding, the Ryu agent sends its welcome as an assistant message. If a local model is
still downloading or starting, the chat waits and shows the welcome when the model is ready.

In the agent grid, each card's footer shows the agent runtime's version when Ryu can read it. When a
newer version is published for a runtime Ryu manages, the footer shows **Update available** and an
**Update** button. The update runs on the node and can take up to a minute. An agent CLI installed by its
own vendor installer shows where to update it instead.

## Jay Jr., the founder bot

Ryu also adds **Jay Jr.** next to the Ryu agent. Jay Jr. is an AI twin of Jay (Jia Wei Ng), the
founder of Ryu. Ask it about Jay, his projects and writing, or why Ryu exists. It runs on the same
engine as the Ryu agent and follows that agent's model routing: its model calls go through your
Gateway unless the Ryu agent is set to your own provider key. Through the Gateway, its spend and
budgets are Jay Jr.'s own, not the Ryu agent's.

Jay Jr. answers from a Space named **Jay Jr. · jiaweing.com**. The Space holds a snapshot of Jay's
personal website that ships inside Ryu: his profile, about page, projects, books, and an index of his
blog posts with short excerpts. Ryu adds the Space once and indexes it with your embedding model. It
does not download anything from the website to build it. Jay Jr. can search that Space and open a
web page, such as a full blog post you ask about. It has no other tools. Although it runs on the Ryu
agent's engine, it cannot run commands or read and write files on your computer.

The Space is yours. On a node that belongs to an organization, Ryu shares the Space with that
organization, so Jay Jr. can use it in every member's chats. If nobody is signed in when Ryu starts on
such a node, Ryu adds the Space the next time it starts with someone signed in. You can add notes to
the Space, detach it from Jay Jr. in the agent's access settings, or delete it. Ryu does not add a
deleted Space back.

Jay Jr. is an AI, and it does not speak for Jay or A Major. Its instructions tell it to say so when
asked, to say when it doesn't know something, and not to make promises or commitments for Jay or A
Major. You can edit those instructions like any agent's, so they only hold while you keep them. A
personality profile that replaces an agent's instructions replaces these too. Unlike the Ryu agent,
you can remove Jay Jr. from the agents catalog and add it back later.

## Get agent suggestions from your work

On an eligible first-run setup, Ryu can use the read-only connections and imported agent sessions
you approved to spot repeated workflows. For example, repeated release checks can become a draft
release helper. Each suggestion shows its name, what it does, why it appeared, the connected apps,
the tools it would use, and its complete generated prompt.

Each suggestion also shows its **Identity**, which starts as **Acts as you**. Select **Change** to
pick **Acts as you**, **Its own identity**, or **Both** on the same cards as the new-agent dialog;
account access starts with no limit within that choice, and you can narrow it later in the agent's
editor. Before adding a suggestion set to **Its own identity** or **Both**, Ryu runs the same
launch check as the new-agent dialog. If the agent couldn't start that way, it isn't added and the
step shows why, so you can change its identity or skip it.

Review every selected draft and check **I reviewed this draft's prompt and tools** before clicking
**Add**. Each suggestion shows an animated ghost avatar and the logos of its connected apps. Ryu
creates the selected agents together in **Trial** mode with a read-only safety profile, so you can test and
review them before promoting them. Nothing is created if you skip the step, and connected accounts
or external content are never changed automatically. The profile build and these suggestions remain
subject to the same organization-owner/admin and managed-inference eligibility checks as the initial
profile.

## Give each agent a personality profile

The **Personality & tone** section belongs to the agent's configuration. Choose **Agent's own voice**
to use its saved instructions and tone, or assign a reusable profile such as **ELI5**,
**Plain Technical**, or **No AI slop**. Profiles come from the enabled Output Styles plugin
and user/project Markdown style files, so each agent can have a different voice on the same
node. The Store's **Personality Profiles** tab is a browse-only catalog; assignment happens
in the agent editor.

With **Agent's own voice**, the agent's instructions go with every message it answers, including
delegated, scheduled, and channel turns. A profile either keeps those instructions and adds its
style after them, or replaces them, depending on how the profile is written.

## Start with Ryu in ordinary language

You do not need to know how assistants are built. Tell Ryu what you want, such as "keep track of
new customer enquiries and remind me every Friday". Ryu checks what is already available, then
turns the request into a short checklist:

1. what is already available;
2. what app or service is missing;
3. what needs your approval or sign-in;
4. a small test that proves the setup works; and
5. an optional schedule or reusable instruction to save afterward.

Ryu can search the app directory and Ryu Marketplace for an app, workflow, reusable instruction, or
local helper. It explains what each addition can see, whether it uses a cloud service or your device,
and whether it may cost money. Ryu asks before it adds something, changes access, sends a message,
or saves a schedule. You do not need to learn internal names such as **MCP**, **Skill**, or **CLI**
to get started.

## Patrol watches your setup

**Patrol** is a built-in bot that comes installed next to Ryu. It works like the Doctor tools, but it
keeps running on a schedule:

- **Every hour**, it runs the Gateway, Core, and app and plugin doctors. It also checks the audit
  log, the activity feed, and pending approvals for anything new since its last run.
- **Every day at 08:45 UTC**, it writes a report on the last 24 hours. The report also covers
  support access, safe mode, backups, and pending updates.

Patrol only messages you when a problem is new or worse, when a problem is fixed, or when a fix
fails. If Patrol cannot run a check, it lists that check as not checked rather than passed. You can
also ask it questions in chat, such as "what went wrong in the last 24 hours?"

Patrol runs on Ryu's own engine, under its own name, so its usage and budget are tracked separately
from Ryu's. Patrol's **Lifecycle & safety** setting decides what it may fix:

- **Approval required** (the default): Patrol proposes each fix in the approval inbox and explains
  how to undo it.
- **Read-only**: Patrol only reports findings and recommended fixes.
- **Autonomous**: Patrol may apply high-confidence fixes itself. Tell it "set my fix mode to auto-fix
  high confidence" in chat to turn this on. It applies only fixes that the Doctor marks safe, that
  restore a protection, and that can be undone. It previews each fix first and checks the result
  afterward. It still proposes every other fix.

In every mode, Patrol never turns off or weakens protections, deletes data, or touches credentials.
Its two schedules appear under **Routines**, where you can edit or delete them. Deleted schedules
stay deleted after a restart. If you remove Patrol from the agents catalog, its schedules pause. If
you add Patrol back, the schedules resume, and Patrol restores the defaults if you had deleted them.

## Choose when the agent can run

Every new or imported agent starts in **Trial** with **Read-only** access. This gives you a safe
place to test it before schedules or other agents can use it.

- **Draft** is for editing. You cannot use it in chat, schedules, workflows, or channels.
- **Trial** is for testing. It can read and preview, but it cannot change data, send messages, or
  run in the background.
- **Active** lets the agent run in chat, schedules, workflows, channels, and delegated work.

The safety profile controls Active agents:

- **Read-only** blocks tools that change data.
- **Approval required** sends risky tools to the approval inbox.
- **Verified plans only** accepts only typed plans checked by a Safe Actions policy.
- **Autonomous** allows the configured capabilities.

Verified plans replace raw tool access with `plans.submit`, `plans.status`, and `plans.catalog`.
Core blocks direct tool calls and programmatic JavaScript for this profile. Tools without a trusted
effect contract stay blocked. Trial stays read-only, even if you save another profile for later.
Moving an agent back to Draft or Trial pauses its schedules without deleting them.

Lifecycle and safety changes take effect after the connected node accepts them. If a change is
refused, the editor keeps the saved setting so you can try again. Switching connections leaves
other nodes usable while a change is pending. Returning to the same node waits for that change
and reads its saved policy before enabling another change. If that read fails, use **Retry**;
policy controls stay unavailable until the saved setting can be read. Retrying that read keeps
your other unsaved edits in the editor.

Use the **Safe Actions** app to attest live catalog tools, create a default-deny policy, bind it to a
Verified plans only agent, inspect plans that need review, and audit execution receipts. See
[Safe Actions](/docs/security/safe-actions) for the plan language, certificate bindings, and failure
behavior.

To promote an agent, save it as Trial first, test it in a normal chat, then choose Active. Ryu
does not allow Draft to Active as a shortcut.

You can also bring agents in from another coding agent: Codex subagents are
imported through **Import agent setup** and appear here like any agent you
created (see [Import from another agent](/docs/surfaces/desktop/user-guide/import-agent)).

## Set up agent routines

Open an existing agent's **Triggers → Routines** view to manage its background work. A routine
contains a cron expression or interval, custom instructions, an optional model pin, and an
approval choice. The view also shows a 24-hour status strip and each routine's recent outcomes.

Choose **New chat each run** when every firing should have its own durable transcript. Choose
**Keep one persistent chat** to append every firing to an existing chat; this is also what happens
when an agent creates a routine from inside a chat and omits a destination. From a chat's action
menu, **Add scheduled task** opens with that chat selected and lets you switch to another chat for
the same agent before saving. When you open the routine form directly, choose a chat from the
required picker before saving a persistent-chat routine. You can edit, pause, run now, or delete
routines from the same view. Deleting a routine does not delete the chat
transcripts it already produced.

The **Run history** view combines interactive chats with automated runs. Open an automated entry to
inspect its transcript; the status overview and **Calendar → Agenda** use the same green-success,
red-failure, and amber-scheduled timeline vocabulary.

### Browse the saved-agent calendar

Open **Calendar** on a saved agent to see that agent's scheduled work from the selected node.
Switch between **Month**, **Week**, **Day**, and **Agenda**, use the previous/next controls to change
the visible period, or choose **Today** to return to the current date. Select a day or scheduled
entry to inspect its details; closing the day panel returns to the same calendar period.

**New automation** starts with the saved agent selected and refreshes the calendar after saving.
If an initial read or refresh fails, **Try again** reloads the data. Refresh keeps the existing
calendar visible while the replacement data is loading. This agent calendar is separate from
the Calendar app's broader calendar surface.

## Configure tools

Each agent can be granted a set of **tools** from MCP (Model Context Protocol) servers. An MCP
server provides tools that an agent can use, such as browsing the web, reading files, or calling a
service. New, imported, published, and auto-installed agents start with no MCP tools. Use the
access controls to grant a custom subset, or explicitly choose **All tools** when that is what you
intend. An empty skills selection still means all enabled skills; disabled plugins and skills remain
unavailable regardless of an agent's tool grants.

The pre-installed **Goal** plugin contributes `goal.set`. Grant it to an agent when you want that
agent to set or replace a durable goal for the conversation it is currently working in. The tool
derives the conversation scope from Core's caller context, so an agent cannot target another chat.

Agents can also use the always-on `workspace` tools. `workspace.open_tab` opens a safe first-party
Ryu page in a normal workspace tab, `workspace.open_panel` keeps the current chat visible beside
that page, and `workspace.open_browser` opens an HTTP(S) URL in the embedded Browser panel. The
browser capability tools (`browser.tabs`, `browser.navigate`, `browser.snapshot`, `browser.click`,
`browser.type`, `browser.scroll`, and `browser.screenshot`) then inspect or control the browser
when its provider is enabled. Page keys and browser URLs are validated by Core and the Desktop
shell; an agent cannot supply an arbitrary shell route or broadcast a shared-node navigation to
another user.

<Callout type="info">
  Tool calls made through Ryu Core are governed by the Gateway. Built-in tool servers such as
  Ghost (desktop automation) and Shadow (screen and audio capture) are available through the
  MCP registry.

  Trial guarantees apply to tool and background paths routed through Ryu Core. A native ACP
  client may expose tools outside that bridge; treat those tools as untrusted until the client
  routes them through Ryu Core.
</Callout>

## Per-agent evals

The Activity area's agent-scoped traces, Quality tests, Prompt Studio suites, and version history are covered in [Agent observability and evals](/docs/surfaces/desktop/user-guide/agent-observability-and-evals).

Evals, the security sweep, and online scoring target the agent's own model when it names one, and
otherwise the node's default model: the model set under **Gateway → Default agent & model**, or the
local chat model the node serves when no default is set. When no model can be resolved, the Run
action stays disabled and the panel says so, rather than falling back to a hosted provider. The
Evals view and the Gateway's **Run evals** panel still accept any model id you type.

The Activity area also has an **Optimizations** view. Once the agent has 10 sessions, **Run
analysis** replays a sample of its recent requests on cheaper models, judges each answer against
the reply the agent really gave, and flags allowed tools it never calls. Each suggestion shows the
measured quality and cost for every model tried. **Apply** updates the agent (you can restore the
previous settings from **Versions**), and **Dismiss** leaves it unchanged. See
[agent optimizer](/docs/core/agent-optimizer) for the rules it uses.

## Council chat

Council chat lets several agents share one conversation. **@mention** an agent by name to
direct a turn to it, and bring multiple agents into the same thread to compare answers or have
them build on each other.
