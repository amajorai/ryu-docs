The Store is how you extend Ryu without leaving the app: browse and install **apps**, **models**,
**skills**, **MCP servers**, and **plugins**, then watch every download in one place. All the catalog logic
lives in Ryu Core, so the desktop is a thin browser over it.

<TryInRyu page="store" />

This page covers free browse and install. To **buy, sell, or manage licenses** for paid items, see
[Marketplace](/docs/surfaces/desktop/user-guide/marketplace). For the full depth on browsing and running
models, see [Models](/docs/surfaces/desktop/models).

## Apps vs plugins

The quick way to choose is:

- **Apps** are complete experiences you use inside Ryu, like Tests or Learning. They answer: “What do
  you want to use Ryu for?”
- **Plugins** add capabilities to Ryu, such as tools, skills, agents, and workflows. They answer: “What
  do you want Ryu to do?”

In short, apps help you use Ryu for a job; plugins help Ryu do more.

## For you

The Store can show a **For you** section that combines relevant apps, plugins, skills, MCP servers,
agents, and models. Recommendations are generated by the default cloud agent from bounded preference
signals such as installed capabilities, enabled plugins, connection categories, and memory categories.
Raw memories, connection domains, and connection credentials are never returned to the Store UI or
recommendation cache.

The section is enabled by default and refreshes weekly. Use the refresh action to generate a new set
immediately, or choose a daily, weekly, or monthly cadence. The hide icon at the right of the section
heading stops fetching and generating recommendations for your account; re-enable it from Marketplace
preferences. A Gateway administrator can disable recommendation generation for the whole Gateway,
which overrides individual preferences.

## One Marketplace surface on web and desktop

The web Marketplace at `/marketplace` and the desktop Store use one shared built-in section contract:
**Home**, **Integrations**, **Apps**, **Plugins**, **Models**, **Skills**, **MCP**, **Agents**,
**Engines**, **Workflow Templates**, **Themes**, **Marketplaces**, **Browse**, **Connections**, **My licenses**, and
**Sell**, in that order. They use the same Marketplace shell, search bar, section strip, Home shelf
order, shared catalog-card primitives, headings, loading/empty states, and six-card teaser limit. The
host adapter supplies the catalog data and the action that makes sense there; native install, account,
and preview behavior can therefore remain platform-specific without creating a second Marketplace
shell.

Home has one optional **For you** block followed by the shared **Popular models**, **Featured skills**,
**MCP servers**, **Agents**, **Apps**, and **Plugins** shelves. The old admin-curated **Featured** rail
is not a second Home shelf. Empty shelves keep their heading and empty/loading state, so an unavailable
feed cannot make the web and desktop Home pages take different shapes. The Browse tab uses one shared
category order:
Apps, Skills, Plugins, MCP, Models, Agents, Stack Templates, Workflows, Themes, Spaces, Profiles, Output
Styles, and Bundles. On the web, that category row is the only in-page navigation while Browse is open;
the broader Marketplace section strip is hidden there so the same destinations are not presented twice.
Other sections keep the shared section strip for switching between Marketplace surfaces.

On the web, opening a published Marketplace listing updates the URL to its canonical
`/marketplace/<kind>/<id>` page. In a mobile viewport, that navigation is intercepted into a
full-page preview dialog so it keeps the browser URL and back-button behavior while using the whole
screen. Refreshing, sharing, or opening the URL directly renders the same canonical page without the
dialog. Pressing **Esc**, using the close control, or navigating back closes the intercepted preview.

## Library and section counts

The desktop **Library** brings the collections behind the sidebar into one tabbed surface, including
Chats, Agents, Channels, Teams, Projects, Skills, MCP, Tools, Engines, and the other built-in
sections. App-registered sidebar sections are added automatically through the same contribution, so
an app does not need a second Library-specific registration. Store and Library tabs show an
authoritative total as a muted number after the tab label; a paginated response is never mistaken
for a total, and searching a collection does not change its tab count.

## How the catalog works

Every catalog kind routes through one `CatalogSource` seam (`apps/core/src/catalog_source/`).
`CatalogKind` is one of `model`, `skill`, `mcp`, `plugin`, `knowledge`, or `agent`, and each kind has a per-kind registry
of built-in plus user-added sources with a persisted active selector:

| Kind | Built-in sources |
|---|---|
| `model` | Hugging Face, ModelScope, model-index / custom URL |
| `skill` | Federated skills.sh, vendor/community GitHub taps, browse.sh, ClawHub, LobeHub, Ryu Marketplace, and custom Claude `marketplace.json` sources |
| `mcp` | official MCP registry, Smithery, Ryu-hosted |
| `plugin` | Ryu-hosted marketplace |
| `knowledge` | Ryu-hosted knowledge catalogs |
| `agent` | Ryu-hosted agent catalogs |

Sources return **descriptors only**; Core keeps the privileged install step. List and switch the
active source per kind through `GET /api/catalog/sources?kind=<kind>` and
`POST /api/catalog/sources/select` (custom sources persist to `~/.ryu/catalog-sources.json`, the
active selection to the prefs KV `catalog.active_source.{kind}`).

Catalog cards use a few shared signals across the desktop and web surfaces. When a source provides
download totals, the install action shows the compact count (for example, `12.4k`) until you hover
or focus it, then changes to **Add**. For GitHub-backed listings, the total counts downloadable
release assets while excluding signatures, checksums, and metadata files. You can also like apps,
plugins, skills, MCP servers, agents, engines, workflows, and themes from their catalog cards.
Packages that have not been explicitly promoted to stable carry an **Experimental** badge, so check
their permissions and documentation before enabling them in important workflows.

<Callout type="info">
  Every untrusted catalog fetch goes through the SSRF-guarded `guarded_get` / `guarded_get_bytes`
  (https-only, IP-pinned, redirects off, 32 MB cap). The Ryu-hosted marketplace is trusted
  first-party, so it is not SSRF-guarded.
</Callout>

## Compare integrations across providers

The **Integrations** tab is one brand-level directory rather than three separate provider lists.
It merges records from [integrations.sh](https://integrations.sh), Composio toolkits, and the public
[Treg catalog](https://treg.to), so a service that is missing from integrations.sh can still appear
when Composio or Treg knows about it. Matching brands are folded together while each provider's
option remains visible in the preview.

The preview keeps the actions honest: integrations.sh REST/OpenAPI and GraphQL records use Core's
deterministic importers, MCP records jump to the MCP catalog, and CLI or otherwise environment-specific
records open a setup chat with a pre-written request. A Composio option opens the **Connections** tab.
Treg endpoint options also use the setup-chat handoff because browsing a Treg catalog does not create a
Treg credential or imply that Ryu can execute the call. Treg's public index can be browsed without a key;
Composio-only catalog entries require the node's Composio API key to be configured.

When a provider publishes a USD price, Ryu marks **Lowest listed price** only among options with the
same capability and billing unit. Unknown prices and unlike units are not ranked, and the badge is
not a guarantee of account eligibility or runtime availability.

## Health and agent scans

App and plugin detail views show the existing deterministic catalog scorecard in
their **Health** tab. Skills use a skill-specific version of the same scorecard,
covering source trust, audits, maintenance, documentation, and package integrity
without applying plugin permission checks to an instruction package.

On a node-backed desktop, each supported detail view also has **Scan with agent**.
It sends a bounded, read-only evidence snapshot to the reviewer selected in
**Gateway → Guardrails → Catalog scanner**. The agent's report is evidence only:
the deterministic grade remains authoritative, and incomplete output is labeled
**Partial**. Web catalog browsing stays read-only and does not expose the control.

### Add a custom marketplace

The **Marketplaces** tab is the unified source manager. It lists every source registry for Apps and
plugins, Skills, MCP servers, Models, Knowledge, and Agents, including which source is active and
whether it declares authentication. The **Installed** switch remains inside each catalog tab so
installed and available items stay easy to compare without mixing them with source administration.

Ryu-hosted and translated registry sources are managed by Ryu and cannot be removed. The supported
free-form marketplace flow is for custom GitHub-style sources: choose **Apps and plugins** or
**Skills**, then add the repository or manifest URL. Private source access is represented by an
environment-variable reference; the Marketplace UI never displays or returns the token itself.

In the **Marketplaces** tab, **Add marketplace** registers a custom `marketplace.json` catalog. The
reference may be any of:

| Reference | What it points at |
|---|---|
| `owner/repo` or `https://github.com/owner/repo` | a GitHub repo |
| `https://gitlab.com/group/repo`, `git@host:group/repo.git`, or any other git URL | a repo on any git host |
| `/abs/path`, `./rel/path`, or `~/path` | a local directory holding `marketplace.json` |
| `https://host/path/marketplace.json` | a directly-hosted manifest file |

GitHub references are read over `raw.githubusercontent.com`; any other git URL is `git clone`d (a
private repo works through your own git credentials); a local path is read straight from disk. The
The manifest is looked up at `.ryu-plugin/marketplace.json`, then `.agents/plugins/`,
`.claude-plugin/`, then `.cursor-plugin/` (first hit wins).

Marketplace sources are catalog inputs, not a second permission system. Organization, team, project,
and user assignments are resolved by the connected node's effective policy; a source row does not
grant an agent access to an item. Use the catalog tab's **Installed** filter and the agent or tools
allowlist controls for the resulting capability.

## Install a model

The **Models** page searches the active model source (Hugging Face by default) for models you can
run locally.

1. Search for a model.
2. Open a result to see its details: the README plus the quantization **download dropdown** (with
   real file sizes and SHA-256 checksums). The dropdown preselects the best device-fit quantization
   for this machine, badged "Recommended for your Mac/PC/device".
3. Check the **device-fit verdict**. Ryu detects your RAM and GPU VRAM and grades each file as
   *great*, *ok*, *partial offload*, *cpu*, or *too big*, so you know what will actually run.
4. Click **Install**. Core downloads the chosen file with checksum verification and records its
   provenance.

Device-fit is computed locally with zero extra setup. If you set an Artificial Analysis API key,
model detail views are enriched with extra benchmark stats, but no key is required. The full
model-browsing flow lives on [Models](/docs/surfaces/desktop/models).

## Install a skill

The **Skills** page browses all registered skill marketplaces together by default: [skills.sh](https://skills.sh),
vendor/community GitHub taps, [browse.sh](https://browse.sh), [ClawHub](https://clawhub.ai),
[LobeHub](https://lobehub.com), Ryu Marketplace, and custom Claude marketplaces. Use the source
picker to narrow the view to one registry.

1. Search the directory, or browse the featured default list.
2. Open a skill to read its `SKILL.md` documentation and file list.
3. Click **Install**. Core writes the skill into your local skills directory, hot-reloads the
   registry, and records it in your installed view, so the skill is available immediately.

Skills can also be installed directly from a source URL or repo (six forms, via
`POST /api/skills/install-from-source`). See the [Skills](/docs/surfaces/desktop/skills) reference for the
activation model and the per-agent allowlist.

## Install an MCP server

The **MCP** source lists servers from the official MCP registry, Smithery, or the Ryu-hosted
catalog. Installing an MCP server plans a **disabled** entry in `~/.ryu/mcp.json` (remote servers
are wired as `npx -y mcp-remote`), so you review it before it runs. Enable it from the
[Tools and connections](/docs/surfaces/desktop/user-guide/tools-and-connections) surface.

## Install a plugin

A **plugin** is a `manifest.json` manifest that bundles Runnables (agents, workflows, tools, skills)
together with the permission grants they need.

- The **Plugins** page lists the plugins Ryu Core has loaded, each showing its status (Installed or
  Enabled) and its **permission grants**. You can also **install from a URL** that points at a
  `manifest.json`; Core fetches, validates, and hot-reloads it with no restart.
- **Install** a plugin to validate it and its grants, then **Enable** it to activate its Runnables.
- System plugins such as **Ghost** (desktop automation) and **Shadow** (capture and search) are
  available from Core. Other official plugins are signed marketplace packages and are installed
  when you choose Install.

To add your own, drop a `manifest.json` into `~/.ryu/plugins/<your-plugin>/` (restart Core, or use
**install from URL** to hot-reload without one). Ryu validates the manifest per Runnable kind on
load. The manifest format is documented in
[Plugin manifests](/docs/extend/develop/extensions/plugin-json-manifest).

Marketplace and Library cards also show declared **swappable layers**. A badge such as **Browser
toolkit** means the plugin provides the `browser.control` layer; open its detail view to see the
canonical verbs and whether the provider acts locally or on a hosted/remote target. Hosted
providers carry an **External** badge.

Use the **Filters** control in the Apps or Plugins catalog to narrow results by a manifest's curated
`tags[]` array. Tags are separate from `keywords`: tags are short browsing labels, while keywords
remain search vocabulary. The filter spans first-party and community rows currently visible in the
catalog and clears itself when the selected tag is no longer present.

Apps and plugins that are still experimental are hidden from the catalog by default. Open **Filters**
and check **Show unstable releases** to include releases marked **Experimental**, **Alpha**, **Beta**,
**Release candidate**, or another publisher-defined maturity level. The setting applies to both Apps
and Plugins and stays separate from Library. It also composes with the catalog's **Installed** filter:
with both controls active, you see only installed stable releases unless you explicitly include
unstable ones.

Open a listing's **Versions** tab to compare published releases. Each version shows the stability
declared by its manifest. When Ryu has a trusted immutable Marketplace artifact for a historical
release, the row includes **Install this version**. Ryu verifies that exact release before installing
it and asks for confirmation when it is older than the version you have. Community, tag-only, or
otherwise unavailable history remains readable but does not offer an install action.

GitHub listings can declare presentation metadata from `manifest.json`, `.codex-plugin/plugin.json`,
or `.claude-plugin/plugin.json`. Screenshots, banners, author details, policy links, and prompts
are imported as safe server-side display metadata; executable code, permissions, MCP definitions,
and install instructions are not imported from those display manifests.

Open a listing to see its App-Store-style metadata rail: Developer, Category, Version, License,
Repository, Website, Privacy Policy, Terms of Service, Tags, Keywords, capabilities, example
prompts, and the declared screenshot gallery when those fields exist. A banner becomes the listing's
hero background, and a `provides` entry such as `browser.control` is shown as its canonical layer.

<Callout type="warn">
  Review a plugin's permission grants before enabling it. Grants determine what the plugin's
  Runnables are allowed to reach, and they are enforced through the Gateway.
</Callout>

<Callout type="info">
  Plugins that declare `post_assistant_turn` hooks (such as the built-in **double-check** and
  **goal** plugins) run their hook code in the same deny-by-default Deno sandbox as tool execution.
  This turn-hook runtime is live and backs installable plugins today. It requires **Deno on PATH**
  for code-exec hooks; when Deno is absent the runtime gracefully no-ops so chat is never blocked.
</Callout>

<Callout type="info">
  A plugin, app, or model's detail view shows a screenshot gallery when the listing carries
  screenshots. Click any screenshot to open it in the fullscreen lightbox (same viewer as chat image
  previews): use **Download** in the top-right, the image title and `− / percentage / +` zoom
  control at the bottom, plus arrow-key/chevron/dot gallery navigation; **Esc** or overlay-click
  closes it.
</Callout>

## The Download Center

Every long-running download Core fetches, including engine binaries, GGUF models, Audio models,
skills, and other artifacts, is tracked in one place. The desktop surfaces it as a compact icon in
the sidebar footer with a badge for active or failed downloads; click it to open a panel listing
each download (`apps/desktop/src/components/downloads/DownloadCenter.tsx`). Core owns the lifecycle,
so the panel is a thin view over its endpoints.

Each row shows a progress bar, transfer size, speed, and an estimated time left, with per-item
controls that depend on the download's state:

| State | Available controls |
|---|---|
| `active` | Pause, Cancel |
| `paused` or `queued` | Resume, Cancel |
| `verifying` | Cancel |
| `failed` (retryable) | Retry, Dismiss |
| `completed` or `cancelled` | Dismiss |

A **Clear finished** action removes all completed and cancelled entries at once.

The controls map directly onto Core's endpoints (`apps/core/src/server/mod.rs`):

| Endpoint | Purpose |
|---|---|
| `GET /api/downloads` | Snapshot of all tracked downloads |
| `GET /api/downloads/stream` | SSE: a full snapshot on connect, then live deltas |
| `POST /api/downloads/:id/pause` | Pause a download |
| `POST /api/downloads/:id/resume` | Resume a download |
| `POST /api/downloads/:id/retry` | Retry a failed download |
| `POST /api/downloads/:id/cancel` | Cancel a download |
| `DELETE /api/downloads/:id` | Clear (dismiss) a terminal entry |

The stream always sends a full snapshot as its first event, so a late or reconnecting client
self-heals without a separate fetch (`apps/core/src/server/mod.rs`, `downloads_stream`). The typed
client lives in `apps/desktop/src/lib/api/downloads.ts`.

<Callout type="info">
  Some installs cannot report a total size up front, for example a model or Audio model fetched from
  Hugging Face, where the source streams no byte total. Those downloads show an indeterminate
  progress bar (a running byte count without a percentage) rather than a filling bar, then complete
  normally.
</Callout>
