The **Payments** app (`@ryu/mpp`) supports the [Machine Payments Protocol (MPP)](https://mpp.dev).
It finds compatible services, shows the exact charge, and asks for approval before it pays. Payments
are off until you install the app from the [Store](/docs/surfaces/desktop/user-guide/store) and
create its wallet.

<Callout type="warn">
  The Payments app supports only Tempo testnet and pathUSD. It does not send mainnet funds.
</Callout>

## Choose a payment provider

For general purchases, Ryu recommends **Stripe Link Agent Wallet** when you have a supported U.S.
Link account:

1. Install it from the Marketplace MCP catalog and review it. Catalog installs start disabled.
2. Enable the `stripe-link` server in MCP settings.
3. Complete Link sign-in and any purchase approval in Link yourself.

Link CLI uses the Link account's default eligible payment method unless you select another one.
Link applies its own sign-in and approval rules, and Ryu does not store the Link account session.
Keep one-time payment credentials out of chat and logs.

| Payment route | Use it for | Scope |
| --- | --- | --- |
| **Stripe Link Agent Wallet** | Standard checkout, eligible Stripe checkout, and Stripe MPP | U.S. Link accounts; one-time card credentials, Link Pay Tokens, or Shared Payment Tokens |
| **Payments app** | MPP `tempo/charge` requests | Tempo testnet and pathUSD only; no mainnet funds |
| **x402 MCP** | Stablecoin payments to services using HTTP 402 | Separate x402 wallet and policy; it does not share the Payments app budget |
| **MPP Services** | Finding MPP-enabled services | Read-only catalog; it cannot spend |

The Link CLI's `mpp pay` flow supports merchants that accept the Stripe MPP payment method. Use the
x402 server when a merchant requests x402; Link approval and the Tempo wallet policy do not govern
that separate provider.

## Set up the wallet and policy

1. Install **Payments** from the Store and open its Companion UI.
2. Create the wallet. The signing key is generated locally. Core encrypts it and keeps it in the
   app's private storage.
3. Fund the wallet with testnet pathUSD.
4. Add the HTTPS origins you trust, then set a maximum charge, daily cap, and approval threshold.

The Companion UI has three tabs:

- **Services** finds services and pays them.
- **Policy** holds the wallet and budget controls.
- **Receipts** is the read-only local ledger of completed settlements.

Just before signing, the app checks the exact integer amount in the challenge against the policy
again. A redirect cannot leave the original origin. A prepared approval token works only once.

The daily cap uses the local reservation date, not the merchant's receipt timestamp.

<Callout type="warn">
  Once signing begins, an error or a missing receipt keeps that amount reserved in that day's
  budget. It does not return to the available budget. Check the merchant and wallet before you
  make another payment.
</Callout>

## Pay an HTTP endpoint

Choose **HTTP**, enter the method and the allowlisted endpoint URL, then select **Review payment**.
Ryu first sends the request without a credential. If the service returns an MPP
`402 Payment Required` challenge, the approval dialog shows:

- the exact pathUSD amount and the remaining daily budget;
- recipient, origin, network, purpose, and challenge fingerprint;
- the challenge expiry.

Approving signs that exact challenge and retries with `Authorization: Payment`. If any material
part of the challenge changes, Ryu stops and asks for a new review. A successful response must
include a protocol receipt before Ryu commits the reservation.

## Pay an MCP tool

Choose **MCP**, enter the remote Streamable HTTP server URL and the tool name, then review the
charge in the same dialog. Ryu recognizes both standard MPP forms:

- JSON-RPC error `-32042` with `data.httpStatus: 402` and `data.challenges`;
- a tool result carrying `org.paymentauth/payment-required` metadata.

After approval, Ryu retries the tool call with `org.paymentauth/credential` metadata and requires
`org.paymentauth/receipt` on success. An ordinary MCP call never becomes a payment without your
review.

## Automation and approvals

Auto-pay is optional. It applies only when the charge is below the approval threshold and every
other guardrail passes. Calls to the `mpp.pay` tool still show as risky actions in Ryu's tool
approvals.

For agent workflows, use `mpp.payment_prepare` for HTTP or `mpp.mcp_payment_prepare` for MCP.
Review the returned payment summary, then pass its one-time `approvalToken` to `mpp.pay`.

## Receipts and private data

The Receipts tab stores amount, network, recipient, origin, timestamp, method, and reference for
each settlement. It does not store payment credentials, signing proofs, private keys, request
bodies, or response bodies.

Wallet keys never enter chat or app state. Network safety is split between the app and Core:

- The app's sidecar forwards only a small allowlist of request headers, limits request and response
  sizes, and rejects cross-origin redirects.
- Core's guarded network egress blocks private and local network targets and pins the resolved
  public address for each request.
