---
title: "Virtual Desktop"
description: "Stream a managed cloud Bot's own Linux desktop live and drive it with your mouse and keyboard."
---

The **Virtual Desktop** panel streams a node's *entire* desktop — a real graphical session, not a
browser tab — to the desktop app live, with full mouse and keyboard input. On an opted-in managed
cloud node, the Virtual Desktop app assigns each Bot a stable screen on the same node computer. The panel's Bot
selector lets you watch or control the screen that belongs to that Bot.

## What you get

- **A whole computer, live.** The node runs a headless X session (Xvfb + a window manager + starter
  apps) with a VNC server on loopback. The panel connects a real VNC client (noVNC) to it over
  Core's WebSocket tunnel.
- **Interactive, not a view.** Pixels stream down the same socket your mouse and keyboard events go
  up. It feels like a remote desktop, because it is one.
- **One cloud computer, separate Bot screens.** Files, installed applications, and the underlying
  node are shared by design. Virtual Desktop screens and Browser app tab lanes are routed per Bot
  so simultaneous work does not collide. This is an execution and UX boundary, not a tenant or OS security boundary;
  do not place mutually untrusted tenants on one shared node.
- **Works on any node, with no new firewall rule.** The stream rides Core's existing port through a
  generic WebSocket tunnel. Nothing extra is exposed on the network; the VNC server binds loopback
  only.

<Callout type="info">
The virtual desktop is **Linux-first**: it needs the `xvfb`, `tigervnc`, and `openbox` packages
on the node. On macOS or Windows the
sidecar reports itself unavailable and the panel explains why. Managed cloud nodes can opt in at
provision time; self-hosted nodes install the toolchain with one flag.
</Callout>

## Enable it

1. **Install the Virtual Desktop app** for the node. In the desktop, open the node selector →
   **Toolkits / layers**, or the Store, and enable **Virtual Desktop** (`@ryu/desktop`). The app is
   opt-in, like Simulators and the Browser sidecar.
2. **Make sure the toolchain is on the node.**
   - **Managed (Ryu Cloud) nodes:** check **Install the managed computer** when creating the node.
     This installs the Linux desktop stack and enables per-Bot screens at provision time.
   - **Self-hosted nodes:** follow the self-hosted installation guide and enable the virtual
     desktop option for the node.
   - **Local Linux:** the panel's "Enable" prompt installs the packages for you.
3. Open the **Virtual Desktop** dock panel from the right side of the workspace. It connects
   automatically and shows the node's desktop.

## Use it

- **Mouse** clicks and drags map to the virtual screen. **Keyboard** input types into the focused
  app on the desktop.
- The connection status dot in the panel header shows whether the stream is live; **Reconnect**
  re-establishes it (useful after switching nodes).
- On a managed cloud node, choose a **Bot** in the panel header. Switching Bots reconnects to that
  Bot's stable screen; switching nodes reconnects to the selected node.
- Self-hosted and local Linux nodes without managed Bot allocations keep the legacy single-screen
  behavior.

### Keep the desktop visible

While the VNC canvas is live, Ryu mirrors its latest frames into the shared live-media
card. **Open PiP** creates a native OS-level always-on-top window, so the remote node
stays visible while you work elsewhere. **Expand** opens a fullscreen lightbox with a
thumbnail-to-fullscreen morph; close it to return to the exact small preview. The
card always follows the currently active node/panel source, so it does not leave an
old node floating after a node switch.

## How it works under the hood

1. The Virtual Desktop sidecar owns a persistent display allocation for each managed Bot and starts
   each Linux graphical session lazily.
2. The desktop panel uses an authenticated Core route bound to the selected Bot. Core checks the
   Bot's view/control permission before the request reaches the sidecar.
3. The sidecar bridges the panel's RFB-over-WebSocket stream to that Bot's loopback VNC session.

Ghost's node-wide `computer.control` target is separate from these app-owned Bot screens. The panel
does not claim that a Ghost action will appear on the selected screen. Browser app tools do receive
the verified calling-Bot identity through the generic tool caller-context field and keep separate
tab lanes without Core knowing about the Browser app specifically.

Because the stream rides Core's authenticated port, no sidecar port is ever exposed on the
firewall, and nothing on the node is reachable without the node token.

<Callout type="warn">
The routing, authorization, allocation, and WebSocket bridge are covered by focused tests. A live
cloud-provider desktop still depends on the node completing provisioning and installing its Linux
toolchain. If the panel shows "no display", check that the managed-computer option was enabled when
the node was created.
</Callout>

## Platform boundary

Managed cloud screens are Linux virtual desktops. A native macOS or Windows node cannot safely
provide the same unattended background guarantee while the user's active desktop remains private;
the local sidecar reports the managed Bot-screen feature unavailable there. Docker Desktop on those
hosts can run a Linux desktop inside its VM, but that is a separate Linux guest rather than a native
macOS or Windows desktop. WebAssembly is suitable for isolated computation, not for hosting a full
interactive GUI operating system and desktop session.
