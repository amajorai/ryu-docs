The composer picker and `@` mentions decide who answers a turn and with what. For the rest of the
composer, see [Composer, Context, and Media](/docs/surfaces/desktop/user-guide/chat-composer-and-media).

## The composer picker

The **+**, `@`, and `/` entry points share one sectioned, searchable menu that opens above the
composer. After opening **+**, keep typing in the composer to filter the list; choosing a result
replaces that search text with its tag. Enabled apps and plugins appear automatically from their
installed manifests, alongside files, chats, and composer actions, without a separate registration step.

### Prompt suggestions

When the composer is empty, a plugin or chat surface can show a ghost prompt. Press
**Tab** to accept it, or use **Arrow Down/Up** to open and move through the suggestion
list; **Enter** or a click fills the highlighted prompt. Typing hides the list. The
shared bridge lets hosts provide suggestions from a fast side agent using recent chat
and project context instead of a hardcoded list.

### Composer predictions

With the [Composer Predictions](/docs/plugins/composer-predictions) plugin enabled, Ryu
predicts the message you are most likely to send next after each reply and shows it as
ghost text in the empty composer. It is written in your own voice, based on how you
have phrased earlier messages in the same chat. Press **Tab** to move it into the
composer, then edit it or press **Enter** to send. Nothing is sent automatically.
When the next step isn't clear, the model abstains, so a prediction doesn't appear
after every reply. A prediction takes the ghost-text slot ahead of the first prompt
suggestion; the suggestion list still works with **Arrow Down/Up**.

Predictions read only the current chat's recent turns, not memories, connected apps,
or other chats. In the plugin's settings, choose a cheap, fast **Prediction model**.
If you leave it empty, Ryu uses your default side model, and otherwise the local
engine on this device. Turn predictions off with **Predict my next message** or by
disabling the plugin.

### Pin frequent composer items

Every row in the **+** menu can be pinned, including apps, skills, plugins, and built-in actions.
Hover a row and select its pin button to move it into the **Pinned** section at the top. Pins are
stored on this device and stay available across composer surfaces; select the pin again to remove
one. Search still filters the pinned section, so clearing the search shows the complete pinned list.

### Choose an agent and model

The composer's agent and model picker is one grouped dropdown with a search box and three sections:

- **Ryu Portal** - the flagship `ryu` agent, with its live model and reasoning-effort pickers when active.
- **Providers** - your configured Pi providers; an unconfigured one links straight to credential setup.
- **External Agents** - installed ACP agents, each probed lazily for its model and permission options when you drill in; agents you have not added yet show an Install button.

When you have used a target before, the picker puts it in a **Recent** section above the catalog.
Recent agent and provider/model rows resolve against the live catalog, so stale entries disappear
after an uninstall or provider removal. Use the remove button on a row to forget one target; the
list is personal to this device and does not change the agent's saved configuration. A model's
reasoning level is shown beside it when the host provides one, so selecting a recent row restores
the same model choice without making you remember which provider owns it.

In **Ryu Work**, the same dropdown is agent-only; the model selector is not shown anywhere in the
composer or nested provider/ACP picker. The selected agent remains the user's choice while model
routing stays automatic. Ryu Work's hidden permission choice is limited to the agent's own advertised
options; it never invents a bypass/full-access mode.

Ryu Work mode also removes the project-folder picker from a new-chat composer. A normal conversation can
start without a folder; a message that clearly asks Ryu to edit or run local project files opens a
contextual project chooser and resumes that message after selection. Once a chat has a project, its
Pinned summary Environment row shows that chat's project name without allowing the row to retarget it.
Ryu Work keeps the Environment section and the number of changed files visible, while hiding
insertion and deletion line-count chips.

### Model insight cards

Hover over a model row to see a compact insight card. Rounded meters compare speed, cost,
intelligence, and context on a five-point scale. Available pricing, rate, token, and supported input
and output details appear beneath the meters.

These cards use your current connection and account. Switching the node or its sign-in reads that
connection's insights again, even for the same model. A late response from the previous connection
does not replace the current card. Reopening a card on the same connection can reuse
its result for up to 15 minutes. If no insight is available, the picker remains usable without a card.

### Provider usage meters

Connected subscription providers in the **Providers** section show the same user-configured usage
meters as subscription ACP agents. The rings or bars follow the Usage meter settings, including
remaining-versus-used mode, 5h/7d windows, and reset details; managed Ryu pool rows continue to show
their separate grant balance.

When a subscription provider has more than one saved login, its row shows the active login's usage
and lists every login's usage in the tooltip. Opening the provider shows a **Usage by account** list
with one meter per saved login. Logins that need a fresh sign-in, or that are excluded from the
account pool, are listed without being read. Per-account usage covers Claude Pro/Max, ChatGPT, OpenAI
Codex and GitHub Copilot; ChatGPT Plan, Kiro, Kimi, Radius, Ant Ling and CLI logins report no
per-account usage.

Ryu reads supported agents' existing local credentials without refreshing or writing them back.
Usage meters currently cover Claude Code, Codex, GitHub Copilot, Grok, Z.ai, Cursor, Devin,
Antigravity, OpenCode Go, and Ollama Cloud. OpenRouter's account credit balance is already shown by
the provider-credit meter.

Devin shows its daily and weekly quota when available, plus its extra-usage balance; when Devin
omits its weekly quota, Ryu follows Devin's daily-usage fallback.

Cursor shows its billing-cycle and model usage, on-demand spend, Credits and Grok Bot quota when
the account returns them. Request-based Enterprise accounts show their included request count when
available.

Antigravity shows its shared Gemini and third-party pools while the IDE is running. OpenCode Go
shows its rolling, weekly, and monthly account limits. Ollama Cloud shows its 5-hour and weekly
usage fractions, plus recent spend when returned; its endpoint does not provide reset times, so Ryu
does not guess them.

Devin and OpenCode Go require their existing CLI logins. Ollama Cloud uses the existing local
Ollama signing key only to sign its fixed usage request; Ryu never sends the private key or writes
it back.

The Ollama endpoint is undocumented and may change. Cursor may need
the Cursor app to renew an expired access token; Ryu never uses Cursor's refresh token. A meter
stays hidden when an agent has no readable credential or the provider does not return a supported
limit.

### Monthly API-equivalent estimate

The Usage page can also show an optional **API-equivalent estimate** for OAuth accounts used by the
Ryu-managed Pi agent. When enabled, Core records completed ACP turns with reported input/output
tokens and attributes them to the provider account active when the turn started. A turn is counted
in the UTC month when it completes. The estimate uses current input/output list prices from
models.dev; it is not the subscription provider's invoice or actual subscription spend. Cached-token
discounts, included subscription allowances, and provider-specific billing rules are not inferred.

Tracking is off by default and begins with new turns after you enable it. The active Core node stores
only provider/account/model IDs and token counts for the current UTC month; prompts and credentials
are never stored in this ledger. Estimates use the current models.dev catalog, so catalog price
updates can change earlier estimates. Turns without reported token counts or a models.dev price are
shown as incomplete/unpriced rather than being treated as free. After a session resume, if ACP
reports only cumulative counts and Core has no prior per-session baseline, the first resumed turn is
marked incomplete instead of counting earlier session usage again.

### Context usage and breakdown

The composer shows how much of the model's context window the chat uses. Warning and critical
rings match their percentage labels and remain readable in light and dark themes.
Click the context meter to open the **Context** panel. It shows Core's last saved attribution by
category, the provider-reported usage, and any unattributed tokens. A new chat or restarted Core
may have no saved breakdown yet; send a turn to create one.

### Prompt cache

When the provider reports cache counters, the context meter's hover card and the **Context** panel
show the last turn's cache hit rate (cached input as a share of all input) and an estimate of
whether the cache is still warm. Warmth counts down from the last turn that read or wrote the cache,
using the provider's published default lifetime: five minutes for Anthropic and 30 minutes for
OpenAI, each refreshed on every hit. Google, DeepSeek, and xAI publish no fixed expiry, so Ryu shows
the cache as cached without a countdown. Ryu cannot inspect the provider's cache directly, so treat the countdown as an
estimate; see [Prompt caching](/docs/gateway/prompt-caching) for how Ryu requests caching.

Prompt caches are tied to one model. In **Agent**, switching models mid-chat while the cache may
still be warm shows a warning: the next message re-sends the whole context at the full input price.
**Bot** has no model picker, so it never shows this warning.

## Choose which computer a new chat runs on

When you have added more than one computer, the workspace strip at the bottom of a new chat's
composer starts with a computer chip, before the project chip. It shows where the chat will run,
with a status dot for each computer in its menu. A chat started with **+** on a computer in the **All computers** sidebar
starts on that computer. The chip needs per-tab computers; when you turn that off it is hidden and
every new chat runs on your default computer.

You can change the computer only before the first message. A chat's history lives on the computer
it started on, so after the first message the chip is locked and its tooltip says **Start a new
chat to use another computer**. Changing the computer on an empty chat reloads that tab.

## Target a turn with `@` mentions

The composer's `@` menu routes a turn before you send it:

- **`@agent`** directs the message at a specific conversation participant.
- **`@group`** fans the message out to a group's members under its coordination strategy (see [Groups](/docs/surfaces/desktop/user-guide/teams)).
- **`@workflow`** runs the message through a workflow: the text becomes the workflow's input, its nodes stream back as a live checklist, and the output is the reply. Only workflows that accept a chat input (a root `input` node) appear. See [Run a workflow from chat](/docs/core/workflows#run-a-workflow-from-chat).
- **`@app`**, **`@plugin`**, and **`@skill`** add an installed capability as a reference in the prompt.
- **App list items**, **Space pages**, and **personality profiles** are also available from the same
  `@` directory. App list items come from the app's existing sidebar/Library source, so the row
  opens the same destination in chat that it opens from those surfaces. A personality profile opens
  the Agents page, where you assign it to an agent.
- **`@integration`** references an active connected integration, such as a Composio GitHub or Slack account. Integrations appear only when the active node has Composio access configured through BYOK or its managed subscription/proxy; unconfigured nodes show none.

Picking an agent, team, or workflow also sets the turn target from the mention itself; chats, Space
pages, personality profiles, app list items, spaces, skills, apps, plugins, integrations, MCP servers,
folders, and composer plugins are plain reference tokens.

### Mention attachments and rearrange chips

Each image or file you attach also adds a chip to the end of your message: `@image-1`, `@image-2`,
and so on for images (shown with the image's own thumbnail), and `@file-1`, `@file-2` for text files.
Use them to say which attachment you mean, for example `@image-1 with the face from @image-2`.
Images and files are numbered separately in the order you attached them, which is also the order
they are sent. Removing an attachment removes its chip and renumbers the rest, so each chip keeps
pointing at the same file.

Drag any mention chip, including agents, workflows, chats, and attachments, to move it to a
different spot in the message. In the plain composer the chip snaps to the nearest gap between words;
in the rich Markdown composer it drops where you release it. Spacing around the chip is adjusted for
you.

The **+** button and paste (plus drag-and-drop on the chat page) attach images and plain-text files
such as `.txt`, `.md`, `.csv`, `.json`, `.yaml`, and source code, up to 2 MB per text file. Other file
types are not attached yet; Ryu tells you which files it skipped.
