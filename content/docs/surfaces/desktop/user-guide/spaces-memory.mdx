Ryu gives agents two kinds of grounding. A **Space** is a document store you build and attach to
an agent so its answers cite your own material. **Long-term memory** is what an agent records
about you over time, used as background on every reply. Both run locally in Core, and both are
swappable defaults rather than locks.

This page is the how-to. For how retrieval is scored and assembled, see
[Spaces & RAG](/docs/core/spaces-rag); for how memory is captured, encrypted, and recalled, see
[Memory](/docs/core/memory).

## Browse Spaces as project folders

The desktop Spaces Library shows each Space as a **Project Folder**. Open a folder to preview its
top-level pages and databases. Select a page to open its full page editor, which renders Markdown
in the PlateJS reading surface, or select a database to open its full database editor. Preview
cards load independently, and the folder offers **Try again** if its document list cannot load.
Selecting a preview or creating a page or database closes the folder before opening the editor.

## Create a Space and add documents

A Space is a vector store backed by sqlite-vec inside Core. To build one:

1. Open the **Spaces** page in the desktop app.
2. Create a Space, give it a name, and choose **Private** or **Team** visibility. New Spaces
   default to **Private**. This calls `POST /api/spaces`.
3. Add content. Each document is embedded on ingest (`POST /api/spaces/:id/documents`, the
   `spaces.ingest_document` path) so it can be retrieved by meaning as well as keyword.
4. Or start a blank **page** (`POST /api/spaces/:id/pages`) and write notes directly in the
   editor.

## Import files and connected-app data

Open a Space and choose the **Import** tab to convert existing content into editable Space
documents. This is different from attaching a raw file for search: an import creates pages and
databases that you can open, edit, and search like documents created in Ryu.

- **Documents become pages.** Ryu accepts text, Markdown, HTML, Word (`.docx`), PDF, EPUB, and
  OPML files. You can choose several files in one pass.
- **Spreadsheets become databases.** CSV, TSV, DSV, Excel (`.xls` and `.xlsx`), and OpenDocument
  (`.ods`) files create typed database columns and rows. CSV-style headers are de-duplicated, and
  Ryu recognizes number, checkbox, URL, short-text, and long-text columns.
- **ZIP archives can contain both.** Ryu imports each supported file inside a ZIP and records all
  resulting pages and databases together. Nested ZIP files and unsafe archive paths are rejected.

Binary document and spreadsheet conversion uses the active document parser. The built-in text
reader handles text-based formats; formats such as PDF, Word, Excel, EPUB, and OpenDocument need
an enabled parser that advertises them. Each uploaded file can be up to 32 MB, while expanded ZIP
content is limited to 256 MB.

The **Third-party imports** card reads from accounts connected through Composio. Choose a
connected app, an action Composio marks with its reviewed `readOnlyHint` behavior tag, its required
fields, and whether the result should become a page, a database, or be chosen from the returned
data. Ryu does not infer safety from words such as `GET` or `LIST` in an action name. Configure
accounts from **Store → Connections** before using this card.

## Choose Vector or Graph retrieval

Each Space has a retrieval picker in its detail view:

- **Vector / Quick search** compares chunk embeddings. It is the default and works well for direct
  semantic similarity.
- **Graph / Connected search** extracts normalized terms and connects terms that occur in the same
  chunk, then follows those connections for up to three hops. These are co-occurrence connections,
  not LLM-inferred facts or relation labels.

Changing to Graph starts a background rebuild and shows its progress. The current mode remains
active until the replacement graph commits. You can cancel before finalization without changing
the current mode; switching back to Vector removes the term graph but keeps existing embeddings.
If the app cannot confirm a terminal job response, it refreshes the Space instead of claiming the
mode is unchanged.

Graph mode is intentionally bounded. One document can contribute at most 256 chunks, Core extracts
at most 64 terms per chunk, and a Space can contain at most 2,000,000 graph rows. Split an oversized
document or use Vector mode when a Graph ingest reaches one of these limits.

Every file and connected-app import appears under **Previous imports** with its status, source,
time, size or item count, errors, and links to every created document. This history is stored with
the Space and remains available after reopening the app. If Core is interrupted during an import,
the abandoned row is reported as failed instead of spinning forever.

| Import action | Route |
|---|---|
| List previous imports | `GET /api/spaces/:id/imports` |
| Import a file or ZIP | `POST /api/spaces/:id/imports/files` |
| Import from a connected app | `POST /api/spaces/:id/imports/composio` |

## Share a Space as Markdown

Use **Export package** in a Space to download a portable <code>.ryupack</code> archive. The archive
is an OKF-compatible Markdown folder: top-level pages are Markdown files, and each database is a
folder with an <code>index.md</code> schema file plus one Markdown file per row. YAML frontmatter
uses the same attribute style as Obsidian, so the content remains readable and editable outside
Ryu.

The package contains source pages, database structure, row values, and frontmatter only. It does
not contain embedding vectors, vector indexes, provider credentials, chat history, or binary files.
When you import it on another node, Ryu creates a new **private** Space with no vectors. Run the
manual embedding re-index when you want RAG on that node; its current retrieval and embedding setup
is used then. Sharing the resulting Space with a team is still an explicit visibility action on
that node.

You can also import a portable package from the Space's **Share this Space** card. An imported
package is a content snapshot: disabling or uninstalling its Marketplace package removes the
imported Space, while exporting the Space again creates a new source snapshot.

| Portable action | Route |
|---|---|
| Export a portable Markdown package | <code>POST /api/spaces/:id/export</code> |
| Import a portable Markdown package | <code>POST /api/spaces/import</code> |

## Open files in workspace tabs

Uploaded files and agent-created artifacts open beside chats, pages, databases, and Browser tabs.
Ryu chooses the built-in surface from the stored file type:

| File | Workspace support |
|---|---|
| PDF | Page navigation and zoom in a read-only viewer |
| DOCX | Rich-text Word document editor |
| XLSX / XLSM | Multi-sheet spreadsheet editor with formulas and typed cells |
| PPTX / PPTM | Slide previews plus editable text boxes |

Office files use an explicit **Save** button. Saving replaces the file in its Space, keeps the same
document identity and access rules, and refreshes its searchable content. **Download** always exports
the latest saved revision. Legacy `.doc`, `.xls`, and `.ppt` files remain downloadable but are not
presented as editable Office Open XML documents.

## Share a Space with your team

Spaces are private by default, but a shared node can keep personal and team knowledge side by
side. Use the visibility control in the Space's sidebar menu to switch between:

- **Private** — only the Space owner can list, open, search, or retrieve its content.
- **Team** — members of the organization that owns the node can use the Space.

Pages, databases, whiteboards, and uploaded documents inherit the visibility of their parent
Space by default. Changing a Space back to **Private** immediately removes pages that inherited
the Space's shared scope from the team's lists and retrieval results; you do not need to move or
re-index the documents.

The same visibility indicator appears beside each Space in the sidebar. It is also shown in the
Space picker, so an aggregate view never hides whether its contents are personal or shared.

You can also drag a Space row between the **Private** and **Team** groups. Ryu asks for
confirmation before changing the scope, and the menu action offers the same confirmation for
keyboard and context-menu users. Moving a Space moves the effective visibility of its pages,
databases, whiteboards, and uploaded documents because those resources inherit the parent Space's
scope. Moving a Team Space back to Private is restricted to organization admins and owners; other
members see **Make private (admins only)** disabled.

| Action | Route |
|---|---|
| List Spaces | `GET /api/spaces` |
| Create a Space | `POST /api/spaces` |
| Ingest a document | `POST /api/spaces/:id/documents` |
| Create a blank page | `POST /api/spaces/:id/pages` |
| List imports | `GET /api/spaces/:id/imports` |
| Import a file | `POST /api/spaces/:id/imports/files` |
| Import from Composio | `POST /api/spaces/:id/imports/composio` |
| Download a file | `GET /api/spaces/:id/documents/:doc_id/blob` |
| Save a file revision | `PUT /api/spaces/:id/documents/:doc_id/blob` |
| Search a Space | `POST /api/spaces/:id/search` |
| Change Space visibility | `POST /api/spaces/:id/visibility` |
| Delete a Space | `DELETE /api/spaces/:id` |

## Edit documents in the PlateJS editor

Open any document to edit it in Ryu's Notion-style PlateJS editor
(`apps/desktop/src/pages/SpaceDocEditorPage.tsx`, route `/spaces/:spaceId/doc/:docId`). Saving
sends `PUT /api/spaces/:id/documents/:doc_id`, which re-embeds the document so retrieval always
reflects the latest text. Delete a single document with
`DELETE /api/spaces/:id/documents/:doc_id`.

<Callout type="info">
  Meeting notes reuse this exact surface. When a meeting is finalized, Core writes the notes and
  transcript as a markdown document into an auto-created "Meetings" Space, so you view and edit
  them in the same PlateJS editor. See [Meeting notes](/docs/core/meeting-notes).
</Callout>

## Beyond pages: databases, whiteboards, and a wiki graph

A Space holds more than ingested documents and markdown pages. Three richer document kinds live
alongside them, and all of them feed the same retrieval so an agent can still ground its answers in
them.

### Databases

A database is a Notion-style data grid (`kind="database"`), created with
`POST /api/spaces/:id/databases`. Columns are typed (text, number, checkbox, date, url, select, and
multi-select), each row can open as its own page, and you can view the same data as a **table**, a
**board / kanban** grouped by a select column, a **gallery**, or a **list** - views are a display
layer, so switching never mutates the data (`apps/desktop/src/components/spaces/views/ViewBar.tsx`,
`BoardView.tsx`). For retrieval, Core flattens each row's labels and cell text before embedding, so
a database is searchable the same way a page is.

### Whiteboards

A whiteboard is an Excalidraw canvas stored as a third kind (`kind="whiteboard"`), created with
`POST /api/spaces/:id/whiteboards`. You can also generate one from a prompt: `POST
/api/whiteboard/generate` runs a single side-model call, which is Gateway-routed like every other
model call, and the diagram is drawn client-side from the model's output
(`apps/desktop/src/lib/whiteboard/`). For search, Core extracts the text on the canvas elements and
embeds that.

### Wiki links, backlinks, and a graph

Pages can link to each other with `[[wikilinks]]` and `@mentions`. Ryu tracks these as a
document-to-document graph (the `document_links` store), which powers a backlinks panel under the
editor (`apps/desktop/src/components/spaces/BacklinksPanel.tsx`,
`GET /api/spaces/:id/documents/:doc/backlinks`) and a knowledge-graph view (`GET /api/spaces/:id/graph`,
or `GET /api/graph` across all Spaces). It also feeds retrieval: link-expansion pulls chunks from
linked documents into the candidate set before reranking, on by default and controllable with
`RYU_SPACES_LINK_EXPANSION`.

<Callout type="info">
  This document-link graph is separate from the chunk-level term co-occurrence GraphRAG (`graph_nodes`). Both
  feed search independently. For how retrieval scoring and GraphRAG work, see
  [Spaces & RAG](/docs/core/spaces-rag).
</Callout>

## Attach a Space to an agent

Attach a Space from the agent's configuration (the **Agent** edit page). Once attached, the agent
retrieves relevant passages from that Space and grounds its answers in them instead of relying on
the model's training alone. This is how you build an agent that answers from your own knowledge
base. To manage agents, see [Agents](/docs/surfaces/desktop/user-guide/agents).

<Callout type="info">
  The embedding model and retrieval strategy are configurable, not hardcoded. Core ships a local
  default (the `nomic-embed-text-v1.5` GGUF served by the bundled `llamacpp-embed` sidecar) so
  RAG works on install. Change the embedding model and re-index via
  `GET/POST /api/embeddings/model`. See [Spaces & RAG](/docs/core/spaces-rag).
</Callout>

## Long-term memory

Separate from Spaces, Core keeps an encrypted long-term memory store (`server/memory.rs`,
`MemoryStore`). It is captured as you converse, so you do not curate it by hand, and it is
encrypted at rest on your machine.

Before each reply Core retrieves relevant snippets from long-term memory and past conversations
and passes them to the model as background context. This **auto-recall** is on by default, never
blocks a reply if retrieval is unavailable, and skips the current conversation. The internals are
documented in [Memory](/docs/core/memory).

### View, search, and add memory

Manage memory from **Settings -> Memory** in the desktop app (`MemoryTab.tsx`):

- **Long-term memory** is enabled for fresh installs so onboarding can build a useful starting
  profile. Existing explicit disables are respected; you can turn it off any time in Settings.
- The onboarding profile job can write source-backed drafts to both your user memory and the selected
  organization memory after explicit “Share everything” consent. Facts are drafts to review, not
  automatic decisions.
- **Auto-recall** is the on-by-default similarity search across long-term memory and indexed
  Space documents, controlled by the `auto-recall-enabled` preference.
- **Search memory and Spaces** runs a ranked similarity search via `POST /api/retrieval/search`,
  the same retrieval path the desktop uses to surface context.
- **Index a memory chunk** manually adds a piece of text so Core can retrieve it later
  (`POST /api/retrieval/index`).

```
POST /api/retrieval/search
POST /api/retrieval/index
```

These are available to any client that talks to Core on `:7980`.

### Track memory in a local Git repository

The Memory Library also has an explicit **Git-backed memory** binding. Choose a local repository
and Ryu writes a source-only `memory/` tree: one Markdown file per memory, plus an `index.md`.
The files use YAML frontmatter for scope, category, importance, tags, and stable memory ids, so
they are readable in Obsidian and reviewable in normal Git diffs. Export and import are explicit;
Ryu never writes encrypted SQLite rows, conversation provenance, provider credentials, or vectors
to the repository. Local indexing remains a node concern and can be regenerated with that node's
current embedding setup.

The card shows the current branch and changed-file count, can initialize a repository, and can
commit the Markdown source with the existing Core Git boundary. Import reads only the `memory/`
folder; absent files are not deleted from Ryu automatically, so a Git checkout or deletion is
never mistaken for permission to erase durable memory. This is intentionally an opt-in plaintext
export: treat the selected repository as sensitive and review changes before committing or
pushing.

<Callout type="warn">
  Long-term memory remains personal to the signed-in caller. A shared Space is different: its
  documents are filtered by the Space's visibility, and auto-recall uses the current caller's
  permissions. A shared conversation does not give one teammate access to another teammate's
  private memory or private Space. The "Connected" presence panel answers who is on a node, not
  who may see every resource. See [Node & presence](/docs/core/node-and-presence).
</Callout>
