Use these views to inspect an agent, change it in plain language, and roll it back. For the rest of
agent setup, see the [Agents guide](/docs/surfaces/desktop/user-guide/agents).

## Inspect an agent passport

From a chat with one agent, open **Agent profile and activity** in the title bar to see that
agent's activity beside the conversation. The profile shows the selected node's connection state
and groups the agent's chats and automated runs by day. Open an entry to return to its transcript.
The other profile views show the agent passport and trace ledger and its saved identity details.
When the Calendar app is enabled, the profile also has a **Calendar** tab. It shows only this
agent's past and upcoming scheduled runs, opens on **Agenda**, and starts **New automation** with
this agent selected. The Calendar app provides this tab, so disabling the app removes it. A team
chat does not show this single-agent profile.

The agent editor's **Activity → Agent passport** view, and the agent profile under **Settings →
Stats → Your team**, show a read-only passport for a saved agent. It includes the stable agent ID,
version, lifecycle, safety profile, runtime/model binding, creation and last-configuration times,
and capability counts for tools, skills, identity bindings, and memory.

Selecting an agent under **Settings → Stats → Your team** opens its profile: its badge, a year of
daily usage, and lifetime stats (tokens, hours worked, requests, level, and best streak, the most
consecutive UTC days the agent was used). Each badge
in the roster is a button named for its agent, so you can also reach it with Tab and open the
profile with Enter or Space. **Back to team** returns to the roster. If the agent's stats can't be
read, the profile says so and offers **Retry** rather than showing zeros, which are reserved for an
agent that has no usage yet.

The passport's **Trace ledger** joins the latest redacted Gateway model/tool/credential/widget events
with agent-management control changes. Each row distinguishes the performer from the initiator:
for example, "Support agent performed a tool execution on behalf of Jia Wei" versus "Changed by Jia
Wei". Rows retain the request ID and Core session ID when available, plus the exact timestamp,
target, outcome, and bounded provider/backend summary. Prompts, tool arguments, provider keys, and
decrypted identity credentials are never rendered.

On an organization-bound node, the ledger reads the organization audit projections so a viewer can
see activity across the organization's reporting gateways. On a standalone node it reads the local
Gateway audit. If an audit source is unavailable, the passport says so rather than presenting a
partial result as a complete history. Use the correlation IDs to move from an activity row to its
run transcript or the organization Audit log.

## Agent builder

While an agent's edit page is the focused tab, the docked **Ask Ryu** panel acts as that agent's
builder. Tell it what you want in plain language, for example "make it formal" or "add the web
search tool", and it applies the change. The config form refreshes after each change.

The builder uses Core's built-in `agent_builder` tools (`get_agent`, `configure_agent`, and
`create_agent`). When you ask for a change, the model calls `configure_agent` to patch the saved
agent record.

The editor keeps the setup decision in one place: instructions in the composer, with the agent and
provider/model picker in its footer. Expand the composer when you need the full Markdown toolbar.
The other tabs cover tools, triggers, and, in Agent, connections and testing.

Builder behavior:

- Builder turns run with `persist: false`, so they never enter your chat history.
- For a brand-new agent, Ryu creates a **draft record** on your first builder message so the
  builder has a real record to edit.
- `configure_agent` refuses to edit a `built_in` or `locked` record, so the flagship `ryu` agent and
  the builder meta-agent cannot be rewritten through the builder.
- Changing an agent through `configure_agent`, including an app alias, requires an interactive
  permission decision and review in the approval inbox. A network-only tool call cannot supply
  that interactive consent. Agent creation also requires the calling agent's creation capability.
  Delegation and peer discovery require its orchestration capability, including when a tool is
  called through another tool.

<Callout type="warn">
  The builder runs a tool loop, so it needs a running Core and a model that can make tool calls.
</Callout>

## Restore an agent checkpoint

Open **Versions → History** in the agent editor to compare or restore a saved checkpoint. Restore
reloads the saved instructions, model, capabilities, persona, and safety settings. If the request is
refused, the error stays visible in History and your unsaved editor draft stays available. Choose
**Restore** again to retry.

Switching to another node or agent loads that selection. A late response from the previous selection
cannot replace its editor or history state. Editing the same agent's instructions keeps its open
version history, comparison, and pending restore intact.

When you save an agent after restoring a checkpoint, its delegation and agent-creation choices are
saved with the rest of its configuration. Explicitly disabled capabilities stay disabled. A
capability left at its default keeps the node's default behavior.

For what a checkpoint contains, see
[Agent Observability and Evals](/docs/surfaces/desktop/user-guide/agent-observability-and-evals#know-what-a-checkpoint-contains).
