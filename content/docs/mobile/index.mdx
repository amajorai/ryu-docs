---
title: "Mobile"
description: "Native Ryu on iOS and Android, including on-device AI and mobile tools."
---

Ryu Mobile keeps the shared remote Core experience while exposing a native-only
on-device route. The universal picker can choose a remote node and agent, or a
downloaded GGUF model backed by `llama.rn`.

Mobile chat actions are native to the handset. They include operations such as
rename, pin, archive, and delete, but omit Desktop window, tray, updater,
file-manager, editor-launch, and always-on-top window controls. Shared UI blocks
feature-detect the mobile host instead of inferring Desktop behavior from screen
size or user agent.

## Plans, credits, and Marketplace purchases

Ryu Mobile is a consumption-only surface for account billing in the default iOS
and Android builds. It can show the signed-in account's existing plan, credit
balance, usage, licenses, and installed apps, but it does not show upgrade,
checkout, or top-up controls. Marketplace app/plugin prices do not gate catalog
browsing, installation, or use, so paid and free rows keep the same install path.

If you need to change a plan or add credits, use the device or browser where you
purchased Ryu. Marketplace item pricing is optional commerce metadata. Apple purchases are managed in
Apple Account subscriptions, Google Play purchases in Play Store subscriptions,
and web purchases in Ryu on the web. The same account can continue using an
existing entitlement on mobile; Core remains the authority that confirms access.

## What Mobile adds

Mobile owns native model execution, OS notifications, and device feedback. These capabilities stay
behind the mobile host bridge and remain unavailable when a plugin runs in a browser or terminal.

| Capability | Mobile behavior |
|---|---|
| On-device models | Run downloaded GGUF models with `llama.rn` in a native development client or store build |
| Notifications bridge | Let approved companions call `native.notifications.create` for a bounded local notification |
| Live run status | Update iOS Live Activities or Dynamic Island, and Android ongoing notifications |
| Device feedback | Use grant-gated haptics, app shortcuts, navigation, files, media, and hardware tools |

Check `host.capabilities` before showing a native action. The host may lack a capability because the
OS, build, foreground state, or permission does not support it. See [Native bridges](/docs/extend/develop/extensions/native-bridges).

## On-device models

The Models screen starts with two curated choices: SmolLM3 3B Q4_K_M and Qwen3
4B Q3_K_M. Weights are never bundled or downloaded without the user selecting a
model. Downloads are resumable, support split GGUF files, write through a
temporary file, and finish with an atomic move into app-scoped storage.

The mobile screen combines Core's universal DownloadCenter snapshot/SSE events
with the native handset-copy task using the same lifecycle states and progress
fields. Core remains the authority for node-side staging; the handset task is
the final local copy leg.

`llama.rn` is compiled into a native development client or EAS build. Expo Go
and the browser do not load the native module. Browser-local AI remains a
separate browser provider path.

## Mobile tools and privacy boundaries

The local model can use Ryu/MCP tools only through Core's typed MCP and approval
APIs when a node is reachable. Offline runs hide remote tools and keep native
mobile tools available. The native registry covers device status, navigation,
notifications, haptics, camera/media, sharing, clipboard, user-selected files,
contacts, calendar, BLE discovery, and Ryu-owned background tasks.

Every descriptor declares its risk, OS permission, foreground requirement,
offline availability, and confirmation policy. Sensitive reads and all writes
show an in-app confirmation card by default. The card puts a first-person
question such as “Can I read the current battery and power state?” above the
plain-language summary, then offers the decision. Results and tool arguments
are redacted before local transcript persistence. Local `local:` conversations
are separate from Core conversations and only cross that boundary when the user
explicitly copies content.

## Native OS surfaces

Ryu keeps useful agent state visible when the app is not in the foreground:

- On iOS, an enabled Live Activity shows a running agent on the lock screen and
  Dynamic Island. On Android, the equivalent is a low-priority ongoing agent
  notification.
- When a background run finishes, Ryu can post a separate finished alert. Push
  registration is scoped to the active node and only starts after the operating
  system permission is granted.
- Quick actions expose common entry points such as New Chat and Tasks from the
  app icon. Haptics cover sends, quick actions, and run outcomes, and respect the
  Haptics setting in the app.

The native capability tool reports which of these surfaces are available in the
current build and whether notifications are currently permitted. Expo Go and the
browser intentionally report fewer native capabilities than a development client
or store build.

Sandboxed app companions use the same read-only `host.capabilities` descriptor and, when their
approved grants allow it, the narrow native bridge methods `native.haptics`,
`native.notifications.create`, and `native.liveActivities.update`. The bridge bounds text, keeps
the node credential on the trusted host, and returns an explicit unavailable or permission failure
when the OS surface is missing. A plugin must not infer iOS or Android behavior from the user agent;
feature-detect first. See [Native bridges](/docs/extend/develop/extensions/native-bridges) for the
cross-surface contract.

## Tool-call explanations

The existing `@ryu/action-summary` plugin adds a first-person question plus a
short out-of-band explanation for thinking blocks and tool calls in remote Core
conversations; the mobile chat renders that intent above the summary as a
separate callout. Core's remote approval request carries the same question and
summary bridge. On-device models receive the same one-sentence instruction
before native tool use; if a model emits a bare function call, the native loop
supplies a short descriptor-based line instead. Sensitive actions still pause on
a confirmation card. The explanation is not a substitute for the permission or
confirmation boundary.
