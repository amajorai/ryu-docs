title: "Auto-update"
description: "One Core-computed update verdict with native download and install behavior for each surface."
---

Ryu keeps the update decision understandable across every surface (desktop, web app, CLI, gateway, island,
extension, and mobile). The release verdict is shared where a surface talks to Core; the install *mechanism*
remains platform-specific. Per the [Core vs Gateway](/docs/start-here/architecture/core-vs-gateway) rule,
deciding *what runs* (including which build of the binaries runs) is Core's job. The Gateway governs what is
allowed, measured, and paid, never the install lifecycle.

For the complete Stable, Beta, Nightly, Canary, and local Dev comparison, including local data roots and
sharing boundaries, see [Ryu Release Channels](/docs/start-here/release-channels). This page focuses on
the update verdict and install mechanisms.

## One verdict, native install

Each Stable Ryu release uses a **single release train**: one git tag (`vX.Y.Z`) builds and publishes every
binary together, so `core`, `gateway`, `cli`, and `desktop` share a version. Canary and Nightly are separate
prerelease trains with versioned suffixes and their own feeds. Beta is currently backed by the signed Stable
feed, and Dev is a local build rather than a published train. Core's own crate version (`CARGO_PKG_VERSION`)
is therefore the canonical version for the build that is answering an update check, and `current_version()`
returns it.

Every client reads Core's one verdict instead of each re-implementing GitHub-release polling. What differs is
only how the bytes land:

| Surface | Mechanism | On launch |
|---|---|---|
| Desktop (Tauri) | Signed Tauri updater feed with a durable, one-artifact cache | After sign-in, the first onboarding screen checks the desktop bundle and lets the user continue at any time. By default, eligible updates download and verify in the background. Ryu then asks before installing and restarting. |
| Web app (browser) | Deployment refresh | Does not show a native-app update step or claim that a desktop bundle is current. A new web deployment is picked up through the browser's normal refresh/reload path. |
| CLI (Rust) | Manual download (prints the release URL) | Prints a one-line notice when an update is available; `ryu version` / `ryu update` show details. |
| Extension (Chrome) | Chrome Web Store (auto) | Mounted notify-only toast, deduped per release; the extension does not try to install its own package. |
| Island (Electron) | Core `DownloadCenter` for the managed bundle, plus `electron-updater` when the companion is running | Desktop and one-line setup stage the bundle through the global resumable download path while Island is disabled. Once enabled, the running companion reads the shared `auto-updates` pref; enabled updates install silently and relaunch, while disabled updates remain available without an unattended install. |
| Mobile (Expo) | `expo-updates` (EAS OTA) | Checks on launch when enabled; Settings can check manually and offers an available OTA for explicit installation. |
| Gateway (Rust) | Updated with Core (managed sidecar) | Ships in the same release, replaced when Core is. |

The headless binaries (core, gateway, cli) have no native updater of their own, so Core also owns the binary
self-update for them (see [Applying an update](#applying-an-update)).

## Desktop first-run check

After a user presses **Get Started** and completes device sign-in, the desktop app opens onboarding on an
update step before asking whether to run locally, use Ryu Cloud, or connect to an existing node. The step
checks the signed-in user's Core verdict, compares the release against the running desktop bundle, and keeps
**Continue** available even when Core or the release service is unreachable. An unknown result is shown as
“Couldn't check for updates,” never as a false “up to date” claim.

The step uses the same Desktop-local **Download updates automatically** preference as App Settings. It defaults
to on. When an eligible update is ready, the action changes to **Install and restart**; Ryu never treats the
download preference itself as permission to install. Browser builds reuse the onboarding code but skip this
step because a web deployment cannot install a Tauri bundle.

## Checking for an update

Three Core routes back the whole system. They are registered in `apps/core/src/server/mod.rs` and each has an
API reference page.

| Endpoint | Purpose |
|---|---|
| [`GET /api/version`](/docs/extend/develop/api-reference/core/health/get_version) | Installed version plus the per-component build list and the running `os-arch` platform. |
| [`GET /api/update/check`](/docs/extend/develop/api-reference/core/health/update_check) | Compares the installed version against the latest GitHub release and returns the verdict. |
| [`POST /api/update/apply`](/docs/extend/develop/api-reference/core/health/update_apply) | Downloads and installs an update for the headless binaries. |

`GET /api/update/check` queries the latest release on the requested channel, compares semver (a malformed tag
parses to `(0,0,0)`, so it never claims to be newer than a real version), picks the best release asset for the
running platform, and returns an `UpdateCheck`:

| Field | Meaning |
|---|---|
| `current` | Currently installed Ryu version. |
| `latest` | Latest published release tag, with a leading `v` stripped. |
| `update_available` | `true` only when `latest` is strictly newer than `current`. |
| `notes` | The GitHub release body, if any. |
| `html_url` | Link to the human-readable release page. |
| `asset` | The release asset matching this platform (`name`, `url`, `kind`, `size`), when one resolved. |

The asset matcher gates by OS first (filename and extension heuristics), then scores an arch bonus for
`x86_64`/`aarch64` and common aliases (`amd64`, `x64`, `arm64`), keeping the highest-scoring asset. The `kind`
is inferred from the extension (`msi`, `exe`, `dmg`, `appimage`, `deb`, `archive`, or `unknown`).

<Callout type="info">
  The check **fails open** for launch safety: a network or API error never blocks the app. Surface clients
  still distinguish “unknown” from a genuine no-update verdict so they do not tell users that they are
  current when the service could not answer.
</Callout>

## Keep working through GitHub outages

GitHub-backed skill taps and Marketplace listings keep the last successful browse result in a short-lived
memory cache and, for the default catalog view, a disk cache. If GitHub or the Marketplace endpoint is
temporarily unavailable, Ryu labels the result as cached and keeps browsing possible. An already-installed
skill can also be retried from its local copy when its recorded catalog identity matches the requested skill.
A first install still fails closed when the bytes cannot be verified or downloaded, so stale data never
turns into an unverified install or silently substitutes a same-named skill from another repository.

## Applying an update

For the headless binaries `POST /api/update/apply` stages the asset and either self-replaces or hands the path
back (`apps/core/src/update/apply.rs`):

- A bare executable on Windows is swapped in place. A running `.exe` cannot be overwritten, so Core renames the
  live binary aside to `<exe>.old`, copies the new binary into the original slot, and reports
  `restart_required`. The `.old` crumb is removed on the next launch by `cleanup_stale_backup()`.
- An OS installer (`msi`, `dmg`, `deb`, `appimage`) is staged to disk and its path returned. The client runs
  the platform installer; Core does not launch GUI installers itself.

The download stages atomically: write to a `.part` file in `~/.ryu/updates/`, then rename into place.

The Electron companion completes its enabled-update path automatically after the signed download: on
Windows it invokes the NSIS updater in silent mode and relaunches the companion, so users do not have to
step through an installer wizard. Windows security policy can still show a UAC consent prompt when the
installation location requires administrator approval; an application cannot safely bypass that OS decision.

The Island bundle itself is also a Core-managed artifact. Its first install and refresh use the global
Download Center and a release checksum, so progress, pause/resume, retry, cancellation, and durable
history are shared with models and sidecars. Island remains stopped while the feature is disabled;
downloading its bundle does not launch it. Desktop does not keep a second direct downloader, so an
older Core that lacks this verified installer must be updated before Island can be installed.

## Update settings by surface

The Tauri app has a device-local **Download updates automatically** preference. It defaults to on and controls
only whether that desktop downloads an eligible app bundle in advance. It does not authorize installation.
After download and signature verification, App Settings and the persistent update notice both offer
**Install and restart**. Turning the preference off changes the first action to **Download update**.

Core and remote-node automatic updates remain a separate policy. Changing the Tauri download preference does
not change whether a server updates its Core or Gateway binaries. The Chrome extension is notify-only because
Chrome owns package installation. Mobile uses its own secure device setting for Expo OTA, and the web app has
no bundled binary toggle because deployments are refreshed by the browser.

<Callout>
  The Tauri app keeps at most one prepared update. The artifact survives an app restart and its signature is
  checked again immediately before installation. An interrupted or invalid download is never offered for
  installation. If a signed feed is unavailable, Ryu keeps working and offers the manual download page.
</Callout>

## Desktop signing

The desktop updater verifies a minisign signature on every downloaded artifact using the public verification
key embedded in the installed app. The private release key stays outside the source repository. A prepared
artifact is verified again immediately before installation, so changing cached bytes makes the update invalid.

<Callout type="warn">
  The installed app trusts a specific release key. If a future release must use a different key, existing
  installations may need a one-time manual reinstall before automatic downloads can continue.
</Callout>

<Callout type="warn">
  A development checkout can verify the prepared-update state, cache validation, and user-facing flow, but it
  cannot install a production desktop bundle. A real installation still requires a newer published artifact
  signed by the release key trusted by the installed app.
</Callout>
