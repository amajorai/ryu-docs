This page continues the store list from [What Is Sealed](/docs/core/encryption-what-is-sealed). For the cipher and key custody, see [Encryption at Rest](/docs/core/encryption-at-rest).

| Store | Sealed now? | Field(s) | Where |
|---|---|---|---|
| Ryu Browser profile | Cookies: yes, with the OS key store. Everything else: no | cookie values | release builds turn on Chromium cookie encryption with the macOS Keychain, Windows DPAPI, or on Linux the Secret Service or KWallet. On Linux without either, Chromium can only obfuscate cookies with a built-in key, and the browser logs a warning. History, site storage, and downloads are not encrypted; the profile is in the app's own data folder (owner-only) and is removed with the app's data |
| Third-party MCP servers you install | No | whatever each tool saves (for example a browser profile or saved sign-in) | these programs store their own state in their usual folders under your home directory; Ryu cannot encrypt it. Remove a tool's saved sign-ins with that tool |
| `gateway.toml` (OS configuration folder) | Yes | every credential leaf: provider `api_key`/`api_keys` (native, compatible, SDK accounts, web search and fetch accounts), Google Cloud TTS and Amazon Polly credentials, `[auth]` client keys and `master_key`, channel bot tokens and secrets, Composio, control-plane, credits, and compression secrets | sealed as `encc:v1:` with the Gateway's derived key by every Core and Gateway writer; non-secret settings stay readable; legacy plaintext is read as-is and sealed in place when the Gateway starts. An external Gateway without the derived key keeps reading a plaintext file, and Ryu adds no new credential to that file until the key is handed over |
| Gateway `audit.db` | Hashed, not encrypted | client keys are stored as a SHA-256 lookup digest plus a 6-character display prefix, never the key itself | the database is owner-only (`0600`); raw keys left by older builds are rehashed, and each existing database is rebuilt once on open so leftover raw key bytes are purged from free space (backups made earlier are not). Request metadata (user, model, token counts, errors) is not encrypted |
| Desktop account vault (signed-in accounts and their session tokens) | Yes | the whole vault | sealed as `enc:v1:` in the data folder's `secrets/` with the desktop's own key from the OS keychain; nothing is kept in the desktop's web storage or `auth.bin` any more. Copies left there by older builds are moved into the sealed file and deleted on first launch |
| Desktop license key | Yes | the key | sealed like the account vault; a key left in `entitlement.bin` by an older build is moved and deleted on first read. The cached plan and trial start date stay in `entitlement.bin` and are not secret |
| `nodes.json` (saved remote nodes) | No | each node's token | the terminal client reads this file directly and cannot reach the desktop's keychain, so tokens stay plaintext. Desktop and the CLI write the file owner-only (`0600`) in an owner-only `state/` folder. A token an earlier Desktop build encrypted is decrypted and written back so the terminal client can use it again (see [the CLI reference](/docs/surfaces/cli/reference)) |
| Desktop CLI setup snapshots | Yes | the copy of each tool's previous config kept for Reset, which can hold that tool's own API keys | sealed with the desktop key; older snapshots are sealed when the CLI setup screen next loads |
| Coding-tool configs Ryu writes the Gateway key into (Claude Code, Codex, Gemini CLI, opencode, Pi, and others) and the Roo Code import file | No | the Gateway key | each tool reads its own file directly, so these stay plaintext. Ryu writes them owner-only (`0600`); remove a key from them with Reset |
| Browser extension account vault and node tokens | Encrypted in the browser | session tokens, node tokens | AES-GCM with a non-extractable key kept in the extension's IndexedDB; see below |
| Web app account vault, license key, and node tokens | Encrypted in the browser | session tokens, license key, node tokens | same browser scheme as the extension. Provider API keys entered in the web app are not kept in the browser at all |
| Island service settings | Yes, where the OS offers a key store | the Core token you enter | sealed with Electron `safeStorage` (macOS Keychain, Windows DPAPI, Linux Secret Service or KWallet); without one the token is kept for the session only. A token Island picks up from `RYU_TOKEN` or the local Core is never written |
| Node control-plane credentials (`secrets/node-control.token`, `bootstrap-ack.token`, and an older `gateway-durable.token`) | Yes | the whole file | sealed as `enc:v1:` with the master key; a plaintext file from an older build is read and sealed in place, and a new credential is refused rather than written in plaintext when no key is available |
| `secrets/gateway-relay.token` | Yes | the whole file | sealed as `encc:v1:` with the Gateway's derived key, because the local Gateway reads it to send diagnostics summaries. A Gateway without the key skips those summaries |
| `secrets/gateway-relay.key` (Core's local inference key) and `secrets/core.token` | Yes | the whole file | sealed as `enc:v1:`; only Core reads them, and the Gateway receives the inference key when Core starts it |
| Gateway `gateway-admin.key` and `gateway-relay.key` (beside `gateway.toml`) | Yes, when the Gateway has a key | the whole file | sealed as `encc:v1:`; print one with `ryu-gateway print-key admin` or `print-key relay`. A Gateway started with no key source at all (no key from Ryu, no `RYU_MASTER_KEY`) keeps them in plaintext, owner-only, and warns at startup |
| Gateway marketplace signing key | Yes, when the Gateway has a key | the private seed | sealed as `encc:v1:`. Without a key the seed is not saved: the Gateway signs with a key that lasts until it stops, and says so. Set `RYU_MARKETPLACE_SIGNING_KEY` for a stable key on servers |
| `secrets/node-auth.token` (the node's owner token) | No | the token | Desktop, the CLI, the MCP bridge, Island, and SDK tools read this file directly and cannot reach the master key, so it stays plaintext, owner-only (`0600`) in an owner-only folder, and is left out of backups and profile copies. Clients that can use `RYU_TOKEN` or pairing do not need the file |
| Local service tokens (screen history, Research engine, Sites) | No | loopback shared secrets | read by shell hooks and helper processes that cannot reach the master key; created owner-only (`0600`). The Sites file exists only while Sites runs |
| Data-folder export (Settings → Storage → Export backup, `ryu-core data-path export`) | Yes | the whole archive, including the key file a file-key node keeps in `secrets/` | encrypted with a passphrase you choose (at least 12 characters; PBKDF2-HMAC-SHA256 key, AES-256-GCM frames), and written owner-only. Ryu does not keep the passphrase, and the backup cannot be restored without it. While an export or restore runs, the unencrypted zip exists only in a temporary file with no name inside the data folder's owner-only `tmp/` (or the system temp folder when restoring to a folder that does not exist yet), never in the folder you save the backup to or restore it from. Exports made by older builds are plain zips and still restore without a passphrase |
| S3 backup staging | Encrypted before upload; plaintext only in unnamed temporary files | the zip of the node, Space, or app being backed up or restored | staged in the data folder's owner-only `tmp/backups/` (not the shared system temp folder). The zip itself lives in a temporary file with no name that the OS removes even if Ryu is killed, and is dropped as soon as it is encrypted, before the upload. Database copies made while snapshotting are deleted as each one is added, and anything an interrupted job left behind is removed when Ryu next starts |
| Node recovery folder (`state/backups/recovered/<job>/`) | No | a full copy of the restored node, with that node's key file in `secrets/` | a node restore creates a separate folder you start with file-key custody, so it holds the source node's key in an owner-only (`0600`) file in an owner-only folder, the same protection as any node that keeps its key in a file. Ryu does not delete it; delete the folder yourself once you have started from it or no longer need it. A half-written folder left by an interrupted restore is removed at startup |
| Workspace handoff patches and bundles (`state/rnp/`) | Yes | the patch and commit bundle a handoff carries between nodes | sealed with the master key while they wait in the sender's staging folder (up to an hour) and the receiver's queue (up to a day); the receiver decrypts one into an owner-only temporary file only for the moment Git applies it. Without a key, a handoff export or upload is refused rather than stored in plaintext |
| `/etc/ryu/core.env` and `gateway.env` on a Linux server install | No | the node's configured tokens and keys | the service manager reads them before Ryu starts; they are root-owned and `0600` |

## Gateway configuration

`gateway.toml` is read and written by both Core and the Gateway, and the Gateway runs as its own
process, so its credentials use a key derived for the Gateway rather than the master key itself:
HKDF-SHA256 of the master key, bound to the Gateway, with a separate `encc:v1:` envelope. When Ryu
starts the Gateway it passes only that derived key, and the Gateway removes it from its environment
before starting anything else. A Gateway run on its own takes that derived key from the
`RYU_SEAL_KEY` and `RYU_SEAL_SCOPE` printed by `ryu-core gateway-seal-env`, or derives it from
`RYU_MASTER_KEY`, so files sealed either way stay readable. Until an external Gateway has the key,
Core refuses to seal a new credential into a file that holds no sealed value yet.

Without a key, plaintext files still
load, but sealed values cannot be read and new credentials are refused rather than written in
plaintext. Account ids are computed from the key itself, so they do not change when a key is
sealed. See [Provider API keys](/docs/security/provider-api-keys) for the threat model.

Gateway chat caches are in-memory only, so no chat content is at rest there.

## Node and Gateway credential files

Credentials Ryu keeps one per file, such as a node's control-plane token or a Gateway key it
generated, are stored as one sealed value. Ryu writes a complete sealed copy and then swaps it in,
so a crash never leaves a partly written or plaintext file, and a file that cannot be opened is an
error rather than a reason to make a new credential. A Gateway reads them with the same derived key
it uses for `gateway.toml`.

On a Linux server install, Core and the Gateway use the master key file in the data folder's
`secrets/` (or `RYU_MASTER_KEY` when you set it in `/etc/ryu/core.env` and `gateway.env`), so both
services open what the other sealed. Anyone who can read that folder as the service user or as root
can read the key too: sealing there protects copies of individual files, not the whole folder.

## App credentials

Apps run as their own processes and never receive the master key. When Ryu starts an app that
stores credentials of its own (an app whose process declares the `crypto:seal` grant: Mail,
Social, Monitors and Dashboards among the built-in apps), it derives a key for that app alone
(HKDF-SHA256 of the master key, bound to the app's id) and passes it to the app's process, which
removes it from its environment before starting anything else; the key is never written to
disk. Other apps receive no key, so the programs they start (experiment code, `gh`, ffmpeg, a
browser) cannot inherit one. An app seals the credentials it stores with that key
in an `encp:v1:` envelope (ChaCha20-Poly1305), so one app cannot read another app's secrets.

An app run on its own derives the same key from `RYU_MASTER_KEY`. Without a key an app still opens
and reads values stored in plaintext by older versions, but it refuses to save a new credential
rather than store it in plaintext.

## Desktop, browser, and Island clients

Ryu Desktop seals the stores only it reads (the account vault, the license key, and CLI setup
snapshots) with its **own** key rather than Core's master key, so reading them at every
launch never prompts for access to another app's keychain entry. That key is created on first use and
kept in the OS keychain under service `ryu`, resolved the same way as the master key:
`RYU_MASTER_KEY` first, then the keychain, then an owner-only file in `secrets/` only where no
keychain is reachable. Once the desktop has saved anything, a locked or unreachable keychain
leaves its encrypted values locked until the keychain is available again: no new key is created.

Without a key nothing is saved: you stay signed in for the session, and Ryu does not fall back to
writing tokens in plaintext. Values encrypted under a desktop key the app used earlier (for
example a key file from a launch on an older version while the keychain was locked) still open
and are encrypted again under the current key. Values in the desktop's web view that an older
version set aside after such a key change are restored automatically once they open: they come
back where nothing has replaced them, are merged where they can be (Prompt Studio test suites and
collaborative documents), and otherwise stay set aside next to the newer value.

The browser extension and the web app cannot reach the OS keychain. They encrypt their stored
tokens with AES-GCM using a key the browser generates as **non-extractable** and keeps in the
site's or extension's IndexedDB. Script can ask the browser to use that key but can never read it.
This protects against a copy of the browser profile's storage files (a backup, disk forensics, a
synced or stolen profile folder) being read outside the browser. It does **not** protect against
code running in the same site or extension, which can decrypt just as Ryu does, or against a full
copy of the browser profile, which carries the key with the data. It is not keychain custody. When a
browser offers no IndexedDB or WebCrypto, tokens are kept for the open tab only.
