---
title: Managed fleet configuration
description: Enroll servers, distribute managed apps, plugins, MCP servers, skills, and rules, and share portable Stack Templates.
---

Ryu organizations can manage a consistent tool stack across cloud-hosted and local servers without opening an inbound administration port. Each enrolled server makes an authenticated outbound connection, verifies a signed desired-state snapshot, applies it through its normal local installers, and reports its actual state back to the organization dashboard.

Enrollment and MCP access are separate. Enrollment binds the server to an
organization for fleet configuration and policy. A local or self-hosted direct
MCP client still needs that server's bearer or a paired token. Desktop's managed
server selector receives a short-lived user JWT and Core narrows it to the
organization, team, or personal server scope. An external MCP client should use
the hosted `/mcp/<node-id>/<agent-id>` URL; the hosted service checks the user's
Better Auth grant and sends Core a short-lived delegation for that server and agent.

## Enroll a server

In Desktop, open **Gateway settings → Workspace → Organization binding** while
the self-hosted server is active. Choose an organization, name the server, and select
**Bind server**. Desktop creates a one-time enrollment code and sends it straight
to Core. The code expires after ten minutes; you do not copy an organization ID,
Fleet URL, or Gateway secret.

Server names are trimmed and must contain 1 to 128 characters.

Enrollment is a two-phase relationship:

- Fleet identity, used for desired configuration and status;
- purpose-separated organization credentials for server control and managed
  inference.

Core first records the enrollment as pending and durably saves the complete
credential set before activation. It activates the server only after the server
acknowledges that the credentials were persisted. Afterward, Desktop shows the
organization name, stable server ID, and **Managed inference ready**.
Those fields come from Core, so they remain visible after Desktop or Core
restarts.

The web **Fleet status** page can also issue the same one-time code for a server
enrollment client. The code still binds Fleet identity and managed inference to
the organization that issued it. Desktop's Workspace card uses the direct flow
above and does not ask you to paste that secret.

Creating or redeeming an organization binding requires the live
`gateway.configure` permission. Organization owners and admins have it by
default. A custom organization role may grant it to another member. A
team-scoped grant applies only to enrollment for that team. People without the
permission can inspect status, but the binding controls stay read-only.

<Callout type="warn">
An enrolled server cannot be moved to another organization by selecting a new one
or issuing another code. Revoke the existing binding first, then use an explicit
rebind flow. This prevents a server from silently changing which subscription it
can spend.
</Callout>

The enrollment does not copy a plan name, balance, or entitlement flag onto the
server. Each managed request resolves the organization from the enrolled relay
credential and checks that organization's current subscription, credits,
budgets, and policy. A binding remains valid when a subscription starts, stops,
or changes tier; access follows the live entitlement.

Revoking a server stops future desired-state downloads. The dashboard shows desired and observed revisions, last contact, compatibility failures, missing setup, and whether a server is using stale last-known-good state.

Fleet revisions are independent from policy configuration revisions. The config-as-code screen shows both counters, while policy rollback continues to affect only policy layers.

## Managed content

The **Managed content** page assigns apps, plugins, MCP servers, and skills at organization, team, project, or user scope. Every assignment is pinned to an exact signed artifact digest.

- **Required** installs the item. It starts disabled unless the assignment explicitly enables it.
- **Optional** makes the item an approved choice without installing it.
- **Blocked** disables the item and removes it from runtime discovery. A blocked user-owned copy and its data remain on disk.

The most specific applicable scope wins unless an ancestor assignment is locked. At the same scope, blocked wins over required, and required wins over optional. Local project folders are mapped to organization projects on each server; local paths never leave the server.

Configuration contains setup-slot references rather than credential values. A required integration that is missing a credential remains disabled and reports **Needs secret**.

## Managed rules

Instruction rules are composed from broad to specific scope and appear in the agent context as a separately labelled organization-managed block. They do not edit a repository's `AGENTS.md` or other files.

Command rules match executable argument prefixes and can allow, prompt, or deny. The built-in hardline safety rules always run first and cannot be bypassed by an organization rule or by turning the ordinary risk scanner off. Project-scoped rules apply only when the current folder maps to that project.

## Offline behavior

An enrolled server caches its last verified snapshot and referenced artifacts. It can use that last-known-good state for up to seven days while offline. After expiry, Ryu retains managed deny and block rules, drops managed allows, and disables managed executable integrations until the server reconnects. User-owned data is not deleted.

## Stack Templates

A Stack Template is a portable list of pinned apps, plugins, MCP servers, skills, rules, project aliases, and setup placeholders. It never contains secrets, account or server identifiers, absolute paths, local URLs, caches, or artifact bytes.

Export a server's current verified stack with:

```bash
ryu stack export ryu-stack.json
```

Imports always show a preview before applying changes. Templates fork by default, so later publisher edits do not silently change an imported organization. A template can be private to named organizations, shared through an unlisted link, or published in Marketplace. Importing a template never transfers access to a private artifact; the destination organization's server ACL must authorize it.

Preview a JSON template at organization scope, then apply the same import after reviewing its conflicts, grants, and missing setup:

```bash
ryu stack import ryu-stack.json --org <organization-id>
ryu stack import ryu-stack.json --org <organization-id> --apply
```

Use `--scope team|project|user --scope-id <id>` for a narrower destination. Marketplace items referenced by a template must first be imported into the destination's managed artifact registry; free and paid items use the same signed-release and organization/server ACL checks. The import copies the verified release into an immutable, organization-signed artifact record without transferring the publisher's credentials or private artifact access.

An imported stack can optionally subscribe to its publisher. **Manual** subscriptions record a newer release for preview and explicit application. **Auto** subscriptions update only records owned by that template import; they stop and report a conflict if the release needs an unavailable artifact or would replace separately managed content. Removing a template import never removes user-created assignments or local data.
