The feature formerly called the **Identity Vault** is now [Ryu Passport](/docs/standalone/passport),
an independently deployable service for per-domain agent identity connections. Passport owns the
tenant stores, encryption, login lifecycle, and credential-consuming HTTP/MCP operations. Core and
the Gateway keep the agent binding, permission, budget, and audit decisions around each read.

Use the [Passport setup guide](/docs/standalone/passport) for a new deployment and the
[Passport API reference](/docs/standalone/passport-api) for its versioned HTTP contract. This page
remains at the historical Core URL so existing bookmarks and links continue to explain the
ownership change.

<Callout type="info">
  Core still exposes its compatibility `/api/identities/*` routes. With `RYU_PASSPORT_URL` set,
  those management operations forward to Passport with a separate administration credential.
  Without remote configuration, Core's embedded `ryu-vault` path remains available for local-first
  compatibility; new service deployments should use Passport as the durable identity owner.
</Callout>

## Ownership

| Concern | Owner | Boundary |
|---|---|---|
| Per-profile, per-domain connection state | Passport | One encrypted SQLite store per configured tenant |
| Login, import, refresh, and provider transport | Passport | Runtime and management bearer contracts |
| Agent/profile binding and tool allowlists | Core | The installed agent's declared profile scope |
| `identity.read`, risk approval, budgets, and audit | Core + Gateway | Checked before a credential-consuming dispatch |
| MCP hosting and Composio/tool integration edge | Connect | Separate from Passport's identity custody |

Passport returns profile and connection metadata only. Sealed state and decrypted credentials never
appear in its API responses, model context, or normal logs.

## The object model

```text
Agent configuration ──binds──▶ Profile (1) ──▶ Connection (N, one per domain)
                                                   │
                                                   └── Passport tenant store
```

| Object | Meaning |
|---|---|
| **Profile** | A grouping key for the domains an agent may use. |
| **Connection** | One domain login with `AUTHENTICATED` or `NEEDS_AUTH` state. |
| **Binding** | The profile IDs saved on an agent; an empty list grants no identity access. |

The connection's durable `status` is separate from its transient `flow_status`. A stale or missing
login stays explicit and leads to a human re-authentication path; it never silently falls back to a
different tenant, profile, or credential source.

## Core compatibility routes

Existing Desktop and Core clients may continue using these routes:

| Method + path | Purpose |
|---|---|
| `GET /api/identities` | List status-only profiles and connections |
| `POST /api/identities/connections` | Create a `NEEDS_AUTH` connection |
| `POST /api/identities/connections/{id}/login` | Begin the configured login flow |
| `GET /api/identities/connections/{id}` | Read status and flow metadata |
| `POST /api/identities/connections/{id}/import` | Seal user-provided state through Passport |
| `DELETE /api/identities/connections/{id}` | Remove the connection |

These are adapters for existing clients, not a second public identity store. The standalone
contract, including runtime-scoped connection metadata and authenticated fetch, is documented in
[Passport API](/docs/standalone/passport-api).

## Governed runtime access

At an identity-consuming tool boundary, the runtime:

1. resolves the calling agent and its bound Passport profiles;
2. asks Passport for status-only metadata and the permitted connection operation;
3. asks the Gateway for the `identity.read` grant and any required risk approval; and
4. lets Passport consume the credential and return only the fetched content or MCP response.

The model supplies the tool request, never the Passport runtime credential. A missing profile
binding, denied grant, unavailable Passport service, or unknown action fails closed or produces an
explicit re-authentication/availability result.

## OAuth and MCP connections

Passport also owns OAuth discovery, PKCE, callback completion, token refresh/revocation, and the
long-lived MCP transport for remote authenticated servers. Core keeps the MCP registry and its
agent-level policy; it receives an opaque local handle rather than a Passport token or provider
secret. See [MCP OAuth custody](/docs/standalone/passport-api#mcp-oauth-custody) and
[authenticated MCP](/docs/extend/develop/extensions/authenticated-mcp).

## What Passport does not do

Passport is not a browser automation engine and does not make a login decision for an agent. A
provider-specific capture surface may supply state through Passport's credential-source seam, but
the runtime must still authorize the identity read. For MCP hosting, Skills, tool execution, and
Composio actions, use [Ryu Connect](/docs/standalone/connect).
