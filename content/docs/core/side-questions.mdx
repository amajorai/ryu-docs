---
title: "Side Questions (/btw)"
description: "A quick question about the current conversation, answered with full context and no tools"
---

A side question lets you ask something quick *about the conversation you are already in* without
starting a new turn or spawning a tool. It is modeled on Claude Code's interactive `/btw` and is
the inverse of a sub-agent: full conversation context, zero tools. The model sees the transcript
and answers once. When the question is asked over a stored conversation, Core keeps the exchange
as a lightweight "side chat" entry tied to that conversation; when the client holds its own
transcript (no Core `conversation_id`), nothing is persisted.

The feature is owned by the built-in `@ryu/side-chats` plugin. The plugin contributes the `/btw`
command and the desktop side-chat feature, and gates the HTTP surface below. Core provides the
generic side-model bridge and conversation-store implementation; disabling the plugin removes the
command and makes these routes unavailable.

Core owns one side-question primitive, `POST /api/btw`, handled by `btw_handler` in
`apps/core/src/server/mod.rs`. It reuses the same single non-streaming gateway call as
[double-check](/docs/core/double-check) (`call_side_model`), so the model call still routes
through the Gateway like every other model call in Ryu.

For how to fire a side question from the composer, see
[Chat](/docs/surfaces/desktop/user-guide/chat). This page documents the primitive.

## What it is

| Property | Value |
|---|---|
| Route | `POST /api/btw` (top-level, not under `/conversations/:id`) |
| Handler | `btw_handler`, `apps/core/src/server/mod.rs` |
| Backing call | `call_side_model` - one non-streaming gateway call |
| Tools | None. The system prompt tells the model it has no tools and cannot run commands, read files, or browse |
| Owner | `@ryu/side-chats` (Core-tier, default-on, disableable) |
| Persistence | A `btw_entries` row keyed to the parent conversation, when a `conversation_id` is supplied. The exchange never becomes chat history |
| Returns | `{ answer, model, id }` |

The route is top-level rather than nested under a conversation because some clients (the CLI and
mobile) hold their own transcript and have no Core `conversation_id` to address.

## Request

The body is a `question` plus a transcript, supplied one of two ways.

| Field | Type | Required | Notes |
|---|---|---|---|
| `question` | string | yes | The side question. An empty/whitespace-only value returns `400` |
| `messages` | array of `{ role, content }` | no | A client-held transcript. The server uses at most the most recent 30 messages |
| `conversation_id` | string | no | A stored Core conversation used when `messages` is absent; the last 30 messages are loaded |

If `messages` is present and non-empty it wins; otherwise Core loads the transcript from
`conversation_id`. If neither is supplied, the side question still answers, it just has no prior
context to draw on. The desktop sends the visible main-chat transcript with the request, including
the latest in-flight user/assistant text, so a side question has the same context the user is
looking at rather than a stale server snapshot.

```json
POST /api/btw
{
  "question": "wait, which provider did we decide on earlier?",
  "conversation_id": "conv_01abc..."
}
```

```json
{
  "answer": "You chose OpenRouter routing the Gemini slug, since there is no direct Google provider.",
  "model": "...",
  "id": "…"
}
```

When the request carried a `conversation_id`, `id` is the persisted side-chat entry (present and
non-null). A request with only a client-held `messages` transcript gets `id: null` and is not
persisted anywhere.

## Persistence

Side questions over a stored conversation are kept in the `btw_entries` table in the same
`~/.ryu/conversations.db` as messages, sealed at rest with the same `FieldCipher` (see
[Encryption at rest](/docs/core/encryption-at-rest)). Each row stores the question, answer, model
and timestamp, keyed to its parent conversation — so it is **not** chat history and never renders
in the conversation timeline, but it can be listed and deleted like one:

| Route | Purpose |
|---|---|
| `POST /api/btw` | Ask a side question; persists a row when `conversation_id` is supplied |
| `GET /api/conversations/:id/btw` | List a conversation's side chats, newest first |
| `DELETE /api/btw/:id` | Delete one side chat |

When the `@ryu/side-chats` plugin is enabled, the desktop Context rail and sidebar both show a
conversation's persisted side chats and can re-open them; the rail's "New side chat" action and
the sidebar rows round-trip through these endpoints (`apps/desktop/src/lib/api/btw.ts`). A
`conversation_id` supplied only for context still answers — it just also leaves a recoverable
entry behind.

## Model and effort resolution

Nothing is hardcoded. The answering model and reasoning effort resolve through a preference chain,
matching the rest of Core's side-model surfaces.

| Setting | Preference | Env fallback | Final fallback |
|---|---|---|---|
| Model | `btw-model` | `RYU_BTW_MODEL`, then `RYU_DEFAULT_LLM_MODEL` | built-in default (`registry::DEFAULT_LLM_MODEL`) |
| Effort | `btw-effort` | `RYU_BTW_EFFORT` | resolver default |

## Behavior and guarantees

- **Side chat, not history.** When asked over a stored conversation, the exchange is persisted as
  a `btw_entries` row (sealed at rest) and can be listed and deleted, but it never becomes a chat
  message. A client-held transcript with no `conversation_id` is answered and forgotten.
- **No tools.** The system prompt instructs the model to answer only from the provided context and
  to say so briefly rather than guess when the answer is not there.
- **Single answer.** One gateway call in, one `{ answer, model, id }` out. There is no streaming and no
  follow-up turn.
- **Context-bounded.** Only the most recent 30 messages (`BTW_TRANSCRIPT_LIMIT`) are included,
  whether the transcript came from the desktop/client or from `conversation_id`.
- **Fails loud on the model.** If the gateway model is unreachable the route returns `502` with
  `side-question model unavailable: ...`.

## Clients

Side questions are wired on all three clients that reach Core, each intercepting `/btw <question>`
before the message is sent.

| Client | Intercept | Transport | Surface |
|---|---|---|---|
| Desktop | `ChatPage` | `lib/api/btw.ts` (passes `conversation_id`) | `components/chat/BtwOverlay.tsx` dialog |
| CLI | `apps/cli` before send | `chat::ask_btw` (posts the held transcript) | ratatui overlay in `ui.rs`, dismiss Space/Enter/Esc |
| Mobile | `apps/native/app/(drawer)/ai.tsx` `onSubmit` | `lib/btw.ts` (posts the `useChat` transcript) | `components/btw-modal.tsx` |

<Callout type="warn">
The route, its `cargo check`, the CLI `cargo build`, and the desktop/mobile `tsc` + biome checks
pass, but the live answer round-trip needs a routable gateway model. It has not been
end-to-end verified against a running model.
</Callout>
