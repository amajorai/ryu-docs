## App record stores (Family, Rooms, UGC, Expenses, Places, Feedback Board, Drafts, Projects, Tuition, Blueprint, News, Subtitles, Teams)

These apps run as separate processes and encrypt their own records with a key that only the app receives from Ryu (derived from your node's master key). Each value is encrypted separately and tied to its record, so a value copied into another record does not decrypt. Each database also records which key encrypted it: started with a different key, an app refuses to change that data instead of mixing keys, and reports it in its health status. A record that cannot be decrypted is left out of lists and counted in the app's health status rather than breaking the page. Records stored by an older version are encrypted when the app starts.

| App | What is encrypted | What stays readable, and why |
|---|---|---|
| Family | people's names and relationships, date labels, list names and items, preferences (every one, not only those marked sensitive), wishlist entries, gift ideas | which account and family a record belongs to, who can see it, the day and month of dates (the reminder sweep reads them), amounts, statuses and timestamps. People and preferences are sorted after decrypting. Reminder notifications name the person and the occasion, and Ryu's notification inbox is not encrypted, so each delivered reminder keeps a readable copy of that name and date label |
| Rooms | room messages, each run's prompt, partial answer and error text, participant names | room ids, statuses, model ids, sharing settings and timestamps. A room still opens when one of its records cannot be decrypted |
| UGC | each creator's record (handles, contact email, payout handle, notes) and display name | campaigns, submissions (post links), metric snapshots and payout amounts, which hold no creator contact details and feed the totals. The roster is searched and sorted after decrypting |
| Expenses | merchant, account, note and amount | date, category and currency, which the filters and sort use. Totals are added up after decrypting |
| Places | place names, addresses, links and notes, member names and notes, list names, the activity feed's copies of those, trips, stops, reservations (including confirmation codes), trip expense titles and checklists, in the node map and in every personal or organization map | coordinates, categories, dates, amounts, ratings and statuses, which the map, routes, budgets and settle-up need, so a copy of a map file still shows where saved places are. Each map is encrypted separately, so a value copied between maps does not decrypt |
| Feedback Board | a request submitter's email, which only the admin view decrypts | titles, bodies, categories, tags and author names are public board content and stay readable so board search works. Comment emails are no longer stored, and those stored by an older version are removed |
| Drafts | each queued prompt and its send error | the send condition, conversation, agent and model ids, folder and timestamps the scheduler checks |
| Projects | each project, its context notes, workers and subscriptions | which account a project belongs to and when a subscription next runs |
| Tuition | subject and skill descriptions, your materials (titles, links and text), each question's prompt, choices and answer key, your answers and their feedback, session summaries, suggested review cards | subject and skill names, mastery and schedule numbers, which the planner and reminders use; accepting a suggested review card turns the skill it names into a readable skill name |
| Blueprint | every plan file: the plan, each revision, annotations and verdicts | plan ids, which name the plan folders. New plans get a random id; a plan created by an earlier version keeps an id made from its title (its first 48 letters and digits), so that part of an older plan's title stays readable |
| Wire (News) | source titles and feed links (a private feed link can carry a token), watch names and queries, story titles, summaries and named entities, briefs | articles, which are copies of public feed items and carry the duplicate checks; read, saved and archived marks. Subscribing to a feed twice or saving two watches with one name is still refused, using keyed fingerprints that only show which entries share a value |
| Subtitles | the transcript and its translation, the video's file name and location, error text | job status, progress, language, format and counts. Downloads are built from the encrypted transcript, so no other copy of a finished subtitle file is kept in the app's data; the file written beside your video is your own export and is not encrypted |
| Groups (Teams) | each team's name and instructions | the member list (agent ids), coordination strategy and lead agent |
| Recursive Language Model | nothing yet | everything it stores: each context (the full text of the documents you load or an agent sends) and each run's question and step-by-step trace are kept unencrypted in the app's data folder. Delete contexts and runs you no longer need |
| Reasoning | nothing yet | each policy file, including the full text of the document it was drafted from, its rules and test cases, is kept unencrypted in the app's data folder. Delete policies you no longer need |

Ryu's notification inbox is not encrypted. Blueprint, Wire and Subtitles notifications therefore name no plan, watch or video, only counts; Meetings notifications name no meeting, and CRM notifications name no deal or follow-up, only the new stage. Open the app to see which one. Family reminders are the exception noted above.

Family, Places, Expenses, Tuition, Blueprint and Wire also offer agent tools through a separate tool process that Ryu starts without the key. Those tools run inside the app itself while it is running; when the app is stopped, they refuse to use encrypted data and ask you to open the app in Ryu, which starts it again.

If one of these apps is updated before Ryu itself, an app whose data was never encrypted keeps working unencrypted until Ryu delivers its key, and its health status says it is waiting for a Ryu update; an app whose data is already encrypted refuses changes until the key is back. Run without Ryu, an app uses the key you provide or creates its own key file in its data folder; keep that file with the data. Older versions cannot read the encrypted data; export before downgrading.

## TypeScript and Python apps (Desktop screenshots, Sites, Forms, Video Studio, MPP, Research, Finetune)

These apps run as separate processes. Sites, Forms, Video Studio, Payments (MPP) and Research encrypt their own records with a key that only the app receives from Ryu, and record which key encrypted them, so a different key never mixes into existing data.

| Data | Encrypted? | What is encrypted | Notes |
|---|---|---|---|
| Desktop app screenshots | Not stored | Not applicable | screenshots of the agent's virtual desktop are captured into a private folder, read, and deleted immediately; they are no longer left in the system temporary folder, and a screenshot an earlier version left there is deleted when the app starts |
| Sites visitor data and Site settings | Yes | visitor uploads and their file names, records saved on the node, each Site's settings including viewer and editor email addresses | published pages, saved versions, visitor ids, record keys, sizes and analytics counts stay readable so pages, lookups and quotas work; upload quotas count the original file size |
| Forms responses | Yes | each response's answers | form definitions, response times and counts stay readable; exports decrypt the answers |
| Video Studio projects | Yes | projects and undo history, transcripts and their search indexes, generation prompts, media analyses | the media library list and export jobs stay readable. Imported and generated media, rendered exports, cached poster frames, imported fonts and LUTs, and shot analysis results (including shot descriptions used by media search) are ordinary files readable only by your account and are **not encrypted**; the video tools read the media directly. Temporary work files of an export or capture, such as its caption file, are deleted when the job ends, and any left by a crash are deleted at the next start |
| Payments (MPP) receipt ledger | Yes | who was paid, the requesting site, the settlement reference | amounts, currencies, networks, statuses and times stay readable so budgets work; wallet keys keep their existing encryption |
| Research campaigns | Yes | campaign goals, attempt hypotheses, descriptions and run logs, proposals and analyses, each campaign's history and results ledger files | names, scores, statuses and times stay readable. Experiment workspaces, including code and version history, are **not encrypted** because experiments run that code directly. Ryu gives the key to the Research app, not to the Research tools agents call: content an agent writes before the app has run is encrypted the next time the app opens, and once data is encrypted the agent tools work only while the app is running |
| Fine-tune adapters and merged models | No | Nothing | the training and inference engines read model weights directly from disk. They are readable only by your account; training checkpoints and export scratch files are deleted when a run ends, and leftovers from an interrupted run are removed at the next start. Dataset files you place in the app's dataset folder are not encrypted. A model trained on private data can repeat parts of it |

Data saved by an earlier version is encrypted the first time the updated app starts. If one of these apps is updated before Ryu itself, an app whose data was never encrypted keeps working unencrypted until Ryu delivers its key, and its status says it is waiting for a Ryu update; an app whose data is already encrypted refuses changes until the key is back. Run without Ryu, an app uses the key you provide or creates its own key file in its data folder; keep that file with the data. Older versions cannot read the encrypted data; export before downgrading.

## Cloud content and personal data, Ryu Connect inbox

Ryu Cloud is adding encryption for message content and personal data in its database, on top of the sealed sign-in credentials described in [Relationship to the Cloud control plane](/docs/core/encryption-at-rest#relationship-to-the-cloud-control-plane). Each value is encrypted with a key specific to one inbox, organization or user and to the kind of record, and is tied to the record it belongs to, so it cannot be moved to another record and still be read. The service holds the keys, so features that need the content keep working; this protects against copies of the database, not against a compromise of the service itself.

The change rolls out in two steps: first every server learns to read encrypted values while still writing readable ones, then new writes are encrypted and older records are converted in the background. Until the second step and the conversion have run, records stay readable in the database. Encrypting a record replaces it in place, so the old readable value also remains, until it ages out or is rewritten, in the database's replication log, in unused space inside its data files, on replica copies (including delayed ones), and in backups and exports taken before the conversion. After the conversion, the operator lets the replication log roll over, compacts or resyncs each copy, and retires older backups and exports.

| Cloud data | Encrypted once rolled out | Stays readable (why) |
|---|---|---|
| Hosted mail messages | subjects, bodies, previews, headers, reply-to, cc and bcc addresses | sender and to addresses (threads and filters), labels, dates, attachment names and sizes, recipient counts and sizes (quotas and storage), and search fingerprints |
| Hosted mail drafts | subjects, bodies, recipients, headers, attachments saved with the draft | send time, status, labels, attachment names |
| Mail event history and saved send responses | the whole payload | event type and time |
| Agent mail addresses, send policies and approvals | held agent sends are drafts, encrypted as above | each agent's address and display name, the addresses each agent has already corresponded with (the send policy compares them), the recipient address an inbound message was routed by, approval reasons and decisions |
| Emails Ryu itself sends you (Account settings, Emails) | not encrypted | recipient address, subject and the rendered message, kept for a year |
| Managed agent sessions | event contents (messages, tool calls and results), agent instructions, session titles and metadata | event types, tool call ids, session status and errors (so sessions can resume), usage |
| Organization audit stream outbox | each queued event | delivery status; the audit log itself keeps its short, redacted details readable so admins can filter it |
| Sign-in sessions, sign-in approvals, email changes, account merges | IP addresses, device descriptions, the email addresses in email-change and merge requests | your account's email address and name, which sign-in looks up directly |
| Waitlist applications, feature waitlist submissions and user stories | (not encrypted) | email address, name, company, role, website, country, and the free-text answers and story you submit |
| Gift recipients and messages, referral invite emails, challenge entries | (not encrypted) | recipient email address and name, gift message, invited email address, entrant name, email address and pitch, and the review note |
| New-mail notifications in your Ryu inbox | (no message content is kept) | a generic title and the inbox name; the notification and its email no longer include the subject or sender, and it is removed when the message is deleted |

Search in hosted mail uses keyed fingerprints of words instead of the words. Each inbox has its own fingerprints, so the same word looks different in two inboxes; within one inbox they show which messages share a word. Search matches whole words in subjects, names, addresses and the start of each message body. Sender and recipient addresses stay readable, so a part of an address (such as a domain) still matches. Raw incoming messages and attachment files are kept in cloud storage that is encrypted by the storage provider.

Text that only looks like encrypted data, such as an incoming subject that starts with an encryption prefix, is always stored encrypted or marked as ordinary text, so it is never mistaken for encrypted data. A record that cannot be decrypted is shown without its content in mail lists instead of breaking the list. The fingerprints that detect a repeated send or agent request, and those that match a sent agent message with the agent provider, are keyed per organization or user, so they cannot be used to confirm a guessed message.

The Ryu Connect event inbox encrypts each pending webhook event with the operator's key (`RYU_CONNECT_DATA_KEY`), tied to the tenant and delivery. Without that key the event inbox and trigger delivery stay off; set the key before upgrading a deployment that delivers triggers (see [Ryu Connect](/docs/standalone/connect)).
