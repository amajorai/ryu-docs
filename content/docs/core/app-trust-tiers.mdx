A plugin's trust tier, its fresh-install seeding, and whether Core can remove it are all decided by
constants in Core, never by the manifest. For the manifest file and the install, enable, update, and
uninstall operations, see [App Manifest and Lifecycle](/docs/core/app-manifest-lifecycle).

## Two-tier registry

A plugin's trust tier is **derived from membership** in a constant, never asserted by a manifest
field, so a plugin cannot promote itself. The lists live in `apps/core/src/plugins/builtins.rs`.

| Tier | Meaning |
|---|---|
| `core` | A reviewed capability tier listed in `CORE_PLUGINS`. It may be marketplace-installed; the tier does not mean the package is embedded in Core |
| `community` | Everything else, including ordinary installed packages. It requires the relevant approved Gateway grants |

A subset of Core plugins is seeded enabled on a fresh install (`CORE_PREINSTALLED` in
`apps/core/src/plugins/builtins.rs`). It includes the local engine (`@ryu/engines`), the durable
workflow engine (`@ryu/durable`), the four default tool apps (`@ryu/ghost`, `@ryu/shadow`,
`@ryu/spider`, `@ryu/agentbrowser` - see [Default tool apps](#default-tool-apps-auto-seed)), the
chat turn-hook plugins (`@ryu/goal`, `@ryu/proof`, `@ryu/double-check`), and the pre-turn prompt
improver (`@ryu/auto-expand`). The constant holds the full list.

Ids are the scoped manifest `id` (for example `@ryu/engines`). The seed runs once at startup and
respects user choice: it acts only when there is no prior record for that plugin, so a later
disable survives a restart (`main.rs` pre-installed seeding).

The opt-in Core plugins (`@ryu/firewall`, `@ryu/routing`, `@ryu/sandbox`, `@ryu/predict`) are
Core-tier but excluded from the pre-installed set because they change Gateway, sandbox, or capture
behaviour.

## Default tool apps auto-seed

Ghost, Shadow, Spider, and Agent Browser are the default tool apps. Their manifest ids
are in `CORE_PLUGINS` and the pre-installed policy (`apps/core/src/plugins/builtins.rs`). The
compiled system manifests are available from Core immediately; ordinary official packages are
fetched from the signed marketplace package and then installed and enabled automatically on a fresh
install.

| App | Tool | Cross-platform | Reaches the web |
|---|---|---|---|
| `ghost` | Desktop automation (29 tools) | yes (Win/mac/Linux) | no |
| `shadow` | Screen and audio capture + semantic memory | yes (Win/mac/Linux) | no |
| `spider` | Web crawler (Rust `spider-rs/spider`) | yes | yes |
| `agentbrowser` | Web browsing (npx-launched MCP server) | yes | yes |

The seeded record is a **governance shell**. Ghost and Agent Browser declare `runnables: []`
because their tools come from their own MCP provider (Ghost through Core's MCP registry, Agent
Browser as an npx MCP server), so the record never double-lists those tools. Shadow and Spider
declare `tool` runnables that call their own process. Enabling the record makes each one a
governed app that you can disable; the tool process still runs through its own sidecar or MCP
lifecycle. Ghost, Shadow, Agent Browser, and Browser are the compiled **system** manifests; Spider is
Core-tier and pre-installed but remains an installable marketplace package.

<Callout type="info">
Because the run path is the sidecar/MCP provider, not the plugin record, the tool process still has
to be installed and started on its own (`POST /api/setup/:name/install`,
`POST /api/sidecar/:name/start`). The auto-seeded record makes the app show as installed; it does not
download the tool binary by itself. See the Ghost/Shadow note under
[Built-in and system manifests](#built-in-and-system-manifests).
</Callout>

## Built-in and system manifests

**Built-in** and **System** answer different questions. Built-in means the manifest bytes are in the
production Core distribution (`BUILTIN_MANIFESTS`), so Core can validate and project the package
without downloading its manifest from the marketplace. It does not mean the package is seeded or
enabled. **System** means Core refuses to uninstall the plugin: it is required for Core, a
sidecar-backed system component, or part of the `CORE_PREINSTALLED` seed (which would re-add a
removed record on the next boot). The Store and the installed list derive the label from that same
uninstall rule, so a System plugin never offers **Remove** and every plugin that cannot be removed
reads System. A package may be built-in without being system, and a system package may still
arrive through the signed marketplace install path.

The rest of the official catalog is not compiled into Core: its signed package is downloaded from
the Ryu Marketplace when installed.

| Manifest source (marketplace paths are in `amajorai/ryu-marketplace`) | What it declares |
|---|---|
| `plugins/plugins/ghost/manifest.json` | Ghost desktop-automation MCP tool |
| `plugins/plugins/shadow/manifest.json` | Shadow screen and audio capture + semantic memory |
| `plugins/plugins/agentbrowser/manifest.json` | Agent Browser MCP tool |
| `apps-store/browser/manifest.json` | Chromium sidecar surface (`@ryu/browser` app) |

Official marketplace packages such as Spider, Exa, policies, engines, and app companions use the
same manifest validation and lifecycle after installation, but their manifest and code files live
under the installed package directory rather than inside the Core binary.

<Callout type="warn">
Ghost and Shadow are **cross-platform** and **sidecar-managed**. Their lifecycle is sidecar-based
(`POST /api/setup/:name/install` to install, `POST /api/sidecar/:name/start|stop` to run), not the
`PluginStore` install/enable path. When the sidecar is not installed or running, Desktop shows an
unavailable state.
</Callout>
