This page covers access to managed cloud computers in a [Fleet](/docs/core/managed-fleet) organization.

## SSH keys

New managed cloud computers wait for SSH setup before provisioning. Every setup creates
a fresh random key for that cloud computer; SSH keys are never derived from Ryu's master encryption key.
Open the cloud computer details in your organization, choose **Generate SSH key**, download the private
key, and confirm that you saved it. The key is generated in your browser. Ryu
receives the public key and installs it for the cloud computer's root account.

You can optionally protect the downloaded SSH key with a passphrase before
generating it. This passphrase protects the key file itself. Your SSH client may
ask for it when connecting. Ryu never receives or resets it.

Private-key backup is off by default. You can choose **Keep an encrypted backup
with Ryu** and supply a separate passphrase of at least 16 characters. Your browser
encrypts the key before uploading it. The passphrase is never sent to Ryu. To
download the key again, select **Unlock recovery backup** and re-verify your account,
then enter that passphrase in the cloud computer's SSH access card; decryption
happens in your browser. Each release of the encrypted copy is recorded in the
organization audit log. Ryu cannot reset a forgotten backup passphrase.

**Delete encrypted backup** removes the saved encrypted copy. Your downloaded key
continues to work, and the cloud computer's authorized public key stays installed. Normal
infrastructure backup retention may retain older encrypted copies. Without your
downloaded key or a usable encrypted backup, Ryu cannot recover that private key.

Connect using your downloaded file and the cloud computer's public IP address. On macOS
or Linux, restrict the file permissions with `chmod 600` before using it with
`ssh -i`. Existing cloud computers are labelled **Existing cloud computer**. Generate and save an owner
key there, then choose **Download owner setup script**. Run that script on the cloud computer
from your own existing root session. It adds the public key and installs the same
local update service used by new cloud computers. Ryu does not log in or run this migration,
and the page keeps showing **Owner setup required** because it cannot verify your
manual installation. The script preserves existing authorized keys; review them
and remove any access you do not own. When handing a cloud computer to another owner, rotate SSH keys on it:
transferring an organization binding does not revoke downloaded keys.

### Personal keys for organization members

A cloud computer administrator can opt into **Allow personal SSH keys** in the cloud computer's
organization SSH settings. Each allowed member can then opt in on their device
and generate a separate key for this cloud computer. Generation starts a private-key
download. You can optionally retain a passphrase-protected copy in this browser.
Local retention requires protecting the key file with a passphrase; that
passphrase is never saved. Browser storage is not an operating-system SSH agent
or a cross-device backup. Keep the downloaded file safe.

Each member receives a separate Linux login without sudo. Access requires current
organization permission to view the cloud computer and matching team or personal scope.
Public-key enrollment remains **Pending** until the cloud computer confirms installation.
New cloud computers install the local access service during provisioning. Existing cloud computers
need an owner to install it through their existing root session.

The cloud computer checks current authorization before accepting a new personal SSH login.
Revoking a personal key, disabling personal SSH access, or losing organization
access blocks new logins. Revocation does not terminate an already-open shell.
Enabling this feature delegates authorization to Ryu's organization identity and
permission service. It does not provide a cryptographic guarantee against a
compromised control plane or trusted software update.

Opening a cloud computer in the Ryu app continues to authenticate with your signed-in
account and the cloud computer's organization, team, or personal permissions. Downloading
an SSH key does not silently install it into your computer's SSH agent. To open
a shell, use your personal Linux username and downloaded key in an SSH client.

### Recovery with Shamir shares

You can choose **Shamir recovery** instead of a passphrase-encrypted backup.
Set the total number of shares, the minimum needed for recovery, and how many
Ryu retains. For example, with 10 total shares and a minimum of 5, any 5 distinct
shares recover the key. Ryu may retain 0 to 4 shares in that example, so its
allocated shares alone cannot recover the key. Shares held by different Ryu
servers still count together.

The browser encrypts the key file with a fresh random encryption key and splits
that encryption key. Download the customer recovery kit and distribute its
individual shares to separate trusted people or locations. Keeping the entire
kit together means one holder may have enough shares to recover the key.
Ryu stores the encrypted backup and only its chosen subset of shares. Accessing
stored recovery material requires credential re-verification.

Recovery combines enough distinct shares on your device. It reconstructs the
key file locally; it is not joint approval or threshold signing for every login.
If the file also has an SSH passphrase, that passphrase is still required to use
it. Duplicate, mixed, or damaged shares cannot be used for recovery. Deleting a
backup does not invalidate previously downloaded copies or shares.

## Updates without operator SSH access

New managed cloud computers start from plain Ubuntu 24.04 and keep themselves patched.
Every step runs on the cloud computer itself, so routine updates do not require Ryu to
hold your SSH key. Cloud computers run on UTC, and the nightly sequence is:

| Time (UTC) | What happens |
| --- | --- |
| About 01:30 | The package lists refresh. |
| About 02:00 | Unattended upgrades install Ubuntu security updates, including kernel updates. Services that still use a replaced library are restarted automatically. |
| About 03:00 | The cloud computer checks for a new stable Ryu release. |
| 04:30 | The cloud computer reboots, but only if an installed patch requires a reboot. |

Each step can start up to 30 minutes after its listed time. Ryu also checks for releases
at 09:00, 15:00, and 21:00 UTC, but these extra checks install only security releases.
The schedule survives reboots, and checks missed while the cloud computer was off run
after it starts.

The local update service installs only signed stable releases and never moves to an
older version. It checks the release's signed checksum list, refuses any release that
fails the check, and verifies each binary before replacing anything. It then restarts
services, checks that Core starts, and restores the previous binaries if the new
release fails to start. A release that failed this check is remembered and skipped, so
it does not restart services again, until a newer release is published.

A signed release can also update the Bun runtime that Ryu's sidecars use, and only moves it to a
newer version.

<Callout type="warn">
Release signing is not enabled yet. Until it is, cloud computers check for new Ryu releases and
report them, but do not install them automatically. Ubuntu security updates are not affected and
still install nightly.
</Callout>

Ryu rolls out routine releases in stages. Each cloud computer belongs to a fixed group
that installs a release 0, 1, or 2 days after it is published, and installs only during
the 03:00 UTC check. A release can therefore take up to three days to reach every cloud
computer. Security releases skip the stages and install at the next check, usually
within about six hours of publication.

The **Security updates** row on the cloud computer's server page shows the latest patch
report: **Up to date**, **Reboot pending**, the number of security updates still pending,
or **Security status unavailable**. When Ryu's own automatic updates are off, an
additional **Ryu auto-updates disabled** badge appears beside that state, so a pending
reboot or pending security updates are never hidden by it. The row also shows when the cloud computer last checked
in and when its automatic OS update job last ran. That job runs daily even when there is
nothing to install, so use the pending count to see whether updates are still waiting.
Cloud computers report about every six hours,
and a report more than a day old is marked **No recent report**. The row is read-only.

The cloud computer owner can turn off Ryu's local automatic updates over SSH by creating
the file `/etc/ryu/disable-auto-updates`. The cloud computer then keeps reporting that
updates are disabled, and from then on the owner is responsible for keeping it patched.
Other ways of stopping updates, such as disabling the update timer, are not reported, and
the row keeps showing the last update result.

<Callout type="warn">
Owner-held SSH keys remove Ryu's custody of your plaintext SSH key. They do not
make a managed VM inaccessible to its infrastructure operator. Ryu still manages
the Hetzner project, whose recovery and disk controls can provide access to server
data. Ryu's application identity services and published updates remain trusted
parts of the system. This feature is not a promise of provider-independent data
encryption.
</Callout>
