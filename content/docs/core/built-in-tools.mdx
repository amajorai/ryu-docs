This page is the reference for the **built-in tool servers** — the tools that ship with Core and need
no registration. Every tool has a fully-qualified id of the form `<server>.<tool>` (for example
`spider.crawl`), and that id is the allowlist key end to end: you grant it, you test it, and the
agent calls it by it. See [MCP registry](/docs/core/mcp-registry) for how servers register and the
per-agent allowlist, and [Unified tool catalog](/docs/core/unified-tool-catalog) for the search and
governance layer on top.

## The always-on built-ins

These are Core-tier reserved providers — compiled in, always listed, dispatched by a name-matched
arm. They are the "batteries included" of the tool surface:

| Server | Tools | What it does |
|---|---|---|
| `web_fetch` | `web_fetch.get` | Authenticated web fetch over HTTPS. Injects the user's [Identity Vault](/docs/core/identity-vault) session for the URL's host server-side (acts as the user; the credential never reaches the model) |
| `search_conversations` | `search_conversations.search` | Semantic search over the user's past chat messages. Backed by the message index; see [Search and recall](/docs/surfaces/desktop/user-guide/search-and-recall) |
| `threads` | `create_thread`, `list_threads`, `read_thread`, `send_message_to_thread`, `set_thread_title`, `set_thread_pinned`, `set_thread_archived`, `fork_thread` | Coordinator threads: spin up and manage worker threads, each running in its own git worktree. See [Coordinator threads](/docs/core/coordinator-threads) |
| `delegate` | `delegate.fanout` | Fan out independent subtasks to sub-agents that run in parallel in a clean context, returning all results in one call. Ephemeral — for durable workers use `threads`. See [Delegation](/docs/core/delegation) |
| `agent_control` | `agent_control.set_active_target` | Select the active agent target for a governed operation; the host still applies identity and approval checks |
| `orchestrator` | `orchestrator.discover_agents` | List the agents available to delegate to (id, name, description) so an orchestrator can find the right specialist before handing it a subtask via `delegate.fanout` |
| `skills` | `skills.search`, `skills.load`, `skills.author` | Discover, load, and (opt-in) author Agent Skills on demand. Progressive disclosure: search is always on, author is gated. See [Skills catalog](/docs/core/skills-catalog) |
| `sandbox` | `sandbox_create`, `sandbox_destroy`, `sandbox_exec`, `sandbox_run` | Run a selected execution backend with default-deny capabilities. The server name is retained for compatibility; see [Execution backends](/docs/core/sandbox) |
| `notify` | `notify.desktop` | Show a native desktop notification |
| `channel` | `channel.send` | Post a message to a Slack/Discord incoming-webhook URL |
| `ui` | `ui.render` | Render a rich interactive UI inline in the chat from a JSON render spec, using the app's own components |
| `artifact` | `artifact.create`, `artifact.render` | `create` saves a generated file into a Space (default the Artifacts space); `render` draws an artifact card (code file, page, diagram, Space doc, database) inline in the chat with Open / Open-in-tab affordances |
| `spaces` | `list_spaces`, `list_documents`, `search`, `create_space`, `rename_space`, `create_page`, `create_file`, `attach_space`, `detach_space` | Read and manage the Spaces available to the calling agent. Reads are owner/visibility scoped; creating, uploading, renaming, attaching, and detaching are human-approved mutations when approval mode is `smart` or `manual` |

### Generative UI formats

`ui.render` uses Ryu's native `json-render` format by default: a flat `{ root, elements }` tree
from the closed component catalog. Set `"format": "a2ui"` to pass an A2UI v0.9/v0.9.1
envelope, message array, or `{ "messages": [...] }`. Ryu maps the supported A2UI basic-catalog
components into the same native components and preserves data-model bindings and server actions.
JSONL streams are also accepted when the A2UI messages arrive as newline-delimited JSON.

Unsupported A2UI components appear as inert notices. A2UI `functionCall` expressions and local
actions are not executed. One `ui.render` card represents one A2UI surface.

AG-UI is an agent-to-frontend event transport rather than a component format; it belongs at the
agent/event integration boundary. MCP Apps and `ui://` resources are sandboxed app widgets and
remain a separate rich-app surface rather than being converted into native Agent UI components.

### Builders and self-build

These built-ins let an approved agent inspect and create durable Ryu definitions. They are listed
explicitly because they are easy to miss when searching only the always-on server table:

| Server | Tools | What it does |
|---|---|---|
| `ryu_self_build` | `scaffold_runnable`, `install_app`, `write_ryu_json`, `write_tool`, `verify_tool`, `install_tool` | Create, validate, and install a runnable, app, or tool package. Writes remain subject to the active approval policy |
| `agent_builder` | `get_agent`, `configure_agent`, `create_agent`, `create_agent_team` | Inspect and author agent definitions and teams |
| `workflow_builder` | `get_workflow`, `create_workflow`, `configure_workflow` | Inspect and author workflow definitions |
| `dashboard_builder` | `get_dashboard`, `create_dashboard`, `configure_dashboard` | Inspect and author dashboard definitions |

Builder tools may be absent in a restricted client or test context even though their Core contract
exists. Check the live tool catalog before calling them, and treat generated definitions as
untrusted input until validation and approval complete.

### End-of-turn result cards

`ui.render` and `artifact.render` place their result inline by default. Set
`"placement": "turn-end"` when the result should remain as a completed card at the end of the
assistant turn, after tool work has finished. This is useful for a release summary, a decision,
or a link the user is expected to open later. JSON UI cards can use the catalog's `Card`,
`LinkPreview`, `Link`, and `Button` components; artifact cards keep their normal **Open** and
**Open in tab** actions.

The card is reconstructed from the saved tool part when the conversation is reopened. Keep
untrusted URLs in the built-in link or artifact fields so the client can apply its normal safe-URL
handling.

## Swappable capability facades

The four swappable layers reserve a server name each. The tool **names stay the same**; which
provider serves them is selected in the layer picker. The capability catalog answers whether a
layer can actually serve a call today.

| Server | Tools | What the verbs do |
|---|---|---|
| `web` | `web.search`, `web.extract`, `web.crawl` | Search, extract, and crawl. The provider is selected in the layer picker |
| `browser` | `browser.navigate`, `browser.snapshot`, `browser.tabs`, `browser.click`, `browser.type`, `browser.screenshot`, `browser.scroll` | Drive a real browser (local Chromium or a cloud browser provider) |
| `computer` | `computer.capture`, `computer.click`, `computer.type`, `computer.key`, `computer.scroll`, `computer.focus_app` | Screen perception + input control through the selected desktop-control provider |
| `memory` | `memory.search`, `memory.store`, `memory.context`, `memory.sync`, `memory.forget` | Durable fact memory. The built-in store is always available; `context` and `sync` are opt-in bridges |

<Callout type="info">
  The facade verbs are provider-neutral on purpose: a declarative provider tool cannot branch between
  routes, so the contract keeps one stable verb per capability and the bound provider fills in the
  rest. The `browser.tabs` / `browser.navigate` ids are how you learn a `tab_id` to re-point; other
  browser verbs accept an optional `tab_id` (omit for the active tab) but never invent one.
</Callout>

### Provider slots and availability

The facade follows the provider-slot pattern used by Hermes: the agent sees stable capability verbs,
while a provider supplies the implementation behind them. Hermes has separate backend families for
web search/extraction, browser control, memory, image generation, video generation, speech
transcription, and context engines. Ryu does not claim to implement all of those families. Its
current host-owned slots are `web.search`, `web.extract`, `web.crawl`, `browser.control`,
`computer.control`, and `memory`; other provider types remain ordinary plugin or app contributions.

Ryu keeps three states separate:

| State | Meaning |
|---|---|
| Implemented | Core owns the stable facade contract and can dispatch a verb when a provider is bound. |
| Discoverable | A manifest or catalog entry advertises a provider or backend family, but it is not necessarily enabled or runnable on this node. |
| Provider slot | A generic capability seam that a plugin may implement; it is not a promise that a remote service, sidecar, credential, or device is present. |

The capability catalog reports enabled providers, installable-but-disabled providers, the current
bound provider, and whether a provider serves verbs or a brokered route. A row being discoverable
does not grant access, and a provider being available does not bypass its manifest permissions,
agent allowlist, approval mode, or external service requirements.

## Sidecar- and key-backed built-ins

These are real config-file servers (or plugin-declared servers) that degrade gracefully when their
backend is absent:

| Server | Tools | Backend / availability |
|---|---|---|
| `ghost` | ~29 `ghost.*` tools (`ghost.ghost_click`, `ghost.ghost_type`, `ghost.ghost_hotkey`, `ghost.ghost_scroll`, `ghost.ghost_focus`, `ghost.ghost_annotate`, `ghost.ghost_run`, `ghost.ghost_read`, `ghost.ghost_screenshot`, …) | Desktop automation: screen perception + input control. Managed by the installed `ghost` sidecar and backed by the [`@ryu/ghost`](/docs/plugins/ghost) plugin |
| `shadow` | `shadow.search`, `shadow.semantic_search`, `shadow.timeline`, `shadow.recent_context` | Search everything Shadow has captured (screen text, audio transcripts, input). Routed through the authenticated Shadow sidecar bridge and declared by the [`shadow`](/docs/plugins/shadow) plugin |
| `spider` | `spider.crawl` | Web crawling / scraping. Shells out to the `spider` binary; degrades gracefully when not installed |
| `exa` | `exa.search`, `exa.free_search`, `exa.find_similar` | Neural web search. Requires the provider's configured credentials; degrades gracefully when unavailable |
| `composio` | `composio.<slug>` | Hosted catalog of third-party actions. Searchable, never listed; dispatched by the `composio.` id prefix. See [Unified tool catalog](/docs/core/unified-tool-catalog) |

<Callout type="warn">
  Ghost and Shadow are cross-platform and many built-ins are opt-in or require a sidecar/key. A
  server that fails to start is logged and skipped, so one unavailable built-in never hides the rest.
</Callout>

### Spaces access

The Spaces provider derives the target agent and user from the host conversation; an agent cannot
choose another agent id to mutate. It can list and search only Spaces it can read, and it can create
pages or files only in a Space it owns. A shared/system Space can be used as an artifact destination
when the operation explicitly allows it, but it cannot be renamed by an agent.

## App and core-api tools

Two further `kind`s join the built-ins in the catalog without being reserved servers:

| Server segment | Source | Notes |
|---|---|---|
| `app` | A plugin tool exposed as a Runnable | The synthetic `app` server segment; declarative app tools (http, inline Deno, alias) land here, while `command` tools get their own kind |
| `core-api` | A Core HTTP endpoint exposed as an agent-drivable tool | Derived from Core's own OpenAPI document, so an agent can drive Ryu itself |

## Allowlisting by id

Because the id is `<server>.<tool>`, an allowlist entry of `exa` grants every Exa tool while
`exa.search` grants just one. Two paths are deliberately stricter and match the fully-qualified id
**only** (no bare-name or server fallback): Composio (`composio.<slug>`) and `app.`-namespaced app
tools — this closes a cross-plane allowlist bypass where a broad server-name entry could reach a tool
the author never intended. See [MCP registry](/docs/core/mcp-registry#the-per-agent-allowlist).
