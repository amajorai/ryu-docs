This page is the reference for the **built-in tool servers** — the tools that ship with Core and need
no registration. Every tool has a fully-qualified id of the form `<server>__<tool>` (for example
`spider__crawl`), and that id is the allowlist key end to end: you grant it, you test it, and the
agent calls it by it. See [MCP registry](/docs/core/mcp-registry) for how servers register and the
per-agent allowlist, and [Unified tool catalog](/docs/core/unified-tool-catalog) for the search and
governance layer on top.

## The always-on built-ins

These are Core-tier reserved providers — compiled in, always listed, dispatched by a name-matched
arm. They are the "batteries included" of the tool surface:

| Server | Tools | What it does |
|---|---|---|
| `web_fetch` | `web_fetch__get` | Authenticated web fetch over HTTPS. Injects the user's [Identity Vault](/docs/core/identity-vault) session for the URL's host server-side (acts as the user; the credential never reaches the model) |
| `search_conversations` | `search_conversations__search` | Semantic search over the user's past chat messages. Backed by the message index; see [Search and recall](/docs/desktop/user-guide/search-and-recall) |
| `threads` | `create_thread`, `list_threads`, `read_thread`, `send_message_to_thread`, `set_thread_title`, `set_thread_pinned`, `set_thread_archived`, `fork_thread` | Coordinator threads: spin up and manage worker threads, each running in its own git worktree. See [Coordinator threads](/docs/core/coordinator-threads) |
| `delegate` | `delegate__fanout` | Fan out independent subtasks to sub-agents that run in parallel in a clean context, returning all results in one call. Ephemeral — for durable workers use `threads`. See [Delegation](/docs/core/delegation) |
| `orchestrator` | `orchestrator__discover_agents` | List the agents available to delegate to (id, name, description) so an orchestrator can find the right specialist before handing it a subtask via `delegate__fanout` |
| `skills` | `skills__search`, `skills__load`, `skills__author` | Discover, load, and (opt-in) author Agent Skills on demand. Progressive disclosure: search is always on, author is gated. See [Skills catalog](/docs/core/skills-catalog) |
| `sandbox` | `sandbox_create`, `sandbox_destroy`, `sandbox_exec`, `sandbox_run` | Run WASM/WASI modules with default-deny capabilities. Compiled-in wasmtime, toggleable; only available with the `sandbox-wasmtime` feature. See [Sandbox](/docs/core/sandbox) |
| `notify` | `notify__desktop` | Show a native desktop notification |
| `channel` | `channel__send` | Post a message to a Slack/Discord incoming-webhook URL |
| `ui` | `ui__render` | Render a rich interactive UI inline in the chat from a JSON render spec, using the app's own shadcn components |
| `artifact` | `artifact__create`, `artifact__render` | `create` saves a generated file into a Space (default the Artifacts space); `render` draws an artifact card (code file, page, diagram, Space doc, database) inline in the chat with Open / Open-in-tab affordances |

## Swappable capability facades

The four swappable layers reserve a server name each. The tool **names stay the same**; which
provider serves them is selected in the layer picker. `GET /api/capabilities` is the endpoint that
answers whether a layer can actually serve a call today.

| Server | Tools | What the verbs do |
|---|---|---|
| `web` | `web__search`, `web__extract`, `web__crawl` | Search, extract, and crawl. The provider (Exa, Tavily, Spider, …) is selected in the layer picker |
| `browser` | `browser__navigate`, `browser__snapshot`, `browser__tabs`, `browser__click`, `browser__type`, `browser__screenshot`, `browser__scroll` | Drive a real browser (local Chromium or a cloud browser provider) |
| `computer` | `computer__capture`, `computer__click`, `computer__type`, `computer__key`, `computer__scroll`, `computer__focus_app` | Screen perception + input control through the selected desktop-control provider |
| `memory` | `memory__search`, `memory__store`, `memory__forget` | Durable fact memory. The built-in store is always available; an external provider can be selected alongside it |

<Callout type="info">
  The facade verbs are provider-neutral on purpose: a declarative provider tool cannot branch between
  routes, so the contract keeps one stable verb per capability and the bound provider fills in the
  rest. The `browser__tabs` / `browser__navigate` ids are how you learn a `tab_id` to re-point; other
  browser verbs accept an optional `tab_id` (omit for the active tab) but never invent one.
</Callout>

## Sidecar- and key-backed built-ins

These are real config-file servers (or plugin-declared servers) that degrade gracefully when their
backend is absent:

| Server | Tools | Backend / availability |
|---|---|---|
| `ghost` | ~29 `ghost__*` tools (`ghost__ghost_click`, `ghost__ghost_type`, `ghost__ghost_hotkey`, `ghost__ghost_scroll`, `ghost__ghost_focus`, `ghost__ghost_annotate`, `ghost__ghost_run`, `ghost__ghost_read`, `ghost__ghost_screenshot`, …) | Desktop automation: screen perception + input control. Spawned per request as `~/.ryu/bin/ghost mcp`. Cross-platform; unavailable until the `ghost` sidecar is installed. Backed by the [`@ryu/ghost`](/docs/plugins/ghost) plugin |
| `shadow` | `shadow__search`, `shadow__semantic_search`, `shadow__timeline`, `shadow__recent_context` | Search everything Shadow has captured (screen text, audio transcripts, input). HTTP to the Shadow sidecar through Core's authenticated `/api/shadow/*` proxy. Declared by the [`shadow`](/docs/plugins/shadow) plugin |
| `spider` | `spider__crawl` | Web crawling / scraping. Shells out to the `spider` binary; degrades gracefully when not installed |
| `exa` | `exa__search`, `exa__free_search`, `exa__find_similar` | Neural web search. HTTP, BYOK via `RYU_EXA_API_KEY`; degrades gracefully when the key is absent |
| `composio` | `composio__<slug>` | Hosted catalog of third-party actions. Searchable, never listed; dispatched by the `composio__` id prefix. See [Unified tool catalog](/docs/core/unified-tool-catalog) |

<Callout type="warn">
  Ghost and Shadow are cross-platform and many built-ins are opt-in or require a sidecar/key. A
  server that fails to start is logged and skipped, so one unavailable built-in never hides the rest.
</Callout>

## App and core-api tools

Two further `kind`s join the built-ins in the catalog without being reserved servers:

| Server segment | Source | Notes |
|---|---|---|
| `app` | A plugin tool exposed as a Runnable | The synthetic `app` server segment; declarative app tools (http, inline Deno, alias) land here, while `command` tools get their own kind |
| `core-api` | A Core HTTP endpoint exposed as an agent-drivable tool | Derived from Core's own OpenAPI document, so an agent can drive Ryu itself |

## Allowlisting by id

Because the id is `<server>__<tool>`, an allowlist entry of `exa` grants every Exa tool while
`exa__search` grants just one. Two paths are deliberately stricter and match the fully-qualified id
**only** (no bare-name or server fallback): Composio (`composio__<slug>`) and `app__`-namespaced app
tools — this closes a cross-plane allowlist bypass where a broad server-name entry could reach a tool
the author never intended. See [MCP registry](/docs/core/mcp-registry#the-per-agent-allowlist).
