The scheduler is Core's always-on tick loop. It fires persisted jobs on a cron expression or a
fixed interval and runs a workflow, an agent prompt, an app's own scheduled job (such as a
website-monitor check), a quest detection pass, a Passport health sweep, or a continual-learning
cycle. Per the Core-vs-Gateway rule it is Core. It decides *what runs and when*, and enforces no policy. Each fired job hands its model calls to the normal
chat and workflow routing path where the Gateway sits (`apps/core/src/scheduler/mod.rs`).

Jobs are file-backed, so schedules survive a Core restart. On boot the scheduler reloads every job
from disk and resumes ticking (`apps/core/src/scheduler/store.rs`).

## The job model

A `ScheduledJob` (`scheduler/store.rs`) is one persisted unit of work. It carries an id, a display
name, a schedule, a target, an `enabled` flag, a `require_approval` flag, and a bounded execution
history.

| Field | Type | Meaning |
|---|---|---|
| `id` | string | Unique job id (also the on-disk filename). |
| `name` | string | Display name, logged when the job fires. |
| `schedule` | `Schedule` | Cron expression or fixed interval (see below). |
| `target` | `JobTarget` | What the job runs (see below). |
| `enabled` | bool | When false the tick loop skips the job without deleting it. Defaults to true. |
| `require_approval` | bool | When true a due firing raises a human-in-the-loop approval request instead of running directly. Defaults to false. |
| `created_at` / `updated_at` | string | RFC 3339 timestamps. |
| `last_run_at` | string? | When the job last fired (success or failure). |
| `last_outcome` | `success` \| `failure` | Outcome of the most recent run. |
| `history` | `ExecRecord[]` | Bounded execution log, oldest first. |

Each job is stored at `~/.ryu/state/scheduled-jobs/<id>.json`. The data folder root is configurable. See
[Data and storage](/docs/surfaces/desktop/user-guide/data-and-storage).

## Schedules

A `Schedule` is one of two shapes (`Schedule` enum, tagged on `kind`).

| Kind | Field | Example | Behavior |
|---|---|---|---|
| `cron` | `expr`, optional `tz` | `0 9 * * *` | Classic 5-field cron expression, evaluated in UTC unless `tz` names an IANA time zone. Fires at most once per matching minute. |
| `every` | `interval` | `30s`, `5m`, `1h` | Fixed interval parsed by `humantime`. |

Cron expressions are parsed by `CronSchedule::parse` (`apps/core/src/scheduler/cron.rs`) and a
malformed expression makes the job never due rather than crashing the loop. Interval jobs that fail
to parse are treated the same way.

<Callout type="info">
An interval job that has never run fires once immediately and then debounces to its interval. After
a Core restart, the interval is measured from the job's recorded `last_run_at`, so restarting Core
(an update, a crash, or relaunching the desktop app) does not replay an interval job that ran
recently. A cron job likewise does not fire a second time for a minute it already started a run in
(`is_due` in `scheduler/mod.rs`).
</Callout>

## Job targets

`JobTarget` (`scheduler/store.rs`) is tagged on `type` and has seven variants.

| Variant | Fields | What it runs |
|---|---|---|
| `workflow` | `workflow_id`, `input` map | Loads the persisted workflow and runs it (`workflow::executor::run_workflow`). Records the workflow run id on success. |
| `agent` | `agent_id`, `prompt`, optional `model`, optional `conversation_id` | A durable chat turn against the configured agent. `conversation_id` appends to one existing chat. When omitted, every firing gets a new persistent chat. |
| `app_job` | `plugin_id`, `job_id`, optional `payload` | One job an app owns, run through that app's `jobs.run` capability (see [App-owned jobs](#app-owned-jobs)). Website-monitor checks are app jobs of the Monitors app. |
| `provider_account` | `provider_id`, `account_id`, `prompt`, optional `model` | One minimal turn on one saved subscription account of a provider pool, bypassing the pool's account selection. Used for usage-window warmups. |
| `quest` | `quest_id` | One quest detection pass: Core gathers Shadow context and calls the Quests app's `quests.judge` capability (see [Quests](/docs/core/quests)). |
| `identity_health` | none | Runs the configured Passport health sweep (or the embedded compatibility store) and flips stale connections to `NEEDS_AUTH`. |
| `learning_cycle` | none | Runs the opted-in continual-learning sweep and dispatches eligible retraining work. |

A job file written by an older Core with the retired `monitor` target (`{ "type": "monitor",
"monitor_id": "<id>" }`) still loads: Core reads it as an `app_job` of the Monitors app and, at
startup, rewrites the file in place with the same id, name, schedule, enabled state, and history.
Downgrading to a Core that predates `app_job` is not supported, because it cannot read the migrated jobs.

The `agent` target routes through `global_agent_runner()` so the configured agent handles the
prompt on the real chat path. Scheduled agent runs persist both the instruction and response in
the selected conversation. A routine created while an agent is answering in an existing chat can
omit `conversation_id` to keep using that chat; set `new_chat` in the agent tool or choose **New
chat each run** in the Desktop editor to create a separate durable transcript per firing.

## Agent routines

Agents have a built-in `routines` tool server for background work:

| Tool | Purpose |
|---|---|
| `routines.list` | List the current user's agent routines, destinations, outcomes, and bounded history. |
| `routines.create` | Create a cron or interval routine with instructions, approval, model, and chat-destination options. |
| `routines.update` | Edit a saved routine without recreating it. |
| `routines.delete` | Remove a routine while leaving its chat transcripts intact. |
| `routines.run_now` | Execute the saved target immediately and record the result. |

Routine mutations are approval-gated by default under the normal agent approval policy. On an
org-bound node, Core scopes routine visibility and existing-chat selection to the verified user
who owns the current conversation. Only **Active** agents may run an enabled routine. Pausing an
agent pauses its schedules without deleting their definitions.

The Desktop agent editor's **Routines** view is the setup and operations surface. It shows an
uptime-style 24-hour status strip, per-routine history, the last outcome, and controls to add,
edit, pause, run now, or delete. The **Run history** view links automated entries back to their
persistent transcripts, while **Calendar → Agenda** provides the cross-agent timeline.

### Quick routines

`POST /heartbeat/jobs` accepts an optional `quick_routine: true` for an agent
target. Core saves one canonical quick routine per agent within the existing
routine ownership scope. Concurrent requests and retries reuse its ID, creation
time, and execution history. Requests without this field continue to create
independent jobs, including multiple jobs for the same agent.

On an update through this quick-routine contract, omitting
`target.conversation_id` retains the existing destination after checking current
access. An explicit `null` clears it, and a string selects an existing accessible
transcript. Ambiguous legacy generated routines return `409` for review.
Invalid targets or inaccessible destinations are refused before a slot is saved.
Corrupt slot state fails closed. A refused file replacement leaves the original
job available for readback and retry.

Configuration updates merge execution records completed during validation.
If the saved configuration changed, retry after reloading the routine; the
stale update returns `409`. Deleting a routine invalidates in-flight saves and
late execution completion cannot recreate it. A fresh quick-routine creation
after deletion receives a new ID. If physical file removal is refused after
the deletion marker is saved, the routine stays hidden and cannot be resumed
by a late completion; retry deletion to finish removing the file.

Each execution is bound to the saved routine configuration before work starts.
A changed or deleted routine is refused before execution. Completion merges into
the current history of that same routine identity, preserving edits made during
the run. Approval-triggered runs use the same history recording contract. An approval
covers its saved target, including the agent instructions, model, and chat
destination. Changing that target while approval is pending refuses the old
action before execution; request a new approval for the updated routine.

### Agent templates can carry several schedules

An exported or marketplace agent template may include `agent_config.schedules`. Each entry has a
name, a cron or interval schedule, its own custom `instructions`, an `enabled` flag, and an optional
approval gate. Importing the template materializes one independent agent-target job per entry, so a
single agent can do different work at different times. Exporting the agent includes the schedules
currently attached to it; deleting the agent removes those jobs.

The first-party templates are listed in [Agent Templates](/docs/surfaces/desktop/user-guide/marketplace#agent-templates).
Two show how templates use the scheduler:

- **Security Guard** ships two schedules with separate instructions: an hourly quick scan and a
  midnight deep configuration scan.
- **Codex Quota Reset Watch** runs about every 30 minutes. Once a reset time is confirmed, the agent
  edits its own routine to a longer interval that ends after that time, then restores the 30-minute
  cadence on waking. Because an interval starts when the current run finishes, the wake may be later
  by that run's duration. Source failures back off from 30 minutes to at most four hours. Routine
  edits made during a run survive its completion. Unknown model pricing, a missing connection, or an
  unavailable action blocks setup instead of choosing an expensive fallback. The template never
  posts on X, does not buy credits, and does not grant itself permissions.

A template grants only tools that Core registers, and mutating calls stay approval-gated under the
normal agent approval policy. Scheduled runs need an awake, running node. The scheduler does not
wake an offline computer.

The desktop agent editor's **Routines** section lets you add, remove, pause, run, and edit several
entries without creating a workflow for each one. The calendar shows each materialized job, and a
routine created by an agent can explicitly stay in the current chat or start a new persistent chat
for each firing.

## Reconciled jobs

`workflow` and `agent` jobs are created by hand (`provider_account` jobs come from warmup scheduling). The other targets are reconciled
automatically so they ride the same tick loop as everything else, using deterministic ids.

| Source | Deterministic id | Reconciled by |
|---|---|---|
| A workflow schedule trigger | `wf-sched-<workflow_id>-<idx>` | Core, from the workflow's triggers |
| An app's scheduled job | `app-<hash>` (32 hex characters of a SHA-256 of the app id and job id) | Core, from the app's `jobs.list` |
| A website monitor created before app jobs | `monitor-<id>` (kept for its existing history) | Core, from the Monitors app's `jobs.list` |
| An open quest | `quest-<id>` | Core, from the Quests app's quest list |
| Passport health | `identity-health` | Ensured once at startup |
| Continual learning | `learning-cycle` | Ensured once at startup |

The ids are stable across re-saves, so reconciliation is idempotent. Editing a workflow's triggers
converges the `wf-sched-*` jobs to the declared set and deletes stale ones, and deleting the
workflow, monitor, or quest tears down its backing job. Quest jobs are enabled only while the
quest is open. Completing or dismissing a quest disables (and then removes) its backing job. See
[Workflows](/docs/core/workflows) for trigger reconciliation and
[Website monitoring](/docs/core/website-monitoring) for the monitor lifecycle.

Core's declared workflow triggers, app jobs, quests, and built-in maintenance
jobs may recreate their fixed IDs during authoritative reconciliation. Such
recreation starts a fresh creation time and empty history. A completion from the
deleted identity cannot appear in the recreated job. A refused recreation stays
hidden until reconciliation retries successfully. Ordinary updates preserve
history and cannot restore a deleted identity.

### App-owned jobs

An app that needs scheduled work does not write jobs itself. It provides two capabilities, and
Core keeps one `app_job` per job the app lists:

- `jobs.list` returns the app's jobs, each with an id, a name, a schedule and an enabled flag.
  Every 30 seconds Core writes the jobs it has not seen, updates the ones that changed, and deletes
  the ones the app no longer lists.
- `jobs.run` runs one job when it is due. A non-2xx reply is recorded as that run's failure.

Only first-party apps take part, and Core is the only caller of these capabilities.
Deletions happen only on a complete, successful list. While the app is disabled, unreachable, or
answering with an error, its jobs are kept as they are, and the tick skips them without recording
anything. An `every` interval shorter than one minute is raised to one minute, and each run is
bounded to two minutes. A job runs at most once at a time, an app may have at most two runs in
flight, and four across all apps, so app jobs never take the whole run budget from agent and
workflow jobs. **Run now** and approved runs count against the same limits. Run now answers
`409 Conflict` while the job (or its app) is busy, and an approved run waits up to five minutes
for a free slot. See
[Scheduled job capabilities](/docs/extend/develop/sdk/plugin-sidecar-capabilities#scheduled-job-capabilities) for the
contract.

App jobs carry the app as their owner, so they appear in the app's uninstall inventory and stop
while the app is off. Uninstalling the app removes its jobs with it. If you install it again, Core
recreates them from the app's list on the next pass, with an empty run history.

Through `/heartbeat/jobs` you can run an app job now, but you cannot create one, retarget one (to
or from `app_job`), approval-gate one, or change its name, schedule, or enabled state. Those follow
the app on every pass, so Core refuses the change instead of letting the next pass undo it. App jobs
never wait for approval when they come due. Deleting one answers `409 Conflict` while its app is
installed, because the next pass would recreate it with an empty run history; once the app is
uninstalled, a job left behind can be deleted. To pause or remove an app job, pause or remove the
item in the app that owns it (for example, the monitor in the Monitors app). Clients show these
rows read-only.

## The tick loop

The scheduler spawns one background loop that wakes on a fixed interval and evaluates every
persisted job against the current time (`Scheduler::tick`).

| Constant | Value | Meaning |
|---|---|---|
| `TICK_INTERVAL` | 30 seconds | How often the loop wakes to evaluate due jobs |
| `MAX_CONCURRENT_JOBS` | 8 | Bound on jobs running concurrently |

On each tick the loop lists all jobs from disk, skips the disabled ones, and fires those that are
due. The 30-second cadence means a cron job that matches a given minute is caught within that
minute. An interval finer than 30 seconds is effectively floored to the tick.

Firing marks the job's last-fired instant *before* spawning the actual run, so a slow agent or
workflow run never stalls other due jobs in the same tick. Spawned runs share a semaphore of
`MAX_CONCURRENT_JOBS` permits, so a flood of due jobs queues rather than spawning unbounded tasks.

<Mermaid chart={`flowchart TD
  Tick["Tick every 30s"] --> List["List jobs from disk"]
  List --> Enabled{"enabled?"}
  Enabled -- no --> Skip["Skip"]
  Enabled -- yes --> Due{"due now?"}
  Due -- no --> Skip
  Due -- yes --> Approval{"require_approval?"}
  Approval -- yes --> Gate["Raise approval request"]
  Approval -- no --> Mark["Mark last_fired"]
  Mark --> Permit["Acquire permit (max 8)"]
  Permit --> Run["Run target"]
  Run --> Record["Record outcome + persist"]

### Once-per-slot semantics

The scheduler holds no mutable in-memory job state beyond a per-job last-fired instant, used to
avoid double-firing (`SchedulerInner.last_fired`). When that instant is missing after a restart, it
falls back to the persisted run record, which is `last_run_at` for an interval job and the latest history
entry's `started_at` for a cron job. A cron job fires at most once per matching minute. An interval
job fires only once its interval has elapsed since the last firing. Because `last_run_at` records
when a run finished, the first run after a restart can come up to one run's duration later than the
interval alone would suggest. A run is recorded only when it finishes, so a run that a crash or
restart interrupted leaves no record, and an interval job runs again after the restart.

## Execution history

Every run appends an `ExecRecord` to the job and persists it. The history is bounded to the last 50
records (`MAX_HISTORY`), oldest dropped first.

| Field | Meaning |
|---|---|
| `started_at` / `finished_at` | RFC 3339 timestamps for the run. |
| `outcome` | `success` or `failure`. |
| `run_id` | Workflow run id, or the persistent conversation id for an agent run. |
| `error` | Human-readable error string, on failure. |

A failed workflow or agent run records the failure and the loop continues. One failing job never
blocks the others.

## The API

The scheduler is served under the `heartbeat` prefix (`apps/core/src/server/mod.rs`).

| Action | Endpoint |
|---|---|
| List jobs | `GET /heartbeat/jobs` |
| Create a job | `POST /heartbeat/jobs` |
| Fetch a job | `GET /heartbeat/jobs/:id` |
| Update a job | `PUT /heartbeat/jobs/:id` |
| Delete a job | `DELETE /heartbeat/jobs/:id` |
| Run a job now | `POST /heartbeat/jobs/:id/run` |

Creating a job validates the cron expression or interval before persisting, so a malformed schedule
is rejected up front rather than failing silently at run time. The list, update, delete, and manual
run routes are scoped to the verified user on an org-bound node. Personal nodes retain their
single-user behavior. Running a job now while that job is already running (a scheduled firing or
an earlier manual run) returns `409` instead of starting a second, overlapping run.

`GET /heartbeat/jobs` leaves out `app_job` rows unless the request adds `?include=app_jobs`, and
`provider_account` rows unless it adds `?include=provider_accounts`, so an older client keeps parsing
the list. `GET /api/approvals` applies the same
rule to approvals that run an app job.

<Callout type="info">
Most users never call these routes directly. You create scheduled work from an agent's **Routines**
view, a [workflow](/docs/core/workflows), a [website monitor](/docs/core/website-monitoring), or a
[quest](/docs/core/quests). Core persists the job and reconciles the backing jobs automatically.
</Callout>
