Core can run untrusted code through an explicit execution backend. The default secure backend is
[wasmtime](https://wasmtime.dev) running WASIp1 modules: no daemon, no external process, no network
or filesystem access unless explicitly preopened. A backend is a runtime choice, not a promise that
the host has that runtime installed.

Placement follows the Core-vs-Gateway rule (see [Core vs Gateway](/docs/start-here/architecture/core-vs-gateway)).
Deciding *what runs* - which module, which capabilities - is Core. Deciding *what is allowed* -
DLP on the module's stdout, network egress - is the Gateway. The sandbox module enforces only the
structural default-deny; policy belongs upstream.

## Backend vocabulary

The public configuration term is **backend**. The historical MCP server name remains `sandbox` so
existing tool ids and allowlists keep working. `sandbox.sandbox_exec` is the one-shot entry point;
the persistent `sandbox_create`, `sandbox_run`, and `sandbox_destroy` tools use the configured Box
or Daytona workspace path.

| Backend | Shape | Current status |
|---|---|---|
| `wasmtime` | In-process WASI module, default-deny | Implemented when the Wasmtime feature is compiled |
| `docker` | Local container command execution | Implemented only when a rootless Docker daemon is reachable; rootful daemons are refused |
| `microsandbox` | Local microVM command execution | Implemented when its CLI/runtime is reachable; rejects unexpressible FS/network grants |
| `opensandbox` | Local isolated command execution | Implemented when its CLI/runtime is reachable; rejects unexpressible FS/network grants |
| `daytona` | Remote persistent workspace and command execution | Implemented through the metered Daytona path |
| `box` | Durable Ryu Box service over HTTP | Implemented through the Ryu Box API and metered remote workspace path |
| `local` | Host-local provider slot | Recognized but deliberately not an isolation implementation |
| `ssh` | Remote provider slot | Recognized; provider wiring is not bundled in Core |
| `modal` | Remote provider slot | Recognized; provider wiring is not bundled in Core |
| `vercel_sandbox` | Remote provider slot | Recognized; provider wiring is not bundled in Core |
| `singularity` | Local provider slot | Recognized; provider wiring is not bundled in Core |

<Callout type="warn">
  A recognized backend is not automatically available, and availability is not authorization. Core
  probes only what it can safely identify, then returns an explicit unavailable/error result when a
  selected backend is missing or not wired. It never silently falls back from an explicit backend to
  another runtime. This makes a Box, Daytona, SSH, Modal, Vercel Sandbox, or Singularity plugin a valid
  extension point: it can own provider credentials and implementation while Core keeps the stable
  backend vocabulary and approval boundary.
</Callout>

The Docker backend is deliberately unavailable when the reachable daemon is rootful. A Docker
socket backed by a rootful daemon is equivalent to host-root access; use a rootless daemon or the
default Wasmtime backend for local execution.

## The execution contract

The execution contract takes a backend plus a request and returns a bounded output. The request
shape is intentionally shared across one-shot runtimes and command backends.

| `SandboxRequest` field | Type | Meaning |
|---|---|---|
| `wasm_bytes` | `Vec<u8>` | The WASM bytecode to execute |
| `args` | `Vec<String>` | Command-line args (`argv[0]` is always `"wasm"`) |
| `env` | `Vec<(String, String)>` | Environment variables |
| `stdout_cap` | `usize` | Stdout/stderr size cap in bytes, default 1 MiB |

| `SandboxOutput` field | Type | Meaning |
|---|---|---|
| `stdout` | `Vec<u8>` | Captured stdout, up to `stdout_cap` |
| `stderr` | `Vec<u8>` | Captured stderr, up to `stdout_cap` |
| `duration_ms` | `u128` | Wall-clock duration: instantiation plus run |

## How the wasmtime backend behaves

`WasmtimeSandbox` (behind the host's WASM runtime feature) holds a shared `Engine`, so the
Cranelift JIT initialization (roughly 10 to 30 ms) is paid once and reused across calls.

Each `run` then:

1. Compiles the module from `wasm_bytes` (the cold-start cost, roughly 40 to 120 ms for a small
   module). A caller can pre-serialize with `Module::serialize` keyed on content hash to skip
   recompilation on repeated calls.
2. Wires WASIp1 into a `Linker` and redirects stdout and stderr to in-memory `MemoryOutputPipe`
   buffers sized to `stdout_cap`, so the caller can inspect output.
3. Passes `args` (after the synthetic `argv[0]`) and `env` into the WASI context.
4. Invokes the module's default `_start` export.

When `timeout_secs` is set, Core enables Wasmtime epoch interruption and advances a shared epoch
clock. The store receives its own deadline, so a non-yielding module is interrupted and reported as
a timeout rather than running indefinitely. A missing timeout keeps the existing explicit
no-deadline behavior.

A clean exit, including `proc_exit(0)` (which WASI surfaces as a trap wrapping `I32Exit(0)`), is
treated as success. A non-zero exit code surfaces as an error carrying the captured stderr. Total
cold start is roughly 10 to 120 ms.

The default-deny posture is structural: no filesystem preopens and no socket WASI ABI are wired,
so a module cannot reach the host disk or network. Granting either is a deliberate, future
capability decision.

The `microsandbox` and `opensandbox` command surfaces currently do not document equivalent
filesystem or network flags. They accept the deny-all capability set, but fail closed when a caller
requests a path or network grant instead of silently ignoring it; use Wasmtime or Docker for a
verified capability mapping.

## The `sandbox_exec` tool

The backend is exposed to agents as a single built-in MCP tool, `sandbox.sandbox_exec`, reachable
through the same registry call surface as every other tool. See the [MCP registry](/docs/core/mcp-registry)
for how built-in tools are listed and dispatched.

The tool receives WASM bytecode as a base-64 string (`wasm_b64`) plus optional `args` and `env`
arrays, and returns stdout, stderr, and the exit code. It is registered through the normal tool
loop, so calls go through the existing tool-approval path in the ACP adapter; the sandbox adds no
new approval UI of its own.

## Scope and workspace access

Two declarative capability fields on `SandboxCapabilities` let an agent narrow how a sandbox run is
isolated and what it may do to the workspace. Both default to today's behavior, so a call that sets
neither is the historical per-exec run. They are parsed from optional tool arguments; an absent or
unknown value falls through to the deny-safe default.

### Sandbox scope

`SandboxScope` declares the lifetime an isolated environment should be shared across:

| `scope` arg | Enum | State |
|---|---|---|
| `exec` (default) | `Exec` | One environment per execution, torn down after the run. Today's behavior |
| `agent` | `Agent` | Declared, not yet honored |
| `session` | `Session` | Declared, not yet honored |
| `shared` | `Shared` | Declared, not yet honored |

Scope is declarative metadata. Only `Exec` is wired today; `Agent`, `Session`, and `Shared` are
declared but not yet honored, deferred to a later scheduler epic. Declaring one is safe: it records
intent without changing how the run is isolated.

### Workspace access

`WorkspaceAccess` is a tightening-only clamp on the filesystem mounts a sandbox run receives:

| `workspace_access` arg | Enum | Effect on mounts |
|---|---|---|
| `read_write` (default) | `ReadWrite` | Per-path access as before. A no-op ceiling that reproduces the historical FS logic exactly |
| `read_only` | `ReadOnly` | Every mount is forced read-only |
| `none` | `None` | All workspace mounts are stripped |

Because the default is `ReadWrite`, the clamp is behavior-preserving out of the box. A shared
`SandboxCapabilities::effective_mounts()` centralizes the strip/force-read-only/per-path semantics so
both the wasmtime backend (preopened dirs) and the Docker backend (`-v` mounts) apply identical
rules. The network-deny posture is untouched: the clamp only tightens filesystem access.

## Selecting a backend

The secure WASM backend is enabled by default when the host includes the WASM runtime. A user or
operator can choose a different backend in the host's execution settings or in an agent's tool
configuration. The selected backend, credentials, quota, approval, and runtime availability remain
separate checks. When a backend is disabled or unavailable, the tool remains discoverable and
returns an explicit unavailable result; it does not silently change runtimes.

## Sandbox vs programmatic tool calling

The wasmtime sandbox runs an arbitrary WASM module. It is distinct from
[programmatic tool calling](/docs/core/programmatic-tool-calling), which runs model-authored
JavaScript that fans out across tools. PTC uses a Deno-subprocess for real process isolation by
default (with a rivet secure-exec V8 isolate behind an off-by-default feature), not wasmtime. Reach for the sandbox when you have a
WASM workload to run in isolation; reach for PTC when an agent needs to orchestrate many tool
calls in code.

## Building a backend plugin

Use a plugin when a backend needs a provider SDK, credentials, quota model, or a sidecar that should
not be compiled into Core. The plugin should:

- declare the backend name and required grants;
- expose a typed tool or app contribution that accepts the shared execution request;
- report availability separately from authorization;
- preserve default-deny filesystem/network capabilities and bounded output;
- return an explicit unavailable result when its provider is not configured.

Do not register an arbitrary name and quietly route it to host execution. The backend selector is
strict so a typo, an unsupported Hermes-compatible name, or a disabled provider is visible to the
caller. See [built-in tools](/docs/core/built-in-tools) for the stable tool ids and the
[Hermes terminal backend configuration](https://hermes-agent.nousresearch.com/docs/user-guide/configuration#terminal-backend-configuration)
for the comparative backend vocabulary this contract is designed to accommodate.
