---
title: "Double-Check"
description: "A second model reviews each assistant reply, fired once per message as a turn-hook plugin"
---

Double-check runs a second, separately configured model over the latest assistant answer and adds
the reviewer's verdict as a note: `Looks correct.` or a brief correction. It fires **once per message** with no loop and no re-kick
(unlike [Goals](/docs/core/goals), which re-judge every turn).

<Callout type="warn">
  Double-check ships as the `@ryu/double-check` plugin, marked `experimental`. It is off until you
  turn on the **Double-check** toggle in the composer.
</Callout>

## How it runs

The plugin declares one `post_assistant_turn` turn hook, `double-check.review`
(`hooks/review.js` in the plugin package). It matches only when the conversation has
the `io.ryu.double-check` flag, which the composer toggle sets. After each assistant turn the hook:

1. Takes the latest `assistant` message as the answer under review, and the `user` message before
   it as the question.
2. Calls `host.sideModel` with a fixed reviewer system prompt. The reviewer replies `Looks correct.`
   when the answer is correct and complete, or gives a brief, specific correction.
3. Returns a `note` directive with the reviewer's text. An empty reply returns no directive.

`host.sideModel` sends one non-streaming `POST /v1/chat/completions` through the Gateway, so the
firewall, budget, and audit pipeline applies. The plugin needs the `hook:side-model` grant. The
reviewer judges only from the text it is given. It cannot run code or browse.

## Reviewer model

The reviewer model resolves through the plugin host's side-model chain
(`apps/core/src/plugin_host/bridge.rs`, `resolve_model`):

| Order | Source |
|---|---|
| 1 | The `double-check-model` preference, set by **Reviewer model** in the plugin's **Double-check** settings tab |
| 2 | The node-wide default selection |
| 3 | `RYU_DEFAULT_LLM_MODEL` env var |
| 4 | The bundled local chat model |

A selection that carries an effort forwards it as `reasoning_effort` on the Gateway request. The
model id is any Gateway-routable id, such as a local model stem, an `openrouter/...` slug, or a
provider id.
