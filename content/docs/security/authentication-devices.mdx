Part of the [Authentication and pairing](/docs/security/authentication-and-pairing) guide. Client
sign-in, Core node pairing, and hardware pairing are three separate flows with separate credentials.

| Flow | Owned by | Credential issued |
|---|---|---|
| Client sign-in (desktop, mobile, CLI, extension) | Better Auth | Client session bearer, or a website cookie |
| Core node pairing | Core | Node bearer for one Core node |
| Hardware pairing | Core | Device token sealed to one device, plus a phone relay credential |

## Website-centered approval for every client surface

The website is the shared human sign-in surface for desktop, mobile, the browser extension, and
CLI. Those clients do not repeat the email field in their own shells. They start a Better Auth device
grant, open the website with the client context, and show a short matching code while they wait.

If the account already has an active Ryu session, the website, desktop shell, extension, or foreground
mobile session receives an account-level approval prompt.

1. The user reviews the requesting surface, device label, and matching code, then approves.
2. The requester receives a one-time session grant.
3. The website redeems its grant into the normal HttpOnly cookie. Non-browser clients store their
   bearer in protected local storage.

Closing a prompt leaves that request pending in the current session, without approving or denying
it. It stays hidden there through stream reconnects, while newly arriving requests still open.
Choose **Not now** to deny the request.

```mermaid
flowchart LR
  Requester["Website · desktop · mobile · CLI · extension"] --> Start["Start device grant"]
  Start --> Website["Open shared website sign-in"]
  Website --> Email["Website email field"]
  Email --> Prompt["Live prompt on an active signed-in session"]
  Prompt --> Review["Review surface + matching code"]
  Review -->|"Approve"| Redeem["One-time grant redemption"]
  Redeem --> Cookie["Website HttpOnly cookie"]
  Redeem --> Vault["Protected client token storage"]
  Website -. "QR: user code only" .-> Scan["Ryu Mobile scanner"]
  Scan --> Review
```

### Approve with the Ryu Mobile QR scanner

On a website sign-in, the waiting dialog also shows a QR code generated from Better Auth's
`verification_uri_complete`. In Ryu Mobile, an already-signed-in account can approve it:

1. Open **Settings → Scan sign-in QR** and scan the code.
2. Review the requesting surface, device label, and matching code.
3. Tap **Approve sign-in**.

Scanning only loads the pending request; it never approves it by itself. The short-lived QR holds
the user code, not the raw device grant. The app reveals a matching pending request only for the
account currently signed in on that phone. The matching code remains available as a fallback when
QR scanning is unavailable.

### Scope of an approval

The prompt is account-scoped, not node-scoped. A new client may not have a Core node yet, and any
already-signed-in session for the account can approve it. If no active session is available, use the
normal website sign-in methods or return to the code page later.

Every request is short-lived, one-time, and bound to its client id and account. An approval cannot
pair a Core node or authorize a different account.

### The website approval page

- Confirm the displayed device code and requesting app before you select **Approve device**. The
  page warns that the client receives full account access.
- If the server declines approval or the connection fails, the page shows an error and enables the
  approval button so you can retry the same code.
- The page shows activation, and follows a permitted return link, only after the server confirms
  success.
- A different signed-in account cannot approve the request.
- If several browser accounts are signed in, you can switch accounts on the device page before
  approval. **Add account** opens the sign-in flow and returns to the same pending device code, so
  you do not restart device authorization.

## Device authorization for desktop, mobile, CLI, and extension fallback

Device authorization is the shared sign-in path for clients that cannot use the website's cookie.
The desktop, MCP bridge, and extension can call the Ryu auth service directly. Mobile can start the
same flow through its connected Core node. In every case, the human signs in and reviews the client
in the browser.

The website approval page shows the user code, names the requesting client when known, and explains
the access being granted before the user chooses **Approve device**. An unfamiliar client is shown by
its identifier. If client details are unavailable, the page keeps the generic device label.

```mermaid
flowchart TD
  Client["Desktop · mobile · CLI · extension"] --> Start["Start device authorization"]
  Start --> AuthEndpoint["Ryu auth endpoint creates device code and user code"]
  AuthEndpoint --> Browser["Open verification URL in a browser"]
  Browser --> Existing{"Browser already has a session?"}
  Existing -->|"Yes"| Approve["Review and approve this client"]
  Existing -->|"No"| SignIn["Complete website sign-in, then approve"]
  SignIn --> Approve
  Client --> Poll["Poll the token endpoint"]
  Approve --> AuthEndpoint
  AuthEndpoint --> Poll
  Poll --> Bearer["Receive the client bearer once"]
  Bearer --> Vault["Encrypted vault or protected device storage"]
  Vault --> Calls["Call the Ryu control plane"]
```

### What the client bearer is

The client polls for its own bearer and stores it locally. This bearer identifies the user and the
client session to Better Auth.

- It is not the Core node bearer used by direct Core MCP.
- Desktop may exchange the signed-in session for the short-lived managed `userJwt` returned by the
  control-plane node list. That derived credential is a separate, scope-checked managed-node path.
- Signing out or revoking the session stops future control-plane calls. Removing a paired node
  client is the separate action that stops access to that node.

For identity-token exchanges (`GET /api/auth/token`), Desktop checks the currently selected account
session:

- When a check sees an account switch or sign-out, pending results from the old session supply no
  identity token and cannot replace the current session's cached token.
- Requests for the same current session share one exchange. If it fails, the next request can retry.

## Browser extension auto-authentication

The extension's primary sign-in button opens the website with an explicit extension app flow. If
the browser already has a valid session, the website skips another login and asks Better Auth for a
short-lived One-Time Token (OTT). If it does not, the user signs in once in the browser and the same
handoff continues.

```mermaid
flowchart TD
  Extension["Extension: browser sign-in"] --> Login["Website app flow: extension"]
  Login --> Session{"Browser session exists?"}
  Session -->|"No"| WebSignIn["Sign in once in the browser"]
  Session -->|"Yes"| Generate["Generate a short-lived OTT"]
  WebSignIn --> Generate
  Generate --> Handoff["Open extension URL with the OTT"]
  Handoff --> Clean["Extension removes the OTT from its URL"]
  Clean --> Verify["POST one-time-token/verify"]
  Verify --> SessionBearer["Return a session bearer; do not set a cookie"]
  SessionBearer --> LocalVault["Store in the extension account vault"]
  LocalVault --> Ready["Reload the extension as authenticated"]
```

The OTT is single-use, expires after a short window, and is stored hashed by the server. The raw
session bearer is never placed in the extension URL. If browser handoff is unavailable, **Use an
approval code instead** runs the device-authorization flow. The OTT is implemented by Better Auth's
[One-Time Token plugin](https://better-auth.com/docs/plugins/one-time-token).

## Mobile sign-in has no website token handoff

Mobile signs in with [device authorization](#device-authorization-for-desktop-mobile-cli-and-extension-fallback):
the user approves the phone and its matching code on the website.

The website does not mint a one-time token for the mobile app or open a `ryu://` link with one. Any
installed app can register a custom URL scheme, so a token sent that way could reach an app other
than Ryu. A website sign-in link that names the mobile app is treated as an ordinary website
sign-in.

Any web page or message can still open a `ryu://auth/callback` link, so the app never switches
accounts from such a link on its own, even to an account already on the device:

- The app shows the email address of the account the link signs in to.
- It adds that account and makes it active only after you choose **Sign in**.
- Choose **Cancel** if you did not start the sign-in yourself. Cancelling revokes the session the
  link redeemed.

Mobile hardware setup is separate from account sign-in. It uses the
[hardware pairing](#hardware-qr-and-ble-pairing) flow below.

## Core node pairing

Core owns node pairing, not Better Auth. Pairing works locally and does not need an account or a
network round trip.

| Route | Purpose |
|---|---|
| `POST /api/pair/code` | A client that cannot read the node's own token requests a pairing code, valid for 10 minutes |
| `GET /api/pair/requests` | An authenticated client lists pending requests |
| `POST /api/pair/approve` / `POST /api/pair/deny` | An authenticated client approves or denies the human-visible code |
| `POST /api/pair/token` | The new client polls with its device code and receives the node bearer once |
| `GET /api/pair/clients` | List paired clients |
| `DELETE /api/pair/clients/:id` | Revoke a paired client |

```mermaid
flowchart TD
  NewClient["Browser, extension, or remote client"] --> Request["POST /api/pair/code"]
  Request --> Pending["Core keeps a pending request with a 10-minute TTL"]
  Pending --> Codes["Client displays secret device code and human code"]
  Trusted["Already-authenticated Core client"] --> List["Read pending pairing requests"]
  List --> Decision{"Approve the matching human code?"}
  Decision -->|"No"| Deny["Deny; client receives access denied"]
  Decision -->|"Yes"| Issue["Issue a node bearer and persist only its hash"]
  Codes --> Poll["Client polls POST /api/pair/token with device code"]
  Issue --> Poll
  Poll --> NodeToken["Deliver node bearer once"]
  NodeToken --> NodeCalls["Call this Core node"]
  Revoke["Remove paired client"] --> NodeCalls
  Revoke --> Blocked["Future node requests are rejected"]
```

Approval is itself authenticated. Pairing lets a trusted client vouch for another client; it does
not turn an unauthenticated request into an organization grant. Revoking the paired client removes
the node credential without changing the user's cloud account session.

### Node credentials in the web app

In the web app, a node credential belongs to the signed-in account that paired it.

- Switching accounts loads only the new account's paired nodes. Switching back restores the
  original account's nodes.
- Signing one account out removes that account's node credentials from the browser. Signing out of
  every account removes all of them.
- Other open web app tabs follow at once: when one tab switches accounts or signs out, every other
  tab stops using the previous account's node credentials, without a reload.
- If you switch accounts while a pairing code waits for approval, the approved credential is
  discarded. Pair again from the account you want to use.
- Nodes saved by earlier web app versions keep their name and address but need to be paired again,
  because the browser cannot tell which account they belonged to.

## Hardware QR and BLE pairing

Hardware pairing uses device-specific keys, not an account OTT. The mobile app must already have
node access to register the hardware.

1. The device and the node each contribute fresh randomness.
2. The user compares a 6-digit code (shown on the watch or desk, beeped by the necklace) and presses
   the device button.
3. Core issues nothing until the device's confirmation verifies.
4. Core seals the device token, node URL, and optional WiFi credentials so that only the device can
   open them.
5. The phone gets a separate relay credential that can only open that device's encrypted relay
   connection.
6. The device pins the node's key and connects over an end-to-end encrypted session.

```mermaid
flowchart TD
  Hardware["Hardware shows ryu-pair QR or advertises over BLE"] --> Info["Device id, type, nonce, public key, commitment"]
  Mobile["Mobile scans the QR or picks the device"] --> Info
  Info --> Begin["Authenticated POST /api/hardware/pair/begin"]
  Begin --> Offer["Core returns a pairing id and its node key; app passes the offer to the device"]
  Offer --> Compare["Device shows or beeps the code; app shows Core's code; user compares"]
  Compare -->|"Codes differ"| Cancel["Cancel; nothing is issued"]
  Compare -->|"Codes match"| Press["User presses the device button"]
  Press --> Tag["Device returns its confirmation"]
  Tag --> Confirm["Authenticated POST /api/hardware/pair/confirm"]
  Confirm --> Verify{"Core verifies the confirmation"}
  Verify -->|"Mismatch"| Cancel
  Verify -->|"Valid"| Sealed["Device token, node URL, and WiFi sealed to the device"]
  Verify -->|"Valid"| RelayCred["Relay credential for the phone"]
  Sealed --> Provision["App writes the sealed credentials over BLE"]
  Provision --> Session["Device opens an encrypted session with pinned keys"]
  RelayCred --> Session
  Session --> DeviceAPI["Only this paired device is authorized"]
  Remove["Remove hardware from the node"] --> Revoke["Revoke the device and relay credentials"]
  Revoke --> DeviceAPI
```

<Callout type="warn">
Devices paired with older firmware keep using the earlier nonce-and-token flow until they are
re-paired, and the app marks them as legacy. That flow has no code compare or button press, so it
does not prove the caller controls the device. Keep the node on a LAN or tailnet while legacy
pairing is in use.
</Callout>

An account session, device-grant bearer, or app OTT must never be substituted for the hardware
device token. The device token can be revoked without signing the user out everywhere.
