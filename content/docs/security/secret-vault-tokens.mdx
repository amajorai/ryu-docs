[Machine identities](/docs/security/secret-vault-engines#machine-identities) log in and receive a
vault token (`rvt_…`). This page covers what a token can do after login, how to hand a secret to
another process exactly once, and how to keep a runaway caller from overloading the vault. The
routes follow the HashiCorp Vault and OpenBao token model.

## Token lifetime and renewal

Every token has a TTL (one hour by default, at most 24 hours per grant) and a hard maximum
lifetime. A renewable token can be renewed up to the identity's `maxTtlSecs` (24 hours by default,
at most 30 days), and never past `explicitMaxTtlSecs` when that is set.

- A machine renews its own token with `POST /api/vault/agent/self/renew` (optionally with an
  `incrementSecs`) and reads its full metadata with `GET /api/vault/agent/self/lookup`. The CLI
  equivalents are `ryu-cli secrets token renew [--increment S]` and `ryu-cli secrets token lookup`.
- An administrator renews a token by accessor with `POST /api/vault/tokens/{accessor}/renew`, and
  lists or looks up tokens with `GET /api/vault/tokens`. Responses never include a token.

A **periodic** token (`periodSecs`) renews by one period at a time and has no maximum lifetime
unless `explicitMaxTtlSecs` is set. Use it for long-running services that check in regularly.

Set an identity's defaults with `PUT /api/vault/machines/{id}/token-config` (`admin` on
`sys/machines`):

| Field | Meaning |
|---|---|
| `maxTtlSecs` | Renewable lifetime cap (default 24 hours, at most 30 days) |
| `explicitMaxTtlSecs` | Hard cap that also applies to periodic tokens |
| `periodSecs` | Makes issued tokens periodic |
| `numUses` | Requests a token may authenticate before it is revoked |
| `boundCidrs` | Client addresses allowed to log in for and present the token |
| `renewable` | `false` makes issued tokens non-renewable |

`numUses` is counted on every request the token authenticates. AppRole secret ids can also carry
their own `cidrList` (where the secret id may log in from) and `tokenBoundCidrs` (bound to the
tokens it issues, inside the identity's `boundCidrs`).

## Child tokens and token roles

A token can mint a narrower **child** with `POST /api/vault/agent/self/child`. The child gets a subset of its
policies, a TTL capped by the parent, and optionally a use limit. Children can nest eight levels
deep. Revoking a token also revokes its non-orphan children, the leases they hold, and their
cubbyholes. `POST /api/vault/tokens/{accessor}/revoke-orphan` revokes a token but keeps its
children as orphans.

A **token role** is a named template for child and administrator-created tokens:
`allowedPolicies`, `disallowedPolicies`, `orphan`, a default `ttlSecs`, and the token settings from
the table above. Manage roles with `/api/vault/token-roles/{name}` (`admin` on
`sys/token-roles/<name>`). Administrators can mint a token for an identity with
`POST /api/vault/tokens`; the token is returned once.

## Client addresses

CIDR binding and quotas use the client address of the request. The socket peer is authoritative.
`X-Forwarded-For` is used only when the peer is listed in `RYU_VAULT_TRUSTED_PROXIES`
(comma-separated CIDRs, empty by default), and then the right-most entry that is not itself a
trusted proxy wins. When the address cannot be known, such as a request through a forwarding
tunnel, CIDR-bound tokens are refused.

## Response wrapping

Wrapping turns a response that carries a secret into a single-use **wrapping token** (`rvw_…`). An
orchestrator can give a sandbox or sub-agent the wrapping token, and only that recipient ever sees
the secret.

- Add `X-Ryu-Wrap-TTL: <seconds>` (or HashiCorp's `X-Vault-Wrap-TTL`) to a request, such as a
  reveal, an AppRole secret-id issue, a dynamic credential, or a child token. The response then
  contains only the wrapping token.
- `POST /api/vault/sys/wrapping/wrap` (or `/api/vault/agent/wrapping/wrap` with a vault token)
  wraps any JSON object. It needs `use` on `sys/wrapping`.
- `POST /api/vault/sys/wrapping/unwrap` returns the original response once. `lookup` describes a
  wrapping token without using it, and `rewrap` moves the response to a new token with the same
  TTL. These routes are authenticated by the wrapping token itself.

```sh
ryu-cli secrets wrap DB_PASSWORD --ttl 300   # prints rvw_…
ryu-cli secrets unwrap rvw_…                 # prints the value, once
```

Wrapping TTLs range from one second to 24 hours (default five minutes), and a wrapped response can
be up to 1 MiB. The response is stored encrypted, and only a hash of the token is kept. A second
unwrap of the same token is reported and audited as a reuse. Treat the secret as compromised in
that case: someone else may have intercepted the handoff. Event streams (`/api/vault/events`,
`/api/vault/agent/events`, and an item's `/events`) never end, so a wrap header on them is refused
with `400 vault_invalid_request`.

## Cubbyholes

A **cubbyhole** is a small private key/value store that belongs to one machine token. Only that
token can read or write it with `/api/vault/agent/cubbyhole/{key}`, values are encrypted, and the
whole store is destroyed when the token is revoked or expires. A cubbyhole holds up to 256 keys of
at most 64 KiB each. Use it for scratch credentials that must not outlive one job.

## Lease administration

Each dynamic-credential lease has a prefix path `<role>/<lease id>`, so `db/` selects every lease of
role `db`. A token with `admin` on `sys/leases` can use these routes:

- `GET /api/vault/sys/leases` lists leases by prefix and holder, and `GET /api/vault/sys/leases/count`
  counts live leases per role.
- `GET /api/vault/sys/leases/lookup/{id}` describes one lease. The lease holder can use it too.
- `POST /api/vault/sys/leases/revoke-prefix` revokes every live lease under a prefix.
- `POST /api/vault/sys/leases/tidy` removes old revoked leases (older than 30 days by default) and
  closes leases of deleted roles.

## Quotas

Quotas protect the vault from runaway callers. Manage them with `/api/vault/sys/quotas/{name}`
(`admin` on `sys/quotas`):

```json
{ "kind": "rate-limit", "path": "agent/", "rate": 120, "intervalSecs": 60, "blockIntervalSecs": 300 }
```

```json
{ "kind": "lease-count", "role": "db-*", "maxLeases": 50 }
```

- **`rate-limit`** allows `rate` requests per `intervalSecs` for each client address under a route
  prefix (relative to `/api/vault/`; empty means every vault route). Once exceeded, a client can
  be blocked for `blockIntervalSecs`. Over the limit the vault answers `429` with `Retry-After`, and
  the first rejection of each run is audited.
- **`lease-count`** caps live leases for dynamic roles matching a glob, so a looping agent cannot
  create unbounded database users.

A built-in `default-login` quota limits `/api/vault/auth/*` to `RYU_VAULT_LOGIN_RATE_PER_MIN`
(`vault.loginRatePerMin` in [`node-config.json`](/docs/start-here/configuration#core-node-config))
requests per minute for each client address (default 60; `0` turns it off). It applies only to
clients with a known address.
