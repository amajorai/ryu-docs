---
title: "WebSocket Broker Services"
description: "Let agents open WebSocket connections through the credential broker, with handshake credentials added and placeholders swapped in text messages."
---

The [credential broker](/docs/security/secret-vault-broker) also handles WebSocket connections. An
agent opens `ws://` or `wss://` through the broker like any other request, and the broker treats
the opening handshake as a brokered request:

- The handshake must match a service the session may use, follow the environment's unmatched-host
  policy, and pass the same network checks as other requests. A refused handshake gets the usual
  JSON error, and the request log records it.
- The service's auth headers, and `header`, `path`, and `query` placeholders, are added to the
  handshake. The agent's `Proxy-Authorization` header is never sent upstream.
- If the upstream accepts (`101 Switching Protocols`), the broker relays the connection until either
  side closes it. If it answers anything else, such as `401`, the agent gets that response as is.
- For a service with `oauth` auth, the handshake counts as a delete under the connection's access
  level, because the messages it carries can write or delete. A connection that does not allow
  deletes is refused with `oauth_access_denied` before anything reaches the upstream.
- The connection closes when its broker session is revoked or expires, and it counts against the
  session's limit of open tunnels.

## Placeholders in messages

Add `websocket` to a substitution's `in` list to substitute placeholders in the text messages the
agent sends:

```json
{
  "name": "realtime",
  "host": "realtime.example.com",
  "auth": { "type": "bearer", "token": "secret:REALTIME_TOKEN" },
  "substitutions": [
    { "placeholder": "__SESSION_KEY__", "ref": "secret:REALTIME_SESSION_KEY", "in": ["websocket"] }
  ]
}
```

- A text message that is valid JSON gets JSON string escaping. Other text gets the raw value.
- Fragmented text messages are reassembled before substitution. Text messages over 1 MiB and binary
  messages are relayed unchanged.
- In text messages the upstream sends back, the broker replaces each substituted value (4 characters
  or longer) with its placeholder, so an echo does not return the credential to the agent.
- Compression (`permessage-deflate`) is not offered on these connections, because compressed
  messages cannot be rewritten.
- Each message that contains a placeholder is checked against the current policies and uses the
  credential's current value, so a policy change, a revoked machine token, or a rotated secret
  applies to the next message without reconnecting.
- If a placeholder's credential cannot be used, for example because policy denies it, the broker
  closes the connection with code `1008` and the message is never sent.

<Callout type="warn">
Only text messages under 1 MiB are scanned for echoed values. An upstream that returns the
credential in a binary message, or in a larger text message, would still expose it. Enable
`websocket` substitution only for upstreams that do not echo what they receive.
</Callout>

Card placeholders are never substituted on WebSocket connections, so a host covered only by a
card's merchant list cannot be reached this way. HTTP/2 is not brokered: intercepted connections
use HTTP/1.1.
