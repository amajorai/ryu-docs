title: "Permissions and roles"
description: "The org/team RBAC permission vocabulary, built-in roles, and how Core enforces them on a shared node."

Ryu is local-first and single-tenant by default, but a node can be bound to an organization (a shared "company brain"). On such a node, Core enforces org/team role-based access control on its REST surface, keyed to a per-user identity verified from a signed JWT. The permission vocabulary and the built-in role sets are a contract shared byte-for-byte with the TypeScript control plane (`apps/core/src/identity_verify/permissions.rs`), so an effective-permission check agrees on both sides.

<Callout type="warn">
This is Core-side enforcement of a caller's role. Ryu's scoped Better Auth API keys and
official MCP OAuth grants are separate control-plane credentials; they do not replace the
node ACL or silently grant control of every node. See [Authentication and pairing](/docs/security/authentication-and-pairing)
for the credential boundaries.
</Callout>

## The permission vocabulary

28 `resource.action` keys, defined in `PERMISSIONS` (`apps/core/src/identity_verify/permissions.rs`). The Rust constants and the TypeScript control-plane array must match exactly.

| Key | Grants |
|---|---|
| `gateway.view` | Read gateway config and status |
| `gateway.configure` | Edit gateway config (firewall, budgets, auth, routing) |
| `workflow.view` | List and read workflows |
| `workflow.run` | Execute a workflow |
| `workflow.edit` | Create or edit a workflow |
| `workflow.delete` | Delete a workflow |
| `space.read` | Read a space's documents |
| `space.write` | Write a space's documents |
| `space.delete` | Delete a space or its documents |
| `agent.view` | List and read agents |
| `agent.run` | Run an agent |
| `agent.edit` | Create or edit an agent |
| `agent.delete` | Delete an agent; channels and their session history remain |
| `channel.manage` | Edit a shared organization channel configuration or credentials |
| `channel.delete` | Delete a channel configuration; its shared Core session history remains |
| `tool.exec` | Execute a tool |
| `members.manage` | Add, remove, and re-role members |
| `roles.manage` | Create, edit, and assign custom roles |
| `billing.manage` | Manage billing and subscriptions |
| `audit.view` | Read the audit log |
| `app.install` | Install a marketplace package on a node |
| `app.update` | Download and apply a new package release on a node |
| `app.enable` | Enable an installed package on a node |
| `app.disable` | Disable an installed package on a node |
| `app.uninstall` | Remove an installed package from a node |
| `marketplace.view` | Browse marketplace packages |
| `marketplace.publish` | Publish a marketplace package |
| `marketplace.transfer` | Transfer marketplace package ownership |

## Built-in roles

Four built-in roles map from a caller's Better Auth org role (`permissions_for_role`). An unknown role fails closed to `viewer` (the least-privileged floor).

| Role | Permission set |
|---|---|
| `owner` | Every permission |
| `admin` | Every permission except `billing.manage` |
| `member` | `gateway.view`, `workflow.view`, `workflow.run`, `space.read`, `space.write`, `agent.view`, `agent.run`, `tool.exec`, `marketplace.view` |
| `viewer` | `gateway.view`, `workflow.view`, `space.read`, `agent.view`, `marketplace.view` |

A member's **effective** permissions are the built-in set of their role UNION every permission granted by a custom role assigned to them in the org. The role tier is the fail-closed fallback when the custom-role lookup is unavailable.

By default, only organization owners and admins can delete agents or Spaces. A custom role may grant
the corresponding delete permission explicitly, but Core still checks that effective permission on
the server. The desktop surfaces the same boundary and requires a deliberate slide confirmation for
destructive agent, Space, channel, and team actions; cancelling or failing the request leaves the
resource unchanged.

Shared organization channel records are visible to organization members, but only the creator or a
caller with `channel.manage` can edit their routing, enablement, platform settings, or credentials.
Only `channel.delete` removes a shared channel record.

## How Core gates a request

Every request may carry a signed user identity in the `x-ryu-user-jwt` header (`USER_JWT_HEADER`, `apps/core/src/server/mod.rs`). Middleware verifies it offline (EdDSA against the control plane's JWKS) and attaches an optional `VerifiedCaller`. A handler then calls `enforce_permission(state, caller, perm)`.

Enforcement branches on whether **this node** is bound to an org (`registered_org()`), because per-user RBAC only makes sense on a shared node and the single-user local flow must never be degraded.

| Node state | Caller | Result |
|---|---|---|
| Unbound (local/dev) | any (or none) | Allow - the shared `RYU_TOKEN` already implies one trusted operator |
| Org-bound | No / invalid JWT | Deny (403) - a tokenless caller must not inherit full trust |
| Org-bound | Valid JWT for a different org | Deny all (403) - a non-member holds nothing here |
| Org-bound | Member of the node's org | Allow iff `perm` is in their effective set |

For a member, the built-in role tier is checked first (no network on the common path). On a miss, Core resolves the custom-role slice from the control plane and unions it in.

### Handlers gated today

Core wires `enforce_permission` into these handler families (call sites in `apps/core/src/server/mod.rs`):

| Permission | Surface |
|---|---|
| `gateway.view` | Read gateway configuration, status, and Doctor reports |
| `gateway.configure` | `PUT /api/gateway/config` (the "employees can't edit the gateway" gate) |
| `workflow.view` / `run` / `edit` / `delete` | Workflow REST handlers |
| `space.read` / `write` / `delete` | Space document REST handlers |
| `agent.view` | Agent REST reads plus sync scans, status, and exports |
| `agent.run` | Agent runs, ACP resume, and proactive openings |
| `agent.edit` | Agent writes plus sync profiles, imports, and conflict resolution |
| `agent.delete` | Agent deletion |

The `channel.manage` key is enforced by the control plane for updates to an organization-owned
channel created by another member. The `marketplace.*` keys govern catalog visibility, publishing,
and ownership transfer on the control plane. The remaining keys (`tool.exec`, `members.manage`,
`roles.manage`, `billing.manage`, `audit.view`) are part of the shared vocabulary; member, role,
and billing management are enforced on the control-plane side (the epic's `roleSatisfies` gates).
`audit.view` gates the organization Audit log, which merges org control changes with reported
Gateway control changes; the local Gateway audit endpoint retains its own master-key gate.

## Node-scoped marketplace lifecycle

Marketplace packages use the five independent `app.*` permissions above, regardless of whether the
package is an app, plugin, skill, agent, workflow, theme, output style, Space, profile, or bundle.
There is no implicit implication between install, update, enable, disable, and uninstall.

Core validates the node scope before resolving the ACL:

| Node scope | Caller requirement |
|---|---|
| Organization | Caller belongs to the organization |
| Team | Caller belongs to the team, or is an organization owner/admin |
| Personal | Caller is the owning user; organization administration does not bypass this |
| Unbound | Existing local-token owner behavior is preserved |

Owners/admins receive the default lifecycle permissions on organization and team nodes. Ordinary
members/viewers receive none by default; team, member, role, and custom-role grants are explicit.
An individual deny overrides a team grant. The stable node ID is preserved when a gateway credential
rotates, so an ACL continues to govern the same machine.

The read-only desktop explanation is `GET /api/plugins/lifecycle-capabilities`. Node ACLs are read or
edited with `GET`/`PUT /api/acl/resources/node/:nodeId`; editing requires `roles.manage`, with a
personal-node owner and an organization owner/admin receiving implicit management authority. A
denied lifecycle request returns a structured `403` with `required_permission` and `node_scope`,
before filesystem or package state changes.

## Custom-role resolution and caching

The custom-role slice Core cannot compute locally is fetched from the control plane (`resolve_permissions`, `apps/core/src/sidecar/control_plane.rs`). Core sends only its `x-gateway-key` credential and the `userId`; the org is derived server-side from the key.

- The lookup is **fail-closed** - any failure (no gateway key, network error, non-2xx, decode error) returns an empty set, never an error and never a wide set. The caller falls back to the built-in role tier alone (never full access).
- Only **successful** lookups are cached, for `PERMISSIONS_TTL` (30 seconds), keyed by user id. A transient failure is not cached, so it never denies a user for the whole window. A role or grant change propagates within 30 seconds.
