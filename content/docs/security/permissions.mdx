Ryu is local-first and single-tenant by default, but a node can be bound to an organization (a shared "company brain"). On such a node, Core enforces org/team role-based access control on its REST surface, keyed to a per-user identity verified from a signed JWT. The permission vocabulary and the built-in role sets are a contract shared byte-for-byte with the TypeScript control plane (`apps/core/src/identity_verify/permissions.rs`), so an effective-permission check agrees on both sides.

<Callout type="warn">
This is Core-side enforcement of a caller's role. Ryu's classic and fine-grained personal access
tokens, organization API keys, and official MCP OAuth grants are separate control-plane credentials.
They do not become a node bearer automatically. The one exception is the short-lived
`userJwt` returned for an organization-bound managed node; Core verifies it against the control-plane
JWKS and still applies the node's organization, team, personal-owner, and route checks. See
[Authentication and pairing](/docs/security/authentication-and-pairing) for the credential boundaries.
</Callout>

## The permission vocabulary

| `workflow.run` | Execute a workflow |
| `workflow.edit` | Create or edit a workflow |
| `workflow.delete` | Delete a workflow |

## Built-in roles

Four built-in roles map from a caller's Better Auth org role (`permissions_for_role`). An unknown role fails closed to `viewer`, the least-privileged set.

| Role | Permission set |
|---|---|
| `owner` | Every permission |
| `admin` | Every permission except `billing.manage` |
| `member` | `gateway.view`, `workflow.view`, `workflow.run`, `space.read`, `space.write`, `agent.view`, `agent.run`, `tool.exec`, `notifications.view`, `mail.read`, `messaging.read`, `projects.manage`, `nodes.view`, `marketplace.view` |
| `viewer` | `gateway.view`, `workflow.view`, `space.read`, `agent.view`, `notifications.view`, `mail.read`, `messaging.read`, `nodes.view`, `marketplace.view` |

The built-in `billing` role is not a rung on this ladder. It is additive: Core adds `billing.manage` to the set of the caller's other role, or to `viewer` when `billing` is the only role (`permissions_for_ba_role`). For what each role is for, see [Organization admin controls](/docs/security/organization-admin-controls#roles).

A member's **effective** permissions are the built-in set of their role plus every applicable permission granted by a custom role assigned to them. Organization assignments apply at organization scope; a team assignment applies only when the caller is a member of that team and the resource is in that team. The role tier is the fail-closed fallback when the custom-role lookup is unavailable.

Better Auth remains the source of truth for membership, invitations, and teams, using only the
static roles above. Custom roles are Ryu's own: they are resolved by the control plane and carried
to Core separately, so a role that merely looks like `admin` is never proof of a Ryu capability.

Custom-role changes are bounded by the person making them:

- You can only grant permissions you hold yourself, and the same limit applies to taking them away.
  Editing or deleting a custom role, or removing it from a member, is refused when the role carries
  a permission you do not hold.
- You cannot change the custom roles of a member whose built-in role is above yours, and only the
  primary owner can change the primary owner's custom roles.
- When a member leaves or is removed, their custom-role assignments and the vault policies bound
  directly to them are deleted, so they do not come back if the same person is invited again.

### Owners and the primary owner

Each organization has one **primary owner** above the other owners. Nobody can demote or remove the
primary owner, and only the primary owner can grant or revoke the owner role, transfer primary
ownership, or delete the organization. The primary owner has the same permission set as any owner,
so every permission check above treats them as `owner`. See
[Organization admin controls](/docs/security/organization-admin-controls#primary-owner).

### Self-hosted node binding

Binding a self-hosted node to an organization requires the caller's current
`gateway.configure` permission. Owners and admins receive it through their
built-in role. A custom organization role can grant it to another member.
Team-scoped grants authorize only enrollment for the matching team; they do not
widen to organization, personal, or another team's nodes.

Desktop and the web Fleet page use the same effective-permission result to show
or disable the action, but the organization service remains authoritative. It
checks the permission when it issues the ten-minute enrollment code and again
on first redemption. Issuing the code also asks the caller to confirm it's you
(the same step-up that issuing a gateway key needs), because an enrolled node
can resolve members' shared secrets. Losing membership, removing the custom role, or revoking
the grant therefore stops a code from creating a binding even if an older page
still has its form open.

The code owns the organization scope. A node cannot submit an organization ID,
plan, tier, wallet, or owner override. Once activated, the enrolled relay
credential resolves the organization's live subscription and policy for each
managed inference connection. Rebinding to another organization requires an
explicit revoke-and-rebind flow.

By default, only organization owners and admins can delete agents or Spaces. A custom role may grant
the corresponding delete permission explicitly, but Core still checks that effective permission on
the server. Desktop shows the same boundary and requires a slide confirmation for
destructive agent, Space, channel, and team actions; cancelling or failing the request leaves the
resource unchanged.

Creating an organization channel requires `channel.manage`. Shared organization channel records are
visible to organization members, but only the creator or a caller with `channel.manage` can edit their
routing, enablement, platform settings, or credentials.
Only `channel.delete` removes a shared channel record.

## How Core gates a request

An already authenticated node request may carry a signed user identity. Middleware verifies it
offline with the control plane's signing keys and attaches the verified caller. On an unbound
local/self-hosted node, that JWT is only identity context: the node bearer, paired token, or
delegation still admits the request. On an organization-bound managed node, the short-lived
`userJwt` may also be the primary bearer; Core narrows it to this node's organization and then to
its team or personal owner before applying route capabilities. A handler then intersects the
caller's node capability with `enforce_permission(state, caller, perm)`.

Hosted MCP delegations carry the verified subject, organization, team, exact node, exact agent,
scopes, audience, issuer, unique ID, and a short expiry in one signed envelope. Core verifies all of
those fields locally. A destination path cannot select a different agent than the signed binding.
The `gateway:route` OAuth scope permits routing and vault metadata reads; changing or deleting a
vault secret requires separate `vault:write` consent. Reads that release secret or key material
need `vault:write` consent too, even though they are `GET` requests: value subkeys, TOTP codes,
static-role credentials, passwords generated from a password policy, and transit key export and
backup. Shared node, team, and organization secrets
also require the handler's existing management permission.

Enforcement branches on whether **this node** is bound to an org (`registered_org()`). Per-user role-based access control (RBAC) applies only on a shared node, so the single-user local flow is unchanged.

| Node state | Caller | Result |
|---|---|---|
| Unbound (local/dev) | valid node bearer/pair/delegation | Allow according to that credential; a user JWT alone is not admission |
| Unbound (local/dev) | no valid node credential | Deny - loopback limits exposure but does not disable the node gate |
| Org-bound | valid managed `userJwt` in node scope | Allow iff its role has the required capability |
| Org-bound | no / invalid JWT and no other valid credential | Deny - a tokenless caller must not inherit full trust |
| Org-bound | Valid JWT for a different org | Deny all (403) - a non-member holds nothing here |
| Org-bound | Member of an organization node | Allow iff `perm` is in their effective set |
| Org-bound | Member outside the node's team or personal owner | Deny before route capability checks |

For a member, the built-in role tier is checked first (no network on the common path). On a miss, Core resolves the custom-role slice from the control plane and unions it in.

For the handlers and control-plane surfaces each key gates, see
[Permission enforcement by surface](/docs/security/permissions-enforcement). For the `app.*`
lifecycle keys, node and resource ACL edits, and app permission levels, see
[Marketplace and app permissions](/docs/security/permissions-marketplace).

## Custom-role resolution and caching

The custom-role slice Core cannot compute locally is fetched from the control plane (`try_resolve_permission_context`, `apps/core/src/sidecar/control_plane.rs`). Core sends only its gateway credential and the organization/team scope is derived server-side from that credential and the registered node.

- The lookup is **fail-closed**. Any failure (no gateway key, network error, non-2xx, decode error) returns an empty set, never an error and never a wide set. The caller falls back to the built-in role tier alone.
- Only **successful** lookups are cached, for `PERMISSIONS_TTL` (30 seconds), keyed by user id and registered team scope. A transient failure is not cached, so it never denies a user for the whole window. A role or grant change propagates within 30 seconds.
