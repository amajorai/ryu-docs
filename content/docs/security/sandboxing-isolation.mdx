---
title: "Sandboxing and isolation"
description: "Swappable sandbox backends for tool execution, and what isolation each one actually provides today."
---

Tools that execute code run inside a sandbox backend. Ryu treats the sandbox as swappable - you can pick a default and override it per call - so the isolation strength is a deployment choice rather than a hardcoded one. For the Core-side configuration surface, see [Sandbox](/docs/core/sandbox).

## Backends

| Backend | Selection | Isolation / execution today |
|---|---|---|
| `wasmtime` | Default when compiled, or an explicit `backend` | In-process WASI with no filesystem or network unless granted |
| `docker` | Explicit `backend` | Local container execution when the daemon is reachable |
| `microsandbox` | Explicit `backend` | Local microVM execution when the runtime is reachable |
| `opensandbox` | Explicit `backend` | Local isolated command execution when the runtime is reachable |
| `daytona` | Explicit `backend`, or persistent workspace tools | Remote persistent workspace; metered and provider-dependent |
| `box` | Explicit `backend`, or persistent workspace tools | Remote durable Box service; driver-dependent isolation with explicit stop/resume/fork |
| `ssh`, `modal`, `vercel_sandbox`, `singularity` | Explicit provider slot | Recognized vocabulary; Core does not pretend to execute these without provider wiring |
| `local` | Explicit provider slot | Recognized but not treated as an isolation boundary or implicit host fallback |

The `backend` argument is strict. An explicit unknown or unavailable backend returns a visible error;
Core does not silently substitute the node default. This lets a plugin implement a provider-backed
slot such as Daytona without changing the meaning of another backend name.

Availability and permission are different controls. A detected runtime only says that the host may
be able to start it; it does not authorize a plugin, agent, or user to use it. Execution still passes
through the relevant manifest grants, agent allowlist, approval policy, and resource limits. A
provider or sandbox that is discoverable but disabled must remain unavailable to the caller.

<Callout type="warn">
  Runtime presence is not permission, and a provider slot is not an implementation. Every execution
  still passes through manifest grants, agent allowlists, approval policy, resource limits, and the
  selected backend's own credentials/quota checks. If those checks fail, the call must remain
  unavailable; it must not fall back to a less isolated host process.
</Callout>

## Why this matters

Because a tool call originates from untrusted model output, the selected backend is the containment
layer for code the model decided to run. Wasmtime supplies the strongest built-in default-deny
boundary; container, microVM, and remote backends add their own isolation semantics. Command approval
(a human gates dangerous operations) and environment scrubbing (the child never inherits secrets)
remain load-bearing controls around every backend.

## Managed agent process containment

Ryu-managed Codex sessions also pass through a Ryu-owned child runner before ACP starts the agent:

| Host | Process boundary | Default behavior |
|---|---|---|
| Linux | Landlock removal rules | Denies file unlink, directory removal, and rename for the agent and its descendants |
| macOS | Seatbelt deletion-denial profile | Denies file unlink for the agent and its descendants; packaged App Sandbox or a VM is the stronger follow-up |
| Windows | Native AppContainer runner | Ryu refuses to start managed Codex until an AppContainer deletion boundary is available |

This runner is deliberately a lower-level backstop for the Codex hook and command scanner. It does
not make arbitrary host writes safe: overwriting or truncating an existing file can still destroy
content. For work without system backups, use a disposable copy-on-write workspace or a VM and
promote reviewed changes back to the host through a controlled file broker. The current Ryu runner
does not yet provide that broker; the host/user must perform Trash or Recycle Bin moves outside the
confined process.

The runner is fail-closed. If the platform boundary cannot be established, Ryu does not silently
fall back to an unconfined managed Codex process. Other ACP agents retain their existing scanner
and permission behavior until they are migrated to the same process contract.

## Scope

This page covers the sandbox around **tool execution**. Plugin code is a separate question with a separate answer - see [Plugin isolation](/docs/security/plugin-isolation).
