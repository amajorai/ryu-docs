---
title: "Value Types"
description: "Mark Secret Vault values as config, secret, or sealed, and what each type allows."
---

Every Secret Vault value has a type that says how sensitive it is. The type decides whether the
value can leave the vault as plaintext. It never changes whether the value can be used: apps, MCP
servers, tools, and the credential broker resolve all three types the same way.

| Type | Meaning | Reveal and export |
|---|---|---|
| `config` | Plain configuration such as a log level or a public URL. | Yes, with `read`. |
| `secret` | The default. Hidden until someone reveals it. | Yes, with `read`. |
| `sealed` | Use-only. Apps and tools can use it, but nobody can read it back. | Never. |

Values written before types existed are `secret`.

## Sealed values

A sealed value resolves wherever its name is used, through `secret:` references, MCP and plugin
credentials, Team and Organization values that nodes resolve at run time, and the
[credential broker](/docs/security/secret-vault-broker). It never comes back as plaintext:

- **Reveal** is refused for every caller, including people with `read` and service-account keys.
  The answer is `403` with `vault_denied`. Desktop and the web console show **Sealed** in place of
  a Reveal button.
- `export` and `ryu-cli secrets export` leave sealed values out. A sealed value still shadows a
  lower-precedence value with the same name, so an export never substitutes the imported value
  that runtime resolution would not pick. This holds across tiers too: a sealed value in your own
  or this node's vault also keeps a shared Team or Organization value with that name out of the
  export.
- Encrypted snapshots (`POST /api/vault/snapshot`) leave sealed values out.
- External sync destinations (GitHub Actions, Vercel, AWS Secrets Manager, Google Secret Manager,
  and KV stores) are never sent a sealed value. Values of the other types in the folder still sync.
- A leak scan with stored values never compares text against a sealed value, so a scan cannot
  confirm which string equals it.
- `ryu-cli secrets run` without `--broker` gets its values from an export, so a sealed value is not
  in the command's environment. Use `ryu-cli secrets run --broker SERVICE -- CMD`, a plugin or MCP
  credential, or a `secret:` reference to use it.
- The Vault-compatible KV v2 read of a folder that holds a sealed key is refused, and so is
  `subkeys` on a sealed JSON value, because its key names are part of the value.
- Importing a file never reports a sealed value as unchanged, so an import cannot confirm a guess.
  An imported value written over a sealed one stays sealed.

Sealing is one-way. A sealed value cannot be changed back to `config` or `secret`. To stop using
it, delete it or write a new value under another name. Writing a new version of a sealed value
keeps it sealed.

## AI coding agents

When `ryu-cli` runs inside a coding agent such as Claude Code, Cursor, or Codex (see
[When an AI coding agent runs the CLI](/docs/security/secret-vault#when-an-ai-coding-agent-runs-the-cli)),
redaction follows the type. The agent may read `config` values; `secret` and `sealed` values stay
out of what it sees.

- `ryu-cli secrets get NAME` prints the value only when it is `config`. A `secret` or `sealed`
  value is refused before it is read. The check uses the environment the read uses (`default`
  when `--env` is not given), and without `--scope-id` every owner's value with that name, scope,
  and folder must be `config`. Earlier versions are refused, because they may predate a change to
  `config`.
- `ryu-cli secrets export` writes only the names whose every value, in any scope, environment, or
  folder, is `config`, and says on stderr how many it left out. `--name` and `--tags` narrow it
  further.
- `ryu-cli secrets run`, when it sends the command through the credential broker, also puts the
  `config` values in the command's environment. Credentials still reach it only through the broker.
  This does not apply with `--isolation=container`.
- `ryu-cli secrets set NAME --type config` without a new value is refused, because it would mark
  the stored value, which may be a secret, as readable. Pass the new value in the same command.
- `ryu-cli secrets rollback` is refused, because an earlier version may have been written as a
  secret.
- The types are checked before and after the value is read. If one changes in between, or the
  types cannot be listed, nothing is printed and no `config` value is added to a run. A listing
  without its Team and Organization values (because the control plane could not be reached)
  counts as one whose types cannot be listed.
- A machine token (`RYU_VAULT_TOKEN`) cannot list types, so `get` and `export` refuse with one.

A person at an interactive terminal can still add `--human` to lift these checks for one command.
Without an interactive terminal, the checks stay on.

## Setting the type

- **Desktop**: pick **Type** when you add a value, or change it in the value's details.
- **Web console**: pick **Type** in the value editor of the organization Vault.
- **CLI**: `ryu-cli secrets set NAME VALUE --type config` (or `secret`, `sealed`).
  `ryu-cli secrets list` shows each value's type.
- **API**: send `metadata.valueType` (`config`, `secret`, or `sealed`) with
  `PUT /api/vault/secrets/{name}`, or change it with `PATCH /api/vault/secrets/{name}/metadata`.
  Listings return `metadata.valueType` for every value.

A write that leaves out `valueType` keeps the stored type, so rotating a value never resets it.
In a protected environment, changing the type is a change like any other and follows the same
approval rules.
