---
title: "OAuth Broker Services"
description: "Let agents call an OAuth-protected API through the credential broker with your connected plugin account, refreshed automatically and never handed to the agent."
---

A broker service can authenticate with an OAuth connection instead of a stored secret. When you
have connected a plugin's remote MCP server (see
[MCP authentication](/docs/security/authentication-mcp#plugin-remote-mcp-oauth)), a service with
`oauth` auth adds `Authorization: Bearer <access token>` from that connection to each matching
request. The broker refreshes the token shortly before it expires, and if the API still answers
`401`, it refreshes once more and resends the request, so a long agent run keeps working. The agent never sees the token, and the request log never records it.

```json
{
  "name": "linear",
  "host": "mcp.linear.app",
  "auth": {
    "type": "oauth",
    "plugin": "@ryu/linear",
    "server": "linear",
    "resource": "https://mcp.linear.app/mcp",
    "scopes": ["read", "write"]
  }
}
```

| Field | Meaning |
|---|---|
| `plugin` | The plugin that owns the MCP server |
| `server` | The MCP server's name in that plugin's manifest |
| `resource` | The exact MCP server URL the connection was made for |
| `profile` | The identity profile that holds the connection (default `personal`) |
| `clientId` | The plugin's declared OAuth client ID, when it has one |
| `scopes` | Scopes the service needs (optional) |

## Rules

- **The token goes only to its own host.** The service's `host` must be the host of `resource`. A
  wildcard host, a different host, or a different port is rejected when the service is saved.
- **HTTPS only.** `resource` must use `https://`; plain `http://` is accepted only for a loopback
  address. `allowInsecureHttp` is rejected for any other host.
- **Each session uses its minter's own connection.** A session you mint uses your connection. On a
  personal node, runtime and machine-token sessions use the node owner's connection. On a shared
  node, a session with no signed-in user cannot use OAuth services.
- **The connection's access level still applies.** `GET`, `HEAD` and `OPTIONS` count as reads,
  `POST`, `PUT` and `PATCH` as writes, and `DELETE` as a delete. A read-only connection refuses
  writes, and other methods are always refused. A
  [WebSocket](/docs/security/secret-vault-broker-websockets) counts as a delete, because its
  messages can write or delete, so only a connection that allows deletes can open one.
- **Passport remote mode.** A node that keeps OAuth credentials in Passport cannot inject them
  through the local broker, so these services report `unavailable`.

## Status and refusals

`GET /api/vault/broker/services` returns an `oauthStatus` map, and agent discovery
(`GET /api/vault/agent/broker/discover`) adds an `oauth` object to each OAuth service. Neither
includes a token:

| `state` | Meaning |
|---|---|
| `connected` | Connected with every required scope |
| `needs_scopes` | Connected, but missing the scopes listed in `missingScopes` |
| `needs_connect` | No connection exists yet |
| `reauth_required` | Refresh was rejected or the server changed; reconnect |
| `unavailable` | This node cannot use OAuth connections for brokered requests |

When a connection is not ready, the broker refuses the request before it reaches the upstream, so
the API never receives a token it would reject. The refusal names the service and its status, and
the `x-ryu-broker-error` header carries the code:

| Code | HTTP | What to do |
|---|---|---|
| `oauth_needs_scopes` | 403 | Reconnect and grant the listed `missingScopes` |
| `oauth_connect_required` | 428 | Connect the account in Ryu |
| `oauth_reconnect_required` | 428 | Reconnect the account in Ryu |
| `oauth_access_denied` | 403 | Raise the connection's access level, or use a read request |
| `oauth_unavailable` | 503 | Use a node that holds its OAuth credentials locally |
| `oauth_token_failed` | 502 | The provider did not return a token; try again |
