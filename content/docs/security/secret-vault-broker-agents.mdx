---
title: "Brokered Agent Runs"
description: "How agents that Ryu starts get their own credential-broker session, and when Ryu leaves a run unbrokered."
---

When the broker is listening and the active environment has at least one enabled service and
either the `passthrough` unmatched-host policy or the agent-run opt-in described below, each agent
Ryu starts in a trusted folder (Ryu's own engine, Claude Code, and other ACP agents) gets its own
broker session over that environment's enabled services, plus the broker proxy environment. The session is revoked when the agent process ends,
and lasts at most 24 hours. These sessions show in the session list with a `runtime:` minter, and
they never use payment cards.

## Agent identities

Each kind of agent Ryu starts has its own [machine identity](/docs/security/secret-vault-engines#machine-identities):
`ryu-agent-pi`, `ryu-agent-claude-code`, and `ryu-agent-acp`. Ryu creates it, with no policies, the
first time it brokers a run of that kind. Attach policies to it, or bind them to `machine:<id>`, to
decide what those runs may do:

- With no policies, runs work as described above.
- With policies, each run's session is minted by the identity. It covers only the enabled services
  whose `sys/broker/<service>` the policies give `use` on, and it resolves `secret:` references and
  cards under those policies alone, with no defaults. When the policies allow no enabled service,
  the run is left unbrokered.
- Disabling the identity ends the sessions of runs already going and leaves new runs unbrokered.

Each identity holds at most 10 live broker sessions at once, so further concurrent runs of that kind
start unbrokered until one ends.

## When a run is brokered

Ryu brokers a run only when doing so neither cuts the agent off nor widens what it can reach. The
agent and every tool it starts (shells, package managers, MCP servers) send their HTTPS through the
broker, and requests to hosts that no service covers follow the environment's unmatched-host policy.
So Ryu brokers a run only when the folder is trusted and the policy is `passthrough` (or the
environment opts in under `deny`), and leaves it unbrokered when:

- the environment has no enabled services;
- the policy is `deny` (the default) and the environment has not opted in, since `deny` refuses
  every host no service covers and would cut the agent off from the network it otherwise has;
- the environment opted in under `deny` but the agent reaches its model provider directly instead
  of through the Ryu Gateway (Claude Code signed in to its own account, for example), since `deny`
  would refuse the model's own traffic;
- the folder is not trusted, under any setting (see below);
- the agent's account access is limited;
- a proxy (`HTTPS_PROXY`, `HTTP_PROXY`, or `ALL_PROXY`) is already set for Core or the agent, since
  the broker connects upstream directly.

To broker agent runs, run the agent in a trusted folder and either set the active environment's
unmatched-host policy to `passthrough` on the
[Credential Broker](/docs/security/secret-vault-broker#requests-to-unknown-hosts) page, or keep
`deny` and turn on **Broker agent runs in trusted folders** in the same environment settings (Vault,
**Broker** tab, **Settings**). With the opt-in, a brokered agent and every tool it starts can reach
only the hosts your services cover; anything else gets the broker's `403` with a proposal hint. The
opt-in is per environment, off by default, and needs `admin` on `sys/broker` to change.

### Untrusted folders

An agent in a folder you have not trusted is never brokered, whatever the policy or opt-in. Its
sandbox cuts its network down to the Ryu Gateway (and Core, for Ryu's own engine). Brokering it would
mean opening the broker inside that cut, which lets code from a folder you have not vetted send
authenticated requests, as you, to every service in the session. Nothing about the folder narrows
which services those would be, and trusting the folder is the one decision you made about it. To
broker an agent, trust its folder, or run it in a cloud task's
[Box](/docs/standalone/box-network-secrets), whose network secrets are added on the way out without
the agent holding them, and which can reach the broker services you
[mark for Boxes](/docs/standalone/box-network-secrets#vault-broker-services-in-a-cloud-task-box)
through a session of its own.

The run's child environment is the same proxy environment `ryu-cli secrets run --broker` sets, listed
on the [Credential Broker](/docs/security/secret-vault-broker#run-a-command-through-the-broker)
page. As with any proxy variable, a process can ignore it; the broker narrows what an agent holds,
it does not force every connection through itself.

## Command tools

A plugin's `command` tool (a local binary Ryu runs for an agent) is not brokered unless its manifest
names the services it needs, one `vault:broker:<service>` entry per service in `permission_grants`:

```json
{
  "permission_grants": ["tool:command:gh", "vault:broker:github"]
}
```

Each call then gets its own broker session over those services, if they are enabled in the active
environment, and the binary gets the broker proxy environment. The session ends when the binary
exits, and it never uses payment cards. There is no wildcard: the session covers only the services
the manifest names, and other hosts follow the environment's unmatched-host policy, so under `deny`
the binary reaches only those services.

`vault` is a reserved grant namespace, so a plugin cannot approve these grants for itself. The
Gateway must allow each one (for an operator, by listing it in `RYU_MARKETPLACE_GRANT_ALLOWLIST`), or
the plugin cannot be enabled.

A tool that names services does not run at all, and returns why, when the broker is not listening,
none of its services is enabled in the active environment, or the agent calling it has limited
account access. A tool cannot name services and also declare `egress_url_arg`; the manifest's
per-call URL proxy and the broker cannot both carry the same binary's traffic.

## Ask for access from an agent

When the broker refuses a host that no service covers, its `403` answer carries a `proposalHint`
that names the ways to ask for it. A brokered agent already holds its broker session in its proxy
variables, so it needs no other credential for these:

```sh
ryu-cli secrets broker discover
ryu-cli secrets broker propose --host api.linear.app --credential secret:LINEAR_TOKEN \
  --message "Read the issues assigned to me"
ryu-cli secrets broker proposal prop_…
```

`discover` lists the services and placeholders the agent may use. `propose` asks for a host, with
the credential it needs named by reference (`secret:NAME`, `op://…`, or `bws://…`), never by value.
`--auth` picks how the broker adds it (`bearer`, the default with a credential, `api_key` with
`--header`, or `passthrough`). `proposal ID` exits `3` while the proposal waits for a person, `0`
once it is approved, and `1` when it is rejected or expired.

Agents that use MCP get the same three actions as tools: `ryu-mcp` started inside a brokered agent
registers `ryu_broker_discover`, `ryu_broker_propose`, and `ryu_broker_proposal`. Outside a brokered
agent, these commands and tools need a machine token (`RYU_VAULT_TOKEN`).

Neither sends the session or token to a Core it cannot verify. Against a local `http://` Core, the
CLI and `ryu-mcp` first have Core prove that it holds the agent's session (or the node token, when
one is set), and they send the credential only on the connection that passed. A remote `http://`
address is refused; use `https://`. When `ryu-mcp` cannot verify Core, it leaves the three tools out
and says why on stderr.

The [hosted MCP endpoint](/docs/extend/integrate/mcp-integration) (`/mcp/<agent_id>`) offers the
same three tools when the MCP request carries the agent's broker credential: its `rvb_` session in
an `X-Ryu-Broker-Session` header, or a machine token in `X-Ryu-Vault-Token`. The node token that
admits the request is not broker access on its own, so without one of these headers the tools are
not listed. An agent with a restricted tool list must name each tool (or `*`). Read-only and trial
agents can discover and check proposals but not file them, and verified-plan-only agents get none
of the three. The tools count against the same [rate-limit quotas](/docs/security/secret-vault-tokens#quotas)
as the agent routes, and a token or session bound to address ranges works only when the MCP request
comes from an allowed address. On the same request, `tool_search` finds them (for example, a search
for "broker proposal" or "credentials") and `describe` returns their argument schemas, so an agent
that follows the endpoint's search-first instructions can find them after a broker `403`. A tool the
request may not use is neither listed nor found.

## Proposal notifications

When an agent files a [proposal](/docs/security/secret-vault-broker#proposals), or a
password-manager reference waits for its first approval, Ryu sends one notification for it. It goes
to the person behind the request (the person who started the agent's broker session, or the signed-in
account on the node when no person is named): an Inbox entry, a desktop notification, and a push
to their registered phones. When nobody is signed in, every connected desktop shows it instead.

Tapping the notification opens the **Broker** tab on the Vault page with that proposal highlighted,
ready to approve or reject. The in-app notification has an **Open** button that does the same. When
someone already decided the proposal, or it expired, the tab says so instead. The notification names the environment, the hosts, and the credential
names the agent asked for. It never includes the agent's message or any value.

On a phone, tapping the push opens a **Broker proposal** screen in the Ryu mobile app. It looks for
the proposal on the connected node first, then on the phone's other nodes, and names the node when
the proposal is on another one; approving or rejecting goes to that node. It shows the agent's
message, the environment, the hosts, and the credential names, with **Approve** and **Reject**
buttons while the proposal is pending. The phone never asks for or shows a value: approving there
adds the requested services, and values for requested credentials are added on the desktop, in
Vault. Approving a password-manager credential-use request on the phone allows one use; choose a
longer grant (1 hour, 24 hours or 30 days) on the desktop. When no node lists the proposal because
it was already decided or expired, the screen says so.
