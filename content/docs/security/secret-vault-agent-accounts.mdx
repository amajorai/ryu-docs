---
title: "Agent Accounts"
description: "Let agents sign up for and log in to websites with their own vault-held passwords and authenticator codes, without the agent ever seeing a credential."
---

An agent that signs up for a website needs a login of its own. Agent accounts keep that login in the
[Secret Vault](/docs/security/secret-vault) and let the agent use it by id. The agent never sees the
password, the authenticator seed, or a one-time code: the [Browser](/docs/apps/browser) app types
them straight into the page.

## How it works

1. **Create.** The agent calls `chromium.create_account` with the site and, optionally, a username
   or email. Ryu generates a strong password inside the vault and returns only metadata: the account
   id, site, username, email, and whether a password and authenticator are set.
2. **Fill.** On the sign-up or login form, the agent calls `chromium.fill_credential` with the
   account id, the field (`username`, `email`, `password`, or `totp`), and the element to fill. The
   browser asks the vault for that one value and types it into the page. The tool result says only
   that the field was filled.
3. **Enroll 2FA.** When a site shows an authenticator setup QR code or setup key, the agent calls
   `chromium.capture_totp` and points it at the QR code or key. The browser reads the secret and
   stores it with the account. The agent gets only `enrolled: true`.
4. **Log in later.** The agent finds the account with `chromium.list_accounts`, fills the username
   and password, and fills `totp` when the site asks for a code. The vault computes the current
   6-digit code at fill time.

## Safeguards

- **Origin binding.** A value is released only for a page on the account's own host, over HTTPS
  (plain HTTP is allowed only for `localhost`); `www.` is ignored. Subdomains do not match, because
  a subdomain can serve other people's content, so a site that signs in on a separate host such as
  `accounts.example.com` needs an account saved for that host. A phishing page on another host gets
  nothing, even if the agent is tricked into filling there.
- **Field checks.** The browser fills a password only into an `<input type="password">`, and fills
  nothing into a field that has focus inside an embedded frame.
- **Per-agent folders.** Each agent's accounts live in its own folder of the `agents` environment.
  One agent can neither list nor fill another agent's accounts.
- **No secret in tool results.** Creating and listing accounts return metadata only. Values reach
  only the browser, through a capability that requires the reviewed `vault:fill` grant. No route
  that a tool call can reach returns a secret.
- **Audit.** Every password or authenticator release is an audited item reveal, recorded on the
  item's timeline without the value.

Authenticator keys must use the common defaults (SHA-1, 6 digits, 30 seconds). A setup page that
offers only other parameters is refused with a clear error.

## Manage agent accounts

Agent accounts are for agents whose **Identity** setting is **Its own identity** or **Both**. An
agent set to **Acts as you** keeps the agent accounts it already has while its account access is
unrestricted; once you limit it to selected accounts, Ryu refuses to create or fill an agent account
for it. When an agent's account access is limited, it can fill only the agent accounts you selected.
An account it creates for itself is added to its selection, so it can use it right away. Every agent
account still appears in the agent's **Account access** list, so you can select or clear it. See
[Choose which accounts an agent can use](/docs/surfaces/desktop/user-guide/agent-account-access#choose-which-accounts-an-agent-can-use).

Apps you connect to the agent's own Composio user are separate from these Vault logins; see
[Connect apps for an agent](/docs/surfaces/desktop/user-guide/agent-account-access#connect-apps-for-an-agent).
An event trigger on one of those apps runs only that agent, and Ryu checks the agent's identity and
account access again on every event.
An agent with limited account access, or set to **Its own identity** or **Both**, can't read the
Vault's files from its shell either: its
engine runs in a sandbox that hides Ryu's data folders, on computers where that sandbox is
available.

Agent accounts are ordinary [typed items](/docs/security/secret-vault-items#typed-credential-items) of kind
`agent_login` in the `agents` environment, under one folder per agent. You can view, reveal, change,
or delete them in the Vault like any other item, or with `ryu-cli secrets items list --env agents`.

Access follows item policies on `sys/items/agents/<folder>/*`. `list` to list an agent's accounts
and `write` to create one. To require `admin` for new agent accounts, mark the `agents` environment
as protected.

## API

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/api/vault/agent-accounts` | Lists the calling agent's accounts (metadata only); `?site=` filters by site |
| `POST` | `/api/vault/agent-accounts` | Creates an account with a generated password; body `{site, username?, email?, password_length?, label?}` |

The calling agent is set by Core, not by the request body.
