## 7. Choosing an MCP authentication boundary

Ryu has several MCP-shaped surfaces. They do not all need the same credential.

```mermaid
flowchart TD
  MCPClient["MCP client or host"] --> Surface{"Which MCP surface is it using?"}
  Surface -->|"Website /mcp"| Public["Anonymous, read-only website MCP"]
  Surface -->|"Official Ryu remote resource"| Official["Better Auth OAuth, PKCE, scopes, consent"]
  Surface -->|"Direct Core MCP"| Local["Node bearer, paired token, or managed user JWT"]
  Surface -->|"Plugin's remote MCP server"| Plugin["Core OAuth broker and Identity Vault"]
  Public --> NoAccount["No account or node access is granted"]
  Official --> OrgPolicy["Organization and Gateway policy still apply"]
  Local --> NodePolicy["Controls one particular Core node"]
  Plugin --> ProviderPolicy["Sends provider token only to declared resource"]
```

The public website MCP endpoint is intentionally anonymous and read-only. It is not the official
Ryu control plane and does not grant account or node access.

## 8. Official Ryu MCP OAuth

The official server-side MCP authorization service is the right place for a remote MCP client that
needs consented access to protected Ryu resources. The client discovers the authorization metadata,
uses PKCE, obtains user consent, and receives a scoped access token.

```mermaid
flowchart TD
  Client["Remote MCP client"] --> Discovery["Discover OAuth and protected-resource metadata"]
  Discovery --> Register["Register or reuse an OAuth client"]
  Register --> Challenge["Create PKCE verifier and challenge"]
  Challenge --> Authorize["Open Ryu authorization endpoint"]
  Authorize --> Session["User signs in or reuses account session"]
  Session --> Consent["User reviews requested MCP scopes"]
  Consent --> Code["Ryu returns an authorization code"]
  Code --> Token["Client exchanges code plus verifier"]
  Token --> Access["Scoped MCP access token"]
  Access --> Resource["Call the protected Ryu MCP resource"]
  Resource --> Policy["Organization membership and Gateway policy enforce each call"]
```

For a local or self-hosted direct Core MCP connection, use that node's bearer
or pairing flow. For a managed node selected by Desktop, Core accepts the
short-lived managed `userJwt` after checking organization, team, or personal
ownership. External MCP hosts should use this OAuth path; the hosted service
exchanges the grant for a short-lived exact-node delegation and does not forward
the original OAuth token to Core. See [MCP security](/docs/extend/mcp/security)
and the [Better Auth MCP plugin documentation](https://better-auth.com/docs/plugins/mcp).

## 9. Plugin remote MCP OAuth

When a plugin connects to another company's remote MCP server, the provider credential belongs to
that provider connection, not to the Ryu account session and not to the node bearer.

```mermaid
flowchart TD
  Plugin["Plugin declares a remote MCP resource"] --> Connect["User chooses Connect"]
  Connect --> Broker["Core OAuth broker starts provider authorization"]
  Broker --> PKCE["Use provider discovery and PKCE when supported"]
  PKCE --> Provider["Provider sign-in and consent"]
  Provider --> Callback["Provider callback returns authorization"]
  Callback --> Seal["Seal grant in the node Identity Vault"]
  Seal --> Call["Plugin requests a tool call"]
  Call --> Inject["Inject provider token only at dispatch time"]
  Inject --> Resource["Send token only to the declared provider origin"]
  Resource --> Audit["Record governed access and audit event"]
  Disconnect["Disconnect plugin account"] --> Delete["Delete or revoke provider grant"]
  Delete --> Resource
```

The model never receives the provider token. Removing the plugin connection revokes this provider
grant; it does not sign the user out of Ryu or revoke unrelated node clients.
