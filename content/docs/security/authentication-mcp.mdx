## Choose an MCP authentication boundary

Ryu has several MCP-shaped surfaces. They do not all need the same credential.

```mermaid
flowchart TD
  MCPClient["MCP client or host"] --> Surface{"Which MCP surface is it using?"}
  Surface -->|"Website /mcp"| Public["Anonymous, read-only website MCP"]
  Surface -->|"Official Ryu remote resource"| Official["Better Auth OAuth, PKCE, scopes, consent"]
  Surface -->|"Direct Core MCP"| Local["Node bearer, paired token, or managed user JWT"]
  Surface -->|"Plugin's remote MCP server"| Plugin["Core OAuth broker and Passport"]
  Public --> NoAccount["No account or node access is granted"]
  Official --> OrgPolicy["Organization and Gateway policy still apply"]
  Local --> NodePolicy["Controls one particular Core node"]
  Plugin --> ProviderPolicy["Sends provider token only to declared resource"]
```

The public website MCP endpoint is anonymous and read-only. It is not the official Ryu control
plane and does not grant account or node access.

## Official Ryu MCP OAuth

Use the official server-side MCP authorization service for a remote MCP client that needs consented
access to protected Ryu resources. The client discovers the authorization metadata,
uses PKCE, obtains user consent, and receives a scoped access token.

An OAuth client can request `mail:read`, `mail:send`, and `mail:manage` for the hosted Mail
tools that Ryu's MCP endpoint serves when the request names no node (see
[hosted Mail tools](/docs/standalone/sdk/mcp-hosted-mail)). On the consent screen they
appear under **Mail**, and you can lower or remove them before authorizing. A grant holds only
the scopes the client requested, so a client that sends and reads mail should request both.

`mail:manage` lets the client create Mail inboxes, and nothing else it covers for an API key.
Ryu never grants it by default. Ryu's OAuth metadata does not list it, an authorization request
with no `scope` leaves it out, and a client asks for it by name after `mail_create_inbox` answers
with an `insufficient_scope` challenge that names `mail:manage`. The consent screen describes it
as "Create Mail inboxes in your organization (each counts toward its inbox allowance)" and leaves
it off until you choose it.

Each level is labelled by what it grants, with a plain description under **Mail**: a client that
requests only `mail:send` is shown **Send**. An app Ryu has not reviewed is marked
**Unverified app**. When it returns you to a web address, the screen names that address; an app
that returns you to a program on your device shows none.

Your consent does not by
itself open an organization's mail: each organization must also allow the app by its client id
(an owner or admin adds it on the organization's Security page), and none is allowed by
default. OAuth clients cannot request any `messaging:*` or `prompts:*` scope; for
those, create a Ryu API key with the scope in the console. A hosted MCP token never reaches Mail's
HTTP API or Managed Agents directly.

On the consent screen, review the application and requested scopes before choosing Authorize
or Deny. Ryu returns you to the application's callback with the approval or denial result.
If the request is incomplete, return to the application and start authorization again. The
server checks the signed request and your account session before completing authorization.

If you are signed out when the application opens Ryu's authorization page, Ryu asks you to sign in
first. After your password and any emailed or authenticator code, Ryu continues to the consent screen
for the same request instead of opening your dashboard.

When an MCP client you have already approved authorizes again for the same permissions, for example
to reconnect, Ryu issues it a new access token without showing the consent screen again. A request
for new permissions shows the consent screen again.

At Ryu's hosted MCP endpoint, earlier access tokens keep working until they expire, you revoke the
application (which also ends its refresh tokens), or the Ryu session you approved them from ends
(you sign out of it, it expires, or it is revoked). They are refused while the application is
disabled. Signing out of a different Ryu session does not end them. If a client asks for
sender-constrained (DPoP) tokens, Ryu accepts such a token only with a valid DPoP proof from that
client's key.

```mermaid
flowchart TD
  Client["Remote MCP client"] --> Discovery["Discover OAuth and protected-resource metadata"]
  Discovery --> Register["Register or reuse an OAuth client"]
  Register --> Challenge["Create PKCE verifier and challenge"]
  Challenge --> Authorize["Open Ryu authorization endpoint"]
  Authorize --> Session["User signs in or reuses account session"]
  Session --> Consent["User reviews requested MCP scopes"]
  Consent --> Code["Ryu returns an authorization code"]
  Code --> Token["Client exchanges code plus verifier"]
  Token --> Access["Scoped MCP access token"]
  Access --> Resource["Call the protected Ryu MCP resource"]
  Resource --> Policy["Organization membership and Gateway policy enforce each call"]
```

For a local or self-hosted direct Core MCP connection, use that node's bearer
or pairing flow. For a managed node selected by Desktop, Core accepts the
short-lived managed `userJwt` after checking organization, team, or personal
ownership. External MCP hosts should use this OAuth path; the hosted service
exchanges the grant for a short-lived exact-node delegation and does not forward
the original OAuth token to Core. See [MCP security](/docs/extend/mcp/security)
and the [Better Auth MCP plugin documentation](https://better-auth.com/docs/plugins/mcp).

## Plugin remote MCP OAuth

When a plugin connects to another company's remote MCP server, the provider credential belongs to
that provider connection, not to the Ryu account session and not to the node bearer.

```mermaid
flowchart TD
  Plugin["Plugin declares a remote MCP resource"] --> Connect["User chooses Connect"]
  Connect --> Broker["Core OAuth broker starts provider authorization"]
  Broker --> PKCE["Use provider discovery and PKCE when supported"]
  PKCE --> Provider["Provider sign-in and consent"]
  Provider --> Callback["Provider callback returns authorization"]
  Callback --> Seal["Seal grant in Passport"]
  Seal --> Call["Plugin requests a tool call"]
  Call --> Inject["Inject provider token only at dispatch time"]
  Inject --> Resource["Send token only to the declared provider origin"]
  Resource --> Audit["Record governed access and audit event"]
  Disconnect["Disconnect plugin account"] --> Delete["Delete or revoke provider grant"]
  Delete --> Resource
```

The model never receives the provider token. Removing the plugin connection revokes this provider
grant; it does not sign the user out of Ryu or revoke unrelated node clients.
