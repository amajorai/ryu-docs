---
title: "Vault Rotation"
description: "How Ryu rotates generated vault values on a schedule, including Team, Organization, and Project values."
---

Part of the [Secret Vault](/docs/security/secret-vault) guide. Ryu can replace a credential on a
schedule and keep every `secret:NAME` reference working. Each new credential is written as a new
version with source `rotate`, so the previous value stays in history and you can roll back.

## Generated values

A value that has both a rotation period (`rotationPeriodSecs`, at least 300) and a generator rotates
on its own once the period has passed. Values on a node and shared values in the control plane both
work this way.

- **User and Node values.** Core's scheduler writes the new value.
- **Team, Organization, and Project values.** The control plane checks every 15 minutes and writes
  each due value as a new version. The audit log gets a `vault.secret.rotate` event with the new
  version number. The value itself is never logged.

A value without a generator is marked **rotation due** and stays that way until someone writes its
next value. Deleted and expired values never rotate. Values in a family workspace are not rotated,
because that vault does not accept writes.

If someone writes a value while a rotation of it is running, their write is kept and the rotation
moves to the next pass. Several control-plane servers can run the job together, and each value
rotates only once.

Scheduled rotation does not go through a change request, even in a protected environment. The
change request covers the step where the rotation period and generator are set.

## Existing accounts

To rotate a credential that belongs to another system, such as a database password, an AWS access
key, or an AI provider key, use a [static role](/docs/security/secret-vault-seal-auth#static-roles).
