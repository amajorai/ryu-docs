Ryu's Secret Vault lets you save a value once and reference it from an MCP server as
`secret:NAME`. Core resolves that reference only while it is dispatching the governed MCP call.
The value is not inserted into the prompt, skill text, tool schema, transcript, or API response.

This works like a GitHub Actions secret, but the reference is explicit:

```json
{
  "mcpServers": {
    "github": {
      "type": "stdio",
      "command": "github-mcp-server",
      "env": {
        "GITHUB_TOKEN": "secret:GITHUB_TOKEN"
      }
    }
  }
}
```

For a remote MCP server, use the same reference in a header:

```json
{
  "type": "streamable-http",
  "url": "https://mcp.example.com/mcp",
  "headers": {
    "Authorization": "Bearer secret:EXAMPLE_TOKEN"
  }
}
```

The reference is safe to keep in `mcp.json`; the secret value is not. Open the Desktop **Vault**
page, or run `ryu-cli secrets set NAME`, to save the value. Listings show the name, scope, environment,
folder, version, and status, never the value.

The Vault page also switches environments, browses folders, shows version history with rollback
and restore, reveals a value when you hold `read` (hidden again after 30 seconds), imports and
exports files, lists pending approvals, and, for administrators, shows the audit log and the seal
state.

Clearing a secret asks for confirmation. Members without shared-secret management permission can
use User and Node scopes; Team and Organization scopes stay disabled for them.

<Callout type="warn">
An MCP server is still a credential consumer. A stdio server receives a resolved value in its
child environment, and a remote server receives it in the configured request header. Grant access
only to a server you trust, and keep that server's tools allowlisted and governed.
</Callout>

## Three credential stores, three purposes

| Store | Holds | How it is used |
|---|---|---|
| **Passport** | Per-domain login state such as cookies, tokens, and sessions | A bound agent can act as the logged-in user on a matching domain |
| **Secret Vault** | User-managed named values such as `GITHUB_TOKEN` or `STAGING_API_KEY` | An MCP header or environment entry resolves `secret:NAME` during dispatch |
| **Provider key vault** | Ryu's provider credentials for the inference fleet | Gateway/provider routing; it is not a user variable store |

An agent that calls HTTP APIs itself can use Secret Vault credentials without holding them through
the [credential broker](/docs/security/secret-vault-broker), a local egress proxy that adds the
credentials to its requests.

Passport profiles remain owner- and tenant-scoped login profiles. They do not automatically become
organization or team identities just because a node has an organization boundary. Secret Vault
scope is the separate mechanism for sharing a named value.

## The four Secret Vault levels

Every value has one scope id. Core pins that id from the current node and verified caller; the
client cannot submit a different user's, team's, organization's, or node's id.

| Level | Scope id | Who can use it | Who can change it | Typical use |
|---|---|---|---|---|
| **User** | Verified user id | That user's governed sessions | The user | A personal GitHub PAT or a private SaaS token |
| **Node** | Exact node id | Governed sessions running on that node | The node operator or authorized node administrator | A node-local service account or staging endpoint token |
| **Team** | Verified team id | Members of that team on an eligible node | Organization administrator or an authorized configuration role | A shared QA environment credential |
| **Organization** | Verified organization id | Members of that organization on an eligible node | Organization administrator or an authorized configuration role | A company-wide integration credential |

On an unbound local node, **User** uses the local operator context and **Node** uses that node's
stable local id. Organization and Team levels require a verified organization-bound context. On a
managed node, Core checks the node's organization, team, or personal-owner boundary before it
considers a value.

User and Node values live in the node's encrypted local store. A Node folder can instead be
backed by an [external store](/docs/security/secret-vault-external) (OpenBao, HashiCorp Vault, or
Infisical); such a folder is read-only in Ryu. Items in 1Password or Bitwarden Secrets Manager
can be used through [password-manager references](/docs/security/secret-vault-password-managers)
(`op://…`, `bws://…`) without storing them, after a person approves each consumer's first use.

Team and Organization values on a managed node live in the control plane, and each node fetches
them at dispatch time. How they are cached, which access policy applies, and when a change, reveal,
or export asks you to confirm it's you are on
[Shared values and confirmations](/docs/security/secret-vault-shared-values).

## Superseding and lookup order

When a governed MCP call asks for `secret:NAME`, Core builds a server-side context from the
current node and the owning chat conversation. It checks candidates in this order:

```text
User → Node → Team → Organization
```

The first available value wins: a user value supersedes a node value, a node value
supersedes a team value, and a team value supersedes an organization value for the same name.

At each level, an exact MCP binding is checked before an unbound value:

```text
same level + mcp:github → same level + any MCP consumer → next level
```

An unbound value is written without a binding and can be used by any supported MCP consumer in
that caller's resolved scope. A bound value uses this metadata shape:

```json
{
  "kind": "mcp",
  "id": "github"
}
```

The binding id is a stable MCP server or owning plugin id, not a display name typed into a chat
prompt. If a value is missing, unauthorized, or cannot be decrypted after a key change, Core
omits the reference instead of sending the literal `secret:NAME` upstream. Deleting a
value does not create a deny/tombstone, so a broader value can become effective again; use a
policy deny to block one.

## MCP, tools, and skills

Secret scope and tool permission are separate checks:

1. the MCP server must be registered and enabled;
2. the calling agent must be allowed to call the tool;
3. the node, user, team, and organization boundary must resolve;
4. the Secret Vault name and optional MCP binding must match;
5. Gateway egress, firewall, budget, audit, and any approval policy still apply.

Skills are instruction packs, not secret containers. A skill can tell an agent to use a GitHub MCP
tool, but the skill body never receives the token. The MCP server's `headers` or `env`
configuration holds the `secret:NAME` reference, and Core performs the substitution at the
tool boundary. A skill allowlist therefore cannot grant a secret by itself, and a Secret Vault
entry cannot grant a tool that the agent is not allowed to call.

The same rule applies to Ryu Apps and imported REST tools: a declared secret reference is only a
server-side input to the known HTTP/MCP consumer. It is never added to model-authored arguments.

## Environments, folders, and references

Every value also has an **environment** (`default`, `staging`, `prod`, …) and a **folder**
(`/`, `/db`, `/payments/stripe`). The same name can hold a different value per environment, and
folders keep large sets of values organized. A reference can name both:

```text
secret:NAME                 node's active environment, root folder
secret:/db/PASSWORD         active environment, /db folder
secret:prod:NAME            prod environment, root folder
secret:prod:/db/PASSWORD    prod environment, /db folder
```

A node's active environment comes from `RYU_VAULT_ENVIRONMENT` (default `default`). Lookup order
inside one folder is unchanged (user, node, team, organization; exact MCP binding before
unbound). A folder can **import** another folder as a lower-precedence fallback, so a shared
`/common` folder can back several service folders without copying values.

A value can opt in to **references** to other values with `${NAME}`, `${/folder/NAME}`, or
`${ENV:/folder/NAME}`, for example `postgres://app:${DB_PASSWORD}@db:5432/app`. References resolve
with the same lookup rules, are limited to five levels, and fail closed on a cycle or a missing
value. Write `$${` for a literal `${`.

Add `#totp` to a reference (`secret:GITHUB_TOTP#totp`) when the value holds a one-time-password
seed: the reference resolves to the current code instead of the seed. See
[One-time passwords](/docs/security/secret-vault-engines#one-time-passwords-totp).

## Versions, expiry, and rotation

Every change creates a version. You can list versions, roll back to an earlier one (which writes a
new version with the old value), soft-delete a value and restore it later, or destroy specific
versions permanently. Each value keeps its newest 20 versions unless you set `maxVersions`
(1 to 100). Writes can pass `expectedVersion` so two editors cannot silently overwrite each other.

Values carry optional metadata: a description, tags, an expiry time, a rotation period, a
generator, and up to 64 non-secret `customMetadata` entries. An expired value stops resolving. A
value whose rotation period has passed is marked **rotation due**; if it has a generator (`{ "kind": "random", "length": 32, "charset":
"alphanumeric" }`), Ryu rotates it automatically and records the new version.
A generator can also name a [password policy](/docs/security/secret-vault-engines#password-policies)
with `{ "kind": "random", "policy": "<name>" }`.

### Version metadata

These routes follow the HashiCorp Vault and OpenBao KV version 2 engine:

- `GET /api/vault/secrets/{name}/metadata` returns detailed metadata and version summaries
  (`list`).
- `PATCH /api/vault/secrets/{name}/metadata` changes metadata with a JSON merge patch and creates no
  new value version. Send `expectedMetadataVersion` to refuse a concurrent change (`write`).
- `PATCH /api/vault/secrets/{name}/data` applies a JSON merge patch to a JSON-object value and
  writes the result as a new version (`write`).
- `GET /api/vault/secrets/{name}/subkeys` returns the value's key structure with `null` leaves,
  never the value (`read`).
- `POST /api/vault/secrets/{name}/versions/delete` soft-deletes specific versions (`delete`), and
  `versions/undelete` brings them back (`write`).

`deleteVersionAfterSecs` (one minute to ten years) soft-deletes non-current versions after that
age. `casRequired` on a value, or on its environment, makes every write send `expectedVersion`.
In a protected environment these changes need `admin`. `GET /api/vault/secrets?limit=…` pages the
list in a stable order (default 200, at most 1000) and returns `nextAfter` for the next `after`;
`detailed=true` adds version summaries and requires paging. Team and Organization values kept by
the control plane do not support these routes yet and answer `501`.

Who may list, use, read, or change a value is set by capabilities and policies. See
[Vault policies and approvals](/docs/security/secret-vault-policies).

## Reading, exporting, and running with values

Values stay write-only by default. Revealing or exporting needs the `read` capability, and every
reveal and export is audited.

| Need | Use |
|---|---|
| See one value | `ryu-cli secrets get NAME` or **Reveal** on the Vault page |
| Run a command with values in its environment | `ryu-cli secrets run --env staging -- npm test` |
| Run a command through the [credential broker](/docs/security/secret-vault-broker) without exposing values | `ryu-cli secrets run --broker openai,github --env staging -- python agent.py` |
| Run it in a container whose only network path is the broker | `ryu-cli secrets run --broker openai --isolation=container -- python agent.py` |
| Manage broker services, sessions, logs, and proposals | `ryu-cli secrets broker services`, `sessions`, `logs`, `proposals [approve\|reject ID]`, `ca` |
| Get or check a one-time code | `ryu-cli secrets totp code NAME`, `ryu-cli secrets totp validate NAME CODE` |
| List, read, write, or delete a typed item | `ryu-cli secrets items list`, `items get KEY`, `items put KEY --type TYPE --field NAME=VALUE[:plain]`, `items delete KEY` |
| Reveal one item field | `ryu-cli secrets items reveal KEY FIELD` |
| Inspect or renew a machine token | `ryu-cli secrets token lookup`, `ryu-cli secrets token renew --increment 3600` |
| Hand a value to another process once | `ryu-cli secrets wrap NAME --ttl 300`, then `ryu-cli secrets unwrap rvw_…` ([response wrapping](/docs/security/secret-vault-tokens#response-wrapping)) |
| Write a `.env`, JSON, YAML, or shell file | `ryu-cli secrets export --format dotenv > .env` |
| Create a Kubernetes Secret | `ryu-cli secrets export --format k8s --k8s-name app \| kubectl apply -f -` |
| Import an existing `.env` or JSON file | `ryu-cli secrets import .env --env staging` |
| Check a repository for leaked credentials | `ryu-cli secrets scan .` |

`ryu-cli secrets run` does not hand its own environment to the command. The command receives the
exported values plus a small set of runtime settings it needs to start: `PATH`, home and
temporary directories, locale, terminal, time zone, certificate bundles, and proxy routing
(`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`). Any other variable in your shell, such as
Ryu tokens, `RYU_VAULT_TOKEN`, master keys, or provider API keys, is not passed through. A proxy
URL that contains a username or password is also withheld. Store a value in the vault and select
it with `--env` and `--path` when the command needs it.

`ryu-cli secrets scan` looks for common credential shapes (cloud keys, Git hosting and chat tokens,
private keys, model-provider keys, credentials in URLs) and for exact copies of values stored in the
vault that you may read. Findings show a short redacted preview and a fingerprint, never the value.
Add `ryu-scan:ignore` to a line to skip it.

### Snapshots

`POST /api/vault/snapshot` exports every value you may read, with its metadata, as a file encrypted
with a passphrase you choose (at least 12 characters). It does not depend on the node's keys, so it
restores on another machine with `ryu-cli secrets import FILE --format snapshot`. Version history,
audit rows, and engine keys are not included.

## API summary

The protected Core API lives under `/api/vault`. The main routes:

| Method | Route | Behavior |
|---|---|---|
| `GET` | `/api/vault/secrets` | Lists visible metadata, filterable by `environment` and `path` |
| `PUT` | `/api/vault/secrets/{name}` | Writes a value and/or metadata; `202` with a change request in a protected environment |
| `DELETE` | `/api/vault/secrets/{name}` | Soft-deletes the selected value |
| `GET` | `/api/vault/secrets/{name}/versions` | Version history, without values |
| `GET`, `PATCH` | `/api/vault/secrets/{name}/metadata` | Detailed metadata; JSON merge patch with `expectedMetadataVersion` |
| `PATCH` | `/api/vault/secrets/{name}/data` | JSON merge patch of a JSON-object value, as a new version |
| `GET` | `/api/vault/secrets/{name}/subkeys` | The value's key structure, never the value (`read`) |
| `POST` | `/api/vault/secrets/{name}/versions/delete`, `/versions/undelete` | Soft-deletes or restores specific versions |
| `POST` | `/api/vault/secrets/{name}/reveal` | Returns the value (`read`, audited) |
| `POST` | `/api/vault/secrets/{name}/rollback` | Restores an earlier version as a new one |
| `POST` | `/api/vault/export` | Effective values for an environment and folder in one format |
| `POST` | `/api/vault/import` | Imports `.env`, JSON, or an encrypted snapshot |

The full list, including environments, folders, policies, approvals, and the routes on the
[policies](/docs/security/secret-vault-policies), [items](/docs/security/secret-vault-items),
[audit](/docs/security/secret-vault-audit), [engines](/docs/security/secret-vault-engines), [seal and machine login](/docs/security/secret-vault-seal-auth),
[token](/docs/security/secret-vault-tokens), [broker](/docs/security/secret-vault-broker),
[external store](/docs/security/secret-vault-external), and
[password manager](/docs/security/secret-vault-password-managers) pages, is in the
[Core API reference](/docs/extend/develop/api-reference/core/vault). Responses that carry metadata are marked
non-cacheable; timestamps are RFC 3339.

## What the Vault does not do

- It does not turn a secret into a model-visible variable such as `process.env` in the prompt.
- It does not grant MCP tools, skills, filesystem access, network egress, or organization membership.
- It does not make a Passport login profile organization-shared.
