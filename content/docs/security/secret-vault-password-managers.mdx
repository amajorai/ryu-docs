---
title: "Password Managers"
description: "Use 1Password and Bitwarden Secrets Manager items from the Secret Vault without storing them: references resolve at use time, and each agent or person's first use waits for a human approval."
---

The [Secret Vault](/docs/security/secret-vault) can use credentials that live in **1Password** or
**Bitwarden Secrets Manager** without copying them into Ryu. You connect an **account**, then name
an item with a **reference** such as `op://dev/GitHub/token`. Ryu fetches the value from the
provider each time it is used and never stores it. The first time an agent or a person uses a
reference, Ryu asks a human to approve that use.

## Accounts

| `provider` | Connects to | Needs |
|---|---|---|
| `1password-connect` | A 1Password Connect server | `address` (the Connect server URL) and a Connect access token |
| `1password-service-account` | 1Password through the `op` CLI | A service-account token; `op` installed on the Core host |
| `bitwarden-sm` | Bitwarden Secrets Manager through the `bws` CLI | A machine-account access token; `bws` installed on the Core host; optional `address` for a self-hosted server |

Add an account with `POST /api/vault/password-managers/accounts`, for example:

```json
{ "name": "work", "provider": "1password-connect", "address": "https://connect.example.com", "token": "…" }
```

or from the CLI, which reads the token from standard input so it never appears in your shell
history or the process list:

```bash
op read "op://Private/Connect token/credential" | \
  ryu-cli secrets pm add work --provider 1password-connect --address https://connect.example.com
```

The token is encrypted with the vault's keys and is never returned, logged, or audited. Ryu passes
it to `op` or `bws` only through that program's environment (`OP_SERVICE_ACCOUNT_TOKEN`,
`BWS_ACCESS_TOKEN`), never on its command line. The CLI is found on the Core host's `PATH` when you
add the account; an operator can point at a specific binary with `RYU_VAULT_PM_OP_BIN` or
`RYU_VAULT_PM_BWS_BIN`. A request can never choose which program runs. A Connect server is reached
through the same SSRF guard as [external secret stores](/docs/security/secret-vault-external): HTTPS,
no redirects, and no link-local or cloud-metadata addresses.

Private network ranges and this host's
loopback interface are refused unless the operator allows them with the same
[external-store settings](/docs/security/secret-vault-external) (`RYU_VAULT_EXTERNAL_ALLOW_PRIVATE=1`
for a Connect server on your network, `RYU_VAULT_EXTERNAL_ALLOW_LOOPBACK=1` for one on the Core host,
which also allows plain `http`).

An account is `connected` or `reconnect_required`. It becomes `reconnect_required` when the
provider rejects its token during a test or a use. `POST …/accounts/{id}/test` (or
`ryu-cli secrets pm test work`) checks the connection without reading a value, and
`POST …/accounts/{id}/token` (or `ryu-cli secrets pm reconnect work`) replaces the token. Removing an
account also removes its grants and rejects its pending approvals.

Managing an account, approving its uses, and revoking its grants needs `admin` on
`sys/password-managers/<account>`.

## References

```text
op://[<account>@]<vault>/<item>[/<section>]/<field>
bws://[<account>@]<secret-id>
```

- `op://` references resolve through a 1Password account. The vault, item, section, and field are
  matched by name or by their 1Password id. Names may use letters, digits, spaces, `.`, `_`, and
  `-`; use the id for anything else.
- `bws://` references name a Bitwarden Secrets Manager secret by its id (a UUID) and resolve to its
  value.
- Add `<account>@` only when you have more than one 1Password account, or more than one Bitwarden
  account, for example `op://work@dev/GitHub/token`. Once a second account of the same kind exists,
  an unqualified runtime template or read stops resolving until you qualify it.

You can use a reference in three places:

- **Credential broker services.** Use the bare reference wherever a
  [broker service](/docs/security/secret-vault-broker) takes a credential, for example
  `{ "type": "bearer", "token": "op://dev/GitHub/token" }`. Creating the service needs `use` on the
  account, and Ryu stores the reference qualified with that account (`op://work@dev/GitHub/token`),
  so the service keeps using the account it was authorized against even if you add another one
  later.
- **Runtime templates.** In an MCP server header or environment template, write
  `secret:op://dev/GitHub/token` or `secret:bws://<id>`. Template words are split on spaces, so use
  ids instead of names that contain spaces. A policy that denies the run's user, team, or role
  `use` on `sys/password-managers/<account>` keeps the reference from resolving.
- **An explicit read.** `ryu-cli secrets pm read op://dev/GitHub/token` (or
  `POST /api/vault/password-managers/read` with `{ "ref": "…" }`) prints the value for a signed-in
  person who holds `read` on the account.

## Approvals and grants

Nothing resolves until a human approves the exact consumer, account, and reference. The consumer
names both who is asking and how, so approving one never approves another:

| Consumer | Who | Example |
|---|---|---|
| `broker:<minter>` | Broker sessions minted by a person, the local operator, or a machine identity | `broker:user:u1`, `broker:operator` |
| `runtime:<server>:<owner>` | One MCP server or plugin's runtime template, for the user who owns the run (or the node when no user does) | `runtime:github:user:u1` |
| `read:<person>` | The explicit read API | `read:user:u1`, `read:operator` |

An approval for your own `ryu-cli secrets pm read` does not let your agents' broker sessions or your
MCP servers use the value, and an approval for one MCP server does not cover another. Every broker
session minted by the same principal shares one consumer, so they share one request and one grant.

The first use files an approval request and does **not** contact the provider. The broker answers
`403 credential_approval_required` with the request id, a template reference resolves to nothing,
and the read API answers `202` with the pending request (the CLI exits with status 3). Asking again
returns the same pending request.

A person with `admin` on the account approves or rejects the request in the desktop app (the
**Broker** tab on the Vault page lists it with the pending proposals, with a choice of how long the
approval lasts), with `ryu-cli secrets pm approvals approve <id> --grant 30d`, or with
`POST /api/vault/password-managers/approvals/{id}/approve`. The grant lasts:

| `grant` | Lasts |
|---|---|
| `once` | One use, within 24 hours |
| `1h`, `24h` | That long |
| `30d` (default) | 30 days |

`ryu-cli secrets pm grants` lists active grants (`--all` includes revoked, used, and expired ones), and
`ryu-cli secrets pm grants revoke <id>` revokes one, so the next use asks again. A machine identity's
broker sessions also need `use` on the account in that identity's own policies.

## Values and audit

Values are fetched for each use and held only in memory for that request. They are never cached,
written to disk or the database, or logged. Every resolution is recorded in the
[audit log](/docs/security/secret-vault-audit#audit) with the provider, account, reference, and
consumer, never the value. With fail-closed auditing on, a use whose audit record is not accepted
is refused and the value is discarded; an approve-once grant is not used up by a refused or failed
resolution. Provider errors are reported without the provider's output: an authentication failure,
a missing item, or an unreachable provider.
