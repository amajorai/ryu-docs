---
title: "Command approval and HITL"
description: "How Ryu scans shell commands before execution, blocks permanent file deletion, and stops for human approval."
---

Before Core runs any shell command a tool produced, it sends the command to the Gateway's exec-governance scanner. The scanner classifies the command and returns a verdict - allow, deny, or approval required. This is the human-in-the-loop gate that sits between untrusted model output and your shell.

## Modes

The mode comes from `RYU_EXEC_APPROVAL_MODE`. **The gate is armed whenever that value is anything
other than `off`, including when it is unset** — disarming is explicit, never a default. That
posture is what keeps a headless (non-interactive) run from auto-approving unscanned commands.

The desktop writes the mode as a preference (**exec-approval-mode**) and Core applies that change
to the live scanner immediately. A hand-exported env var wins over the stored preference, so an
operator can force the gate on regardless of what the desktop has saved.

| Mode | Wire value | Behavior |
|---|---|---|
| Manual | `manual` | Every matched pattern requires human approval |
| Smart | `smart` | A cheap classifier auto-allows low-risk commands, auto-denies clearly dangerous ones, and escalates the uncertain to human approval — see [Local classifier tier](/docs/core/classifier-tier) |
| Off | `off` | Pattern approval is disabled; the permanent-deletion and hardline blocks below still always deny |

A session or global YOLO bypass, where one exists, can skip pattern approval - but the hardline blocklist ignores mode and YOLO entirely.

## Permanent deletion and the hardline blocklist

Ryu has a permanent-deletion guard above ordinary approval modes. It returns `deny` before a
command reaches a shell, even when pattern approval is `off`, the Gateway is unreachable, or a
managed rule would otherwise allow the command. The guard covers:

- `rm`, `unlink`, `rmdir`, `shred`, Windows `del`/`erase`/`rd`, and PowerShell removal commands
- `find -delete` and `rsync --delete`
- `git clean`, `git reset --hard`, and bulk `git checkout`/`git restore`
- common Python, Node, Ruby, and Perl deletion APIs
- raw-disk writes and destructive storage tools such as `dd ... of=/dev/...`,
  `mkfs`, `wipefs`, `blkdiscard`, `fdisk`, `parted`, and `diskutil eraseDisk`
- host power controls such as `shutdown`, `reboot`, `halt`, and `poweroff`
- explicit file-deletion patches and filesystem-shaped MCP delete tools
- literal nested deletion commands inside `bash -c`, `bash -lc`, `sh -c`, `zsh -c`, `cmd /c`, and PowerShell wrappers

The existing catastrophic hardline cases also always return `deny`, regardless of mode, YOLO, or
any ordinary approval rule. They are catastrophic and have no legitimate agent use.

- `rm -rf /` and its variants
- `rm -rf --no-preserve-root`
- the fork bomb `:(){ :|:& };:`
- `mkfs.*` targeting a root or mounted device
- `dd if=/dev/zero of=/dev/sd*` (disk zeroing)
- piping an untrusted URL straight to a shell at the filesystem root

Ryu never silently rewrites a blocked command. Use the verified recoverable mechanism instead:

- macOS: `/usr/bin/trash <absolute-path>`; do not add `--`
- Linux: the installed `gio trash` or `trash-put` command
- Windows: the verified PowerShell helper, using .NET's `Microsoft.VisualBasic.FileIO`
  `DeleteFile`/`DeleteDirectory` APIs with `RecycleOption.SendToRecycleBin`

These are host-side recovery actions. A confined agent may be unable to execute the Trash helper
because the OS deletion boundary intentionally denies unlink/removal to the agent itself; ask the
user or host broker to perform the recoverable move.

If the host has no reliable recoverable mechanism, Ryu refuses to launch its managed Codex route
until one is configured. There is no configuration or approval override for permanent deletion;
the legacy `RYU_ALLOW_PERMANENT_DELETE` variable is ignored.

On Windows, Ryu probes PowerShell and the .NET Recycle Bin API before starting a managed Codex
route. The helper uses `Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile` or
`DeleteDirectory` with `RecycleOption.SendToRecycleBin`; if that API is unavailable, Ryu fails
closed instead of offering a permanent-delete fallback. See the [Microsoft API reference](https://learn.microsoft.com/en-us/dotnet/api/microsoft.visualbasic.fileio.filesystem.deletefile).

## Pattern categories

Beyond the hardline set, roughly forty compiled regex patterns flag commands for approval (in `manual`) or classification (in `smart`). Patterns are compiled once at the top level, never inside the request path.

| Category | Examples |
|---|---|
| Recursive destructive | `rm -r`, `chmod 777 -R`, `chown -R root` |
| System modification | `mkfs`, `dd if=`, writes to `/dev/sd*`, `/etc/`, `~/.ssh/` |
| Service control | `systemctl stop/restart/disable/mask` |
| Process kill | `kill -9 -1`, `pkill -9` |
| Code execution | `bash -c`, `python -c`, `curl \| sh`, `bash <(curl ...)` |
| Sensitive overwrites | `tee` or `>` / `>>` to sensitive paths |
| Dangerous combos | `find -exec rm`, `xargs rm`, `sed -i` on `/etc/` |

## The scan endpoint

Core posts the command to the Gateway's exec-governance plane before execution.

```
POST /v1/exec/scan
```

Request:

```json
{
  "backend": "local",
  "command": "rm -rf ./build",
  "session_id": "sess_123",
  "agent": "coder"
}
```

Response:

```json
{
  "decision": "approval_required",
  "reason": "matched recursive destructive pattern",
  "findings": [
    { "pattern": "rm -r", "category": "recursive_destructive", "severity": "high" }
  ]
}
```

`decision` is one of `allow`, `deny`, or `approval_required`. Each finding carries the matched `pattern`, its `category`, and a `severity` of `low`, `medium`, `high`, or `critical`.

## How Core maps the verdict

| Verdict | Core action |
|---|---|
| `allow` | Proceed and run the command |
| `deny` | Block, and post an exec audit event |
| `approval_required` | Depends on the exec path (see below) |

How `approval_required` resolves depends on where the command originated:

- Core PTC and tool-exec path: this path is synchronous and deadline-bounded, and there is no in-process machinery to await an approval decision, so `approval_required` currently fails closed - deny, audit, and log. Wiring a true blocking approvals-inbox gate here is follow-on work.
- Interactive ACP seam: the request surfaces to the user as a permission prompt and execution blocks on their decision (allow or reject). In headless ACP sessions there is no human to ask, so `approval_required` also fails closed to reject.

## Fail-closed

If the scanner is unreachable, Core default-denies. The only escape hatch is `RYU_ALLOW_GATEWAY_FALLBACK=1`, which mirrors the exec-budget fallback semantics exactly. Do not set it in a shared or server deployment.

That fallback does not bypass the permanent-deletion guard. Permanent deletion remains denied
even when the ordinary scanner is disabled, unavailable, or given an allow rule.

## ACP seam

ACP agents (Claude Code, Codex, and the flagship Pi engine) run their own shell, so Ryu gates them at the ACP permission-request seam. When an agent asks to run a tool and `RYU_EXEC_APPROVAL_MODE` is not `off`, Core extracts the command from the request and runs it through the same scanner before granting: a `deny` verdict rejects the permission outright - even in a headless session that would otherwise auto-approve - and `approval_required` rejects in headless mode or surfaces to the user in interactive mode.

**File-mutating tools are gated alongside shell execution.** Native coding agents do not run `sed` to
edit a file — they call a dedicated tool shaped `{ file_path, content }` or `{ file_path, new_string }`
with no `command` field at all, so a shell-only scan would let every write slip the gate. For
`Write`/`Edit`/`MultiEdit`/`NotebookEdit` and their equivalents, Core synthesizes a `write <path>`
string and scans that, so a policy denying writes under `.ssh`, `.env`, or `/etc` still fires.
Read-only tools that carry a path but no write payload (`Read`, `Grep`) are deliberately not swept in.

Command extraction is otherwise best-effort (the scanner is accident prevention, not containment): a
tool call from which neither a command nor a write target is recoverable is not scanned. ACP
agents are first-party binaries that legitimately need their own credentials, so Ryu gates their
commands rather than scrubbing their environment - see [Credential and environment scrubbing](/docs/security/credential-scrubbing).

For the Ryu-managed Codex entry, Ryu also materializes an isolated Codex home with a durable global
deletion instruction, user-level `forbidden` command rules, `workspace-write` and `on-request`
defaults when those settings are absent, and a `PreToolUse` hook. The hook is intentionally
defense in depth: Codex requires the user to review and trust non-managed hooks, and Core's local
guard still denies permanent deletion if the hook is skipped, disabled, or bypassed. Ryu never
edits the user's normal `~/.codex` configuration.

Managed Codex also starts through Ryu's OS-aware child runner. Linux installs a Landlock rule that
denies unlink, directory removal, and rename; macOS uses its available Seatbelt runner; Windows
fails closed until a native AppContainer runner is available. This protects the removal operation
itself, but does not prevent every destructive write such as truncation or overwrite. Without
backups, a disposable copy-on-write workspace or VM remains the appropriate containment layer.

Other Codex processes launched outside Ryu, and ACP agents Ryu does not manage, are not covered by
Ryu's isolated Codex home. Use their own system or user policy layer for those processes. Command
approval also composes with each agent's permission mode; see [ACP session controls](/docs/extend/develop).

<Callout type="warn">
Smart mode's classifier may be heuristic or a stub at ship - if so, prefer `manual` anywhere the blast radius matters. The permanent-deletion and catastrophic hardline blocks deny unconditionally; ordinary risk patterns still depend on the configured mode. In shared or server deployments keep `RYU_EXEC_APPROVAL_MODE=manual` and never set `RYU_ALLOW_GATEWAY_FALLBACK=1`.
</Callout>
