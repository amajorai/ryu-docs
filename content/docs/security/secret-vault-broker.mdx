---
title: "Credential Broker"
description: "Let agents call APIs through a local egress proxy that injects Secret Vault credentials, so the agent process never holds the real secrets."
---

The credential broker is a local egress proxy for agents and the tools they run. An agent process
is started with `HTTPS_PROXY` pointing at the broker. For each request, the broker finds the
matching **service**, resolves that service's `secret:` references from the
[Secret Vault](/docs/security/secret-vault), adds them to the request, and forwards it upstream with
normal certificate verification. The agent sees only placeholders such as `__OPENAI_KEY__`, so a
prompt injection or a leaked transcript does not expose the credential.

The broker resolves credentials with the `use` capability, as runtime resolution does. It never
needs `read`, and no broker route returns a value.

## Turn on the broker

The broker listens on loopback only, and only when `RYU_VAULT_BROKER_PORT` is set to a port number.
When it is unset or `0`, the broker is off. `GET /api/vault/broker/status` reports whether it is
listening.

## Run a command through the broker

The quickest way is the CLI. It mints a broker session, writes the CA bundle, and starts the
command with the proxy environment:

```sh
ryu-cli secrets run --broker openai,github --env staging --ttl 3600 -- python agent.py
```

The child process gets:

| Variable | Value |
|---|---|
| `HTTPS_PROXY`, `HTTP_PROXY` (and lowercase) | The loopback proxy URL carrying the session token |
| `NO_PROXY` (and lowercase) | `localhost,127.0.0.1,::1` |
| `NODE_EXTRA_CA_CERTS` | The broker CA certificate (Node adds it to its trust store) |
| `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO` | A bundle of the operating system's CAs plus the broker CA |

The combined bundle keeps hosts that the broker tunnels without interception verifiable. A runtime
that ignores these variables needs the broker CA added to its own trust store; download it from
`GET /api/vault/broker/ca.pem` or with `ryu-cli secrets broker ca`.

When the command exits, the CLI removes any CA bundle it wrote and revokes the session. A session
minted with a machine identity's `RYU_VAULT_TOKEN` is not revoked; it ends with its TTL or its
token. Ctrl-C reaches the command through the terminal, and the CLI waits for it to exit and
returns its exit code. If the CLI receives `SIGTERM` or `SIGHUP` while the command runs, or any of
`SIGINT`, `SIGTERM`, or `SIGHUP` before the command starts, it does not wait. It cleans up the same
way and exits with 128 plus the signal number, so a command that is still running loses broker
access.

## Run in an isolated container

A proxy variable is a request, not a rule: a process can ignore `HTTPS_PROXY` and connect
directly. To make the broker the only way out, run the command in a container:

```sh
ryu-cli secrets run --broker openai,github --isolation=container -- python agent.py
ryu-cli secrets run --broker github --container --image node:22-bookworm \
  --mount /srv/fixtures:/data:ro -- npm test
```

`--container` is short for `--isolation=container`, which needs `--broker`. Before it mints the
broker session, the CLI checks Docker, validates the working directory and every mount, and
prepares the images, so a run that cannot start leaves no session behind. Then it:

- creates a Docker bridge network for this run only and starts a relay on the host that forwards
  the container's connections to the broker;
- starts a small network container from Ryu's own image, which sets the firewall for the run:
  everything is dropped except connections to the relay, including DNS and all IPv6, and nothing
  can connect into the container. Host names are resolved by the broker, not the container. The
  CLI checks that the relay is reachable through the firewall before your command starts;
- starts your command in that container's network namespace with every Linux capability dropped,
  `no-new-privileges`, a read-only root filesystem, and writable `/tmp`. It runs as your own user
  and group, so it cannot change the firewall. When the CLI runs as root, the command runs as
  `nobody` (uid 65534) instead;
- mounts the current directory at `/workspace` and the broker CA read-only. The Docker socket is
  never mounted;
- removes both containers, the network, the relay, and temporary files and revokes the session
  when the command exits or fails, or when the CLI receives `SIGINT`, `SIGTERM`, or `SIGHUP`, also
  during setup. The command's exit code is returned; a run interrupted before the command starts
  exits with 128 plus the signal number.

While the command runs, `SIGTERM` and `SIGHUP` sent to the CLI are passed to the command. Ctrl-C
reaches it once, through Docker.

The container's whole environment is the proxy and CA variables listed above, with the proxy URL
pointing at the relay, `NO_PROXY` empty, `NODE_USE_ENV_PROXY=1`, `DENO_CERT`, and `HOME=/tmp/home`
added, plus the image's own `PATH`. Nothing else is inherited from your shell. The session token
reaches Docker in a private environment file, never on a command line.

| Option | Purpose |
|---|---|
| `--image REF` | Run your command in your image. It is pulled if missing and pinned by image ID for the run. The firewall always comes from Ryu's image, and your image only runs without privileges, so it needs nothing but `/bin/sh`. |
| `--mount SRC:DST[:ro]` | Mount another host path (repeatable). `SRC` must exist and is checked after following symlinks. |

On first use the CLI builds Ryu's image, a small Debian image pinned by digest with `curl`, `git`,
and `iptables`, and reuses it until the CLI's image definition changes. Without `--image`, your
command also runs in this image.

Mounts are refused when they would weaken the container:

- the host root, any Unix socket, or a directory that contains a Docker, Podman, or containerd
  socket. This includes the socket of the active Docker context and the usual Docker Desktop,
  colima, OrbStack, and Rancher Desktop sockets, also when reached through a symlink;
- Ryu's data directory (`~/.ryu`, a profile directory such as `~/.ryu-dev`, or `RYU_DIR`) or a
  directory that contains it, such as your home directory. This also applies to the working
  directory, so run from a project folder;
- container paths on, inside, or above `/`, `/bin`, `/dev`, `/etc`, `/lib*`, `/proc`, `/run`,
  `/sbin`, `/sys`, `/tmp`, `/usr`, `/var/run`, and `/workspace`. Mount extra data at paths such as
  `/data` or `/opt/tools`.

Requirements and limits:

- Docker on Linux or Docker Desktop on macOS or Linux, running Linux containers, reached through a
  local socket. Windows hosts, remote Docker daemons (a `tcp://` or `ssh://` context or
  `DOCKER_HOST`), rootless Docker, and daemons with `userns-remap` are not supported, and the CLI
  explains which requirement failed.
- The CLI must run on the same machine as Ryu, as for any `run --broker`.
- On Linux, the relay listens only on the run's network gateway and accepts only that network. A
  host firewall must let containers reach the host on that address. On Docker Desktop the relay
  listens only on the host's loopback interface, which Docker Desktop's host gateway reaches. If
  the relay is not reachable, the run stops before your command starts.
- The root filesystem is read-only. Write to `/workspace`, `/tmp` (also `HOME`), or a mount.
- The firewall controls where the container can connect, not what the broker forwards. With the
  `passthrough` unmatched-host policy (see below), the broker still tunnels to any host. Keep the
  environment on `deny` for a strict allowlist.
- The broker sees container traffic as local, so a machine-minted session's address restriction
  applies to the host, as it does without a container.

## Trusting the broker CA

To add credentials to HTTPS requests, the broker intercepts TLS with certificates issued by a local
certificate authority. The CA is an ECDSA P-256 key that is created on first use and encrypted with
the vault's keys. Only its certificate is ever returned. Leaf certificates for each host are created
when needed and are valid for 24 hours. When the vault is sealed, the broker discards its signing
key and cannot intercept anything.

Trust the broker CA only in the processes you run through the broker, never system-wide.

## Services

A service tells the broker which requests it covers and how to authenticate them:

```json
{
  "name": "openai",
  "environment": "staging",
  "host": "api.openai.com",
  "pathPrefix": "/v1/",
  "auth": { "type": "bearer", "token": "secret:OPENAI_API_KEY" },
  "substitutions": [
    { "placeholder": "__OPENAI_ORG__", "ref": "secret:OPENAI_ORG", "in": ["header"] }
  ],
  "notes": "Use the Responses API. Send __OPENAI_ORG__ in OpenAI-Organization."
}
```

| `auth.type` | Adds |
|---|---|
| `bearer` | `Authorization: Bearer <token>` |
| `basic` | `Authorization: Basic …` from `username` (literal or reference) and `password` |
| `api_key` | `<header>: <prefix><value>` |
| `custom` | Header templates with `{{secret:REF}}` tokens |
| `passthrough` | Nothing; placeholders still substitute |

A service matches on host, optional port, and path prefix. Credentials are not added over plain
`http://` unless the service sets `allowInsecureHttp`. `GET /api/vault/broker/catalog` lists
built-in templates for common APIs (Anthropic, OpenAI, GitHub, GitLab, Gemini, Linear, npm, Slack,
and Stripe), and `notes` gives agents Markdown instructions through discovery.

Services are managed with `/api/vault/broker/services`. Creating or changing one needs `admin` on
`sys/broker/<name>` and `use` on each credential it references, so a service cannot be used to reach
a value you could not use yourself. `ryu-cli secrets broker services` lists them.

## Placeholders

A placeholder is two underscores, 1 to 64 letters, digits, `_`, or `-`, and two underscores, such
as `__STRIPE_KEY__`. The agent writes it where the credential belongs, and the broker replaces it on
the surfaces the substitution allows:

- `header` (the default): replaced as-is. A value containing CR, LF, or NUL fails the request.
- `path` and `query` - opt-in; the value is percent-encoded.
- `body` - opt-in. JSON bodies get JSON string escaping, form bodies percent-encoding, and text or
  XML bodies the raw value. Compressed, multipart, binary, and non-UTF-8 bodies, and bodies over
  1 MiB, are left unchanged.

<Callout type="warn">
Enable `path`, `query`, or `body` substitution only for upstreams that do not echo those parts back.
An error page that repeats the path, a search endpoint that repeats the query, or a redirect whose
`Location` holds the URL would return the credential to the agent.
</Callout>

## Card placeholders

[Payment card items](/docs/security/secret-vault-items#payment-cards) have their own placeholders, which
need no service:

| Placeholder | Field |
|---|---|
| `__CARD_<KEY>_NUMBER__` | Card number |
| `__CARD_<KEY>_CVC__` | Security code |
| `__CARD_<KEY>_EXP_MONTH__` | Expiry month (`07`) |
| `__CARD_<KEY>_EXP_YEAR__` | Expiry year (`2029`) |
| `__CARD_<KEY>_NAME__` | Cardholder |

`<KEY>` is the card's item key as written, such as `__CARD_team-visa_NUMBER__`. The merchant hosts
of cards a session may use are intercepted like service hosts. The broker replaces card
placeholders in headers and in JSON, form, and text bodies, never in the path or query:

- Only for a session whose minter has `use` on the card (`sys/items/<env>/<folder>/<key>`): the
  machine identity that minted it, or the person who started it (their current policies apply).
- Only on an **HTTPS** request to a host on the card's merchant allowlist. In a request the broker
  reads (plain HTTP, or HTTPS to an intercepted service or merchant host), placeholders that cannot
  be filled are forwarded unchanged and a blocked use is recorded on the card, with the reason
  (`no_merchants`, `merchant_not_allowed`, `insecure_scheme`, or `denied`). An HTTPS connection
  the broker passes through without intercepting is opaque to it, so nothing is recorded.
- When the environment denies unmatched hosts, a merchant host that no service covers is reachable
  only by HTTPS requests whose card placeholders the broker fills. Any other request to it is
  refused like an unmatched host.
- One card per request. Placeholders of two cards in one request are refused with `400`.
- A placeholder for a field the card does not store, such as `__CARD_<KEY>_CVC__` on a card saved
  without a security code, is refused with `409 card_field_missing`. Nothing is sent, and the use is
  returned to the approval.
- Every use needs a [spend approval](/docs/security/secret-vault-items#spend-approval). Without one the
  request is not forwarded, and the agent gets `428` with `approvalId`, the path a person approves
  it at, and the path the agent polls:

```json
{
  "error": "card_approval_required",
  "approvalId": "cap_…",
  "approvePath": "/api/vault/cards/approvals/cap_…/approve",
  "statusPath": "/api/vault/agent/cards/approvals/cap_…",
  "card": { "key": "team-visa", "brand": "visa", "last4": "4242" },
  "merchant": "shop.example.com"
}
```

After a person approves, the agent sends the request again. If the merchant cannot be reached
(the connection fails before the request is sent), the use is returned to the approval.

## Sessions

An agent authenticates to the broker with a short-lived session token (`rvb_…`) in the proxy URL. A
session is bound to one environment and an explicit list of up to 32 services. It lasts one hour by
default, from one minute up to 24 hours, and each subject can hold 10 live sessions. Sessions that
ended with their minting machine token (revoked, expired, or identity disabled) do not count toward
that limit. Only a hash of the token is stored, and the token is shown once.

- A person mints a session with `POST /api/vault/broker/sessions`, or `ryu-cli secrets run --broker`.
- A machine identity mints one with `POST /api/vault/agent/broker/sessions` and its vault token. Its
  sessions end when that token (or a parent token it was created from) is revoked or expires, or the
  identity is disabled. The session resolves credentials and cards with that token's current
  policies, so a child token limited to fewer policies passes on only those.

Minting needs `use` on `sys/broker/<service>` for every listed service. A session only allows
brokering: it is not a vault token, and no route that returns a value accepts it.
`ryu-cli secrets broker sessions` lists live sessions, and `DELETE /api/vault/broker/sessions/{id}`
revokes one.

## Requests to unknown hosts

Each environment has an **unmatched-host policy**, set with
`PUT /api/vault/broker/environments/{env}` (`admin` on `sys/broker`):

- `deny` (the default): the broker answers `403` and tells the agent how to propose a service.
- `passthrough` - the broker forwards or tunnels the request without adding anything.

The same route stores Markdown **skills** (up to 64 KiB) that agents read through discovery.
`GET /api/vault/agent/broker/discover` lists the session's services and their placeholders, never
values.

## Proposals

When an agent needs a host or credential that no service covers, it can file a proposal with
`POST /api/vault/agent/broker/proposals`. A proposal names the service and the credentials it needs,
with instructions for getting them. A person with `admin` on `sys/broker` approves it, optionally
entering the credential values, or rejects it. The agent can poll its proposal. Pending proposals
expire after seven days. Each environment can hold 20 pending proposals, and each requester 3.

```sh
ryu-cli secrets broker proposals
ryu-cli secrets broker proposals approve prop_…
ryu-cli secrets broker proposals reject prop_…
```

A service credential can also be a [password-manager reference](/docs/security/secret-vault-password-managers)
such as `op://dev/GitHub/token` or `bws://<secret-id>`. The first request that needs it is refused
with `403 credential_approval_required` and an approval request appears with the proposals; nothing
is fetched from the password manager until a person approves it once or for a set time
(`ryu-cli secrets broker proposals approve <id> --grant 24h`).

In the desktop app, the **Broker** tab on the Vault page lists pending card spend approvals, the
configured services, and the pending proposals, with **Approve** and **Reject** on each. Broker admins see the tab's controls;
everyone else sees a notice that the tab is for broker admins only.

## Request log

Every brokered request is logged without values: time, session, service, method, host, path, and
status. `GET /api/vault/broker/logs` pages it, and `GET /api/vault/broker/discovered-hosts` lists
hosts that agents asked for without a matching service. Both need `list` on `sys/broker`. The CLI
equivalent is `ryu-cli secrets broker logs`.

## Network and limits

The broker checks every resolved address when it connects. Private and loopback addresses are
refused unless `RYU_VAULT_BROKER_ALLOW_PRIVATE=1` is set or the address is inside a CIDR in
`RYU_VAULT_BROKER_NETWORK_ALLOWLIST`. Cloud metadata addresses are always refused.

The limits also have [`node-config.json`](/docs/start-here/configuration#core-node-config) paths (`vault.brokerRps`, `vault.brokerBurst`,
`vault.brokerMaxRequestBytes`, `vault.brokerLogMaxAgeHours`, `vault.brokerLogMaxRows`,
`vault.brokerNetworkAllowlist`). A set environment value wins over the file.

| Variable | Default | Purpose |
|---|---|---|
| `RYU_VAULT_BROKER_PORT` | unset (off) | Loopback port of the broker |
| `RYU_VAULT_BROKER_RPS` | `20` | Requests per second per session |
| `RYU_VAULT_BROKER_BURST` | `200` | Burst size per session |
| `RYU_VAULT_BROKER_MAX_REQUEST_BYTES` | 10 MiB | Largest request body (larger is `413`) |
| `RYU_VAULT_BROKER_LOG_MAX_AGE_HOURS` | `168` | Request-log retention |
| `RYU_VAULT_BROKER_LOG_MAX_ROWS` | `10000` | Request-log row cap |
| `RYU_VAULT_BROKER_ALLOW_PRIVATE` | off | Allow private and loopback upstreams |
| `RYU_VAULT_BROKER_NETWORK_ALLOWLIST` | empty | CIDRs allowed despite the private-range block |

## Permissions

| Policy key | Capability | Allows |
|---|---|---|
| `sys/broker/<service>` | `use` | Brokering through the service and minting sessions for it |
| `sys/broker/<service>` | `admin` | Creating, changing, and deleting the service |
| `sys/broker` | `admin` | Environment settings, all sessions, and proposals |
| `sys/broker` | `list` | The request log, discovered hosts, and proposal list |
