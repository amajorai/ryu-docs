---
title: "Vault Access Requests"
description: "Ask for time-bound access to a vault path, approve it through ordered steps, and let it expire on its own."
---

Part of the [Secret Vault](/docs/security/secret-vault) guide. An access request asks for
capabilities on part of an environment for a limited time, such as `read` on `prod/payments/**`
for one hour. Approvers named by an access policy decide it step by step. Once every step is
approved, the access is granted and ends on its own when the time is up.

Access requests work the same way for values on your device and for Team, Organization and
Project values in the console.

## Access policies

An admin (the `admin` capability on `sys/access-requests`) writes access policies. Each one says
who approves requests under a path, what may be requested there, and for how long:

```json
{
  "path": "prod/**",
  "capabilities": ["use", "read"],
  "maxDurationSecs": 14400,
  "requestTtlSecs": 86400,
  "steps": [
    { "name": "lead", "approvers": ["role:eng-leads"], "approvals": 1 },
    { "name": "security", "approvers": ["team:security"], "approvals": 2 }
  ]
}
```

| Field | Meaning |
|---|---|
| `path` | Glob over `ENV/folder/NAME`, as in [policies](/docs/security/secret-vault-policies). No identity templates. |
| `capabilities` | What may be requested: any of `list`, `use`, `read`, `write`, `delete`. `admin` and `approve` can never be requested. |
| `maxDurationSecs` | Longest grant, from 60 seconds to 30 days. |
| `requestTtlSecs` | How long a request waits for approval, from 60 seconds to 7 days (default one day). |
| `steps` | One to five approval steps, run in order. Each names approver subjects and how many distinct approvals it needs (1 to 5). |

When a request's path touches the paths of several access policies, all of them apply: their
steps run one after another (in policy-name order), the shortest maximum duration wins, and each
must allow the requested capabilities. So a stricter policy on `prod/payments/**` still applies to
a request for all of `prod/**`. At least one policy must cover the whole requested path; a path no
policy covers cannot be requested.

## Request access

A request names a path that starts with an environment, the capabilities, a duration, and a
reason:

```json
{
  "path": "prod/payments/*",
  "capabilities": ["read"],
  "durationSecs": 3600,
  "reason": "Investigating the failed payouts"
}
```

The path may use `*` and `**` but not `?`, and its first segment must be one environment name.
System paths under `sys/` can never be requested, even when an access policy covers every path.
You can hold up to 16 pending requests at a time.

`read` cannot be requested on a path a [control group](/docs/security/secret-vault-policies#control-groups)
may gate. Reveal those values through the control group instead, so its approvers still decide
each read.

## Approve

Only an approver of the step the request is waiting on can act on it, and steps open strictly in
order. These rules always hold:

- You can never approve or deny your own request.
- One person counts toward one step only, so separate steps need separate people.
- Approving twice does not count twice.
- If an admin changes the access policies after the request was made, approvals already given
  no longer grant; the requester opens a new request.
- If a control group starts to gate `read` on the requested path before the last approval, a
  request for `read` no longer grants; the requester opens a new request.
- A request that is not decided before its request lifetime ends expires.

Any approver of the waiting step can deny the request, with an optional reason. The requester
can cancel a pending request.

## Grants and expiry

When the last step is approved, Ryu writes a one-rule policy named `access-<request id>` and binds
it to the requester with an `expiresAt` at the end of the duration. It is an ordinary
[expiring binding](/docs/security/secret-vault-policies#bindings): it stops applying at that time,
explicit denies still win, and it never reaches values outside your scope. Expired grants are
cleaned up automatically.

The requester or an admin can revoke a grant early, which removes the policy and its binding at
once.

Every step is recorded in the [vault audit log](/docs/security/secret-vault-audit) with the
request id, path and capabilities. Values never appear there.

## Routes

On your device:

| Method | Route | Behavior |
|---|---|---|
| `GET` | `/api/vault/access-policies` | Lists access policies |
| `PUT` / `DELETE` | `/api/vault/access-policies/{name}` | Writes or removes one (admin) |
| `GET` / `POST` | `/api/vault/access-requests` | Lists requests you made or can approve, or opens one |
| `GET` | `/api/vault/access-requests/{id}` | One request |
| `POST` | `/api/vault/access-requests/{id}/{action}` | `approve`, `deny`, `cancel`, or `revoke` |

For Team, Organization and Project values, the same routes live under
`/api/control-plane/orgs/{orgId}/vault/access-policies` and `…/vault/access-requests`. Writing an
access policy there needs a recent second-factor check, like other policy changes.
