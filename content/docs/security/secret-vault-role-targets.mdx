---
title: "Role Targets and Delegated Admins"
description: "Which hosts a dynamic or static Secret Vault role can reach, depending on whether a configuration manager or a delegated role admin wrote it."
---

[Dynamic credentials](/docs/security/secret-vault-engines#dynamic-credentials) and
[static roles](/docs/security/secret-vault-seal-auth#static-roles) connect from Core to a target
you name: a Postgres server, a Redis or Valkey server, a webhook, or an AWS STS endpoint. Core makes
those connections from its own host, so a target on `localhost` or your LAN is reached with the
host's network position.

Who may point a role at those addresses depends on who wrote the role.

## Who wrote the role

Ryu records the writer on every dynamic and static role each time it is saved:

| Writer | Who | Targets |
|---|---|---|
| Configuration manager | The local operator of an unbound node, or a member with `gateway.configure` (or the owner of a personal node) | Any host, including loopback and private networks |
| Delegated admin | A member who holds only `admin` on `sys/dynamic/<name>` or `sys/static/<name>` through a policy | Public hosts only |
| Machine token | A vault token from a machine login (such as AppRole) whose policy grants `admin` on the role | Public hosts only |

A token's authority comes only from its policies, never from configuration-manager rights, so a role
saved through a token is a delegated role. To let automation manage a role on `localhost` or your
LAN, have a configuration manager save the role; tokens and members can then issue, renew, and
revoke against it, because the check follows the role's writer, not the caller.

Saving a role again records the new writer. If a delegated admin edits a role that a manager wrote,
even to change only its TTL, the role becomes a delegated role and its targets must be public. A
manager can save it again to restore its access. A delegated admin cannot re-stamp a dynamic role
that still has live leases, because those leases are renewed and revoked through the same target.
Revoke them first.

## What a delegated role may reach

Ryu checks a delegated role's target when the role is saved, and again on every connection: issue,
renew, revoke, scheduled rotation, and each webhook call. A check made only at save time would not
stop a host name whose DNS answer changes later.

- The target must name exactly one TCP host. Unix sockets and `host=` or `hostaddr=` connection
  overrides are refused.
- Host names such as `localhost`, `*.local`, `*.internal`, and cloud metadata names are refused.
- The host is resolved once. Every resolved address must be public. Loopback, link-local,
  private (RFC 1918), carrier-grade NAT, IPv6 unique-local, unspecified, and multicast addresses
  are refused, including IPv4 addresses embedded in IPv6.
- Ryu connects to the exact address it checked, so a DNS answer that changes after the check
  (rebinding) is never used.
- Webhooks and STS endpoints must use `https`. They are sent without an HTTP proxy, and responses
  are capped at 1 MiB.

When a check fails, the operation fails with a message that names the reason. A failed revoke keeps
its lease live, and Ryu retries it later.

A delegated role's webhook and STS calls never follow redirects; a `3xx` answer counts as a failed
call. A manager's role is unchanged: it uses the host's network and proxy settings and follows
redirects as before.

## Roles saved before the writer was recorded

Roles saved by an earlier release have no recorded writer:

- On an **unbound node**, every earlier writer was the local operator. These roles keep working
  unchanged.
- On a node **bound to an organization, team, or account**, Ryu cannot tell whether a manager or a
  delegated admin wrote them, so it treats them as delegated. A role that targets `localhost` or a
  private network stops issuing, renewing, revoking, or rotating until a configuration manager saves
  it again with the same settings. Saving it again is allowed even while the role has live leases.
- The first time such a role is used on a bound node, Ryu records it as delegated. It stays
  delegated if the node is later unbound, until a configuration manager saves it again.
