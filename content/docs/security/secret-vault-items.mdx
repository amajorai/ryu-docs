Part of the [Secret Vault](/docs/security/secret-vault) guide. A value holds one string; an item holds the fields of one credential.

## Typed credential items

A value holds one string. An **item** holds the fields of one credential together, such as a
login's username, password, and TOTP seed, or an API client's id and secret. Items live in an
environment and folder like values, under a key of letters, digits, `.`, `_`, or `-`.

- **Fixed schema.** You set up to 32 fields when you create the item, and they cannot change
  afterwards. Each field has a name, an optional label, a type (`text`, `email`, `url`,
  `password`, `totp`, or `note`), and `required` and `sensitive` flags. `password` and `totp`
  fields are always sensitive. A `totp` field accepts a Base32 seed or an `otpauth://totp/` URI
  and stores only the seed.
- **Per-field encryption.** Each field value is encrypted on its own. A read returns every field
  with `hasValue`, and returns the value only for non-sensitive fields such as a username. A
  sensitive value is returned only by an audited reveal.
- **Status.** An item stays `pending_collection` until every required field has a value. After
  that it is `ready`.
- **Safe re-runs.** `PUT` creates the item (`201`). If an identical item already exists it changes
  nothing and returns `200`. If the item exists with a different schema, description, or value,
  it returns `409`. `PUT` only confirms values you are allowed to see: `read` for sensitive
  fields, `use` or `read` for the others. If you send a value you cannot see, you get `409` without
  any comparison, so `PUT` cannot be used to guess a password. `PATCH` must send the item's
  current `expectedVersion` and `expectedId`, or it returns `409`. Omitted fields keep their
  values and `null` clears one.
- **Event timeline.** Creation, updates, status changes, reveals, and deletes are recorded per item
  with field names and never values. Read the timeline with an `after` cursor. Add `wait` (up to 60
  seconds) to hold the request open until the next event arrives. With `list` you see the current
  item's events. Events from an earlier item that was deleted at the same key need `read`.

Items authorize against `sys/items/<environment>/<folder>/<key>`. You need `list` to see an item,
`use` or `read` to receive its non-sensitive values, `read` to reveal a field, `write` to create or
change it, and `delete` to remove it. Configuration managers and the local operator of an unbound
node have all of these by default, and anyone else needs a policy. Items do not use change
requests. In a protected environment, creating, changing, or deleting an item needs `admin`. An
environment cannot be deleted while it still holds items. Items are node-local. They are not part
of `secret:` references or encrypted snapshots.

Agents can hold their own website logins as items, with generated passwords and authenticator
seeds they never see. See [Agent accounts](/docs/security/secret-vault-agent-accounts).

## Payment cards

A `card` item stores a payment card for an agent to pay with, without the agent ever holding the
card number. Create it with `kind: "card"` and no `fields`. The schema is fixed:

| Field | Sensitive | Rules |
|---|---|---|
| `cardholder` | no | Required, one line |
| `number` | yes | Required. Spaces and dashes are removed, then 12 to 19 digits that pass the Luhn check |
| `expMonth`, `expYear` | no | Required. Month 1 to 12, year `YY` or `YYYY`. The card must not be expired when you store or change the expiry |
| `cvc` | yes | Optional, 3 or 4 digits |
| `postalCode`, `country`, `addressLine1`, `addressLine2`, `city`, `region` | no | Optional billing address. `country` is a two-letter code |

Card keys are 1 to 40 letters, digits, `_`, or `-`, with no `__` and no leading or trailing `_`.
Ryu derives the brand (Visa, Mastercard including the 2-series, American Express, Discover, JCB,
Diners Club, UnionPay) and the last four digits. Listings and reads show a `card` object with the
brand, last four digits, expiry, merchants, and broker placeholders. They never show the number or
security code, and neither do events, audit rows, or error messages.

```sh
printf '%s\n%s\n' "$CARD_NUMBER" "$CARD_CVC" | ryu-cli secrets items put team-visa --type card \
  --cardholder "Ada Lovelace" --exp 07/29 --merchant shop.example.com --merchant '*.pay.example' \
  --postal-code 94107 --country US
```

The CLI reads the number and security code from stdin (the number on the first line, the code on
the second) and refuses them as arguments, which other processes and shell history can see.

### Merchant lock

Each card carries an allowlist of up to 32 merchant hosts, set with `merchants` on `PUT` or `PATCH`.
An entry is an exact host such as `shop.example.com` or a wildcard such as `*.example.com`, which
matches subdomains but not `example.com` itself. A card's fields leave the vault only in three ways:

- **Through the [credential broker](/docs/security/secret-vault-broker#card-placeholders).** The
  agent writes card placeholders, and the broker fills them in only on HTTPS requests to an
  allowlisted host.
- **Fill.** `POST /api/vault/items/{key}/fill` with `{"origin": "https://shop.example.com"}` returns
  the card fields for that origin, including the number and security code. Ryu cannot confirm which
  page the caller fills, so a fill needs both `use` and `read` on the card, and an HTTPS origin on
  the allowlist. Any other origin, or a caller with only `use`, is refused with `403`; a `use`-only
  agent pays through the broker, which never hands it the values.
- **Reveal.** Revealing `number` or `cvc` needs `read` on the card and its own approval for that
  field, granted once per reveal. Other card fields reveal as usual.

A `PUT` to an existing card never confirms a stored number or security code by comparison, even
when the values match: change them with `PATCH`.

### Spend approval

Every card use needs a person's approval. The first use does not release anything. A fill or reveal
answers `202` with a pending approval request, and a brokered request gets `428
card_approval_required` naming the request. Pending requests expire after an hour. A person with
`write` on the card decides. Requesters cannot approve their own fill or reveal; a person who
started a broker session may approve that session's requests. On a local install without a signed-in
account, the local operator confirms its own requests. An approval covers only the channel (`broker`,
`fill`, or `reveal`) and, for a reveal, the field it was requested for.

| Decision | Effect |
|---|---|
| Approve `once` (the default) | One use by the requesting broker session or person, at that merchant, within `ttlSecs` (default 15 minutes) |
| Approve as a `grant` | Uses by the requesting broker session (`subject: "session"`) or by the agent behind it (`subject: "agent"`, meaning the machine identity or the person who started the session) at that merchant, for `ttlSecs` (60 seconds to 24 hours, default 15 minutes), optionally capped by `maxUses` |
| Reject | Nothing is released. The next use files a new request |
| Revoke | Ends an active grant |

```sh
ryu-cli secrets cards approvals
ryu-cli secrets cards approvals approve cap_… --mode grant --subject agent --ttl 30m --max-uses 3
ryu-cli secrets cards approvals reject cap_… --reason "not this merchant"
```

The routes are `GET /api/vault/cards/approvals` (pending, approved, and past requests for cards you
can `list`) and `POST /api/vault/cards/approvals/{id}/approve`, `/reject`, and `/revoke`. An agent
polls its own request with `GET /api/vault/agent/cards/approvals/{id}` and its vault token or broker
session. In the desktop app, pending card uses appear on the **Broker** tab of the Vault page with
**Approve once**, **Allow 15 min**, and **Reject**. Deleting a card ends its pending requests and
grants.

Every use is audited, and a use is refused when [fail-closed auditing](/docs/security/secret-vault-audit#audit-devices) cannot
record it. Events and audit rows record the card key, brand, last four digits, merchant host,
channel (`broker`, `fill`, or `reveal`), and outcome. Per-card spending limits are not supported:
an approval covers uses, not amounts.

## Routes

| Method | Route | Behavior |
|---|---|---|
| `PUT` | `/api/vault/items/{key}` | Creates a typed item, or confirms an identical one (`201`/`200`/`409`) |
| `GET` | `/api/vault/items/{key}` | Field schema, `hasValue`, and non-sensitive values |
| `PATCH` | `/api/vault/items/{key}` | Changes values with `expectedVersion` and `expectedId` |
| `POST` | `/api/vault/items/{key}/reveal` | Returns one field's value (`read`, audited) |
| `GET` | `/api/vault/items/{key}/events` | Item timeline after a cursor, optional `wait` |
| `GET` | `/api/vault/agent-accounts` | Lists the calling agent's website accounts, metadata only ([Agent accounts](/docs/security/secret-vault-agent-accounts)) |
| `POST` | `/api/vault/agent-accounts` | Creates a website account for the calling agent with a generated password |

The full list is in the [Core API reference](/docs/extend/develop/api-reference/core/vault).
