title: "Network binding and auth"
description: "Loopback-by-default binding, when to set RYU_TOKEN, and how clients authenticate when you expose Ryu off-box."
---

By default Core binds `127.0.0.1:7980` and the Gateway binds `127.0.0.1:7981` - loopback only. Nothing is reachable from another machine until you deliberately change the bind address. Core still mints and requires a local node credential: loopback limits network reach, but it is not a substitute for authentication between local processes. See [Ryu port scheme](/docs/core) for the full port layout.

## Token auth for non-loopback exposure

Loopback is the safe binding default. Core's protected routes also require a valid owner, paired,
or delegated credential. If Core cannot load or persist its node credential, protected routes fail
closed until storage is repaired; they do not become unauthenticated owner routes.

| Setting | Default | Effect |
|---|---|---|
| Bind address | `127.0.0.1` | Reachable only from the same machine |
| `RYU_TOKEN` | locally generated when unset | Operator-supplied owner credential; otherwise Core persists a random local owner credential |

Clients pass the token as a standard bearer header:

```
Authorization: Bearer <RYU_TOKEN>
```

## Gateway admin enforcement

The Gateway gates its admin surface on a loopback check derived from the connection's `ConnectInfo` rather than the bearer-auth middleware.

<Callout type="warn">
The admin loopback check uses `ConnectInfo`, which reflects the directly-connected peer. If you place Ryu behind a reverse proxy that terminates the connection locally, every forwarded request appears to originate from loopback and would satisfy the admin check - a fail-open risk. When you expose the Gateway off-box, do not let a proxy front the admin surface on loopback without its own auth, and prefer keeping admin endpoints unreachable from outside the host.
</Callout>

## When to set a token

- Binding to `0.0.0.0` or a LAN address - always set `RYU_TOKEN` first.
- Exposing through a tunnel or proxy - set the token and verify the proxy forwards the `Authorization` header.
- Pure local single-user use on loopback - let Core generate its local credential; clients pair for narrower access.

Use the owner token only for recovery and owner-only administration. Ordinary apps and MCP hosts
should use a paired capability bearer, which can be scoped, bound, expired, and revoked independently.

For a locally generated owner token, `POST /api/node/token/rotate` atomically persists a new token and
switches every live Core verifier before responding. The previous bearer stops working immediately
across REST, realtime sockets, extension proxies, and local self-calls; no Core restart is required.
An operator-supplied `RYU_TOKEN` cannot be rotated through this route because the environment remains
authoritative—change the deployment secret and restart the process instead.
