---
title: "Run a Workflow on a Schedule"
description: "How-to for adding a cron or interval schedule trigger to a workflow so it runs on its own, with optional human approval before each run."
---

Add a schedule trigger to a workflow so the scheduler runs it on a cron expression or fixed interval.
You can also require approval before each run. Scheduled execution survives restarts.

## What you'll use

- [Workflows](/docs/core/workflows): the DAG engine, triggers, and durable resume.
- [Scheduler](/docs/core/scheduler): the always-on tick loop that fires the job.

## Steps

<Steps>

<Step>

### Have a workflow to run

Start from a workflow you have built on the **Workflows** page, or assemble one. You can drag nodes
on the canvas, or describe it to the builder chat and let it build the DAG.

<TryInRyu page="workflows" />

</Step>

<Step>

### Add a schedule trigger

A workflow declares zero or more triggers. Above the canvas, the trigger panel lets you add a
**schedule** trigger and choose either a cron expression or an `every` interval.

| Kind | Example | Fires |
|---|---|---|
| `cron` | `0 9 * * *` | At most once per matching minute, evaluated in UTC (here, 9:00 UTC daily) |
| `every` | `30m` | On a fixed interval parsed like `30s`, `5m`, `1h` |

On save, Core reconciles the trigger into a scheduler job with a deterministic id
(`wf-sched-<workflow_id>-<idx>`) and target `JobTarget::Workflow`. The job is file-backed, so the
schedule survives a Core restart. On boot, the scheduler reloads it and resumes ticking.

<Callout type="info">
Triggers are reconciled idempotently on every save. Editing the schedule updates the same job, and
deleting the trigger (or the workflow) removes the job. A cron expression wins over `every` if you
set both.
</Callout>

</Step>

<Step>

### Optional: require approval before each run

To review each run first, set `require_approval: true` on the schedule trigger in the workflow
definition. The reconciled scheduler job copies the flag. When a flagged job fires, it raises one
deduplicated entry in the approval inbox instead of running. Approving it starts the same run the
tick would have started. Rejecting it, or letting it expire, skips that run.

```json
{
  "triggers": [
    { "type": "schedule", "cron": "0 9 * * *", "require_approval": true }
  ]
}
```

</Step>

<Step>

### Let the scheduler run it

You do not start anything. The scheduler's tick loop fires the job on its cron or interval, runs the
workflow, and checkpoints every node to disk so a crash mid-run resumes rather than restarting. Watch
runs on the Workflows page, or trigger one immediately to test the wiring:

```http
POST /api/workflows/:id/run
```

</Step>

</Steps>

## Check your work

- On save, a scheduler job appears with the deterministic id `wf-sched-<workflow_id>-<idx>`.
- `POST /api/workflows/:id/run` runs it immediately so you can verify the wiring without waiting for
  the next tick.
- Restart Core and the schedule survives. The file-backed job reloads on boot and resumes ticking.
- If you flagged the job for approval, its firing raises one entry in the approval inbox instead of
  running.

## Going further

- Fire the workflow from an external event instead of a clock: the `webhook` and `composio` triggers in [Triggers and schedules](/docs/core/workflow-triggers-and-history#triggers-and-schedules).
- Pause mid-run for a human decision: the `Awakeable` HITL gate in [Workflows](/docs/core/workflows).
- Make a flaky step retry with backoff and a timeout: the per-node `retry` policy in [Workflows](/docs/core/workflow-execution#reliability-and-durable-execution).
