---
title: "Triage a Backlog with a Coordinator Agent"
description: "How-to for a coordinator agent that uses the threads tools to start parallel worker threads for a task list, optionally in separate git worktrees, then read the results back."
---

Use a coordinator agent to split independent tasks, such as bug reports, file summaries, or repo
audits, into worker threads. The workers run in parallel, optionally in separate git worktrees, and
the coordinator collects their results when they finish.

## What you'll use

- [Coordinator threads](/docs/core/coordinator-threads): the built-in `threads.*` tools a
  coordinator uses to create, run, and read worker threads.
- [Conversations and sessions](/docs/core/conversations-sessions): each worker thread is a real
  conversation, so it is durable, searchable, and resumable.
- [Git workspace](/docs/surfaces/desktop/user-guide/git-workspace): per-conversation worktrees keep
  parallel workers from colliding on the same files.
- [Delegation](/docs/core/delegation): the ephemeral alternative, contrasted at the end.

## Steps

<Steps>

<Step>

### Grant the coordinator the `threads` tools

The `threads` tools are allowlist-gated. Only an agent whose tool allowlist grants `threads.*` can
start and manage workers. Pick the agent that will act as your coordinator and add the threads tools
to its allowlist on the **Tools** tab of its edit page.

The built-in `ryu` agent is seeded with the explicit `*` grant, so it can reach `threads.*`. A new
agent has no executable MCP tools. Grant `threads.*` (or `*`) before you use it as a coordinator.

<Callout type="info">
This is an agent-facing capability with no dedicated coordinator screen in Desktop. You chat with
the coordinator agent, and it calls the tools through its normal tool loop.
</Callout>

</Step>

<Step>

### Ask the coordinator to start a worker per task

In a chat with the coordinator, give it the list and ask it to create one worker thread per item and
dispatch each one. It calls `threads.create_thread` for each task, then
`threads.send_message_to_thread` to run that thread's agent on the instruction.

By default `send_message_to_thread` runs in the background and returns immediately, so the
coordinator dispatches the whole list without waiting on each worker.

```json
{
  "thread_id": "<worker-id>",
  "message": "Investigate the database issue and propose a fix",
  "isolate": true
}
```

The response confirms the dispatch without waiting for the work to finish:

```json
{ "ok": true, "thread_id": "<worker-id>", "dispatched": true, "status": "running" }
```

A process-global limit of 8 concurrent background workers applies. If you queue more than eight at
once, the extras wait for a slot instead of being rejected.

</Step>

<Step>

### Use worktree isolation to keep workers apart

When the working directory is a git repo and `isolate` is true, each worker runs in its own
per-conversation git worktree. Two workers editing the same repo do not change each other's files,
because each has its own checkout. When `isolate` is omitted, the **Worktrees** setting in the
Gateway settings decides. That setting is off by default. The worktree is created on the first
`send_message_to_thread` and reused for that thread's later turns, keyed on its conversation id.

See [Git workspace](/docs/surfaces/desktop/user-guide/git-workspace) for how the per-conversation worktrees
are created and how their diffs surface.

</Step>

<Step>

### Read the results back

The workers run in the background, so the coordinator checks on them. `threads.list_threads` shows
every thread with its `run_status`, title, message count, and pinned and archived flags.
`threads.wait_for_thread` blocks until a thread's run finishes, up to `timeout_ms` (default 30000,
maximum 300000). `threads.read_thread` returns a thread's most recent messages plus its
`run_status`. `limit` defaults to 20 and is capped at 100.

```json
{ "thread_id": "<worker-id>", "limit": 20 }
```

Each message body is truncated to 2,000 characters so a long worker reply does not fill the
coordinator's context. `run_status` tells the coordinator whether a worker is `running`,
`completed`, `failed`, or `interrupted`. Once a worker is finished, the coordinator can summarize
it, archive it with `threads.set_thread_archived`, or pin the ones worth keeping in view with
`threads.set_thread_pinned`.

For a blocking call, pass `wait: true` to `send_message_to_thread`. It returns the reply inline
instead of dispatching in the background.

</Step>

</Steps>

## Check your work

- After dispatch, `threads.list_threads` shows one thread per task, each with a `run_status` that
  moves from `running` to `completed` (or `failed`) as workers finish.
- `threads.read_thread` returns a worker's latest messages plus its `run_status`, so the
  coordinator knows a result is ready before summarizing it.
- With `isolate: true` in a git repo, each worker gets its own worktree. More than 8 concurrent
  dispatches wait for a slot instead of being rejected.

## Threads vs delegate: which one

Both split work across agents, for different needs.

- Use [coordinator threads](/docs/core/coordinator-threads) when the work is **durable**: each worker
  is a persistent conversation you can read, resume, and revisit. Use it for a backlog the
  coordinator checks on over time.
- Use [`delegate.fanout`](/docs/core/delegation) when the work is **ephemeral**: parallel subtasks
  with clean contexts whose results come back in one call, with nothing to revisit afterward.

If a worker should run, finish, and be forgotten, delegate. If it should stick around as a thread you
can open later, use coordinator threads.
