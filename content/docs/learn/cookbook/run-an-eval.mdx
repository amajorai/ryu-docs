---
title: "Run an Eval from the Evaluator Catalog"
description: "How-to for the Gateway evaluator catalog: list it, read which evaluators actually run inline, then score a dataset with POST /v1/evals/run."
---

The Gateway ships a shared evaluator catalog with 30 built-in entries across Security, Safety,
Quality, Conversation, Trajectory, Image, and Voice. Two of them are blank Custom templates (an LLM
rubric and a JS/Python function). This recipe reads the catalog, checks which entries are wired to
execution, and runs an offline evaluation over a small dataset.

"Eval" means two things here. The catalog (`GET /v1/evaluators`) is the shared definition surface.
The offline runner (`POST /v1/evals/run`) replays a dataset and scores each case. Pass registry
`evaluators` ids (run-level, per-case, or both) to score with catalog judges, or use `assertions` for
deterministic checks.

## What you'll use

- [Gateway evals](/docs/gateway/evals): the runner, its dimensions, and evaluator catalog.
- [Security and governance](/docs/gateway/governance): the policy surface the inline evaluators back.

## Prerequisites

- **A running Ryu Core**, which runs the Gateway as a managed sidecar on `http://127.0.0.1:7981`.
- A model the Gateway can route, so a dataset run has something to call.

## Steps

<Steps>

<Step>

### Discover the catalog

The catalog endpoint is read-only and is not behind the admin gate. It returns the built-in seed
table merged with any custom evaluators in the Gateway config. A custom entry overrides a built-in
with the same `id` and reports `builtin: false`. List it from the Gateway:

```bash
curl http://127.0.0.1:7981/v1/evaluators
```

The response is `{ "evaluators": [...] }`. Each entry carries an `id`, a `category`, a `target`
(`Input` / `Output` / `Conversation` / `Trajectory` / `Image` / `Audio`), and a `capabilities`
object with `inline` and `offline` booleans. Read `capabilities` first. The Quality, Conversation,
Trajectory, and Voice categories are **offline-only** and are never offered as inline guardrails,
because they need a reference, a full conversation, or a trajectory to score.

</Step>

<Step>

### Read the status flags

Two flags tell you what runs today and how to read a score.

- `enforced` - `true` on exactly the five text detectors wired to real **inline** execution today:
  `pii_leakage`, `code_injection`, `prompt_injection`, `toxicity`, and `bias_fairness`. Every other
  entry ships `enforced: false`, including the two image judges, which need a vision-capable judge
  that is not wired yet. `enforced` is an inline-wiring flag, not an offline-capability flag.
- `higherIsBetter` - `false` on negative-signal judges (toxicity, bias, hallucination, and the like),
  where a high score means a worse output. The security regex detectors keep `true` because their
  scorer already inverts, so `1.0` means clean.

<Callout type="info">
Filter the list to the entries whose `enforced` is `true` to see the guardrails that block, sanitize,
or warn on the request path right now. Treat the rest as catalogued definitions, not live execution.
</Callout>

</Step>

<Step>

### Run an offline eval set

The runner is `POST /v1/evals/run`. It replays each prompt in `dataset` through the full pipeline
(firewall, routing, provider call) and scores each case. Pass registry evaluator ids in a run-level
`evaluators` array, per-case `evaluators`, or both. Use `assertions` for deterministic checks. An
explicit run always scores, independent of passive evals. Use `max_concurrency`, `timeout_ms`,
`repeat`, `cache`, and `tags` to bound and label the run:

```bash
curl -X POST http://127.0.0.1:7981/v1/evals/run \
  -H "Authorization: Bearer $RYU_GATEWAY_TOKEN" \
  -H "content-type: application/json" \
  -d '{
    "model": "gpt-4o-mini",
    "evaluators": ["exact_match"],
    "dataset": [
      {
        "prompt": "What is the capital of France?",
        "expected": "Paris"
      },
      {
        "prompt": "Reply with valid JSON only.",
        "assertions": [{ "kind": "json_valid" }]
      }
    ]
  }'
```

Assertions include deterministic containment/validity/latency/cost/Levenshtein and nested assertion
sets, plus model-assisted rubric/similarity/factuality/relevance checks. Set `judge_model` to hold one
judge fixed across every case. The response returns per-case raw usage, provider/model, rendered prompt,
metadata, assertion results, and per-evaluator breakdowns plus an aggregate. An empty `dataset` uses a
built-in 3-case set. See [Gateway evals](/docs/gateway/evals) for the full field list.

From Core, `POST /api/gateway/evals/run` accepts the same body. Add the optional
`code_evaluators: [{ id, lang, source }]` (`lang` = `js` | `python`) for user functions Core runs
locally and merges into each case's `evaluators` array.

To score a production result after the model call has already completed, use
`POST /api/gateway/evals/score` from Core. It accepts the response, optional trace latency/cost, and
the same assertions/evaluator ids without replaying the provider call.

</Step>

</Steps>

## Check your work

- With no custom evaluators configured, `GET /v1/evaluators` returns 30 entries. Exactly five report
  `enforced: true`
  (`pii_leakage`, `code_injection`, `prompt_injection`, `toxicity`, `bias_fairness`). Every other
  entry, including both image judges, reports `false`.
- `POST /v1/evals/run` returns per-case scores and an aggregate. Registry `evaluators` add
  per-evaluator breakdowns.
- A multi-model run with `llm_judge` fans out `models * cases * (1 + judge_calls)` provider calls
  under Core's 120s proxy timeout, so keep the matrix small or it times out at the proxy.
