This lesson shows how to package your Runnables so other people can install them. You ship either a
**plugin** or an **app**. Both use the same native `manifest.json` contract and the same
install and enable lifecycle. There is no separate app schema.

- A **plugin** runs its essential logic at a Ryu boundary - a Runnable, hook, adapter, or policy.
- An **app** packages its own process or product surface - a sidecar, backend, widget, Companion UI,
  or capability provider.

The choice is about ownership and where the code runs.

```mermaid
flowchart LR
  Manifest["manifest.json\nshared contract"] --> Choice{"Where is the essential logic?"}
  Choice -->|"Core boundary or turn"| Plugin["Plugin\nrunnables / hooks / adapters"]
  Choice -->|"Own process or surface"| App["App\nsidecar / backend / UI"]
  Plugin --> Lifecycle["Gateway grants\ninstall + enable lifecycle"]
  App --> Lifecycle
```

## The manifest

The canonical native manifest file is `manifest.json`. Core still reads the older native names
`ryu.json` and a legacy `plugin.json`. An Agent Plugins `plugin.json` can also sit beside it as a
generated interop file, identified by its Agent Plugins `$schema`. Keep `manifest.json` as the source
of truth.

```json
{
  "id": "com.example.weather",
  "name": "weather-app",
  "version": "1.0.0",
  "runnables": [
    { "kind": "agent", "id": "weather-helper", "name": "Weather Helper" },
    { "kind": "tool", "id": "get_weather", "name": "Get weather" }
  ],
  "permission_grants": []
}
```

Each Runnable entry needs an `id`, a `name`, and a `kind`. Core validates each entry against the rules
for its kind, so an agent entry is checked differently from a tool entry.

The manifest is Ryu's native runtime contract. Two other files can travel with it:

- For cross-host portability, the SDK derives the Agent Plugins `plugin.json` and an optional stdio
  `mcp.json` from the manifest.
- For a Marketplace release, an outer `ryu.package.json` envelope declares the artifacts and produces
  a deterministic `.ryupack` release.

See [Extension schemas & folder layouts](/docs/extend/develop/extensions/schemas-and-layouts).

## Lifecycle and grants

<TryInRyu page="apps" />

You can install and enable plugins and apps without a restart. Each one declares the permission
grants it needs in `permission_grants`. The lifecycle has these operations:

- **install** - fetch and cache the app.
- **enable** - turn it on, with Gateway grant validation.
- **disable** - turn it off without uninstalling.
- **update** - move to a new version.
- **uninstall** - remove the package and its owned runtime artifacts.

```mermaid
stateDiagram-v2
  [*] --> Installed: install (fetch + cache)
  Installed --> Enabled: enable (Gateway grant validation)
  Enabled --> Installed: disable
  Installed --> Installed: update
  Enabled --> Enabled: update
```

<Callout type="warn">
  Enabling an app validates its grants against the Gateway. An app cannot reach a model, tool, or surface it was not granted.
</Callout>

## Study the package layouts

Use the extension guide's examples to decide what belongs in your tree:

- A plugin can add `hooks/`, `adapters/`, `skills/`, `output-styles/`, or native MCP declarations.
- An app can add `backend/`, `sidecar/`, `ui/`, public mounts, and capability bindings.
- Either one can declare Runnables and publish through the same signed Marketplace package flow.

See [Extension schemas & folder layouts](/docs/extend/develop/extensions/schemas-and-layouts) and
[Portable packages](/docs/extend/develop/extensions/portable-packages) before choosing a release
layout.
