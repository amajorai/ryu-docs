This lesson explains how channel bots put your agents into chat platforms (Telegram, Slack, WhatsApp Personal, WhatsApp Business, and Discord) and how you set them up. A bot is not a separate agent. It is another surface onto the same agent the desktop app talks to.

## A bot is another surface

Inbound bot messages route through Core sessions. They use the same agent path, the same memory, and the same Gateway routing as the desktop app. A question asked in a Telegram group gets the same agent, context, and governed model calls as a question asked in the desktop app.

- The agent path is shared, so behavior is consistent across surfaces.
- Memory is shared, so a bot conversation is not cut off from the rest of your history.
- Gateway routing applies, so a bot's model calls are governed like any other.

```mermaid
flowchart LR
  D[Desktop app] --> Core
  TG[Telegram] --> L[Gateway listeners]
  SL[Slack] --> L
  WAP[WhatsApp Personal] --> L
  WAC[WhatsApp Business] --> L
  DC[Discord] --> L
  L --> Core["Same Core session (same agent and memory)"]
  Core --> GW["Gateway routing (governed model calls)"]
```

## How you set them up

<TryInRyu page="channels" />

Open **Channels** from the desktop sidebar. There you create, edit, and delete bot configs.

- Each bot routes to one agent or one team.
- The page talks to the control-plane server with your signed-in account, not to a Core server
  directly.
- Saved tokens are write-only. The page never shows them again, and leaving a credential field
  blank on edit keeps the stored value.

The Gateway runs the platform listeners. Once a config exists, the Gateway connects to Telegram,
Slack, and the other platforms.

<Callout type="info">
  The Channels page describes a bot. The Gateway listens and responds on the platform.
</Callout>

For Telegram, the desktop app may show **Create a bot for me**. This managed path opens a QR code or
deep link in Telegram, waits for a bot owned by your Telegram account, and asks you to verify its
`@username` before connecting it. Use **Paste a token** when the managed option is unavailable or
when you want to reuse an existing BotFather bot.

## Hosted bot grants

- Creating or changing a grant requires organization administrator access.
- Each grant accepts at most 1,024 agent IDs and 1,024 team IDs. Oversized lists are rejected before their entries are processed.
- A grant accepts public HTTPS node addresses without credentials, query strings, or fragments. Loopback and private destinations are rejected.
- Requests validate DNS at connection time, have a two-minute deadline, and accept at most 1 MiB of response data.
- An unavailable or invalid node returns a visible delivery error.

## Organization-aware channel records

The Channels page resolves the active organization when it creates a record.

- The Gateway's enabled-channel view uses that same organization, so an enabled bot created while
  an organization is active is served by that organization's Gateway.
- A team binding must belong to the same organization.
- In a personal context, the record stays personal and is not attached to a team.

<Callout type="info">
  If a bot is not receiving messages, check that it is enabled, that the Gateway is running for
  the organization that owns the record, and that its platform credential is valid.
</Callout>
