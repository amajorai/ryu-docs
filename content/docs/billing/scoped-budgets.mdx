---
title: "Project, Bot, and Credit-Source Budgets"
description: "Cap organization spend per project and per bot, and split any spend cap between subscription credit and API credit, for example $1,000 of API credit and $10,000 of subscription credit a month."
---

These caps extend the organization [spend limits](/docs/billing/usage-limits). They use the same
limit spec fields, windows, actions, and alerts, and they are set from **Limits & budgets** in the
console or with the [Limits and Usage API](/docs/billing/usage-limits-api).

## API and subscription credit budgets

A cap's `budgetMicroUsd` limits all of its charged spend. `fundingBudgets` adds separate caps on
where that spend is paid from:

| Credit source | Field | What counts toward it |
|---|---|---|
| Subscription credit | `subscriptionMicroUsd` | Spend paid from your plan's included credit (**Plan credits** on the [Credits](/docs/billing/credits) page) |
| API credit | `apiMicroUsd` | Spend paid from purchased credit: on-demand top-ups and [standalone service credits](/docs/billing/standalone-credits) |

Free (promotional, referral, and challenge) credit and gift balance count toward **neither** source.
They count only toward the total `budgetMicroUsd`. Calls served with your own provider keys or
local models are not charged, so they count toward nothing.

For example, to let a project spend up to $1,000 a month of API credit and up to $10,000 a month of
subscription credit:

```json
{
  "projects": {
    "PROJECT_ID": {
      "budgetWindow": "monthly",
      "budgetAction": "stop",
      "fundingBudgets": { "apiMicroUsd": 1000000000, "subscriptionMicroUsd": 10000000000 }
    }
  }
}
```

A spent source cap only stops spend that source would pay for. Your wallet draws plan credit first,
so the project first spends up to $10,000 of subscription credit. Once that cap is reached, or the
plan pool runs out, the project can still spend $1,000 of API credit. Once both caps are spent,
its requests stop. Add `budgetMicroUsd` as well to cap the combined spend, including free and gift
credit.

- Credit-source caps share the spec's `budgetWindow`, `budgetAction`, `downgradeModel`, and
  `alertThresholdsPct`, and each is checked independently of the total. A `stop` cap blocks when the
  total is exhausted, or when the cap of the source the wallet draws from next is exhausted. When
  that source is unknown, either exhausted source cap blocks.
- A source is measured from the credit it was actually debited from. Your wallet draws plan credit
  first, so spend usually reaches the subscription cap before any API credit is used.
- Between limit fetches, the Gateway counts its new spend against the source the organization's
  wallet is currently drawing from. If that source is unknown, it counts the spend against both,
  so a cap is never under-counted.
- Credit-source spend is measured from Ryu credit wallet debits. An organization whose usage is
  billed only through the payment provider's meter has no per-source breakdown, so its
  credit-source caps see only the spend a Gateway has served since its last limits fetch.

### Where credit-source caps apply

Credit-source caps are checked everywhere a `stop` total is:

- **Gateway requests**, for every scope (organization, member, team, key, service account, project,
  and bot).
- **Requests made with an organization API key**: a key whose source cap is spent is refused with
  `402`.
- **Ryu Messaging charges**: a send or number purchase whose quoted charge would pass the key,
  member, or organization source cap is refused with `402 spend_limit_reached`. Charges still on
  hold count toward the total but not toward a source, because their source is only known once they
  are debited.
- **Managed Agent turns**: the organization, member, key, and bot caps are checked before each turn
  starts.

## Project limits

A cap under `projects[projectId]` is shared by all usage attributed to that project:

- requests through a Gateway or node that runs for the project (configured with `RYU_PROJECT_ID`;
  see [Organization policy](/docs/gateway/organization-policy));
- requests made with a Gateway key whose `project_id` names the project.

The project id is checked by Ryu before it is applied, so a caller cannot move its spend to
another project by sending a different id. Usage with no project counts toward no project cap.

A Gateway that runs for a project names that project whenever it checks a key with Ryu. A key that
can't use the project, such as a personal key, a team key outside the project's team, or a key
checked after the project was deleted, still works but its traffic is attributed to no project.
A node that runs for a project it can't use is still refused.

In the console, **Limits & budgets → Per project** lists the organization's projects.

## Bot limits

A cap under `bots[botId]` limits one bot:

- **A Ryu agent** served through a Gateway, keyed by its agent id. The id counts only when the
  Gateway verified it: the request uses a dynamic Gateway credential and carries Core's signed
  proof for that agent. An `x-ryu-agent-id` header without that proof is ignored, so a caller
  can't dodge or exhaust another bot's cap.
- **A Managed Agent**, keyed as `ma:` followed by the Managed Agent's id (`magt_` and 32
  lowercase hex characters), for example `ma:magt_0f3a9c2e7b1d4a6e8c5f0b2d9e4a7c1f`. Its turns are
  checked against the cap before they start, and their spend counts toward it.

In the console, **Limits & budgets → Per bot** takes the bot id.

## Gateway version support

Project caps, bot caps, and credit-source budgets are enforced by Gateways released with them and by
Ryu's hosted Gateway. An older self-hosted Gateway ignores them and keeps enforcing the
organization, member, team, key, and service account totals, so update every Gateway that serves
the organization before relying on them.
