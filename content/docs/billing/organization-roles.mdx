Organizations use built-in roles plus narrower custom Ryu roles, and every protected operation
checks the live membership, role, and resource ACL. This reference is for owners, admins, and
developers who manage roles or create organization keys. Membership and teams are on
[Organization Access](/docs/billing/organization-access).

## Roles

Organizations use built-in **Owner**, **Admin**, **Member**, and **Viewer** roles and can add
narrower custom Ryu roles. A custom role is a permission bundle that can be assigned at the whole
organization or one team. Billing, notification management, node management, member management,
and capability execution are separate permissions, so an organization can give a process
operator access without giving them spending authority.

Ryu keeps two role systems separate. Better Auth owns organization membership,
invitations, teams, and its own organization-management actions; its dynamic-role support remains
available for those actions. Ryu owns the capability catalog used by Core, Gateway, Agent Mail,
Marketplace, and resource ACLs. A Better Auth role or custom Better Auth action never widens a Ryu
capability by itself. Ryu checks the live member row, custom assignment, team membership, node
scope, and resource ACL on every protected operation.

To create or assign a Ryu role, a caller needs `roles.manage` and may only grant permissions they
already hold. Deleting a role removes its assignments. A role assignment cannot target a team
unless the target user is a member of that team. Deleted role keys remain reserved so a stale node
ACL cannot unexpectedly reactivate when a later role uses the same key. This prevents a role editor
from minting a privilege ceiling above their own authority. When a Secret Vault policy is bound to
a custom role, creating, deleting, assigning, or removing that role also requires vault policy
administration (`admin` on `sys/policies`).

Each role change adds an entry to the organization's **Audit log** (and to SIEM export when it is
configured) that names the admin who acted:

- Creating a role (`role.create`) records its key, name, and permissions.
- Editing one (`role.update`) records the name and permissions before and after.
- Deleting one (`role.delete`) records the permissions it carried and how many assignments it
  removed.
- Changing a member's custom roles (`role.assign`) records that member, the assignments added and
  removed, how many they hold before and after, and the full assignment lists, with team-scoped
  assignments written as `role@team:<team id>` after the organization-wide ones.
- A member role change made with an Admin API key is recorded as `member.role.update` with the
  previous and new role.
- When a role change is refused (403), the attempt is recorded as `<action>.denied`, for example
  `role.create.denied`.

A long list is packed into comma-separated entries; if a list is still too long for one entry, the
entry records how many items it left out (for example `addedOmitted`) instead of dropping them
silently. A role key longer than 240 characters is shortened with a digest of the full key, so two
long keys stay distinct.

## Identity checks and Desktop role editing

Removing a member, changing a member's role, cancelling a pending invitation,
and inviting someone with more access than a member (owner, admin, or billing
manager) ask the signed-in admin to verify their identity first. Inviting
someone as a member does not.

Desktop users can open **Gateway settings → Workspace** to inspect the active
organization's member roster and built-in roles, create and edit custom Ryu
roles, and assign those custom roles to members. Custom role changes ask the
signed-in user to verify their identity before the request is sent. Desktop
does not edit invitations, built-in member roles, or seat quantity there;
**Manage members** opens the organization page for those actions. If the
organization, member, role, permission, team, or member-role list cannot be
loaded, the setting shows a retry action instead of treating the failed read as
an empty list. Role assignment controls stay unavailable until their saved
assignments load. While a custom role is saving, its fields stay locked until the
request succeeds or fails; a failed save keeps the draft open for retry.

## API keys

Organization roles govern the Better Auth organization-management actions exposed by Ryu.
Viewing organization API-key metadata, creating a key, and revoking one all require the Gateway
configuration permission (`gateway.configure`), which owners and admins hold by default and a custom
role can grant. Members and viewers without it cannot list the organization's keys, including
through the authentication API. Custom roles can narrow those management actions without becoming a
shortcut to Ryu's capability scopes.

API keys are separate from membership. When a member creates an organization key, every requested
`resource:action` scope must be covered by that member's own effective permissions in the
organization: for example, `tools:exec` needs tool execution and `workflows:run` needs workflow
runs. A request for a scope the creator does not hold is refused with `403` and names the scopes.
Ryu also clamps the scopes to the caller's account role and returns the plaintext only once. The key remains owned by the organization, so removing its creator does
not silently remove the integration. Revoke or rotate the key from **Organizations → API keys** if
the integration changes hands or the secret may have leaked.

Ryu still evaluates the key's scopes, organization membership, server ACLs, entitlements, budgets,
and Gateway policy on every protected request. A Better Auth role that can manage a key record does
not, by itself, grant access to chat, agents, files, or other Ryu resources. Personal nodes are
owner-only; team nodes require team membership (or organization-level node management); and
organization nodes remain visible to organization members. Issuing or revoking a team node's
gateway key needs node management for the organization, or through a role scoped to that team; an
organization-level holder does not have to join the team first.

A personal node and its gateway keys belong to one member and work only while that person is a
member. Only that member can issue a personal node's enrollment token or gateway key; an
administrator cannot create one in another member's name.

When a member leaves or is removed, Ryu revokes the personal nodes and personal gateway keys
issued for them in that organization, and stops accepting them even if that revocation has not
finished. The same applies to the organization-wide and team nodes and gateway keys that member
enrolled: they are revoked when the member leaves, so an organization or team node set up on a
departing administrator's machine must be re-enrolled by another member with node management.
Cloud-provisioned servers and service-account keys are not affected. A member with organization-level node management can see the name, owner, and status of
other members' personal nodes and keys and revoke them, but cannot read or change their personal
configuration.
