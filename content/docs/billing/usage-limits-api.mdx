These endpoints read and change the caps described in
[Spend Limits and Usage API](/docs/billing/usage-limits) and report the usage they are measured
against. Calls need the permissions listed in
[Permissions](/docs/billing/usage-limits#permissions).

## Limits API

All paths are under `/api/control-plane` and use your signed-in session.

### Read and replace limits

```http
GET /api/control-plane/orgs/{orgId}/limits
PUT /api/control-plane/orgs/{orgId}/limits
```

`PUT` replaces the whole limits document. The body is the limits object, or
`{ "limits": { ... }, "expectedRevision": 7 }`.

`GET` returns the document's `revision`. Send it back as `expectedRevision` so a save made from an
outdated copy is refused with `409` (`code: "limits_stale"`) instead of overwriting another admin's
change; reload and apply your change again. Without `expectedRevision` the replace is
unconditional.

- `GET` also returns the read-only `planRateCeiling` described in
  [Plan rate ceilings on the hosted Gateway](/docs/billing/usage-limits#plan-rate-ceilings-on-the-hosted-gateway),
  which a `PUT` cannot change.
- Creating a key with its own cap adds only that key's entry and also advances the revision.

```json
{
  "org": { "budgetMicroUsd": 500000000, "budgetAction": "stop", "alertThresholdsPct": [80, 100] },
  "memberDefault": { "budgetMicroUsd": 25000000, "budgetWindow": "weekly", "rpm": 60 },
  "members": {},
  "teams": {
    "TEAM_ID": { "budgetMicroUsd": 100000000, "budgetAction": "downgrade", "downgradeModel": "gpt-4o-mini" }
  },
  "keys": {},
  "serviceAccounts": {},
  "projects": {
    "PROJECT_ID": {
      "budgetAction": "stop",
      "fundingBudgets": { "apiMicroUsd": 1000000000, "subscriptionMicroUsd": 10000000000 }
    }
  },
  "bots": {
    "ma:MANAGED_AGENT_ID": { "budgetMicroUsd": 50000000, "budgetAction": "stop" }
  }
}
```

The `PROJECT_ID` entry caps the project at $1,000 of API credit and $10,000 of subscription credit
per month, with no cap on the combined total. See
[API and subscription credit budgets](/docs/billing/scoped-budgets#api-and-subscription-credit-budgets).

Validation rules:

- Responses always contain every map (`members`, `teams`, `keys`, `serviceAccounts`, `projects`,
  `bots`), as `{}` when empty, and every spec contains `fundingBudgets`.
- Omit a field or send `null` for no limit.
- A `budgetMicroUsd` of `0` is a real cap that blocks all charged spend.
- `rpm` and `tpm` must be at least `1`.
- `fundingBudgets` may be omitted, or either of its fields left out or `null`, for no credit-source
  cap. Any other field inside it is refused.
- Map keys are ids of up to 128 letters, digits, `_`, `-`, and `:`. Bot ids are a verified agent id
  or `ma:` followed by a Managed Agent id.
- Invalid fields return `400` with the path of the first problem.

The fields of each limit spec are listed in
[Spend Limits and Usage API](/docs/billing/usage-limits#limit-spec-fields).

### Current-window status

```http
GET /api/control-plane/orgs/{orgId}/limits/status
```

Returns one row per budgeted scope, measured in that scope's current window:

```json
{
  "rows": [
    {
      "scope": "org",
      "id": "org",
      "label": "Organization",
      "window": "monthly",
      "spentMicroUsd": 412000000,
      "budgetMicroUsd": 500000000,
      "pct": 82.4,
      "action": "stop",
      "fundingSpend": { "subscriptionMicroUsd": 380000000, "apiMicroUsd": 20000000 },
      "fundingBudgets": { "subscriptionMicroUsd": null, "apiMicroUsd": null }
    }
  ]
}
```

`scope` is `org`, `member`, `team`, `key`, `serviceAccount`, `project`, or `bot`. Member labels
show the member's name and email; team, key, service account, and project labels show their names.

`fundingSpend` is the window's spend paid from subscription credit and from API credit, and
`fundingBudgets` repeats the cap's credit-source budgets. Free and gift credit appear only in
`spentMicroUsd`, so the two sources can add up to less than it. A row is listed when the cap has a
total budget or a credit-source budget.

## Usage & Cost API

### Breakdown

```http
GET /api/control-plane/orgs/{orgId}/usage/breakdown?groupBy=model&from=2026-10-01T00:00:00Z&to=2026-10-08T00:00:00Z&bucket=day
```

| Parameter | Values | Default |
|---|---|---|
| `groupBy` | `user`, `key`, `team`, `model`, `provider`, `project`, `serviceAccount` | `user` |
| `from`, `to` | ISO 8601 timestamps, half-open range `[from, to)` | the last 30 days |
| `bucket` | `day`, `hour`, `none` | `day` |

- Ranges are limited to 400 days, and hourly buckets to 31 days.
- With `groupBy=serviceAccount`, rows and totals cover only traffic made with service account
  Gateway keys, one row per account.
- Key and team usage from requests through the hosted Gateway is credited to the organization that
  owns the `rgw_` key or the team, the same way as usage from your own Gateway. It counts toward that
  organization's key and team caps.

```json
{
  "groupBy": "model",
  "bucket": "day",
  "from": "2026-10-01T00:00:00.000Z",
  "to": "2026-10-08T00:00:00.000Z",
  "rows": [
    {
      "key": "gpt-4o",
      "label": "gpt-4o",
      "bucketStart": "2026-10-01T00:00:00.000Z",
      "requests": 120,
      "inputTokens": 340000,
      "outputTokens": 51000,
      "cacheTokens": 0,
      "costMicroUsd": 1730000
    }
  ],
  "totals": { "requests": 120, "inputTokens": 340000, "outputTokens": 51000, "cacheTokens": 0, "costMicroUsd": 1730000 },
  "truncated": false
}
```

#### Key usage covers whole UTC days

Key usage is rolled up per UTC day, so `groupBy=key` and `groupBy=serviceAccount` support only `day`
and `none` buckets, and a range covers every UTC day it overlaps. For both groupings, the
response's `from` and `to` are widened to UTC midnight, and `rangeAdjusted` is `true` when that
changed the range you asked for. Console shows the covered days.

#### Reading the response

- `bucketStart` is `null` when `bucket=none`.
- Usage that cannot be attributed to a member, team, or project is returned with an empty `key` and
  the label `Unattributed`.
- With `groupBy=team`, a request from a member of several teams is counted under each of those
  teams, so team rows can add up to more than the organization total.
- `cacheTokens` counts prompt-cache reads and writes for every grouping. It is `0` for traffic from
  Gateways that do not report cache usage.
- A response holds at most 10,000 rows. `truncated` is `true` when more matched, so narrow the range
  or the bucket.
- `totals` always cover every matching row, even when `rows` is truncated; Console shows a notice in
  that case.

### CSV export

```http
GET /api/control-plane/orgs/{orgId}/usage/export.csv?groupBy=team&from=...&to=...&bucket=none
```

Returns the same rows as CSV with the columns `key`, `label`, `bucketStart`, `requests`,
`inputTokens`, `outputTokens`, `cacheTokens`, `costMicroUsd`, and `costUsd`.

- Cells are quoted per RFC 4180.
- Text that a spreadsheet would evaluate as a formula is prefixed with an apostrophe.
- The `X-Ryu-Truncated` response header reports whether the 10,000-row cap was reached. It is
  readable from cross-origin browser requests, and Console warns when a downloaded export is
  partial.

### Your own usage

```http
GET /api/control-plane/orgs/{orgId}/usage/me?groupBy=model
```

Any member can read their own usage with the same parameters, grouped by `user`, `model`,
`provider`, or `project`.
