## 1. How to read this list

“Customer Data” has the meaning in the [Terms of Service](/docs/legal/terms). A Major may process Customer Data as a processor or service provider when a customer uses a managed Ryu service and gives the relevant instructions. A customer may instead use its own account, API key, infrastructure, or connected service; in that case, the customer is responsible for the provider relationship and the provider may process data directly under its own terms.

The list describes documented Ryu product paths. It is intentionally conditional because Ryu supports local, self-hosted, customer-selected, and managed deployments. It should be reconciled against the actual production inventory before it is presented as a contractual subprocessor list.

## 3. Model and inference providers

Ryu can route a task to a local engine, a customer-supplied provider, or a Ryu-managed inference provider. Depending on the route and model, the provider may receive prompts, conversation context, files or media, tool results, model parameters, token counts, and request metadata needed to produce an output.

Examples supported by current Ryu provider integrations include OpenAI, Anthropic, Google, OpenRouter, Fal, Modal, and Replicate. This is an example family, not a statement that every provider is enabled, that A Major has a direct agreement with every provider, or that every customer’s data is sent to them. The active provider, credentials, data path, and provider terms control.

If a customer uses its own API key or account, the customer should review and contract with that provider directly. If A Major supplies the route as part of a managed feature, the provider should be listed as an approved subprocessor for that feature before publication.

## 4. Customer-selected apps, channels, tools, and plugins

Customers can connect Slack, Telegram, Discord, WhatsApp, repositories, databases, MCP servers, plugins, marketplace apps, and other external services. Those services may receive Customer Data at the customer’s direction and may process it under their own terms. They are not fixed Ryu subprocessors merely because Ryu can connect to them.

The customer is responsible for:

- choosing the connection and reviewing its privacy and security terms;
- configuring the minimum required scopes and credentials;
- informing its users and data subjects about the connection; and
- removing or rotating access when the connection is no longer needed.

## 5. Conditional operational integrations

The repository also supports optional operational integrations such as object storage, email delivery, Notion content publishing, cloud telemetry, and customer-configured communication or relay services. These may be used for Ryu’s own content operations or only when a customer enables the associated feature; they are not automatically processors of Customer Data.

Examples that require deployment-specific confirmation include:

- AWS S3, Cloudflare R2, Hetzner Object Storage, or DigitalOcean Spaces for configured object storage;
- Amazon SES where an email path or Ryu Mail deployment uses it beneath the email service;
- Notion for Ryu-managed blog, help, or changelog publishing; and
- a customer- or operator-selected OTLP collector, relay, model, app, or channel.

This list should name only the entities that are actually used, state the purpose and data categories precisely, and link each entity’s current DPA or privacy terms.

## 6. Providers that do not receive local data by default

The following are not A Major subprocessors of a local installation merely because the software contains a corresponding feature:

- a local Ryu Core, Gateway, model, trace store, or audit store;
- a self-hosted Gateway, database, object store, email service, or OTLP collector;
- a customer’s own model-provider account, API key, app, channel, MCP server, or plugin; and
- a connected service that the customer has not enabled or that the local installation has not been configured to call.

Local data can still become cloud or third-party data when the operator enables synchronization, a remote provider, a managed node, a connected service, diagnostics export, analytics, crash reporting, or support access.

## 7. Subprocessor changes and DPA requests

The DPA should specify how A Major gives notice of a new or changed subprocessor, the objection process, security and incident obligations, international-transfer safeguards, deletion or return of Customer Data, and audit information. This page should be updated when a provider is added, removed, or materially changes its purpose or data categories. Counsel should insert the notice period and contractual mechanism.

For a DPA request, processor question, or list correction, contact **hello@ryuhq.com**. Security vulnerabilities should be reported to **security@ryuhq.com**.
