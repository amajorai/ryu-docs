Ryu supports three kinds of custom provider: OpenAI-compatible model endpoints, Pi agent model
providers, and Toolkit providers. A custom model endpoint is not a custom Toolkit provider.

## Custom model endpoints

An OpenAI-compatible endpoint can be used through a configured OpenAI or local provider slot when it
implements the operation you need. The endpoint may provide chat, embeddings, reranking, image,
STT, or TTS independently.

| Need | Use |
|---|---|
| Hosted endpoint with a user credential | Gateway OpenAI-compatible provider with a custom base URL |
| Local endpoint without cloud egress | Local provider with the node-local base URL |
| Native Gemini-family adapter | GenAI provider with its adapter-key map |
| Pi or ACP provider account | The agent runtime's provider catalog and account store |
| Media prediction API with a non-OpenAI shape | A Gateway provider implementation such as Fal or Replicate, or a separate app/provider seam |

Ryu checks the provider contract, not the provider name. If an endpoint does not implement
`/embeddings`, it is not an embedding provider just because it serves chat.

### Pi agent model providers

The Pi agent connection editor uses Pi's `models.json` for a compatible chat endpoint. It accepts
an endpoint URL, API format, key, and model ID; it does not author a Pi provider extension or
describe custom image/classifier implementations. Pi's built-in provider login handles supported
subscription OAuth flows separately. Ryu writes the active credential for each provider to
Pi and keeps the other saved accounts in its account store. Ryu asks Pi's provider-owned
OAuth flow to refresh an expiring credential before a new agent turn and saves the rotated
credential back to the active account.

When you add a custom endpoint, Ryu tries its OpenAI-compatible `GET {baseUrl}/models` endpoint
and adds returned model IDs to Pi's model picker. Saved model entries and their enabled settings
survive later discovery. The provider remains saved if discovery is temporarily unavailable; you
can enter a model ID manually and retry **Discover models** from its provider card. A keyless
loopback endpoint such as `http://localhost:11434/v1` is supported. Other private-network
endpoints still follow the node's egress policy.

The agent connection editor scopes discovered models to the selected account and
endpoint. Switching a saved account or changing a custom endpoint fetches that
connection's catalog. Saving a credential invalidates its cached discovery result.

To replace a custom provider's key, enter the new key in its card and select **Save**.
Ryu keeps its URL, API format, and saved model settings, then retries model discovery with the
new key. Leaving the key blank keeps the current credential setting.

For Claude, a successful OAuth connection only confirms authentication. Anthropic may charge
third-party tools against usage credits instead of a subscription's included limits, and a
connected account can still reject model requests when its applicable allowance is exhausted.
Check Claude's Usage settings or connect an Anthropic API key for separately billed API access.
See [Anthropic's third-party tool policy](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account).

Pi supports richer model metadata, dynamic discovery, and custom streaming through trusted
provider extensions. Verify the endpoint's protocol before you declare it compatible. See
[Pi's custom provider guide](https://pi.dev/docs/latest/custom-provider) for the Pi runtime
contract. Gateway embeddings, speech, video, search, and fetch use their own service adapters;
a Pi chat model entry does not automatically enable those operations.

## Custom Toolkit providers

Toolkit providers declare a capability such as `web.search`, `browser.control`, `memory`, or
`document.parse` in their app or plugin manifest. They can map the canonical verb to a provider
tool, add bounded defaults, map the response, or use a constrained adapter for an async or nested
provider API.

The canonical capability remains the source of truth. A provider declaration does not create a new
Core route, grant execution permission, or make the provider available on every host.

## Provider data and credentials

Keep these boundaries separate:

- the model ID and capability declaration are non-secret metadata;
- provider credentials belong to the Gateway or the agent runtime's credential store;
- local model weights and sidecar caches belong to the node;
- Toolkit grants and provider bindings are policy state;
- a provider response is untrusted external data and must be normalized before it reaches an agent.

Do not put API keys, tokens, or private endpoints in a public manifest, model card, or documentation
example. Use the [BYOK and provider accounts](/docs/providers/byok) page for account setup and the
[capability broker](/docs/extend/develop/extensions/capability-broker) for extension contracts.

## Checklist for a custom integration

1. Name the owning layer: Gateway provider, local engine, app sidecar, or Toolkit capability.
2. Define the supported operations and failure states.
3. Keep the stable public shape separate from provider-native fields.
4. Declare credentials and grants at the owning boundary.
5. Add availability and unavailable states to the picker or API.
6. Document the provider and add a focused contract test.

Read [Plugin JSON manifests](/docs/extend/develop/extensions/plugin-json-manifest) and [Swappable layers](/docs/core/swappable-layers)
for the manifest and provider-mapping forms.
