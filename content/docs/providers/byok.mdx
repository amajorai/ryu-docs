BYOK (bring your own key) means the request uses a provider credential you or your organization
controls, such as your own OpenAI API key or a Claude subscription login. It does not mean the
provider skips Ryu's Gateway policy, and it does not make a local model a cloud provider.

## Account paths

| Account path | Examples | Stored or enforced by |
|---|---|---|
| Gateway provider credential | OpenAI, Anthropic, OpenRouter, Fal, Replicate, Modal, or a custom endpoint | Gateway configuration and credential boundary |
| GenAI adapter credential | Gemini, Groq, xAI, DeepSeek, Cohere, and other configured native adapters | GenAI provider's adapter-key map; Gemini also supports extra keys with session-aware rotation |
| Agent provider account | Pi or ACP subscription/provider accounts | Core's provider account store and agent runtime |
| Local runtime | Ollama, Docker Model Runner, Mesh LLM, or another local OpenAI-compatible service | The local node or adopted runtime |
| Ryu-managed route | Managed OpenRouter or a credit-isolated provider slot | Managed control plane and Gateway policy |

The same vendor can appear in more than one row. An OpenAI BYOK slot and an OpenAI credit-isolated
slot use the same protocol but must remain separate for billing and credential custody.

## Personal versus shared use

Provider accounts and Gateway providers answer different scope questions:

- a personal account is used by the selected user or agent runtime;
- a Gateway provider can serve multiple governed callers on a node or fleet;
- a managed provider can use a platform-owned credential while still recording the calling identity;
- a local provider has no cloud credential but can still be restricted by node and Gateway policy.

Selecting an account does not change other agents. Account switching is explicit, and the
provider and model selection is a separate setting. Removing a personal OAuth account also
removes its eligibility for native subscription requests; an old Pi credential file does not
override the account store after it has been initialized.

When a provider has multiple saved OAuth accounts, you can rename each account in its account menu.
The custom label is account metadata. It does not change the credential, provider, or
active-account selection.

## Several accounts for one provider

A provider can hold more than one saved account: several Gateway API keys, several Claude or
ChatGPT logins, or several managed Pi accounts. Each new conversation is bound to one account and
keeps it while it stays healthy, so the provider-side prompt cache remains useful. The selection
strategies, session binding, cooldowns, and retries for every pool are on
[Account routing](/docs/providers/account-routing).

## Usage and billing

Usage dimensions remain separate:

- provider-native subscription usage belongs to the provider account;
- Ryu wallet or credit usage belongs to the managed or credit-isolated route;
- local inference has node resource cost but no upstream provider bill;
- media and tool calls can carry a provider-reported cost or a clearly labeled estimate.

The provider ID used for a request is the attribution boundary. A managed OpenRouter request and a
BYOK OpenRouter request must not be reported as the same account just because they share a vendor.

The Usage tab refreshes provider-account snapshots on a five-minute cadence while
active. Hidden tabs pause these reads. Returning to the tab reuses a fresh snapshot
or refreshes an older one; use Refresh when you need an immediate update.

## Set up and verify a provider

### Modal deployment accounts

Modal needs your deployment's OpenAI-compatible `base_url`; it has no shared inference URL.
Configure `[providers.modal]` with that URL and an `api_key`, plus optional additional `api_keys`.
The deployment must accept those values as bearer tokens. `MODAL_BASE_URL`, `MODAL_API_KEY`, and
`MODAL_API_KEYS` can supply the same settings.

Once the endpoint is configured, Gateway → API keys shows Modal's masked account list with Add, Remove,
Replace first, and Clear controls. Removing the last account or clearing its keys retains the URL
and disables the provider until another key is saved. Modal keys follow the Gateway API-key pool rules on
[Account routing](/docs/providers/account-routing#gateway-api-key-pools). Keys authenticate your deployed app, rather than Modal's deployment
management API.

### Verify a provider

1. Add the credential through the Gateway or agent runtime's account surface.
2. Select the provider and model for the intended agent, modality, or Toolkit layer.
3. Confirm the provider is configured and available.
4. Send a bounded test request and inspect the provider/request attribution.
5. Remove or rotate the credential in its owning store when it is no longer needed.

Secrets are write-only or redacted when read back. Do not copy them into model IDs,
public manifests, documents, or chat prompts.

See [Agent runtimes](/docs/surfaces/desktop/engines/agent-runtimes), [Gateway configuration](/docs/gateway/configuration),
and [Custom providers](/docs/providers/custom).
