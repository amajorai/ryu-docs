---
title: "Kiro HTTP Provider"
description: "How to sign in to the Kiro HTTP provider with AWS Builder ID, what it supports (text, tools, reasoning), and how its saved accounts and refresh behave."
---

Kiro HTTP is a chat provider that sends requests straight to Kiro with a saved Kiro login. It is
separate from the [Kiro CLI agent](/docs/surfaces/desktop/engines/agent-runtimes) and its
[native accounts](/docs/providers/native-kiro-accounts).
Select **Kiro (HTTP · login)**
in provider settings and sign in with AWS Builder ID. Follow the authorization link and
enter the displayed device code when asked. Core saves the issued login in the sealed
account vault. Pi and the local Gateway use an authenticated Core relay instead of
receiving the vendor refresh token.

Choose a model returned by Kiro model discovery, or enter the exact model ID accepted
by your account. Available models and service access depend on the vendor account.
Ryu does not infer a free allowance or remaining quota from a successful login.

The HTTP provider supports text chat, tool calls and tool results, and reasoning
events. It validates the AWS event frames before emitting streaming text. Image
input is rejected. Use the native Kiro CLI agent when you need its agent
workflow and isolated CLI profile.

A conversation keeps its selected saved account. Changing the active account affects
new conversations. Disabling or removing a bound account stops its requests. It does not
switch the conversation to another login. Provider settings expose the supported selection
strategies and priorities; missing usage observations do not become a quota estimate.

Refresh dispatch is recorded for the exact credential generation before sending the
request. An uncertain delivery or a failed write after token rotation requires a new
sign-in. Restarting Core does not replay that generation's refresh token. An explicit
revocation also requires sign-in; a later saved login remains usable.

Inference requests are not replayed after uncertain delivery. Streaming text already
received may be visible when a later frame fails validation; the request then ends
with an error instead of a successful completion.

See [provider accounts](/docs/providers/byok) for account configuration
and [provider pools](/docs/providers/provider-pools) for Gateway model routing.
