OpenRouter is a hosted model router with a live catalog of many upstream model families. Ryu
registers it as a Gateway provider. It keeps model choice on
one OpenAI-compatible route while OpenRouter selects or exposes the upstream model family.

## Model IDs

Ryu routes the following model-ID forms to the OpenRouter provider:

| Form | Meaning |
|---|---|
| `openrouter/auto` | OpenRouter chooses an upstream model for the request |
| `openrouter/pareto-code` | OpenRouter's coding-oriented router chooses a model |
| `openrouter/<provider>/<model>` | A specific OpenRouter catalog model, using the model slug returned by discovery. Ryu sends it to OpenRouter as `<provider>/<model>` |

`router/<model>` reaches OpenRouter too when OpenRouter is the selected
[routing layer](/docs/providers/upstream-routers); `router/auto` becomes `openrouter/auto`.

The catalog is live. Do not copy a temporary model list into an agent definition when discovery or
the OpenRouter catalog can provide the current ID. Ryu also keeps the two router entries above in
the built-in model surface so they can be selected without enumerating every upstream model.

## Supported Ryu operations

| Operation | Gateway route | OpenRouter endpoint |
|---|---|---|
| Chat completions | `POST /v1/chat/completions`, streaming and non-streaming | Chat completions |
| Embeddings | `POST /v1/embeddings` | Embeddings |
| Reranking | `POST /v1/rerank` | Rerank |
| Image generation | `POST /v1/images/generations` | Images API, or chat image output when the request carries `messages` |
| TTS | `POST /v1/audio/speech` | Speech API, or streamed chat audio for audio-output models |
| STT | `POST /v1/audio/transcriptions` | Transcriptions API |
| Video generation | `POST /v1/videos/generations`, polled at `GET /v1/videos/generations/{id}` | Video generation jobs |

Every operation works with both Ryu-managed OpenRouter and a BYOK OpenRouter key. Each model
supports only the operations in its own output modality. Browse
[OpenRouter's collections](https://openrouter.ai/collections) to find a model for an operation.

### Model discovery

Gateway model discovery lists OpenRouter's full catalog, not only text models. Non-chat entries
carry a `modality` field: `image`, `tts`, `stt`, `video`, `embedding`, or `rerank`. Models that
produce text, including models that also produce images or audio, remain chat models. Agent and
provider model pickers list only chat models, so a speech, video, or embedding model cannot be
selected as an agent's chat model.

### Images

A request with a `prompt` goes to OpenRouter's Images API and returns OpenAI-shaped
`data[].b64_json` with `data[].media_type`. Options such as `size`, `aspect_ratio`, `quality`,
`n`, and `seed` pass through to OpenRouter. Images are always returned inline, so a
`response_format` of `url` is ignored. The Ryu desktop app and SDK use `media_type` to label
each image, for example as WebP or JPEG. If the Images API does not serve the selected model, the
request falls back to chat image output. A request that carries `messages` uses chat image output
directly and returns `data[].url` data URLs.

### Speech and audio generation

Speech models such as ElevenLabs use OpenRouter's Speech API. Pass the model's native `voice`.
OpenRouter returns `mp3` (the default) or `pcm`. A request for `wav`, `opus`, `aac`, or `flac`
receives MP3 audio, and the response `Content-Type` is `audio/mpeg`. The Speech API response does
not include a cost, so Gateway reads the cost from OpenRouter's generation record after the audio
arrives. If that record is still unavailable after a few seconds of retries, the request is
billed at the Gateway's per-call speech rate.

Chat models that output audio, such as music-generation models, use OpenRouter's streamed chat
audio. Gateway recognizes these models from OpenRouter's catalog, which it loads on the first
speech request and refreshes hourly. To use chat audio with another model, add
`"modalities": ["text", "audio"]` to the request body.

`POST /v1/audio/speech` always takes its text from a non-empty string `input`. For chat audio,
`input` becomes the user message and `instructions` becomes the system message. Both fields pass
through the Gateway's inbound firewall and guardrails. A request that includes `messages` is
rejected; use chat completions for a conversation. `voice` and `response_format` become the chat
`audio` options. An omitted `response_format` requests MP3, as for speech models. `pcm` is sent
as `pcm16`, and `aac` is served as MP3. Gateway collects the stream and returns one audio file.
The response body contains only the audio bytes; a model's text transcript is not returned.

`/v1/audio/speech` returns at most 8 MiB of audio. A larger result fails after it has been
generated and charged, so request a compressed format such as MP3 for long music or speech.

### Transcription

Audio is sent to OpenRouter as base64 `input_audio`. Its format comes from the request's
`format` field or the uploaded file's extension, and defaults to `wav`. `language`,
`temperature`, `timestamp_granularities`, `diarize`, and `keyterms` pass through. OpenRouter
returns JSON only, so a `text`, `srt`, or `vtt` `response_format` returns the JSON transcript
with its `text` field.

### Video

Video generation is job-based. Request fields such as `duration`, `resolution`, `aspect_ratio`,
`size`, `generate_audio`, `seed`, `frame_images`, and `input_references` pass through to
OpenRouter. Each request produces one video.

The polling account and connection stay bound to the accepted job. A completed video hosted on a
third-party HTTPS URL is returned as that URL. A video that is only available from OpenRouter's
authenticated content endpoint is downloaded and returned as a `data:video/...` URL, so the
OpenRouter key never reaches the client. Such a video larger than 48 MiB fails the job instead of
being truncated, and the failed job is not charged.

The reported OpenRouter cost is used for credit accounting when OpenRouter returns it.

## Ryu-managed versus BYOK OpenRouter

| Path | Credential owner | Policy behavior |
|---|---|---|
| Ryu-managed OpenRouter | Ryu's managed delivery boundary | The deployment can enforce provider privacy, usage accounting, and credit policy |
| BYOK OpenRouter | Your OpenRouter account | Your account and key fund the request; Ryu still applies the local Gateway policy path |
| Custom OpenRouter-compatible endpoint | The endpoint owner | Ryu uses the configured base URL and only the operations that endpoint implements |

Every OpenRouter request carries a required privacy policy. See
[Required privacy policy](#required-privacy-policy).

Gateway inference requests to OpenRouter include app attribution headers. They list Ryu in
OpenRouter's rankings and marketplace. Ryu sends `HTTP-Referer: https://ryuhq.com`,
`X-OpenRouter-Title: Ryu`, and `X-OpenRouter-Categories: personal-agent`. It also sends the legacy
`X-Title` header for compatibility. These headers identify the app and do not change the request
body or OpenRouter response cache key.

## Managed request routing options

Open **Gateway → Network → Managed request routing** in a Business organization to configure
OpenRouter requests that pass through Ryu Gateway. The controls use OpenRouter's provider routing
fields directly, and the provider picker loads OpenRouter's public provider catalog. You can still
enter a custom provider slug if it is missing from the catalog. The advanced JSON editor exposes the
complete `provider` object so newer OpenRouter fields remain available before the typed controls are
updated. The control plane resolves this entitlement for each organization; stale saved values are
ignored when the organization is no longer on Business.

The settings cover:

- Provider `order`, `only`, and `ignore` lists, with reordering for the preferred provider order.
- OpenRouter's default health-aware routing or sorting by throughput, latency, or price.
- Provider fallbacks and model fallbacks after the requested model.
- Required Zero Data Retention (`zdr`), exclusion of data-collecting providers, and distillable-text requirements.
- Parameter support, quantization, preferred throughput and latency percentiles, and maximum price
  for prompt tokens, completion tokens, requests, and images.

Leaving provider order and sort unset keeps OpenRouter's default provider health routing. A sort or
explicit order changes its normal load balancing, so leave provider fallbacks on when availability is
the priority. The [uptime optimization guide](https://openrouter.ai/docs/guides/best-practices/uptime-optimization)
explains how OpenRouter uses provider health information. For example, sorting by throughput while
keeping provider failover enabled corresponds to:

```json
{
  "sort": "throughput",
  "allow_fallbacks": true
}
```

### Required privacy policy

Gateway sets `provider.data_collection: "deny"` and `provider.zdr: true` on every OpenRouter
request and for every Ryu plan, with Ryu-managed and BYOK keys alike. These settings exclude
data-collecting providers and require endpoints that meet OpenRouter's Zero Data Retention (ZDR)
policy. Caller requests and saved configuration cannot disable them. Other advanced routing
controls keep their existing plan requirements. Billing uses the actual reported provider cost
without an additional Ryu ZDR fee.

ZDR covers provider inference endpoints. It does not cover tools or plugins; see
[Composio billing and privacy](/docs/billing/credits#composio-usage-and-zero-data-retention). See
OpenRouter's [data collection guide](https://openrouter.ai/docs/guides/privacy/data-collection),
[ZDR guide](https://openrouter.ai/docs/guides/features/zdr), and
[provider routing reference](https://openrouter.ai/docs/guides/routing/provider-selection) for the
current behavior and request fields.

Saved routing values are defaults. An explicit `provider` or `models` field on an
individual request takes precedence for routing choices. The required
`data_collection: "deny"` and `zdr: true` privacy policy remains authoritative.

When OpenRouter returns routing metadata, Ryu stores the billing route (`openrouter`) and the actual
upstream provider (for example, Azure or Google Vertex) separately on the usage transaction. The
upstream provider is left empty when a compatible endpoint does not return routing metadata.

## Prompt caching

OpenRouter can reuse eligible prompt prefixes automatically, while some model families require
explicit cache markers. Ryu-managed Pi agents add those markers for supported models. Cache reads
and writes appear in usage details when the upstream reports them. See
[Provider prompt caching](/docs/providers/prompt-caching) for model behavior, pricing caveats, and
cache visibility.

## Routing

The `openrouter/` prefix is resolved before the Gateway default provider. A specific
OpenRouter model remains on the OpenRouter path even when the node's default provider is local or
OpenAI. Fallback and budget policy still run before the upstream request.

See [Routing](/docs/gateway/routing), [Chat and models](/docs/providers/chat-and-models), and
[BYOK and provider accounts](/docs/providers/byok).
