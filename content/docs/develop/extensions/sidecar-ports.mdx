A manifest sidecar declares one TCP port:

```json
{
  "sidecars": [
    {
      "name": "engine",
      "process": { "kind": "local", "command": "my-engine", "port_env": "MY_ENGINE_PORT" },
      "port": 8321,
      "health_path": "/health"
    }
  ]
}
```

Core uses that number for three things: it tells your process which port to bind, it health-checks
`http://127.0.0.1:<port><health_path>`, and it forwards proxied requests there. All three must
agree, and the way they stay in agreement is that **your process binds the port Core hands it**,
not a constant you compiled in.

This page is only about the port. For the rest of the field, see
[Bundle Runnables with manifest.json](/docs/develop/extensions/plugin-json-manifest#declare-a-managed-sidecar);
for download, spawn, health and reconcile behaviour, see
[App Manifest & Lifecycle](/docs/core/app-manifest-lifecycle#manifest-declared-managed-sidecars).

## Read your port from `port_env`

Name an environment variable in `port_env` and Core sets it on your child process at spawn:

```json
"process": { "kind": "local", "command": "my-engine", "port_env": "MY_ENGINE_PORT" }
```

Your process reads it, and falls back to the declared port only so it stays runnable standalone:

```ts
const PORT = Number.parseInt(process.env.MY_ENGINE_PORT ?? "", 10) || 8321;
app.listen(PORT, "127.0.0.1");
```

```python
port = int(os.environ.get("MY_ENGINE_PORT") or 8321)
uvicorn.run(app, host="127.0.0.1", port=port)
```

<Callout type="warn">
  Bind `127.0.0.1`, never `0.0.0.0`. A sidecar that binds all interfaces is reachable from the
  local network, and Core's proxy is the only intended way in.
</Callout>

### Why the environment wins over the constant

The value Core injects is **not always the number in your manifest**. A node runs under a
*profile*, and every profile but the default shifts every port by a fixed offset - a `dev` node
adds 1000 to everything, so a developer can run a dev build beside a release install without the
two fighting over sockets. Core shifts your sidecar's port the same way it shifts its own.

So on a `dev` node, a manifest that says `8321` is health-checked and proxied on `9321`. A process
that hardcodes `8321` binds a port nobody is watching: Core reports the sidecar unhealthy, the
proxy 502s, and nothing in the error names a port. Reading `port_env` makes that case correct for
free.

The same reasoning covers the future: treat the manifest `port` as *what you would like*, and the
environment as *what you got*. A process written that way keeps working if Core ever assigns the
port itself.

<Callout type="warn">
  `port_env` exists on the `local` and `python` process kinds only, but a `node` sidecar is still
  told its port - it has no `port_env` field because the value arrives under a fixed name,
  `RYU_HOST_PORT`, alongside `RYU_HOST_HEALTH_PATH`. Read that one instead.

  A **`binary`** sidecar is the exception: it is spawned with no port injection at all, so it must
  bind the declared port literally. That is correct on a default-profile node and wrong on every
  other one, because Core still health-checks and proxies the shifted port. If your process reads
  configuration from the environment anyway, that gap is a reason to prefer `local` or `python`; if
  you ship a downloaded executable you have no choice, so test on the profile your users run.
</Callout>

## Choosing a number

There is no port registry, and no allocator: the number in your manifest is the number Core tries.
Pick from the community band.

| Range | Who uses it | Safe for your app? |
| --- | --- | --- |
| `3200`, `7980`, `8000`, `8080`-`8096`, `9070`, `30000` | Core's own substrate - local inference engines, speech, image generation, the workflow runtime, the SDK adapter | No, never |
| `7990`-`8079` | Ryu's first-party apps | No - this band fills up as Ryu ships apps |
| `8300`-`8699` | community | Yes - pick here |

Two things about that band that are easy to get wrong.

**It ends at `8699` because plugins share the space.** App sidecars and plugin sidecars are
allocated from one range, and installed plugins already sit above it - `8787` is taken by a
first-party plugin, and one declares `47821`. There is no separate "plugin ports" region to hide in.

**`8000` is carved out of the first-party band, not spare.** It sits inside `7990`-`8079` but Core's
own inference server binds it, so it belongs to the row above.

Within `8300`-`8699`, avoid round and famous numbers - `8500`, `8443` and the like are crowded by
software that has nothing to do with Ryu. Check the ports of any app or plugin you expect to be
installed next to yours: a neighbour is as likely to collide as Ryu itself.
`GET /api/sidecar/status` lists what is registered on the node you are testing against.

## When the port is already taken

Port numbers are not unique to Ryu. Your user's machine also runs their own software, and nothing
stops a database, a dashboard, or another vendor's agent from binding the number you picked. The
band table above tells you what *Ryu* claims; it cannot tell you what else is on the host.

Core checks before it spawns you. `claim_port` consults its registry of live sidecars and then
bind-probes the port itself, and **fails the start** if either check fails:

```
port 8321 is already claimed by sidecar '@acme/other/engine'
port 8321 is already in use on the host (bind probe failed: …)
```

The first means another Ryu sidecar holds it. The second means anything at all does - another Ryu
sidecar that is a compiled-in built-in, or software Ryu has never heard of.

<Callout type="warn">
  This is detection, not resolution. Core does **not** move your sidecar to a free port, and there
  is no per-app port override a user can set. A collision is an app that will not start, and the
  only place the port is named is that error string.
</Callout>

The failure is quieter than you would expect, in three ways worth designing against:

- **Enabling the app still succeeds.** The sidecar is spawned off the request thread so a slow
  download never blocks enable, so the enable call returns fine and the app reads as on.
- **The sidecar is missing from `GET /api/sidecar/status`, not listed as unhealthy.** A sidecar that
  never cleared the port check is never registered, so it does not appear at all. Code that polls
  status for your sidecar must treat *absent* as a failure state, not as "still starting".
- **Requests are still proxied to that port.** The proxy resolves its target from your manifest
  rather than from whether your process actually started, so `/api/ext/<plugin_id>/*` is forwarded
  to whatever is listening there. You do not get a clean error; you get another program's answers.
  Never assume a response on your own route came from your own process - version or identify it.

Nothing retries, either: the health monitor reports and does not restart, so a sidecar that lost its
port stays down until Core restarts.

So the remedies are all outside the app:

- **Free the port.** Stop whatever holds it. This is the only fix that keeps the declared number.
- **Shift every Ryu port at once** by running the node under a non-default profile - each profile
  offsets the whole set, which resolves a collision against non-Ryu software but moves Core too.
- **Report it to the app author.** A port that collides on many machines is a bad pick, and the fix
  is a new manifest port in the next release.

Design for the failure rather than assuming it away: surface the sidecar's health state in your UI
instead of letting requests hang, so a user whose port is occupied sees a reason.

### The probe cannot be airtight

A bind probe proves the port was free a moment ago, not that it is free when your process binds. The
listener Core opens is dropped immediately so your child can take the port, and another process can
win that gap. If your process can lose the race, exit non-zero on `EADDRINUSE` rather than retrying
in a loop or silently binding something else - a sidecar listening on a port Core is not watching is
reported unhealthy and proxied to a dead socket, which is much harder to diagnose than a clean exit.

Treat the manifest `port` as *what you asked for* and `port_env` as *what you got*. An app written
that way needs no changes if the number it is handed ever stops matching the number it declared.

## Your port is not your public URL

Clients never dial your sidecar. Core exposes it at

```
/api/ext/<plugin_id>/<your route>
```

and proxies through to whatever port your process ended up on. That indirection is what makes a
port change - a profile shift, a reinstall, a future allocator - invisible to every caller. Do not
publish `127.0.0.1:<port>` in your app's own docs or bake it into a companion UI; use the
`/api/ext/` path, which is stable.

The shorter `/api/<name>` mounts you see on Ryu's first-party apps are reserved to built-ins and
registered when Core builds its router, so a third-party app cannot claim one - and does not need
to.

## Checklist

- Declare `port` and `port_env` together.
- Read `port_env` in the process; fall back to the declared port only for standalone runs.
- Bind `127.0.0.1`.
- Serve `health_path` (default `/health`) with a 2xx as soon as you are listening - Core treats
  that as "started".
- Pick from `8300`-`8699`, avoiding round numbers and the ports of apps you ship beside.
- Exit non-zero if the bind fails; never fall back to a different port on your own.
- Point clients at `/api/ext/<plugin_id>/*`, never at the port.
